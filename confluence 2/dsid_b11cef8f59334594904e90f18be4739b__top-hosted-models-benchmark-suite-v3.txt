Top Hosted Models Benchmark Suite v3 (Prompt Sets + Workload Distributions)

## 1. Purpose
This document defines **Benchmark Suite v3** used for performance benchmarking and quality sanity checks across Redwood’s **top hosted models**. The suite is designed for:

- **Kernel comparisons** (FP16/BF16 baseline vs FP8/INT8 variants) under realistic request shapes.
- **End-to-end serving benchmarks** (TTFT/TPOT/throughput) with representative prompt and generation-length distributions.
- **Quantization safety**: a lightweight quality sanity layer to catch obvious regressions (formatting, tool-call validity, long-context behavior).

Suite v3 is explicitly aligned to production traffic patterns observed on the hosted API, while avoiding inclusion of customer-proprietary content.

---

## 2. Scope and non-goals
### In scope
- Chat + instruction following
- RAG-like prompts (retrieval context included)
- Summarization + extraction
- Code generation + edit
- Structured output (JSON schemas)
- Tool-calling style prompts (function arguments)
- Short-form classification/labeling
- Long-context stress cases (prefill-heavy)

### Not in scope (tracked separately)
- Multimodal inputs
- Fine-tuned customer prompts
- Domain-specific evals (legal/medical), unless requested by PM/CS for a specific launch
- Safety/policy compliance scoring (owned by Safety program; can be layered on top)

---

## 3. Design principles
1) **Traffic representativeness**
- Suite composition (workload mix + prompt/generation lengths) approximates the hosted API’s request distribution for top models.
- We intentionally include a small number of “tail” cases (long context, structured output) because they materially impact p95 latency and kernel behavior.

2) **Kernel sensitivity**
- Prompts are chosen to induce common shape regimes that matter for kernels:
  - Small/medium/large prefills
  - Decode lengths spanning short (32–128 tokens) to medium/long (512–1024 tokens)
  - Attention patterns that stress KV-cache and memory bandwidth

3) **Reproducibility**
- Deterministic prompt ordering, stable random seeds for sampling, and explicit versioning.
- Prompts are stored internally with immutable IDs; suite definitions reference IDs and weights.

4) **No customer data**
- Prompts are synthetic or sourced from permissible open datasets and then rewritten/normalized.

---

## 4. Suite composition (workloads)
Suite v3 is split into **six workload groups**. Each benchmark run uses the configured workload mix (Section 5) unless explicitly overridden.

### 4.1 Chat (general assistant)
**Goal:** representative “default chat” traffic (balanced prefill/decode).
- Prompt style: user asks for explanation, brainstorming, or step-by-step guidance.
- Typical system prompt included (short, Redwood-default style).
- Output: natural language.

### 4.2 RAG-style QA (context-in-prompt)
**Goal:** represent retrieval-augmented prompts where the prefill dominates.
- Prompt includes: instruction + question + 1–4 context chunks (1–3k tokens typical).
- Output: short answer + citations-like formatting (not strict).

### 4.3 Summarization + extraction
**Goal:** common enterprise and product workloads; tests long prefill + medium decode.
- Inputs: meeting notes, policy snippets, support ticket-like text (synthetic).
- Outputs:
  - Summaries (bulleted)
  - Key points
  - Extraction (entities, action items)

### 4.4 Code generation + edit
**Goal:** code models and code-heavy prompts stress different token distributions and may shift decode behavior.
- Prompts:
  - Generate a function from a spec
  - Refactor/edit an existing function (input includes code)
  - Fix a bug given failing test description
- Output: code blocks, sometimes multi-file pseudo-structure.

### 4.5 Structured output (JSON)
**Goal:** enforce schema adherence; catches quantization-induced formatting drift.
- Prompts include a schema and strict instructions.
- Output must be valid JSON (no trailing commentary).
- Includes:
  - Simple schema (flat fields)
  - Nested schema (objects + arrays)

### 4.6 Tool-calling (function arguments)
**Goal:** approximate tool-call patterns without relying on any single SDK; measures latency impact and validity of arguments.
- Prompts request selecting a tool and producing a JSON-like argument object.
- Validation checks:
  - Valid JSON
  - Required fields present
  - Basic type checks (string/number/bool/array)

## 5. Workload mix + distributions
### 5.1 High-level workload weights (default)
The default suite mix is weighted to approximate hosted traffic for top models:

- Chat (general): **35%**
- RAG-style QA: **20%**
- Summarization + extraction: **15%**
- Code generation/edit: **10%**
- Structured output (JSON): **10%**
- Tool-calling: **10%**

Rationale: Chat dominates absolute volume; RAG and summarization materially influence capacity planning due to heavier prefills; structured output/tool calling are smaller by volume but high-sensitivity for customer-visible correctness.

### 5.2 Prompt length distribution (approximate)
Prompt lengths are measured as **model tokens after formatting** (system + user + any inserted context).

Default prompt-length buckets:
- **S (short): 64–256 tokens** → 25% of requests
- **M (medium): 256–1,024 tokens** → 45% of requests
- **L (long): 1,024–4,096 tokens** → 25% of requests
- **XL (very long): 4,096–12,288 tokens** → 5% of requests

Notes:
- XL is intentionally small but present to capture long-context TTFT behavior and KV-cache pressure.
- RAG workload draws more heavily from L/XL buckets; chat draws more heavily from S/M.

### 5.3 Generation length distribution
Generation lengths are capped and sampled per request. Default decode buckets:
- **32–128 tokens** → 40%
- **128–384 tokens** → 35%
- **384–768 tokens** → 20%
- **768–1,024 tokens** → 5%

Rationale: Many hosted applications are short/medium responses; the long tail exists and matters for TPOT and sustained throughput.

### 5.4 Prefill vs decode emphasis (why kernels care)
We categorize suite cases by **prefill-heavy** vs **decode-heavy** shapes:
- Prefill-heavy (RAG, long summarization): drives TTFT and attention/matmul prefill kernels.
- Decode-heavy (short prompts, long generation): drives TPOT and decode attention kernels, KV-cache access, and launch overhead.

In Suite v3, approximately **55–65% of total compute time** (not request count) is prefill, depending on model and batching configuration.

## 6. Prompt sets (what’s inside)
### 6.1 Prompt library structure
Suite v3 references prompt IDs from the internal prompt library:
- Namespace: `aml_eval_prompts/hosted_suite/v3/`
- Each prompt has:
  - `prompt_id` (immutable)
  - `workload_group` (Section 4)
  - `length_bucket` target (S/M/L/XL)
  - `language` (mostly English; small multilingual slice)
  - `format_requirements` (none/json/tool)
  - `safety_notes` (if any)

### 6.2 Multilingual slice
A small multilingual slice is included to reflect production usage without dominating the suite:
- **5%** of requests are non-English:
  - Spanish (2%)
  - French (1%)
  - German (1%)
  - Japanese (1%)

This slice is primarily in Chat + Summarization groups.

### 6.3 Redaction and licensing
- No customer text.
- Sources are synthetic or derived from permissive corpora; rewritten where needed.
- Any prompt containing “realistic ticket/customer” patterns is fully synthetic.

## 7. Structured-output and tool-calling variants
### 7.1 Structured JSON tasks
Two levels are used:

**JSON-Simple** (approx. half of structured-output cases)
- 6–10 fields
- Mostly strings + integers
- Example use cases: extraction, metadata normalization

**JSON-Nested** (approx. half)
- Arrays of objects, nested structures
- Example use cases: itinerary planning, task breakdowns, RAG citation objects

Validation rules:
- Must parse as JSON
- Must contain required keys
- No extra keys when `additionalProperties=false` (where defined)

### 7.2 Tool-calling tasks
Tool calls are represented as “produce the arguments for tool X” prompts, where tool X is described in the prompt.

Tool set (representative):
- `search_documents(query, top_k, filters)`
- `create_ticket(title, description, severity, tags)`
- `schedule_meeting(attendees, start_time, duration_minutes, agenda)`

Validation rules:
- Valid JSON
- Required fields present
- Simple type checks

Why this is included in perf benchmarking:
- Tool calling is sensitive to **formatting and small-token probabilities** (quantization can cause increased invalid JSON rates).
- These cases are often latency-sensitive in production because they block downstream actions.

## 8. How the suite is used in benchmarking
### 8.1 Benchmark modes
Suite v3 supports two primary modes:

1) **E2E Serving Mode (recommended for sprint decisions)**
- Runs through the serving stack with realistic scheduler behavior.
- Captures TTFT, TPOT, tokens/sec, queueing, and error rates.

2) **Microbench Assist Mode (kernel shape coverage)**
- Uses extracted shapes from Suite v3 tokenization to drive targeted matmul/attention microbenches.
- Used to explain wins/regressions seen in E2E.

### 8.2 Standard run parameters (defaults)
Unless a methodology page overrides, use:
- Temperature: 0.0 for structured output/tool calling; 0.2 for chat-style tasks
- Top_p: 1.0
- Frequency/presence penalty: 0
- Stop sequences: workload-specific (JSON/tool modes enforce strict stops)
- Streaming: enabled for E2E mode where applicable (TTFT is primary metric)

### 8.3 Concurrency and batching
The suite is designed to be executed under multiple load points (owned by runtime benchmarking methodology). Suite v3 itself provides the **request shape distribution**; scheduling tests should vary:
- concurrency (e.g., 1, 8, 32)
- batching windows
- prefill/decode mixing policy

## 9. Quality sanity checks (minimum required)
Suite v3 includes lightweight checks to detect obvious regressions when enabling FP8/INT8.

Required checks by workload:
- Chat/RAG/Summarization/Code: heuristic checks (non-empty, no repeated garbage, length sanity) + spot-check sampling
- Structured JSON: strict JSON parse + schema validation
- Tool-calling: strict JSON parse + required fields/type checks

Minimum acceptance guidelines (for default enablement proposals):
- JSON validity rate: **>= 99.5%** on JSON tasks
- Tool-arg validity rate: **>= 99.0%** on tool tasks
- No new systematic failure mode (e.g., truncation, invalid unicode, persistent repetition) in spot-check sample

Any proposed default change (FP8/INT8) must also comply with the quantization policy sign-off criteria.

## 10. Versioning, change control, and auditability
### 10.1 Versioning rules
- Suite version is `vMAJOR.MINOR` (this doc is v3; minor bumps allowed for prompt additions/removals without rebalancing weights).
- Any change that affects distributions (weights, length buckets, multilingual %) requires a **MINOR bump** and explicit rationale.
- Any substantial redesign requires a **MAJOR bump**.

## 11. Rationale: why this matches production traffic
Suite v3 matches production behavior because:
- It reproduces the dominant workload classes (chat + RAG + summarization) and includes smaller but high-impact classes (structured output/tool calling).
- The prompt-length and generation-length distributions approximate observed hosted traffic shape regimes, including long-context tail cases that influence p95 and kernel selection.
- It covers both prefill-heavy and decode-heavy regimes, which is necessary to make correct decisions about kernel auto-selection and scheduler tuning.
- It includes strict formatting tasks to catch the failure modes most likely to become customer-visible during quantized rollouts.

Known limitations:
- True customer prompt diversity is broader than any fixed suite; this is a representative benchmark, not a guarantee.
- Some domains (highly technical, regulated) are underrepresented; request an add-on suite if needed for a specific customer/launch.
