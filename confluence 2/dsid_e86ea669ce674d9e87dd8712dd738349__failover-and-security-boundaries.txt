Failover and Security Boundaries (Data Residency, Audit Logging, and Cross-Region Routing)

## Purpose
This document defines **security boundaries that must be preserved during regional failover** for Redwood Inference (Hosted API and Dedicated). It specifies:
- How **data residency constraints** restrict routing/failover.
- **Audit logging** requirements for automated and manual failover actions.
- Guardrails for **cross-region routing** by customer tier (especially Enterprise and regulated workloads).

This guidance is mandatory for:
- Smart routing and policy engine changes that can influence region selection.
- Failover automation controller behavior (including dry-run and simulation modes).
- On-call execution and controlled failover tests ("game days").

## Scope / Non-scope
**In scope**
- Hosted API and Dedicated failover behavior across Redwood-managed regions.
- Data residency enforcement at routing and control-plane policy layers.
- Audit events, retention, and access control for failover decisioning.

**Out of scope**
- Customer-specific Private deployment automation (see Private guidance). This doc provides patterns only.
- Changes to customer contracts/SLA language (handled separately).

## Definitions
- **Region**: A cloud provider region (e.g., us-east, eu-west).
- **Residency boundary**: The allowed set of regions in which a tenant’s **inference data plane** traffic may be processed.
- **Data plane**: Prompts, model inputs, outputs, embeddings, and tool/function payloads processed by inference.
- **Control plane**: Tenant metadata, config, quotas, routing policy config, and operational telemetry.
- **Failover**: Automatic or operator-approved routing change that shifts traffic from a primary region to another region.
- **Enterprise tier**: Contracted customers with security requirements (auditability, residency, notification expectations).

## Security principles (must-haves)
1) **Residency first**: If a tenant has a residency constraint, failover MUST stay within that boundary. Availability must be achieved *within* the allowed set; otherwise we prefer **graceful degradation** (e.g., 503 + Retry-After) over violating residency.
2) **Explicit allow-listing**: Cross-region routing must be controlled by explicit configuration per tenant (or per org) and audited.
3) **Least privilege and separation of duties**: Only designated on-call/SRE roles may initiate or approve production failover actions. Changes to residency boundaries require Security approval.
4) **Audit everything**: Every recommendation, execution, rollback, and override must emit a structured audit event with enough evidence to reconstruct “who/what/why/when/impact.”
5) **Deterministic policy evaluation**: Given the same inputs, routing policy evaluation must produce the same output (to enable security review, auditability, and predictable enforcement).

## Data residency policy
### Residency categories
Redwood supports the following residency categories for the **inference data plane** (prompts/outputs/embeddings):

| Category | Description | Example allowed regions | Example prohibited regions |
|---|---|---|---|
| Global (no residency) | Tenant allows processing in any supported region | us-east, us-west, eu-west, ap-southeast | none |
| US-only | Processing restricted to US regions | us-east, us-west | eu-west |
| EU-only | Processing restricted to EU regions | eu-west, eu-central | us-east |
| Region-pinned | Processing restricted to a single region | eu-west only | all others |
| Custom boundary | Contract-defined set | (explicit per tenant) | all non-listed |

Notes:
- Residency applies to **data plane processing**. Control-plane metadata may be replicated as needed for availability, but must follow the data classification and storage policies in Security standards.
- Region naming above is conceptual; the authoritative list is in routing config.

### Default behavior by tier
- **Self-serve / Standard Hosted**: Default category is **Global**, unless the tenant explicitly configures otherwise.
- **Enterprise Hosted**: Default category is **Global**, but residency constraints may be contractually required (EU-only, US-only, or Custom boundary). These constraints MUST be encoded as enforceable routing policies.
- **Dedicated**: Default category follows the contracted deployment footprint. Failover is restricted to the customer’s approved Dedicated regions.
- **Private**: Residency enforcement is the customer’s responsibility, but Redwood-provided guidance should mirror the principles in this document.

## Cross-region failover rules
### Hard rules (never violate)
1) **Do not route data plane traffic outside the tenant’s residency boundary.**
2) **Do not “temporarily” violate residency to restore availability.** If no in-boundary failover target is healthy, degrade service within the boundary.
3) **Do not change residency boundaries during an incident** to work around a capacity/regional outage unless:
   - Approved by Security (delegate on-call) AND
   - Approved by the customer (if Enterprise/regulated) AND
   - Documented in an incident timeline with explicit timestamps and scope.

### Allowed failover patterns
- **Within-boundary failover** (preferred):
  - EU-only: eu-west → eu-central
  - US-only: us-east → us-west
  - Custom: primary → secondary (both explicitly allow-listed)
- **Region-pinned tenants**:
  - No cross-region failover. Use load shedding and communicate impairment.

### Decision hierarchy interaction (security perspective)
Routing may decide to fail over due to reachability, 5xx burn, tail latency burn, or capacity exhaustion; however:
- The policy engine MUST apply **residency gating as an absolute precondition** before evaluating “best” region.
- If the “best available” region is outside boundary, the decision must become **DEGRADE** (or keep traffic in-region with protective measures), not “fail over.”

## Implementation requirements (routing, controller, and configs)
### Residency gating in the policy engine
The policy engine must support a first-class predicate (conceptual):
- `allowed_regions(tenant_id)` returns a stable allow-list.
- Region selection must be `candidate_regions = healthy_regions ∩ allowed_regions`.
- If `candidate_regions` is empty, policy result must be one of:
  - `DEGRADE_WITHIN_BOUNDARY` (e.g., return 503/429 with Retry-After, reduce max tokens, disable optional features), or
  - `STAY_PUT_WITH_PROTECTION` (tight circuit breakers and load shedding), depending on product behavior.

Security requirement: the code path must be **provably non-bypassable** (no “emergency override” without producing an audit event and requiring explicit approvals).

### Configuration source of truth
For Hosted and Dedicated:
- Residency boundary configuration must be stored in a **controlled configuration system** with:
  - Change review (required reviewers include Security for any boundary-tightening/loosening).
  - Immutable change history.
  - Rollback support.

### Dedicated-specific constraints
Dedicated customers may have:
- Hard region allow-lists bound to capacity pools.
- Explicit “no failover without approval” requirements.

Failover automation for Dedicated must:
- Respect pool-level constraints (do not shift load to a pool not designated for that tenant).
- Coordinate with drain/evacuation procedures without exposing cross-tenant data.

## Audit logging requirements
### What must be logged
All systems participating in failover must emit structured events for:
- Recommendation (dry-run computation)
- Execution (policy flip applied)
- Rollback (automated or manual)
- Override (operator forcing a decision)
- Blocked action (attempted failover rejected due to residency boundary)

### Required fields (minimum)
Each audit event must include (as applicable):
- **event_type**: recommend | execute | rollback | override | blocked
- **timestamp_utc**
- **tenant_id / org_id** (or an internal stable identifier)
- **tenant_tier**: self_serve | enterprise | dedicated
- **residency_category**: global | us_only | eu_only | region_pinned | custom
- **primary_region**, **target_region** (target may be empty for blocked/degrade)
- **decision**: failover | degrade | stay_put
- **reason_code**: reachability | error_burn | latency_burn | capacity | manual
- **evidence_refs**: links/IDs to region health snapshots, burn-rate alert IDs, probe runs
- **actor**: automation_controller | user:<id>
- **approval_state**: not_required | pending | approved | denied
- **change_id**: routing policy config revision / feature flag revision
- **correlation_ids**: incident_id (if any), request_id samples (optional), dashboard annotation ID

### Retention and access
- Default retention (internal): **180 days** for audit events.
- Enterprise add-on / compliance packages: **≥ 400 days** retention, unless otherwise specified.
- Access must be restricted to:
  - SRE on-call and routing/control-plane engineers with an operational need
  - Security & compliance for audits and investigations
  - Customer Success only via approved exports/redactions (no raw prompt data)

### Data minimization
Audit events must not include:
- Prompt text, model outputs, embeddings, or customer payloads.
- Customer secrets (API keys, tokens).

If request samples are needed for investigation, use approved secure logging mechanisms and follow incident response data handling procedures.

## Handling of regulated / data-residency constrained customers
### If a region impairment occurs within a constrained boundary
Example: EU-only customer and eu-west is impaired.
- If eu-central is healthy and has capacity: **fail over to eu-central**.
- If no EU region is healthy/capable: **degrade within EU**.
  - Return 503 + Retry-After (preferred for overload)
  - Enforce stricter rate limits / max tokens for fairness
  - Disable non-essential optional features if supported by product policy

### Communication expectations (Enterprise)
- During a real incident: follow the Regional Failover Communication Playbook.
- For planned tests: notify only customers whose traffic might be impacted, and explicitly state that residency boundaries will not be violated.
- If any customer perceives cross-region behavior, immediately:
  - Pull audit events for the tenant
  - Validate residency gating decisions
  - Engage Security and Support escalation

## Controlled failover tests (“game days”) security requirements
Prior to production tests:
1) Confirm residency gating is active and validated in staging.
2) Explicitly exclude region-pinned and regulated tenants unless written approval is obtained.
3) Ensure audit events and dashboard annotations are functioning.
4) Validate that “blocked due to residency” is observable (metric + audit event).

During the test:
- Any attempted out-of-boundary action must be treated as a **SEV-2 security incident** if it results in data plane processing outside the boundary.

After the test:
- Export the audit event summary for the test window and attach it to the game day results doc.

## Operational checklist (on-call)
When failover automation suggests a policy change:
1) Identify tenant tier and residency category.
2) Confirm proposed target region is in allow-list.
3) Confirm automation approval requirements (some Enterprise/Dedicated tenants require ack).
4) Verify audit event emission is healthy (controller + policy engine).
5) Execute or approve.
6) If boundary prevents failover, choose degrade/stay-put path and update incident comms accordingly.

## Examples
### Example A: Enterprise EU-only tenant during us-east incident
- Primary region: us-east (should not happen for EU-only; indicates misconfiguration)
- Required action:
  - Immediately block and correct routing policy (within incident change management)
  - File Security follow-up for residency misconfiguration
  - Confirm no data plane processing occurred outside EU via audit/telemetry

### Example B: Global tenant during eu-west reachability failure
- Primary: eu-west
- Allowed: any region
- Action: fail over to us-east (or nearest healthy region by policy), emit audit events for recommend + execute + any rollback.

### Example C: Region-pinned tenant when region is impaired
- Primary: eu-west
- Allowed: eu-west only
- Action: do not fail over. Enable protective controls (circuit breakers, load shedding), return Retry-After, and communicate impact.

## Monitoring requirements (security-relevant)
Minimum dashboards/alerts needed:
- Count of `failover_blocked_due_to_residency` by tier
- Audit event delivery health (ingest lag, drop rate)
- Unauthorized/rare overrides (manual force actions)
- Drift detection: tenants with residency=EU-only receiving any non-EU routing decisions (should be zero)
