Kernel Selection Determinism and Telemetry Standards

h1. Standard: Kernel Selection Determinism and Telemetry (PERF-STD-014)

This standard defines:
* Determinism and replayability requirements for *kernel selection* decisions in the Serving Runtime.
* Required telemetry fields to make selection decisions explainable and debuggable at scale.
* Performance regression gating requirements for selector changes and new kernel mappings.

These requirements apply to the kernel auto-selection module (v1, v2, and future versions) and any control-plane policy/gate that influences which kernel is chosen.

h2. Scope

In scope:
* Selector decision logic (candidate generation + scoring/rules + tie-breaking)
* Feature extraction used by the selector (model family/arch tags, sequence length regime, GPU SKU, driver/CUDA, quantization profile, etc.)
* Fallback logic and denylist/allowlist evaluation
* Runtime configuration that changes selector behavior (feature gates, overrides, per-model policy)
* Telemetry emitted for per-request selection decisions

Out of scope:
* General request tracing standards not specific to kernel selection
* Model quality/eval telemetry (covered by separate eval standards)

h2. Definitions

* *Kernel selection*: choosing an execution kernel implementation/config for an inference request (e.g., attention kernel variant, fused kernels, prefill vs decode tuned paths).
* *Determinism*: given an identical set of inputs, the selector produces the same decision.
* *Replayability*: the selection decision can be reproduced offline (or in a debug environment) using the recorded inputs and selector version.
* *Selection event*: telemetry emitted when a selection decision is made, containing fields defined below.
* *Gate*: runtime or control-plane condition that enables/disables selector versions or specific kernels (e.g., v2 enablement, driver guardrails, denylist rules).

h2. Determinism requirements

h3. D1. Inputs must be explicit and complete
The selector MUST depend only on an explicit input set ("selection context") and MUST NOT consult implicit process-local state that changes nondeterministically.

The selection context MUST include, at minimum:
* Model identity and serving variant (model_id, model_version, quantization profile)
* Workload regime signals (prompt/prefill length bucket, decode length bucket or target, and whether the request is prefill-only vs streaming decode)
* Hardware identity (GPU SKU normalized), plus driver/CUDA/runtime build identifiers
* Selector configuration (selector version, config hash, enabled flags, and applicable allowlist/denylist ruleset version)

h3. D2. Stable ordering and tie-breaking
If multiple candidates are equivalent by score/rules, the selector MUST choose deterministically by a documented tie-break order.

Requirements:
* Candidate lists MUST be sorted deterministically (e.g., by kernel_id then config_id) before evaluation.
* Tie-breaks MUST be stable across runs and machines (no iteration over hash maps without sorting).
* If randomness is required for experimentation, it MUST be:
  * Disabled by default for production.
  * Controlled by an explicit seed in the selection context.
  * Logged in telemetry (seed + experiment_id).

h3. D3. No time-based or load-based branching
Selection MUST NOT branch on wall-clock time, system load, or other ephemeral signals unless:
* The signal is explicitly part of the selection context AND
* The behavior is documented AND
* Replay tooling can supply the same value.

(Note: scheduler-provided *workload hints* are allowed if they are explicitly passed in the context and logged.)

h3. D4. Versioning and compatibility
The selector MUST expose a *selector_version* and a *schema_version* for its telemetry payload.

When selector logic changes:
* Increment selector_version (semantic versioning recommended: major.minor.patch).
* If telemetry semantics change, increment schema_version.
* Maintain backward compatibility for offline replay for at least 2 minor versions, or provide a documented migration tool.

h3. D5. Deterministic replay tests (CI)
Every selector change MUST include deterministic replay tests that assert:
* Given identical selection contexts, the chosen kernel_id/config_id is identical.
* Candidate sets (post-filtering) are identical.
* The decision path (rule hits / score components) is identical.

Minimum requirement:
* A fixed suite of replay fixtures covering: 2+ model families, 3+ seq buckets (short/medium/long context), and 2+ GPU SKUs.

h2. Replayability requirements

h3. R1. Minimum data for offline reproduction
To reproduce a decision, the recorded event MUST be sufficient to reconstruct:
* The selection context
* The set of candidates considered (or a reproducible method to generate it)
* The final chosen kernel and the reason

At minimum, record:
* selector_version, schema_version
* features (model_family, seq buckets, gpu_sku_norm, driver/cuda, quantization profile)
* candidate list (or candidate_set_hash + a registry_version that can regenerate it)
* chosen kernel_id/config_id
* filters/fallbacks applied (denylist hit, missing kernel, unstable SKU guardrail, etc.)
* configuration provenance (gate state + config hash)

h3. R2. Trace correlation
Selection events MUST be correlatable to request traces and aggregated metrics.

Requirements:
* Include trace_id and span_id when available.
* Include a stable request_id (internal) for joining with runtime logs.
* Include model_route and region/cluster identifiers for fleet-level analysis.

h3. R3. PII and prompt safety
Selection telemetry MUST NOT include raw prompts or user content.

Allowed:
* Token counts, sequence buckets, and coarse distribution stats.
Disallowed:
* Prompt text, tool arguments containing user content, user identifiers beyond a pseudonymous internal customer_id.

h2. Required telemetry fields (per-request selection event)

All fields below are REQUIRED unless marked OPTIONAL. Fields may be emitted as structured logs and/or spans/events in tracing.

h3. Event naming
* Event name: kernel_selection.decision
* Category: runtime.performance

h3. Sequence bucket definitions (standard)
Buckets MUST be consistent across runtime and perf tooling. Unless explicitly overridden for a model family, use:
* prefill short: 0–512 input tokens
* prefill med: 513–2,048 input tokens
* prefill long: 2,049–8,192 input tokens
* prefill xlong: 8,193+ input tokens

Decode buckets (target/new tokens) recommended:
* decode short: 0–128
* decode med: 129–512
* decode long: 513+

If a model uses different context window semantics, map into these buckets and record the raw counts only as integers (no text).

h2. Telemetry overhead and cardinality controls

h3. Sampling
Because per-request decision telemetry can be high volume, sampling is REQUIRED.

Default policy (can be tightened for incidents):
* Hosted: 1% sampled globally, with burst to 10% during active canaries.
* Dedicated: 5% sampled for allowlisted pools during rollout, 1% after GA.
* Private: default off unless customer enables; if enabled, 1% with local retention.

Sampling policy MUST be recorded in sampling_rate.

h3. Field length limits
To protect logging pipelines:
* decision_path MUST be <= 512 bytes.
* candidate_kernels MUST be <= 1,024 bytes (use compact encoding or hash if needed).
* workload_hint_summary MUST be <= 128 bytes.

If truncation occurs, set decision_reason to include "truncated" and include candidate_count.

h3. Cardinality rules
To avoid high-cardinality explosions:
* cluster MUST be from a controlled vocabulary (pool ids), not pod names.
* model_version should be a stable serving version, not a per-build artifact id.
* denylist_rule_id/allowlist_rule_id MUST be stable identifiers, not free-form text.

h2. Performance regression gating requirements

These gates apply to:
* Any selector logic change
* Any new kernel mapping by GPU SKU
* Any change to fallback precedence or denylist defaults

h3. G1. Required benchmark coverage
Before enabling a selector change beyond internal dev environments, teams MUST run the perf suite across:
* At least 3 model families relevant to production traffic (e.g., Llama, Mistral, Qwen/Gemma)
* At least 3 seq regimes (short, med, long/xlong)
* At least 2 GPU SKUs (one data-center, one cost-optimized SKU if applicable)

h3. G2. Pass/fail thresholds (default)
Unless an exception is granted by Runtime Architecture + SRE, the following thresholds apply.

Metrics are compared v2 vs v1 (or change vs baseline) per {model_family, model_id, gpu_sku_norm, seq_bucket_prefill, seq_bucket_decode}:

* p95 latency: must not regress by > 3% for any bucket
* p99 latency: must not regress by > 5% for any bucket
* Throughput (tokens/sec at steady state): must not regress by > 2% for any bucket
* Error rate attributable to kernel execution: must not increase by > 0.05% absolute

Any single bucket breach is a FAIL unless:
* The bucket is explicitly excluded in the rollout allowlist, AND
* An issue is filed with owner and mitigation plan, AND
* Dedicated/Private guidance is updated to avoid the bucket/SKU combo.

h3. G3. Canary requirements
For canary rollout:
* Run v1 and v2 in parallel cohorts where possible.
* Monitor for at least one full traffic cycle (minimum 24 hours) OR 2x the longest expected workload cycle for dedicated customers.

Canary success criteria:
* No sustained p99 regression > 3% at the fleet level for any top-10 model routes
* No increase in kernel-related error rate beyond error budget policy
* Selection distribution stable (no unexplained drift in chosen_kernel_id shares > 10% day-over-day, excluding planned policy changes)

Rollback triggers (recommended defaults):
* p99 latency regression >= 8% for 15 minutes on any top-5 model route within a region
* Kernel error spike >= 0.2% absolute for 5 minutes
* Widespread denylist/fallback activation (fallback_level=hard/emergency) >= 1% of sampled events

h3. G4. SLO/error budget coordination
Selector rollouts are considered *performance-impacting changes*.

Requirements:
* SRE MUST approve alert threshold changes prior to canary.
* Error budget burn MUST be monitored for the canary cohort separately when possible.
* If rollback is initiated, retain selection telemetry at elevated sampling for 2 hours post-rollback to confirm recovery and diagnose.

h2. Operational requirements for overrides

To support oncall and customer escalations:
* Manual pinning of kernel choice MUST be possible at least by model_id + gpu_sku_norm + region/cluster.
* Overrides MUST be auditable and show up in telemetry (override_type, override_id).
* Overrides MUST have safe defaults and an expiration mechanism (time-based or explicit removal procedure).

h2. Exceptions

Any exception to this standard (telemetry omissions, determinism relaxation, threshold changes) requires:
* Documented rationale
* Risk assessment (tail latency + correctness)
* Explicit owner and expiration date
* Approval from Runtime Architecture (Noah Patel or delegate) and SRE (Aisha Bello or delegate)
