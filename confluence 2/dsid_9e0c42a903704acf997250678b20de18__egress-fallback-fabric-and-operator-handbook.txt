Egress Fallback Fabric — Operator Handbook

Summary:

This document describes the Egress Fallback Fabric: an operational pattern and Terraform/IaC modules used to implement deterministic, auditable failover of tenant egress traffic when primary egress paths degrade. It combines network topology primitives (NAT pools, privateLink/VPN fallbacks, BGP advertisements), an orchestration service (egress-orchestrator), and a small operator-facing edge-proxy to enable rapid, reversible reroutes for GPU/Inference workloads across accounts and regions.

Goals:
- Maintain tenant SLAs when primary egress (Direct Connect/Transit Gateway) becomes unavailable or expensive.
- Provide a minimal-privilege, auditable operator workflow to perform rapid failover and rollback.
- Ship reusable Terraform modules for the fabric and CI/CD checks that validate routing changes before promotion.

Scope:
- Applies to production GPU inference clusters (both hosted and Dedicated) and their control-plane APIs.
- Does NOT replace long-term network design; intended as a controlled emergency and scheduled-fallback mechanism.

Architecture overview:
- Egress Fabric components:
  - egress-orchestrator: central control-plane service (k8s deployment) that stores policy, calculates fallback paths, and triggers IaC changes through a gated pipeline.
  - edge-proxy: lightweight sidecar / edge node that rewrites next-hop and performs health checks to validate path integrity.
  - nat-pool-manager: Terraform-managed NAT gateways and elastic IP pools per-region per-account.
  - bgp-advertiser: optional component that announces fallback prefixes into partner networks using a dedicated BGP session.
  - egress-audit-log: centralized logging (CloudWatch/Stackdriver -> S3/Long-term store) capturing operator actions, Terraform plan outputs, and orchestration decisions.

Diagram (text):
- region-a: primary Transit Gateway -> Tenant VPC -> GPU cluster
- region-a fallback: edge-proxy -> NAT-pool-A -> BGP-advertiser -> partner-net
- controller: egress-orchestrator (global) -> triggers terraform apply to tagged nat-pool module

CI/CD and gating requirements:
- All terraform changes must pass: `tf validate`, `tf plan` against a staging account, and the egress-orchestrator integration test suite.
- Pipeline blocks (manual approval) when changes include: adding new BGP sessions, modifying allowed_prefixes, or increasing nat_pool_size > 4.
- Commit hooks: `pre-commit` checks for module version pinning and policy-as-code (OPA) rules verifying least-privilege IAM.

Runbook: Triage & emergency failover (ordered):
1. Detect & confirm: Verify alerted symptoms (latency/egress errors) using dashboards: egress-latency, nat-health, bgp-sessions.
2. Evaluate scope: Which tenants (tenant tags) are affected? Check `egress-orchestrator` incident view.
3. Safety checks (do NOT run apply if any fail):
   - Is there an ongoing Terraform apply initiated by another operator? If yes, coordinate in Slack and wait for completion.
   - Is the planned fallback address space free of conflicting advertisements? Run `./scripts/check-prefix-collisions.sh <prefix>`
4. Initiate fallback (operator-only):
   - Update the egress-orchestrator incident with intended action and link to the TF plan.
   - Run `make plan-target TENANT=tenant-123 ENV=staging` and validate the plan output in the CI job.
   - Promote to `apply` using the pipeline UI with an approval note. The pipeline will run `tf apply` in a restricted service account and return the plan artifact.
5. Verify path and canary:
   - Run `kubectl -n infra exec -it $(kubectl get pod -l app=edge-proxy -o name | head -n1) -- /bin/sh -c "curl -sS http://metadata/fallback-check?tenant=tenant-123"`
   - Verify remote endpoint path via `tcptraceroute` and `bgp-sessions` dashboard shows the announced prefix.
6. Monitor: watch egress-audit-log for errors and token-level request latencies for 10m.
7. Rollback if instability: Use pipeline rollback button which applies the prior plan (pipeline stores last-known-good plan).

Emergency rapid reroute checklist (short):
- [ ] Confirm owner oncall present and Slack channel created (#egress-incident).
- [ ] Ensure audit logging is enabled and S3 write OK.

- [ ] Confirm billing tagging is present for post-incident reconciliation.

Change window, rollout and rollback:
- Changes to the fabric must be deployed during a pre-approved change window unless the change is marked emergency by a product SRE manager. For scheduled changes: canary rollout to 5% of tenants in staging -> canary to 1 region in prod -> global promotion after 48h stability.
- Rollback: use pipeline stored plan artifacts or run `make rollback TARGET_PLAN_ID=<id>` which will reapply the stored plan from the previous stable state.

Testing plan and CI checks:
- Unit tests: module outputs and variable schema checks (run `go test` / `pytest` in module repo).
- Integration tests: ephemeral tenant created in staging, egress simulated failure using BGP withdraw script, pipeline should detect and provision fallback.
- Chaos tests: monthly scheduled chaos job that simulates Transit Gateway outage and verifies fallback completes within SLO.

Known limitations & caveats:
- BGP advertising requires partner support; in some cloud providers we only have NAT fallback which increases latency and egress costs.
- IPv6 fallback is not yet supported by module v1.4.0.
- Terraform applies are asynchronous; the plan ID must always be recorded for safe rollback.

Operational run cadence and playbooks:
- Weekly: review nat-pool utilization and rotate elastic IPs older than 90 days.
- Monthly: run the chaos test and validate egress-orchestrator metrics.
- Quarterly: update OPA policies for new IAM principals and verify pipeline gates.

FAQ (short):
Q: When should I use BGP vs NAT fallback?
A: Prefer BGP when you need short path latency and traffic steering. Use NAT-only when partner BGP is unavailable or for short-lived emergency usage.
