Tenant Egress Capacity Kit — Terraform patterns and chargeback projection

Overview

This document defines the Tenant Egress Capacity Kit: a collection of Terraform patterns, CI/CD checks, and small runtime adapters that standardize how tenant egress capacity (egress bandwidth and NAT/IP pool allocation) is provisioned, monitored, and charged back for GPU-backed inference workloads. The goal is to provide a repeatable IaC pattern teams can adopt to avoid ad-hoc egress provisioning, reduce unbounded egress costs, and enable transparent tenant chargeback.

Why this exists

- Problem: GPU inference tenants have unpredictable egress profiles (batch evals, streaming responses, model downloads), producing surprise bills and noisy-neighbor network contention.
- Goal: Provide a Terraform-first kit that encodes capacity budgeting, guardrails, and chargeback telemetry while integrating with existing GPU allocation modules.
- Non-goals: This kit does not replace tenant-level application-layer throttling or billing ingestion pipelines; it produces the egress surface and meter points required by billing teams.

Scope and audience

- Primary audience: Infra and platform engineers responsible for tenant onboarding, Cloud Networking, and GPU fleet capacity planners.
- Secondary audience: Finance/FinOps (chargeback inputs), SRE (alerting), and Product (quota SLAs).
- Covered clouds: AWS (NAT/SG/ENI) and GCP (Cloud NAT, IP allocation). Azure patterns are listed as adapters.

High-level design

1. Terraform module family
   - tenant_egress_budget (root module): declares expected egress band, NAT IP reservation, and tenant egress class (low/standard/high). Produces labels and tags consumed by downstream modules.
   - egress_shaper_policy (optional): generates network policy objects (VPC-level or CNI annotations) for rate-limiting and routing to shared proxies.
   - egress_billing_exporter (sidecar): small lambda/container pipeline that subscribes to VPC flow logs and emits tenant-tagged sampling metrics to billing Kafka.

2. Runtime adapters
   - NAT reservation adapter: maps tenant class to NAT IP pools and attaches routes with failover priorities.
   - Egress telemetry shim: adds tenant_id labels to flow logs and exports summarized 1m/5m metrics.

3. CI/CD and validation
   - Terraform plan/time-bound approvals for increases > X GiB/day.
   - Static checks: module version pinning, var defaults, tagging enforcement.
   - Unit/integration tests: terratest suites that assert IP counts and route tables in a sandbox account.

Detailed Terraform schema (summary)

Use the following as the recommended interface for tenant_egress_budget. Teams should import this module rather than copy it.

| Variable | Type | Default | Description | Allowed values / notes |
|---|---|---|---|---|
| tenant_id | string |  | Unique tenant identifier (tenant-xxxxx) | required |
| egress_class | string | "standard" | Capacity class | low | standard | high |
| daily_egress_gib | number | 10 | Expected daily egress in GiB | used for billing forecast |
| nat_ip_count | number | 1 | Number of NAT/Gateway IP addresses to reserve | computed from class if omitted |
| allow_burst | bool | true | Permit short bursts beyond daily estimate | triggers autoscaling policy if true |
| cost_center | string |  | Finance chargeback code | optional but recommended |

| Output | Type | Description |
|---|---|---|
| tenant_tags | map(string) | Terraform tags to attach to all resources (tenant_id, egress_class, cost_center) |
| billing_dataset_exporter | string | ARN/URL of the exporter consuming flow logs |

Example usage (AWS)

terraform
module "tenant_egress_budget_alpha" {
  source           = "git::ssh://git.company.com/infra/terraform-modules.git//tenant_egress_budget?ref=v1.2.0"
  tenant_id        = "tenant-alpha"
  egress_class     = "standard"
  daily_egress_gib = 25
  cost_center      = "prod-ai-42"
}

# attach NAT pool (reusable module)
module "tenant_alpha_nat" {
  source     = "git::ssh://git.company.com/infra/terraform-modules.git//nat-reservation"
  tenant_tags = module.tenant_egress_budget_alpha.tenant_tags
  ip_count   = 2
}

Rollout and migration procedure (recommended)

1. Sandbox testing (team infra account)
   - Apply module in sandbox with a fake tenant_id and enable terratest. Verify outputs: expected IPs, tags, and billing exporter registration.
2. Canary tenants (<= 5 tenants)
   - Migrate low-impact tenants to use module-managed NAT and enable exporters. Observe flow logs for 48–72 hours.
3. Gradual migration
   - Enable monthly batches of tenants for migration using automation. Set conservative daily_egress_gib and allow_burst=false for initial 2 weeks.
4. Full enforcement
   - After a run-in period, enable CI gating to block tenant NAT increases without finance OK.

Operational runbook (responding to egress surprises)

1. Alerting thresholds
   - warn_egress_high: tenant > 2x daily_egress_gib for 30m -> P1 notification to tenant-owner channel.
   - critical_egress_overrun: tenant > 4x daily_egress_gib for 15m -> Pager to infra oncall.
   - nat_ip_exhaustion: remaining global NAT IP pool < 10% -> Pager and auto-throttle new tenant allocations.

2. Investigation steps (order)
   1. Confirm tenant tags in VPC flow logs via logging console.
   2. Use the billing_exporter UI to query 1m-sampled egress distribution.
   3. If caused by eval or CI job, temporarily block egress by updating egress_shaper_policy to "no-egress" for the tenant.
   4. If caused by cross-tenant misrouting, escalate to network infra, snapshot route tables, and enable route debug logs.

3. Short-term remediation playbooks
   - Auto-adjust: If allow_burst=false, decrease route priority for the tenant and route to burst-proxy with 5% bandwidth cap.
   - Chargeback: Emit a high-resolution invoice event (1m window) to billing Kafka for immediate cost-visibility.

Chargeback and forecasting model

- Forecast inputs: daily_egress_gib (declared), historical 7-day median, modelled burst factor (x1.5), cost-per-GiB by region.
- Projection table (example)
| Tenant | Declared GiB/day | 7d median GiB/day | Projected month cost (USD) |
| Alpha | 25 | 28 | $1,020 |
| Beta  | 5  | 7  | $250 |
| Gamma | 200 | 180 | $7,200 |

Notes on accuracy: We recommend aligning declared GiB/day with 7-day median within 20% during the first month to avoid large reconciliations.

CI/CD guardrails and tests

- Terraform fmt + tflint + custom rule: module must set tenant_tags and have no hard-coded account ids.
- PR check: diffs that increase nat_ip_count or daily_egress_gib by >50% must include a chargeback justification file in PR body and a finance reviewer.
- Terratest integration: run in parallel against a disposable sandbox and assert that route tables, reserved IPs, and exporter subscriptions exist.

Security and compliance

- Flow logs: Ensure PII is redacted; do not export payload-level data. Only metadata and byte counts are exported.
- IAM: exporter and NAT reservation modules must follow least-privilege: limited to VPC Flow Logs read/subscribe and ephemeral credentials for billing export.

Backout and rollback plan

1. If new NAT allocations cause global IP exhaustion: revert the terraform to previous version and re-attach tenants to shared NAT gateway (runbook script: tools/revert-tenant-nat.sh).
2. If exporter mislabels tenants: run script to re-tag flow logs and reprocess last 24h in billing pipeline.

Acceptance checklist (before marking module ready for org-wide use)

- [ ] Module passes tflint with company rule set.
- [ ] Terratest passes in sandbox account with mocked flow logs.
- [ ] Chargeback projection accuracy within 15% of realized costs during a 30-day canary.
- [ ] SRE runbook reviewed and oncall trained.
- [ ] Finance used sample exports and approved cost center mapping.

Operational ownership matrix

- Module maintenance: infra/terraform-team (owner)
- Oncall for egress outages: network-sre team
- Chargeback ingestion: finance-platform team
- CI checks and test harness: infra-ci team

Appendix A — Terraform example: small adapter to compute nat_ip_count

# tenant_egress_helpers.tf (pseudocode)
locals {
  class_profile = {
    low = { multiplier = 0.5; nat_per_100gib = 1 }
    standard = { multiplier = 1.0; nat_per_100gib = 2 }
    high = { multiplier = 1.6; nat_per_100gib = 4 }
  }
}
variable "daily_egress_gib" { type = number }
variable "egress_class" { type = string }

# compute recommended NATs
locals {
  profile = local.class_profile[var.egress_class]
  recommended_nat = ceil(var.daily_egress_gib / 100 * local.profile.nat_per_100gib)
}
output "recommended_nat_count" { value = local.recommended_nat }

Appendix B — troubleshooting quick commands

- List NAT reservations: aws ec2 describe-addresses --filters Name=tag:tenant,Values=tenant-alpha
- Sample recent egress (1m): aws logs filter-log-events --log-group-name /vpc/flow-logs --start-time $(date -d '5 minutes ago' +%s)000 --filter-pattern "tenant=tenant-alpha"
