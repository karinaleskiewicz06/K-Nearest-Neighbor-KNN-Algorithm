Cross-account GPU burst SLO contract and CI lifecycle

Summary

Overview:
This document defines the operational contract (SLOs, quotas, billing guardrails) and the CI/CD lifecycle for the cross-account GPU burst fabric. It is intended for platform engineers, tenant owners, and on-call responders who coordinate cross-account bursting between Redwood-managed GPU pools and partner or tenant cloud accounts.

Goals and scope:
- Define a minimal, enforceable SLO contract that tenant teams and platform teams can rely on during bursts.
- Specify Terraform/IaC module shape and CI/CD checks required for enrolling an account in cross-account bursting.
- Provide an operator runbook for common failure modes (burst denied, egress exhaustion, billing disputes).
- Describe test, canary, and rollback requirements for rollouts that change allocation or billing behavior.

Key definitions:
- Burst: short-lived use of extra GPU capacity in another account or region to satisfy a spike. Typically preemptible/spot/borrowed nodes.
- Borrower: tenant account consuming burst capacity.
- Lender: Redwood-managed account providing burst capacity.
- SLO contract: set of measurable targets (latency, success rate, cost cap) enforced by telemetry + circuit breakers.

SLO contract (high level):
1) Availability SLO: 99.8% request success for burst path (30d rolling window).
2) Latency SLO: 95th-percentile tail latency for bursted requests must be <= 1.5x local-pool P95 for the same model class.
3) Cost safety cap: each borrower sets a daily burst spend cap; the cross-account router enforces hard-stop at cap + 10% buffer.
4) Fairness SLO: lender pool should reserve a minimum of 20% capacity for local tenant commits; cross-account allocator must not exceed 80% burst saturation.

SLO measurement signals and owners:
- Request success rate: measured with per-route status codes in "burst-router" trace spans. Owner: eng-platform (metrics).
- Tail latency: measured by p95/p99 spans, stored in trace-store. Owner: eng-serving-runtime.
- Spend cap enforcement: measured by cost-exporter and billing-allocator. Owner: finance+infra.
- Pool saturation: measured by allocator telemetry (allocator-exporter). Owner: gpu-fleet-and-capacity.

SLO violation responses (automated + manual):
- On minor violations (in the 24h window), throttle new burst requests by 30% across all borrowers for 30 minutes and notify the borrower owners.
- On repeated violations (>3 in 7 days) escalate to capacity planning and trigger a temporary ban of non-critical bursts for offending borrowers until mitigation.
- Persistent fairness violations lead to reconfiguration of tenant priority buckets and invoicing adjustments.

Enrolling an account: IaC and CI requirements
All borrower accounts must be enrolled via the cross-account IaC module and pass a CI gate before they can request burst capacity. The enrollment pipeline contains three stages: preflight, canary, and promote.

Required artifacts:
- Terraform module: redwood-gpu-burst-enroll (variables defined below).
- IAM template: minimal role with AssumeRole policy and scoped permissions.
- Network check manifest: list of allowed egress CIDRs, NAT config, and verification probe.
- Cost cap config: daily_limit_usd and emergency_hard_stop flag.

Preflight checks (automated):
1) Terraform plan must be clean with no drift.
2) IAM role can be assumed by lender test harness.
3) Egress probe from borrower to lender control plane succeeds (latency < 200ms).
4) Cost cap configured and billing-family contact set.
5) CI-run smoke generation: 100 synthetic requests against a small model to validate end-to-end prefix caching and KV fill.

Canary phase (7 days):
- Canary scope: 1% of production traffic or synthetic schedules occupying up to 5% of a small lender pool.
- Telemetry to monitor: p95 latency, error rate, billing deltas, KV cache miss rate.
- Canary acceptance criteria: no SLO violations and cost deltas within +/- 15% forecast.

Promote:
- After passing canary, account is automatically promoted by CI to full enrollment. Promotion creates a BurstPolicy CR and final Terraform apply in the lending account.

CI/CD gating rules (must be enforced in the pipeline):
- Terraform plan must include a cost_cap variable. Missing cost caps cause pipeline failure.
- Any changes to burst routing or allocator policy require a staged rollout with a mandatory canary pipeline and a signed plan by gpu-fleet owner.
- Module updates that change default priority buckets require a migration job runbook and data-backfill pre-approve step.

Operator runbook: common failure modes
1) Burst denied / AssumeRole failure:
   - Symptoms: immediate 403s from lender AssumeRole API, burst requests return 403.
   - Quick checks:
     a) Verify IAM role ARN and trust policy is unchanged (terraform state vs remote).
     b) Check STS assume role logs and recent IAM policy changes.
     c) Confirm that the borrower has not exceeded daily_limit_usd.
   - Remedy:
     i) If IAM trust changed, restore from audit log and reapply terraform.
     ii) If cost cap exceeded, contact borrower owner to raise cap or wait until reset.
     iii) If transient STS errors, retry with exponential backoff and alert.

2) Egress exhaustion / NAT saturation:
   - Symptoms: high packet drops, elevated egress latency, failed health probes.
   - Quick checks:
     a) NAT gateway metrics, connection tracking exhaustion, and SNAT port usage.
     b) Check egress billing spikes for partner account.
   - Remedy:
     i) Shift scheduled canaries to alternate egress path (operator toggle).
     ii) Apply temporary egress shunting policy to limit concurrent burst sessions (rate-limit config).
     iii) Open a ticket to networking ops for NAT scaling and attach for capacity.

3) Billing reconciliation disputes:
   - Symptoms: borrower disputes invoice line items tied to burst usage.
   - Resolution path:
     1) Pull per-request cost attribution logs (cost-exporter).
     2) If root cause is metered misattribution, replay allocations from allocator-audit logs.
     3) Apply credit or invoice adjustment within 3 business days; notify finance and borrower owner.

Runbook escalation matrix:
- Pager: gpu-fleet-oncall for allocator and pool issues.
- Pager: eng-platform on config and CI gating errors.
- Slack incident channel: #gpu-cross-account-incidents (primary).
- Escalation timeline: 15m initial ack, 1h mitigation plan, 4h customer comms update.

Capacity forecasting and billing guardrails:
- Weekly forecast cadence: run a ten-day rolling capacity forecast for lender pools using prior 14-day peak metrics + scheduled bursts.
- Forecast outputs: expected spare GPU count per region, expected burst revenue, and risk band (low/med/high).
- Action thresholds:
  - If spare GPUs < 25 in a lender pool -> place a soft cap on new canaries for 48 hours.
  - If expected burst revenue delta > 20% month-over-month -> schedule a capacity planning sync.

Testing, canaries and chaos simulation:
- Synthetic storm harness: used in CI to simulate 2x traffic spikes to validate allocator throttles and cost caps.
- Chaos tests to run quarterly: IAM revocation simulation, NAT failure, allocator leader failover.
- Required test artifacts committed with any IaC change: plan summary, smoke logs, and canary dashboard link.

Rollout checklist (pre-promotion):
1) IaC module version pinned and reviewed.
2) Cost cap and billing contact set.
3) Canary plan documented with duration and telemetry thresholds.
4) Runbook updated with ownership and runbook play IDs.
5) Observability dashboards and alerts defined and attached to the CI run.

Appendix A — Example Terraform module variables (excerpt):

```hcl
variable "borrower_account_id" {
  type = string
  description = "Target account id for borrower"
}
variable "daily_limit_usd" {
  type = number
  description = "Hard stop for borrower burst spend per day (USD)"
}
variable "emergency_hard_stop" {
  type = bool
  default = false
  description = "If true, lender will refuse all new bursts immediately"
}
output "burst_policy_cr" {
  value = local.policy_cr
}
```

Appendix B — Minimal IAM trust policy (description):
- Role: redwood-burst-borrower-assume-role
- Trust scope: lender-control-plane-principal only.
- Permission scope: STS:AssumeRole, logs:PutLogEvents (only for audit), ec2:DescribeInstances (read-only), monitoring:GetMetricData.
