Tool Calling Parity Guidelines (Python/TypeScript/Go)

## Purpose
These guidelines define the **canonical tool-calling semantics and example patterns** that must remain consistent across:
- `redwood-sdk-python`
- `redwood-sdk-typescript`
- `redwood-sdk-go`
- `redwood-docs` code tabs and runnable snippets

The intent is to:
1) Reduce copy/paste failures and support tickets.
2) Ensure all SDKs tell the same story about tool definitions, tool call arguments, parallel tool calls, and tool result messages.
3) Provide a clear checklist for reviewers to validate parity during PR review.

## Scope (what this page covers)
This page covers **tool calling** for chat/text generation APIs, including:
- Tool definition naming and structure shown in examples
- Argument typing + validation conventions (SDK type hints + runtime validation)
- How to represent **parallel tool calls**
- How to send **tool result messages** back to the model
- Streaming considerations (partial arguments, ordering)

Non-goals:
- Redesigning the underlying API protocol
- Prescribing a single validation library across languages (we recommend options)
- Comprehensive coverage of every model’s tool behavior (see product support matrix in docs)

## Terms and mental model
**Tool**: a developer-defined function the model can request.

**Tool call**: a model-produced request to invoke a tool. Tool calls have:
- A stable `id` (tool-call identifier)
- A `name` (must match the tool’s registered name)
- `arguments` (JSON object; may arrive incrementally during streaming)

**Tool result message**: developer response sent back to the model after executing a tool call. Tool result messages must reference the original tool call `id`.

**Parallel tool calls**: a single assistant turn may request multiple tool calls. Examples must show looping over calls and returning results for each.

## Canonical conventions (must match across SDKs/docs)
### 1) Naming conventions
**Tool name**
- Use `snake_case` tool names in all examples (even in TypeScript/Go) to reduce visual differences between languages.
- Keep tool names stable and descriptive (e.g., `get_weather`, `search_docs`, `create_ticket`).
- Avoid overloaded names like `call_api` or language-specific method names.

**Argument keys**
- Use `snake_case` for JSON keys.
- Prefer small, explicit schemas over free-form strings. Example: `{"location": "Seattle, WA", "units": "f"}`.

**Tool result payload keys**
- Use `snake_case` keys.
- Keep result objects shallow when possible and include minimal fields needed for the model.

### 2) Tool definition format shown in examples
Examples must present tool definitions in a consistent conceptual structure:
- `name`: string
- `description`: string (1–2 sentences; mention units/constraints)
- `parameters`: JSON Schema object (at least `type: object`, `properties`, and `required`)

Do not show examples where tool parameters are described only in prose; always include a schema.

### 3) Tool call argument typing and validation (required)
All examples that execute tools must:
- Parse arguments as JSON object (not raw string concatenation)
- Validate required fields and basic types
- Provide a failure path (return an error result the model can use, or retry the model with corrected constraints)

**Minimum validation requirements for examples**
- Required keys present
- Type checks for strings/numbers/booleans/arrays
- Enum validation if an enum is declared

Recommended validation approaches (examples may vary by language):
- Python: `pydantic` (preferred in examples), or manual validation for small schemas
- TypeScript: `zod` (preferred), or `valibot` / manual guards
- Go: `json.Decoder` + struct validation (`go-playground/validator`) or explicit checks

### 4) Parallel tool calls must be demonstrated consistently
If the model returns multiple tool calls:
- Execute each tool call independently
- Return a tool result message for each tool call (each with the correct `tool_call_id`)
- Preserve the tool call `id` exactly as provided

**Ordering guidance**
- Examples should preserve order for readability (iterate in the order received).
- Correctness does not depend on ordering, but logging and troubleshooting are easier when order is stable.

### 5) Tool result messages must be structured
Tool results must be returned as a tool-role message that references the tool call `id`.

Examples must avoid:
- Sending tool results as assistant text
- Omitting the `tool_call_id`
- Returning ambiguous strings like "success" without any structured payload

Preferred result format (conceptual)
- `role: "tool"`
- `tool_call_id: "..."`
- `content`: JSON string or object (SDK-specific) representing the result

### 6) Error handling conventions (show at least one failure branch)
Examples must include one of:
- A tool execution error branch that returns `{ "error": { "message": "...", "type": "..." } }` as tool content
- An argument validation failure branch that returns a tool result with an error payload and does not crash the sample

Do not silently swallow errors.

## Canonical tool-calling flow (examples should follow this structure)
1) Send user message + tool definitions.
2) Receive assistant response.
3) If tool calls are present:
   a) For each tool call: parse + validate arguments
   b) Execute tool
   c) Append a tool-result message referencing `tool_call_id`
4) Send an additional request including the assistant turn + tool results to let the model produce the final response.

Note: Some models may produce final text and tool calls in the same turn. Examples should still treat tool calls as authoritative and continue the loop.

## Streaming-specific guidance (parity requirements)
See also: *Streaming Event Model Conventions*.

### Partial arguments during streaming
During streaming, tool call arguments may arrive as partial JSON fragments. Examples must:
- Accumulate argument deltas per tool call `id`
- Only parse JSON once the tool call is marked complete (or once a final event indicates completion)
- Handle parse errors by continuing to buffer (do not fail on first invalid partial JSON)

### Multiple tool calls in one streamed assistant turn
Streaming may interleave tool call deltas. Examples must:
- Key buffers by tool call `id`
- Avoid a single global buffer for all tool calls

### Logging (recommended in examples)
At minimum, log:
- tool name + tool_call_id
- whether args validated
- tool execution latency (rough wall-clock)

Avoid logging full raw tool arguments if they may contain secrets (examples should use safe, non-sensitive inputs).

## Example-level schema guidance (what to show in docs)
Examples in docs and READMEs should use **small, teachable schemas** with:
- 1–4 fields
- At least one required field
- At least one constraint (enum, min length, numeric bounds)

**Good example schema**
- `location` (string, required)
- `units` (enum: `"c" | "f"`, required)

**Avoid in docs examples**
- 20+ property schemas
- Deep polymorphic schemas that obscure the basic flow
- Schemas that rely on model behavior that varies widely across model families

## Cross-SDK parity requirements (what must match)
The following must be consistent across Python/TypeScript/Go examples and docs:

### Required invariants
- Tool definition includes: name, description, JSON schema parameters
- Tool call fields are referenced consistently: `id`, `name`, `arguments`
- Tool result references: `tool_call_id`
- Parallel tool calls: shown as an array/list; loop is explicit
- Validation step exists before tool execution

### Allowed differences (SDK-idiomatic)
- How requests are initiated (client naming, method names)
- How streaming iteration is expressed (async iterators vs channels)
- Validation library choice (as long as validation exists and is easy to follow)
- Whether tool result `content` is passed as a JSON string vs object (depending on SDK API), but the conceptual payload must match

## Reviewer checklist (use for every tool-calling PR)
Copy/paste this checklist into PR descriptions where applicable.

### A) Definitions and naming
- [ ] Tool names are `snake_case` and consistent with docs examples
- [ ] Tool parameters are expressed as JSON schema (not only prose)
- [ ] Argument keys are `snake_case`

### B) Tool call handling
- [ ] Example handles **multiple tool calls** (parallel calls) correctly
- [ ] Tool call `id` is preserved and used as `tool_call_id` in tool results
- [ ] The sample shows a full loop: request → tool call(s) → tool result(s) → follow-up request

### C) Argument parsing + validation
- [ ] Arguments are parsed as JSON object (not string slicing / eval)
- [ ] Required fields are validated with an explicit error path
- [ ] Type checks / enum checks exist for at least one field

### D) Tool results
- [ ] Tool results are returned as tool-role messages (not assistant text)
- [ ] Tool result payload is structured (JSON object with clear fields)
- [ ] Error results use a structured error object (message + type)

### E) Streaming considerations (if streaming example)
- [ ] Partial tool arguments are buffered by tool_call_id
- [ ] JSON parsing happens only after completion (or is resilient to partial fragments)
- [ ] Disconnect/cancel behavior is handled or called out (at least a comment)

### F) Docs and maintainability
- [ ] Snippet compiles/runs as published (smoke tested)
- [ ] Output shown in README/docs matches actual output
- [ ] If behavior is model-dependent, the example includes a short callout and fallback guidance

## Common pitfalls (observed in support + reviews)
1) **Parsing partial JSON too early** (streaming): results in intermittent JSON parse errors.
2) **Forgetting tool_call_id**: model cannot associate results; leads to repeated tool calls.
3) **Returning tool output as assistant text**: breaks the expected protocol and confuses users copying examples.
4) **Implicit parallelism**: examples that only handle one tool call hide a common real-world behavior.
5) **TypeScript-only “types” without runtime validation**: leads to runtime crashes when models return unexpected shapes.

## Appendix: Reference payload vocabulary (example-level)
To keep parity, docs and examples should use the following terms consistently:
- “tool definition” (not “function spec” in Redwood docs)
- “tool call” (not “function call”)
- “tool result message” (not “tool response”) when referring to the message sent back to the model
- “parallel tool calls” for multiple tool calls in a single assistant turn

If referencing OpenAI-compat behavior, add a short note and link to the compatibility doc; do not imply identical streaming semantics across providers.
