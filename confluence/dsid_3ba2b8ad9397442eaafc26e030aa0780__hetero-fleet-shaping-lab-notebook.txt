Heterogeneous GPU Fleet Shaping — Lab Notebook

Overview

This lab notebook documents reproducible experiments and operational recipes for shaping a heterogeneous GPU fleet to optimize inference cost, latency, and reliability. It is intended for infra engineers, SREs, and performance-focused platform owners who run experiments to inform pool sizing, placement policies, and IaC configurations.

Goals

- Produce repeatable experiments that compare mixed-GPU pools (e.g., A100, H100, L4, T4) across representative inference workloads.
- Measure economics (per-token CPU/GPU cost), tail latency (p95/p99 for token generation), throughput, and preemption impact.
- Generate Terraform variants and CI artifacts that can be promoted into staging for safety testing.
- Deliver recommendations (pool mixes, instance families, spot vs on-demand ratios) and a data capture template for decision records.

Scope and assumptions

- Focus on inference-serving workloads (short to long context LLM token streaming and batch embedding jobs).
- Experiments run in a dedicated sandbox AWS account with service quotas isolated from prod.
- The notebook emphasizes metrics capture over model selection — model variants are instrumented separately in the eval harness.

Prerequisites

1) Sandbox AWS account with permissions: terraform, EC2/GPU quota, CloudWatch, S3.
2) CI runner with GPU access (Buildkite/Runner images as provisioned by ci-cd team).
3) Runner image containing: nvidia drivers, CUDA, docker, runc, and the inference harness container.
4) Terraform module catalog referenced: sources/confluence/eng-infra/terraform-and-iac/* (use the fleet-allocator module in staging).

Experiment matrix (example)

Columns: experiment_id | pool_mix | spot_pct | region | workload_profile | target_qps
Rows:
- E1 | 1x A100 + 4x L4 | 10% | us-west-2 | streaming-short (context=1024) | 500 qps
- E2 | 2x H100 + 2x A100 | 0% | us-east-1 | batch-embeddings (batch=512) | 200 qps
- E3 | 6x L4 | 40% | us-west-2 | low-latency-chat (context=256) | 800 qps
- E4 | mixed (A100/H100/L4) with node-affinity tiling | 25% | eu-west-1 | mixed (100ms/500ms tail targets) | 600 qps

Workload profiles (definitions)

- streaming-short: synthetic prompt stream that produces 50–300 tokens per request, 10–40 ms token inter-arrival for burst simulation.
- batch-embeddings: CPU-heavy batching workload; high memory usage per request; measures per-item latency and tokenized overhead.
- low-latency-chat: small contexts (<=256), high QPS, sensitive to p95/p99 tail.

Data capture schema (CSV/JSON keys)

- experiment_id, timestamp, region, instance_type, pool_mix, spot_pct, qps_target, measured_qps, p50_latency_ms, p95_latency_ms, p99_latency_ms, avg_gpu_util_pct, avg_gpu_mem_pct, cost_per_hour_usd, tokens_generated, failure_count, preemptions_count

Operational runbook (high-level steps)

1) Create a new experiment branch and Terraform workspace:

   $ git checkout -b exper/hetero-shape-E1
   # update variables in examples/hetero/vars.tfvars
   $ terraform workspace new lab-E1 || terraform workspace select lab-E1

2) Apply IaC with a canary: deploy a minimal canary allocation (10% of target traffic) using the fleet-allocator module.

   $ terraform init && terraform apply -var-file=examples/hetero/vars.tfvars -target=module.fleet_allocator.canary

3) Validate node boot and agent health: verify node labels, kubelet registration (if using k8s), or placement service logs.

   - Check cloud console for driver installation status.
   - Validate node exporter and nvidia-smi metrics streaming to CloudWatch.

4) Kick off synthetic load generator (inference-harness container) with experiment metadata tag to S3:

   $ docker run --rm \
     -e EXPERIMENT_ID=E1 \
     -e S3_BUCKET=redwood-lab-artifacts \
     redwood/inference-load-generator:latest \
     --profile streaming-short --target-qps 500 --duration 30m --sink s3://redwood-lab-artifacts/E1/

5) Monitor telemetry for SLOs and abort conditions (these are automated in the CI runner):

   Abort if:
   - p99 latency increases > 2x baseline for 10m
   - GPU OOMs > 0.5% of requests
   - Preemptions increase by > 3x baseline

6) After run completion, collect artifacts, attach to experiment branch and register on the lab index.

CI/CD integration (promote -> staging -> canary)

- Pipeline stages: plan -> apply-canary -> run-smoke -> run-lab -> collect-and-archive -> promote.
- Buildkite job names (recommended): gpu-lab/plan, gpu-lab/apply-canary, gpu-lab/launch-loadgen, gpu-lab/collect.
- Safety gates: plan must be signed; apply-canary requires manual approval by infra-sre on-call.

Telemetry and dashboards

- Core metrics to stream to CloudWatch/Prometheus: gpu_util_pct, gpu_mem_pct, gpu_power_w, nvidia_gpu_temp_c, inference_latency_ms (p50/p95/p99), request_rate, tokens_per_second, preemption_events, node_boot_duration_sec.
- Dashboard template: heterogeneous-fleet/lab-experiment-template (save as JSON in Grafana dashboard repo).

Decision criteria (how we decide winners)

- Winner is a pool_mix that: meets p99 latency target <= baseline_target AND reduces per-token cost >= 10% over reference mix, with preemption risk acceptable (<2% additional failures).
- Secondary filters: operational complexity (number of distinct instance families), observable variance across regions, and Terraform churn risk (module changes required).

Example findings summary (fictional example)

- E1 (A100 + L4) reduced cost per token by 18% vs A100-only baseline, p99 increased by 8ms (within SLO). Preemptions were stable at 0.7%.
- E3 (L4 heavy, 40% spot) showed best cost but p99 spikes at high burst windows; recommend hybrid with reserve on-demand buffer for peak windows.

Artifacts and deliverables

- Experiment CSV/JSON results (S3 path): s3://redwood-lab-artifacts/{experiment_id}/results.json
- Terraform varfiles for each variant in git: infra-labs/experiments/{experiment_id}/vars.tfvars
- Grafana dashboard snapshot link: grafana/internal/dashboards/hetero-lab/{experiment_id}
- Post-run decision note (short ADR): register in confluence under eng-infra/decision-records with link to artifacts.

Safety considerations and rollback

- Never promote lab module changes directly to prod without a staged rollout and automated SLO fuzz tests.
- Rollback path: terraform workspace select <prod> && terraform apply -var-file=prod/vars.tfvars -refresh-only to remove lab tags; then run fleet rebalancer with target pools pinned to prod mix.
