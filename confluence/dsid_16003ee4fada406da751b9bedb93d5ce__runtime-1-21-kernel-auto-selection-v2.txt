Runtime 1.21 Release Notes: Kernel Auto-Selection v2

## Summary
Runtime **1.21** introduces **Kernel Auto-Selection v2** ("selector v2") for GPU inference kernels. The selector chooses the best available kernel **per request** using a deterministic, explainable rule-based policy keyed on:
- **Model family / architecture** (e.g., Llama-like vs Mistral-like vs Qwen-like)
- **Sequence-length regime** (prefill-heavy, decode-heavy, mixed; plus long-context buckets)
- **GPU SKU** (e.g., A100 vs H100 vs L40S; including normalization of common cloud instance naming)

This release is focused on reducing **p95/p99 latency** and improving **throughput stability** across heterogeneous fleets without correctness regressions.

Selector v2 is shipped **behind feature gates** and includes fast rollback, per-model allow/deny controls, and guardrails for known-unstable driver/CUDA combinations.

---

## What’s New in 1.21
### 1) Kernel Auto-Selection v2 (gated)
- Expanded feature extraction: model-family tags + seq-length buckets + GPU SKU normalization.
- Explicit fallback hierarchy when a preferred kernel is unavailable or denied on a SKU.
- Deterministic decision logic and replay tests (same inputs => same kernel choice).

### 2) Selection Telemetry (sampled)
New per-request telemetry is available (sampling-controlled) to support debugging and rollout monitoring:
- chosen kernel
- candidate set (capped)
- feature vector (model family, seq bucket, gpu sku)
- fallback reason (if applicable)

### 3) Operator Controls & Debugging
- Force kernel selection for reproductions and customer escalations.
- Dump selection traces locally (or in canary pods) for triage.
- Hot-reloadable allow/deny rules (control plane) for fast mitigation.

## Configuration / Flags
Selector v2 is **off by default** in Runtime 1.21 unless enabled by the control plane gate or local runtime config (Dedicated/Private).

### Feature gates (Hosted / Dedicated via control plane)
Gate key:
- **kernel_selection.v2.enabled**

Scoped overrides supported:
- by model (exact model id)
- by model family (architecture tag)
- by region
- by GPU SKU

### Runtime config (Dedicated / Private)
The following keys are supported in `runtime.yaml` (or equivalent env var mapping).

**Core toggles**
- `kernel_selection.mode`: `v1` | `v2` | `auto` (default: `auto`)
- `kernel_selection.v2.enabled`: `true` | `false` (default: `false`)

**Allow/Deny lists (hot reload where supported)**
- `kernel_selection.v2.model_allowlist`: comma-separated model ids
- `kernel_selection.v2.model_denylist`: comma-separated model ids
- `kernel_selection.v2.gpu_sku_denylist`: comma-separated normalized SKUs (e.g., `A100-80GB`, `H100-SXM`, `L40S`)
- `kernel_selection.v2.driver_denylist`: comma-separated driver/CUDA tuples (example: `535.104.05+cuda12.2`)

**Telemetry**
- `kernel_selection.telemetry.enabled`: `true` | `false` (default: `true`)
- `kernel_selection.telemetry.sample_rate`: float 0.0–1.0 (default: `0.01`)
- `kernel_selection.telemetry.max_candidates`: integer (default: `6`)

### Runtime CLI flags (debug / reproduction)
Available in `redwood-runtime` binaries starting 1.21:
- `--kernel-selection=v1|v2|auto`
- `--force-kernel=<kernel_id>` (disables auto-selection)
- `--dump-kernel-selection=<path>` (writes per-request selection traces)
- `--kernel-selection-telemetry-sample-rate=<0.0-1.0>`

Notes:
- Forcing a kernel is intended for debugging and should not be used as a steady-state configuration unless directed by the runbook.
- Telemetry sampling does **not** affect selection behavior and does not introduce nondeterminism into decisions.

## Expected Performance Impact
Observed improvements vary by model family, GPU SKU, and workload mix.

In internal benchmark coverage (A100/H100/L40S) with representative prompt/decode distributions:
- **p95 latency:** typically **3–12% improvement** on mixed workloads; larger wins on SKU/model pairs where v1 frequently fell back to conservative kernels.
- **p99 latency:** typically **2–10% improvement** when the workload is correctly bucketed; long-context workloads are the most sensitive (see Known Limitations).
- **Throughput stability:** fewer oscillations under bursty mixed prefill/decode traffic due to better regime bucketing.
- **Selector overhead:** bounded and low; microbench indicates selector evaluation cost is in the **single-digit microseconds** range, and sampling-controlled telemetry overhead is negligible at default settings.

Performance regressions should be treated as a **P0** if they increase p99 tail latency beyond rollout budgets (see SLO gates / dashboards).

## Compatibility Notes
- Supported GPU families in rollout scope: **A100, H100, L40S**.
- MIG: supported, but SKU normalization is strict; ensure the runtime reports a normalized `gpu_sku` consistent with the control plane rules.
- Private deployments pinned to constrained GPU types should validate with the benchmark matrix before enabling v2 globally.

---

## Known Limitations / Risks
1) **Long-context misclassification risk (prefill-heavy)**
   - Very long prefill requests (e.g., summarization with large context windows) are sensitive to incorrect bucketing.
   - If you observe tail spikes concentrated in long-context routes, disable v2 for the affected model(s) and region, then collect selection traces.

2) **Driver/CUDA guardrails**
   - Selector v2 is automatically disabled on specific driver/CUDA combinations that have not completed validation.
   - If you are running a nonstandard driver stack (common in some on-prem installs), confirm you are not implicitly falling back to v1.

3) **Telemetry cardinality**
   - New fields can increase metric cardinality if dashboards are queried without the recommended grouping limits.
   - Follow the dashboard spec for safe group-bys (model family / SKU / seq bucket) and avoid raw model-id group-bys unless sampled and capped.

4) **Kernel availability differences by SKU**
   - Some optimized kernels are SKU-specific. v2’s fallback rules are explicit, but you may see different kernel distributions between A100 and H100 under identical traffic.

## Rollout / Enablement Guidance
Recommended staged rollout order:
1. Enable v2 in **Hosted canary** for a small model allowlist.
2. Expand allowlist by model family + SKU cohorts (monitor p95/p99 and error rates).
3. Enable in **Dedicated pools** with explicit customer opt-in and documented rollback contact.
4. Promote to broader GA once SLO gates are green for at least one full traffic cycle.

Default enablement approach:
- Start with `kernel_selection.v2.model_allowlist` and keep a conservative denylist for known-sensitive long-context models until validated.

---

## Rollback Instructions (Fast Path)
If you suspect a latency regression, elevated error rate, or unexpected kernel distribution shift, roll back v2 using the smallest-scoped change that resolves impact.

### Hosted / Dedicated (control plane gate)
1. Disable v2 for the affected scope (start with model + region):
   - Set `kernel_selection.v2.enabled=false` (scoped) OR remove the model from the v2 allowlist.
2. Confirm hot reload applied:
   - Verify the selector mode in runtime logs: `kernel_selection_mode=v1` (or `v2 disabled by gate`).
3. Validate recovery:
   - Monitor p95/p99 latency and error rate panels in the Kernel Selection v2 rollout dashboards.
   - Confirm kernel distribution shifts back to expected v1 baselines.

### Private (customer-managed runtime config)
1. Set `kernel_selection.v2.enabled=false` and/or `kernel_selection.mode=v1` in `runtime.yaml`.
2. Restart the runtime service (or reload config if supported in the deployment).
3. Validate with the customer’s canary route:
   - Compare p99 latency for long-context traffic before/after.

### If immediate mitigation is required
- Pin a kernel only as a temporary measure:
  - Use `--force-kernel=<kernel_id>` (or equivalent config) for the impacted route/model while investigating.
  - Open a follow-up issue to remove the pin once denylist or thresholds are corrected.

---

## Troubleshooting Checklist
When filing an issue or escalating to oncall/runtime-kernels, include:
- Model id + model family
- GPU SKU (normalized) + whether MIG is used
- Driver/CUDA version tuple
- Workload description (prefill-heavy vs decode-heavy; typical context lengths)
- Selection traces (`--dump-kernel-selection`) for 20–50 representative requests
- Dashboard links: latency deltas + selection distribution by SKU/seq bucket
