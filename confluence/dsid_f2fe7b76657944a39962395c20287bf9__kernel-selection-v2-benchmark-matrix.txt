Kernel Auto-Selection v2 — Benchmark Matrix (Coverage + Pass/Fail Criteria)

## Purpose
This page defines the benchmark plan and coverage matrix used to qualify **Kernel Auto-Selection v2** prior to staged rollout (Hosted → Dedicated pools → GA). The goal is to validate that v2 improves p95/p99 latency and throughput stability across heterogeneous GPU fleets **without correctness regressions** or tail-latency spikes due to workload misclassification.

We use this matrix for:
- Pre-merge perf verification (CI lightweight)
- Nightly/per-release characterization (benchmark-lab)
- Canary gating (perf-canary + SLO gates)


## What we compare
All scenarios are run under:
- **Selector v1 (baseline)**
- **Selector v2 (candidate)** behind feature gate

Comparison is performed per (model family, GPU SKU, sequence regime), with identical runtime config except for selector.

### Primary KPIs (reported per scenario)
- **TTFT / Prefill latency**: p50 / p95 / p99 (ms)
- **Decode latency**: p50 / p95 / p99 (ms) for steady-state decode
- **End-to-end request latency**: p50 / p95 / p99 (ms)
- **Throughput**:
  - **tokens/sec/GPU** (steady-state) and
  - **requests/min** under fixed concurrency
- **Stability**: coefficient of variation (CV) for throughput and p99 across 10-minute windows
- **Error rate**: non-2xx, runtime errors, OOMs

### Secondary metrics (diagnostics)
- Selected kernel distribution (% by kernel id)
- Kernel switch rate (per 1k requests)
- Selector overhead (µs)
- KV cache hit behavior (where applicable)


## Pass/Fail thresholds (gating rules)
Thresholds below apply to **v2 vs v1** deltas within the same environment.

### Global hard gates (must pass)
1) **Correctness / determinism**
- 0 correctness regressions in golden output checks (where enabled) and 0 crashes.
- Deterministic selection: given identical inputs (model id/version, GPU SKU normalized, seq bucket, runtime flags), v2 must choose the same kernel across repeated runs.

2) **Error rate**
- v2 must not increase error rate by more than **+0.02% absolute** in any scenario.
- Any new error signature (OOM, illegal memory access, NaN) is an automatic fail.

3) **Tail latency protection**
- For long-context scenarios, **p99 end-to-end latency regression must be ≤ +2%**. (Rationale: long-context tail spikes are a primary risk.)

### Performance success targets (should hit; can be waived with explicit sign-off)
- **p95 latency improvement**: target ≥ **3% better** in at least 70% of scenarios.
- **Throughput improvement**: target ≥ **2% better** in at least 60% of scenarios.

### Scenario-level gating (defaults)
The following gates are enforced per scenario unless explicitly noted:

| Metric | Default gate (v2 vs v1) | Notes |
|---|---:|---|
| TTFT p95 | ≤ +2% regression | TTFT is user-visible; small regressions allowed if decode improves materially. |
| End-to-end p95 | ≤ +1% regression | Hosted canary uses this as a primary alarm. |
| End-to-end p99 | ≤ +3% regression | Except long-context where ≤ +2%. |
| Decode tokens/sec/GPU | ≥ -1% regression | Throughput regressions are typically not acceptable unless TTFT improves. |
| Stability (p99 CV) | must not worsen | Worsening stability triggers investigation even if averages improve. |

### Escalation / waiver policy
A scenario may be waived only if:
- The regression is explained (e.g., kernel denied on a SKU → safe fallback) AND
- A mitigation exists (denylist/allowlist rule, threshold tweak, or explicit override) AND
- Approved by **Runtime Architect (Noah Patel)** + **Perf/Evals (Claire Dubois or Marcus Reed)**.


## Test environments
### GPU SKUs (required coverage)
We test at minimum the following:
- **A100 80GB (SXM)** — primary baseline for legacy fleets
- **H100 80GB (SXM)** — primary for next-gen fleets
- **L40S 48GB** — cost-optimized inference pools

Optional/when available (recommended for Dedicated readiness):
- A100 PCIe 80GB
- H100 PCIe 80GB
- MIG variants (A100 1g/2g where used in Dedicated)

### Runtime + software constraints
- Fixed runtime build (e.g., runtime 1.21 release candidate)
- Fixed CUDA / driver versions per lab pool; record exact versions in run metadata
- CPU host class pinned (avoid mixed host types in same comparison)


## Workload regimes and distributions
We bucket workloads by **(prefill tokens, decode tokens)** and include both synthetic and trace-derived distributions.

### Sequence regime buckets (canonical)
- **S (short)**: prefill 64–256, decode 16–128
- **M (medium)**: prefill 512–2k, decode 128–512
- **L (long-context)**: prefill 4k–16k, decode 64–512
- **XL (very long)**: prefill 16k–32k, decode 16–256 (run on capable SKUs only)

### Request mix patterns
- **Single-regime**: all requests in same bucket (S-only, M-only, L-only)
- **Mixed**: 70/20/10 split (S/M/L) and 50/50 split (S/L)
- **Bursty**: periodic concurrency spikes (to stress batching & selection stability)


## Model coverage
We cover representative architectures and common serving configurations. Model versions are pinned to a specific runtime-known commit/hash in benchmark harness.

### Model families (required)
- **Llama** (e.g., Llama-3.x style) — dense decoder-only
- **Mistral** (incl. MoE variants where supported)
- **Qwen** (dense, long-context common)
- **Gemma** (smaller parameter regimes, latency-sensitive)

### Parameter scales (minimum set)
- ~7–9B class (latency-sensitive)
- ~13–14B class (balanced)
- ~70B class (throughput + memory pressure)

## Run configuration (standardized)
To minimize noise, all benchmark runs must adhere to:
- Warm-up: **3 minutes** (excluded from metrics)
- Measurement window: **10 minutes**
- Repetitions: **3 runs** per scenario, report median + min/max
- Random seed: fixed per scenario (for request mix generation)
- Batching config: pinned (unless the specific scenario is intended to test dynamic batching interactions)
- Telemetry sampling: selector decision events sampled at **1%** by default; for lab characterization can be raised to **5%** with overhead check

### Reporting convention
For each (scenario, repetition):
- report absolute metrics for v1 and v2
- compute percent delta (v2-v1)/v1
- store full selector decision histogram keyed by normalized GPU SKU + seq bucket + model family


## Noise control and statistical handling
- If run-to-run variability (p99) exceeds **±5%** on v1 baseline, the pool is considered unstable; rerun or move to a dedicated perf lane.
- When comparing v1 vs v2, we require **paired runs** (same node image + GPU host class) whenever possible.
- A regression must reproduce in **2/3 repetitions** to be marked as a true regression; otherwise mark as flaky and investigate harness/pool noise.


## CI vs Lab vs Canary (where each part runs)
### CI (lightweight)
- Subset: A1, A2, C1 (short/medium only)
- Goal: catch large regressions, validate selector determinism tests
- Budget: < 30 minutes

### Benchmark-lab (nightly / release candidate)
- Full matrix A–G
- Produces “ship room” report for runtime 1.21 RCs

### Perf-canary (rollout monitoring)
- Focus: end-to-end p95/p99 deltas + selection distribution drift
- Canary uses production-like traffic mixes (trace-derived) on at least 2 SKUs per region


## Acceptance checklist (for rollout readiness)
A release candidate is eligible for Hosted canary if:
- All **global hard gates** pass
- No scenario violates the long-context p99 gate
- Any waived scenarios have approved denylist/allowlist changes ready for rollout
- Dashboards for selection distribution and latency deltas are live and validated

Eligible for Dedicated expansion if additionally:
- Required SKUs for the target Dedicated pool have full matrix coverage
- Manual override path (pin kernel / disable v2 by model+SKU+region) has been exercised in staging
