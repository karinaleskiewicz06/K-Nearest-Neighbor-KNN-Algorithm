egress-contract-testbed-and-provisioning-harness

Blueprint and runbook for the multi-account egress contract testbed used to validate tenant-level egress SLAs, to provision ephemeral egress infrastructure via Terraform, and to integrate tests into CI/CD. Includes validation criteria, rollout/rollback steps, and monitoring/telemetry guidance.
Overview

This document describes the Egress Contract Testbed and Provisioning Harness: a repeatable test environment and IaC patterns for validating per-tenant egress contracts (bandwidth, NAT/HTTP success, routing correctness, and billing labels) across multi-account GPU workloads. The harness has three goals:

- Validate network-level SLOs before tenant onboarding and before major infra changes.
- Provide an automated, canary-style provisioning flow for ephemeral NAT/egress gateways used in CI.
- Offer a runbook for triage, rollback, and CI integration so changes are exercised automatically.

Design principles

1) Infrastructure-as-tests: treat egress behavior as a contract validated by automated CI that runs Terraform + active traffic tests.
2) Least privilege topology: ephemeral NAT/Gateway instances created in tenant accounts with time-limited roles and strict egress ACLs.
3) Observable assertions: every validation run emits metrics, traces, and artifacts for audit and billing reconciliation.
4) Safe rollouts: every Terraform change is gated by a contract test pass and a canary promotion policy.

Scope and when to use

Use the harness for:
- New tenant onboarding requiring egress SLOs or bandwidth guarantees.
- Infra changes that affect NATs, proxies, routing, or BGP adverts.
- CI/CD validation for new Terraform modules that touch egress components.

High-level components

- Terraform provisioning modules (module.egress-testbed): creates ephemeral NAT gateway(s), a test VPC peering, IAM roles for the test harness, and a metrics exporter.
- Traffic generator (egress-checker): containerized test runner that issues HTTP/TCP workloads, measures throughput, success rates, and tail latency.
- Shadow-router (optional): a programmable virtual router that allows injecting route perturbations for resilience testing.
- Test orchestrator (buildkite / GitHub Actions): runs plan/apply + egress-checker, collects artifacts, and publishes pass/fail.
- Observability sink: Prometheus metrics, traces (jaeger compatible), and artifacts stored in S3/GCS for forensic review.

Contract validation matrix (example)

| Contract | Success criteria (CI) | Alert threshold | Artifact |
|---|---:|---|---|
| Per-tenant HTTP success | 99.95% 2m rolling window | <= 99.90% fail -> alert | egress-checker HTTP log + response histogram |
| Sustained bandwidth (burst) | >= 600 Mbps for 60s (burst tier) | < 580 Mbps -> fail test | iperf log + pcap sample |
| NAT session capacity | 120k concurrent ephemeral sessions | < 110k -> fail | netstat snapshot + exporter metrics |
| Labeling and billing tags | All egress flows contain expected X-Client-Tag header or NAT-tag | any missing tags -> fail | packet capture + tag report |

Terraform module usage (example)

Note: the module is intentionally minimal — real usage in tenant onboarding pipelines should supply account IDs, CIDR ranges, and TTLs for ephemeral resources. Example snippet for the test harness: 

```hcl
module "egress_testbed" {
  source              = "git::ssh://git.internal.redwood/infra/terraform-modules.git//egress-testbed"
  tenant_account_id   = var.tenant_account_id
  region              = var.region
  allowed_destinations = ["0.0.0.0/0"]
  ephemeral_ttl_hours = 4
  nat_instance_size   = "c6g.large"
  enable_shadow_router = true
  labels = { workload = "egress-contract-test" }
}
```

CI/CD integration

- Pipeline steps (Buildkite example):
  1. terraform init + fmt + validate
  2. terraform plan (submit artifact)
  3. gated approval (if applies to prod-like accounts)
  4. terraform apply (ephemeral resources)
  5. run egress-checker suite against the testbed (3 parallel scenarios: http, udp/bandwidth, route-perturbation)
  6. aggregate metrics and publish results to test report artifact
  7. terraform destroy (if run was ephemeral) or tag for promotion if passing and requested

Command-line to run locally (example):

$ export TENANT=123456789012
$ export REGION=us-west-2
$ terragrunt apply -target=module.egress_testbed --terragrunt-non-interactive
$ docker run --rm -e TARGET_IP=$(terraform output -raw nat_ip) ghcr.io/redwood/egress-checker:stable --profile http,bandwidth,tagging --out /tmp/egress-result.json

Validation criteria and gating policy

- All three scenario groups (HTTP, bandwidth, tagging) must report PASS.
- If any scenario FAILs: pipeline marks change as failed, creates a rollback job, and notifies owners (pager duty and #infra-egress).
- For infra changes touching production NATs, run the same contract tests in a scheduled preflight window (see Runbook).

Runbook: triage and rollback (on test failure)

1. Inspect CI artifacts: /buildkite/artifacts/<run-id>/egress-result.json and pcap samples in S3.
2. Look at Prometheus metrics for exporter (egress_testbed:success_rate, egress_testbed:bandwidth_mbps).
3. If failure is reproducible locally: run the same terraform apply in a subordinate test account and reproduce.
4. If Terraform change caused failure: revert the PR or terraform apply the previous state (see fast rollback steps below).
5. If network route issue: use shadow-router to reapply baseline routes, or de-register BGP announcements that were recently added.
6. Notify stakeholders: #infra-egress, oncall (paging), and the tenant owning the change.

Fast rollback steps (Terraform-focused)

- If ephemeral testbed: simply `terraform destroy` to remove resources.
- If runway change in shared modules: 1) run `terraform state pull` and detect resource diff; 2) apply saved plan from before the PR (pipeline stores last known-good plan); 3) promote previous module tag in module registry and re-run apply.

Metrics and alerting

Recommended metrics to emit from the egress-testbed exporter:
- egress_testbed:http_success_rate (gauge, 0-100)
- egress_testbed:bandwidth_mbps (gauge)
- egress_testbed:nat_sessions (gauge)
- egress_testbed:tag_coverage_pct (gauge)
- egress_testbed:test_duration_seconds (histogram)

Suggested alert rules (examples):
- ALERT EgressContractFailure WHEN egress_testbed:http_success_rate < 99.9 for 5m FOR 1m
- ALERT EgressBandwidthDrop WHEN egress_testbed:bandwidth_mbps < 80% of contract_burst for 2m

Ownership and run cadence

- Owner: Network Platform (eng-infra/networking)
- Secondary: GPU Fleet (eng-infra/gpu-fleet-and-capacity) for tenant impact analysis
- Scheduled runs: nightly in staging accounts; preflight runs before any ci-cd promotion touching egress modules; weekly canary in prod-mirroring account.

Security and IAM model

- Provisioned roles use short-lived credentials minted by the central provisioning service.
- Ephemeral NATs created with a least-privilege role: no access to customer data, only to tagging and metrics write.
- All pcap artifacts are stored in encrypted buckets with lifecycle 30 days, tagged with run-id and owner team.

Testing matrix and acceptance checklist

1. Module plan + lint: terraform validate + tflint + tfsec (no high severity findings).
2. Provisioning smoke: nat_ip responds to ICMP and metadata endpoint configured.
3. HTTP contract: 2m window at 1-3 rps, 99.95% success.
4. Burst contract: iperf runs at configured bandwidth for 60s.
5. Labeling test: random header injection and NAT-tag confirmation.
6. Billing reconciliation: ensure exported tag summary matches the billing-collector mapping.

Operational notes and gotchas

- Be careful with ephemeral_ttl_hours: long-lived ephemeral NATs can accidentally get picked up by billing reports.
- Shadow-router increases test complexity; isolate it from production BGP sessions.
- On AWS, NAT instance vs NAT gateway cost/behavior differs; our module defaults to instance for testbeds to allow packet capture.
