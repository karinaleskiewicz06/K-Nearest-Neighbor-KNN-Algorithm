Ephemeral Sandbox Lane Provisioner — Terraform Adapter and CI Integration

Summary

This design and runbook describes the Ephemeral Sandbox Lane Provisioner: a Terraform-focused operator + CI adapter that creates short-lived GPU tenant sandboxes with isolated network lanes (egress-sharded), per-sandbox IAM, and integrated cost accounting. The goal is to let developers and evaluators provision production-like GPU sandboxes (0.5–8 GPUs) for up to configurable TTLs while ensuring egress, billing, and security guardrails are enforced automatically.

Goals
- Fast self-service provisioning via CI pipeline or web UI (<= 5 minutes typical)
- Strong network isolation and egress fencing per sandbox
- Automatic reclaim and cost chargeback with audit trail
- Repeatable Terraform modules and operator for multi-account/environments
- CI adapter that enforces policy and runs pre-delete safety checks

Non-goals
- This doc does not replace long-lived Dedicated capacity provisioning.
- It does not detail GPU driver image creation (see gpu-node-bootstrap pipeline).

Design overview

1) Actors and components
- Provisioner Operator (k8s controller): watches Sandbox CRs and reconciles TF resources via a TF runner pod.
- Terraform Adapter Module (reusable): exposes inputs for GPUs, CIDR allocation, egress policy, and billing tags.
- CI Adapter (pipeline tasks): provides pre-apply linting, security gating, and post-destroy verification.
- Egress-shard Gateway (network proxy): enforces per-sandbox egress quotas and NAT mappings.
- Billing Sidecar (metashop collector): tags resources and emits cost events to chargeback ledger.

2) Workflow (user story)
- Developer opens a PR referencing a sandbox blueprint (or runs self-serve UI).
- CI runs the Terraform adapter lint, then the operator applies the sandbox (TTL: 3h default).
- Operator creates: tenant VPC subnet, ephemeral credentials, GPU node pool (or attaches to warm pool), egress lane rules, Cloud NAT assignment, and KMS-bound secrets.
- Billing sidecar tags all created resources with sandbox_id and owner for chargeback.
- On TTL expiry or explicit destroy, operator drains workloads, snapshots any requested checkpoints, runs a pre-destroy security scan, then destroys resources and archives logs.

Key constraints and safety guardrails
- Max GPUs per sandbox: configurable policy (default: 4) enforced by operator admission.
- Egress cap: default 10GB/day per sandbox; enforced at egress-shard gateway and reconciled to billing.
- Immutable production endpoints: sandbox subnets cannot inject routes into prod VPCs (IAM + route table guard).
- TTL enforcement: operator ensures destroy >= last_touch + grace period; manual extends require approver role.

IAM and secrets model
- Per-sandbox service account with least-privilege for: subnet modification, node-pool attach/detach, NAT mapping, secrets write to KMS-scoped secret.
- Short-lived TLS certs for developer ssh to bastion (if allowed) minted via ephemeral-ssh-cert operator.
- KMS keys are customer-managed in enterprise environments; operator supports injecting external key ARN.

Table: IAM roles created by module
| role_alias | permissions | notes |
|---|---|---|
| sandbox-admin | ec2:CreateTags, ec2:RunInstances, iam:PassRole | scoped to sandbox resources |
| sandbox-network | ec2:CreateRoute, ec2:ModifySubnetAttribute | limited to sandbox subnets |
| sandbox-nat | cloudwatch:PutMetric, compute:nat:Assign | write-only metrics for egress-metering |

CI integration and gating
- Pre-apply checks (must pass in CI): TF fmt/tfsec, module policy checks (OPA), gpu quotas, egress_quota sanity.
- Approval step: sandbox requests for >4 GPUs require an approver label on PR or an explicit approver in the UI.
- Post-create verification: health checks (node pool ready, egress rule active), telemetry ping, billing tags present.

Reclaim and cost accounting
1) TTL enforcement: operator runs background sweeper every 5m; sandboxes with expiry < now + grace are marked DRAINING.
2) Reclaim steps:
   1. Mark sandbox state = DRAINING and send notif to owner + slack channel.
   2. Run pre-destroy snapshot hook (optional) to S3 with retention=7d.
   3. Drain and cordon nodes; evict pods.
   4. Destroy infra with TF destroy; on failure escalate to infra-oncall.
3) Chargeback: Billing sidecar emits a cost event when resources are created and daily delta events. Chargeback keys: sandbox_id, owner, team, project.

SLOs and observability
- Provision latency SLO: 95th percentile <= 7 minutes for warm-pool attachment flows, <= 12 minutes for cold provisioning.
- Reclaim SLA: Automatic destroy completes within 20 minutes of successful destroy plan application.
- Telemetry to emit: provision.duration, destroy.duration, egress.usage_gb, cost.daily_usd.
- Dashboards: per-team sandboxes active, egress overage alerts, orphaned resources >24h.

Runbook: Responding to failed destroy
1. Incident detection: alert when TF destroy fails or orphaned aws resources detected for >1 hour.
2. Triage steps:
   1. Check operator logs (k8s namespace: infra-sandbox).
   2. Verify terraform state in remote backend: terraform state list for sandbox_id.
   3. If state contains stuck resources, attempt tf state rm <resource> -> re-run destroy.
   4. If IAM prevented destroy, escalate to cloud-account-owner with the IAM diff (copy from audit).
   5. If resources are billing-critical, run manual tagging and create a billing hold ticket.
3. Post-incident: produce an incident note in /confluence/eng-infra/runbooks and tag owner.

Testing and CI patterns
- Unit tests: module plan unit tests using terraform-compliance and kitchen-terraform.
- Integration tests: ephemeral cluster deployed into a sandbox test account; CI runs smoke provision, egress test, and destroy.
- Chaos testing: periodic chaos-day that simulates NAT SIGTERM and preemption of warm pool.

Migration and rollouts
- Blue-green tf module releases via module registry; operator reads module tag and has canary rollout config to apply to up to 10% of provisioning flows before full promotion.
- Backward compatibility: new module inputs must provide defaults and operator includes a migration transformer for older CRs.

Appendix: quick CLI cheatsheet
- Create sandbox via operator CR (kubectl apply -f sandbox-cr.yaml)
- Force destroy: kubectl annotate sandbox <id> infra.redwood/force-destroy=true && kubectl delete sandbox <id>
- Inspect terraform plan logs: kubectl logs tf-runner-<id> -n infra-sandbox
