Kernel auto-selection v2 — Known issues and workarounds

## Purpose
This page is the living source of truth for *known issues* in Kernel auto-selection v2 ("KASv2") and the approved workarounds (denylist/allowlist rules, overrides, guardrails).

**Audience:** Runtime oncall, SRE, Release Engineering, Dedicated/Private customer readiness.

**Scope:** Issues that can impact correctness, determinism/replayability, p95/p99 latency, throughput stability, or operational clarity during rollout.

---

## Quick triage checklist (oncall)
1) **Confirm it is KASv2-related**
   - Check dashboard panel: selection distribution + latency delta (v1 vs v2) for the affected model/GPU/region.
   - Verify request traces include selector fields (`selector_version=2`, chosen kernel, seq bucket).

2) **If tail latency spike or correctness concern**
   - Apply the safest mitigation first:
     - Disable v2 for *model+region* (preferred) or *GPU SKU* if localized.
     - Pin kernel to stable fallback if disabling v2 is too broad.
   - Validate recovery using p95/p99 and error rate within 10–20 minutes.

3) **Capture minimum artifacts**
   - Selection trace sample (10–50 requests): features, candidates, chosen kernel.
   - GPU SKU normalization string(s), driver/CUDA versions, model id + revision.
   - Workload description: prompt length distribution + decode lengths (or observed bucket).

For exact commands and config locations, use: **Kernel selection v2 override and rollback runbook**.

## Detailed issues

### KASV2-001 — Long-context prefill mis-selection causing tail latency spikes
**Severity:** High (SLO risk)

**Symptom**
- p95 stable but **p99 spikes** (often +25–80%) for long-context workloads.
- Spikes correlate with requests where prefill tokens exceed the selector’s long-context threshold.

**Affected**
- Model families: Llama variants (including instruct), some Qwen long-context fine-tunes.
- Workload: prefill >16k tokens, or mixed traffic where the long-context share is low but impactful.
- Fleets: more pronounced on heterogeneous fleets (A100 + L40S) due to differing kernel sweet spots.

**Likely cause**
- Seq-length regime bucketing for prefill was too permissive in mixed workloads; selector chose a kernel optimized for mid-length prefill which has worse tail behavior at >16k.

**Detection signals**
- Selector telemetry shows `seq_bucket=prefill_mid` or `prefill_decode=mixed` even when observed prefill tokens are in the long bucket.
- Latency delta panel spikes only for `seq_bucket` transitions.

**Workarounds (approved)**
1) **Disable v2 for the affected model in the affected region** (preferred for immediate stabilization).
2) **Force/pin prefill kernel** for the model on the affected SKU(s) if disabling v2 is too broad.
3) **Temporary allowlist restriction**: only enable v2 for that model on GPU SKUs where long-context kernel has been validated.

**Notes / follow-ups**
- This is partially addressed by threshold updates shipped during Runtime 1.21 canary tuning. Still a watchlist item due to workload diversity.

**Last verified**: 2026-02-21

### KASV2-002 — L40S + driver 535.x crash on FlashAttention v3 kernel path
**Severity:** High (correctness + availability)

**Symptom**
- Occasional worker crash with:
  - `CUDA error: an illegal memory access was encountered`
  - or `misaligned address` originating from attention kernel launch.

**Affected**
- GPU SKU: L40S (not consistently reproducible on A100/H100)
- Driver/CUDA: NVIDIA 535.x (most reports on 535.129–535.161)
- Kernel family: FlashAttention v3 attention kernels (prefill + decode variants)

**Likely cause**
- Driver interaction with FA3 kernel variant under specific head dimensions / rotary embedding settings.

**Workarounds (approved)**
- **Hard denylist** the FA3 kernel variants for `gpu_sku=L40S` when `driver_major=535`.
- Fallback to FA2 or baseline attention kernels per ADR fallback precedence.
- If Dedicated/Private cannot change drivers quickly: keep denylist and plan driver upgrade.

**Operational guidance**
- If crash rate > 0.1% of requests on the pool, treat as rollback trigger for v2 on that pool.

**Last verified**: 2026-02-25

### KASV2-003 — Throughput jitter on H100 pools under mixed seq regimes
**Severity:** Medium (performance stability)

**Symptom**
- Throughput oscillates (e.g., ±10–20%) across 5–15 minute windows.
- p95 latency may remain acceptable; p99 can degrade during oscillation.

**Affected**
- GPU SKU: H100 (SXM and PCIe), especially when pools run both short chat and long summarization.
- Workload: time-varying traffic mix (diurnal) or bursty long-context jobs.

**Likely cause**
- Selector decisions are correct per-request, but too reactive without using recent workload distribution hints; frequent switching between kernels interacts poorly with batching/kv-cache locality.

**Workarounds (approved)**
1) **Enable scheduler seq-distribution hints** to the selector (requires control-plane config + runtime flag in the pool).
2) Increase decision cache reuse for `(model_revision, gpu_sku, seq_bucket)` when the fleet is stable.
3) If jitter persists, restrict v2 to stable kernels only (allowlist) for that model family on H100.

**Last verified**: 2026-02-18

### KASV2-004 — Non-deterministic selection due to inconsistent GPU SKU normalization (incl. MIG)
**Severity:** Medium (determinism + operability)

**Symptom**
- Same request (features identical) yields different chosen kernel across replicas.
- Replay tests pass in CI but fail intermittently in specific clusters.

**Affected**
- Environments where GPU identity strings differ by:
  - cloud instance naming
  - driver reporting differences
  - MIG partition naming (e.g., `A100 40GB MIG 1g.5gb`)

**Likely cause**
- Selector key includes normalized `gpu_sku`. If normalization differs across nodes, candidate sets differ.

**Workarounds (approved)**
- Apply the SKU normalization patch set in the fleet (control-plane normalization + runtime canonicalization).
- Until normalization is confirmed, **disable v2 when `gpu_partitioned=true`** (MIG) for production pools.

**Last verified**: 2026-02-12

### KASV2-005 — FP8 decode instability / quality drift on H100 for specific model variants
**Severity:** Medium (quality + stability)

**Symptom**
- No crash, but:
  - increased token-level mismatch vs baseline
  - occasional decode instability (retries / early termination)
  - customer-reported “weird outputs” localized to a model revision

**Affected**
- GPU SKU: H100
- Kernel: FP8 decode kernels (variant-specific)
- Models: certain fine-tunes where activation ranges differ from base checkpoints

**Likely cause**
- FP8 kernel path requires stricter calibration assumptions than BF16; some model revisions violate expected ranges.

**Workarounds (approved)**
- Keep FP8 decode **allowlist-only**:
  - allowlist by `(model_revision, gpu_sku)`
  - default fallback to BF16 decode when not explicitly allowed
- For Dedicated/Private: provide an explicit config knob to disable FP8 decode kernels while keeping v2 enabled.

**Last verified**: 2026-02-23

---

### KASV2-006 — Telemetry cardinality increase causing dashboard noise / false alerts
**Severity:** Low (observability)

**Symptom**
- Alert fatigue: perf-canary / rollout panels show scattered spikes.
- Metrics backend reports high cardinality due to `candidate_kernels` / `kernel_variant` tags.

**Affected**
- Canary regions with high model diversity.

**Workarounds (approved)**
- Reduce sampling rate for verbose selector events.
- Emit candidate set as a **hashed bucket** instead of raw list.
- Update dashboards to group by `kernel_family` rather than `kernel_variant` where possible.

**Last verified**: 2026-02-14

### Example policy snippet (illustrative)
Use the control-plane policy engine configuration format from the rollout runbook. Example below demonstrates the intent only.

- Deny v2 on L40S with driver 535.x:
  - match: gpu_sku == "L40S" AND nvidia_driver_major == 535
  - action: set selector_version = 1

- Allow FP8 decode kernels only for validated model revisions:
  - match: gpu_sku IN {"H100-SXM", "H100-PCIe"} AND model_revision IN {"qwen2.5-72b@2026-02-10", "llama-3.1-8b@2026-02-01"}
  - action: allow kernel_family = "decode_fp8"
  - else: force kernel_family = "decode_bf16"

## Customer-facing guidance (Dedicated/Private)
- If the customer has a constrained SKU (single GPU type), prefer **pinning a known-stable kernel** over frequent policy changes.
- For driver-sensitive issues (e.g., L40S 535.x), recommend a driver upgrade plan; use denylist as interim safety.
- Always document any override in the customer’s deployment record and include:
  - model(s), region(s), sku(s)
  - start time + expected duration
  - success criteria + rollback criteria

## How to add a new known issue
When adding an item, include:
- Unique ID (`KASV2-###`)
- Severity (High/Medium/Low) and impact area (correctness/perf/determinism/ops)
- Repro info: model revision, GPU SKU, driver/CUDA, seq bucket/workload
- Detection signals: metrics + telemetry fields
- Workaround: exact deny/allow/override guidance and blast radius
- Owner + review-by date

**Escalation:** If correctness is suspected (not just latency), page Runtime Kernels and Runtime Architecture/perf guardrails immediately.
