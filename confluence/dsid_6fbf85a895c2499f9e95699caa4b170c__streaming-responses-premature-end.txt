Known issue: Streaming responses may end prematurely on OpenAI-compatible API

## Summary
Some customers have reported that streaming responses on Redwood’s OpenAI-compatible API may end early (without the terminal `[DONE]` event). The HTTP status is frequently 200 and the client receives partial tokens before the stream disconnects.

This is most frequently observed in **eu-west** and appears correlated with periods where upstream token generation is temporarily quiet long enough to trigger a gateway read/idle timeout.

## Symptoms
- Client sees partial SSE token events, then a stall (10–20s reported), then connection closes
- Missing final SSE terminal event (`[DONE]`)
- Partial assistant output surfaced to end users
- Retries can cause duplicate token usage if not guarded

## Affected surfaces
- Endpoint: `/v1/chat/completions` with `stream=true` (OpenAI-compatible)
- Transport: SSE over HTTP/1.1
- Highest volume of reports: **eu-west**

## Customers with confirmed reports
The following customers have provided request IDs and confirmed occurrence:
- **AsterixPay** (see SUP-2481)
- **OrchidCRM** (see SUP-2490)
- **BluePeak Analytics** (tracked in SUP-2490 comms)

## Workarounds (customer-facing)
1. Treat streams that do not end with `[DONE]` as failed and retry the request.
2. If possible, include an idempotency key on retries to reduce the risk of double processing.
3. Log `x-request-id`, region, and the last SSE event received for any truncated stream and share with Redwood Support.

## Mitigation / fix status
Engineering is rolling out two mitigations in eu-west first:
- Emit periodic SSE heartbeat comments when upstream tokens are quiet (prevents idle timeout closes).
- Increase gateway read timeout for OpenAI-compat streaming routes.

We will update this page once rollout is complete and confirm whether the issue is fully resolved.
