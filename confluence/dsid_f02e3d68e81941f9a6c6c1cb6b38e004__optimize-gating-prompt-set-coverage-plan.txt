Optimize Quality Gates — Prompt Set Coverage Plan (v1)

## Overview
Optimize can recommend batching, prefix/KV caching, and quantization profile changes that materially affect model outputs. Quality gates require representative, stable prompt sets to detect regressions before an optimization is applied to production traffic.

This document defines:
- The workload categories we must cover
- Sampling strategy (including token length distribution, language, and formatting constraints)
- What “golden outputs” mean for gating (and what we do *not* attempt)
- A catalog of known hard cases (especially for quantization + long context)
- Ownership and maintenance workflows (including quarantine for flakiness)

## Non-goals
- This plan does not redefine gating metrics/thresholds. See: **Quality Gate Metrics and Thresholds v1**.
- This plan does not overhaul model onboarding benchmarks; it integrates with the existing eval-harness prompt suite system.

## Key principles
1) **Coverage is stratified, not “one giant set”.** Different optimization types fail differently; suites must be analyzable by slice.
2) **Golden = evaluable artifacts, not exact text match.** For most prompts, exact-string goldens are brittle.
3) **Bounded cost/latency.** Every prompt set has a smoke tier and a full tier.
4) **Reproducible and auditable.** Every gate run must reference a prompt-set version and include artifacts (inputs, outputs, scores, and evaluator versions).
5) **Privacy by default.** Prompt sets used for gating are synthetic or explicitly approved/redacted; no customer PII.

## Prompt set taxonomy (what we cover)
We maintain multiple suites, each tagged for routing and analysis. A “gate run” selects suites based on config diff type, model family, and (where relevant) hardware SKU.

### Coverage table (v1)
Format: `Suite ID` | Primary workload | Why it matters for Optimize changes | Included in smoke? | Included in full?

- **opt.gate.chat.general.v1** | General chat + instruction following | Catches broad semantic drift, refusal/overcompliance changes | Yes | Yes
- **opt.gate.rag.qa.v1** | RAG-style QA with provided context | Sensitive to caching/prefix changes and long-context attention behavior | Yes | Yes
- **opt.gate.summarization.v1** | Summarization with constraints (length, bullet format) | Sensitive to quantization affecting coherence + constraint adherence | Yes | Yes
- **opt.gate.extraction.json.v1** | JSON/structured extraction (schemas) | Quantization and batching can break formatting; easy pass/fail checks | Yes | Yes
- **opt.gate.toolcalling.v1** | Function/tool call selection + argument JSON | Detects subtle format/tool selection regressions | Optional (subset) | Yes
- **opt.gate.code.basic.v1** | Short code generation + fixes | Token distribution differs; catches syntax and compilation regressions | No | Yes
- **opt.gate.math.numeric.v1** | Numeric reasoning / unit conversions | Quantization may impact exactness; evaluator can be deterministic | No | Yes
- **opt.gate.multilingual.v1** | Non-English (ES/FR/DE/JA) instructions | Ensures optimizations don’t disproportionately harm non-English | No | Yes
- **opt.gate.longctx.stress.v1** | Long context (8k–32k) w/ “needle” facts | Critical for KV cache/quant profiles; higher variance | No | Yes (selective)

Notes:
- Smoke tier always includes at least one structured suite (**extraction.json**) plus one semantic suite (**chat.general**).
- Long-context stress runs are **not** default for every change due to runtime cost; they are required for:
  - quantization profile changes that affect attention/KV kernels
  - cache policy diffs that touch eviction, compression, or prefix-sharing behavior

## Sampling strategy
### 1) Stratified sampling dimensions
Each suite is constructed with explicit strata so we can ensure stable representation across changes.

Required strata (applies to all suites unless stated):
- **Prompt length**: short (≤256 tokens), medium (257–1024), long (1025–4096), and longctx (≥4097 where applicable)
- **Output length targets**: short (≤128), medium (129–512), long (513–2048)
- **Constraint intensity**:
  - none (open-ended)
  - soft constraints (tone/format hints)
  - hard constraints (exact JSON schema, strict bullet counts, “must include N items”, etc.)
- **Temperature sensitivity**: prompts flagged where minor randomness causes large semantic changes (used for flake modeling)
- **Safety/refusal boundary**: a small, curated set to ensure refusals don’t flip unexpectedly (kept minimal and reviewed)

Additional strata (suite-specific):
- RAG QA: context size buckets; answerability (answer present vs “not in context”)
- Extraction JSON: schema complexity (flat vs nested), numeric + date fields, Unicode edge cases
- Tool calling: tool choice ambiguity levels; argument validation complexity
- Longctx stress: needle position buckets (early/mid/late), distractor similarity levels

### 2) Prompt counts and budgets
We maintain two tiers:

**Smoke tier (fast gates)**
- Goal: fast feedback for Optimize recommendation UI and CI-level checks
- Target size: **50–120 prompts** total (across multiple suites)
- Target runtime: **≤12 minutes** on standard shared eval GPU pool per model/config pair
- Retries: limited (see flake policy below)

**Full tier (release gates / apply-to-prod eligibility)**
- Goal: statistically meaningful detection of small-but-real regressions
- Target size: **400–900 prompts** total depending on model family and change type
- Target runtime: **45–120 minutes** (bounded); longctx suite may be run as an add-on job

Default inclusion by config diff type:
- **Batching policy change**: chat.general + extraction.json + summarization; optional toolcalling subset
- **Caching/KV policy change**: rag.qa + longctx.stress (if touching eviction/compression/prefix-sharing) + extraction.json
- **Quantization profile change**: extraction.json + math.numeric + longctx.stress (model-dependent) + chat.general

### 3) How we source prompts
Accepted sources:
- **Synthetic prompts** authored internally to reflect common product patterns
- **Public datasets** (license-checked) transformed into prompt format with attribution stored in metadata
- **Opt-in customer exemplars** only if explicitly approved by Legal/Security and redacted; default is *not* to use customer prompts

Disallowed:
- Raw customer traffic prompts
- Prompts containing secrets, credentials, personal data, or proprietary documents

### 4) Versioning and immutability
- Prompt sets are versioned as `suite_id@semver` (e.g., `opt.gate.extraction.json.v1@1.3.0`).
- A gate run must reference an immutable prompt-set version; no “latest” pointers in production gating.
- Changes that materially alter suite difficulty require a minor version bump; evaluator changes require at least a patch bump.

## Golden outputs: definition and implementation
### What we mean by “golden”
For gating, we treat “golden” as **a reference evaluation artifact** used to score outputs consistently across baseline vs candidate configs. We do **not** require exact-text matching except for narrowly defined deterministic tasks.

Golden artifacts include:
- Prompt + expected constraints (schema, required facts, allowed tools)
- Baseline output(s) produced by a pinned baseline config (stored for traceability)
- Evaluator configuration (rubric or deterministic checker) and evaluator version

### Golden types by suite
1) **Deterministic goldens (strict match / programmatic checks)**
   - JSON extraction: strict JSON parse + schema validation + field-level checks
   - Math/numeric: exact numeric equivalence within tolerance; unit normalization
   - Tool calling: JSON argument validity + required tool selection for unambiguous prompts

2) **Rubric-based goldens (judge/evaluator-based)**
   - Chat, summarization, RAG QA (semantic correctness, completeness, adherence)
   - Uses evaluator models + rubric prompts, with:
     - deterministic temperature settings
     - calibration examples embedded
     - explicit disallowed failure modes (hallucination, missing key constraints)

3) **Reference-output comparison (soft goldens)**
   - In a subset of prompts we compare candidate output to baseline output for consistency signals (e.g., does it omit key facts present in baseline?)
   - This is a *signal*, not the sole pass/fail condition.

### Storage and traceability
- Goldens and evaluator configs are stored as eval-harness artifacts and referenced by artifact IDs in gate runs.
- Required per-run artifacts:
  - outputs (baseline + candidate)
  - per-prompt scores
  - aggregated suite metrics
  - evaluator versions + prompt-set versions

## Known hard cases (must include)
These are regression-prone prompts that must be present in at least the full tier for relevant change types.

### Quantization-sensitive hard cases
- **Long-context needle retrieval** with distractors that share near-duplicate entity names
- **Structured JSON with Unicode + escaped characters** (e.g., quotes, backslashes, emoji/unicode categories) to catch tokenization/format drift
- **Numeric tables** where small precision errors flip categorical decisions
- **“Exact format” prompts** (e.g., JSON only, no prose) to catch verbosity creep
- **Code generation with compilation** for a minimal subset (syntax correctness is a strong early warning)

### Caching/KV policy hard cases
- **Prefix sharing boundaries**: prompts where the beginning is identical but later context diverges; ensures caching isolation
- **Eviction pressure**: multi-turn prompts where key facts are introduced early and referenced late
- **System prompt + tool spec changes**: prompts that rely on tool definitions appearing early in the context

### Batching policy hard cases
- **High concurrency-style prompts** simulated by mixed prompt lengths within the same batch to catch scheduling-induced truncation/latency-side behaviors that might surface timeouts or partial outputs
- **Streaming boundary prompts** where early tokens must adhere to strict structure (e.g., JSON starts immediately)

## Flakiness management and quarantine policy
We expect some variance in rubric-based evaluation and in model outputs. Prompt sets must be stable enough to support gating.

### Flake score and actions
- Each suite maintains a rolling **flake score** (see eval-harness flake scoring).
- Action thresholds (initial policy; subject to tuning with Sana Farid):
  - **flake_score < 0.05**: normal
  - **0.05–0.12**: warn; require 1 automatic rerun for failing runs
  - **> 0.12**: quarantine suite subset from smoke tier; require owner review before re-enabling

### Rerun rules (gating)
- Smoke tier: at most **1 rerun** and only if failure is within “near-threshold” band.
- Full tier: up to **2 reruns** with aggregated decision logic (median-of-runs for rubric suites; best-of for deterministic checks is not allowed).

### Quarantine workflow
- Suite owner files a ticket tagged `quality-gates-flake` with:
  - prompt IDs suspected
  - evaluator version
  - failure pattern
  - proposed fix (prompt rewrite, rubric clarification, or evaluator update)
- Quarantined prompts are not deleted; they are moved to `opt.gate.quarantine.*` suites for tracking.

- All suite changes go through PR review (eval-harness repo or prompt-set repo), with:
  - clear changelog
  - before/after difficulty check on baseline config
  - flake score re-estimation on at least one representative model

- **Monthly:** flake review, quarantine sweep, and evaluator drift check
- **Quarterly:** add new coverage based on:
  - observed gate escapes
  - new model families/hardware SKUs
  - new Optimize recommendation types (future)

## Appendix A — Minimum acceptance checklist for a new suite
A suite can be admitted to smoke or full tier when:
- It has a named owner and reviewers
- Prompt-set versioning is in place
- Evaluators are defined and pinned
- Flake score is measured and below thresholds (or flagged as full-tier-only)
- Licensing/PII review is complete
- Documentation includes: intent, strata, and known failure modes
