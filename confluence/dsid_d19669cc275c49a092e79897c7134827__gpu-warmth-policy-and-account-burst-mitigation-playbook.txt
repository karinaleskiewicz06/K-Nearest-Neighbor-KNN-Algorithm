GPU Warmth Policy and Multi-Account Burst Mitigation Playbook

Summary

Purpose:
This playbook defines the GPU "warmth" policy (what we call node/slot readiness for low-latency inference) and prescribes a cross-account burst mitigation strategy to protect multi-tenant capacity, egress, and billing signals during demand spikes. It combines runtime controls, Terraform/IaC patterns, CI/CD gating, and runbook steps for incident responders and infrastructure owners.

Audience:
- Infra oncall and SREs
- Platform engineers owning GPU pools and tenant routing
- IaC/TF module authors
- Security and finance stakeholders for billing/leak protection

Scope:
- Applies to hosted and dedicated GPU pools (cloud regions) and bursting flows that cross accounts or organizations.
- Covers: warm-pool sizing policy, preempt-aware seeding, cross-account egress controls, Terraform module parameters for burst controls, CI/CD gates for image/driver rollouts, and an operational runbook for mitigation.

Definitions
- Warmth: a numeric score (0-100) assigned to each GPU node/slot representing readiness for low-latency requests. Factors include KV cache priming, kernel warmup, and networking egress path pre-qualification.
- Burst: a short-duration (<= 15 min) aggregate increase in inbound inference request QPS that requires additional capacity or cross-account borrowing.
- Borrowing window: the time interval where a tenant may use another account's burst capacity under agreed cost/credit rules.

Policy Overview
- Baseline SLOs:
  - P95 latency impact to pinned tenants <= +10% during controlled burst-handling (goal).
  - No tenant billed >2x expected egress band in a single burst window without an approval/escrow event.
  - Warmth recovery (cold -> warm) target: 90% of slots within 90s for prefix-warmed requests.

- Controls (ordered by preference):
  1. Automatic prefix caching and KV seeding for priority tenants.
  2. Conservative autoscale with warm-pool reservation per-tenant.
  3. Cross-account borrowing with escrowed credits and egress fencing.
  4. Circuit-breaker: per-tenant throttles with graceful 503 surface and fallback model variant.
  5. Emergency manual drain/evict for noisy tenants.

Warmth Scoring Model (high-level)
- Score components (weights):
  - KV cache hit likelihood (40%)
  - Recent inference QPS affinity (20%)
  - Kernel/driver warm cycles (20%)
  - Egress path verification (10%)
  - Hardware thermal headroom (10%)
- Implementation note: score calculated by runtime probe every 30s and exported as telemetry: metric name infra.gpu.warmth_score{pool,slot,tenant}.

Terraform / IaC Patterns
- Provide a small, reusable Terraform module to declare warm-pool reservations and cross-account escrow objects. Example usage: 

  module "warm_pool_reservation" {
    source = "git::ssh://git.internal/repo/terraform-modules.git//gpu-warm-pool?ref=v1.4.0"

    name                = "region-us-west2-warm-reserve"
    region              = "us-west2"
    min_reserved_slots  = 50
    per_tenant_quota    = { "tenant-a" = 10, "tenant-b" = 8 }
    max_burst_multiplier = 2.0
    escrow_account_id   = "123456789012"
  }

- Required module variables (table):
  - name: string - human identifier
  - region: string - cloud region
  - min_reserved_slots: number - lower bound of warm pool active slots
  - per_tenant_quota: map(string -> number) - pre-allocated warm slots per tenant
  - max_burst_multiplier: number - limit for per-tenant burst over quota
  - escrow_account_id: string - account used for cross-account borrowing billing reconciliation

- Best practices:
  - Keep min_reserved_slots <= 20% of total pool to avoid long-term underutilization.
  - Use per_tenant_quota for top 10% of tenants by spend.
  - Tie escrow_account_id to a billing notification webhook and an automated cost-reconciliation job (batch).

CI/CD and Gating
- Driver and kernel rollouts must execute through canary lanes that simulate warm-pool traffic:
  1. Canary pipeline generates synthetic inference traffic with KV prefixes and burst patterns.
  2. Metrics must pass warmth regression checks (see testing below) before promotion.
  3. A fail-open toggle exists but is gated behind oncall approval; default is fail-closed (block promotion).
- Recommended test matrix in CI: 
  - Short prefix load (5s pulses) measuring P95 warmup latency
  - Sustained small-burst (5m) measuring egress and billing telemetry
  - Preemption injection where spot nodes are removed and recovery observed

Operational Runbook (for oncall)
- Symptom: sudden latency spike and large egress billing delta for a tenant; metrics: infra.gpu.warmth_score drops; queue length increases.

Step-by-step mitigation:
1. Triage (0-5 min):
   - Identify impacted pool (dashboard: GPU Pool Overview).
   - Query metrics:
     - infra.gpu.warmth_score{pool=..} (trend)
     - infra.gpu.queue_length{tenant=..}
     - billing.egress.delta_last_15m{tenant=..}
   - Check recent IaC events (terraform apply jobs) and CI/CD promotions.
2. Short-term containment (5-15 min):
   - If noisy tenant: enable per-tenant rate limiter to cap QPS to "burst_allowed" limit.
   - If cross-account borrowing triggered unexpectedly: pause further borrow ops via escrow API: POST /internal/escrow/{id}/pause
   - If warmth_score is uniformly low: enact fast-warmup by activating reserved slots: terraform apply -var 'force_activate=true' module warm_pool_reservation
3. Recovery (15-90 min):
   - Gradually increase warm pool reservation to meet observed demand; monitor thermal headroom.
   - Use tenant fallback model variants (smaller models) if latency SLOs are at risk.
4. Post-incident (90m+):
   - Run billing reconciliation for escrow flow and open a chargeback ticket if needed.
   - Create a postmortem if the event violated SLO or caused >$X unexpected cost.

Escalation Matrix
- Level 1 oncall (infra): execute triage and short-term containment.
- Level 2 (platform core): run Terraform changes and negotiate escrow unpause.
- Level 3 (SRE lead + Finance): review billing anomalies and authorize cross-account credits.

Testing and Canary Criteria
- Warmth regression thresholds (gate tests):
  - P95 generation latency must not increase >8% vs baseline during synthetic warmup.
  - KV cache hit rate drop <= 3 percentage points.
  - Recovery time from cold to targeted warmth_score >= 90% within 90s.
- Synthetic tests should be run daily in CI and prior to any GPU runtime/driver promotion.

Observability and Dashboards
- Required dashboards/tiles:
  - Warmth score histogram by pool and tenant (last 1h / 24h).
  - Borrowing events timeline (who borrowed, amount, duration).
  - Egress delta alarms per-tenant (threshold: > 150% of 1h baseline).
  - Canary CI burn chart for kernel/driver releases with warmup checks.

Metric names (telemetry):
- infra.gpu.warmth_score{pool,slot,tenant}
- infra.gpu.warm_pool_reserved_slots{pool}
- infra.gpu.borrow_events{from_account,to_account,tenant}
- infra.gpu.preemption_rate{pool}
- billing.egress.delta_last_15m{tenant}

Implementation notes for runtime engineers
- Warmth scoring should be implemented in the runtime's health sidecar so it can be independently queried and updated without a full model process restart.
- Expose a short-lived token-based admin API for pausing/resuming cross-account borrow flows; every operation must be logged to audit-log+billing pipeline.

Rollout plan for the policy
1. Stage: lab (2 weeks) - implement module and local warm-pool simulator, add metric exports.
2. Stage: canary (4 weeks) - enable in us-west2 on 1/4 of capacity; exercise synthetic burst tests nightly.
3. Stage: regional (6 weeks) - expand to two regions and enable cross-account escrow for a small tenant cohort.
4. Stage: global (8 weeks) - enable as default for all hosted pools; surface controls in Redwood Console.

Rollback guidance
- If warm-pool changes cause regression in latency or availability:
  - Revert Terraform changes using git tags and terraform apply -target to revert resource variations.
  - If rollback fails, scale down new reserved slots and drain new nodes.

Security & Billing controls
- All escrow operations must be authenticated via service identity and require a two-person approve for credit > $5k/day.
- Egress fencing prevents borrowed flows from exceeding per-tenant egress multiplier by writing egress policies into the per-tenant NAT/proxy.

FAQ
Q: Why not keep a bigger warm-pool all the time?
A: Warm pools have material cost and utilization tradeoffs. This policy prescribes a modest reserve for reliability and uses cheap, automated borrowing for short bursts.

Q: How do we measure fairness during borrowing?
A: The borrowing ledger records borrow volume and time; fairness reports are generated daily and used in tenant chargeback reconciliations.
