gpu-hotpatch-safeguard-and-rolling-drain-playbook

Overview
-------
This playbook defines the safe, auditable procedure for applying kernel/driver hotpatches and userland security fixes to GPU worker nodes, coordinating rolling drains, IaC feature flags, and CI/CD gating. It is intended for platform and infra engineers performing maintenance on shared GPU pools (ephemeral or production). The runbook emphasizes minimal impact to latency SLOs, predictable capacity changes, and fast automated rollback if regressions are detected.

Scope and applicability
----------------------
- Applies to all GPU worker node pools managed by the GPU orchestrator service (service name: gpu-orch).
- Includes: OS kernel hotpatches, NVIDIA driver minor updates (non-major ABI changes), runtime bundle updates (signed-gpu-runtime), and node-level security patches.
- Excludes major driver upgrades that change PCI IDs or require model re-baking — those are handled via the full versioned upgrade ADR.

Key goals and SLO constraints
----------------------------
- Maintain 99.9% application-level token-latency SLO during the maintenance window where possible.
- Keep global GPU capacity drain under the configured burst budget: default 10% of total GPU capacity for non-emergency hotpatches.
- Canary progress step must not increase 95th-percentile p99 inference latency by more than 20% relative to baseline or increase error rate by >0.5 percentage points.

Prerequisites and prechecks (Preflight)
--------------------------------------
1. Verify scheduled maintenance window has been approved in calendar and change-management ticket exists. Include: start/end times, expected impact, rollback SLA.
2. Ensure current fleet utilization snapshot is captured: run `curl -s http://gpu-orch.internal/metrics/pool-status` and save JSON to the ticket.
3. Confirm at least 1.5x warm-pool reserves exist (warm-pool and burst pools combined) for the target tenant class.
4. Confirm signed images are built and available: `registry.redwood.net/gpu-runtime/signed:YYYYMMDD-<sha>` and listed in the artifact catalog.
5. Check automation toggles in Terraform workspace: ensure `hotpatch_rollout_enabled` = true in the feature-flags module (see terraform workspace: infra-features/gpu-hotpatch).
6. Validate network path and NAT/egress budget: ensure egress pool assignment and cross-account peering are green via `egress-health check` in the networking dashboard.

Roles and ownership
-------------------
- Runbook owner: eng-infra/platform (oncall owner for window).
- Primary executor: platform engineer assigned to the maintenance ticket.
- Canary validation owner: runtime-performance (responsible for latency/throughput checks).
- Escalation target: SRE lead for GPU fleet (page: oncall list).

Components touched
------------------
- gpu-orch (routing + scheduler)
- node-agent (handles cordon/drain/shutdown hooks)
- capacity-orchestrator (manages warm-pool and burst capacity)
- signed-gpu-runtime (OCI image registry and image signer)
- terraform modules: `modules/feature-flags`, `modules/gpu-node-pools`
- CI/CD pipelines: buildkite job `gpu-runtime/canary-deploy` and `gpu-runtime/promote`

High-level procedure (summary)
------------------------------
1. Preflight checks and snapshot telemetry
2. Toggle IaC feature flags (if required) and run a dry-run `terraform plan` in infra-features workspace
3. Launch canary group (1–3 nodes or 1–3% of pool, whichever is greater) using `gpu-orch canary-create`
4. Validate canary: perf suites, smoke tests, and traffic injection for 30–45 minutes
5. If canary OK, advance to progressive rolling drains in batches (size controlled by capacity budget)
6. Post-deploy verification and close ticket

Detailed step-by-step runbook
-----------------------------
A. Preflight commands and artifacts
- Collect fleet snapshot (save to ticket):
  - `curl -sS http://gpu-orch.internal/metrics/pool-status > /tmp/pool-status-$(date +%F).json`
  - `kubectl get nodes -l pool=gpu -o wide`
- Confirm signed image exists:
  - `regctl manifest get registry.redwood.net/gpu-runtime/signed:20251201-abcdef`
- Terraform feature flag dry-run:
  - `cd infra/terraform/workspaces/infra-features`
  - `terraform workspace select gpu-hotpatch || terraform workspace new gpu-hotpatch`
  - `terraform plan -var "hotpatch_rollout_enabled=true" -out=plan.out`
  - Review plan and attach to ticket.

B. Canary creation (automated via CI/CD)
1. Trigger canary deploy (Buildkite):
  - Start job: `buildkite-agent pipeline upload .buildkite/gpu-runtime/canary.yml --env IMAGE_TAG=20251201-abcdef`
2. CI job will call gpu-orch API to provision canary nodes with image tag and ensure nodeAgent health hook runs.
3. Wait for nodes to register: `gpu-orch canary-status --canary-id <id>`

C. Canary validation checklist (30–45m)
- Functional smoke tests: run inference on representative prompt set (prompt-set: security-hotpatch/check-01).
- Performance tests (automated):
  - Run `perf-checker run --suite hotpatch-canary` and confirm metrics saved.
  - Required pass: p50/p95 delta < 10% and p99 delta < 20% vs baseline.
- Error and retry checks: evaluate request success rate and transient error rate < 0.5% absolute.
- KV/prefix cache sanity: ensure warm-cache hit rate for RTT-critical routes remains within 5% of baseline.

D. Canary failure handling (immediate steps)
1. If any check fails, stop rollout: mark canary as failed via `gpu-orch canary-fail --id <id>`.
2. Revert image on canary nodes back to previous signed tag using `gpu-orch node-update --node <id> --image <previous-tag>`.
3. Notify channel #infra-gpu-maint with templated message (see message template section).
4. Open postmortem ticket and tag `regression-hotpatch`.

E. Progressive rolling drain and patching (if canary OK)
- Batch sizing: default 2–4 nodes per batch for large pools; smaller pools use 10–20% of pool. Constrain batch size such that total draining capacity <= configured burst budget (default 10%).
- Automated sequence (recommended):
  1. For batch in planned_batches:
     a. Mark nodes as cordoned: `kubectl cordon <node>` or `gpu-orch node-cordon --node <id>`
     b. Drain with timeouts and eviction-budget enforcement: `kubectl drain --ignore-daemonsets --delete-emptydir-data --grace-period=300 --timeout=15m <node>`
     c. Wait for nodeAgent pre-stop hooks to finish: check `node-agent logs` for `prestop:cache-flush:ok`
     d. Apply OS/driver patch via remote runbook command or `kexec` where applicable; for container runtime updates, perform `docker pull`/`ctr images pull` then restart runtime service.
     e. Reboot node if required: `sudo systemctl reboot` (nodeAgent should update node metadata when it comes back).
     f. After node returns, run post-patch smoke and perf run: `perf-checker run --node <id> --suite rolling-batch-check`
     g. If post-patch checks pass, uncordon node: `kubectl uncordon <node>` and mark batch successful.
- Maintain a stagger window of 5–10 minutes between batches to allow autoscaler and capacity-orchestrator to rebalance.

F. Rollback policy and automation
- If at any point the rolling drains increase global p99 by >20% or error rate increases >0.5pp and does not stabilize within two successive batches, automatically abort and begin rollback.
- Rollback actions:
  1. Pause further batches.
  2. For recently patched nodes (last 2 batches), re-image to previous signed runtime tag: `gpu-orch node-update --node <id> --image <previous-tag>` and reboot.
  3. If capacity shortfall persists, scale up warm-pool via `capacity-orchestrator scale --pool warm --delta +X` (requires manager approval for >20% changes).

Monitoring and telemetry required
-------------------------------
- Metric checks (automated):
  - token_latency.p50/p95/p99 per-tenant
  - request_error_rate per-tenant
  - node_registration_time histogram
  - warm_pool_fill_ratio and burst_pool_usage
  - node_agent_restart_count
- Dashboards to watch: `infra/gpu/maintenance-hotpatch` and `infra/gpu/canary-health`
- Alerts to suspend rollout: `alert:gpu-hotpatch-p99-regression`, `alert:gpu-hotpatch-error-rate-spike` (quiet hours suppressed for emergency patches only).

CI/CD and IaC interactions
-------------------------
- Buildkite pipelines:
  - `gpu-runtime/canary-deploy`: builds signed image and triggers `gpu-orch` canary API.
  - `gpu-runtime/promote`: after full rollout, promotes signed tag to `stable` channel in registry and triggers Terraform image tag update in `modules/gpu-node-pools` followed by `terraform apply`.
- Terraform patterns:
  - Use feature-flag toggle `hotpatch_rollout_enabled` to gate automated rollouts. The module `modules/feature-flags` stores toggles as a simple key/value map in the state with tagging for audit.
  - Always perform `terraform plan -out` and store plan artifact in ticket before `apply`.

Network and cross-account considerations
-------------------------------------
- Some GPU pools are in customer-dedicated accounts with constrained egress. Ensure the node image registry NAT / egress route is open for the maintenance window. If not, use pre-staged images in the account's private registry mirror.
- When draining cross-region pools, validate inter-region transit latency. Prefer region-local patching where possible to avoid multi-region QoS impact.

Safety guardrails and hard limits
--------------------------------
- Never exceed `max_drain_pct_for_maintenance` = 15% unless approved by SRE lead.
- For peak-hours (08:00–20:00 PT Mon-Fri), no more than 5% drain budget without exec approval.
- Emergency security patches: skip canary only if CVSS >= 9 and legal approves; document justification and obtain SRE lead sign-off after the fact.

Post-maintenance validation and closeout
---------------------------------------
- Run full fleet perf-checker `perf-checker run --suite post-hotpatch-full` and save outputs to ticket.
- Verify warm_pool_fill_ratio returned to normal and that autoscaler metrics show no residual backpressure.
- Update Terraform `modules/gpu-node-pools` with promoted image tag and attach the plan + apply outputs to the ticket.
- Close ticket with checklist: preflight, canary outputs, batch logs, rollback notes (if any), and post-run metrics.

Appendix: Common commands and snippets
-------------------------------------
- Cordon and drain (safe wrapper):
  - `scripts/gpu/drain-safe.sh --node <node> --timeout 900 --eviction-budget 0.1`
- Check nodeAgent status:
  - `journalctl -u node-agent -f -n 200`
- Re-image node via gpu-orch API: (curl example)
  - `curl -X POST -H "Authorization: Bearer $TOKEN" -d '{"node":"i-0123","image":"registry.redwood.net/gpu-runtime:prev-20251130"}' https://gpu-orch.internal/api/v1/node/reimage`
