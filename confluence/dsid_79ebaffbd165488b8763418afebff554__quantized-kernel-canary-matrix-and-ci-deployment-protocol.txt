Quantized Kernel Canary Matrix and CI Deployment Protocol

Summary:
This document defines the end-to-end canary and CI deployment protocol for shipping quantized inference kernels across heterogeneous GPU families. It contains the experimental matrix (GPU families, quant formats, model archetypes), CI pipeline stages, telemetry gating rules, rollout and rollback criteria, IaC snippets for feature gating, and an operational troubleshooting checklist. The goal is to minimize customer-visible regressions (latency, correctness) while enabling cost-reducing quantized kernels to reach production safely.

Intended audience:
- Runtime engineers responsible for kernel builds and releases
- CI/CD and release engineers
- Serving and infra SREs running canaries
- Platform/product owners tracking performance economics

Background and motivation:
As we add quantized execution paths (int8/4, nf4, dynamic quant), kernel behavior can diverge across GPU microarchitectures (A100/H100/L4/RTX/Infer32). Small numerical differences and microkernel scheduling can result in subtle latency spikes or accuracy regressions for particular prompt shapes. We need a systematic canary protocol that: 
- Validates performance and correctness across representative workload slices
- Runs as part of CI for kernel artifacts and again as a gated canary in the staging fleet
- Provides reproducible rollback criteria and automated safety gates

Key definitions and SLAs:
- Canary run: a staged traffic experiment targeting a small window of production-like instances with shadowed or sampled real traffic.
- SLOs for kernel merges to master: no P95 latency regression > 12% and no model-level accuracy regression > 1.5% on the canonical eval set for the target model archetype.
- Canary SLOs: P50/P95 latency within 10% of baseline, 99.9% successful stream rate for streaming API paths, and token generation quality metrics within configured thresholds.

Quantized Canary Matrix (canonical):
| GPU family | Quant modes | Representative model archetype | Typical sequence lengths | Notes |
| A100 (PCIe/80GB) | int8, int4, nf4 | 7B causal / chat | 64, 512 | Baseline for host fleet; stable kernels first validated here. |
| H100 (HBM3) | int8, nf4 | 34B encoder-decoder | 128, 1024 | Check large KV cache behavior and HBM scheduling. |
| L4 / T4 | int8, nf4 | 2B/4B generators | 32, 128 | Cost-optimized edge; watch small-batch tail latency. |
| RTX-like (dev fleet) | int8 | dev-only | 8, 32 | Early detection of vector lane issues; not for canary traffic. |

Notes on model archetypes: pick one canonical model from each size class that exercises attention, kv cache, and streaming code paths. Maintain a small but stable prompt set per archetype used in validation.

CI Pipeline Stages (automated):
1) Kernel unit tests (per-kernel correctness): fast, must pass before artifact publish.
2) Microbench harness: deterministic microbench of matmul/attention kernels across compiler flags. Baseline: within 5% of golden runs.
3) Integration smoke in emulator: run on dev docker image with CPU/GPU mock to catch obvious API/abi regressions.
4) Mixed-workload CI (nightly matrix): run the quantized kernels across the full Quantized Canary Matrix (above) using ephemeral sandbox clusters; produce per-run telemetry and diffs to baseline.
5) Canary staging rollout: push artifact to staging fleet with sampled production-like traffic (1-5% traffic or controlled shadow traffic).
6) Automated metric gate check and human sign-off window (15–60 minutes depending on model).
7) Gradual ramp to production (if canary passes) using the rollout policy in the Release Orchestrator.

Gating metrics to compute and thresholds (automated):
- Latency p50, p95, p99 (tokens and request-total) — fail if P95 increase > 12% or P99 increase > 20% over baseline.
- Successful response rate (no kernel crash, no OOM) — fail if < 99.9%.
- Throughput (tokens/sec) for fixed-batch workloads — fail if drop > 15%.
- Quality metrics: per-model eval score (BLEU/ROUGE/exact-match/LLR-based scoring) on canonical prompt set — fail if delta < -1.5% absolute or relative (configurable per model).
- Token-level distribution sanity checks (e.g., unknown token rate, stop-token frequency) — fail if anomalous spike > 5x baseline.
- Memory and GPU telemetry: sustained GPU memory usage, swap rates, kernel queue latency — fail on unexpected allocation growth > 10% sustained.
- Telemetry tagging: every canary run must tag kernel artifact id, compilation flags, CUDA/CUDNN/driver versions, and quantization profile id.

Manual and automated rollback criteria:
- Automatic rollback: any automated gate failure triggers an immediate rollback step in rollout controller (traffic shifted to last-good variant).
- Semi-automatic rollback: metric degradation outside warning but within recoverable band triggers page to owners and pauses rollout.
- Human-initiated rollback: on-call or owner can abort canary and trigger rollback with one-button action in the Release Console.

Canary deployment checklist (preflight):
- [ ] Artifact ID and provenance recorded (git commit, build id, container digest).
- [ ] Quantization profile annotated and stored in model catalog (profile id).
- [ ] Baseline telemetry snapshot for target GPU family captured within last 7 days.
- [ ] Eviction and slot pressure test run (simulate preemption).
- [ ] Alerting channels configured: #canary-alerts, oncall pager, and Release Console notification.
- [ ] Health probes and synthetic prompts configured for streaming and non-streaming paths.
- [ ] MustHave: smoke test pass on a single instance of each GPU family for this artifact.

Example IaC feature-gate snippet (Terraform) for controlled kernel rollout:
```hcl
resource "redwood_feature_flag" "quant_kernel_canary" {
  name        = "quant-kernel-canary-${var.artifact_id}"
  description = "Route X% of inference traffic to quantized kernel ${var.artifact_id}"
  project     = var.project
  default     = 0
  rules = [
    {
      type  = "percentage"
      value = var.canary_percentage
    }
  ]
  metadata = {
    kernel_artifact = var.artifact_id
    quant_profile   = var.quant_profile_id
  }
}
```
Operational runbook (on-call steps when canary alarms fire):
1) Confirm alert: check Release Console for failing gates, identify artifact id and impacted GPU family.
2) Collect immediate telemetry: p50/p95 over the last 5m, GPU memory growth graphs, OOM/driver errors.
3) If auto-rollback is not already triggered, execute emergency rollback via Release Console. Record action id.
4) If rollback not possible, reduce canary percentage to 0 and route traffic to last-good.
5) Gather reproducer prompts and attach kernel logs + driver logs; create incident if service impact > 1% traffic disruption.
6) Owners to run the directed microbench and reproduce locally following the repro steps below.

Reproducer checklist (kernel engineer):
- Reproduce deterministic failing prompt set on the same GPU family and driver combo.
- Run the quant microbench with identical compilation flags and quant profile.
- Capture kernel timelines (NVIDIA Nsight/trace or perf counters) and diff against baseline.
- If numeric correctness differs, run fallback float path to narrow root cause.

Observability and dashboards to produce per canary run:
- Canary Overview (per artifact): p50/p95/p99 latency trends, success rate, throughput, quality delta.
- GPU Family Breakdown: per-instance GPU memory, SM utilization, kernel queue latency, temperature.
- Prompt Set Replay: a table of canonical prompts and per-prompt metric deltas.
- Canary Event Log: feature-flag changes, rollout steps, rollback records, and human approvals.

Data retention and experiments store:
- Keep full canary traces (histograms and kernel traces) for 90 days. Aggregate summaries kept for 2 years for cost analysis.
- Store exact kernel build artifacts and quant profiles in the binary artifact registry with immutable IDs.

Release cadence and ownership:
- Kernel engineering owns kernel artifact creation and unit test passing.
- CI/CD team owns the mixed-workload CI stage and nightly matrix orchestration.
- Serving SRE operates the staging canary fleet and gating automation.
- Product economics owner tracks token-cost improvements and signs off on production ramp.

Rollout ornaments (best practices):
- Start with small-sequence, small-batch traffic slices before scaling to long sequences and bursty workloads.
- Use shadowing (mirror requests) to compare outputs without impacting users when evaluating quality.
- Prefer gradual ramp (1% -> 5% -> 10% -> 25% -> 50%) with 30–60 minute hold windows when quality metrics are sensitive.

Known limitations and future work:
- We currently do not support automatic cross-GPU microarchitecture translation of quant profiles; profiles are per-family. Work item: canonicalize quant-profile translation and auto-tune.
- Small-batch tail latency on L4 remains the most common source of false positives; plan: add synthetic burst tests to the nightly matrix.

Appendix: Example CI job YAML (GitLab-style)
```yaml
stages:
  - unit
  - microbench
  - integration
  - nightly_matrix

quant-kernel-microbench:
  stage: microbench
  image: gpu-build:stable
  script:
    - ./build/kernel --quant-profile ${QUANT_PROFILE} --target ${GPU_FAMILY}
    - ./test/unit
    - ./benchmark/run_microbench.sh --artifact $CI_COMMIT_SHA --out /tmp/bench.json
  artifacts:
    paths:
      - /tmp/bench.json
    expire_in: 7d
```
