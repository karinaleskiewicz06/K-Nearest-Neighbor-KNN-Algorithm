Benchmark Data Validation & Review Checklist (Latency/$ Report)

## Purpose
This checklist defines the minimum validation and review steps required before Redwood Inference publishes any benchmark-derived numbers (web table, PDF, blog charts, sales enablement). It is designed to:
- Prevent accidental cherry-picking or misconfigured runs.
- Detect missing regions/models and instability (variance) early.
- Standardize outlier handling and rerun criteria.
- Ensure public artifacts are reproducible and safe (redacted), with a clear sign-off trail.

This document applies to the **Latency/$ Benchmark Report** and any subsequent refreshes/addenda.

## Definitions (quick)
- **Run**: One execution of a workload against a specific (model, region, deployment mode, hardware profile, config).
- **Sweep**: A set of runs covering a region×model matrix.
- **Manifest**: The canonical machine-readable record for a run (config, environment, inputs, timestamps, commit SHAs, metrics pointers).
- **Derived dataset**: Aggregated outputs used in public claims (latency/$, $/1M tokens, p50/p95, throughput).
- **Stability gate**: Automated rule that triggers reruns or blocks publish when variance exceeds thresholds.

## Required artifacts (must exist before review)
[ ] 1. Run manifests for all runs included in the report (including reruns).
[ ] 2. Raw logs/metrics pointers referenced by manifests (stored per retention policy).
[ ] 3. Derived dataset (CSV + JSON) with schema version and generation timestamp.
[ ] 4. Data dictionary / metric definitions used for computation (must match methodology page).
[ ] 5. Validation report (automated checks output + manual reviewer notes).
[ ] 6. Redaction report confirming removal of sensitive identifiers in public artifacts.

## A. Completeness checks (model/region coverage)
### A1. Define the expected publish matrix
Populate the expected set for the specific release:
- Models: (list in release ticket / methodology lock)
- Regions: NA/EU/APAC where available
- Deployment mode(s): Hosted (default), and if applicable Dedicated/Private notes
- Workloads: prompt set version(s), concurrency tiers, context-length buckets

Checklist:
[ ] The expected matrix is written down (link to the release ticket / commit tag).
[ ] Each published table/chart references only a single locked matrix (no ad-hoc additions).

### A2. Missing region/model detection (hard block)
Hard-block conditions (must be resolved or explicitly removed from scope with PMM+tech lead approval):
[ ] Any expected region is missing for a model that is otherwise published.
[ ] Any expected model is missing for a region that is otherwise published.
[ ] Any expected workload tier (e.g., concurrency level) is missing for a (model, region) entry.

Acceptable exceptions (must be documented in the “Release Notes / Caveats” section of the report):
- Region temporarily unavailable due to capacity constraints AND removed consistently across all models for that section.
- Model not supported in a region (documented limitation with date).

Documentation requirement:
[ ] A one-paragraph explanation is included for each exception, with an internal link to the incident/ticket and the date.

## B. Manifest validation (reproducibility + config integrity)
### B1. Manifest schema validation (automated)
Each manifest must include, at minimum:
- Run identity: run_id, sweep_id, start/end timestamps (UTC)
- Code provenance: benchmark harness git SHA, runner image digest, config file checksum
- Environment: cloud provider, region, instance type/GPU SKU, driver/CUDA/runtime versions
- Model: model_id, model version/revision, quantization profile (if any)
- Serving config: batching on/off + parameters, caching policy + parameters, max tokens, streaming on/off (if applicable)
- Workload: prompt_set_id + version, token distribution settings, concurrency level, request rate (if rate-driven)
- Warmup: warmup duration/requests and exclusion policy
- Metrics pointers: paths/URIs to raw logs and summarized metrics
- Cost inputs: pricing table version, currency, cost attribution source

Checklist:
[ ] Manifest passes schema validation with **zero** missing required fields.
[ ] Manifest includes runner image digest (not just a tag).
[ ] Manifest includes the benchmark harness git SHA (not “dirty”).
[ ] All referenced raw metric URIs resolve and are accessible to the review group.

### B2. Config integrity (manual spot checks)
For each sweep, randomly sample at least 5% of runs (minimum 5 runs) and confirm:
[ ] Model ID/version matches the published label.
[ ] Region matches the published label.
[ ] Concurrency tier and token limits match the methodology.
[ ] Caching/batching policy matches the methodology (or is explicitly marked as an experimental addendum).
[ ] No “debug” flags were used (e.g., reduced iterations, disabled kernels, forced low batch).

## C. Data quality checks (sanity + invariants)
### C1. Basic sanity checks
[ ] No negative or zero values for latency, throughput, or cost.
[ ] p95 >= p50 for all entries (if violated: investigate aggregation bug or mixed populations).
[ ] Throughput is within plausible range for the hardware tier (flag extreme values for review).
[ ] Cost-per-token and $/1M tokens are within plausible bounds (flag order-of-magnitude errors).

### C2. Cross-field invariants
[ ] latency/$ is consistent with its definition (units and directionality). Confirm the report uses one label consistently (e.g., “lower is better” vs “higher is better”).
[ ] If both throughput and latency are reported, ensure they were measured over the same window (post-warmup).
[ ] If streaming metrics are included, confirm whether latency is time-to-first-token (TTFT) vs end-to-end; ensure charts do not mix definitions.

### C3. Duplicate and partial runs
[ ] Deduplicate runs: no identical (model, region, workload, timestamp window) counted twice unless clearly labeled as separate replicates.
[ ] Remove partial runs: any run with aborted execution, missing metrics, or known infra incident overlap must be excluded.
[ ] All exclusions are logged with reason code (see Section F).

## D. Outlier handling (rules + documentation)
### D1. Outlier policy (default)
Outliers can occur due to queueing effects, transient network issues, kernel selection changes, or noisy neighbors. We do not remove outliers to “improve” results; we remove them only when we can attribute them to non-representative run conditions or obvious measurement errors.

Default policy:
1) Prefer **rerun** over exclusion when instability is detected.
2) Exclude only when one of the following is true:
   - Known incident overlap (capacity disruption, elevated 5xx/429, runner error).
   - Measurement artifact (missing warmup exclusion, timestamp misalignment, corrupted metrics file).
   - Manifest indicates mismatched config vs methodology.

Checklist:
[ ] Outliers are flagged automatically using a robust rule (see D2), but removal requires an explicit reason.
[ ] Any excluded run has a reason code and linked evidence (ticket/incident/log snippet).

### D2. Outlier detection heuristic (reporting + triage)
Use a robust detector for triage (not auto-exclusion):
- Within each (model, region, workload tier), compute median and MAD (median absolute deviation).
- Flag runs where p95 latency deviates by > 3.5 MAD from the median.
- Also flag cost anomalies where $/1M tokens deviates by > 3 MAD.

Checklist:
[ ] Flagged outliers are reviewed by the benchmark owner (Applied ML) and one runtime reviewer.
[ ] The number of flagged runs and resolution outcome is recorded in the validation report.

## E. Stability gates and rerun thresholds (publish blockers)
### E1. Minimum replicate requirements
Unless otherwise specified in the methodology lock:
- Each (model, region, workload tier) must have at least **3 valid replicates**.
- Replicates must be non-overlapping in time (avoid back-to-back runs only).

Checklist:
[ ] Replicate count meets minimum for every published cell.

### E2. Variance thresholds (auto-rerun)
Trigger reruns when any of the following is true within a (model, region, workload tier):
- p95 latency coefficient of variation (CV) > **7%** across replicates
- OR median p95 differs by > **10%** between two consecutive sweeps in the same day
- OR throughput CV > **8%** (if throughput is used in narrative claims)

Rerun protocol:
1) Rerun up to 2 additional replicates.
2) If instability persists, escalate to Runtime + Infra to diagnose (queueing, kernel changes, capacity).
3) If unresolved within timeline, either (a) remove the cell from publication, or (b) publish with a clearly labeled “higher variance” caveat (requires PMM + tech lead approval).

Checklist:
[ ] Stability gates executed and results attached to the validation report.
[ ] Any “publish with variance caveat” is pre-approved and mirrored across all assets (web + PDF + enablement).

### E3. Regression guardrails vs last published version (refreshes)
For refreshes or v1.1+ updates:
- If latency/$ changes by > **15%** for a previously published (model, region) cell, require a short root-cause note (expected vs unexpected).

Checklist:
[ ] Large deltas are explained (e.g., new runtime version, different GPU SKU, different prompt set, pricing update).

## F. Exclusion log (required format)
Maintain an exclusion log for auditability. Minimum columns:
- run_id
- (model, region, workload tier)
- exclusion_reason_code (INCIDENT, CONFIG_MISMATCH, CORRUPT_METRICS, PARTIAL_RUN, OTHER)
- reviewer
- link_to_evidence (incident/ticket/log)
- date

Checklist:
[ ] Exclusion log exists and is stored alongside derived datasets.
[ ] Exclusions are reflected consistently (no excluded run appears in any chart/table export).

## G. Public artifact safety (redaction + claim alignment)
### G1. Redaction checklist (hard block)
Public exports (CSV/JSON) and any embedded examples must not include:
- Customer identifiers, org IDs, API keys, request IDs that can be correlated externally
- Internal hostnames, fleet IDs, or instance IDs
- Raw prompts that contain customer data (prompt sets must be synthetic/approved)

Checklist:
[ ] Redaction step executed on all public artifacts.
[ ] A reviewer (Security/Compliance partner) confirms the redaction report.

### G2. Claims alignment checklist
[ ] All metric definitions in assets match the methodology page (names + units).
[ ] Any comparative language (e.g., “faster”, “cheaper”, “best”) is either removed or explicitly scoped with substantiation and disclaimers.
[ ] Charts include required footnotes/disclaimers (variance, workload definition, date range, hardware notes).

## I. Final “ready to publish” checklist (single page)
Before the final publish commit/merge:
[ ] Expected matrix confirmed; no missing regions/models (or documented exceptions approved).
[ ] All manifests validate; sampled runs match methodology.
[ ] Stability gates passed; reruns completed where required.
[ ] Outliers reviewed; exclusions logged with evidence.
[ ] Derived dataset schema versioned; export files match the dataset hash.
[ ] Redaction verified; public artifacts reviewed.
[ ] Charts/tables match exported data (spot-check 10 random cells).
[ ] Disclaimers and footnotes present on web + PDF.
[ ] All sign-offs recorded with dates.

## Appendix: Suggested spot-check procedure (10-cell audit)
1) Randomly select 10 cells from the interactive table (mix of regions/models).
2) For each cell, trace back to the derived dataset row(s) and then to the 3+ run manifests.
3) Confirm: (a) region/model labels, (b) workload tier, (c) metric definitions, (d) replicate count, (e) no excluded run included.
4) Record any discrepancies and block publish until resolved.
