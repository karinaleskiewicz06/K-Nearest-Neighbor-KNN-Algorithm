Adaptive telemetry sampling for GPU inference (ingest budgeting & operator patterns)

Summary:
This document describes an adaptive telemetry sampling strategy for GPU inference workloads designed to keep telemetry ingest costs bounded while preserving signal quality for latency, error, and quality monitoring. It introduces the SamplingRateController and IngestBudgetOperator patterns, concrete sampling policies, CI/CD constraints for sampling config changes, and a runbook for investigating sampling-related telemetry gaps.

Audience:
- Infra SREs and telemetry engineers
- Serving/runtime owners
- Observability and cost engineering teams

Goals:
- Limit telemetry ingest costs to a configurable daily budget per account/region (SLO: budget adherence 99.5% monthly).
- Maintain fidelity for high-priority slices (latency-critical paths, p95/p99, and customer-impacting errors).
- Provide safe rollout and auditability of sampling changes via CI/CD and Terraform modules.

Motivation and context:
Redwood's inference fleet emits high-cardinality telemetry: per-request traces, per-token latency histograms, and model KV-cache metrics. Unbounded sampling causes Firehose/Kafka ingestion and downstream analytics costs to spike during evals, gated rollouts, or bursty traffic. A deterministic, observable sampling controller reduces costs while keeping actionable signals.

Key concepts and components:
- SamplingRateController (SRC): a control-plane service that computes per-tenant, per-route sampling rates at 1-minute cadence.
- IngestBudgetOperator (IBO): Kubernetes operator that enforces daily ingest budgets by adjusting SRC targets and throttling verbose telemetry producers.
- Priority slices: groups such as (latency-sensitive), (A/B canaries), (long-sequence-models), (eval-run), and (customer-critical).
- Downstream connectors: Firehose -> Kafka -> ClickHouse/OLAP and Firehose -> S3 cold-storage.

Sampling policy taxonomy:
1) Deterministic overrides (always-on): small subset (~0.5%) of requests sampled deterministically for full traces and token-level profiling. Applied to: canaries, internal eval runs, and tenant debug flagging.
2) Priority-preserving stratified sampling: ensures high-priority slices are sampled at higher rate than baseline.
3) Latency-aware adaptive sampling: sampling rate increases for requests near p95/p99 latency thresholds to capture tails.
4) Budget-driven backoff: when projected daily ingest > budget, SRC reduces baseline and deprioritizes low-value slices.

Configuration examples (YAML) - sampling rule (for operator and SRC):

# sampling-rule.yaml (applies via gitops to SRC)
apiVersion: telemetry.redwood/v1
kind: SamplingRule
metadata:
  name: long-seq-and-canary-prioritization
spec:
  selectors:
    - route: "/v1/generate"
      model_family: "redwood-*-opt"
      labels:
        - "canary"
        - "internal-eval"
  priority: high
  deterministic_rate: 0.02   # 2% forced full sampling for high-priority
  baseline_rate: 0.10        # baseline sample rate for this slice
  tail_boost:
    latency_threshold_ms: 400
    boost_to: 0.50            # if latency > threshold, sample 50%
  cost_weight: 1.2          # inflates cost accounting for long sequences

Operational table: config knobs and typical defaults

| knob | purpose | default | notes |
|------|---------|---------|-------|
| global_baseline_rate | baseline sample for non-priority traffic | 0.02 | tuned to keep cold-storage useful |
| deterministic_pool_pct | fraction of requests always recorded | 0.005 | used for perf regression/eval |
| daily_ingest_budget_per_region | soft ingest cap (USD) | 3000 | adjusted per environment (prod/staging) |
| tail_latency_threshold_ms | latency threshold to boost sampling | 300ms | p95 threshold baseline |

Implementation notes and infra patterns:
- The SamplingRateController reconciles sampling config from the GitOps repo (sampling-service-config) and augments with real-time signals from Prometheus and the cost estimator (Kafka partition size + Firehose bytes/sec).
- The IngestBudgetOperator watches daily_ingest_budget CRs and reconciles per-region throttles by patching the SamplingRateController via its HTTP API. Operator uses optimistic concurrency and emits events to the cluster event-sink.
- Telemetry producers (service SDK) must implement a sampling API: set_sample_rate(slice_id, rate, deterministic_pool_key). The SDK exposes a local token-bucket so rate changes apply without request restarts.
- Cost estimator: rolling 1h projection uses: current bytes/sec, 24h traffic profile, and average message size per route. Error margin target 10%.

Prometheus alerts and SLOs (examples):
- Alert: HighTelemetrySpillover
  expr: (sum by(region) (firehose_bytes_total[5m]) / 1024 / 1024) > (region_ingest_budget_bytes_per_hour * 1.1)
  severity: page
  notes: "Firehose bytes exceeding 110% of hourly budget projection; triggers IBO reconciliation. See runbook below."

- SLO: Telemetry budget adherence
  objective: 99.5% monthly
  indicator: fraction of days where actual_ingest_cost <= daily_ingest_budget

CI/CD and change control:
- Sampling rules live in telemetry-config repo under /sampling/rules/*.yaml.
- PR requirements: unit tests (rule parser), a cost-impact diff tool (estimates delta bytes/day), and an integration test that validates the rule compiles to SRC config.
- Merge gates: changes to deterministic_rate or baseline_rate that increase projected ingest > 5% require:
  1) approval from Observability lead and Cost Engineering, and
  2) a documented rollback plan in PR description.
- Terraform module: telemetry-ingest-budget (module) accepts: region, daily_ingest_budget_usd, owner_team, slack_channel, alerting_policy_id. See example usage in the module README.

Rollout & Canary strategy for sampling changes:
1) Stage: push config to staging SRC. Monitor projected ingest and Firehose bytes for 1 hour.
2) Canary: apply to 5% of traffic in prod (route-level canary tag). Hold for 2 hours; run synthetic workload to verify tail capture.
3) Gradual ramp: 5% -> 25% -> 100% over 6 hours if budget and alert signals clear.
4) Automatic rollback: if HighTelemetrySpillover fires or error budget > 0.5, IBO sets baseline_rate back to last-known-good and notifies owners.

Runbook: investigating sampling gaps or signal loss
1) Symptom: missing traces or reduction in p99 visibility. Check Prometheus metrics: sampled_traces_total_by_slice and firehose_bytes_total.
2) Check IBO CR status: kubectl get ingestbudget -n telemetry -o yaml. Look for conditions.throttled=true.
3) Query SRC API: curl -s http://src.internal:8080/api/v1/current-rates?region=us-east-1 and inspect per-slice rates.
4) If rates are unexpectedly low and budget not exhausted: look at SRC logs (/var/log/sampling-controller.log) for config parsing errors.
5) To temporarily restore visibility: apply a short-lived override in the telemetry-config repo:
   - Add a SamplingRule with deterministic_rate: 0.01 for the affected slice and deploy.
6) Post-incident: run a cost impact audit (script: tools/telemetry/cost-audit.sh) and file a follow-up with observability and cost tags.

Audit and compliance notes:
- Deterministic sampling of tenant traffic requires consent when QoS includes customer-sensitive payloads. For customers with restricted telemetry, IBO respects customer_flags.telemetry_allowed=false and sets sampling to 0.
- All sampling rule changes are recorded in the audit log (GCS bucket: gs://redwood-telemetry-audit). Each operator action includes a git commit hash and operator identity.

Metric checklist to monitor after rollout:
- firehose_bytes_total (region) — keep below budget projection 
- sampled_traces_total_by_slice (route, model_family) — should not drop by >25% for priority slices
- src_reconcile_errors_total — must be < 1/day
- ingestbudget_overrides_count — track frequency of manual overrides; target <= 3/month
