GPU rebalancer operator design and TF schema

Summary:
This document describes the design, Terraform schema, CI/CD gating, and operational runbook for the GPU Rebalancer Operator — a control-plane component that automatically rebalances heterogeneous GPU pools across regions, instance types, and tenant slices to preserve SLOs (latency, throughput, cost) while minimizing disruption.

Goals and non-goals:
- Goals:
  - Maintain per-tenant placement SLOs (95th latency < 120ms for inference class A; token/sec floor for batch workloads).
  - Reduce hot/cold pool imbalances that cause tenant throttling or excessive preemptions.
  - Make rebalancing decisions auditable, reversible, and IaC-configurable via Terraform modules and Helm values.
  - Ensure operator changes can be safely rolled out through CI/CD canaries + perf validation.
- Non-goals:
  - Not intended to implement tenant-level billing changes (billing handled downstream).
  - Not a replacement for long-term capacity planning; it smooths short-to-medium-term skew only.

High-level architecture (text diagram):
- Control plane (k8s)
  - Rebalancer Controller (CRDs: PoolSlice, RebalancePlan, EvictionFence)
  - Decision Engine (policy engine + cost model)
  - Intent store (etcd via k8s CustomResources)
- Data plane
  - Node agents (lightweight daemon): collect utilization, drain hooks, safe-eviction handshake
  - Placement API sidecar: accepts safe-routing updates for the serving runtime

Key design principles:
1) Conservative, reversible actions: every move must be represented as a RebalancePlan with a TTL and explicit approve/rollback lifecycle.
2) Workload-aware moves: decisions weigh KV-cache reseeding cost, model checkpoint transfer size, and tenant prewarm state.
3) IaC-first configuration: operator policy primitives are configured and versioned in Terraform modules so infra owners can review changes via PRs.
4) Safety nets: circuit breakers (max concurrent live evictions per AZ), probe-based canaries, and automatic abort on SLO degradation.

CRD summary (conceptual):
- PoolSlice: logical grouping (region, instance family, runtime flavor, tenant tag).
- RebalancePlan: list of intended moves, priority, estimated disruption score, and dry-run flag.
- EvictionFence: temporary hold to prevent moves for a pool during maintenance.

Terraform module schema example (text table):
| Field | Type | Description | Default | Validation |
| pool_rebalancer_enabled | bool | Enable operator for the account | true | - |
| default_concurrency | number | Max live node drains per AZ | 4 | >=1 and <= 50 |
| eviction_timeout_minutes | number | Grace period for a live eviction to finish | 30 | >=5 and <= 180 |
| probe_canary_thresholds | map | Performance checks to run post-move | see example | - |

CI/CD gating and perf validation
- Pipeline goals:
  1) Every change to Terraform module or operator manifests must pass unit tests, integration tests against a local k8s testbed, and a perf canary stage that validates key thresholds.
- Pipeline stages (high level):
  1. Lint & static checks (terraform validate, tfsec, tflint).
  2. Unit tests for decision engine logic (python/Go).
  3. Integration: deploy operator to ephemeral cluster (KinD) and run end-to-end move simulations using synthetic tenant traces.
  4. Canary perf stage: deploy to a shadow AZ (or small percentage of traffic) and run the canonical workload suite (latency, throughput, KV-cache hit recovery).
  5. Promote: if canary passes SLOs and disruption score below threshold, allow module promotion.

Example GitHub Actions job (pseudo):
jobs:
  canary-validation:
    runs-on: ubuntu-latest
    steps:
      - name: Deploy ephemeral cluster and operator
      - name: Run synthetic workload (10m)
      - name: Collect metrics and assert thresholds

Canary pass/fail criteria (examples):
- Recovery latency: 95th percentile must not increase > +15ms over baseline.
- Throughput: batch token/sec drop <= 5% for <= 5 minutes.
- Disruption score (composite): < 0.25 (computed by decision engine).

Operational runbook (quick actions):
1) When RebalancePlan fails or stalls:
   - Inspect RebalancePlan CR: kubectl get rebalanceplan -o yaml
   - Check NodeAgent logs for handshake failures: kubectl logs daemonset/node-agent -n infra
   - If many handshakes failed, set EvictionFence for the affected PoolSlice and notify infra-sre.
2) Abort a live rebalancing wave:
   - kubectl annotate rebalanceplan <name> infra.redwood.io/abort=true
   - Operator will halt new drains and attempt to restore previous intents.
3) Emergency rollback (if SLOs breached):
   - Trigger plan rollback via API: POST /v1/rebalancer/plans/<id>/rollback (internal admin endpoint)
   - Re-schedule KV-cache reseed jobs using the placement sidecar to minimize cold misses.
4) Debugging metrics to check:
   - rebalancer.plan.success_rate (1m/5m)
   - node_agent.handshake_failures_total
   - pool.slice_utilization and pool.data_transfer_bytes

Safety knobs and SLO integration:
- Circuit breakers configured by TF: max_concurrent_evictions_per_account, max_data_transfer_gb_per_hour.
- Observable outputs: per-plan audit log (who approved, diffs, estimated disruption), per-tenant incident annotations.
- Rollout policy: default to manual approval for cross-region moves and auto for same-AZ redistributions.

Testing matrix and recommended experiment list:
- Unit tests: decision rules, cost model math, dry-run behavior.
- Integration tests: simulate heterogeneous pool with mix of preemptible and on-demand nodes.
- Performance canaries: 10–20% traffic shadow for 30 minutes then sweep to check stability.
- Chaos experiments: interrupt node-handshake mid-eviction, simulate large checkpoint transfers, simulate network egress throttling.

Migration and upgrade plan for existing pools:
1) Start in dry-run mode and produce RebalancePlans for 2 weeks to collect disruption estimates.
2) Run a limited canary in a single AZ with at most 1 concurrent eviction.
3) Expand to multi-AZ with increased concurrency after validating KV-cache reseed time and net egress.
4) Switch TF module to production values and perform final audit.
