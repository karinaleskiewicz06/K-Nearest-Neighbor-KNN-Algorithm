GPU NAT Fabric Orchestrator and Service-Account Routing Playbook

Summary:
This playbook describes the NAT Fabric Orchestrator (NFO) pattern we use to provide predictable, accountable egress from GPU tenant environments. It bundles: a Terraform module (nat_fabric) for per-account SNAT allocation, a control-plane service that maps service-accounts to NAT pools, CI/CD validation for network changes, and an on-call runbook for egress incidents. The goal is to ensure tenant isolation, avoid noisy-tenant egress storms, and enable safe burst routing into shared burst pools.

Why this exists:
- Past incidents showed that unmanaged SNAT exhaustion and hairpinning caused large customer-facing tail-latency spikes.
- The NFO enforces per-tenant quotas, predictable billing attribution, and safe fallback to burst NAT pools.

Key components:
- nat_fabric Terraform module: creates NAT pools, route tables, allocation resources and IAM bindings.
- nfo-controller: Kubernetes control plane that watches ServiceAccount annotations and allocates an IP from the tenant pool.
- egress-metrics pipeline: Prometheus metrics, Grafana dashboards, and billing tags exported to telemetry.
- e2e network test pipeline: runs in CI to validate SNAT allocation, NAT failover, and DNAT whitelist rules.

SLOs and thresholds:
- Total egress connection setup failure rate: <= 0.2% (5m window)
- Redis-backed allocation latency (p99): <= 75ms
- SNAT exhaustion alerts: trigger when free IPs < 10% per pool

Terraform module reference (summary table):
| Variable | Type | Default | Notes |
| nat_pool_size | number | 64 | Number of IPs in the pool (per-region) |
| pool_region | string | us-west-2 | Region for the NAT pool |
| tags | map | {} | Billing tags attached to NAT resources |

Example nat_fabric usage (terraform snippet):
```hcl
module "tenant_egress" {
  source = "git::ssh://git@github.com/redwood-infra/terraform-modules.git//nat_fabric?ref=v1.3.0"
  tenant_id = var.tenant_id
  nat_pool_size = 32
  pool_region = var.region
  tags = { team = "gpu-platform", tenant = var.tenant_id }
}
```

nfo-controller annotations (Kubernetes):
- redwood.io/egress-pool: "tenant-123-usw2"
- redwood.io/egress-band: "standard|burst"
- redwood.io/egress-retries: "3"

CI/CD validation checks (Buildkite / GitHub Actions):
1) Terraform plan must include nat_fabric schema lint and an assertion that no public IPs are leaked.
2) Network emulator test: create ephemeral pod with annotated SA and assert outbound IP matches allocated pool.
3) Failover test: simulate pool drain and assert controller switches to burst pool within 30s.
4) Billing tag check: all created resources contain required billing tags.

Runbook: Egress exhaustion or unexpected NAT failures
1) Detection: Pager fires from "nat_pool_exhaustion" alert (prometheus rule).
2) Initial triage (5m): on-call runs `kubectl get ephemerals --selector=redwood.io/egress-pool=POOL` and `redis-cli -h redis-nfo-1 HGETALL allocations:POOL`.
3) If free IPs < 5%: an automated scale job (terraform apply via pipeline) will be triggered to add pools. If automation fails, follow manual scale (see section below).
4) If allocation latency high: check nfo-controller logs `kubectl logs -l app=nfo-controller -n platform` and `systemctl status nfo-allocator` on dedicated nodes. Restart nfo-controller if stuck: `kubectl rollout restart deployment/nfo-controller -n platform`.
5) Fallback to burst pool: annotate critical service-accounts with `redwood.io/egress-band: burst`. Use the helper script: `scripts/burst-fallback --tenant tenant-123 --region usw2` (stored in repo infra/tools).
6) Communication: update status page and slack channel #infra-egress with pool, impact, and mitigation steps.

Manual scale (when automation fails):
1) Checkout terraform branch `git checkout infra/nat-pool-scale` and update module nat_pool_size.
2) Run `mage tf:init && mage tf:plan` in the repo root.
3) Approve via terraform pipeline with required two reviewers.
4) After apply, validate with CI network emulator and confirm allocations.

Observability runbook (dashboards & queries):
- Grafana dashboards: "NFO Overview", "Per-pool utilization", "Per-tenant egress latency".
- Prometheus alerts of interest: `nat_pool_exhaustion`, `nfo_alloc_latency_high`, `nfo_controller_restart_rate`
- Example PromQL: `sum by(pool) (nat_pool_ip_free{job="nfo-exporter"}) / sum by(pool) (nat_pool_ip_total{job="nfo-exporter"})`

Release and migration notes:
- v1.3.0 of nat_fabric introduced lease-time enforcement; rollout pattern: canary 5% of tenants for 48h, then 25% for 24h, then full roll.
- Migration checklist: export current SNAT mapping, dry-run Terraform in staging, run network emulator tests, validate billing tags, and coordinate QBR for customers owning high-traffic tenants.

Security considerations:
- All control-plane requests must be signed and authorized via KMS-backed keys.
- NAT pools with cross-account peering require approval from security; include `confidentiality=restricted` when creating leak-sensitive pools.

Appendix: quick debug commands
- List allocations: `kubectl exec -n platform svc/nfo-cli -- allocations list --pool tenant-123-usw2`
- Force rebind: `kubectl exec -n platform svc/nfo-cli -- allocations rebind --sa default --pool tenant-123-usw2`
- Check terraform state: `terraform state list | grep nat_fabric`
