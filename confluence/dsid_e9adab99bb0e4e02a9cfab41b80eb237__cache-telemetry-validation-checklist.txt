Cache Telemetry Validation Checklist (Prefix + KV Cache)

## Purpose
This checklist verifies that new prefix/KV cache telemetry is:
1) Correct (hit/miss attribution, counters/histograms consistent with request lifecycle),
2) Joinable (model/route/deployment identifiers present and stable),
3) Safe to operate (cardinality bounded, sampling behaves as intended), and
4) Low overhead (near-zero latency/throughput impact).

This is the required validation sequence for runtime changes touching:
- KV cache hit/miss counters and miss reasons
- Prefix cache reuse histograms
- Eviction/pressure indicators
- “Wasted prefill” metrics
- Trace span annotations for cache events

## Scope
Applies to: Hosted, Dedicated, and Private runtime builds that emit cache telemetry.

Out of scope: correctness of cache policy/eviction algorithms themselves (only their *telemetry*).

## Quick acceptance criteria (must pass)
### Correctness
- No systematic double-counting on streaming retries.
- Batched prefill attribution: per-request counters reconcile with batch-level spans.
- Partial reuse semantics are consistent (hit-rate is computed from the same numerator/denominator across dashboards).
- Wasted prefill increases when expected (forced misses/evictions), and stays low on stable repeated prompts.

### Joinability
- Each emitted metric/trace includes (or can be joined to) model identifier + model version, route identifier, deployment mode, and region.
- Join keys are stable across gateway logs, runtime metrics, and analytics aggregates.

### Cardinality & sampling
- No forbidden labels (raw prompt, request_id, user_id, tenant_id at high-cardinality) appear in metrics.
- Prompt length / token counts appear only as approved buckets.
- Sampling reduces event volume without biasing aggregate hit-rate beyond tolerance (see “Sampling bias check”).

### Performance
- p95 latency regression <= 0.5% in perf-canary at default sampling.
- Runtime CPU overhead <= 1% under representative throughput.
- Metrics emission does not increase tail latency variance (p99/p99.9) beyond alert thresholds.

---

## Definitions (what we mean by “correct”)
Use the definitions in the ADR (linked above). In practical validation, we check these invariants:
- A “request” flows through prefill then decode.
- Prefix cache reuse counts only reused prefix tokens that are actually applied to compute subsequent decode.
- KV cache hit/miss is attributed per request and is consistent across streaming and retries.
- Miss reasons are stable, mutually exclusive per miss event, and are not overloaded with transient internal states.

## Step 2 — Smoke test: metrics are present and non-zero
Generate traffic for 5–10 minutes with a mix of:
- Exact prompt repeats (high expected reuse)
- Slight prompt variations (low expected reuse)
- Two-turn chat (prefix reuse expected on turn 2 if canonicalization holds)

Checklist (observability):
- [ ] KV hit/miss counters increase
- [ ] Prefix reuse histogram buckets increase
- [ ] Eviction/pressure signals are present (may remain low)
- [ ] Wasted prefill is present and behaves plausibly
- [ ] Trace spans show cache annotations (if enabled) without high-cardinality tags

If any metric is missing:
- Validate config flags
- Validate metric allowlist in runtime emission
- Validate ingestion-side drop/guard behavior (see Step 6)

---

## Step 3 — Counter reconciliation (single-request invariants)
### 3A) Simple repeated prompt test (no streaming)
Procedure:
1) Send the same prompt N times (N>=50) to the same route/model/region.
2) Keep decode params constant.

Expected:
- Hit-rate increases after warm-up.
- Prefix reuse depth increases (distribution shifts right).
- Wasted prefill decreases after warm-up.

Checklist:
- [ ] After initial warm-up, KV misses per request trend down.
- [ ] Prefix reused tokens per request trend up.
- [ ] Wasted prefill per request trends down.

### 3B) Prompt mutation test
Procedure:
1) Append a random suffix to the prompt each request.

Expected:
- Hit-rate remains low.
- Reuse depth remains near zero.
- Wasted prefill may increase if prefill work is repeatedly not reused.

Checklist:
- [ ] Misses dominate; “hash_mismatch”/equivalent reason increases (if implemented).
- [ ] Reuse histograms concentrate in lowest buckets.

---

## Step 4 — Streaming + retry correctness (negative test)
Goal: ensure we do not double count when a stream is retried.

Procedure:
1) Initiate streaming responses.
2) Induce retry behavior (e.g., client disconnect/reconnect, simulated upstream retry, or known retry harness).
3) Repeat for a small set of prompts where reuse is expected.

Expected:
- Per-request cache metrics represent the logical request outcome, not the number of transport attempts.
- Retries should not inflate hit/miss totals disproportionately.

Checklist:
- [ ] KV hit/miss counters do not exceed expected request count by >2% (tolerance for in-flight edge cases).
- [ ] Wasted prefill does not spike solely due to retries.
- [ ] Trace spans show retry linkage without creating unique metric labels.

If failing:
- Check for duplicate “end-of-request” emission.
- Ensure retry instrumentation uses idempotent accounting.

---

## Step 5 — Continuous batching correctness (batched prefill attribution)
Goal: ensure that per-request counters are correct when multiple requests share a continuous batch prefill.

Procedure:
1) Enable a load profile that triggers continuous batching.
2) Send two cohorts concurrently:
   - Cohort A: repeated prompts (expected high reuse)
   - Cohort B: varied prompts (expected low reuse)

Expected:
- Cohort A shows higher hit-rate than Cohort B even under batching.
- Batch-level behavior does not “bleed” hits across requests.

Checklist:
- [ ] Metrics sliced by request-shape buckets show plausible separation.
- [ ] No systematic over-attribution of hits to shorter prompts.

---

## Step 6 — Sampling verification (volume + bias)
### 6A) Sampling is actually reducing volume
Procedure:
1) Run traffic at a fixed QPS for 10 minutes at sampling=1.0.
2) Run traffic at the same QPS for 10 minutes at sampling=default.
3) Compare emitted series rate / ingestion volume.

Checklist:
- [ ] Event/metric emission volume decreases roughly proportionally to sampling.
- [ ] Rate-limiting (if enabled) activates only under expected high-volume patterns.

### 6B) Sampling bias check (must not distort aggregates)
Compute hit-rate and reuse distributions for the same workload under sampling=1.0 vs default sampling.

Checklist:
- [ ] Aggregate KV hit-rate differs by <= 1.0 percentage point (or documented tolerance) between sampling modes.
- [ ] Prefix reuse histogram shape is not materially distorted (no bucket collapses due to sampling implementation).

If failing:
- Sampling must be applied uniformly at the correct event boundary (per-request, not per-token unless explicitly defined).
- Ensure denominators are sampled consistently with numerators.

---

## Step 7 — Cardinality safety checks (must pass before canary)
Goal: ensure we do not create a metric explosion.

Checklist:
- [ ] No metric includes raw prompt, canonical prompt hash (if high-cardinality), request_id, session_id, or user identifiers.
- [ ] Route/model/version tags are from strict allowlists (known route IDs, known model IDs).
- [ ] Prompt length / token counts appear only in pre-defined buckets.
- [ ] Tenant/customer identifiers are either absent or aggregated to an approved low-cardinality dimension (e.g., “tier” or internal/customer boolean) per policy.

Operational check:
- [ ] Validate ingestion logs for label-drop events are near zero.
- [ ] Validate series count for cache telemetry is within budget (compare to baseline; do not exceed 1.2x expected).

If you see a spike in “dropped labels”:
- Confirm allowlist config matches current route/model identifiers.
- Confirm gateway is populating join keys consistently (no new unexpected values).

---

## Step 8 — Miss reason taxonomy sanity
Procedure:
1) Force each miss reason in a controlled way (as feasible):
   - capacity/pressure: temporarily reduce cache budget or increase load
   - ttl_expired: configure a short TTL, wait, then repeat
   - policy_disabled: disable caching on a route
   - version_mismatch: roll model version and send repeated prompt across versions
   - hash_mismatch: prompt mutation
2) Observe miss reason breakdown.

Checklist:
- [ ] Each forced scenario produces the expected dominant reason.
- [ ] Reasons are mutually exclusive per miss event.
- [ ] “Unknown/other” remains low; if high, instrument a new explicit reason rather than overloading.

---

## Step 9 — Wasted prefill validation
Goal: ensure wasted prefill tracks “prefill work that does not contribute to subsequent decode due to cache misses/evictions” (as defined).

Procedure:
1) Baseline: repeated prompts with stable cache budget (expected low wasted prefill after warm-up).
2) Pressure: increase concurrency or reduce cache budget to trigger evictions.
3) Compare wasted prefill rates.

Checklist:
- [ ] Wasted prefill increases meaningfully under eviction pressure.
- [ ] Wasted prefill remains low in steady-state reuse.
- [ ] Wasted prefill does not increase simply due to longer decodes when reuse is still high.

---

## Step 10 — Trace annotations check (if included)
Goal: provide debuggability without high-cardinality metrics.

Checklist:
- [ ] Cache-related spans/annotations appear on the request trace.
- [ ] Attributes are bounded (e.g., booleans, enums, bucketed ints) and do not include prompt content.
- [ ] Trace sampling does not disproportionately exclude cache-miss traces (avoid only sampling “fast” paths).

---

## Step 11 — Overhead benchmarking (bench + perf-canary)
### 11A) Microbench / bench harness
Run a representative set of workloads:
- Short prompts (e.g., <256 tokens)
- Medium prompts (256–2k)
- Long prompts (>2k)
- Streaming on/off
- Continuous batching on/off

Checklist:
- [ ] Compare latency distributions with telemetry disabled vs enabled.
- [ ] Compare throughput (tokens/sec) with telemetry disabled vs enabled.
- [ ] Compare CPU utilization and allocator/memory overhead.

Acceptance:
- [ ] p95 latency regression <= 0.5% at default sampling
- [ ] p99 latency regression <= 1.0% at default sampling
- [ ] No measurable increase in GC/allocator churn attributable to telemetry tags

### 11B) Perf-canary gate
Procedure:
1) Enable telemetry on perf-canary workload.
2) Run for >= 30 minutes to include steady-state and burst patterns.

Checklist:
- [ ] Canary does not fail SLO gates.
- [ ] Tail latency variance does not increase unexpectedly.
- [ ] Metrics pipeline remains stable (no ingestion throttling alerts).

## Step 12 — Dashboard sanity + operational readiness
Checklist:
- [ ] Dashboards show expected patterns during the above tests:
  - Hit-rate trends respond to workload changes
  - Eviction/pressure correlates with wasted prefill
  - Model/region/route filters work and do not produce empty panels (unless truly no traffic)
- [ ] Alerts are either disabled in staging or tuned to avoid noise during validation.
- [ ] Runbook links from dashboards are correct.

## Common failure modes and how to diagnose
1) **All cache hits = 0**
   - Check: ingestion label-drop or cardinality guard dropping key labels
   - Check: caching policy disabled at route
   - Check: model version mismatch during rollout

2) **Hit-rate looks too good to be true (near 100%)**
   - Check: denominator not incrementing (missed “requests_total”)
   - Check: double counting hits due to retries

3) **Hit-rate collapse after model rollout**
   - Check: version_mismatch misses
   - Check: route now points to new model version without warm-up

4) **Series count explosion**
   - Check: route_id or model_version values not allowlisted
   - Check: prompt hash incorrectly tagged as metric label

## Appendix: recommended test workloads
Use these as standard reproducible workloads:
1) **Exact-repeat chat warm-up**: fixed system prompt + fixed first user turn repeated
2) **Two-turn chat**: same first turn, different second turn; verify partial reuse
3) **Suffix mutation**: same base prompt + random suffix
4) **Eviction pressure**: high concurrency long prompts to push cache budget
5) **Streaming retry**: simulated disconnect/reconnect during decode

Keep prompts synthetic or from approved test sets. Do not use customer prompts in staging/perf-canary.
