Dedicated Fleet Provisioning: Terraform Conventions

## Purpose
This page defines the canonical Terraform conventions for provisioning **Dedicated GPU fleets** (and their supporting resources) in a way that is:
- Repeatable across regions and GPU SKUs
- Safe to roll out incrementally with hard guardrails
- Observable (clear outputs/tags for downstream provisioning automation)
- Drift-resistant with clear expectations for detection and remediation

These conventions are used by Infra/Fleet and Release Engineering and are prerequisites for the Provision-to-Ready automation workflow.

## Scope
Applies to Terraform used to provision:
- Dedicated GPU pools (node groups/instance groups, launch templates, autoscaling)
- Pool-level networking attachments (subnets, security groups) where owned by fleet modules
- IAM/service accounts needed for node bootstrap + validation agent
- Tags/outputs required by the provisioning orchestrator and readiness control plane integration

Out of scope:
- Kubernetes manifests (managed in Helm charts)
- Application-level serving configuration (managed in control plane)

---

## Repository + directory structure
**Principle:** one environment entrypoint, composable modules, and zero “snowflake” region copies.

### Recommended layout
- `environments/`
  - `prod/`
    - `dedicated/`
      - `main.tf` (composes modules)
      - `variables.tf` (minimal; pass-through only)
      - `outputs.tf`
      - `versions.tf` (provider + Terraform version)
      - `regions/` (thin region overlays)
        - `us-east-1.tfvars`
        - `eu-west-1.tfvars`
- `modules/`
  - `dedicated_pool/` (top-level pool module; composes other modules)
  - `gpu_node_group/` (node group primitives)
  - `fleet_tags/` (tag standardization + validation)
  - `rollout_guardrails/` (region/SKU gating logic)

### Module ownership boundaries
- `modules/dedicated_pool`: owned by **Infra/Fleet**
- `modules/rollout_guardrails`: owned by **Infra/Fleet** with **SRE** review for safety knobs
- Provider/backend/state: owned by **Release Engineering**

## Naming conventions
### Resources
- Use predictable, queryable names; avoid random suffixes unless required.
- Format:
  - Dedicated pool name: `dedicated-${var.pool_id}`
  - Node group name: `dedicated-${var.pool_id}-${var.gpu_sku}`
  - Launch template name prefix: `ded-${var.pool_id}-${var.gpu_sku}`
- If the cloud provider has name length limits, apply a stable shortener (documented in module) rather than ad-hoc truncation.

### Variables
- Use `snake_case`.
- Prefix booleans with `enable_`, `disable_`, or `use_`.
- Prefer enums (strings with validation) over multiple booleans.

**Examples**
- `pool_id` (string)
- `region` (string)
- `gpu_sku` (string; e.g., `a100-80gb`, `h100-80gb`)
- `capacity_mode` (string; e.g., `dedicated`, `burst`)
- `image_channel` (string; `candidate` | `stable`)
- `image_version` (string; explicit pin)
- `enable_provision_to_ready` (bool)

### Locals
- Use `locals {}` for derived values only (names, labels, merged tags).
- Locals must not hide business logic (rollout gating stays in `rollout_guardrails`).

## Required tags (cost, ownership, automation)
**Principle:** tags are not optional. They are the join key between cloud resources, fleet automation, dashboards, and audit trails.

All resources created by fleet modules **MUST** include these tags (or their cloud-native equivalents):

| Tag key | Example | Purpose |
|---|---|---|
| `redwood:service` | `gpu-fleet` | Cross-system ownership + inventory |
| `redwood:env` | `prod` | Environment boundary |
| `redwood:pool_id` | `dp-01842` | Primary lookup key for Dedicated pools |
| `redwood:region` | `us-east-1` | Routing + rollout segmentation |
| `redwood:gpu_sku` | `a100-80gb` | Capacity planning + failure heatmaps |
| `redwood:image_channel` | `candidate` | Rollout + rollback workflows |
| `redwood:image_version` | `2025.10.12-1` | Pin + forensic attribution |
| `redwood:provisioning_mode` | `provision-to-ready-v1` | Gating/automation compatibility |
| `owner_team` | `eng-infra` | Human ownership |
| `cost_center` | `inference-platform` | Finance tracking |
| `data_classification` | `internal` | Compliance routing |

### Tag implementation
- Centralize tag generation in `modules/fleet_tags`.
- Always merge tags in a predictable order:
  1) required base tags from module
  2) environment tags (e.g., `redwood:env`)
  3) user-provided `additional_tags` (restricted to a safe allowlist)

**HCL pattern**
```
variable "additional_tags" {
  type    = map(string)
  default = {}
}

locals {
  required_tags = {
    "redwood:service"          = "gpu-fleet"
    "redwood:env"              = var.environment
    "redwood:pool_id"          = var.pool_id
    "redwood:region"           = var.region
    "redwood:gpu_sku"          = var.gpu_sku
    "redwood:image_channel"    = var.image_channel
    "redwood:image_version"    = var.image_version
    "redwood:provisioning_mode"= "provision-to-ready-v1"
    "owner_team"               = "eng-infra"
  }

  tags = merge(local.required_tags, var.additional_tags)
}
```

### Tag guardrails
- Enforce required tags via `validation` blocks and/or module-level checks.
- Do not allow overriding the `redwood:*` namespace via `additional_tags`.

## Region rollout toggles (staged enablement)
We gate provisioning automation and new pool creation by **region** and **GPU SKU** to support staged rollouts and fast rollback.

### Required rollout inputs
All Dedicated pool entrypoints must support these variables:
- `enable_staged_rollout` (bool)
- `rollout_allowlist_regions` (list(string))
- `rollout_allowlist_gpu_skus` (list(string))
- `enable_provision_to_ready` (bool) — toggles integration hooks for readiness gating

### Guardrail behavior
When `enable_staged_rollout = true`:
- Terraform **must fail plan/apply** if `var.region` is not allowlisted.
- Terraform **must fail plan/apply** if `var.gpu_sku` is not allowlisted.
- Terraform must default to **conservative capacity** (see “Capacity safety defaults”).

**HCL validation example**
```
variable "region" { type = string }
variable "gpu_sku" { type = string }
variable "enable_staged_rollout" { type = bool, default = true }
variable "rollout_allowlist_regions" { type = list(string) }
variable "rollout_allowlist_gpu_skus" { type = list(string) }

locals {
  rollout_region_ok = !var.enable_staged_rollout || contains(var.rollout_allowlist_regions, var.region)
  rollout_sku_ok    = !var.enable_staged_rollout || contains(var.rollout_allowlist_gpu_skus, var.gpu_sku)
}

resource "null_resource" "rollout_guardrail" {
  lifecycle { precondition {
    condition     = local.rollout_region_ok
    error_message = "Region not allowlisted for staged rollout: ${var.region}"
  }}

  lifecycle { precondition {
    condition     = local.rollout_sku_ok
    error_message = "GPU SKU not allowlisted for staged rollout: ${var.gpu_sku}"
  }}
}
```

### Recommended rollout defaults (early stages)
- `enable_staged_rollout = true`
- Allowlist only the first rollout slice (example):
  - `rollout_allowlist_regions = ["us-east-1"]`
  - `rollout_allowlist_gpu_skus = ["a100-80gb"]`

## Golden image pinning (channel + version)
Dedicated fleets must pin to a golden image **channel** and **version**.

### Policy
- `image_channel` is an operational control: `candidate` or `stable`.
- `image_version` must be explicitly set (no implicit “latest”).
- Promotion from candidate → stable must be a deliberate change (PR) and must emit audit events in the control plane (handled outside Terraform, but Terraform must carry the tags/outputs).

### Expectations
- The module must expose outputs used by automation:
  - `image_channel`
  - `image_version`
  - `launch_template_id` (or equivalent)

---

## Outputs required by provisioning automation
Terraform is the source of truth for identifiers needed by the provisioning orchestrator.

Every `dedicated_pool` must output:
- `pool_id`
- `region`
- `gpu_sku`
- `node_group_name` (or ASG/MIG name)
- `instance_profile_arn` (or equivalent)
- `security_group_ids`
- `subnet_ids`
- `image_channel`
- `image_version`

Outputs must be stable and not include per-apply randomness.

## Capacity safety defaults
To reduce blast radius during staged rollout, apply conservative defaults when `enable_staged_rollout = true`.

Recommended:
- Start with `desired_capacity = 0` for new pools unless explicitly overridden in a rollout ticket.
- Set `max_unavailable` (if applicable) to 0 for disruptive operations.
- Prevent accidental scale-ups:
  - Add a max cap variable (e.g., `rollout_max_nodes`) and enforce `max_size <= rollout_max_nodes` during rollout.

## State, apply workflow, and approvals
### Remote state
- Use remote state with locking (provider-native locking where supported).
- State must be encrypted at rest.
- No local state for `prod`.

### Apply workflow
- PR-required changes only.
- CI must produce:
  - `terraform fmt` + `terraform validate`
  - `tflint` / static analysis
  - `terraform plan` artifact for reviewers
- Applies are executed via the standard automation runner (e.g., Atlantis/CI apply job) with explicit approvals.

### Approval expectations (prod)
- Any change affecting:
  - `image_channel`, `image_version`
  - security groups / ingress/egress
  - instance profile / IAM
  - rollout allowlists or guardrails
  requires review from **Infra/Fleet** and **SRE**; security-related changes require **SecOps** consult.

## Drift detection and remediation
**Principle:** drift is expected (cloud noise, emergency ops) but must be detected quickly and remediated safely.

### Drift detection expectations
- Nightly drift plan against `prod/dedicated` entrypoints.
- Alert on:
  - tag drift (missing required tags)
  - launch template / image version drift
  - security group rule drift
  - autoscaling min/max/desired drift beyond tolerated bounds

### What is considered acceptable drift
- Provider-managed fields (timestamps, provider default descriptions)
- Autoscaling desired capacity changes made by the approved autoscaler (if explicitly documented and handled via `ignore_changes`)

### Avoiding misuse of `ignore_changes`
- `lifecycle.ignore_changes` must be rare, documented inline, and reviewed by SRE.
- Never ignore:
  - image pinning fields
  - security group rules
  - IAM policies/attachments

### Remediation procedure
1) Confirm whether the drift came from:
   - Approved automation (autoscaler) OR
   - Manual console change OR
   - Provider-side reconciliation
2) If manual change:
   - Prefer reverting via Terraform (make Terraform match intended state).
   - If urgent, document the emergency change and file a follow-up to re-align IaC within 24 hours.
3) If drift indicates compromised/unsafe config (e.g., SG opened broadly):
   - Treat as a security incident per on-call policy and remediate immediately.

## Variable catalog (minimum required)
These variables must exist at the `dedicated_pool` boundary and must be passed explicitly from environment entrypoints:

| Variable | Type | Notes |
|---|---|---|
| `environment` | string | `prod`, `staging`, etc. |
| `pool_id` | string | Immutable identifier; do not reuse |
| `region` | string | Cloud region |
| `gpu_sku` | string | Standard SKU string (see allowlist) |
| `cluster_name` | string | Kubernetes cluster identifier |
| `subnet_ids` | list(string) | Must be private subnets |
| `security_group_ids` | list(string) | Must include baseline GPU worker SG |
| `image_channel` | string | `candidate`/`stable` |
| `image_version` | string | Explicit pin |
| `enable_provision_to_ready` | bool | Enables provisioning hooks/tags/outputs |
| `enable_staged_rollout` | bool | Hard gate for rollout |
| `rollout_allowlist_regions` | list(string) | Required when staged rollout enabled |
| `rollout_allowlist_gpu_skus` | list(string) | Required when staged rollout enabled |

## Common anti-patterns (do not do these)
- Copy-pasting modules per region (creates inconsistent behavior and missed fixes)
- Using `latest` for image selection
- Introducing per-node identifiers in tags (high-cardinality cost/metrics explosion)
- Disabling guardrails to “get it working once” in prod
- Ignoring drift broadly with `ignore_changes = all`
