gpu-ci-safety-orchestrator-and-cost-simulation-harness

Overview
--------
This document describes the GPU CI Safety Orchestrator: a coordinated CI/CD and simulation harness used to validate GPU runtime changes (images, kernel builds, mixed-precision kernels, and Terraform/IaC changes) against safety, performance, and cost guardrails before wide rollout. The orchestrator combines automated canaries, an offline cost-simulation harness, and an IaC adapter that enforces multi-account egress and placement constraints.

Goals
-----
- Provide a deterministic, repeatable pipeline that tests GPU infra changes with production-like placement and egress behavior.
- Surface regressions in allocation, preemption, and cold-start latency before merges reach main.
- Quantify expected unit-cost and egress delta for a given change (image, kernel, TF module) with a simulated tenant workload.
- Automate gating decisions (block/promote) based on SLOs and cost delta thresholds.

Non-goals
---------
- This is not a replacement for full multi-region production canaries (we still run progressive production rollouts).
- Not intended to simulate multi-week long tail effects of noisy neighbors; use long-running eval clusters for that.

High-level architecture
-----------------------
1. CI Orchestrator (service: accelerator-ci-orch)
   - Receives PRs and changes to: GPU images, kernel artifacts, IaC TF modules, and runtime flags.
   - Spins up ephemeral experiment clusters (tenant-sim) in a sandbox account and a mirrored egress topology.
2. Placement/Egress Emulator (service: place-emu)
   - Replays placement decisions using the platform's allocator heuristics; enforces the same tenant quota/priority rules.
3. Cost Simulation Harness (service: cost-sim)
   - Runs synthetic tenant workloads (short inference + eval batches) and profiles token-cost, network egress, and GPU-hours.
4. Gate Engine (service: ci-gate)
   - Evaluates results against configured SLOs and cost thresholds, produces pass/fail + golden-artifact links.

Terraform / IaC adapter requirements
-----------------------------------
To ensure that CI experiments reflect the same placement constraints as production, the orchestrator uses a lightweight IaC adapter. The adapter enforces:
- account-scoped resource tagging (tenant, experiment-id, ci-run)
- ephemeral route tables that mirror production egress sharding
- policy guardrails that inject preemptibility / spot-fallback rules

Example interface contract (table):
| module variable | description | recommended types/values | notes |
|-----------------|-------------|--------------------------|-------|
| tenant_tag | logical tenant id for simulation | string | must map to allocator policy file |
| experiment_profile | preemption/priority profile | enum: [low, medium, high, reserved] | controls simulated preemption |
| egress_gate | egress shard id to emulate | string | matches production shard naming |
| attach_warm_pool | whether to seed warm pool | bool | default true for image/kernel tests |

Snippet: expected tfvars for adapter (example)
```hcl
experiment_profile = "medium"
tenant_tag = "ci-1234"
egress_gate = "egress-shard-us-west-2-a"
attach_warm_pool = true
```

CI pipeline: step-by-step
-------------------------
1) PR opened against: gpu-image, mixed-kernel, or terraform modules.
2) CI Orchestrator validates change format and schedules a CI run.
3) IaC adapter applies tf plan in sandbox account (read-only mocks for external accounts where necessary).
4) Orchestrator deploys the image/kernel to a 3-node ephemeral pool with:
   - allocator configured with the same scoring functions as production
   - simulated egress topology and NAT/fanout rules
5) Cost-sim runs a pre-defined suite for 30 minutes (default) that includes:
   - 5k short-gen requests (text gen distribution matching production p50/p95/p99 lengths)
   - 1 heavy batch eval (long-seq attention stress)
   - 200 embedding requests to measure small-model tail impact
6) Metrics collected: allocation success, preemption count, p95 cold-start, p50 token-latency, GPU-utilization distribution, egress bytes, estimated per-token cost delta.
7) Gate engine compares results to thresholds and produces a decision.

SLOs and gating thresholds (default baseline)
---------------------------------------------
- Allocation success rate: >= 99.5% (measures whether requests were scheduled without backoff).
- Preemption regression: delta <= +1.5x existing preemption count for same workload.
- Cold-start p95: <= 30s for heavy workloads; any change increasing p95 by > 10s fails.
- Latency p50 token: regression < 5% (relative).
- Cost delta: promote if estimated unit-cost change <= +5%; manual review if in (5%, 15%]; fail if > +15%.
- Egress delta: promote only if egress byte delta <= +10% or reviewers sign off.

Interpreting results: scoring rubric
----------------------------------
The gate engine produces a composite score (0–100) computed from weighted SLO pass/fail and cost delta. Sample weights: allocation 35%, preemption 20%, latency 15%, cost 20%, egress 10%. Anything < 60 is an automatic fail.

Cost-simulation details
----------------------
- The harness runs the actual model runtime with sampled traffic traces rather than synthetic microbenchmarks to approximate tokenization patterns and KV-cache reuse.
- Estimated per-token cost = (GPU-hours * hourly-rate + egress-cost + infra-amortization) / tokens_served.
- GPU hourly rates used are pulled from the internal pricing API that mirrors reserved/dedicated + spot footprints to show blended cost.
- The harness supports sensitivity sweeps: change one variable at a time (batch size, sequence length, quantization) and produces a delta matrix.

Example command to run a local simulation (dev):
```bash
# run cost-sim against a built image tag
./bin/ci-run-sim --image redwood/gpu-runtime:pr-2345 --tfvars examples/ci-sim.tfvars --duration 30m --out artifacts/pr-2345.json
```

Outputs produced by a CI run
--------------------------
- artifacts/pr-<id>.json (detailed metrics + trace links)
- prometheus snapshot for the run (push to ci-metrics-bucket)
- cost-report.csv (per-token cost breakdown)
- deployment plan + applied tf state (sandbox)
- gate verdict (pass|manual_review|fail) with justification and diffs to the golden baseline

Runbook: failed canary (quick actions)
------------------------------------
1. Confirm failure mode in artifacts/pr-<id>.json. Identify top regression (allocation/preempt/latency/cost).
2. If allocation/preemption: check allocator logs in place-emu and accelerate-allocator (links are in the artifact). If a scoring change is the likely cause, revert the scoring patch and re-run.
3. If image/kernel increase in cold starts: check warm-pool seeding logs; consider increasing attach_warm_pool = true or run a dedicated warm-pool seeding job.
4. For cost regressions: run sensitivity sweep (batch size / quant / sequence) and attach the cost delta matrix to the PR for reviewers.
5. If unknown or intermittent: escalate to on-call infra lead (pager: infra-oncall) and attach artifacts. Include run id, tf plan, and sample traces.

Rollout checklist (pre-promote)
-------------------------------
1. Ensure unit and integration tests for image/kernel pass.
2. Run full orchestrator a minimum of 3 times across different sandbox accounts (to catch account-scoped egress gating issues).
3. Confirm cost delta < +5% across all three runs.
4. Confirm allocation success >= 99.5% and cold-start p95 within threshold.
5. Add reviewers: release-eng and a representative from customer-success for high-impact changes.
6. Post-promotion: schedule a 24h production smoke canary with rapid rollback path.

Notes and tradeoffs
-------------------
- CI experiments are deliberately time-bounded (default 30m) to maintain CI capacity, which can undercount long-tail noisy-neighbor regressions.
- The cost model uses internal ratecard and approximations for amortization; absolute dollars are approximate but deltas have been validated historically to within +/-8%.
- The IaC adapter intentionally mocks cross-account services (e.g., partner peering) where write access is prohibited; these mocks may hide certain cross-account timing regressions.
