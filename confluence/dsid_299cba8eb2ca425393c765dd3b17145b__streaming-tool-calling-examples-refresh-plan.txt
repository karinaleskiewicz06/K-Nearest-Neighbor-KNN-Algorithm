Streaming + Tool Calling Examples Refresh — Plan (SDKs + Docs + Quickstarts)

## Summary
This plan refreshes Redwood’s developer-facing examples for **streaming responses**, **function/tool calling**, and **structured output (JSON schema)** across:
- SDK repos (Python / TypeScript / Go)
- Docs site (guides + API reference examples)
- Quickstarts/templates
- Runnable samples (redwood-examples)

The intent is to provide **one consistent mental model** across languages so developers can copy/paste snippets and succeed on the first run, while also reducing support load from mismatched semantics.

**Executive sponsor:** Alex Martinez (VP Developer Experience)

---

## Problem statement
Current examples across SDKs and docs diverge in ways that cause real-world confusion and support tickets:
- Streaming event names and handling differ by language; some snippets don’t show robust assembly of deltas.
- Tool calling examples disagree on payload shapes, parallel tool calls, and how/when to send tool results.
- Structured output examples sometimes imply stronger guarantees than the model can provide; parsing/validation guidance is inconsistent.

This produces:
- Higher time-to-first-success in PLG onboarding
- “Works in language X but not Y” parity issues
- Tickets around partial tool args, stream disconnects, and JSON parsing errors

---

## Goals
1) **Streaming parity** across Python/TS/Go
- Use consistent event nomenclature in examples.
- Show reliable “final message assembly” patterns.
- Include error handling for stream termination, timeouts, and retries.

2) **Tool calling parity**
- Align tool definition format and naming.
- Demonstrate argument validation and safe defaults.
- Demonstrate parallel tool calls and correct tool-result message loop.

3) **Structured output parity**
- Provide JSON schema examples that are realistic and copy/pasteable.
- Show validation and failure handling (retry and/or fallback).
- Call out caveats with incremental JSON under streaming.

4) **Maintenance + quality gates**
- Ensure examples match released SDK versions and are tested.
- Add golden transcript fixtures for streaming tool-call sequences.

---

## Non-goals
- Major API redesign of streaming/tool calling protocols.
- New model features (we document current behavior; we do not change it).
- Perfect cross-model determinism for structured output; instead we provide guardrails and fallbacks.

## Canonical example taxonomy
All example updates should map to one of these canonical “recipes.” We will keep naming consistent across repos.

### 1) Basic streaming (text)
**Use when:** developer needs incremental tokens and a final assembled answer.

Must show:
- Consume stream events
- Append deltas to a buffer
- Detect completion
- Handle stream errors + retry guidance (non-automatic)

### 2) Streaming + tool calling (single tool)
**Use when:** simple agent flow with one tool call.

Must show:
- Tool definition
- Tool call detection
- Partial-arguments handling (buffer tool args until valid JSON)
- Tool execution
- Tool-result message
- Continue model call to completion

### 3) Streaming + tool calling (parallel tools)
**Use when:** agent can call multiple tools; developer needs concurrency guidance.

Must show:
- Multiple tool calls in one assistant turn
- Execute tools concurrently (TS: Promise.all; Go: goroutines; Python: asyncio.gather or sequential with note)
- Tool results are returned **one message per tool call**
- Re-enter model call with tool results

### 4) Structured output (JSON schema) — non-streaming and streaming variants
**Use when:** developer needs machine-readable JSON.

Must show:
- Provide JSON schema constraints
- Validate output and handle invalid output safely
- Recommended default: **non-streaming** for strict JSON parsing
- Streaming variant must include warnings and incremental parsing guidance

## Example conventions (what “good” looks like)
These are enforced in review.

### Common conventions
- Prefer consistent model names in examples (docs will provide a “model selection” note).
- Print/log output in a way that makes expected behavior obvious.
- Avoid showcasing unreleased/experimental SDK APIs in primary docs.
- Keep each example runnable with minimal env vars.

### Streaming conventions (examples)
- Event loop should use a `switch`/`if` branch per event type.
- Explicitly show the buffer strategy:
  - `text_buffer += delta`
  - For tool calls: `tool_args_buffer += delta` until valid JSON
- Show a single place where “final assembled message” is produced.

### Tool calling conventions (examples)
- Tool names are `snake_case`.
- Tool args are JSON objects; never rely on positional arguments.
- Validate tool args:
  - Required fields present
  - Types match (e.g., string/number)
  - Bounds checks for known fields
- Tool results:
  - Return structured data where appropriate
  - Include minimal error shape (e.g., `{ "error": "…" }`) rather than throwing raw exceptions

### Structured output conventions
- Include schema with:
  - `type: object`
  - `additionalProperties: false`
  - Required fields
  - Constrained enums/regex where appropriate
- Always validate before using.
- Provide a recommended retry strategy:
  - “Retry once with a tightened instruction”
  - If still invalid, fall back to a non-structured response or abort with a user-visible error

## Definition of Done (DoD)
An example set is “done” when all of the following are true.

### Copy/paste success
- A new user can follow the README/guide and run the example end-to-end with:
  - `REDWOOD_API_KEY` set
  - a single model name configured (if required)
- No manual edits required beyond env/config.

### Parity
- Python/TS/Go examples all demonstrate:
  - same event handling principles
  - same tool calling loop
  - same structured output validation strategy

### Tests and fixtures
- Golden transcript fixtures exist for:
  - streaming with tool call (including partial args)
  - at least one parallel tool calls scenario
- CI runs validations:
  - fixtures parse and match expected event ordering constraints
  - basic lints compile/build in TS/Go

### Docs alignment
- Docs code blocks are updated to match **released SDK versions**.
- Docs include a “Known pitfalls” section covering:
  - truncated/partial tool args mid-stream
  - stream disconnects and retry guidance
  - invalid JSON even under schema constraints, and how to handle it

### Tracking + comms
- Linear tickets closed with links to PRs.
- Release notes/changelog drafted for relevant SDK releases.
- Support enablement message posted (internal) with links to updated docs and examples.

## Risks and mitigations
### Risk: backwards compatibility / unreleased APIs
**Mitigation:** examples must be compatible with released SDK versions; if a newer approach is preferable, include a short “Requires SDK >= X.Y” callout in docs and keep the default snippet on the released path.

### Risk: model variability (tool calling + structured output)
**Mitigation:** document “best effort” vs “guaranteed” behavior; include validation + retry/fallback guidance; add a model support matrix note in structured output guide.

### Risk: streaming edge cases (disconnects, incremental JSON)
**Mitigation:** explicitly show:
- buffering partial tool args
- retry-on-disconnect guidance (idempotency note)
- recommendation to use non-streaming mode for strict JSON outputs

### Risk: CI flakes in golden tests
**Mitigation:** golden fixtures validate structural expectations (event ordering constraints, presence of fields) rather than exact token content; run tests against pinned fixtures rather than live model output.

## Known pitfalls (to be covered in docs + examples)
These map to recurring support issues and must be addressed explicitly.

1) **Tool-call arguments appear truncated mid-stream** (SUP-18421)
- Explanation: arguments are streamed; intermediate deltas may not form valid JSON.
- Fix: buffer until `json.loads()` succeeds (or until a “tool_call_complete” style signal, depending on SDK event model).

2) **Structured output emits invalid JSON** (SUP-18436)
- Explanation: schema constraints improve likelihood but do not guarantee valid JSON across all models/settings.
- Fix: validate; retry with tighter instruction; fallback path.

3) **TypeScript type mismatch / tool result shape** (SUP-18452)
- Explanation: older snippet shapes drifted from SDK typings.
- Fix: align docs snippets with current SDK types; keep compatibility note.

4) **Docs code tabs broken / wrong default tab** (INT-3321)
- Fix: verify code-tab selector; ensure copy button copies active tab.

## Appendix A — “Canonical flow” (language-agnostic)
1) Start a streaming chat request.
2) For each streamed event:
   - If text delta: append to `assistant_text`.
   - If tool call delta: append to `tool_args_buffer[tool_call_id]`.
   - If tool call complete (or buffer becomes valid JSON): parse args and enqueue tool execution.
3) Execute required tool(s) (possibly in parallel).
4) Send tool result message(s) back to the model.
5) Continue until final assistant message completes.
6) If structured output required: validate JSON and retry/fallback on failure.

(For concrete event names and field guidance, see: Streaming Event Model Conventions and ADR for payload shape.)
