GPU Eviction Smoothing & Credit Scheduler — Spec and Runbook

This document specifies a tenant-aware eviction smoothing and credit-based scheduler designed to reduce noisy preemption impact, improve tail latency for interactive inference, and provide a predictable tenant billing signal tied to eviction exposure. It combines a short-horizon predictive filter, time-decayed credit buckets, and topology-aware placement to hedge against large simultaneous preemptions and enable graceful degradation to burst/backfill pools.
Background and why this exists:

- We observed spikes of tenant-visible latency/regressions during large-scale preemptions and spot reclaim events.
- Existing binary eviction/backfill behavior causes tenant request spikes, cache thrashing, and KV-cache warmup storms.
- Teams need a transparent, auditable mechanism to trade cost (eviction exposure) vs. latency predictability.

This spec introduces a scheduling shim that smooths evictions with credits and short-term predictive routing so customers (and internal tenants) experience fewer abrupt QoS regressions while allowing fleet efficiency to remain high.

- Reduce percentiles (p95/p99) of end-to-end inference latency during preemptive events by at least 30% vs today.
- Provide per-tenant eviction-exposure credits that map to billing/alerts.
- Expose a small, well-documented Terraform module and CI checks to enable self-serve adoption across regions.
- Ensure safe fallbacks: when credit exhaustion occurs, route to burst-capacity or lower-cost preemptible pools rather than immediate hard-evict.


- This document does not propose changes to hardware-level preemption settings (BIOS/drivers).
- It does not replace long-term capacity planning policies or reserved capacity contracts.

High-level components:

1) Eviction Predictor (EP): short-horizon time-series filter that consumes node preemption telemetry (spot termination signals, cloud metadata, kernel OOM patterns) and outputs a probability score per node for the next 90s window.

2) Credit Ledger: per-tenant time-decayed credit buckets. Credits are consumed when an instance experiences an unplanned eviction while serving active sessions; credits replenish slowly via background allocation or purchases (billing integration).

3) Smoothing Scheduler: when EP indicates elevated risk, scheduler first consults credit ledger. If tenant has credits, scheduler will attempt to: a) prefer nodes with low risk, b) stagger evictions by migrating short-lived sessions to warm pools, c) throttle new preemptible placements for the tenant.

4) Topology-aware Fallbacks: if entire AZ/region is impacted, route to designated burst pools with explicit KV-cache pre-seeding policies to reduce cold-starts.

5) Observability & Billing Adapter: emits per-tenant eviction events, credit delta metrics, and charge-back fields to infra-telemetry and billing pipeline.
Primary metrics and SLOs:

- Eviction-exposure (EE): number of unplanned evictions per tenant per 24h (target: < 0.05 per tenant-day for premium tiers).
- P95 inference latency during preemption windows (target: 30% reduction vs baseline).
- Credit-bucket depletion rate (operational metric to track adoption).
- Migration success rate (target: > 98% session handoff success when scheduler initiates warm-pool migration).
- Scheduler decision latency (should be < 50ms for placement decision).

Prometheus-style labels to emit: tenant_id, region, node_pool, credit_bucket_id, decision_reason.
Design details and pseudocode:

Overview:
- Credits are represented as a decaying balance: balance_t = balance_{t-1} * e^{-lambda*dt} + allocated - consumed. Lambda chosen to fully decay excess credits over 30 days by default.
- Predictor outputs risk score R in [0,1] per node; scheduler calculates effective_risk = R * node_criticality_factor.

Decision flow (per placement request):
1) Gather candidate nodes and their risk scores.
2) For each candidate, compute score_i = alpha * effective_risk_i + beta * topology_penalty_i + gamma * utilization_i. Lower is better.
3) If tenant_credit_balance > threshold_T: prefer available nodes with score_i < S_preempt. Else: restrict placement to non-preemptible pools or enqueue request to burst queue.
4) On node preemption notification: if active sessions exist, attempt best-effort session transfer to warm pool (session handoff protocol described below) and deduct credit per session transferred (credit cost function in table). If transfer fails within 6s, mark as hard-evict and emit eviction_exposure event.

Session handoff protocol (short):
- Sender checkpoint: send minimal KV-cache diff and session metadata to handoff topic (Kafka).
- Receiver warmup: prefetch checkpointed KV into local cache, attach session token.
- Cutover window: 1–3s window where requests are retried 429->client with fallback routing; client SDK has built-in retry/backoff to follow.

Credit cost table (example):
- short session (< 30s): 0.1 credit
- medium (30s–5m): 0.5 credit
- long (> 5m): 1.5 credits

Tunable knobs: alpha/beta/gamma weights, decay lambda, credit thresholds, handoff timeouts.
Terraform module example (high-level):

module "gpu_eviction_scheduler" {
  source = "git::ssh://git@github.com/redwood/infrastructure-modules.git//gpu-eviction-scheduler"
  region = var.region
  cluster_names = var.cluster_names
  credit_ledger_table = aws_dynamodb_table.gpu_credit_ledger.id
  kafka_topic = module.kafka.eviction_handoff_topic
  ep_stream = module.telemetry.node_risk_stream
  tags = var.common_tags
}

Important outputs:
- module.scheduler_endpoint -> internal address for placement API
- module.credit_ledger_table -> id for billing integration

IaC constraints and checks:
- Module requires IAM role gpu-scheduler-writer with least privilege to DynamoDB, ECS/EKS, and SSM parameters.
- Terraform plan must include a change review gate: if credit bucket policy changes ownership or replenish rate changes > 10% impact, block auto-apply.

CI/CD test hooks to include:
- Unit tests for credit decay math.
- Integration test: simulate EP stream with induced terminations and assert migration success rate > 95% in testbed.
- Security scan: verify no wide-open IAM policies created by module.

Recommended pipeline additions and gating:

- Pre-merge: unit tests, linters, tfsec, and module contract tests (mock DynamoDB + Kafka).
- Canary pipeline: deploy new scheduler module to a shadow cluster (non-customer), run fault-injection (cloud preempt simulation) and collect metrics.
- Promoted deployment must include rollback trigger: if migration success rate drops below 96% or P99 latency increases > 20% in canary windows, automatically roll back.

Test scenarios to codify in CI:
1) Single-node preempt: verify handoff completed and credit deducted.
2) Burst preempt (10 nodes): verify staged evacuations across 30s window instead of instantaneous thrash.
3) Credit exhaustion: verify routing to burst pools and correct billing telemetry emitted.

Operational runbook (oncall steps):

Severity: Eviction-Smoothing SLA breach (pager)
Trigger: p95 latency spikes during preemption window AND migration success rate < 90%
Owner: gpu-fleet-oncall (primary)

Immediate steps:
1) Acknowledge pager and post to #gpu-ops with tags (region, time, incident-id).
2) Query scheduler metrics: recent EP scores, credit-balance per top-5 impacted tenants (Grafana board: "GPU Eviction Smoothing — Live").
3) If EP false-positives spike: disable EP enforcement (feature-flag: scheduler.use_predictor=false) for affected cluster to restore baseline placements.
4) If migration handoff failing: inspect Kafka consumer lag for eviction_handoff_topic, restart consumers with safe-ordering enabled.
5) If credit-ledger is throttled/errored: check DynamoDB write capacity, scale autoscaling policy or switch to on-demand temporarily.

Mitigation and longer-term fixes:
- If repeated cross-tenant failures observed, temporarily increase credit granting rate (ops-only override) and create a ticket to product to reconcile billing later.
- Run targeted canary in same AZ with adjusted alpha/beta weights to recover tail latency.

Post-incident actions:
- Collect: scheduler logs, EP inputs, Kafka handoff traces, migration traces.
- Run root-cause triage within 72h and create remediation PRs for IaC or runtime.

Safe rollback checklist:

- Toggle feature flags in order: 1) disable predictor enforcement, 2) disable credit deductions (preserve ledger state), 3) revert scheduler binary.
- Confirm that no new migrations are initiated during rollback window and that billing emits are paused to avoid false charges.
- Coordinate with billing and product before bulk credit adjustments.

Migration and rollout steps:

Phase 1 — Shadow (2 weeks): deploy scheduler as shadow decision path, emit metrics but do not affect placements. Run chaos tests and tune alpha/beta/gamma.
Phase 2 — Canary (1 cluster, 1 region): enable for low-risk tenants, enable credit accounting in read-only mode.
Phase 3 — Gradual enablement (3–6 weeks): progressively enable for more tenants and add automated replenishment policies for developer sandboxes.
Phase 4 — Global rollout: enable for all preemptible pools with telemetry and billing hooks live.

Rollback windows: 24–48 hours of close monitoring after each stage.
