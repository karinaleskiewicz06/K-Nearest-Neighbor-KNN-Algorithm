GPU Stability Experimentation Lab Notebook

Overview

Purpose: This lab notebook documents reproducible experiments, CI integrations, and telemetry schemas we use to evaluate GPU-driven inference stability under real tenant workloads. The goal is to provide a single reference where engineers can design small-to-large scale experiments, run them safely, and capture metrics in a way that feeds existing SRE dashboards and the model-serving perf database.

When to use: short-lived fidelity tests, kernel rollout canaries, preemptive warm-pool stress tests, and cross-account egress/IO boundary experiments. Not for production benchmarks that feed public docs — use the benchmarking-and-perf-suite for those.

Lab goals and hypotheses
- Goal 1: Quantify stability envelope for mixed-length chat requests when using continuous batching + quantized kernels. Hypothesis: stability regressions correlate with tail latency > 95th percentile and GPU memory fragmentation events.
- Goal 2: Validate preemptive warm-pool seeding reduces cold-KV-cache misses by > 60% for bursty tenant patterns.
- Goal 3: Exercise cross-account egress throttles to measure graceful degradation behavior of the allocator.

Preflight checklist (must pass before any experiment)
1. Create ephemeral Terraform workspace using the test-module (see Terraform sandbox snippet below).
2. Validate network egress ceiling is set to non-production range and egress-billing tags added.
3. Confirm telemetry endpoints are configured and csv+prom exporters enabled. Example dashboards must be present in a synthetic namespace.
4. Register experiment in experiments tracker (link internal) and assign an oncall owner for the duration.

Terraform sandbox snippet (example)
```hcl
module "gpu_experiment_cluster" {
  source = "git::ssh://git@repo.redwood.ai/infra/terraform-modules.git//ephemeral_gpu_cluster"
  name_prefix = "lab-q8-"
  node_count  = 5

```
Notes: use `terraform workspace new lab-<id>` and `terraform apply -var-file=lab-<id>.tfvars`. Destroy immediately after run with `terraform destroy -auto-approve`.

CI/CD integration pattern
- Use a dedicated Buildkite pipeline `lab/experiments` with the following stages: plan -> apply -> run-experiment -> harvest -> destroy.
- Plan stage: produce diffs and post to the experiment ticket.
- Apply stage: gated by approver (owner or SRE).
- Run-experiment: responsible for triggering the load generator and collecting golden traces.
- Harvest: pushes aggregated results to the internal experiments S3, registers metadata in the experiment index (JSON manifest).
- Destroy: teardown and cost-reconciliation.

Load generation and canonical tooling
- Use `inference-loadgen` with tenant-fingerprint profiles. Command example:
`./inference-loadgen --profile burst-chat-70-30 --rps 100 --duration 00:30:00 --out ./runs/lab-123/`
- Always run a short warmup (3–5 minutes) before recording metrics.
- Capture both prom metrics (scrape) and raw traces (jaeger) and the token-level telemetry (tokenizer cache hitcounts, kv-cache eviction counts).

Telemetry schema (required fields)
- Exporter: prom + jsonl trace archive
- Required prom labels: {experiment_id, kernel_variant, node_pool, tenant_class, run_phase}
- Required metrics: gpu_utilization_percent, gpu_memory_free_bytes, kv_cache_hits_total, kv_cache_evictions_total, batch_queue_depth, request_p95_latency_ms, request_p99_latency_ms, oom_events_total

Example CSV manifest (one-line per run)
experiment_id,started_at,ended_at,kernel_variant,node_count,egress_ceiling_mbps,notes
lab-20250220-01,2025-02-20T10:02:00Z,2025-02-20T10:32:00Z,q8_nightly,5,200,short-warmup-3m

Safety controls and automated cutoffs
- Circuit-breaker Lambda: watches p95 latency and OOM count; will post to Buildkite and trigger an immediate `destroy` if thresholds exceeded.
- Billing guard: if projected egress > $500 for the experiment tag, CI job will abort.
- Network isolation: experiments must use sandbox VPC prefixes documented in `eng-infra/cloud-accounts` and not route to customer VPCs.

Post-run analysis checklist (minimum)
1. Upload JSON manifest and raw traces to /internal/experiments/<experiment_id>.
2. Run `lab-analysis` script to compute delta vs baseline.
3. Check for kernel-related regressions: spike in kv_cache_evictions_total or new OOM stack traces.
4. Create an anomaly ticket if: (a) p99 latency regressed > 30% vs baseline, (b) new OOM signature seen, or (c) batch_queue_depth > 95th percentile of known safe runs.

Result reporting template (to paste into ticket)
- Summary: one-line outcome
- Key metrics: p95, p99, kv_cache_evictions_total change, total OOMs
- Artifact links: terraform plan, buildkite run id, s3 manifest, jaeger link
- Recommendation: rollback / promote / further-research

Experiment lifecycle and retention
- Keep run artifacts for 90 days in S3.
- Manifests and high-level summaries are stored indefinitely in the experiments index (small JSON per experiment).
- Any experiment that affects production-facing metrics must be promoted to a tracked canary and a follow-up runbook created.

Common pitfalls and troubleshooting tips
- Symptom: p95 latency spikes only on some nodes. Check kernel versions and CUDA driver mismatch with `nvidia-smi` and `ldd` on the runtime.
- Symptom: sudden KV cache evaporation. Check for aggressive eviction config or OOM-driven restarts on the allocator side.
- Symptom: noisy egress billing. Validate VPC NAT gateway metrics and confirm egress_ceiling_mbps applied.

Appendix: quick commands
- Create workspace: `terraform workspace new lab-<id>`
- Apply: `buildkite-agent pipeline upload pipeline.yml --var EXP_ID=lab-<id>`
- Collect traces: `./collect-traces --experiment lab-<id> --out /tmp/traces`
- Destroy: `./destroy-lab.sh lab-<id>`
