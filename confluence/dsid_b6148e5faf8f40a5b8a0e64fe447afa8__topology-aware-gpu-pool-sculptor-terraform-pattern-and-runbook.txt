Topology-aware GPU Pool Sculptor: Terraform pattern and capacity runbook

Purpose:

This document describes the "Topology-aware GPU Pool Sculptor" pattern: a Terraform module and CI/CD workflow that builds and continuously adjusts logically isolated GPU pools across zones and accounts based on topology, tenant SLOs, and cost signals. The goal is to provide predictable per-tenant latency SLOs while minimizing cross-account egress and burst cost.

Scope and audience:
- Audience: infra engineers, platform SREs, and Terraform module authors.
- Scope: Terraform module design, CI/CD gating for topology changes, synthetic workload-simulation steps, and an on-call runbook for capacity shortfall events.

Background:
- We run multi-account multi-region GPU pools. Past incidents have been driven by topology-agnostic scaling: tenants placed across wrong AZs or with burst paths that cross NAT/egress bottlenecks.
- The Sculptor pattern enforces topology-aware placement (AZ affinity, interconnect latency constraints) and provides CI-guarded changes to pool composition.

Key concepts and terminology:
- Sculptor module: Terraform module that materializes GPU pools (node groups, placement group labels, NAT/Egress routing annotations).
- Pool shape: a named mix of instance types and counts tuned for specific workload classes (short-chat, long-context, batch-eval).
- Topology profile: zone/cross-AZ affinity settings and egress routing hints.
- Safety lanes: pre-configured decompositions that allow graceful degradation (spillover, reduced-concurrency mode).

Design overview:
- Pools are defined declaratively in a single TF file per environment: pools.tf. Each pool maps to a k8s nodeSelector + taints and an egress routing tag.
- The TF module exposes inputs: pool_name, topology_profile, pool_shape (list of instance spec strings), capacity_targets {min,max}, preempt_policy, egress_tag.

Terraform module pattern (example):

```hcl
module "gpu_pool_sculptor" {
  source = "git::ssh://git@repo.internal/infra/terraform/modules//gpu-pool-sculptor?ref=v1.4.0"

  pool_name        = "short-chat-west-1"
  topology_profile = "zone-affine-low-egress"
  pool_shape       = ["g5.12x:6", "g5.2x:8"]  # format instance_type:count
  capacity_targets = { min = 14, max = 32 }
  preempt_policy   = "warm-warmback"
  egress_tag       = "egress-usw-01"

  labels = { team = "inference", workload_class = "latency" }
}
```

Important module behaviours:
- Placement validation: module fails plan if pool_shape spans more than 2 AZs for topology_profile zone-affine-* unless allow_multi_az is true.
- Egress annotation: sets a resource tag consumed by the egress-proxy operator to pin tenant routing.
- Pool shaping hook: a post-apply step writes desired pool composition to the capacity-reconciler service (via a small HTTP call).

CI/CD gating and promotion workflow:
1) Branch: changes to pools/*/*.tf are limited to a single pool per PR.
2) Pre-merge checks (automated):
   - tfsec and tflint
   - plan with topology static-checker (ensures no cross-account egress wildcard)
   - synthetic-workload simulation (see below) runs in ephemeral sandbox and returns latency + cold-start debt metrics
3) Reviewers required: 1 infra oncall + owner team service lead.
4) Post-merge: canary apply to shadow account for 1 hour, smoke test, then apply to prod accounts with 30-minute stagger per region.

Synthetic workload simulation (local harness):
- Purpose: estimate the tail-latency shift and cold-KV cache warmup cost from pool changes.
- Command (ephemeral sandbox):

  ./scripts/simulate_pool_change --pool-manifest=pr/123/pools.tf --duration=20m \
    --workload-profile=short-chat --out=artifacts/pr-123/sim.json

- The harness produces metrics JSON with fields: p50_latency_ms, p95_latency_ms, p99_latency_ms, kv_cache_miss_rate, tokens_per_second_cost_estimate. The CI job fails if: p99_latency_ms increases by > 15% or kv_cache_miss_rate > 12% absolute.

Operational SLOs and metrics table:

| Metric | Target | Alert threshold | Owner |
|---|---:|---:|---|
| Pool allocation success (per apply) | 100% | < 99% | infra-provisioning |
| Pod scheduling latency (p95) | < 60s | > 120s | k8s-scheduling |
| Inter-AZ egress (bytes/min) per pool | < 50 MB/min | > 200 MB/min | network-team |
| p99 inference latency (tenant) | <= 450 ms | > 700 ms | serving-runtime |

Runbook: capacity shortfall (priority incident)
1) Triage: PagerDuty alert -> infra SRE oncall.
2) Quick checks (10 min):
   - kubectl get nodes -l pool=<pool_name> --wide
   - curl -s http://capacity-reconciler.internal/pools/<pool_name>
   - Check metrics in Grafana: pool_node_utilization, pod_pending_reasons, inter_az_egress_rate
3) Fast mitigation (within 20 min):
   a) If node provisioning failed (cloud API quota or spot shortage): flip pool into safety_lane "reduced-concurrency" via the sculptor API: 
      curl -X POST -d '{"pool":"<pool>","lane":"reduced-concurrency"}' https://sculptor.internal/api/v1/override
   b) If egress hotspot detected: apply egress-fanout rule to route traffic to regional egress gateway: 
      ./scripts/apply-egress-fanout --pool <pool_name> --gateway egw-usw-02
   c) If scheduling backlog: scale up emergency warm-pool (pre-allocated) in the same AZ: 
      terraform apply -target=module.gpu_pool_sculptor.emergency_warm_pool
4) Post-incident remediation (within 48 hours):
   - Root-cause analysis, update topology_profile if needed, add new pool_shape to absorb load, update capacity targets, and run capacity chaos tests.

Ownership and escalation:
- Module owners: infra/platform (contact: #infra-modules)
- Oncall for provisioning incidents: infra-sre rotation
- Egress operator owner: network infra

Rollout checklist for new pool shapes:
- [ ] Draft pools.tf and run `./scripts/simulate_pool_change` locally.
- [ ] Open PR with single-pool change and add synthetic sim artifacts.
- [ ] Pass CI static checks and simulation thresholds.
- [ ] Infra oncall review and merge.
- [ ] Canary apply to shadow account + 1-hour observation.
- [ ] Staggered apply in prod accounts.
- [ ] Post-apply smoke tests and tagging of telemetry dashboards.

Testing and chaos experiments:
- Use the chaos harness `chaos/gpu-topology-tilt` with parameters:
  --target-pool short-chat-west-1 --strip-az us-west-1b --duration 15m
- Run in staging first, assert no more than 10% p99 increase.

Known limitations and future work:
- Current sculptor only pins to egress_tag strings; next iteration will support explicit NAT gateway allocations per pool (Q2 2025).
- The simulation harness approximates KV cache behavior and can under-estimate miss-rate for long-context workloads.

- Inspect plan diffs for topology checks:
  terraform plan -var-file=env/usw/pools.tf -out=out.plan && terraform show -json out.plan | jq '.resource_changes[] | select(.address | contains("gpu_pool_sculptor"))'
