KV Cache Memory Layout Overview (Allocator + Compaction)

## Purpose
This page documents the serving runtime’s KV cache memory layout and allocator structures, and describes the compaction-related state machines introduced in runtime 1.22. The goal is to make the KV arena behavior predictable under mixed sequence lengths and bursty churn, while keeping decode throughput stable.

**Audience:** runtime engineers, kernel engineers, SREs debugging tail latency/OOM, and performance engineers updating benchmarks.

---
## Terminology
- **KV cache:** Per-sequence cached key/value tensors for attention, extended incrementally during decode.
- **Sequence (seq):** A single request stream (chat or completion) tracked by the scheduler.
- **Token position:** Decode step index within a sequence.
- **Page:** Fixed-size allocation unit in the KV arena. Pages are the unit of accounting, relocation, and free-list management.
- **Block:** A logical view of KV storage assigned to a sequence for a contiguous range of token positions; implemented as one or more pages.
- **Arena:** Pre-reserved GPU memory region used for KV pages (per model profile / device).
- **Fragmentation:** Free memory exists but is split across non-adjacent page runs, increasing allocation overhead and increasing the chance of opportunistic eviction/compaction at bad times.

---
## High-level layout
The KV cache is stored in a GPU-resident arena allocated per device, partitioned into pages.

**Key design constraints:**
1. Allocation must be fast on the decode critical path (O(1) or small constant factors).
2. Relocation (compaction) must be safe during concurrent decode, cancellation, and streaming.
3. The runtime must be able to attribute memory to a seq for eviction decisions and observability.

### Diagram (conceptual)
```
KV Arena (GPU)
+--------------------------------------------------------------+
| Page 0 | Page 1 | Page 2 | Page 3 | Page 4 | ... | Page N     |
+--------------------------------------------------------------+
   ^ used by seq A   ^ free    ^ used by seq B   ^ free

Compaction moves “used” pages to form longer contiguous free runs.
```

---
## Page and block format
### Page size and alignment
- **Default page size:** 2 MiB (profile-dependent; see configuration section).
- **Alignment:** 256 bytes minimum; page base is aligned to 2 MiB.
- **Rationale:** 2 MiB is a good tradeoff between allocator metadata overhead and relocation granularity; it also plays well with large contiguous copies.

### What a page contains
A page is a container for KV data plus a small header stored in CPU memory (metadata) and a corresponding lightweight tag stored in GPU memory for debugging/tracing.

**CPU-side page metadata (per page):**
- `page_id` (u32)
- `state` (enum; Free, Allocated, RelocatingSrc, RelocatingDst, Quarantined)
- `owner_seq_id` (u64; 0 for free)
- `owner_layer_range` (small range or profile id)
- `token_span` (start_pos, length)
- `refcount` / `pin_count` (for pinned sessions / in-flight kernels)
- `last_touched_ts` (for eviction heuristics)

**GPU-side tag (optional, debug builds / sampling):**
- `page_id`, `seq_id`, `generation` (to detect stale pointers)

### Block view (per sequence)
Each sequence maintains a list of blocks describing where its KV lives. Blocks are appended as decode progresses.

**Block fields:**
- `seq_id`
- `start_pos` (token index)
- `length` (tokens)
- `page_run` (start_page, num_pages)
- `layout_profile` (model-specific KV stride and packing)

**Invariant:** For a given seq, blocks are strictly increasing in `start_pos` and non-overlapping.

---
## KV tensor packing within a page
KV storage is model-profile specific but follows a consistent abstraction:

- KV is stored per layer, per head (or grouped heads), per token position.
- The runtime uses a **layout profile** (resolved at model load) to compute per-token KV bytes and the page fill factor.

### Layout profiles
A layout profile defines:
- `dtype` (fp16/bf16/int8 for quantized KV where supported)
- `head_dim`
- `num_kv_heads`
- `layers_per_arena_group` (some models group layers across arenas)
- `kv_stride_bytes` (bytes per token position per layer-group)
- `pack_mode` (contiguous K then V; or interleaved KV)

### Addressing function (conceptual)
Given `(page_base, token_pos, layer, kv_head, component)`:
- `offset = token_pos * kv_stride_bytes + layer_offset(layer) + head_offset(kv_head) + component_offset(component)`
- `component` ∈ {K, V}

**Notes:**
- The scheduler treats pages as opaque; only the attention kernels interpret the layout profile.
- Compaction never changes the logical layout; it only moves whole pages (or page runs) and updates block metadata.

## Allocator structures
### Arena
Each GPU device maintains one or more KV arenas:
- **Hosted:** typically one arena per (model, quantization profile, device).
- **Dedicated:** may allocate per pool with higher headroom to reduce eviction pressure.

**Arena fields (CPU):**
- `base_ptr` (GPU VA)
- `page_size_bytes`
- `num_pages`
- `watermarks` (low/high pressure thresholds)
- `feature_flags` (compaction enabled, eviction enabled, debug sampling)

### Free list management
We maintain two complementary indices:
1. **Run-based free list:** tracks contiguous free page runs for fast “best fit within class” allocations.
2. **Bitmap / page state array:** tracks per-page state for correctness checks and fast scanning.

**Allocation path (simplified):**
1. Determine required pages for requested `token_span` growth (rounded up).
2. Attempt to allocate from a free run of sufficient length.
3. If no run available but total free pages is adequate → fragmentation case (signals compaction candidate).
4. If under high pressure and compaction budget exhausted → eviction may be triggered depending on tier/policy.

### Fragmentation measurement
We track fragmentation at the arena level.

**Definitions (used in metrics and guardrails):**
- `free_pages_total`
- `largest_free_run_pages`
- `fragmentation_ratio = 1 - (largest_free_run_pages / max(1, free_pages_total))`

Interpretation:
- 0.0 means all free pages are in one contiguous run.
- Values approaching 1.0 indicate heavy fragmentation.

## Compaction: design overview
Compaction reduces fragmentation by relocating allocated pages into lower-address regions, consolidating free space into larger contiguous runs.

**Key properties:**
- **Incremental:** bounded by a time/bytes budget to avoid decode stalls.
- **Safe under concurrency:** respects in-flight kernels and cancellation.
- **Observable:** exports bytes moved, time spent, stalls avoided, and correlation exemplars.

Compaction operates at the page granularity (whole pages), not individual tokens.

---
## Compaction state machines
Compaction is represented by two linked state machines:
1) **Arena-level compaction controller** (plans work and consumes budget)
2) **Per-page relocation lifecycle** (safe movement and commit)

### 1) Arena-level compaction controller
**States:**
- **Idle:** No compaction planned.
- **Armed:** Fragmentation threshold exceeded; waiting for scheduler phase/budget.
- **Planning:** Identify candidate runs: destination free run (low address) + source allocated pages (high address).
- **Relocating:** Execute relocation steps while budget remains.
- **RebuildingFreeRuns:** Update run lists/bitmaps for newly freed pages.
- **Cooldown:** Brief pause to avoid thrash (hysteresis).
- **Aborted:** Stop due to kill-switch, errors, or pressure changes.

**Transitions (high-level):**
- Idle → Armed when `fragmentation_ratio` > trigger and `free_pages_total` above minimal working set.
- Armed → Planning at scheduler boundary (prefill end, decode batch boundary) when budget granted.
- Relocating → Cooldown when budget consumed or no safe candidates.
- Any → Aborted if kill-switch enabled or correctness guard triggers.

### 2) Per-page relocation lifecycle
Relocation moves a page’s contents from a source page to a destination page.

**States:**
- **Allocated:** Page is owned by a seq.
- **RelocatingSrc:** Source is selected; pinned/refcount checked.
- **RelocatingDst:** Destination reserved and tagged.
- **CopyInFlight:** Copy kernel launched (async).
- **CommitPending:** Await synchronization point where it is safe to update pointers.
- **Committed:** Block metadata updated; destination becomes the new owner.
- **Reclaimable:** Source has no pins; can return to free list.
- **Quarantined:** Used if an error is detected (prevents reuse until inspected).

**Safety rules:**
- A page can only transition to `RelocatingSrc` if `pin_count == 0` (or if pins are from known-safe phases with explicit handoff).
- Commit is performed at a scheduler-managed quiescent point to avoid kernels reading old addresses.
- Cancellation is handled by either (a) finishing relocation then freeing both old metadata and destination if seq ended, or (b) aborting before commit and releasing destination. See bugfix notes in runtime 1.22.1 for edge cases.

## Scheduler integration points
Compaction is not allowed to steal unbounded time from decode.

**Budget enforcement** (see ADR: compaction budgeting):
- Budget is granted in **bytes moved** and **wall time** (whichever is hit first).
- The scheduler allocates budget at specific boundaries:
  - After prefill, before entering steady decode batches
  - Between decode micro-batches when queue depth is stable
  - During backpressure handling (optional), to reduce future allocation pressure

**Guideline:** avoid launching compaction copy kernels on the critical path when p99 latency is already elevated unless memory pressure is high.

---
## Eviction interaction (tier-aware)
Eviction is separate from compaction but uses the same observability surface.

- Compaction is preferred when total free pages are sufficient but fragmented.
- Eviction is considered when the arena is under pressure (low free pages) or when compaction cannot create a sufficiently large run within budget.

**Tier-aware behavior (summary):**
- Lower-priority tiers are eligible for eviction earlier.
- Pinned sessions (explicit) are protected.
- Prefix-cache pages may be marked preemptible depending on profile.

## Configuration (runtime flags)
This page documents the “shape” of configuration; exact names may differ by environment.

| Flag / Setting | Default (Hosted) | Default (Dedicated) | Notes |
|---|---:|---:|---|
| `kv.page_size_mib` | 2 | 2 | Profile-dependent; changing requires validation. |
| `kv.compaction.enabled` | true (canary-gated) | true (pool-gated) | Kill-switch overrides. |
| `kv.compaction.fragmentation_trigger` | 0.35 | 0.45 | Dedicated often tolerates more fragmentation due to headroom. |
| `kv.compaction.max_bytes_per_step` | 256MiB | 512MiB | Upper bound per scheduler-granted step. |
| `kv.compaction.max_ms_per_step` | 2ms | 3ms | Target to avoid p99 regressions. |
| `kv.compaction.cooldown_ms` | 50ms | 50ms | Prevent thrashing. |
| `kv.eviction.enabled` | true | true | Policy is tier-aware + LRU by seq. |

**Operational note:** oncall should prefer flipping `kv.compaction.enabled=false` before disabling eviction if correctness is suspected; see runbook for ordering.

## Observability hooks
Metrics and trace spans are mandatory for rollout.

**Core metrics (names standardized elsewhere):**
- `kv_fragmentation_ratio` (gauge)
- `kv_free_pages_total` (gauge)
- `kv_largest_free_run_pages` (gauge)
- `kv_compaction_bytes_moved_total` (counter)
- `kv_compaction_time_ms_total` (counter)
- `kv_compaction_steps_total` (counter)
- `kv_compaction_aborts_total` (counter)
- `kv_evictions_total{reason,tier}` (counter)

**Tracing:**
- `kv.compaction.plan` span
- `kv.compaction.copy` span (includes bytes, src/dst page ids sampled)
- `kv.compaction.commit` span
- `kv.eviction.select` span

**Required dashboards:**
- Fragmentation ratio over time with p95/p99 latency overlay
- Bytes moved + steps per minute
- Evictions per minute by tier and reason

## Correctness invariants and guardrails
### Invariants
- A page is owned by at most one seq at a time (`owner_seq_id` is single-valued).
- A block references only pages in `Allocated` or `RelocatingDst` state (during commit).
- No page can be freed while pinned.
- Commit is atomic from the scheduler’s perspective: either the seq sees old pages or new pages, never a partial mix for a given token span.

### Guardrails
- Quarantine any page involved in a failed relocation until inspected.
- If repeated aborts occur (e.g., >N per minute), automatically reduce compaction aggressiveness and alert.
- If p99 latency increases beyond canary threshold while compaction bytes moved spikes, trigger automated rollback (see SRE guardrails page).

## FAQ
**Why move whole pages instead of compacting within a page?**
Page-level movement keeps attention kernels and layout profiles simple and avoids per-token repacking, while still addressing allocator fragmentation (the dominant contributor to tail spikes under churn).

**Does compaction change output quality?**
No. It does not change numeric operations; it only changes where KV resides in GPU memory.

**What’s the most common operational failure mode?**
Aggressive compaction budgets can introduce additional copy work and scheduling interference, showing up as p99 spikes during bursts. The rollout defaults favor stability; tuning should be validated in benchmark-lab and perf-canary.
