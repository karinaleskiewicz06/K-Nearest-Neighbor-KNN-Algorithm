GPU artifact retention and supply chain hygiene

Summary
This document defines Redwood's engineering standards for long-lived GPU-related build artifacts, container images, Terraform/IaC bundles, and model-eval binaries. It covers retention policies, provenance and signing, supply-chain hygiene checks in CI/CD, storage lifecycle rules, and emergency rollback/cleanup steps. The goal is to reduce storage bloat, limit risk from stale artifacts, and make forensic/reproducibility traceability straightforward while meeting cost and compliance targets.

Scope
- Artifact types: container images (ECR/ACR), OCI manifests, model binaries (s3), evaluation bundles (tar.gz), Terraform module releases, AMIs/golden images, VM snapshots.
- Systems: CI (GHA/Argo), Artifact registries, S3 buckets, Terraform module registry, image scanner (Trivy/Anchore), signing system (sigstore/cosign), IAM/KMS.
- Teams: infra, eng-serving-runtime, eng-infra, security, platform.

Principles
1) Minimal retention justified by ownership and business need. Keep default retention conservative to save cost; allow exceptions via tickets.
2) Provenance metadata stored with every artifact: build-id, commit SHA, pipeline-id, builder image, signing certificate fingerprint, and optional eval-id.
3) Machine-verifiable integrity: all production images/modules must be signed before promotion to protected registries.
4) Automated hygiene gates in CI: vulnerability thresholds, reproducible build checks where feasible, and transitive dependency review for IaC modules.
5) Safe deletion: deletions should be reversible within a short window (soft-delete) and have owner-approved exceptions for permanent removal.

Retention policy (default tiers)
- Protected production images: retain 90 days by default; retain last 10 tagged release images indefinitely if release tag semantics used.
- Candidate/staging images: retain 30 days.
- CI ephemeral artifacts (per-pipeline): retain 7 days.
- Terraform module release bundles (registry): keep last 6 versions; versions older than 6 are archived to cold storage (glacier-equivalent) for 1 year then deleted unless exception raised.
- Model eval bundles and large model artifacts (>1GB): retain 180 days for active projects; archival to cold storage after 180 days.
- AMIs / golden images: keep last 5 per image stream; older images flagged for deletion after automated test against snapshot rollback matrix.

SLOs and thresholds
- Artifact retention cost target: keep month-over-month artifact storage growth < 12%.
- Scan coverage SLO: 100% of images promoted to production must have a successful vulnerability scan result within 24 hours of creation.
- Signing SLO: 100% of promoted artifacts must be signed; failures block promotion.

Owners and responsibilities
- Infra CI Owners (eng-infra): implement lifecycle enforcement in registry and S3 lifecycle policies; provide infra-level tooling and dashboards.
- Service owners (team owning model/service): classify artifacts, file exceptions, and approve archivals/deletions.
- Security: maintain scanning thresholds and review high-severity exceptions.
- Storage/FinOps: report monthly storage costs and growth.

Technical components and configuration samples
1) S3 lifecycle rules (recommended)
- Use object tags to indicate lifecycle policy: "artifact:protected", "artifact:staging", "artifact:ci-ephemeral".
- Sample lifecycle (YAML-like description):
  - Rule ID: "ci-ephemeral-cleanup"
    Filter: tag=artifact:ci-ephemeral
    Action: Transition to STANDARD_IA after 15 days, Expire after 7 days (soft-delete + versioning retention 30 days)
  - Rule ID: "protected-to-archive"
    Filter: tag=artifact:protected AND tag=keep:short-lived!=true
    Action: Transition to GLACIER after 365 days, Expire after 1095 days

2) ECR registry lifecycle policy (JSON)
- Keep last 10 images with tagPrefixList ["release-"] forever; expire untagged and dev tags older than 30 days.
- Example snippet to be managed by IaC:
  "lifecyclePolicyText": "{\n    \"rules\": [\n      {\"rulePriority\": 1, \"description\": \"Keep release images\", \"selection\": {\"tagStatus\": \"tagged\", \"tagPrefixList\": [\"release-\"], \"countNumber\": 10}, \"action\": {\"type\": \"expire\"}},\n      {\"rulePriority\": 2, \"description\": \"Expire dev tags\", \"selection\": {\"tagStatus\": \"tagged\", \"tagPrefixList\": [\"dev-\", \"ci-\"], \"countNumber\": 1}, \"action\": {\"type\": \"expire\"}}\n    ]\n  }"

3) Cosign signing + provenance: recommended pipeline step (bash)
  - Build image and tag with pipeline-id and commit SHA: IMAGE=registry.redwood.local/service:ci-${{ pipeline_id }}-${{ short_sha }}
  - cosign sign --key k8s://projects/infra/secrets/cosign/key-pair $IMAGE
  - cosign verify --attestation $IMAGE || exit 1

4) CI gate example (GitHub Actions)
  - name: Build and scan
    run: |
      docker build -t $IMAGE .
      ./scripts/run-trivy.sh $IMAGE --severity HIGH,CRITICAL --timeout 5m || exit 1
      ./scripts/cosign-sign.sh $IMAGE || exit 1

Automation and enforcement patterns
- Central enforcement: terraform module (registry) and Terraform-managed ECR/S3 lifecycle policies are the ground truth. Self-serve UIs should only request exceptions which create a ticket in the infra exceptions queue.
- Periodic audits: a weekly job (infra-daily) calculates orphaned artifact counts, unscanned images, and unsigned images; emails owners with an action list and generates a paging alert if >5% of promoted artifacts violate rules.
- Soft-delete window: implement object versioning for S3 and image immutability exceptions for ECR; soft-delete window defaults to 30 days for all protected artifacts to allow quick restores.

IaC module and naming conventions
- Terraform module releases should follow semantic versioning and include a CHANGELOG.md and provenance metadata file named PROVENANCE.json alongside the module bundle.
- Module registry naming: modules/redwood/<service>/<module> vX.Y.Z. Module bundles must include a SHA256 checksum file and signed release.

Supply-chain hygiene checks in PRs
- PR checklist for infra changes affecting artifacts:
  1) Does this change modify lifecycle policies or retention? Add tests.
  2) Does this change introduce new third-party tooling or builder images? Update OSV/whitelist.
  3) Is cosign signing integrated into the pipeline? Configure keys in KMS and confirm access controls.
  4) Are destructive deletion steps gated by service-owner approval? Add required reviewers.

Incident response and rollback playbook (high-level)
1) Detection: infra-daily alert or registry-scan detects suspicious deletion or unsanctioned retention change.
2) Triage: infra oncall captures pipeline-id and artifact identifiers; freeze lifecycle rules by toggling a locking tag and escalate to infra-SRE and security.
3) Restore: if soft-delete/versioning enabled, restore object versions via S3 console or CLI and re-tag images to protected prefix. If images were fully deleted, attempt cross-region replica recovery (ECR replication) and consult backup snapshots (if available).
4) Root-cause: identify the IaC change, PR, or manual action and open postmortem. Add safeguards: require module owner approval for policies that change expiration rules.
5) Communication: notify affected service owners and create a customer-impact assessment if production images were removed.

Operational runbook snippets
- Query unsigned images (AWS example, CLI):
  aws ecr describe-images --repository-name service-x --query 'imageDetails[?contains(imageTags, `protected`) == `true` && imagePushedAt < `2025-01-01`].imageTags'
- List old AMIs:
  aws ec2 describe-images --owners self --filters Name=name,Values="redwood-golden-*" --query 'Images[?CreationDate<`2024-06-01`].[ImageId,CreationDate]'

Metrics and dashboards
- Dashboard panels to maintain:
  - Monthly storage spend by artifact type (S3, ECR, AMI snapshots).
  - Percentage of production artifacts with valid signatures and fresh scans.
  - Number of orphaned artifacts older than retention threshold.
  - Rate of retention-exception requests and average approval time.

Exception process
- Create an infra-exception ticket in "Infra Artifact Exceptions" board with: artifact identifiers, justification, owner, requested retention, and expiry of exception.
- Exceptions auto-expire at requested date; infra will not approve >1 year without Finance sign-off.

Checklist for onboarding a new service
1) Define artifact class and retention need in service onboarding doc.
2) Add pipeline steps: tagging conventions, cosign signing, trivy scan.
3) Ensure S3/ECR tags and lifecycle rules are honored by pipeline.
4) Add service to artifact-cost dashboard and FinOps alerts.

Related controls and references
- Signing: sigstore + cosign recommended.
- Scanning: Trivy for quick checks; Anchore for deeper policy enforcement.
- Provenance: attach PROVENANCE.json with schema {build_id, commit_sha, build_time, pipeline_id, signer}.
- Storage lifecycle: use tags rather than prefix conventions to enable flexible rule composition.

Appendix B — Quick CI snippet (GitHub Actions YAML excerpt)
name: Build & Promote
on: [push]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Build image
        run: |
          IMAGE=registry.redwood.local/${{ github.repository }}:ci-${{ github.run_id }}-${{ github.sha::8 }}
          docker build -t $IMAGE .
      - name: Trivy scan
        run: ./scripts/run-trivy.sh $IMAGE --severity HIGH,CRITICAL --timeout 5m
      - name: Sign artifact
        run: ./scripts/cosign-sign.sh $IMAGE
      - name: Push
        run: docker push $IMAGE
