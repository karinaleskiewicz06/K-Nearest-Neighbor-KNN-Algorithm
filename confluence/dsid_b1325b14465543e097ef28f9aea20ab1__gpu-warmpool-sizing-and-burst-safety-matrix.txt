GPU warm-pool sizing and burst safety matrix

Overview

This document defines the guiding principles, SLO-driven sizing heuristics, and an actionable safety matrix for GPU warm pools used by Redwood inference customer-facing fleets. The aim is to ensure predictable latency for bursty traffic while keeping cost and preemption risk within acceptable bounds. This page is intended for infra engineers, oncall SREs, and platform/product teams that configure pool policies.

Goals
- Keep steady-state reserve (warm) capacity sufficient to absorb common burst patterns without impacting P95/P99 latency SLOs.
- Provide a clear, auditable sizing matrix tied to measurable signals (queue depth, cold-start time, token tail latency).
- Define automated safeguards and rollback criteria for autoscaling or bursting across accounts/regions.

Scope
- Applies to all hosted and dedicated GPU pools that support low-latency inference: serving pools for text-generation, chat, and embeddings.
- Does NOT apply to long-running batch/eval clusters (use separate batch pools).

Key concepts and services
- warm-pool-controller: K8s controller that pre-warms GPU nodes and maintains node images/labels.
- burst-router: service that routes overflow requests to regional burst pools or dedicated spare capacity.
- capacity-allocator: Terraform/IaC module and controller that provisions node pools and manages spot vs on-demand mix.
- cold-start latency: time from allocation request to node Ready + runtime warm; measured by metric gpu/node_cold_start_seconds.

Primary SLOs and thresholds (product-level reference)
- P95 request latency (token end-to-end) <= 200ms for hosted-tier customers.
- Cold-start latency target: median <= 45s, P95 <= 120s for GPU node provisioning.
- Warm pool availability (nodes Ready fraction) >= 99.5% across regions during business hours.

Sizing heuristics (rule-of-thumb)
1) Observe burst profile: compute 95th percentile burst size over rolling 7-day window using metric serving/request_concurrent_peak.
2) Compute warm nodes required = ceil((peak_concurrent_requests * average_gpu_parallelism) / requests_per_gpu_slot).
3) Add safety margin: for latency-sensitive pools, +15%; for non-critical, +5%.
4) If spot-based warm pool: increase safety margin by additional 10% during spot-volatile windows (see Spot volatility table below).

Example calculation
- 95th burst concurrent requests = 280
- average_gpu_parallelism = 4 requests per GPU (model-specific multiplexing)
- requests_per_gpu_slot = 4 -> base nodes = ceil((280 * 1) / 4) = 70 nodes
- safety margin (latency-sensitive): 70 * 1.15 = 81 nodes (round up -> 81)

Warm-pool sizing and burst safety matrix

This matrix maps observed signals to an action and guardrail. Use it during incident response and automated scaling policy reviews.

| Signal (metric) | Threshold (7d lookback) | Action | Guardrail / Rollback criteria | Owner | Notes |
|-----------------|-------------------------:|--------|------------------------------|-------|-------|
| queue_depth_per_gpu > 0.8 | sustained 10m | Increase warm pool by +15% via capacity-allocator plan; notify oncall | If P95 latency improves < 10% after 15m, revert increment; if error-rate increases, rollback | infra-sre | High priority for chat model pools |
| node_cold_start_seconds P95 > 120s | single region | Trigger preflight: re-image warm-pool nodes, drain and re-provision top 5% oldest nodes | If cold-start remains >120s after 30m, failover to secondary region via burst-router | platform-ops | Possible cloud API throttling |
| spot_reclaim_events rate > 3/hour | 30m window | Shift 30% of warm pool to on-demand; annotate plan and run as canary | If cost delta exceeds budget threshold (see finance alert), reduce on-demand shift to 15% and alert cost-eng | infra-finops | See Spot volatility table |
| sustained_cpu_utilization_per_node < 10% and billing_utilization < 5% | 60m | Consider downsizing warm pool by 10% during off-peak; tag nodes for scheduled deprovision | If queue_depth rises within 45m after resize, auto-restore previous size | infra-ops | Off-peak schedule: 02:00–06:00 local region time |

Spot volatility table (for reference)
- Low volatility: reclaim_events < 1/hour -> spot_ratio up to 60%
- Medium volatility: reclaim_events 1–3/hour -> spot_ratio up to 40%
- High volatility: reclaim_events > 3/hour -> spot_ratio <= 20% (prefer on-demand)

Automation patterns and IaC examples
- capacity-allocator module parameters (example values):

# terraform snippet (conceptual)
module "gpu_warm_pool" {
  source = "git::ssh://git@repo/redwood/terraform//modules/gpu_warm_pool"

  spot_ratio = 0.4
  node_image = "redwood-gpu-runtime-2025-01-01"

Safeguards implemented in the controller
- Plan preview required: All capacity changes must generate a Terraform plan and pass the plan-guard check (cost delta < configured threshold) before apply.
- Canary applies: Any change > 10% of pool size must be applied to a canary tenant subset for 30 minutes and evaluated for latency regressions.
- Emergency drain protection: If an operation would take more than X% of ready nodes offline, operator must acknowledge in runbook and notify oncall channel #infra-alerts.

Runbook: responding to warm-pool-induced latency spikes
1) Verify alert: check grafana dashboard 'gpu/warmpool/overview' and the 'request_concurrency' and 'node_cold_start_seconds' timeseries.
2) If queue_depth_per_gpu > 0.8: scale warm-pool +15% through capacity-allocator UI (or run 'redwoodctl warm-pool scale --name <pool> --delta +15%').
3) Monitor P95 latency for 15 minutes. If no improvement and error-rate > baseline, revert scale and open incident.
4) If spot reclaim events are high: toggle spot_ratio to on-demand fraction using the terraform var file and apply via canary (example: 'terraform apply -var-file=canary.tfvars').
5) If cold-starts are abnormally long: trigger node reimage job: 'kubectl apply -f /manifests/warmpool-reimage-job.yaml' and monitor node_cold_start_seconds.

Checklist before changing warm pool sizing
- Run 'capacity-allocator plan --region <r>' and confirm the plan shows expected node types, counts, and spot ratio.
- Validate canary tenant traffic shape mirrors production peak (use 'traffic-synth' profile).
- Notify #infra-change two hours prior unless emergency.

Telemetry and dashboards to monitor
- gpu/warmpool/ready_fraction (target >= 0.995)
- gpu/warmpool/queue_depth_per_gpu (alert if > 0.8)
- gpu/node_cold_start_seconds (track median and P95)
- cost/warmpool/daily (per-region cost attribution)
- infra/events/spot_reclaim_count

Ownership and escalation
- Primary owner: infra-sre (team: infra-sre) — responsible for alerting, runbooks, and canary verification.
- Platform-ops: owns warm-pool-controller code and IaC modules.
- Infra-finops: monitors cost signals and approves shifts in spot/on-demand mix.
- Oncall escalation: pages @infra-sre-primary -> infra-sre-rotation -> eng-lead if unresolved for 45 minutes.
