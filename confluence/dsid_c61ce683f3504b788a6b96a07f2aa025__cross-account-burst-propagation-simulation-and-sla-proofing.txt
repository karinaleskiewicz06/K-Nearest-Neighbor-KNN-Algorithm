Cross-account burst propagation simulation and SLA proofing

Summary
-------
This doc describes a reproducible simulation harness, Terraform guardrails, monitoring queries, and an operational runbook to prove that cross-account burst traffic (e.g., tenant GPU evals, CI bursts, or third‑party peering) cannot violate region-level SLOs or egress budget SLAs. It focuses on: quota shaping at NAT/egress proxies, per-account queuing, and emergency throttles.

Goals
-----
- Provide a repeatable simulation to measure how bursts from one account affect other tenants and region-level latency SLOs.
- Define Terraform/IaC module interfaces to attach quotas, shaping policies, and emergency circuit-breakers to shared NAT/egress gateways.
- Produce concrete alerting, dashboards, and a step-by-step incident playbook for oncall.
- Validate billing allocation signals and automated throttling strategies before rollout.

Background and motivation
-------------------------
We run multi-tenant GPU workloads behind shared egress (NAT) and border proxies. Historical incidents showed short, high-volume bursts from a single customer or CI job can cause queueing at the egress path and increase tail latency for model-serving traffic in the same region. Without proven controls, we cannot confidently commit to region-level latency SLOs for Dedicated customers.

Key definitions
- Burst: short - from seconds to a few minutes - spike in outbound egress or connection counts originating from a single cloud account or peered partner.
- Region-level latency SLO: 99th-percentile token-latency for inference <= configured ms per model class.
- Egress budget: daily/weekly bytes/requests budget assigned to account/tenant for non-interactive workloads.

Simulation design and components
-------------------------------
We built a harness composed of three pieces: a traffic generator (k8s Job), an egress shaping layer (tc/netem or Envoy filter), and a telemetry collector (Prometheus + traces). The harness is parameterized by: target account id, burst qps, connection churn rate, duration, packet sizes.

1) Traffic generator
- k8s Job YAML (example snippet):

apiVersion: batch/v1
kind: Job
metadata:
  name: cross-account-burst-generator
spec:
  template:
    spec:
      containers:
      - name: generator
        image: ghcr.io/redwood-inference/burst-generator:stable
        args: ["--target", "http://egress-proxy.region.local:8080/ping", "--rps", "1000", "--conn-rate", "50", "--duration", "60"]
      restartPolicy: Never

This job supports per-tenant headers (X-Account-ID) to simulate multiple account identities. We sweep: rps = [100, 1000, 5000], conn-rate = [10, 50, 200], duration = [30s, 3m, 15m].

2) Egress shaping and policy enforcement
- Two enforcement modes: kernel-level (tc) on NAT instances and edge-proxy (Envoy) rate/queue limits. Both paths implement: token-bucket per-account, queue depth caps, and circuit-breaker that transitions to 'strict-throttle' when global queue depth > threshold.
- tc example (on NAT host):

# limit account X to 100Mbps using tc and iptables mark
iptables -t mangle -A POSTROUTING -m comment --comment "acct-123" -j MARK --set-mark 123
TC_ROOT_DEV=eth0
tc qdisc add dev ${TC_ROOT_DEV} root handle 1: htb default 30
tc class add dev ${TC_ROOT_DEV} parent 1: classid 1:123 htb rate 100mbit ceil 100mbit

3) Terraform module pattern
- Provide a composable module that: creates per-account egress policy objects, attaches them to shared NATs, and wires up CloudWatch/Prom metrics + IAM roles. Interface (inputs/outputs):

Required inputs:
- account_id (string)
- region (string)
- egress_bytes_per_day (number)
- max_conn_per_min (number)
- nat_instance_id (string)
- emergency_throttle_policy (bool)

Outputs:
- policy_id
- prometheus_scrape_target

Design notes:
- Module uses provider aliasing for cross-account resources and IAM role assumption.
- Policies are versioned with a semantic version tag and a migration plan for existing accounts.

4) Validation matrix and acceptance criteria
Run the simulation with the matrix below and assert the following acceptance criteria:
- No increase >20% on region 99th token-latency for production model-serving routes when a 5-minute 5Gb burst occurs in a single tenant.
- Egress bytes charged to the bursting account within 2 minutes of end-of-burst (billing alignment).
- Emergency throttle triggers within 60s if NAT queue depth > 80% capacity.

Simulation sweep matrix (sample):
| scenario | burst rps | duration | conn-churn | expected outcome |
|---------|----------:|--------:|-----------:|-----------------:|
| small-burst | 500 | 60s | 20/s | no SLO impact |
| ci-large | 5,000 | 300s | 200/s | emergency throttle engages |
| peering-spike | 2,500 | 120s | 100/s | isolated impact to owner account |

Monitoring, dashboards, and Prometheus queries
------------------------------------------------
Dashboard recommendations:
- Per-account egress QPS, bytes/day, connection rate
- NAT instance queue depth and avg dequeue latency
- 99th-token-latency split by tenant tag
- Throttle count and circuit-breaker state timeline

Critical queries (PromQL):
- NAT queue depth (host):
  sum(nat_queue_depth_bytes) by (nat_instance)
- Per-account egress bytes in last 5m:
  increase(egress_bytes_total{account_id=~"$account"}[5m])
- Emergency throttle rate (counts per minute):
  increase(egress_throttle_events_total[1m])
- 99th token latency by tenant (derived histogram):
  histogram_quantile(0.99, sum(rate(token_latency_bucket[5m])) by (le, tenant))

Alerting and thresholds
----------------------
Create PagerDuty alerts for: 
- region_slo_violations: fires when 99th-token-latency > threshold for 2 consecutive 1m windows AND detected spikes in nat_queue_depth. Severity: P1.
- emerg_throttle_engaged: fires when emergency_throttle_events_total increases by >10 in 1m. Severity: P2.
- billing_mismatch: fires when egress_bytes are consumed but not attributed to any account for >5m. Severity: P2.

Incident runbook: step-by-step
-----------------------------
1) Triage (0-3 minutes)
- PagerDuty P1 fires. Slack #infra-alerts auto-join. Identify affected region and NAT instance using dashboard.
- Run: kubectl -n infra exec -it controlbox -- /bin/sh -c '\n  curl -s http://prometheus.region.local/api/v1/query?query=sum(nat_queue_depth_bytes)%20by%20(nat_instance)'
2) Contain (3-8 minutes)
- If emergency_throttle is not active, flip the emergency_throttle_policy for the account via the Terraform module hotpath: apply the module with emergency_throttle_policy=true for offending account_id.
- Command sample (ctl tool): redwood-iac apply --module egress-policy --var account_id=123 --var emergency_throttle_policy=true
3) Mitigate (8-20 minutes)
- On NAT host: temporarily lower per-account token-bucket ceilings:
  tc class change dev eth0 parent 1: classid 1:123 htb rate 10mbit ceil 10mbit
- If traffic is from a peered partner, trigger partner circuit-breaker: remove route in peering table and notify partner SRE.
4) Restore and post-incident (20m+)
- Re-run simulation with controlled parameters to validate recovery and confirm no residual tail impact.
- Open a postmortem with: root cause, timeline, changes made, and a rollout plan for turning the per-account limit from soft -> enforced.

Terraform CI/CD and rollout plan
-------------------------------
- All module changes must go through the egress-policy CI pipeline. Pipeline steps: unit terraform fmt + validate -> terratest integration using the harness -> manual approval for production apply.
- Canary strategy: apply policy to a staging NAT (non-prod) and run a targeted 15m simulation. If results meet acceptance criteria, promote module version and schedule rolling apply with 5-minute windows between NATs.
- Migration path: default policies start permissive. We introduce the emergency_throttle flag off by default and flip on for high-risk accounts after validation.
