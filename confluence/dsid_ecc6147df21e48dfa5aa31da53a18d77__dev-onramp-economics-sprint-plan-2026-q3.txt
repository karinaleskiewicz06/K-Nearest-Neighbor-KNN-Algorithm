Developer Onramp Economics: Experiment & Sprint Plan

This document defines a 10-week experiment and sprint roadmap to optimize developer onramp economics: reducing time-to-first-success while minimizing early-stage token spend and supporting self-serve conversion. It covers hypotheses, experimental variants, metric definitions, rollout playbook, ownership and gating criteria for wider productization.
Developer onboarding (trial + first 30 days) drives product-led growth but accounts for large variance in hosted token spend and trial-to-paid conversion. Current telemetry shows 35% of new orgs exhaust free credits within week 1 with a 6% conversion rate. We need controlled experiments to lower cost-per-conversion without hurting activation.
Reduce median cost-to-first-success (CTFS) by 30% for new orgs within 90 days
Increase trial-to-paid conversion by 25% for orgs that hit CTFS improvements
Maintain 99th-percentile latency SLOs for onboarding paths
Produce a repeatable playbook and SDK defaults for self-serve onramp
Self-serve developer flows only (exclude sales-assisted enterprise onboarding)
Hosted inference and sandbox dev environments
Billing / credit mechanics and console UX changes for experiments
Not in scope: Dedicated or Private deployment pricing changes

Cost-to-first-success (CTFS): median and 90th percentile token spend per org
Activation rate: % of orgs making a successful API call sequence defined by activation playbook
Trial-to-paid conversion within 30 days
Average token consumption per active developer (week 1)
Adverse signal: complaint rate, support contacts per 100 orgs
1) Hypotheses: a) Bundled starter credits with guided quickstart lowers CTFS; b) Adaptive prompts + smaller default max_tokens reduces early token spend with negligible effect on activation quality. 2) Variants (A/B/C):

| Variant | Free credits | Default max_tokens | Quickstart flow | SDK defaults |
|---|---:|---:|---|---|
| Control | 1000 tokens | 1024 | Current guided flow | current defaults |
| Variant A | 1500 tokens + 1-time starter bundle | 1024 | Quickstart with sample templates | same |
| Variant B | 1000 tokens | 512 | Current quickstart + adaptive prompt templates | SDK sets max_tokens=512 for first 3 calls |
| Variant C | 1200 tokens + starter bundle | 512 | Quickstart + inline cost estimator | SDK sets soft cap and telemetry hooks |

3) Instrumentation: events (trial_start, first_success, token_spend_session, activation_sequence), cohort tagging, and billing delta. 4) Analysis plan: intention-to-treat and per-protocol analysis; use Bayesian sequential testing with preregistered thresholds (posterior probability > 0.95 for CTFS reduction).
Pre-launch: QA and privacy review; verify telemetry and billing ledger mappings
Week 0: Deploy feature-flagged variants to new orgs (5% traffic)
Monitor daily: CTFS, activation rate, error rate, latency SLOs, support contacts
If negative safety signals (defined below) appear, immediately pause variant and route to control
Week 3: interim analysis; if top-line CTFS improvement and no safety signals, scale to 30%
Document lessons and update SDK defaults for productization if greenlit

Risk: Increased early spend without conversion improvement — mitigation: staged exposure and budget caps; abort criteria: no CTFS improvement by week 3
Risk: Billing disputes from starter bundles — mitigation: clear UX language and receipts; legal & finance sign-off pre-launch
Risk: Latency regressions due to new SDK telemetry — mitigation: performance baseline tests and rollout to canary clusters first
Risk: Developer confusion from changed defaults — mitigation: in-path messaging, 'learn more' links and optional opt-out
Pass if: median CTFS reduced >=30% with posterior probability >=0.95 AND trial-to-paid conversion improved or neutral
Fail if: support contacts per 100 orgs increases by >50% OR 95th-percentile latency increases by >20%
Neutral/iterate if: CTFS improves but conversion declines; run follow-up qualitative interviews and targeted UX experiments
