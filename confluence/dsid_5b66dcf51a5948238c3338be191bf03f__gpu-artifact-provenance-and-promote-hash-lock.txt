GPU artifact provenance and promote hash-lock

Operational runbook and design for ensuring GPU model/runtime artifact provenance, deterministic promotion between CI lanes, and a hash-lock promotion gate to prevent accidental or malicious artifact swaps.
Overview:
This document defines the provenance and promotion controls we use for GPU-facing artifacts (model weights, quantized kernels, runtime bundles, and OCI images) and the hash-lock promotion gate implemented in CI/CD. It combines security-minded signing, deterministic metadata, and a lightweight lockfile mechanism to ensure promotes are auditable and atomic across regions and accounts.

Goals:
- Prevent accidental / silent replacement of artifacts during promotion.
- Make artifact lineage auditable end-to-end (source commit, build inputs, build env, checksum, signer).
- Keep CI promotion fast and automatable while providing a human-reviewable checkpoint for high-risk changes.
- Integrate with existing Terraform/IaC and image registries used by the GPU fleet.

Scope and definitions:
- Artifact: any deployable binary used by the runtime or evals pipeline: OCI image, tarball with kernels, .pt/.bin model weights, quantization tables, or signed kernel blobs.
- Provenance record: JSON document containing build inputs (git sha, module versions, TF vars), environment hash (BUILD_IMAGE, toolchain versions), artifact checksum (sha256), and signer identity.
- Promote: moving an artifact from a lower lane (e.g., canary, staging) to a higher lane (prod/dedicated).
- Hash-lock: a small lockfile checked into the promotion branch that records the expected artifact checksum; the gate requires the artifact checksum to match before the promotion pipeline allows the move.

High-level flow (summary):
1. Build: CI job produces artifact + provenance.json (signed by build-service key).
2. Upload: artifact pushed to registry (OCI or S3) under a lane-specific path with immutable tags (sha256).
3. Lock generation: build job writes a lockfile (artifact-name:sha256) and files it as a PR against the promote branch.
4. Review & sign-off: reviewers verify the provenance and approve the PR.
5. Promote job: verifies lockfile checksum matches registry artifact and that the provenance signature validates; if OK, updates infra promotion state (Terraform var, image tag alias) via a controlled apply.

Detailed components:
- Build-service (buildkite/github-actions): runs hermetic builds using the pinned runner image: ghcr.io/redwood/build-runner:v2025-03-01. Generates: artifact.tar.gz, provenance.json, artifact.sha256, provenance.json.sig.
- Registry patterns:
  - OCI images: us-east1.gcr.io/rw/gpu-images/<lane>/<artifact>:sha256-<short>
  - S3 bundles: s3://rw-gpu-artifacts/<lane>/<artifact>/sha256-<long>.tar.gz
- Provenance schema (example; actual file attached in repo as schema/provenance-v1.json):
  {
    "version": "1",
    "artifact_name": "kernels-nightly-quantized-v2",
    "git_sha": "abcd1234",
    "build_image": "ghcr.io/redwood/build-runner:v2025-03-01",
    "toolchain": {"bazel": "6.2.0", "python": "3.11.2"},
    "build_args": ["--strip-debug","--enable-quant"],
    "artifact_sha256": "<sha256-hex>",
    "timestamp": "2025-11-03T17:02:00Z",
    "signed_by": "build-service@redwood-infra"
  }
(We require the provenance.json to be produced by a single build step to avoid piecemeal assembly.)

Hash-lock promotion pattern (implementation details):
- Lockfile format (PROMOTE_LOCKS/locks.yaml):
  - artifact: kernels-nightly-quantized-v2
  - lane_from: staging
  - lane_to: prod
  - artifact_sha256: 012345abcdef...
  - provenance_path: s3://rw-gpu-artifacts/staging/kernels-nightly-quantized-v2/provenance-v1/012345.json
  - requested_by: dev-queue
  - approvals: []
- Lock lifecycle:
  1) Build job opens PR to promote branch with locks.yaml entry for the artifact. PR title must start with [promote-lock].
  2) At least one reviewer from the gpu-fleet or infra-cd team must approve PR if lane_to == prod or dedicated (policy).
  3) CI promotion job runs on merge: it resolves the lock entry, downloads the artifact from registry, computes sha256, verifies equals artifact_sha256 in lockfile.
  4) It then fetches provenance.json and verifies signature using our internal KMS-backed signing key (see crypto section).
  5) If checks pass, promotion job updates Terraform varstore (terraform workspace:gpu-prod) with the new immutable image reference (sha256) and triggers a targeted apply via the promotion pipeline.

Operator checklist (fast path):
1) Build completed and PR opened (check PR body: provenance link, build logs).
2) Reviewer verifies provenance.json: confirm git_sha, toolchain, and no unexpected external downloads.
3) Approve PR.
4) After merge, monitor promotion job in buildkite: job steps: verify-sha -> verify-signature -> terraform-apply -> rollout-watcher.
5) After apply, confirm Canary metrics (latency P95, error rate) for 30 minutes before wide rollout.

Rollback procedure (if mismatch or regression):
1) If promotion job fails hash-check: do not apply. Revert the lock PR and re-run build.
2) If rollout causes regressions: trigger terraform rollback by applying the previous known-good sha256 alias in the varstore (we keep last-3 releases in promotion metadata).
3) Incident process: open an infra-incident, attach provenance, and run the regression-triage checklist.

Terraform and IaC interactions:
- Promotion job writes to a single Terraform variable file (sequestered in the promotion account): tfvars/promotion-lane-prod.auto.tfvars.json containing {"gpu_service_image": "us-east1.gcr.io/rw/gpu-images/prod/<artifact>@sha256:<long>"}.
- We avoid direct NV to live manifests; promotion applies are gated by the CI operator and auditable via buildkite artifacts.
- Recommended module pattern: module "gpu_service" { source = "git::ssh://git@github.com/redwood/terraform-modules.git//gpu-service?ref=v1.4.2"; image = var.gpu_service_image }

Signing and key custody:
- Build machines hold a short-lived signing token issued by the HSM/KMS service (key rotation every 30 days).
- provenance.json.sig is an RFC5652/CMS-style signature with the signer identity embedded.
- Verification uses the public key bundle pinned in the promotion job (fetched from internal secrets store).

CI/CD snippets (Buildkite/GHA simplified):
- Build step (bash):
  set -euo pipefail
  bazel build //gpu/kernels:release --config=quant
  tar czf artifact.tar.gz bazel-bin/gpu/kernels/release
  sha256sum artifact.tar.gz > artifact.sha256
  ./sign-provenance.sh provenance.json > provenance.json.sig
  aws s3 cp artifact.tar.gz s3://rw-gpu-artifacts/staging/kernels-nightly-quantized-v2/sha256-$(cat artifact.sha256 | cut -d' ' -f1).tar.gz
  gh pr create --title "[promote-lock] promote kernels-nightly-quantized-v2" --body "provenance: ${PROVENANCE_URL}" --base promote/locks
- Promote step (outline):
  - download locks.yaml from merged branch
  - for each lock: curl registry -> compute sha256 -> compare -> verify provenance sig via kms verify -> if ok write tfvars and run terraform apply

Monitoring and observability:
- Telemetry points to emit:
  - build.provenance.generated (counter)
  - promote.hashcheck.success/failure (counter)
  - promote.provenance.verify.duration (histogram)
  - promotion.terraform.apply.duration (histogram)
- Dashboards: GPU infra > Promotions: last 30d promotions, failures by cause, time-to-promote percentiles.

Security considerations and threat model:
- Threat: Malicious actor swaps an image tag in registry after PR approval. Mitigation: strict use of immutable sha256 references and lockfile checks.
- Threat: Compromised build runner. Mitigation: ephemeral build credentials, signer key guarded by KMS with usage policy, and human reviewer check before prod promotes.
- Threat: Man-in-the-middle between registry and promotion job. Mitigation: HTTPS + registry auth, compute and compare checksums locally.

Operational guidance and SLOs for promotion pipeline:
- Availability: promotion pipeline should succeed (or fail noisily) within 10 minutes for staged artifacts (SLO: 99.5%).
- Security: every prod promotion must have at least one reviewer approval and a provenance signature.
- Audit: provenance + lockfile + pipeline logs must be retained for 1 year (compliance).

Open questions and future work:
- Extend proof-of-build reproducibility (rebuild-from-source) to close the reproducibility loop for kernels.
- Integrate sigstore/cosign for wider community tooling compatibility.
- Automatic heuristics to detect suspicious provenance attributes (e.g., unusual toolchain versions) and require additional reviewers.

Appendices:
- Example provenance verification CLI:
  rw-infra verify-provenance --provenance s3://.../provenance.json --sig s3://.../provenance.json.sig --pubkeys /secrets/publishers.pub
- Back-of-envelope timing: full build + upload + PR creation = ~12-18 minutes on standard runners; promote verify + terraform apply (canary only) = 4-8 minutes.
