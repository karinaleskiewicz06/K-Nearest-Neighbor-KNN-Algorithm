Public release notes generation playbook (docs-site)

## Purpose
This playbook describes how the public docs site consumes *generated* model release notes (from the model registry + changelog generator), how routing/URLs are computed, and how to handle:
- Embargoed changes (planned publish time or “do not publish yet”)
- Customer-specific changes (account-scoped, not globally relevant)
- Redaction and “public vs internal” field separation

This document is written for:
- DevEx/Docs maintainers of the docs build
- Release Engineering
- Model Catalog and Console teams (when debugging missing/incorrect public notes)

## Definitions
- **Release note artifact**: A machine-generated document (JSON) produced by the changelog generator for a model version promotion, deprecation, or other publishable change.
- **Public release notes**: Customer-visible notes rendered on the public docs site and exposed via feeds.
- **Console change history**: The Console’s per-model/per-account change history view. It may show additional internal or account-scoped information depending on RBAC.
- **Embargo**: A note that exists in the system but must not be published on the public docs site until a specified time or until explicitly un-embargoed.

## High-level architecture
### Source of truth
1) Model/version metadata is stored in the **model registry/control plane** using *Model Metadata Schema v1*.
2) Changes emit structured events (e.g., model metadata changed, model version promoted, model deprecated).
3) The **changelog generator** consumes events + metadata and writes release note artifacts to an internal artifact store.
4) The **docs build** pulls the public-safe artifacts and renders:
   - Versioned release note pages
   - Index pages (by date / by model)
   - Machine-readable feeds (RSS and JSON feed)

### Public vs internal separation (non-negotiable)
The docs build must only consume artifacts that are explicitly marked public-safe by the generator.
- The generator is responsible for applying redaction rules and producing a *public projection*.
- The docs build must additionally enforce a “deny by default” filter:
  - If an artifact is missing an explicit `visibility=public` marker (or equivalent), treat it as NOT publishable.

## Artifact contract (docs consumer expectations)
The exact schema is owned by the changelog generator team; the docs build treats it as an API.

Docs-site expects each artifact to provide the following fields (names may differ in the implementation; this is the contract by meaning):
- Unique identifier (stable)
- Model identifier and display name
- Model version (semver) and variant/profile identifiers (e.g., quantization profile)
- Publishable categories (security, breaking, perf, quality, bugfix, deprecation)
- Severity level and customer-facing summary
- Public-safe “what changed / why it matters / what to do” sections
- Timestamps:
  - `event_time` (when the change happened)
  - `publish_at` (optional; used for embargo scheduling)
- Visibility and audience controls:
  - `visibility`: public | internal | restricted
  - `audiences`: global | hosted | dedicated | private (and/or other supported deployment scopes)
- Links:
  - Docs links to migration guides / deprecation policy
  - Console deep link (optional)

### Hard requirements for publishability
A release note artifact is eligible for public docs only when:
1) `visibility` is public
2) `audiences` includes `global` (or includes at least one public deployment scope that maps to public docs pages)
3) `publish_at` is either absent or is <= build time
4) It passes the docs-site validator (see “Build-time validation”)

## Docs build integration
### Where the docs build pulls artifacts from
The docs build runs in CI for the `redwood-docs` repository and fetches release note artifacts during the build.
- The fetch step must use a read-only credential with minimal scope.
- The fetch step must request **public artifacts only** (server-side filtering) and still apply client-side filtering.

Operational note: if server-side filtering is not available for a given environment, the docs build must fail closed (do not publish) rather than attempt to infer “public-ness” from content.

### Recommended artifact layout in the docs build workspace
During build, store fetched artifacts under a predictable path:
- `./.cache/generated-release-notes/` (not committed)
- Subfolders optional, but keep the raw files for debugging build failures.

### Build-time validation (docs-site)
In addition to registry/generator validation, the docs build enforces:
- Required field presence for rendering (title, date, model id, version, category, summary)
- Markdown safety checks (no raw HTML if the docs renderer disallows it)
- Link validation (only allowed domains or relative docs paths)
- No internal tokens/IDs in public content:
  - Block patterns like internal Jira keys if they are not explicitly allowed
  - Block “internal-only” markers

If validation fails:
- The build must fail and produce a clear error referencing the artifact ID and missing/invalid fields.
- If the failure is caused by a single artifact and policy allows partial publication, the build may skip that artifact only if an explicit “skip invalid artifact” flag is enabled for that build. Default behavior is fail the build.

## Routing and URL rules
### Canonical public URL patterns
Public release notes are rendered under a stable information architecture.

**1) Release notes index**
- `/release-notes/models/`
  - Lists recent model changes across all models
  - Supports filtering client-side (model, category, deployment)

**2) Per-model release notes index**
- `/release-notes/models/{model-slug}/`
  - Lists notes for a single model

**3) Individual note pages (recommended canonical)**
- `/release-notes/models/{model-slug}/{version}/`
  - Example: `/release-notes/models/redwood-chat-3/3.2.1/`

**4) Optional: Date-based view (if supported)**
- `/release-notes/models/2025/11/`

### Slug rules
- Use a stable `model_slug` provided by the model registry (preferred).
- If not available, derive a slug from the public display name:
  - lowercase
  - replace spaces/underscores with hyphens
  - collapse multiple hyphens
  - remove non-alphanumeric characters except hyphen
- Slugs must be stable. If the display name changes, do not change the slug unless a redirect is added.

### Redirects
If a model slug changes (rare; should require approval):
- Add a permanent redirect from the old slug path to the new path.
- Keep redirects for at least 12 months.

## Feeds (RSS/JSON)
The docs site publishes machine-readable feeds for customers and internal tooling.

### RSS feed
- `/release-notes/models/rss.xml`
Includes:
- title
- publish date
- link to canonical page
- short summary

### JSON feed
- `/release-notes/models/feed.json`
Includes a normalized subset of the public artifact fields.

Feed rules:
- Only include `visibility=public` and `publish_at <= now`.
- Never include account identifiers, internal URLs, or internal-only fields.

## Handling embargoed changes
### Why embargo exists
Embargo is used for:
- Coordinated disclosures (security)
- Launch coordination (blog, partner announcement)
- Rollout sequencing where a note should only appear once a change is generally available

### How embargo is represented
Embargo is indicated via `publish_at` (time-based) and/or an explicit `embargoed=true` marker in the artifact.

Docs build behavior:
- If `publish_at` is in the future: do not render the note.
- If `embargoed=true` with no `publish_at`: do not render the note.
- Do not “placeholder” embargoed notes in public indexes.

### Operational guidance for embargoed security notes
Security-related notes require extra caution:
- Ensure the public summary does not expose exploit details.
- Prefer language like “Addressed an issue that could impact reliability or security under certain conditions” unless Security explicitly approves more detail.
- Confirm that the note includes customer action guidance when required (e.g., “Pinned versions are unaffected” or “Upgrade recommended”).

### Debugging: “note missing from public docs”
Common causes:
- `visibility` not public
- `publish_at` still in the future
- artifact failed validation and was excluded
- docs build used cached artifacts

Resolution steps:
1) Confirm the artifact exists in the artifact store for the intended version.
2) Inspect `visibility`, `publish_at`, and category.
3) Check docs build logs for “skipped due to embargo” or validation failures.
4) If the note should be public now, fix at the source (generator/metadata), do not patch the docs page by hand.

## Handling customer-specific changes (do not publish)
### What counts as customer-specific
Examples:
- Account-specific rollout enablement (“enabled for Northbridge only”)
- Customer-specific model routing/fallback policies
- Private deployment bundle contents for a single customer’s offline environment

These must not appear on the public docs site.

### Supported patterns
**Pattern A (preferred): Console-only, account-scoped visibility**
- Artifact includes `audiences=account:{account_id}` (or equivalent) and `visibility=restricted/internal`.
- Console may render it for authorized roles.
- Docs build ignores it.

**Pattern B: Separate public note + internal note**
- Publish a general public note (e.g., “Improved latency in hosted regions”)
- Keep customer-specific operational details internal.

**Pattern C: Private deployment notes are exported with upgrade bundles (not public docs)**
- For Private upgrade bundles, follow the Private export guidance.
- Do not publish bundle-specific notes publicly unless they are truly generally applicable.

### Redaction warning
Do not rely on “removing names” to make an account-scoped note public-safe. Account-specific rollouts can still reveal sensitive procurement, regulated status, or internal timelines.

## Editing, overrides, and “no manual patches” policy
### No manual edits in docs-site for generated notes
Generated release notes must not be manually edited directly in the docs repository except for:
- Styling/layout improvements to the renderer
- Fixes to the docs build pipeline
- Adding general explanatory content (taxonomy, how to interpret release notes)

If a release note’s text is wrong:
- Fix the source metadata and/or generator templates.
- Rebuild artifacts.
- Re-run docs build.

### Allowed override mechanism (break-glass)
If a release note must be temporarily suppressed due to a verified issue (e.g., contains sensitive content):
- Use a denylist file in the docs repo that blocks specific artifact IDs.
- Denylist entries must include:
  - artifact ID
  - reason
  - owner
  - expiration date (required)
- Notify Security & Compliance if suppression was due to sensitive data exposure.

## Release process and approvals
### Normal publish flow
1) Model change is proposed (metadata update or promotion).
2) CI validates schema and produces a release note preview artifact.
3) Reviewers confirm:
   - correct category/severity
   - no internal details
   - links and customer guidance are correct
4) Promotion lands; generator emits the final public artifact.
5) Docs build pulls and publishes on the next successful docs deploy.

### Approval expectations
- Security category notes require Security review when they reference vulnerabilities or mitigations.
- Breaking changes must include explicit “what you need to do” guidance and link to migration/deprecation docs.

## On-call / incident response
### If an internal-only field leaks to public docs
Treat as a docs incident.
1) Immediately disable publishing of generated notes (toggle docs build step off or block artifacts) if required.
2) Use the denylist to suppress the offending artifact(s).
3) Purge CDN cache for the affected pages.
4) File a follow-up ticket to fix the generator redaction rule and add regression tests.

### If public docs publishes an incomplete note
1) Confirm whether the artifact itself was incomplete or rendering failed.
2) If the artifact is incomplete, fix at source and re-generate.
3) If rendering failed, patch renderer and re-deploy docs.

## Appendix A: Rendering guidance
- Keep summaries short and scannable (1–3 sentences).
- Prefer concrete outcomes over implementation details (e.g., “Reduced first-token latency in hosted regions” rather than “Changed batching scheduler”).
- Avoid numeric claims unless supported by quality/performance evidence and approved wording.

## Appendix B: Quick checklist for docs maintainers
Before enabling/rolling out a change to release note rendering:
- [ ] Build fails closed when public markers are missing
- [ ] Embargo logic is enforced (`publish_at` and explicit embargo)
- [ ] Feeds only include public, non-embargoed artifacts
- [ ] Denylist break-glass exists and requires expiration
- [ ] Link validation prevents internal URLs
- [ ] Regression tests cover public/internal separation
