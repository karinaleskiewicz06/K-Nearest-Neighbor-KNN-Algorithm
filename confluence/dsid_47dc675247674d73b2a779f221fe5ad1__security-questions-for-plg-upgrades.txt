Security questions for PLG upgrades (Hosted → Dedicated/Private) — FAQ + escalation guidance

## Purpose
This page is a sales + solutions engineering (SE) friendly security FAQ for self-serve (PLG) accounts that are considering an upgrade to **Redwood Dedicated** or **Redwood Private**.

It is optimized for common “security checklist” questions we see during expansions triggered by scale, reliability, or compliance needs.

**How to use:**
- If you can answer from this page: answer directly and offer to share the Security Overview / SOC 2 report via the approved process.
- If the question hits the **Escalation** section, loop in Security and/or SE early.

---

## Quick positioning (one paragraph you can reuse)
Redwood Inference is built for production inference with enterprise-grade security controls. Customers can start with the Hosted API and upgrade to Dedicated or Private for stronger isolation, network controls, data residency requirements, and compliance needs. Across all deployment modes we support access controls, auditability, encryption in transit and at rest, and clear retention policies—with additional controls (VPC/private networking, BYOK/KMS integration, and enhanced logging) available for Dedicated/Private.

---

## Definitions (use in conversations)
**Hosted API:** Multi-tenant control plane and multi-tenant compute (logical isolation). Best for fastest onboarding.

**Dedicated:** Dedicated GPU pools for a customer (data isolation + predictable throughput). Control plane is Redwood-managed; compute is customer-dedicated.

**Private:** Customer-specific deployment with customer-managed networking (VPC) and optional on-prem/air-gapped packaging for regulated workloads.

## FAQ (common security questions)

### 1) Do you have SOC 2 / security compliance?
**Answer:** Yes. Redwood maintains a security program with SOC 2 (Type II) coverage for the production platform. We can share the report and supporting artifacts under NDA via the approved evidence process.

**Good follow-up questions to ask:**
- “Do you need SOC 2 for vendor onboarding, or do you also need specific controls (e.g., SSO, audit logs, data residency, retention)?”
- “Is this for a regulated environment (HIPAA/BAA, PCI, financial services)?”

**Escalate when:** customer requests BAA, on-prem, air-gapped, or has regulator-specific requirements (see Escalation).

---

### 2) Is customer data used to train models?
**Answer:** By default, Redwood does not use customer prompts/inputs/outputs to train foundation models.

**Clarify:** Customers are responsible for what they send in; Redwood is the inference provider/runtime. We support data minimization and retention controls, and we can support additional contractual language via Legal for enterprise deals.

**Escalate when:** customer requests custom contractual terms around model training, data processing restrictions, or audit rights.

---

### 3) Encryption in transit and at rest
**Answer:**
- **In transit:** TLS is required for API traffic.
- **At rest:** Data stored in Redwood-managed systems is encrypted at rest.

**Dedicated/Private add-ons:** Customer-managed key options and tighter network boundaries are available depending on deployment.

**Escalate when:** customer requires specific cipher suites, mTLS end-to-end, or “customer-managed keys only” (BYOK) as a hard requirement.

---

### 4) Can we bring our own key (KMS / BYOK)?
**Answer:** In **Private** deployments (and some Dedicated configurations), Redwood can integrate with customer key management requirements (e.g., cloud KMS/HSM patterns) for encryption key control and rotation expectations.

**What you can safely say:**
- We support KMS-based key management patterns for regulated workloads.
- Key rotation and access controls are part of the enterprise security setup.

**What not to promise:** exact architecture (envelope encryption details, key custody model) without Security review.

**Escalate when:** customer requires BYOK, HSM-only, or strict separation-of-duties for key administration.

---

### 5) Audit logs (who did what, when?)
**Answer:** Redwood provides auditability features appropriate for production usage:
- Access and operational events are logged for platform security and troubleshooting.
- For **Dedicated/Private**, audit log requirements (admin actions, key events, access changes) can be configured to meet enterprise needs, including export/integration patterns.

**Examples customers ask for:**
- “User X created/rotated an API key”
- “Role changes / permission updates”
- “SSO configuration updates”
- “Model version pin/rollout changes”

**Escalate when:** customer requires immutable audit logs, SIEM integration (e.g., Splunk) with specific schemas, or regulatory audit evidence timelines.

---

### 6) Data retention controls (inputs/outputs/logs)
**Answer (high-level):** Redwood supports configurable retention aligned to customer needs and product requirements.

**How to frame it:**
- For PLG customers, we retain only what is needed to operate the service, ensure reliability, and support debugging/abuse prevention.
- For Dedicated/Private, we can offer more explicit retention controls and operational logging configurations.

**Common follow-up:** “Can you store nothing?”
- Explain tradeoffs: some minimal operational logging is typically required for security and reliability.

**Escalate when:** customer requests strict retention windows (e.g., <7 days), “no logging,” deletion SLAs, or needs contractual commitments.

---

### 7) Data residency / where is data processed?
**Answer:** Redwood supports regional deployments for customers with residency needs. Dedicated/Private are the typical paths when a customer requires strong assurances on where processing occurs and where operational data is stored.

**Practical guidance:**
- Ask which residency requirement applies: “processing only” vs “storage + processing” vs “support access restrictions.”
- Ask which region(s) they need (e.g., EU/EEA).

**Escalate when:** customer requires EU-only support personnel, specific country-only residency, or contractually binding residency language.

---

### 8) SSO / SAML / SCIM
**Answer:**
- SSO is available for enterprise plans; **SAML-based SSO** is typically provided for Dedicated/Private (and eligible enterprise Hosted plans where applicable).
- Role-based access controls (RBAC) are used to limit access by role.

**What to collect (so Security/SE can help fast):**
- Identity provider (Okta, Azure AD, Google Workspace, etc.)
- Required attributes/claims and any MFA requirements
- Whether they need SCIM provisioning/deprovisioning

**Escalate when:** SSO is a hard gate for production, SCIM is required, or the customer has complex role mapping requirements.

---

### 9) Network security: VPC, private connectivity, IP allowlists
**Answer:**
- **Private** deployments support customer-managed networking (VPC) and tighter controls suitable for regulated environments.
- Dedicated/Private can support more restrictive inbound/outbound rules and private connectivity patterns.

**Escalate when:** customer asks for private endpoints, VPC peering/PrivateLink-style connectivity, or strict IP allowlist requirements.

---

### 10) Access control: API keys, rotation, least privilege
**Answer:**
- Redwood supports API keys for programmatic access.
- Customers should use least privilege, rotate credentials, and restrict key distribution.
- Dedicated/Private engagements typically include additional guidance and controls (SSO, admin roles, auditability).

**Escalate when:** customer requires per-environment key isolation with policy enforcement, automated key rotation hooks, or advanced permissioning tied to IdP groups.

---

### 11) Vulnerability management and penetration testing
**Answer:** Redwood runs ongoing security practices including vulnerability management and periodic testing. For enterprise deals, we can share summaries and attestations through the approved evidence process.

**Escalate when:** customer requests to run their own pen test against production endpoints, needs a specific remediation SLA, or requires a formal security exception process.

---

### 12) Incident response and breach notification
**Answer:** Redwood has incident response processes and customer communications procedures appropriate for enterprise workloads. Contractual notification terms are handled in the MSA/DPA.

**Escalate when:** customer requests specific breach notification windows, custom IR coordination, or audit rights.

---

### 13) Do you support HIPAA / BAA?
**Answer:** This depends on deployment mode and contractual scope. Private deployments are typically the starting point for HIPAA-aligned requirements.

**Escalate immediately:** any HIPAA/BAA request should go to Security + Legal + SE.

## “When to loop in Security / SE” (fast checklist)
Loop in **Solutions Engineering (SE)** when:
- They mention Dedicated/Private architecture questions (VPC, throughput + isolation tradeoffs).
- They have performance + reliability constraints tied to security controls (e.g., private connectivity, residency).
- They want a written security response tailored to their environment.

Loop in **Security (and often Legal)** when:
- Any regulated framework is a hard gate: HIPAA/BAA, PCI, FedRAMP, ITAR, SOX-driven vendor rules.
- They require BYOK/HSM, strict retention/deletion SLAs, or “no logging.”
- They require contract language for residency, breach notifications, or audit rights.
- They request the SOC 2 report, security policy packets, or ask to complete a detailed security questionnaire.

Loop in **both Security + SE** when:
- The deal requires Private deployment, air-gapped, on-prem, or advanced network isolation.
- The customer requests SIEM export, immutable audit logs, or custom logging schemas.

## Talk track: discovery questions that prevent back-and-forth
Use 2–4 of these early:
- “What’s the gating requirement—SSO, residency, retention, audit logs, or vendor compliance (SOC 2)?”
- “Are you in production already, or is this for a pilot?”
- “Is the concern about where data is processed, where it’s stored, or who can access it?”
- “Do you need a Private/VPC deployment, or would Dedicated meet your isolation needs?”

---

## Guardrails (do/don’t)
**Do:**
- Anchor answers to deployment mode: Hosted vs Dedicated vs Private.
- Offer an SE + Security review call when requirements are specific.
- Capture requirements precisely (IdP, region, retention window, audit log needs).

**Don’t:**
- Promise BYOK/HSM specifics, “zero retention,” or exact residency commitments without Security review.
- Provide detailed internal architecture diagrams or vendor lists in writing without approval.
