GPU IaC validation and shard simulation harness

Overview

Purpose: This page documents the GPU IaC validation harness we run in CI to prevent regressions and capacity surprises when changing Terraform modules, account sharding, VPC egress rules, or burst orchestration. The harness synthesizes lightweight simulated fleets, applies proposed Terraform diffs in a sandbox, runs policy & functional checks, and produces an automated risk score for rollouts.

Scope
- Applies to Terraform modules under terraform/modules/gpu-* and terraform/account-templates used for tenant sharding.
- Runs for merge requests that touch: GPU node pools, instance profiles, subnet/egress blocks, burst orchestrator, quota modules, and IAM roles used by the GPU allocator operator.
- Excludes unrelated infra changes (network-only unrelated to GPU egress), but CI job can be manually triggered for broader impact analysis.

Key goals
1) Catch safety violations early: IAM rules granting broad network access, missing resource tags, or breaking quota guardrails.
2) Validate capacity semantics: that new module versions preserve preferred topology (heterogeneous pools, spot fallback), and that warm-pool targets are not reduced below minimums.
3) Simulate cross-account sharding: synthetic workload placement to detect hot shards, egress saturation, or billing spike risk.
4) Emit deterministic promotion criteria for module releases and an automated canary cohort assignment suggestion.

Architecture and components
- CI orchestration: Buildkite pipeline gpu-iac-validate (gpu-iac-validate:preflight -> plan -> sim -> policy -> score).
- Sandbox accounts: two ephemeral AWS accounts per branch (sandbox-a, sandbox-b) provisioned via account-factory; ephemeral resources tagged with branch and CI run id.
- Terraform runner: uses terragrunt wrapper with cached module registry; runs terraform plan/apply against a small-scale replica (2-4 nodes, smaller instance types) to validate provider flows.
- Simulation engine: a Python harness that creates synthetic allocation requests matching histogram of real workloads (taken from last 30 days telemetry), exercises allocator decisions, and measures shard skew and egress pressure.
- Policy engine: Open Policy Agent policies (rego) validating: least-privilege IAM, subnet egress CIDR restrictions, cost tag compliance, and module contract version compatibility.
- Scoring and report: JSON + HTML report uploaded to artifact store and a rollup sent to PR with color-coded score and recommended mitigations.

CI pipeline steps (summary)
1) preflight (quick lint): terraform fmt/checkov/tilt checks; fail fast for formatting and high-severity findings.
2) plan (safe): terraform plan with -out=plan.out. Difference extraction runs through module-contract-checker.
3) sandbox-apply (isolated): apply in sandbox account with tight timeouts; creates synthetic node pools and vault secrets stub.
4) simulation-run: run 12 minute simulation with three workload classes: interactive (p99 latency SLO sensitive), batch eval, and nightly-evals.
5) policy-eval: OPA policies run on planned output and applied state.
6) scoring: combine policy violations, simulation metrics (shard skew, egress util > 70% sustained), and cost-delta estimate into a single score (0-100).
7) artifact publish + PR comment: reports, logs, and triage hints.

Representative CLI snippets
- Run locally against your branch (developer flow):
  # bootstrap ephemeral sandbox account (dev must have sandbox role)
  ./scripts/sandbox-bootstrap --branch feature/FOO --account sandbox-a
  buildkite-agent pipeline upload .buildkite/gpu-iac-validate.yml

- Force a re-run in CI for an existing PR:
  curl -X POST -H "Authorization: Bearer $BK_TOKEN" 
    https://ci.internal.redwood/buildkite/runs/retry?pipeline=gpu-iac-validate&pr=1234

Terraform/terragrunt example (module contract test)
- Example contract assertion in module-contract-checker (pseudocode):
  - required_outputs: ["node_pool_id","min_size","max_size","preemptible"]
  - disallowed_changes: ["tenant_shard_count decrease > 10%","public_egress_cidr remove"]

Simulation metrics and thresholds (defaults)
- shard_skew_ratio (max per-sim): 1.2 (acceptable), >1.5 flagged
- egress_95 (percentile util of egress NAT/gw): 70% acceptable; 70-90% warn; >90% fail
- placement_latency_p99 simulated: must be <= 250ms for interactive class
- cost_delta_estimate: display hourly delta normalized to baseline fleet; >20% increase requires manual review

Policy examples (high-level)
- IAM: no wildcard in iam:PassRole or ec2:RunInstances for non-admin modules.
- Subnets: egress CIDRs must map to approved egress-blocks per account (see /confluence/eng-infra/cloud-accounts-and-networking/approved-egress-blocks.json).
- Tags: resources must include tags {"team","env","billing:owner"}.

Rollout and release guidance for module authors
1) Create a feature branch and open PR with module changes. The validation harness will run automatically.
2) If score > 80 and no critical policy violations, tag the PR for staged promote.
3) Staged promote: create a canary release that updates two non-production accounts and observe production telemetry for 48 hours. Recommended canary cohort: 5% of warm-pool capacity across two regions.
4) Full promote: require two reviewers, green canary telemetry (no p95 CPU spike, egress stable), and cost-delta within threshold.

Oncall and triage playbook (quick)
- If CI fails with policy-violation: tag owner from module manifest and open a blocker label; minor fixes may be pushed as follow-up commits.
- If simulation flags egress saturation: pause promotion and run expanded simulation with real workload replay (runbook link: /confluence/eng-infra/runbooks/cross-region-gpu-failover-simulation-playbook.json).
- If sandbox-apply times out frequently: increase apply timeout in .buildkite/pipelines or mark modules for refactor to reduce external API calls.

Operational ownership
- Maintainers: infra-iac team (primary), gpu-fleet (secondary).
- Alerting: CI pipeline posts to #infra-ci with score < 60 or any critical policy failures. Pager duty: infra-oncall if a release is accidentally promoted with critical violations.

Future improvements (roadmap)
- Integrate model-level evals to ensure new provisioning does not materially impact latency-sensitive LLM evals.
- Add cost-simulated billing estimator per account by replaying token throughput traces.
- Support for on-premise package validation (air-gapped) via local VM-based simulation harness.
