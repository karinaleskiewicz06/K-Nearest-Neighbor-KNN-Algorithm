GPU tenant day0→day2 onboarding, CI/IaC contracts and operational runbook

Summary
This runbook documents the end-to-end tenant onboarding and operational lifecycle for GPU-backed tenants (Day0, Day1, Day2). It unifies CI/CD contracts, Terraform/IaC module expectations, capacity & tagging checks, and incident mitigation playbooks for the GPU fleet. The document is intended for infra engineers, platform SREs, and solutions engineers who operate tenant provisioning and the GPU allocator.

Scope
- Applies to hosted and dedicated GPU capacity delivered through: prod-gpu-account, staging-gpu-account, sandbox-gpu-account.
- Covers Terraform modules: tf-tenant-module, tf-network-zone, tf-warmpool, tf-egress-fence.
- Integrates with CI systems: Buildkite (primary), GitHub Actions (aux), and the build artifact registry.

Ownership and Roles
- Owner: infra-platform (oncall rota: infra-gpu-team)
- Day0 owner (provisioning): tenant-provisioning squad
- Day1 owner (capacity/observability): gpu-capacity squad
- Day2 owner (operational runbook & escalations): platform-sre

Prerequisites and Access
1) Accounts and IAM
  - Ensure tenant account mapping in org: 'tenant-x' -> AWS role arn:aws:iam::987654321098:role/tenant-x-provisioner.
  - Terraform remote state bucket: s3://redwood-tfstate-gpu (KMS key arn:aws:kms:us-east-1:123456789012:key/gpu-iac-key).
2) Secrets
  - Tenant provisioning service account stored in Vault path secret/tenants/provisioner.
  - CI service principal has kms:Decrypt and s3:GetObject for tfstate bucket.
3) Network
  - VPC peering requirement: prod-gpu-account <-> tenant VPC must be present and the egress-sidecar subnet allocated.

Contract: Terraform module expectations (CI/IaC contract)
- tf-tenant-module must expose the following outputs (contract v1):
  - tenant_id (string)
  - mgmt_role_arn (string)
  - warmpool_size (integer)
  - egress_bucket_prefix (string)
- tf-tenant-module must respect the tagging policy: {team, owner, cost-center, project, gpu_tier}. CI will validate tags during plan step.
- Module versioning policy: major versions pinned; only patch/minor auto-promote if integration tests pass.

- Purpose: run IaC plan, module contract verification, and post-plan acceptance gating.

  steps:

Acceptance checks performed by CI (automated)
1) Plan contains expected outputs (tenant_id, warmpool_size)
2) No changes to production security groups unless explicit flag set
3) Tags present for all created resources
4) A smoke deployment to the warmpool (size=1) succeeds in staging

Day0: Provisioning checklist (numbered steps)
1) Create tenant request ticket in internal portal and assign to tenant-provisioning.
2) Validate tenancy: ensure quotas are available in target region (check capacity-index dashboard).
3) Run the CI pipeline: open PR against tf-tenant-module with tenant variables and ci/plan.
4) After CI success, apply must be done by a second approver (2-person rule) in Buildkite.
5) Post-apply verification (in order):
   - terraform output tenant_id returns expected value
   - IAM role mgmt_role_arn is assumable by provisioner (test: aws sts assume-role)
   - Warmpool instance started and connected to gpu-allocator (metric: allocator.healthy_sessions > 0)

Day1: Capacity, tagging, and network checks
- Capacity checks (automated):
  - Metric: gpu.pool_warm_size (expected >= warmpool_size)
  - Metric: gpu.preemption_rate < 2% (alert if > 2% for 10m)
  - Metric: allocator.allocation_latency_p50 < 8s, p95 < 30s
- Tagging checks (policy enforcement): run nightly tag-compliance job which alerts for missing tags.
- Network checks: verify egress-sidecar health and NAT connectivity to object-store endpoints.

Operational SLOs and thresholds
- Allocation latency SLO: 99th percentile allocation latency < 30s (SLO owner: gpu-capacity).
- Warmpool readiness SLO: warmpool healthy instances >= requested warmpool_size 99% of the time.
- Preemptive eviction SLO: eviction-triggered job restarts < 1% per day.
- Alert thresholds:
  - Alert gpu_allocation_latency_high: p95 allocation latency > 60s for 5m -> P1
  - Alert gpu_eviction_surge: eviction_rate > 5% for 5m -> P1
  - Alert warmpool_dry: warmpool_size < requested for 3 continuous minutes -> P2

Day2: Runbook for common incidents (steps and playbook)
1) Symptom: allocations timing out / requests queuing
  1.1) Check allocator logs: kubectl logs -n infra deploy/gpu-allocator. Search for error "no healthy nodes".
  1.2) Check metrics: allocator.allocation_queue_length, allocator.node_healthy_ratio.
  1.3) If node_healthy_ratio < 0.8 -> run warmpool reprovision: scripts/warmpool-reseed --tenant $TENANT --count 2 and notify #infra-gpu-oncall.
  1.4) If preemption spikes -> identify noisy tenant via cost and preempt metrics; throttle via tenant-quotas: tf-tenant-quota apply --tenant $TENANT --cpu_burst=0.
2) Symptom: warmpool fails to attach to allocator
  2.1) Verify IAM role assumptions: aws sts assume-role --role-arn $MGMT_ROLE
  2.2) Re-run cloud-init logs: ssh into warmpool instance and check /var/log/cloud-init-output.log for kernel or container runtime failures
  2.3) If kernel mismatch found (common after golden-image rotation), escalate to ci-cd build-owner and trigger image-rollback per image-rotation policy.
3) Symptom: Egress bucket write errors from tenant workloads
  3.1) Check S3 permissions and KMS decrypt logs in CloudTrail for denied kms:Decrypt events referencing arn:aws:kms:us-east-1:123456789012:key/gpu-iac-key
  3.2) Temporary mitigation: route writes through egress-sidecar with proxy credentials: /ops/egress/egress-proxy-rotate.sh
  3.3) Long-term fix: update tf-tenant-module to grant kms:Decrypt to role mgmt_role_arn and rotate keys according to KMS rotation policy.

Rollback and safe windows
- Any tf-tenant-module change that modifies warmpool size, net gateways, or IAM must have a 30-minute maintenance window and an intended rollback plan.
- Rollback procedure (high level):
  1) Revert Terraform change to the last stable tag in repo (git revert + push).
  2) Trigger the Buildkite apply pipeline with the revert and perform verification steps as in Day0 step 5.
  3) If rollback fails due to state drift, contact infra-iac-owners and open an incident; include state dump and plan output.

Testing and staging guidance
- Staging mirror: Every change must be applied to staging-gpu-account with identical tfstate path prefix before prod.
- Smoke test matrix (automated):
  - Launch 3 warmpool instances and verify allocator responds to 10 synthetic allocation requests within 30s.
  - Run kernel matrix tests from ci/kernel-compat to catch image incompatibilities.

Telemetry, dashboards and run metrics (what to monitor)
- Dashboards: grafana/dashboards/gpu-allocator-overview, grafana/dashboards/warmpool-health, grafana/dashboards/egress-errors.
- Essential metrics (Prometheus): allocator_allocation_latency_seconds, allocator_queue_length, warmpool_count, eviction_rate, preemption_rate, warmpool_boot_failures_total.
- Logs: forward allocator logs to Sentry and stackdriver with tags {tenant, region, pool}.

Automated remediation and safety nets
- Automatic warmpool reseed job: runs when warmpool_count < requested for 2 consecutive minutes. Rate-limited to 2 reseeds per 10 minutes.
- Circuit breaker: If allocator_queue_length > 200 for >10m, the burst-orchestrator disables new noncritical tenant allocations and falls back to pre-warmed shared-pool.

Runbook appendices (snippets and commands)
- Verify IAM role assumption:
  aws sts assume-role --role-arn $MGMT_ROLE --role-session-name sanity-check
- Check allocator health (Kubernetes):

- Trigger warmpool reseed (manual):
  scripts/warmpool-reseed --tenant $TENANT --count 3 --region us-east-1
