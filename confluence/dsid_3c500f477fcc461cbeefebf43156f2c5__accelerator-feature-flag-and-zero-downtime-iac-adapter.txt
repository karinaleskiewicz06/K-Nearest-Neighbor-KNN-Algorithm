Accelerator feature flagging and zero-downtime IaC adapter

A pattern and reusable Terraform adapter that wires runtime accelerator feature flags (kernel/quantization/priority routing) to CI/CD canaries enabling zero-downtime toggles across Dedicated and Private deployments.
Overview

Purpose: provide a standardized, low-risk path to enable or disable accelerator-level features (e.g., mixed-precision kernels, quantized runtime paths, KV-cache prefetching, latency-optimized attention kernels) using feature flags backed by infrastructure as code. This document describes the Terraform adapter pattern, CI gating and rollout procedure, runtime integration points, safety checks, and an on-call runbook for rapid rollback.

Scope and motivation
- Scope: eng-infra Terraform modules, CI/CD pipelines, serving runtime feature gates, and canary rollout runbooks for hosted/dedicated/private environments.
- Motivation: historically enabling kernel-level toggles required manual operator steps, service restarts, or image rollouts. That increases outage risk and long lead times for experiments. The adapter enables:
  - Zero-downtime toggles across fleets by combining runtime dynamic flags with rolling config application.
  - Reproducible IaC for compliance and audit (Terraform-managed flags + versioned state).
  - Safe canary gating in CI that ties to telemetry-based SLO checks before global rollout.

Key concepts and components
1) Feature flag model (infra-first)
- Flag types: runtime-boolean, percent-traffic, config-string, kernel-variant (string).
- Backing store: LaunchDarkly for customer-facing toggles; internal Redis+etcd-backed config-store for infra flags where LaunchDarkly is prohibited (private/onprem).
- Rupture mode: an emergency global off switch owned by Oncall SRE (see runbook).

2) Terraform adapter module (accelerator_feature_flag)
- Purpose: provide a canonical TF module that creates flag metadata, optional provider wiring (launchdarkly flag or k8s ConfigMap + Vault secret), and CI artifact metadata.
- Location: terraform-modules/accelerator_feature_flag
- Interface (module inputs):
  - name (string) - unique flag key, e.g., "runtime.kernel.mixed_precision.v2"
  - description (string)
  - default_state (string) - "enabled" | "disabled"
  - rollout_strategy (string) - "immediate" | "percent" | "canary"
  - canary_targets (list) - list of tenant or node selectors (optional)
  - provider (string) - "launchdarkly" | "k8s_configmap" | "internal_store"
  - owner (string) - pager/team owning the flag
- Outputs:
  - flag_id (string)
  - provider_endpoint (string)
  - ci_gate_metadata (string) - JSON blob used by CI to assert the expected telemetry buckets

3) CI/CD integration patterns
- Pipelines: all feature flag changes must go through a pipeline that:
  1. Validates Terraform plan (tfsec, OPA policies).
  2. Creates a dry-run plan and posts a preview to the PR with expected ci_gate_metadata.
  3. If rollout_strategy == "canary", the pipeline triggers canary gating tasks (see gating checks below).
- Canary orchestration: use Argo workflows step that performs a staged flag enablement:
  - Stage 1: enable flag for internal-eval tenants (5 nodes, 0.1% traffic) for 10 minutes.
  - Stage 2: enable flag for seeded canary tenants (config in canary_targets) for 60 minutes.
  - Stage 3: conditional expand to 10% for 30 minutes, then to 50% pending metrics.
  - Stage 4: full rollout.
- CI gating checks (automated):
  - Latency P50 and P95 delta compared with baseline (reject if P95 increased > 15ms or P95 is > SLO*1.1).
  - Error rate: tokenization or generation errors increased > 0.5% absolute (reject).
  - Cost signal: GPU util per-request significantly increased (reject if average GPU-ms/request > baseline*1.25).
  - Quality signal (optional): eval prompt set regressions >= 2% absolute.

4) Runtime integration
- Serving runtime exposes a stable API to read flags in-process via an SDK (go/java/py) and a hot-reload path for config changes.
- For Private customers where central flag store is unavailable, the module renders a signed config blob into Vault and a node-local agent pulls and hot-applies it.
- Kernel selection example (pseudo-code):
  ```go
  flag := flags.Get("runtime.kernel.mixed_precision.v2")
  if flag.EnabledFor(request.Tenant) {
      executor.UseKernel("mixed_precision_v2")
  } else {
      executor.UseKernel("fp16_fallback")
  }
  ```
- KV-cache/Prefetch toggle: flags must support a "graceful-disable" semantics to drain ongoing sessions before turning off prefetch. The runtime will emit event: "prefetch.drain.started" / "prefetch.drain.completed" to telemetry.

Operational safety and SLOs
- Target SLOs for feature toggles:
  - Canary reaction window: pipeline must evaluate canary metrics within 75% of canary duration (example: 60-min canary -> gate result posted within 45 minutes).
  - Oncall latency blast radius: < 3% of production requests affected for initial canary.
- Telemetry hooks to validate:
  - metric names: inference.latency.p50, inference.latency.p95, inference.errors.tokenize, inference.gpu_ms_per_request, inference.quality.eval_regressions
  - alerting thresholds (examples):
    - inference.latency.p95 > baseline + 15ms -> Pager (severity P2)
    - inference.errors.tokenize > baseline + 0.5% -> Pager (severity P1)

Terraform policy guardrails (examples)
- OPA/Rego snippet (pseudocode): ensure no default_state == "enabled" with rollout_strategy == "immediate" for flags affecting > 10% traffic in production.
- Mandatory review labels: any flag that touches kernel selection must include reviewers: ["eng-serving-runtime", "eng-infra", owner_team].

Rollout and rollback procedure (step-by-step)
1) Author creates a TF change in a branch using accelerator_feature_flag module with rollout_strategy="canary". Include canary_targets.
2) CI runs plan + policy checks and posts PR preview.
3) Merge triggers Argo canary orchestration: Stage 1 -> Stage 2 -> automatic gating.
4) If a gate fails, Argo triggers rollback task: disable flag (or decrease percentage) and emit a rollback ticket into the incident queue.
5) Oncall triage: run the Fault Isolation checklist (see runbook).

Operational runbook (oncall steps for failed canary or emergency)
- Trigger: automated gate failure or customer reported regression correlated to recent flag.
- Immediate actions (within first 5 minutes):
  1. Identify flag_id from CI metadata, PR ID, or tagging in telemetry.
  2. Use the accelerator_feature_flag module outputs (provider_endpoint) to issue an emergency disable:
     - LaunchDarkly: curl -X POST $LD_API/flags/$flag_id/off -H "Authorization: $LD_TOKEN"
     - Internal store: terraform apply with variable force_disable=true (ci-runner account).
  3. Confirm hot-reload events: check service logs for "flag.toggle.received" and "kernel.switch.completed" across 3 representative nodes.
  4. If underlying kernel failed to revert cleanly, follow kernel rollback steps: drain node, restart runtime process, validate health probes.
- Post-incident: create postmortem, capture telemetry slices, and block future immediate rollouts until a retrospective.

Checklist for authors (pre-change)
- Has owner from eng-serving-runtime approved? (required)
- Is rollout_strategy set to canary by default? (required)
- Are canary_targets seeded and reproducible in CI? (recommended)
- Does PR include ci_gate_metadata and expected deltas? (required)

Examples and snippets
1) Terraform usage (example):
```hcl
module "mixed_precision_v2_flag" {
  source = "git::ssh://git@repo/terraform-modules.git//accelerator_feature_flag"
  name = "runtime.kernel.mixed_precision.v2"
  description = "Enable mixed_precision_v2 kernel path for latency experiments"
  default_state = "disabled"
  rollout_strategy = "canary"
  canary_targets = ["canary-tenants/alpha", "node-selector:gpu-type=t4-highmem"]
  provider = "launchdarkly"
  owner = "eng-serving-runtime"
}
```
2) CI gate config (example JSON used by the pipeline):
```json
{
  "flag_id": "runtime.kernel.mixed_precision.v2",
  "expected_deltas": {
    "inference.latency.p95_ms": 10,
    "inference.errors.tokenize_pct": 0.2
  },
  "canary_duration_minutes": 60
}
```

Governance and audit
- All TF changes are captured in the Terraform state and must include a clear change comment. The accelerator_feature_flag module writes an audit annotation (git commit url, PR id, owner).
- Quarterly review: eng-infra and eng-serving-runtime will run a sweep to identify stale flags older than 90 days and recommend removal.
