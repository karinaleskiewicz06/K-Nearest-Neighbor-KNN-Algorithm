Quality Gate Metrics and Thresholds v1 (Optimize config changes)

h1. Purpose
Optimize recommendations (batching policy updates, prefix/KV caching settings, and quantization profile changes) can materially affect model outputs. This document defines v1 quality gate metrics, regression thresholds, and statistical rules to decide pass/fail *before* an Optimize recommendation can be applied to production traffic.

This is the v1 policy for *Hosted API* and *Dedicated (default policies)*. Private/on-prem automation is not part of v1 (manual workflow only).

h2. Scope
* In-scope config change types (gated):
  1. Batching policy updates (continuous batching params, max batch tokens/requests, scheduling knobs)
  2. Prefix/KV cache settings (enablement, cache size/eviction policy, prefill reuse policies)
  3. Quantization profile changes (e.g., fp16 → int8/int4 variants) per model family and GPU SKU
* Out of scope (v1):
  * New model onboarding criteria
  * Training-time fine-tune changes
  * Prompt-set creation process (covered in the Prompt Set Coverage Plan)

h2. Definitions
* *Baseline*: current production config for the same model version + route policy + hardware SKU (for quantization: model family + GPU SKU baseline selection).
* *Candidate*: proposed Optimize config diff.
* *Prompt set*: curated list of prompts + expected evaluation method (golden outputs, rubric, or task checks).
* *Suite*: a group of prompt sets executed together (e.g., "Extraction", "RAG/Long-context", "Code").
* *Primary quality metric*: the metric used for pass/fail. Each prompt set declares its primary metric.

h2. Gate tiers
We run tiered gates to bound cost/latency.

h3. Tier 0: Static checks (pre-eval)
Blocking checks before any GPU eval runs (owned by Runtime/Platform; listed here for completeness):
* Unsupported config combinations (e.g., cache enabled with incompatible scheduler mode)
* Quant profile incompatible with model family / GPU SKU
* Known-unsafe knobs (see Runtime safety constraints)

Result: immediate FAIL with a deterministic reason code (no rerun).

h3. Tier 1: Fast smoke gate
Purpose: catch obvious regressions quickly.
* Target wall time: <= 15 minutes (p95) per gate run
* Minimum coverage: >= 120 prompts total across at least 3 workload categories (see coverage section)
* Rerun policy: 1 automatic rerun if flake score high (see Flakiness section)

h3. Tier 2: Full gate
Purpose: enforce production regression thresholds.
* Target wall time: <= 120 minutes (p95) per gate run
* Minimum coverage: >= 1,000 prompts total with category quotas (see coverage section)
* Rerun policy: 1 automatic rerun for flaky suites; results aggregated

h2. Offline quality metrics (v1)
Each prompt set must declare one *primary* metric and may emit secondary metrics.

h3. Primary metrics
1) *Task Success Rate (TSR)*
* Type: binary pass/fail per prompt
* Examples:
  * JSON schema valid + required keys present
  * Exact match on extracted entities
  * Tool call emitted with correct arguments
* Aggregation: mean success rate across prompts

2) *Rubric Score (RS)*
* Type: ordinal score 1–5
* Rubric anchors are prompt-set specific and stored with the prompt set.
* Aggregation: mean rubric score and % prompts with score >= 4

3) *Model-specific heuristic score (MHS)*
Used only when TSR/RS is not available, and must be explicitly approved by Applied ML.
* Type: scalar score in [0, 1] (higher is better)
* Examples:
  * Summarization coverage score (semantic similarity to reference bullets + length constraints)
  * RAG faithfulness proxy (citation presence + entailment heuristic)
* Aggregation: mean score

h3. Secondary metrics (non-blocking in v1 unless specified by prompt set)
* *Format adherence rate*: e.g., strict JSON, XML tags, markdown sections
* *Refusal / safety policy adherence*: for safety-labeled prompt sets
* *Length / truncation rate*: fraction of outputs hitting max tokens or truncation markers
* *Hallucination proxy*: only for RAG/citation prompt sets where we have reference docs

h2. Regression thresholds (pass/fail)
Thresholds are defined on *delta vs baseline* with confidence requirements.

h3. Global pass criteria
A gate run PASSES if:
1. All required prompt sets meet their primary metric thresholds (per below)
2. No "hard fail" secondary metric crosses its hard threshold (prompt-set specific)
3. Flakiness is within bounds (or quarantined suites are excluded and gate policy allows it)

A gate run FAILS if any required set fails. Overrides are governed by the exception policy.

h3. Full gate thresholds (Tier 2)
Unless a prompt set specifies stricter bounds, use:

*For prompt sets with TSR primary:*
* Allowed degradation: TSR_delta >= -1.0 percentage point (pp)
* Confidence rule: 95% one-sided confidence that TSR_candidate is not worse than (TSR_baseline - 1.0pp)

*For prompt sets with RS primary (1–5):*
* Allowed degradation: Mean_RS_delta >= -0.05
* Confidence rule: 95% one-sided bootstrap CI lower bound for Mean_RS_delta >= -0.05
* Additional guardrail: %RS>=4_delta >= -2.0pp (non-blocking by default; can be blocking for customer-specific routes)

*For prompt sets with MHS primary (0–1):*
* Allowed degradation: Mean_MHS_delta >= -0.010
* Confidence rule: 95% one-sided bootstrap CI lower bound for Mean_MHS_delta >= -0.010

Hard fail secondary thresholds (global defaults):
* Format adherence rate delta < -3.0pp → FAIL (blocking)
* Truncation rate delta > +2.0pp → FAIL (blocking)
* Refusal rate delta > +1.0pp on non-safety sets → FAIL (blocking)

Notes:
* We use tighter truncation/format thresholds because these regressions are highly visible to customers and often correlate with downstream failures.
* If a prompt set is known to be high variance, it may be marked "requires larger n" (see sample sizes).

h3. Smoke gate thresholds (Tier 1)
Smoke gate is intended to be sensitive to large regressions, not to prove non-regression.

Defaults:
* TSR_delta >= -3.0pp (no confidence rule; use point estimate)
* Mean_RS_delta >= -0.15 (point estimate)
* Mean_MHS_delta >= -0.030 (point estimate)
* Hard fail secondary thresholds are identical to Tier 2

If smoke gate fails, full gate is not run unless explicitly forced (admin-only) for debugging.

h2. Statistical treatment and variance handling
Owned by: Sana Farid (methodology), Applied ML (implementation in eval-harness).

h3. Confidence intervals
* TSR (binary): Wilson score interval for each condition; compare via bootstrap over prompts for delta when needed.
* RS and MHS: non-parametric bootstrap over prompts (10,000 resamples) to estimate delta distribution.

We evaluate a *one-sided* 95% bound for regression checks because the decision is "is it worse than threshold?".

h3. Minimum sample sizes
To avoid noisy decisions:
* Tier 1 (smoke): minimum 120 prompts total; minimum 30 prompts per required category.
* Tier 2 (full): minimum 1,000 prompts total; minimum 120 prompts per required category.
* For TSR-based prompt sets with baseline TSR < 80%, increase minimum by 1.5x (variance is higher near mid-range).

If minimum sample size is not met, the gate is marked INCONCLUSIVE and treated as FAIL for enforcement (requires rerun or override).

h3. Multiple prompt sets and aggregation rule
We do not use a single global aggregate score for pass/fail in v1.
* Decision rule: *all required prompt sets must pass*.
* Rationale: customers care about specific workloads; a global average can hide regressions.

We will revisit FDR / multiple-hypothesis correction if the number of required sets expands substantially.

h3. Flakiness scoring and reruns
Eval-harness emits a *flake_score* per prompt set (0–1; higher is flakier) based on rerun variance and historical stability.

Policy (v1):
* If flake_score >= 0.35 and failure margin is within 1.25x of the threshold, automatically rerun once.
* Aggregate rule across two runs:
  * Use the worse of the two point estimates for hard fail secondary metrics.
  * For primary metrics, combine by concatenating prompt-level outcomes if identical prompts were used; otherwise treat as two independent samples and bootstrap across both.
* If still failing and flake_score >= 0.50, label as POSSIBLE_FLAKE and require manual triage (still enforcement FAIL unless quarantined).

Quarantine:
* A quarantined prompt set is excluded only if the route policy explicitly allows it and at least one alternative set covers the same category.

h2. Required coverage per prompt set (v1)
This section defines what prompt sets must be included in a gate run.

h3. Workload categories
Prompt sets are grouped into categories. For v1, categories and minimum quotas are:

|| Category || Examples || Tier 1 (smoke) || Tier 2 (full) ||
| Structured extraction / JSON | entities, schema, tool args | >= 30 prompts | >= 200 prompts |
| General chat / instruction following | short answers, multi-turn | >= 30 prompts | >= 200 prompts |
| Long-context / RAG-style | 8k–32k context, citations | >= 30 prompts | >= 200 prompts |
| Code / reasoning (if route serves code) | codegen, bugfix | optional | >= 200 prompts if code routes |
| Safety / refusal behavior (if safety-sensitive route) | policy prompts | optional | >= 120 prompts |

Total minimum prompts:
* Tier 1: >= 120
* Tier 2: >= 1,000 (includes optional categories when applicable)

h3. Applicability rules
Which categories are required depends on the route/model usage profile:
* Default hosted routes: first three categories required.
* Routes labeled "code": include Code category.
* Routes labeled "safety_sensitive": include Safety category.

Route labels are sourced from Console route metadata (Optimize policy config).

h3. Prompt-set selection
For each required category:
* Select at least 2 prompt sets (to avoid single-suite bias) unless the category has only 1 approved set.
* At least 20% of prompts must be from "hard cases" (long-tail prompts flagged by Applied ML).
* At least 10% of prompts should be "format strict" for structured extraction categories.

h2. Config-type specific requirements
In addition to global coverage, some change types require extra checks.

h3. Batching policy updates
Risks: latency-induced truncation, timeouts that change completion behavior, scheduler interactions affecting determinism.

Additional blocking metrics:
* Truncation rate delta > +1.0pp → FAIL (stricter than global)
* Output length distribution shift: p50 tokens delta must be within [-8%, +12%] for non-length-controlled prompt sets (informational in v1; becomes blocking if correlated failures occur)

Required coverage additions:
* Include at least one "tight latency" prompt set (short prompts, high throughput) in Tier 2.

h3. Prefix/KV caching settings
Risks: cache key collisions, stale prefixes, incorrect reuse under multi-tenant routing.

Additional blocking checks (offline):
* Determinism check set ("CacheCorrectness") must show *0* cache-inconsistency events (binary) on Tier 2.
  * Definition: same request under cache-on vs cache-off produces semantic mismatch beyond a small tolerance for deterministic tasks (TSR-based).

Required coverage additions:
* Include "CacheCorrectness" prompt set (>= 80 prompts Tier 2).

h3. Quantization profile changes
Risks: subtle quality loss, long-context degradation, numeric instability, rare failure modes.

Additional blocking metrics:
* Long-context category thresholds tighten by 0.5x (i.e., TSR_delta >= -0.5pp, Mean_RS_delta >= -0.03, Mean_MHS_delta >= -0.006) for Tier 2.
* Structured extraction category: format adherence delta < -2.0pp → FAIL (stricter)

Required coverage additions:
* Tier 2 must include at least one long-context prompt set with >= 16k context.
* Include numeric/stability micro-suite ("QuantNumeric") if model family has known numeric sensitivity (e.g., function/tool calling heavy routes): >= 120 prompts Tier 2.

Baseline selection note (quant only):
* Baseline is per {model_family, model_version, gpu_sku, current_quant_profile}. If no baseline exists for gpu_sku, use nearest compatible sku baseline (documented in gate run) and require manual review.

h2. Model-family specific heuristics (v1)
Some families exhibit common failure modes. These are *additive* checks.

h3. Llama-family chat models
* Increased sensitivity to quantization on long-context: enforce tightened long-context thresholds (already required for quant changes).
* Tool calling: ensure tool-call format adherence is treated as blocking for tool-call labeled routes.

h3. Mistral-family instruct models
* Often stable on TSR but shifts verbosity: monitor output length deltas (informational) and summarize in gate report.

h3. Embeddings / rerank models
Not in scope for Optimize gating v1. If a route uses embeddings/rerank, Optimize changes must not target that route.

h2. Online signals (informational for v1 gates)
Online canary signals are not used for offline gate pass/fail, but are included in the gate report when available:
* User-visible error rate changes (5xx/4xx)
* Latency shifts affecting truncation
* Downstream task success proxies (customer-defined events when integrated)

If online signals show a severe regression during a canary, rollout controller may halt/rollback independently of offline gates.

h2. Reporting requirements (what the gate must output)
Every gate run must produce:
* Metric table per prompt set:
  * baseline value, candidate value, delta, CI bounds, pass/fail
* Overall decision and reason codes
* Sample size, prompt-set ids, prompt-set versions
* Model version, config diff, hardware SKU, quant profile
* Flake score per set + whether rerun happened
* Artifact pointers (logs, per-prompt results, output diffs for failures)

h2. Enforcement mapping (policy)
Which tier is required depends on change type and route tier:
* Self-serve hosted routes:
  * Batching/caching: Tier 1 + Tier 2 required
  * Quantization: Tier 1 + Tier 2 required
* Enterprise routes (Hosted/Dedicated):
  * Same as above, plus stricter prompt-set applicability (include safety/tool sets when labeled)
* Exception: emergency mitigations may use Tier 1 only with time-bound override (see exception policy).

h2. Known limitations (v1)
* Rubric scoring introduces human/LLM-judge variance; we mitigate via larger n and bootstrap CIs but do not guarantee perfect stability.
* Hard-to-measure attributes (tone, style) are not primary gating metrics in v1.
* Some customer-specific workloads may not be covered by default prompt sets; customers can request custom sets (requires Applied ML sign-off).

h2. Change management and versioning
* This document defines policy version: *quality_gates_metrics_v1*.
* Any threshold change requires:
  1. Applied ML + SRE review
  2. Backtest on at least 10 historical gate runs (or simulated diffs)
  3. Announcement in #eng-ml and #product with a 1-week notice for non-emergency changes

h2. Appendix: Example pass/fail interpretation
Example (TSR prompt set):
* baseline TSR: 92.3%
* candidate TSR: 91.6%
* delta: -0.7pp
* regression threshold: -1.0pp
* one-sided 95% bound on delta: -0.9pp
Result: PASS (bound is above -1.0pp)

Example (format adherence hard fail):
* baseline format adherence: 98.8%
* candidate: 95.0%
* delta: -3.8pp
Hard fail threshold: -3.0pp
Result: FAIL (blocking regardless of primary metric)
