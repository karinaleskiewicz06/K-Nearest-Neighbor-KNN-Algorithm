Cross-account Egress SLA Simulator and Testing Playbook

Summary

This playbook documents the Cross-account Egress SLA Simulator: a reproducible test harness and operational runbook that validates tenant egress behaviour across account boundaries, NAT/Proxy topologies, and GPU fleet regions. The simulator is used for: capacity planning, regression detection after network or TF changes, and SLO proofing before tenant cutover.

Goals

- Provide an automated, auditable way to exercise inter-account egress paths at scale.
- Catch regressions that impact latency/SLA (95th/99th) or cause packet loss to tenant egress.
- Verify Terraform/IaC changes (modules) do not regress NAT failover, BGP swap, or egress quotas.
- Integrate with CI pipelines to gate infra changes and schedule nightly stability sweeps.

Scope

Includes: GPU-serving clusters, inter-account NAT (shared NAT accounts), egress proxies, transit gateway routes, and per-tenant egress quotas. Excludes: workloads that require specialised hardware in on-prem dedicated racks (see private deployments docs).

When to use this playbook

1. Before merging TF changes that modify NAT, route tables, or transit gateway attachments.
2. After kernel or eBPF changes to egress proxies.
3. During onboarding of a new tenant that requires guaranteed egress SLOs.
4. Nightly regression runs and pre-release smoke tests for major infra releases.

Architecture overview

1) Components
- SLA Simulator Service (slasim): lightweight Go service that generates synthetic L4+L7 flows from tenant subnets across accounts.
- Egress Proxy (egress-proxy): Envoy-based edge proxy deployed in the shared egress account.
- NAT Swap Operator (natswap): Kubernetes operator that simulates provider-side preemption and BGP route flips.
- Collector/Analyzer: Prometheus + Loki + a small analysis job (Python) that calculates P50/P95/P99, packet loss, and tail retransmit counts per tenant.

2) Logical flow
- slasim runs flows that mimic real generation patterns: short-chat bursts, streaming long-sequence, and heavy-embedding bulk uploads.
- Flows are labeled with tenant-id, profile, sequence-length, and expected egress-policy (pin-to-nat, proxied, or direct).
- Analyzer produces a per-run report and uploads artifacts to the CI job and to the S3 test-artifacts bucket.

Traffic profiles (examples)

1. Chat-burst (low token count, high QPS): 2000 flows/min, avg size 128 tokens, target p95 latency < 120ms.
2. Longstream (long context): 50 flows/min, avg 4k tokens, target p95 latency < 900ms.
3. Bulk-embeddings (large payloads): 300 flows/hour, high egress bandwidth, target error rate < 0.5%.

This simulator relies on three modular Terraform inputs: transit_gateway_attachment, shared_nat, and egress_proxy. Below is a compact table of required variables and recommended defaults for test runs.

| variable | purpose | example (test) | notes |
|---|---|---:|---|
| tenant_id | logical tenant identifier | test-tenant-42 | used in tags and ACLs |
| egress_account_id | AWS account that hosts NAT/Proxy | 987654321000 | must be available to CI role |
| transit_gw_id | Transit gateway id | tgw-0a1b2c3d | create a staging TGW for test |

CI/CD pipeline integration

We run three pipelines: PR-gate (quick smoke), e2e-nightly (full run), and release-gate (pre-cutover). Example Buildkite pipeline snippet (pseudo-yaml):

steps:
  - label: "PR: egress smoke"
    command:
      - ./scripts/ci/terraform-plan-and-apply.sh --overlay=pr-smoke
      - ./scripts/ci/run-slasim.sh --profile=chat-burst --duration=5m
    env:
      AWS_ASSUME_ROLE: arn:aws:iam::987654321000:role/ci-runner
  - label: "Nightly: full e2e sweep"
    command:
      - ./scripts/ci/terraform-plan-and-apply.sh --overlay=nightly-full
      - ./scripts/ci/run-slasim.sh --profile=all --duration=2h
    concurrency: 1

Pipeline best practices

- PR-gates should not modify production routes or long-lived TGW attachments; use isolated staging TGW and ephemeral accounts.
- PR run duration should be short (5–15 minutes) and validate only latency and basic proxied vs direct routing.
- Nightly runs should reuse a shared staging account that mirrors production routes and BGP configuration.

Runbook: Failure modes and remediation

1) Symptom: p95 latency spikes > SLO (e.g., chat-burst p95 > 300ms)
  - Check: Prometheus rule slasim_request_latency_seconds{profile="$profile"} 
  - Action: pin down which hop increased (egress-proxy vs nat) using per-hop markers; run curl -w and tcpdump on egress-proxy pod.
  - Remediation: if egress-proxy CPU > 75% and queuing observed, scale proxy replicas (kubectl scale deployment/egress-proxy --replicas=N+2) and throttling policy.

2) Symptom: packet loss or TCP retransmits during bulk-embeddings
  - Check: collector logs for retransmit count and ENI errors in AWS CloudWatch.
  - Action: validate NAT instance health, check connection tracking table exhaustion (conntrack).
  - Remediation: increase nat instance size or enable conntrack tuning (net.netfilter.nf_conntrack_max). Update TF var quota_egress_mbps and re-run nightly.

3) Symptom: TF change causes route blackhole after TGW attachment swap
  - Check: routing tables in both accounts, verify BGP session states on provider (if available).
  - Action: trigger natswap operator to re-probe BGP and force route re-announce.
  - Remediation: revert TF change via pipeline rollback and file a RFC with change windows.

Metrics and SLOs (example targets used in simulator validation)

- Chat-burst: p50 < 35ms, p95 < 120ms, p99 < 220ms, error rate < 0.2%
- Longstream: p50 < 400ms, p95 < 900ms, p99 < 1500ms, error rate < 1%
- Bulk-embeddings: throughput >= 90% of quota, error rate < 0.5%

Prometheus alert examples

- ALERT EgressChatBurstP95High
  expr: histogram_quantile(0.95, rate(slasim_request_duration_seconds_bucket[5m])) > 0.12
  for: 10m
  labels: {severity="page"}
  annotations: {runbook="/confluence/eng-infra/runbooks/gpu-latency-regression-investigation-playbook.json"}

- ALERT EgressConntrackExhausted
  expr: node_conntrack_count / node_conntrack_max > 0.85
  for: 5m
  labels: {severity="pager"}

Local developer quick-start

1. Checkout repo: git clone git@internal:infra/egress-simulator.git
2. Build the slasim binary: make build
3. Apply test overlay (requires CI role): ./scripts/ci/terraform-plan-and-apply.sh --overlay=local-smoke --auto-approve
4. Run a quick profile: ./bin/slasim run --profile=chat-burst --duration=2m --target=staging-egress.internal

Artifacts and reporting

- Each run produces: prometheus metrics snapshot, raw pcaps (if enabled), analyzer JSON summary, and a JUnit-style test result uploaded to S3 under s3://redwood-test-artifacts/egress-simulator/YYYYMMDD/<run-id>/
- PRs must include the test artifact link when the PR gate modifies TF modules referenced by this playbook.

Change management and safety gates

- TF changes that alter egress_account_id, transit_gw_id, or route_table associations must:
  1) pass PR-gate smoke test (must complete in <= 20 minutes)
  2) be staged through a canary deployment to a single tenant in staging
  3) be validated by a full nightly run before merging to main

Troubleshooting checklist (short)

- Is the slasim run annotated with correct tenant-id and profile?
- Are egress-proxy pods reporting Envoy 5xx errors? Check /stats and logs.
- Are NAT instances reporting high conntrack usage? Check CloudWatch metrics.
- Did TF apply change route tables? Check last TF plan in pipeline artifacts.
