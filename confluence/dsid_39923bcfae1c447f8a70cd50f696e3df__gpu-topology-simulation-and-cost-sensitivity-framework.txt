GPU topology simulation and cost-sensitivity framework

Summary:
This document describes a reproducible simulation framework and experiment catalog for evaluating GPU fleet topologies against workload mixes, latency SLOs, and unit-cost sensitivities. It codifies inputs (traffic profiles, model families, instance types, pricing), a topology permutation engine, a cost model, and automated CI pipelines for running sweep experiments. The goal is to provide capacity planners, infra engineers, and product stakeholders with an actionable toolchain to compare candidate infrastructures before procurement or cluster rebalancing.

Why this exists:
- Provide an apples-to-apples way to compare heterogeneous options (fractional GPUs, multi-GPU packing, spot vs reserved, cloud region mixes).
- Surface non-linear cost and latency trade-offs caused by batching, KV cache hit rates, and preemption.
- Reduce expensive production experiments by expanding the design space in simulation with validated calibration to telemetry.

Scope and non-goals:
- Included: steady-state throughput simulations, latency tail estimation with queuing approximations, cost sensitivity to spot/ondemand pricing, and IaC artifacts for repro experiments.
- Excluded: model-level kernel microbenchmarks (maintained in eng-serving-runtime), and full end-to-end billing reconciliation (finance owns final invoice checks).

High-level approach:
1) Collect representative workload traces (sequence length distribution, arrival process, model type mix).
2) Calibrate microbenchmarks for each model variant+instance type (p95 token latency at key seq lengths, max throughput).
3) Use a discrete-event simulator to map requests onto candidate topologies with packing heuristics and autoscaler policies.
4) Compute cost per 1M tokens, p99 latency, and percent requests meeting SLO.
5) Produce a ranked report and recommendations with confidence bands.

Key concepts and terminology:
- topology: a description of instance types, GPU counts, and region placement.
- packing policy: how runtime assigns sessions to GPUs (fractional, exclusive, multiplexed).
- warm pool: pre-initialized instances with KV cache seeded; reduces cold-start tail.
- cost-sensitivity: the change in cost efficiency metric (cost per token) as price inputs vary (e.g., spot price +20%).

Inputs (required):
- workload_trace: path to JSON traces (arrival timestamps, model_id, seq_len).
- model_profiles: CSV of {model_id, tokens_per_ms, kv_cache_hit_rate_seqlen, gpu_mem_bytes_required}.
- instance_catalog: YAML of {instance_type, gpu_count, gpus_per_node, vCPU, memory_gb, on_demand_price_hour, spot_price_hour}.
- autoscale_policy: JSON with min_nodes, target_util_pct, cooldown_s.
- pricing_scenarios: list of spot/ondemand multipliers to sweep.

Outputs (artifact set):
- simulation_report_{timestamp}.html (summary with charts).
- per-run CSVs: placement.csv, latencies.csv, cost_breakdown.csv.
- IaC snapshot: terraform-plan.json that represents the target topology for a chosen candidate.
- experiment_manifest.json listing inputs and git commit sha for reproducibility.

Simulation model (short):
- Request model: arrivals are read from workload_trace and optionally resampled to scale traffic.
- Service model: each model_profile entry exposes a per-GPU service curve: tokens/sec at given sequence lengths and p95/p99 latency multipliers.
- Queueing: nodes implement per-GPU queues with M/G/1 approximations. Batching effects are modeled as service-time reductions when concurrent requests align; batching window is configurable.
- Preemption: spot instance failure modeled as random node removal with configurable MTTR and job migration cost (eviction penalty tokens).

Topology permutations and experiment matrix (example):
1) Single-region homogeneous: n x A100-80GB; pack fractional up to 32 sessions per GPU.
2) Multi-region balance: 60% primary region A, 40% secondary cheaper region B with additional 60ms network penalty for cross-region fallbacks.
3) Mixed-instance heterogenous: blend of A100 + T4 for low-cost embedding jobs and A100 for generation.
4) Warm-pool optimized: reserve 10% capacity as warm pool with KV cache seeding from golden prompts.

Experiment parameters to sweep (table):
- traffic_scale: [0.5, 1.0, 1.5, 2.0]
- spot_multiplier: [0.6, 0.8, 1.0, 1.2]
- packing_policy: [fractional, exclusive, mixed]
- warm_pool_fraction: [0.0, 0.05, 0.1]
- kv_cache_hit_rate_shift: [-0.1, 0, +0.1]

Cost model (components broken down):
- instance_hourly_charge = on_demand_price_hour * (1 - reserved_discount) or spot_price_hour * spot_multiplier
- storage_charge = snapshot_gb * storage_gb_hr_rate
- egress_charge = GB_out * eg_rate (apply cross-region surcharge where applicable)
- operational_overhead = 2.5% platform surcharge for managed services
- amortized_gpu_license = license_monthly / (730 * num_nodes)

Example sensitivity metric: cost_per_90pct_requests_meeting_SLO = total_cost / requests_meeting_SLO * 1e6 (scaled per million requests).

Calibration and validation:
- Calibrate model_profiles using the internal perf-benchmark harness (eng-serving-runtime/benchmark) and store results in model_profiles bucket with timestamped keys.
- Validate simulator by replaying a week of production telemetry in a dry-run environment and comparing p95 and p99 latencies within a 10% error target.

CI/CD integration and automation:
- Repository: github.com/redwood-inference/infra-sim
- Tests: unit tests for service curve interpolation, integration tests that run small-sweep scenarios on PRs using ephemeral cloud credits.
- Nightly jobs: run the default experiment matrix in a reduced-size mode (scale factor 0.1) and upload reports to /repro/sim-reports/yyyy-mm-dd/ in the artifacts store.
- Promotion: when a candidate topology is selected, pipeline emits terraform module params and creates a draft PR against the terraform landing zone repo for human review.

Terraform / IaC artifacts and patterns:
- We generate a canonical terraform variables JSON for each candidate rather than full modules. This avoids accidental drift when running many speculative topologies. Example snippet (documented in the repo):

terraform vars example:
{
  "gpu_pool_name": "sim-candidate-42",
  "node_count": "48",
  "instance_type": "a100-80gb",
  "region": "us-west-2",
  "spot": "true"
}

- Ensure any generated plan is annotated with experiment_manifest.json and a TTL tag (sim:ttl=72h) for automatic cleanup.
- Follow existing landing-zone guardrails: egress fencing, iam roles, and budget alerts before full promotion.

Runbook: How to run a new experiment from telemetry (step-by-step):
1) Prepare trace: run scripts/trace_extract.py --start 2025-01-01 --end 2025-01-08 --models production-list > traces/week1.json
2) Update model_profiles with latest microbenchmarks: scripts/collect_profiles.sh --models-file models.csv --output model_profiles/2025-01-08.csv
3) Create a new experiment directory: experiments/2025-01-08-sim1 and add an experiment.yaml describing topology permutations and sweeps.
4) Kick off the simulator locally for a quick sanity run: make run-fast EXPERIMENT=experiments/2025-01-08-sim1 SCALE=0.1
5) For full runs, submit the pipeline: gh workflow run sim-sweep.yml -f experiment=experiments/2025-01-08-sim1
6) After completion, inspect artifacts in the pipeline job and the summary HTML. If a candidate looks promising, open a promote candidate issue: infra/sim -> Promotes with terraform params attached.

Operational checklist when promoting a simulation candidate to staging/prod demo:
- Run the staging canary with 5% traffic routed to candidate region and monitor p95/p99 for 72 hours.
- Configure rollout policy: linear 5% increments every 30 minutes with automatic revert on 3 consecutive SLO breaches.
- Verify cost alerts: set a temporary budget threshold equal to predicted cost * 1.15 for first 24 hours.

Metrics and acceptance criteria for candidate topologies:
- p99 latency <= production SLO + 10ms for generation models at target throughput.
- >= 95% of requests meet configured SLO for at least 72 hour simulated window.
- simulated cost per 1M tokens within the finance target for that product line (as documented in pricing-and-packaging).

Troubleshooting & common failure modes:
- Calibration drift: if observed production tails exceed simulated tails by >20%, re-run microbenchmarks and re-calibrate service curves.
- Packing oversubscription: unexpectedly high queuing indicates model_profiles under-reporting memory or throughput — validate GPU mem accounting.
- Spot flapping: frequent spot evictions can make cost-effectiveness worse; add longer MTTR in spot scenarios to estimate better.
