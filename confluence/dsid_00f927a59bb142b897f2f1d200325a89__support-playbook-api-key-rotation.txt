Support playbook: help customers rotate/revoke Hosted API keys

# When to use
Use this playbook when a customer asks how to rotate/regenerate a key, requests emergency revocation, or reports suspected compromise.

# Guardrails
- Never ask a customer to paste an API key value into email/Jira/Slack.
- If the customer is unable to access Console due to RBAC, escalate to Security for an approved admin-assisted revoke.

# Quick decision tree
1) **Suspected compromise?**  Revoke first, then rotate.
2) **Planned rotation?** Create new key, deploy, validate, then revoke old key.

# Customer instructions (canonical)
Send the customer the link/steps from: "Hosted API key rotation & revocation (customer guide)".

# Emergency revoke procedure (internal)
1. Create/locate the support ticket (SUP-*).
2. Confirm authorization in writing (email from authorized admin or known customer security contact).
3. In Console (admin view), go to Settings  API Keys  select key  Disable.
4. Document: key name, key id, timestamp, who authorized.
5. Ask customer to deploy replacement key.

# Post-actions
- If compromise is likely: tag ticket with `security-incident` and page Security on-call.
- Recommend customer updates any leaked build logs, CI variables, or screenshots.

# Common pitfalls
- Customer confuses **key id** with **key value**  results in 401 after update.
- Customer rotates key but keeps old key in a background job  intermittent 401s.
- Customer uses one key for multiple services  rotation requires coordinated deploy.

# Templates
## Email snippet
"You can rotate a Redwood Hosted API key by regenerating it in Console (Settings  API Keys) or via API. After you deploy the new key and validate traffic, disable the old key. If you suspect exposure, disable first and we can help you recover quickly."
