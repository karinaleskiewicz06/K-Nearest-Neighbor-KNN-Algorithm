GPU IaC Module Release Qualification Playbook

Summary
=======
This playbook defines the acceptance criteria, test matrix, CI/CD checks, and promotion steps required to qualify Terraform/Helm/Ansible modules that change GPU fleet topology, networking, or tenant-facing reservation behavior. The goal is to ensure changes are safe for production, observable, and reversible with minimal blast radius.

Scope
-----
- Applies to any IaC module that: network-attaches GPU nodes, modifies routing/egress policies, creates GPU pools, or changes scheduler-affinity tags.
- Includes modules authored under: terraform-and-iac/, ci-cd-and-build/ build artifacts that influence node bootstrap images, and operator manifests that run in control plane namespaces.
- Excludes pure documentation updates or non-production demo sandboxes.

Quick overview of expectations
------------------------------
- All modules must provide a compatibility matrix, changelog, and a testbed plan.
- CI must pass: lint, unit plan-delta, semantic diff approval, integration smoke tests on a staging GPU cluster, and telemetry-contract verification.
- Promotion requires signed artifacts, a validated Terraform plan with guardrail checks, and oncall-runbook baked into the PR.

Qualification matrix (example)
----------------------------
| Change class                         | Required tests (min)                              | Rollout strategy         | Owner  |
|--------------------------------------|---------------------------------------------------|--------------------------|--------|
| Network ACL / NAT / Egress changes   | Plan-diff, staging apply, egress simulation, perf | Canary (10% regions)     | NetEng |
| GPU pool size or flavor change       | Plan-diff, scale test, allocator-contract smoke   | Phased scale + monitor   | Infra  |
| New scheduler-affinity labels        | Unit tests, scheduling simulation, trace checks   | Dry-run + gradual label  | Runtime|
| Image bootstrap changes (golden AMI) | Signed artifact, boot smoke, secure-boot test     | Blue/Green               | Build  |

Prerequisites
-------------
1. Module repository uses standard module-layout: /modules/<name>/main.tf, variables.tf, outputs.tf, /test/
2. CI runners with GPU staging accounts configured (see GPU CI runner onboarding doc).
3. Terraform state backend and workspaces correctly configured and locked for target environment.
4. Telemetry contract (see below) implemented by module via metrics and logs.

Telemetry / Observability contract (must be verified by CI)
--------------------------------------------------------
- Required metrics emitted by any module that affects runtime:
  - gpu.pool.provision.count (gauge)
  - gpu.node.bootstrap.duration_seconds (histogram)
  - gpu.pool.eviction.rate (counter per-minute)
  - infra.iac.apply.errors (counter with tags: module, env, change_id)
- Log schema: structured JSON with keys: event, module, change_id, node_id, step, duration_ms.
- Trace spans: modules must create an "iac.apply" span that wraps cloud API calls for topology changes.

Automated CI / gating checklist
-------------------------------
1. Static checks
   - terraform fmt & validate
   - tflint with company ruleset
   - checkov / terrascan (policy-as-code)
2. Unit-plan checks
   - terraform plan with -out and plan-diff: CI compares resource counts against baseline. Maximum allowed delta must be declared in module metadata.
3. Integration smoke
   - Apply to ephemeral staging workspace (auto-rollback)
   - Run reservation + KV-cache warmup simulation (10 synthetic requests per node)
   - Egress simulation: synthetic traffic that exercises NAT and egress rules; assert no more than 0.5% packet drop in 5m window
4. Telemetry contract validation
   - Poll metrics endpoint and assert required metrics exist within 2 minutes of apply completion
5. Security checks
   - Secrets scanning, IAM permission review (least-privilege), artifact signature verification
6. Approval
   - PR requires 2 approvers: one from infra owning module and one from network/security if change touches egress/NAT/VPC.

Manual qualification steps (pre-promotion)
-----------------------------------------
1. Run full scale test in a non-prod region (size depends on module: default 20 nodes for pool modules). Capture perf and error-rate baseline.
2. Execute chaos test: temporarily throttle egress at 20% and verify fallback and backpressure behaviors.
3. Run ingress/egress path validation using the egress-probe harness (see related pages).
4. Confirm billing signal: estimate incremental egress and GPU-minute cost and document billing-owner.

Promotion & rollout protocol
---------------------------
- Promotion artifact: signed release bundle (SHA256) containing module sources, changelog, plan-summary.json, and test logs.
- Rollout phases:
  1. Canary: apply in a single low-traffic region with 5% of tenants pinned to new module (duration 6 hours)
  2. Regional ramp: expand to 25% for 24 hours while monitoring SLOs
  3. Global ramp: 100% after 72 hours with no regressions
- Abort criteria (immediate rollback):
  - Increase in p50/p95 tail latency of inference control plane > 25% vs baseline
  - gpu.pool.eviction.rate spikes > 2x for > 10 minutes
  - infra.iac.apply.errors > 0.5% of operations in 15 minutes

Rollback checklist
-----------------
- Execute terraform apply with prior state snapshot (workspace promote rollback tag).
- Notify oncall and post a one-sentence incident summary to #prod-infra.
- If rollback affects tenant routing, trigger DNS TTL squeeze protocol (set TTL=30s) and follow the cross-account routing playbook.

Sample Terraform snippet (module metadata and guardrails)
------------------------------------------------------
```hcl
module "gpu_pool" {
  source = "git::ssh://git@github.com/redwood/modules.git//gpu_pool?ref=v1.2.0"
  name   = "gpu-pool-canary"
  min_size = 2
  max_size = 5
  allowed_flavors = ["a100-40gb","a10g"]
  max_delta = 3 # CI will reject plan diffs that exceed this
  change_id = "PR-4827"
}
```

Sample CI pipeline fragment (GitHub Actions style)
------------------------------------------------
```yaml
name: GPU Module Qualification
on: [pull_request]
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Terraform fmt & validate
        run: |
          cd modules/gpu_pool && terraform fmt -check && terraform validate
  smoke-integration:
    runs-on: [self-hosted, gpu-ci]
    needs: validate
    steps:
      - name: Apply to staging workspace
        run: |
          export TF_WORKSPACE=staging-${{ github.sha }}
          cd modules/gpu_pool && terraform init && terraform apply -auto-approve
      - name: Run smoke tests
        run: scripts/run-gpu-smoke.sh
```

Artifact signing and provenance
------------------------------
- All module releases must be signed using the company GPG key and have a provenance file describing exact inputs. Use the release helper: `scripts/release/sign-artifact.sh <bundle.tar.gz>`
- Retain artifacts in signed S3 bucket with lifecycle 7y for audit.

Operational runbook snippets (to be included in PR description)
--------------------------------------------------------------
1. Monitoring signals to watch: infra.iac.apply.errors, gpu.pool.provision.count, gpu.node.bootstrap.duration_seconds, controlplane.rpc_errors
2. Quick recovery commands:
   - Promote previous workspace: `terraform workspace select promote-rollback && terraform apply -auto-approve`
   - Drain a single problematic node: `kubectl cordon <node>; kubectl drain <node> --ignore-daemonsets --delete-local-data`
3. Pager routing: Team = #oncall-infra (primary), #network (secondary), escalation: SRE lead on-call after 15m

Acceptance rubric (TL;DR)
-------------------------
- Static & policy checks: pass
- Plan delta within module-declared limits: pass
- Smoke apply in staging: no errors, telemetry emitted: pass
- Manual scale and chaos checks: no critical regressions: pass
- Signed artifacts + PR approvals: pass

Appendix: Testbed sizing recommendations
---------------------------------------
- Small modules (label changes, IAM tweaks): 3 nodes, 2 tenants
- Medium modules (pool sizing, flavor changes): 20 nodes, 10 tenants, 20k tokens/min synthetic traffic
- Large modules (image bootstrap, network fabric changes): 100 nodes, multi-AZ, cross-region egress simulation
