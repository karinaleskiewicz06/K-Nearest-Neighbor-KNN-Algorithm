Tenant egress shaper operator design & CI/CD runbook

Summary:
This document describes the design, Terraform module API, operator behaviour, observability, CI/CD pipeline, and runbook for the Tenant Egress Shaper Operator (TESO). TESO enforces per-tenant egress bandwidth and cost budgets for GPU-backed inference workloads by attaching a shaper policy to tenant network routes and exposing a programmable operator that reconciles Terraform-managed configuration with runtime enforcement.

Motivation:
- We need a reliable, auditable mechanism to limit tenant egress (bandwidth and cost) to prevent noisy-billing and cross-tenant egress spikes during burst events.
- Current ad-hoc NAT/proxy rules are difficult to reason about across accounts and get out of sync with accounting.
- TESO provides a single source-of-truth (Terraform), a Kubernetes operator for runtime enforcement, and CI/CD to ensure safe rollouts.

Goals and non-goals:
- Goals:
  - Enforce per-tenant egress bandwidth caps (Mbps) and windowed budget (USD/day).
  - Provide Terraform module for expressive intent: caps, emergency overrides, and priority tiers.
  - Operator reconciles Terraform state with dataplane proxies (egress-proxy) and programs rate limits.
  - Emit metrics and billing annotations for downstream chargeback.
- Non-goals:
  - Not a replacement for deep packet inspection or content filtering.
  - Not responsible for per-request authentication — assumes tenant identity is known upstream.

High-level design:
1) Configuration plane: Terraform module (tenant_egress_shaper) that creates a TenantEgress CR with desired caps, tiers, and billing tags.
2) Control plane: Kubernetes operator (TESO) that watches TenantEgress CRs and reconciles against an egress-proxy control API to apply rate limits, token buckets, and annotation labels.
3) Data plane: egress-proxy (existing) implements per-tenant token buckets and reports usage via Prometheus and billing events to Kafka.
4) Observability: Prometheus metrics + traces + internal billing events used for SLO verification and chargeback.

Terraform module API (example usage):

# Example: module usage
module "tenant_egress_shaper" {
  source = "git::ssh://git@github.com/redwood-infra/terraform-modules.git//tenant-egress-shaper?ref=v1.3.0"

  tenant_id         = "tenant-1234"
  max_mbps          = 200          # burst cap in Mbps
  sustain_mbps      = 50           # sustained baseline cap
  daily_budget_usd  = 150.00       # soft budget for the day
  priority_tier     = "standard"  # standard | premium | emergency
  emergency_contact = "oncall-infra@redwood.ai"
  labels = { team = "search", app = "query-service" }
}

Terraform module outputs (summary table):
- tenant_egress_cr_name: Name of created TenantEgress CR
- enforcement_status: last known enforcement state

TenantEgress CR (CRD schema summary):
- spec.maxMbps: integer
- spec.sustainMbps: integer
- spec.dailyBudgetUSD: number
- spec.priorityTier: string
- spec.override: {enabled: bool, expiresAt: string}
- status.enforcedBy: [controller-name] and status.metricsSnapshot

Operator behaviour and safety rules:
- Reconciliation frequency: default 30s (configurable via env var TESO_RECONCILE_INTERVAL).
- Safety check: operator performs a dry-run check with the dataplane control API before applying changes. If dry-run fails, operator will escalate to a canary channel, mark status.conditions and avoid applying the change to production.
- Emergency override: a TenantEgress.override can be set by owners to temporarily lift caps for up to 2 hours. Overrides are recorded to audit logs and require two reviewers for extensions > 2h.
- Rollback: operator stores last-applied CR spec in an annotation for quick rollback.

SLOs, metrics and alerts (concrete):
- Enforcement SLO: 99.9% of TenantEgress CRs must have enforcementStatus == "Applied" within 60s of Terraform apply (SLO owner: infra-networking).
- Metrics emitted by operator (Prometheus):
  - teso.reconcile.duration_seconds (histogram)
  - teso.enforcement.latency_seconds (gauge)
  - teso.enforcement.errors_total (counter)
  - teso.tenant.usage_bytes_total{tenant_id, tier}
- Billing events published to Kafka topic: events.billing.egress with the following JSON payload (example):
  {
    "tenant_id": "tenant-1234",
    "bytes": 123456789,
    "cost_usd": 4.52,
    "window_start": "2025-11-01T00:00:00Z"
  }
- Alerts:
  - P1: teso.enforcement.errors_total > 5 in 5m AND > 10% of tenants affected -> pager to infra-networking oncall
  - P2: teso.reconcile.duration_seconds p95 > 2m -> slack #infra-alerts and create ticket for investigation

CI/CD pipeline (Buildkite/GitHub Actions examples):
- Goal: terraform module + operator code follow canonical build and promote path with automated canary to staging and gated production rollout.
- Branch flow: main -> release branches. Module releases use semver tags and signed releases.
- Pipeline steps (Buildkite YAML snippet):
  - validate: terraform fmt && terraform validate (module)
  - unit-tests: go test ./... (operator)
  - integration: spin up k3d cluster, deploy operator, apply module and run e2e scenario for failover and override
  - promote: create release artifact and update module registry

# Buildkite sample step snippet
steps:
  - label: "validate terraform"
    command: "cd modules/tenant-egress-shaper && terraform fmt -check && terraform validate"
  - label: "operator unit tests"
    command: "make test-unit"

Promotion and canary policy:
- Canary policy for operator helm chart: deploy canary to staging (10% traffic simulation) -> run chaos test: simulate puppet tenants with 10x egress for 5m -> confirm enforcement and billing events -> proceed with progressive rollout (10%, 25%, 50%, 100%) with 20m monitoring windows.
- Terraform module: create release tag, publish to registry, run a staged apply to a shadow tenant set before approving production applies.

Runbook: common incidents and actions (short checklist):
1) Symptom: enforcement failures (status == "Failed" for many CRs)
   - Check operator logs for enforcement API errors: kubectl -n redwood logs deployment/teso-controller | grep enforcement
   - Check dataplane egress-proxy health: curl http://egress-proxy-admin:8080/health
   - If egress-proxy unhealthy, escalate to infra-networking SRE and initiate dataplane failover (see dataplane failover playbook).
   - If operator out-of-sync after control-plane recovered, run: kubectl -n redwood exec deployment/teso-controller -- /bin/teso repair --tenant=tenant-1234

2) Symptom: unexpected tenant throttling causing P0 customer impact
   - Immediately lift the tenant override via Terraform apply (set override.enabled = true and expiresAt = now()+30m) and notify customer success.
   - Mark incident and open postmortem if root cause is enforcement config mismatch.

3) Symptom: billing divergence (billing events differ from chargeback report)
   - Pull matching windows from Kafka topic events.billing.egress and compare with Prometheus teso.tenant.usage_bytes_total.
   - If divergence persists, enable diagnostic capture in egress-proxy for 5 min (increase sampling) and route artifacts to sig-finance.

Migration and rollout plan for existing tenants:
- Phase 0: Audit current egress paths and annotate tenants with tenant_id (2 weeks).
- Phase 1: Shadow mode – deploy TESO in shadow enforcement (no apply) and verify billing events match current accounting for 7 days.
- Phase 2: Pilot – migrate 10 low-risk tenants to enforced mode with manual monitoring (2 weeks).
- Phase 3: Progressive rollout – use module releases and operator progressive rollout to move remaining tenants with 20m observation windows between steps.

Testing checklist (pre-release):
- Unit tests cover CRD conversions and dry-run logic.
- Integration test validates: reconfiguration, override path, CRD deletion and recreation, and dry-run safety path.
- Load test: simulate 5k tenants with randomized burst patterns and check enforcement latencies.

Ownership, maintenance, and oncall:
- Owner: infra-networking team (primary), infra-sre (secondary)
- Oncall rotations: infra-networking pager for P1 and P0 enforcement errors; infra-sre handles dataplane escalation.
- Maintenance windows: policy changes allowed during designated network change windows; enforcement algorithm changes require a phased canary deploy and a runbook prior to change.
