Tenant egress isolation CI simulator and acceptance tests

Summary:
This document describes the Tenant Egress Isolation CI Simulator: an automated test harness and CI job suite that validates tenant isolation, egress throttling, VPC egress routing, and Terraform/CNI acceptance checks for the inference GPU fleet. The simulator is intended to run in CI (pre-merge and nightly) and as a local developer tool for infra engineers.

Scope:
- Applies to: cloud accounts, VPC egress paths, tenant NAT/egress allocation, CNI QoS rules, and Terraform modules that configure routing and egress guardrails.
- Excludes: application-level request semantics (handled by serving runtime tests) and customer data plane encryption (handled by security).

Motivation:
As Redwood scales multi-tenant inference, subtle changes to egress routing and Terraform drift have caused noisy-neighbor incidents and surprise billing. The simulator enforces acceptance criteria for: egress fencing, cross-tenant bandwidth fairness, NAT IP exhaustion handling, and safe fallbacks for preemption/burst policies.

Goals:
- Detect regressions before Terraform or CNI changes reach production.
- Provide reproducible, low-cost CI scenarios that emulate tenant traffic mixes.
- Measure guardrail effectiveness: tokenized throughput ceilings, per-tenant rate limiting and lightweight QoS enforcement.

Architecture overview:
- Harness components:
  * controller (Go): orchestrates scenarios and signals chaos steps.
  * traffic-generator (Python): simulates tenant request patterns (short chat, embeddings, long-gen).
  * egress-proxy (lightweight envoy): applies simulated NAT pools and QoS policies for test isolation.
  * terraform-checker (bash + terraform): plans and applies ephemeral network modules in a sandbox account.
  * metrics-exporter (Prometheus textfile): emits test metrics consumed by CI assertions.

Test topology (logical):
- 3 simulated tenants: tenant-A (latency-sensitive), tenant-B (high-throughput), tenant-C (sporadic burst).
- Shared egress fabric: NAT pool with two upstream subnets, per-tenant egress ACLs enforced by egress-proxy.
- CNI QoS layer: shapes traffic by DSCP and token bucket parameters.

Acceptance test matrix (examples):
| Test name | Trigger | Success criteria | Notes |
|---|---|---:|---|
| egress-fencing-smoke | PR to terraform/egress | No cross-tenant flow detected; per-tenant NAT IPs not shared | Fail fast in pipeline |
| nat-ip-exhaustion | nightly | New tenants receive HTTP 429 from proxy; older tenants unaffected | Ensures graceful degrade |
| qos-priority-respect | pre-merge | Tenant-A 99th p50 latency < 120ms while Tenant-B limited to <50% BW | Measures priority shaping |
| route-fallback | PR to routing module | Route failover within 7s for simulated AZ outage | Validates multi-subnet design |

CI integration patterns:
1) Pre-merge (fast): run 'smoke' subset that runs for ~2 minutes, uses local egress-proxy, and validates policy templates via terraform plan + a lightweight traffic burst.
2) Merge gate (extended): runs full suite including terraform apply against a sandbox account, end-to-end NAT exhaustion simulation, and metric-based assertions. Runs in parallel with other infra jobs.
3) Nightly (stress): long-running traffic mixes, failure injection (AZ blackout, NAT pool depletion), and regression detection with historical baselines.

CI job example (GitHub Actions snippet):
```yaml
name: egress-acceptance
on: [push,pull_request]
jobs:
  smoke-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - run: ./ci/setup-sandbox-credentials.sh
      - run: ./ci/run-egress-smoke.sh --tenants 3 --duration 120
      - run: ./ci/assert-metrics.sh --threshold-file=ci/thresholds/smoke.json
```

Local developer quickstart:
1) Install: go build ./controller, pip install -r traffic-generator/requirements.txt
2) Start local egress-proxy: docker-compose -f dev/docker-compose.egress.yml up --build
3) Launch controller in dev mode: ./controller --scenario=smoke --sandbox=local
4) Generate traffic and tail metrics: tail -f metrics/test.prom

Terraform/IaC checks and patterns:
- Use ephemeral workspaces per CI run: terraform workspace new ci-${GITHUB_RUN_ID} then terraform apply -var=prefix=\"ci-${GITHUB_RUN_ID}\"
- Validate idempotency: run 'terraform plan' twice; second plan must be empty.
- Minimal IAM: acceptance sandbox account must use least privilege role with temporary credentials.
- State isolation: use remote state backend with per-run key and auto-cleanup in teardown.

Sample Terraform assertion steps (bash):
1) terraform init -backend-config=\"key=${RUN_KEY}\"
2) terraform apply -auto-approve
3) ./ci/validate-egress.sh --expected-nat-pools=2
4) terraform destroy -auto-approve

Operational runbook (when a CI failure surfaces):
1) Identify failing test and CI run ID.
2) Re-run the failing job locally with --debug to capture packet captures and proxy logs.
3) If terraform plan shows drift, inspect remote state and run 'terraform state list' for changed resources.
4) If cross-tenant flows observed: immediately revoke access to the failing sandbox role and open P1 ticket.
5) Notify networking and oncall with playbook template (see Communications below).

Quick remediation checklist:
- Reproduce in sandbox using the same RUN_KEY.
- Run 'ci/repair/runbook.sh <RUN_KEY>' to apply emergency ACLs that fence affected tenants.
- Rotate NAT pool allocations if exhaustion was the root cause.

Observability and assertions:
- Metrics exported:
  * per_tenant_tx_bytes (counter)
  * per_tenant_rx_bytes (counter)
  * per_tenant_latency_ms_bucket (histogram)
  * proxy_429_count (counter)
  * terraform_diff_count (gauge)
- Alerts to trigger from CI:
  * failure_count > 0 for pre-merge smoke => block merge
  * regressions in nightly > 5% compared to 7-day baseline => create issue

Runbook for production follow-ups (post-incident CFG):
- If simulator uncovered cross-tenant leakage in pre-merge, escalate to platform-security and block merge.
- If detected only in nightly, create a ticket with reproducible scenario, attach packet capture, and schedule bugfix in the next infra sprint.

Ownership and escalation:
- Primary owner: infra-networking team (pager: #infra-net on Slack).
- Secondary: gpu-fleet-capacity for throughput regressions.
- Oncall rotation: see eng-sre oncall roster for emergency paging tree.

Maintenance and tech debt notes:
- Update traffic profiles quarterly to reflect observed production mixes (tokens per request, seq-length, embedding sizes).
- Keep sandbox credential rotation in sync with secrets rotation policy (people-ops).
- Add a synthetic 'tenant-C burst' scenario when adding new burst policies.
