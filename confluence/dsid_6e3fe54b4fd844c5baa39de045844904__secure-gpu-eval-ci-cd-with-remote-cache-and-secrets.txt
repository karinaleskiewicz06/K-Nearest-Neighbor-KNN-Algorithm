Secure GPU CI/CD for Evaluation Workloads: remote caching, secrets, and canary gating

Overview
========

Purpose: This document describes a secure, reproducible CI/CD pattern for running evaluation (eval) workloads on GPU pools. It focuses on three operational goals: reducing wall-clock build/eval time with remote caching, protecting secrets and model artifacts during CI, and gating production-facing model rollouts with canary evaluation steps. The guidance here is intended for infra engineers, SREs, model-eval owners, and platform engineers.

Scope and constraints
---------------------
- Applies to evaluation and benchmark pipelines that provision ephemeral GPU nodes (on cloud or dedicated Dedicated pools).
- Assumes use of our standard build registry and image signing pipeline.
- Does NOT cover training jobs or long-running tenant workloads (see tenant onboarding docs).

Key properties of the recommended system
---------------------------------------
- Deterministic builds: content-addressable outputs (CAS) and signed artifacts.
- Fast incremental runs: remote cache for build artifacts and pre-baked evaluation kernels.
- Secret-safe: no plaintext secrets in logs; short-lived creds via Vault and workload identity.
- Safety gate: automated canary eval pass/fail gates before any production route update.

Architecture (text diagram)
--------------------------
GitHub Actions / Tekton / CircleCI -> CI Runner (k8s) -> Build cluster w/ remote cache (GCS/oss-cache) -> Container registry (signed images) -> Canary eval job on GPU pool -> Monitoring & triage (Datadog, Trace)

Detailed pipeline stages and examples
------------------------------------
1) Source checkout and integrity verification
   - Verify commit provenance via signed commits (CLA bot + required GPG/SSH signature check).
   - Pull required submodules via pinned SHAs.

2) Build + remote cache restore
   - Use our hermetic build tool (redwood-build) which supports remote cache with object hash keys.
   - Remote cache backend: GCS bucket with uniform bucket-level access and IAM binding to ci-cache-service-account.
   - Example redwood-build flags: --cache-remote=gs://redwood-ci-cache/eval --cache-mode=restore,store --hash-algo=sha256

3) Image assembly and signing
   - Build image layers deterministically. Produce a content-addressable digest e.g. sha256:...
   - Sign the image with Cosign using the CI KMS-backed key. Cosign command example:

   cosign sign --key kms://projects/redwood/locations/global/keyRings/ci/cryptoKeys/ci-signing-key \\n     gcr.io/redwood/eval-runner:sha256-<digest>

4) Push to registry and store provenance
   - Push to the registry with immutable tags (digest pinned) and store the provenance file in the build metadata bucket.

5) Canary eval on GPU pool (gated)
   - Create ephemeral GPU job (namespace: ci-canary-evals/<build-id>) with resource requests matching production tail latency profile.
   - Canary scope: 5% of daily traffic-equivalent load for 10 minutes, run core eval prompt-set (partial) and performance probes.
   - Failure criteria (auto-fail): accuracy regressions > 0.5% absolute on critical evals, 95th P90 latency increase > 30%, OOMs or kernel panics.

6) Rollout decision and automated notes
   - If canary passes, the pipeline creates a signed rollout artifact and triggers the rollout job in staging/dedicated. If it fails, create an automated ticket in the infra-triage board with logs and suggested rollback.

Secure secrets and credential handling
-------------------------------------
- Short-lived credentials: use Vault AppRole with TTL 10m for ephemeral runners; runners exchange service account tokens for access.
- No secrets in logs: runner step wrapper redacts matching patterns; storage client uses token-only auth.
- Registry pushes: use cosign w/ KMS-backed key rather than storing private key in CI.
- Example Vault step (CLI):

  VAULT_TOKEN=$(vault write -field=token auth/approle/login role_id=$ROLE_ID secret_id=$SECRET_ID)
  export GCR_TOKEN=$(vault kv get -field=gcr-token ci/docker-push)

Remote cache hygiene and retention
---------------------------------
- Cache namespace per repo: prefix cache keys with repo name + commit hash to avoid cross-pollination.
- TTL policy: keep cache entries for 90 days; periodic compacting job prunes unused entries older than 30 days.
- Integrity: store a small manifest with each cache object that includes input hash, builder version, and provenance. CI verifies builder version match before reuse.

Security hardening checklist for runners
---------------------------------------
- Runners run in isolated k8s namespaces with PodSecurityPolicies / OPA gate: no hostPath, no privileged, allowGPU=false only for control-plane jobs.
- GPU-eval runners inherit minimum IAM scopes; escalate via short-lived role binding.
- Image vulnerability scanning must pass (no critical CVEs) before signing.
- Resource caps: memory and GPU limits to prevent noisy neighbor OOMs.

Canary eval gating rules (automation)
------------------------------------
1) Run canary job.
2) Collect metrics: eval-accuracy, p50/p95 latency, GPU-util, mem-faults, kernel panics.
3) Apply thresholds (configurable per-model):
   - accuracy_regression_abs_threshold: 0.005
   - latency_relative_threshold_p95: 0.30
   - fatal_error_rate_threshold: 0.01
4) If any threshold breaches, mark canary as FAILED and create incident ticket.

Rollout / rollback playbook (operational steps)
------------------------------------------------
1) If canary passes, trigger rolling update to staging/dedicated using the signed image digest. Monitor metrics for 60 minutes.
2) If staging shows degradation, immediately roll back to previous signed digest and notify owners via #infra-deploys.
3) Post-mortem: owner creates a short incident note in confluence with root cause analysis within 72 hours.

Failure modes and runbook actions
--------------------------------
- Remote cache put failure: fallback to local build; mark cache backend as degraded and page infra-ci on-call.
- Cosign signing failure: block push; if KMS unreachable, fail fast and escalate to key-ops.
- Canary OOMs: capture GPU traces (nsys) and a core dump; quarantine the image and rollback.
- Latency regression: capture end-to-end traces and profile kernel times; if persistent, revert and assign to model-eval owner.

SLOs and alerting
------------------
- CI success rate (green-to-signed) must be >= 98% for non-experimental branches.
- Median pipeline time for incremental eval runs < 15 minutes.
- Pager threshold: > 5 failing canaries in 1 hour -> page infra-sre on-call.

Observability and dashboards
---------------------------
- Build dashboard: queue time, cache hit ratio, average build time by repo.
- Canary dashboard: pass rate, latency delta, GPU error rates.
- Security dashboard: signing failures, Vault auth failures, scanned CVE counts.

Troubleshooting checklist (quick)
--------------------------------
1) Confirm Vault/role_id/secret_id rotation status.
2) Validate remote cache IAM and bucket permissions.
3) Check cosign/KMS availability and permissions.
4) Reproduce locally with --cache-mode=restore to debug missing cache entries.
5) Retrieve canary logs from namespace ci-canary-evals/<build-id> and attach to ticket.

Appendix A: Example GitHub Actions snippet
-----------------------------------------
name: GPU Eval Canary
on: [workflow_dispatch, push]
jobs:
  build-and-canary:
    runs-on: ubuntu-22.04
    steps:
      - uses: actions/checkout@v4
      - name: Restore remote cache
        run: redwood-build --cache-remote=gs://redwood-ci-cache/eval --cache-mode=restore
      - name: Build and sign image
        run: |
          redwood-build --target=eval-runner --cache-remote=gs://redwood-ci-cache/eval --cache-mode=restore,store
          cosign sign --key kms://projects/redwood/locations/global/keyRings/ci/cryptoKeys/ci-signing-key gcr.io/redwood/eval-runner:${{ github.sha }}
      - name: Trigger GPU canary
        run: redwood-deploy canary --image gcr.io/redwood/eval-runner:${{ github.sha }} --pool ci-gpu-pool --timeout 10m
