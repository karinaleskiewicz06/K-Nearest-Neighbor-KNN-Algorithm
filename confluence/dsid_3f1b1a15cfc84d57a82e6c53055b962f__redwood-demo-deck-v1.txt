Redwood Demo Deck v1 — Canonical Outline (AE/SE)

h1. Redwood Demo Deck v1 — Canonical Outline (AE/SE)

This page is the canonical *slide-by-slide* outline for the standard Redwood Inference sales demo deck (v1). It is designed to be run consistently by any AE/SE pair using the demo tenant.

*Goals*
* Deliver a repeatable story: why now → what breaks in production → how Redwood fixes it → proof via live demo → path to evaluation/POC.
* Provide modular paths for: (a) PLG/hosted-first, (b) Dedicated capacity / predictable throughput, (c) Private/VPC + security reviewer.
* Ensure resiliency: each live segment has a defined *backup mode* (screenshot/recording/canned output).

*Audience*
* Primary: Engineering leaders, platform teams, ML engineers, application engineers.
* Secondary: Security reviewer, procurement.

*Runtime*
* Standard: 30 minutes total (18–22 slides + 8–12 minutes live demo)
* Variants: 20-minute exec skim; 45-minute technical deep dive

----

h2. How to use this outline

*Owner of flow*
* AE: business context, discovery framing, outcomes, next steps.
* SE: product mechanics, live demo execution, technical objections.

*Deck rules*
* Use *synthetic demo data only* (no customer prompts/logs/screens).
* Avoid hard-coding competitor claims; use the approved objection sheet.
* Performance numbers shown must be from the approved “safe-to-share” set; add caveats.

*Backup mode policy*
* If any live step becomes brittle (quota, auth, empty dashboards, model drift), switch to the appendix backup screenshots and continue narrative.

h2. Slide-by-slide outline (v1)

h3. 0. Title / Agenda (0:30)
*Slide title:* “Redwood Inference — Production-grade LLM inference across hosted, dedicated, and private deployments”
*What you say (AE):*
* “We’ll show you a live, production-like environment—not a toy demo.”
* “We’ll cover: what breaks in real inference, how Redwood serves reliably, and the economics levers you can control.”
*What to confirm:* target deployment mode (hosted vs dedicated vs private) and primary metric (latency, cost, reliability, security).

h3. 1. The shift: model capability is not the bottleneck (1:00)
*Slide title:* “The hard part moved from ‘which model’ to ‘serving’”
*Key bullets:*
* Latency variability and tail p99s
* Unit cost per token and unpredictable spend
* Reliability under real traffic (bursts, retries, long contexts)
* Operational overhead (rollouts, observability, eval regressions)
*Speaker note:* keep this non-controversial; align to their pain.

h3. 2. Common failure modes we see in production (1:00)
*Slide title:* “Where LLM features fail in production”
*Bullets (tell as a story):*
* “The model is up, but the app is down” (throttles, timeouts, streaming disconnect)
* Silent quality regressions after model changes
* Noisy neighbor / shared capacity unpredictability
* Dashboards don’t answer: where did cost/latency come from?

h3. 3. What teams want instead (0:45)
*Slide title:* “Predictable performance, controllable economics, and operational safety”
*Bullets:*
* Predictable throughput and latency targets
* Levers to trade off cost vs latency without replatforming
* Rollouts + fallbacks built-in (graceful degradation)
* Observability at token, request, and route levels

h3. 4. Redwood in one slide (0:45)
*Slide title:* “Redwood Inference: unified inference platform”
*3 product pillars (icon row):*
* High-throughput serving runtime
* Control plane for routing/rollouts/pinning
* Console for cost/latency/quality observability
*Deployment modes (footer):* Hosted API • Dedicated Capacity • Private (VPC/on-prem)

h3. 5. Why Redwood (differentiators) (1:30)
*Slide title:* “Developer-first + production economics”
*Bullets:*
* *Production economics:* batching/caching/quantization-friendly execution + clear metrics
* *Reliability:* policy routing + controlled fallbacks when capacity/model shifts happen
* *Unified operations:* same interface across hosted/dedicated/private
* *Prevent regressions:* prompt sets/evals tied to rollouts

h3. 6. What we’ll demo today (0:30)
*Slide title:* “Live demo modules (we’ll tailor based on your priorities)”
*Modules (checklist):*
1) Core API: streaming + structured output + tool calling
2) Economics: batching/caching + token-level breakdown
3) Reliability: fallback routing + graceful degradation
4) Observability: dashboards, traces, rollout view
*Speaker note:* pick 2–3 modules for 30-min; all 4 for 45-min.

h2. Live demo section A — Core API (SE-led)

h3. 7. Core API: developer workflow overview (0:45)
*Slide title:* “From prototype to production: same API, production controls”
*Bullets:*
* Simple API/SDK calls
* Streaming responses
* Structured outputs (JSON schema) to reduce parsing failures
* Tool calling / function routing
* Retries and timeouts that behave predictably

h3. 8. Live step: streaming chat completion (2:00)
*Slide title:* “Live: streaming + retries (realistic app behavior)”
*Live steps (SE):*
1) Open demo app “Chat + tools” (demo tenant)
2) Run a prompt that streams a response
3) Simulate a retry (client-side) and show consistent behavior
*What to narrate:*
* “This is the same path you run in production—no special demo endpoint.”
*Backup mode:* show recording or screenshot of streaming UI + sample response.

h3. 9. Live step: structured output (2:00)
*Slide title:* “Live: structured outputs for reliable integration”
*Live steps:*
1) Switch to “Extract entities / ticket triage” prompt
2) Show JSON-schema constrained output
3) Point out schema validation + reduced post-processing
*Tie back:* “This cuts failure handling and re-tries, which directly affects tail latency and cost.”
*Backup mode:* screenshot of schema + valid JSON output.

h3. 10. Live step: tool calling (2:00)
*Slide title:* “Live: tool calling with guardrails”
*Live steps:*
1) Trigger a tool call (e.g., “lookup policy / calculate refund”) using synthetic tool
2) Show tool input/output + final answer
3) Highlight: “tools are logged and traceable” (bridge to observability)
*Backup mode:* canned tool call trace.

----

h2. Live demo section B — Production economics (SE-led, AE reinforces ROI)

h3. 11. Economics framing (0:45)
*Slide title:* “Unit economics: cost per outcome, not cost per token”
*Bullets:*
* Latency–cost tradeoffs are controllable (not mysterious)
* Token-level breakdown: prompt vs completion, cache hits, batch efficiency
* Measure before/after with the same workload

h3. 12. Live step: toggle batching/caching policies (2:00)
*Slide title:* “Live: tune batching/caching and see impact”
*Live steps:*
1) Open route settings (demo tenant) for a known route
2) Toggle: batching policy preset (e.g., “balanced” → “throughput”) and cache setting
3) Re-run the same prompt set workload (synthetic)
4) Show before/after: cost per 1K tokens and p50/p95 latency
*What to narrate:*
* “These are production levers with guardrails, not a rewrite.”
*Backup mode:* pre-captured Console comparison view.

h3. 13. ROI slide (AE-led) (1:30)
*Slide title:* “What teams typically get: lower cost + fewer incidents”
*Approved framing (avoid absolute promises):*
* “Lower unit cost through better batching/caching defaults and visibility”
* “Fewer ‘black box’ incidents because you can see where time and spend go”
* “Faster iteration because rollouts and fallbacks are first-class”
*Speaker note:* If asked for numbers, use the approved benchmark appendix and caveats.

----

h2. Live demo section C — Reliability (SE-led)

h3. 14. Reliability framing (0:45)
*Slide title:* “Keeping the app online when models/capacity change”
*Bullets:*
* Model/version pinning for stability
* Policy routing (region, latency target, cost)
* Controlled fallback to compatible variants
* Graceful degradation: “degrade quality slightly before you go down”

h3. 15. Live step: fallback routing demo (2:30)
*Slide title:* “Live: controlled fallback (no fire drills)”
*Live steps:*
1) Show route config: primary model pinned + allowed fallback family/regions
2) Trigger a simulated primary unavailability (demo control)
3) Re-run request and show automatic fallback + logged event
4) Show that client contract remains stable (schema/tool calling still works)
*Backup mode:* recorded clip of fallback event + route config screenshot.

----

h2. Live demo section D — Observability + operations (SE-led)

h3. 16. Observability overview (0:45)
*Slide title:* “Console: from request to token to route”
*Bullets:*
* Token-level cost/latency breakdown
* Route dashboards and error analysis
* Tracing hooks for app integration
* Rollouts view: canary + A/B with safety

h3. 17. Live step: dashboard tour (2:00)
*Slide title:* “Live: cost + latency + errors in one view”
*Live steps:*
1) Open project dashboard (demo tenant) with seeded traffic
2) Show charts: volume, cost, latency percentiles, error rate
3) Click into a route and show breakdown
*Pitfall to avoid:* empty graphs. If empty: run synthetic traffic job or switch to backup screenshots.

h3. 18. Live step: rollout view (optional) (1:30)
*Slide title:* “Live: canary rollout with automatic guardrails”
*Live steps:*
1) Show canary split (e.g., 90/10)
2) Show quality/latency gates and automatic fallback policy
3) Tie to “no surprise model changes” story
*Backup mode:* annotated screenshots (Design pack).

h2. Close — next steps and evaluation path

h3. 19. Deployment options (AE-led, SE supports) (1:30)
*Slide title:* “Choose your deployment: hosted, dedicated, private”
*Table (talk track):*
* Hosted API: fastest start, usage-based
* Dedicated: predictable throughput, isolation, SLA targets
* Private (VPC/on-prem): regulated workloads, customer-managed networking + KMS options
*Speaker note:* Keep Private discussion architecture-level unless the audience is a security reviewer.

h3. 20. Security & trust (optional slide; otherwise appendix) (1:30)
*Slide title:* “Security controls teams ask for”
*Bullets (short, non-legal):*
* SSO/SAML, RBAC
* Audit logs and access history
* Encryption + key management integrations (KMS/HSM where applicable)
* Retention controls and residency options (per deployment mode)
*CTA:* “We can share the full security FAQ and set up a dedicated review.”

h3. 21. Evaluation plan (1:30)
*Slide title:* “A fast, low-risk way to validate”
*Bullets:*
* 1–2 priority use cases
* Success metrics: latency p95/p99, unit cost, quality on prompt set
* Timeline: setup → run traffic/evals → review results
* What Redwood provides: sample code, prompt set harness, routing recommendations

h3. 22. Q&A / Objection parking lot (remaining time)
*Slide title:* “Questions we usually get”
*Prompts:*
* “What do you need to see to feel confident moving to a technical evaluation?”
* “Is your primary concern cost, reliability, or security/compliance?”
*Reference:* link to competitive objections cheat sheet.

h2. Speaker notes: “Do / Don’t”

*Do*
* Tie each feature to a production outcome (latency, cost, reliability, security posture).
* Ask one discovery question before the live demo modules to select the right path.
* Use the Console to *show* the cost/latency story (not just claim it).

*Don’t*
* Don’t promise specific percent improvements without context.
* Don’t present Dedicated/Private terms in a way that implies a feature exists in the demo tenant if it doesn’t; use the narrative + appendix architecture.
* Don’t live-debug in front of the customer; switch to backup mode.
