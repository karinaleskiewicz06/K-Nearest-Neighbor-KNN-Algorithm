GPU Thermal and Power Management Guidelines

Summary

This page documents Redwood Inference's operating guidance for GPU thermal and power behaviour across our fleet (hosted, dedicated, private). It defines metrics, alert thresholds, automated mitigations, IaC snippets, and a runbook for thermal incidents. Goal: maintain reliability and model latency SLOs while protecting hardware and minimizing customer impact.

Scope

- Applies to all GPU capacity pools managed by eng-infra: inference-pool-1, inference-pool-2, eval-pool, and onprem-customer clusters.
- Covers chassis-level and GPU-level thermal events, power capping, fan controls, driver/firmware interactions, and scheduler mitigations.
- Excludes datacenter-level HVAC controls (coordinate with Facilities).

Background and motivation

GPUs are optimized for high sustained throughput but can suffer performance throttling when temperatures or power draw exceed safe operating regions. Left unmanaged, thermal events cause:
- sustained clock downclocking and reduced throughput,
- increased token latency and tail latency regressions,
- potential long-term hardware degradation.

We balance three constraints: hardware safety, user-facing latency SLOs (P95 generation latency), and cost (avoid unnecessary preemptions or migrations).

Key metrics and sources

- DCGM and NVML metrics (ingested via node-exporter-dcgmi and dcgm-exporter):
  - dcgm_gpu_temp (C)
  - dcgm_gpu_power_draw (W)
  - dcgm_gpu_power_limit (W)
  - dcgm_gpu_clocks_sm (MHz)
  - dcgm_gpu_fb_usage_bytes
  - node_gpu_fan_speed_pct

- Prometheus / Grafana queries used in alerts:
  - High temp (instance-level): avg_over_time(dcgm_gpu_temp{job="dcgm"}[5m]) > 85
  - Sustained high power: avg_over_time(dcgm_gpu_power_draw{job="dcgm"}[10m]) > 0.95 * dcgm_gpu_power_limit
  - Clock throttling detection: increase(dcgm_gpu_clocks_sm[5m]) < expected_baseline

SLOs and objectives

- Hardware safety: No GPU should exceed 95C. Immediate protective action at >= 95C.
- Fleet health: Less than 0.5% of GPU-time with temperature > 90C in a given week.
- Performance: For inference-pool-1, P95 generation latency should not degrade by more than 20% during automated thermal mitigations relative to baseline.

Thresholds and automated actions (ordered by severity)

1) Warning (proactive): temp > 80C for 10 minutes
   - Alert: Pg: #infra-gpu-thermal (page), Slack: #infra-alerts. Severity: P3.
   - Action: increase fan target to +10% (via daemonset command to thermald/fan-controller). Add to shading policy: temporarily prefer scheduling lower-batch jobs to this node.

2) Elevated (mitigating): temp > 86C for 5 minutes OR sustained power draw > 95% of limit for 10m
   - Alert: P2, page on-call SRE.
   - Action: automatically apply software power cap to 95% of current limit via nvidia-smi/dcgmi. Reduce max batch size via runtime config service (see "runtime-throttle" route). Mark node as 'soft-drain' in scheduler for non-latency-critical queues.

3) Critical (protect): temp >= 95C OR clocks throttled for > 30s
   - Alert: P1 incident, pager to hardware-ops + oncall.
   - Action: cordon node, migrate critical jobs with eviction policy "thermal-evict-priority", offload remaining workloads to fallback model variants in other pools (auto-routing). Queue a hardware maintenance ticket.

Implementation details: how mitigation is performed

- Detection: Prometheus rules evaluate the queries above. Alertmanager routes to Slack + PagerDuty with runbook link.
- Fan & power control: we run a privileged DaemonSet (gpu-power-agent) that uses NVML/DCGM and vendor tooling. The agent exposes a gRPC endpoint (localhost:50051) that accepts control requests from the control plane.
- Scheduler integration: the k8s-gpu-scheduler component listens to node annotations from gpu-power-agent and adjusts pod placement by applying "soft-drain" taints and lower priority to batch workloads.
- Runtime throttling: the serving runtime exposes a /v1/admin/scale endpoint to reduce batch/parallelism per node. The autoscaler calls this endpoint when the agent requests throttling.

Terraform / IaC example (snippet)

This example shows the module we use to deploy the gpu-power-agent DaemonSet and node-exporter-dcgm with provider variables. Use in your tenant module: 

```terraform
module "gpu_power_agent" {
  source = "git::ssh://git@github.com/redwood-inference/infra-modules.git//k8s/gpu-power-agent?ref=v0.7.2"
  cluster_name = var.cluster_name
  namespace = "infra-system"
  tolerations = ["system:gpu"]
  rbac_enabled = true
}

resource "kubernetes_manifest" "gpu_agent_config" {
  manifest = yamldecode(templatefile("${path.module}/agent-config.tpl", { power_limit_w = 300 }))
}
```

CI/CD deployment pattern

- All changes to the gpu-power-agent or its Helm chart must go through the gpu-infra CI pipeline: .github/workflows/gpu-agent-release.yml.
- Steps: unit tests -> integration test in ephemeral cluster (ephemeral-gpu-preview) -> canary to 3 nodes in inference-pool-1 -> full rollout with 10-minute health checks (Prometheus-based).
- Rollback: if temperature or P95 latency regressions exceed thresholds during canary, rollback automatically and open PR that blocks release until manual review.

Monitoring and dashboards

- Dashboards:
  - Fleet Overview: avg_temp_by_pool, percent_over_80c_by_pool, avg_power_draw
  - Node Detail: gpu_temp_time_series, fan_speed, power_limit_history, clock_states (with events)
- PromQL examples included in dashboard JSON (stored in infra/grafana/dashboards/gpu-thermal.json). Query example:
  - percent_over_80c_by_pool = sum(rate(dcgm_gpu_temp > 80)[5m]) / count(dcgm_gpu_temp) * 100

Runbook: incident workflow for critical thermal events

1) Detection and initial triage
   - PagerDuty alert fires (P1). Oncall acknowledges in < 2m.
   - Triage: confirm metric history in Node Detail dashboard, check recent firmware/drivers changes (audit trail: infra-ci build id in node labels).

2) Immediate mitigations (first 10 minutes)
   - Execute automated steps from agent: power cap, fan ramp, soft-drain.
   - If critical jobs are impacted, perform live migration to fallback pool (control-plane command):
     kubectl label node <node> thermal-isolated=true && /opt/infra/bin/migrate-workloads --node <node> --policy thermal-evict-priority

3) Hardware escalation (10-60 minutes)
   - If temp remains >=95C or clocks still throttled: cordon and schedule hardware-inspection. Open hardware ticket: HW-EXC-<cluster>-<node> with the following payload: node id, last 24h temp trace, driver version, firmware, rack power feed.

4) Post-incident actions (within 48h)
   - Root cause analysis (RCA) within 72h. Include: metrics timeline, CI deploys correlated, ventilation/facilities checks, and remediation plan.
   - If firmware or driver upgrade was a contributor, prepare staged rollout with canary nodes.

  - nvidia-smi --query-gpu=index,temperature.gpu,power.draw,clocks.sm --format=csv -l 5
  - dcgmi dmon -e 1000 -o dmon.csv

- Example agent debug: curl -s http://localhost:50051/metrics | grep power

- Ticket template (copy to hardware ticket):
  - Summary: GPU critical thermal event on <node>
  - Time window: <start> - <end>
  - Metrics: attach Prometheus chart links and dcgm-exporter CSV
  - Actions taken: list of automated mitigations and manual steps

Notes and rationale

We prefer soft mitigations (power cap + throttling) before cordoning to reduce customer impact. Power capping is reversible and maintains availability for latency-sensitive workloads while protecting hardware. Fully cordoning/evicting nodes is reserved for critical thresholds.

If you are planning a change that touches power management or thermal thresholds, add a note to #infra-change-requests and link the PR to this page.
