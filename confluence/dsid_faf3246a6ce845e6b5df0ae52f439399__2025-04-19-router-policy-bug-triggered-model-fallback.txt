Postmortem: Router policy regression triggered unintended model fallback (2025-04-19)

h2. Summary
On 2025-04-19, a router policy change caused the system to activate *automatic model fallback* more aggressively than intended for several chat routes. While this reduced errors, it also introduced a quality regression for some customers because the fallback target had different instruction-following behavior.

h2. Impact
* Increased fallback usage on chat routes (primary -> smaller model) for ~52 minutes.
* Some customers reported degraded response quality and formatting differences.
* No prolonged outage; error rate remained below 1.0% due to fallback.

h2. Timeline (UTC)
* 20:05: Router policy v2025.04.19-1 deployed.
* 20:12: Metrics show a spike in fallback_activated_count on chat-default.
* 20:17: Support ticket indicates response quality changes.
* 20:26: On-call reverted router policy to previous version.
* 20:31: Fallback usage returns to baseline.
* 20:57: Follow-up: validate that quality guardrails did not alert because the canary prompts did not cover the affected format.

h2. Root cause
A boolean default in the policy compiler changed from "fail-open" to "fail-closed" for an optional constraint, causing the router to deem the primary model "ineligible" and immediately trigger fallback for certain request shapes.

h2. Mitigation
* Reverted policy deployment.
* Temporarily disabled auto-fallback for enterprise routes with strict quality requirements while we validated the policy fix.

h2. Action items
1) Add a routing policy unit test suite covering eligibility constraints and fallback triggers. Owner: Eng Platform.
2) Expand eval harness prompts to include structured output format checks for top customers. Owner: Applied ML.
3) Add a canary alert when fallback usage deviates > 3x baseline for any route. Owner: Eng SRE.
