Model-aware egress & SLO routing — Terraform adapter + CI/CD gating

Overview

This doc describes the design and implementation guidance for a Model-aware Egress & SLO Routing Terraform adapter plus CI/CD gating patterns. The adapter enforces per-model network and egress shaping policy at provisioning time and wires those policies into runtime SLO routing rules used by the inference traffic router. Goals: reduce costly cross-region egress surprises, enable model-specific latency/cost routing, and provide safe rollout that ties infra changes to model-level canaries.

Why this exists

- Customers run a mix of open & fine-tuned models with different SLOs and egress footprints; a one-size network config leads to overprovisioning or surprises in billing.
- Existing egress docs focus on account-level quotas or proxy failover. We need a pattern that: (a) expresses model-level egress intent, (b) materializes network primitives via IaC, and (c) connects deploy-time assertions to CI/CD canaries.

Scope and non-goals

Scope
- Terraform module interface and recommended variables for attaching model metadata to tenant/network configs.
- CD gating and canary tests that validate routing + egress shaping in staging before production promotion.
- Runbook for common incidents (egress surge, mis-routed model, SLO regressions).

Non-goals
- Replacing runtime model router implementation. The runtime remains responsible for per-request routing decisions. This adapter only manages provisioning and assertion signals.
- Detailed billing exports or invoicing logic (handled by finance hooks).

High-level design

1) Model intent declaration: teams register a model deployment with attributes: model_id, criticality (P0..P3), expected_egress_MB_per_1e6_tokens, preferred_region_list, latency_slo_ms. This lives as a Terraform variable (or a small JSON blob referenced by the module).

2) Terraform adapter responsibilities:
- Create per-tenant egress-shaper resources (rate-limiting proxies, proxy-ingress rules, and egress nat/egress-gateway ACLs where supported).
- Label VPC/subnet route tables and grant IAM roles so the runtime can read allowed egress buckets for each model.
- Emit assertions (policy artifacts) to the deployment pipeline artifact store so the CD can run integration checks against them.

3) CI/CD gating: the pipeline deploys the module into a staging environment, runs synthetic traffic through the runtime with model-specific workloads, verifies measured egress + routing adherence, and checks latency SLOs. If checks pass, promote to prod with a gradual canary (percent-based routing).

Module API (recommended variables and outputs)

Below is a reference table for module inputs and outputs. Implementations may extend but must keep these names for CD assertion tooling.

| Variable (name) | Type | Required | Description | Default |
|-----------------|------|----------|-------------|---------|
| model_declarations | string (JSON) | yes | JSON list of model objects (model_id, criticality, expected_egress_mb_per_1e6, preferred_regions, latency_slo_ms) | none |
| tenant_id | string | yes | Tenant account/namespace the resources will be provisioned into | none |
| egress_gateway_profile | string | no | Name of the pre-defined egress gateway profile (e.g., low-cost, balanced, low-latency) | "balanced" |
| per_model_nat_pool | bool | no | If true, allocate dedicated NAT/egress IP pools per model for tracing and billing | false |
| restrict_to_vpcs | list(string) | no | VPCs/subnets to apply the rules to; if empty, apply to tenant default vpc | [] |

Outputs:
- policy_artifact_uri (string): S3/GCS/Artifact URL containing canonical policy JSON emitted by the module.
- shard_egress_resource_ids (list): resource IDs for per-model egress proxies or K8s NetworkPolicy names.

Example model_declarations JSON (inline):
{"models":[{"model_id":"gpt-1b-ft-v2","criticality":"P1","expected_egress_mb_per_1e6": 120,"preferred_regions":["us-west-2"],"latency_slo_ms": 80},{"model_id":"open-7b","criticality":"P3","expected_egress_mb_per_1e6": 20,"preferred_regions":["us-east-1","us-west-2"],"latency_slo_ms": 250}] }

Terraform snippet (usage):

module "model_egress_adapter" {
  source = "git::ssh://git@github.com/redwood-infra/terraform-modules.git//model-aware-egress-adapter"

  tenant_id = var.tenant_id
  model_declarations = file("./model-decs.json")
  egress_gateway_profile = "balanced"
  per_model_nat_pool = true
}

CD / Pipeline integration pattern

We recommend a 3-stage pipeline (staging -> canary -> prod). At each stage the pipeline performs the listed checks:

1) Staging (apply module into tenant-staging account)
- terraform apply (plan + apply with drift detection)
- fetch policy_artifact_uri and validate JSON schema (tool: rjson-validate)
- run synthetic load harness (locally-run or in-cluster pod) for each declared model:
  a) Generate realistic token distribution for the declared model.
  b) Measure egress bytes, outbound IPs used, and per-request latency.
  c) Assert egress within +/-20% of expected_egress_mb_per_1e6 and latency <= latency_slo_ms * 1.3 for staging.
- Run negative tests: attempt to route traffic to a non-declared external host and verify the egress gateway blocks it.

2) Canary (percent-based production split)
- Gradually shift 5% -> 25% -> 50% depending on success criteria.
- At each step run the same checks as staging but with tighter thresholds: egress within +/-10% and latency <= latency_slo_ms * 1.15.

3) Prod (full rollout)
- Final promote step when canary windows are clean for 72 hours and no billing anomalies in finance dashboard.

CI pipeline YAML fragment (example):

steps:
  - name: terraform-plan
    run: terragrunt plan --terragrunt-non-interactive
  - name: terraform-apply-staging
    run: terragrunt apply -auto-approve
  - name: validate-policy-artifact
    run: rjson-validate $(cat policy_artifact_uri) schemas/model-egress-schema.json
  - name: run-synthetic-harness
    run: ./scripts/run_model_harness.sh --artifact $(cat policy_artifact_uri) --timeout 30m
  - name: assert-results
    run: ./scripts/assert_harness_results.py --thresholds thresholds/canary.yaml

Runbook: common incidents and playbook

1) Symptom: sudden spike in egress for a model (billing alert + egress metric)
- Pager path: oncall-network -> if no ack in 15m escalate to infra-lead.
- Immediate mitigation: toggle per_model_nat_pool = false on the adapter for offending model (works if NAT pools were used), or push a temporary iptables drop at egress gateway to throttle.
- Diagnostic commands:
  - curl -s $EGRESS_GATEWAY/metrics | grep model_id
  - aws cloudwatch get-metric-statistics --metric-name NetworkBytesOut --dimensions Name=InstanceId,Value=$INSTANCE --start-time ...
- Remediation: identify root cause (model misconfiguration or traffic storm), roll back the change that caused churn, enforce quota at runtime if necessary.

2) Symptom: model traffic routed to wrong region causing increased latency
- Check policy_artifact_uri to confirm preferred_regions.
- Validate routing table labels and Runtime policy cache (requests to /runtime/policy/{model_id}).
- Rollback: promote a routing override that pins model to preferred_regions until infra changes are reconciled.

3) Symptom: Canary fails latency checks repeatedly
- Abort promotion, revert traffic split to previous stable, and open a regression ticket with research/serving-runtime.
- Collect traces: grpc/tcp p95 p99, per-token time, and check KV cache hit rates.

Metrics, dashboards and SLOs to create

- Per-model Egress MB / 1e6 tokens (derived metric) — alert: > expected_egress * 1.5 for 10m.
- Per-model p95 latency — alert: > latency_slo_ms * 1.5 for 5m.
- Egress gateway error rate (5xx) — alert: > 3% for 5m.
- Unmapped-model egress attempts (blocked requests) — paging severity if > 100 events / 1h.

Security, IAM and least privilege

- Terraform IAM roles provisioned by module must be scoped to: read model policy artifacts from the specific artifact bucket, manage egress gateway config for the tenant only, and not list other tenants.
- Use KMS-wrapped secrets for any NAT pool credentials.
- Audit logs: enforce CloudTrail/Stackdriver logging for nat/egress-gateway modify events and ship logs to a central, immutable bucket with retention 1 year.

Rollout checklist

1) Implementation readiness
- Module has unit tests (tfunit) and integration test harness that runs in isolated staging account.
- Schema validation for model_declarations added to pipeline.

2) Canary plan
- Choose three low-risk models and a non-critical tenant for the first canary wave.
- Run traffic for 48 hours and ensure metrics are stable.

3) Stakeholder signoffs
- SRE (network), Serving-Runtime, Product (model-owner), Finance represented.

Testing matrix

- Dimension: model criticality (P0..P3), expected_egress band (low/medium/high), topology (single-region, multi-region), nat pool enabled (yes/no).
- Run combinations in staging and record pass/fail for egress and latency checks.

Implementation notes and constraints

- Not all clouds support per-subnet NAT pools; module will emulate via dedicated gateway EC2/VM pools where necessary.
- IP address exhaustion: avoid allocating per-model public IPs unless absolutely needed; prefer shared egress with tag-based accounting.
- Runtime must be augmented to read policy_artifact_uri at startup and reconcile local routing cache every 5 minutes.

Open items

- Automated finance anomaly detection integration (PO: finance) — who will own the final alert thresholds?
- Long-term: expose a telemetry endpoint that maps tokenization characteristics to egress predictions and allow the adapter to auto-suggest expected_egress fields.

Appendix: developer tools and helpers

- ./scripts/run_model_harness.sh: harness that emits realistic token timing, collects egress bytes and latency, and uploads results to artifact store.
- schemas/model-egress-schema.json: canonical schema for model_declarations used by rjson-validate.
- thresholds/canary.yaml: example threshold set for canary pipeline.
