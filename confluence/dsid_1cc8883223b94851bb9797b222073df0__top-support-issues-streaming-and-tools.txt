Top Support Issues: Streaming + Tool Calling + Structured Output (Synthesis and Example Fixes)

## Purpose
This page synthesizes recurring support issues we’ve seen across streaming responses, tool calling (including streaming tool calls), and structured output (JSON schema / “schema-constrained” output). It also documents the canonical guidance that the refreshed SDK/docs/examples now implement, and links to the Jira tickets that motivated changes.

Scope: Hosted API + SDK examples (Python/TypeScript/Go). This is not a protocol redesign; it is “how to build reliably with the current semantics.”

## Executive summary (what’s causing tickets)
Across SUP tickets and Solutions Engineering notes, issues cluster into four buckets:
1) **Streaming consumer loops that assume “one event = one message”** (leading to dropped deltas, incomplete assembly, or treating a disconnect as a clean end-of-stream).
2) **Tool-call arguments that arrive incrementally** (arguments look truncated mid-stream; customers parse too early and fail).
3) **Structured output parsed before the model has finished emitting valid JSON** (JSON parse errors, especially under streaming).
4) **SDK parity mismatches / type mismatches** between examples and actual tool result shapes (mostly TS), leading to copy/paste failures.

The refreshed examples address these by:
- Standardizing event handling and final assembly across languages.
- Explicitly demonstrating incremental tool-call arg accumulation.
- Adding safe validation + retry patterns for structured output.
- Aligning types and tool-result message shapes with the current supported semantics.

## Top issues (recurring patterns)

### 1) Tool-call arguments appear truncated mid-stream (customers parse too early)
**Ticket(s):** SUP-18421-streaming-tool-call-args-truncated

**What customers reported**
- During streaming, the tool call is visible but the arguments string looks cut off (e.g., missing closing braces/quotes).
- Customers attempt to parse JSON as soon as they see a tool call “start,” resulting in JSON decode errors.

**Root cause (typical)**
- Tool call arguments are **delivered incrementally** as deltas. A single event may contain partial arguments.
- Some models emit arguments in multiple chunks; the stream may interleave content and tool-call deltas.

**Correct guidance (canonical)**
- Do not parse tool arguments until the tool call is complete.
- Accumulate deltas keyed by tool_call_id (or equivalent identifier) and parse only once:
  - The stream indicates the tool call is finished, OR
  - A “final response” event is received and the tool call arguments are complete.
- Treat any mid-stream arguments as **opaque strings** until you have the full buffer.

**How refreshed examples address it**
- All language examples now show a “tool call assembly buffer” (map/dict keyed by tool_call_id) and a step that parses after completion.
- Added “known pitfall” callout in tool-calling docs: parsing too early == truncated args symptom.
- Added golden transcript fixtures that include multi-chunk arguments.

**Support playbook notes (triage questions)**
- Ask for: SDK version, model name, whether streaming is enabled, and whether they parse args on the first tool event.
- If they are using OpenAI-compatible mode, confirm payload shape differences and point to the compatibility doc PR.

### 2) Streaming disconnects / incomplete final message assembly
**Ticket(s):** Seen repeatedly in support threads; also tracked via post-launch monitoring counters in monorepo PRs (stream_disconnect) and examples fixes.

**What customers reported**
- Streaming stops unexpectedly; app treats it as success and uses incomplete text.
- Some implementations only read the first few events; final message is missing.
- Customers assume a single “message” object is emitted, rather than incremental deltas.

**Root cause (typical)**
- Consumer loop does not:
  - Handle transient network disconnects.
  - Distinguish between partial deltas and final message.
  - Implement timeouts/backoff and an application-level retry strategy.

**Correct guidance (canonical)**
- Streaming should be treated as an **event sequence**; build the final message by assembling deltas.
- Always handle:
  - Disconnect before receiving a terminal event.
  - Server-sent error events.
  - Local timeout/cancellation.
- Recommended behavior:
  - If disconnect occurs mid-stream: retry with idempotency where possible, or re-request with reduced max_output_tokens.
  - Log a “stream ended without terminal event” error; do not treat as success.

**How refreshed examples address it**
- The streaming examples in Python/TS/Go now:
  - Use a single canonical event loop pattern.
  - Assemble “final content” from deltas.
  - Include explicit branches for error/timeout/disconnect.
  - Print clear logs that map to what Support asks for (event type, request id, tool_call_id).

**Support playbook notes (what to ask for / what to check)**
- Ask for request_id + timestamp + region.
- Ask whether the customer is reading the stream to completion.
- If they are behind a proxy, ask for idle timeout settings (common cause of mid-stream termination).

### 3) Structured output JSON parse errors (especially under streaming)
**Ticket(s):** SUP-18436-structured-output-json-parse-errors

**What customers reported**
- JSON parsing fails intermittently; they see trailing commas, partial objects, or non-JSON tokens.
- Failures are more common when using streaming and attempting to parse partial output.

**Root cause (typical)**
- Customers parse before the model completes valid JSON.
- Schema is too permissive or too complex; model drifts.
- Model family differences: not all models provide the same “schema-constrained” reliability.

**Correct guidance (canonical)**
- Prefer **non-streaming** for strictly validated structured output when latency budget allows.
- If streaming is required:
  - Buffer the emitted text and parse only once a terminal event is received.
  - Validate against a JSON Schema (or equivalent) and implement retry-on-validation-failure.
- Keep schemas small and explicit:
  - Use required fields, enums, min/max constraints.
  - Avoid deeply nested “anyOf/oneOf” unless necessary.

**How refreshed examples address it**
- Structured output examples now include:
  - A schema definition.
  - A validation step.
  - A failure mode that retries with a “repair” prompt or fallback behavior.
- Docs include an “incremental parsing caveat” section: don’t parse until complete under streaming.

**Support playbook notes**
- Ask for the schema and a redacted sample of the raw model output.
- Confirm whether the customer is using streaming.
- If schema is complex, recommend simplifying or switching to non-streaming for that call.

### 4) TypeScript tool calling example fails due to type mismatch / tool result shape
**Ticket(s):** SUP-18452-typescript-tool-calling-type-mismatch

**What customers reported**
- Copy/paste from docs fails to compile or throws runtime errors.
- Confusion about how to represent tool results in subsequent messages.

**Root cause (typical)**
- Example drift vs released SDK types.
- Ambiguity between “tool definition” shape and “tool result message” shape.

**Correct guidance (canonical)**
- Tool calling must follow the supported semantics:
  - Define tools with clear name + JSON schema parameters.
  - When the model requests a tool call, the client executes it.
  - Send a **tool result message** with:
    - tool_call_id
    - tool name
    - serialized result payload (string or JSON, depending on SDK)
- Treat tool results as data; do not embed additional assistant text in tool result messages.

**How refreshed examples address it**
- TS SDK updated types to reflect canonical tool result message shape.
- Docs updated to show the same shape and to avoid older snippet formats.
- Added a reviewer checklist item for “tool result type matches SDK release.”

### 5) Docs page code tabs / copy button issues hide the correct snippet
**Ticket(s):** INT-3321-docs-site-broken-code-tabs

**What customers reported**
- Code block tabs default to the wrong language or stop switching.
- Customers copy an outdated snippet without realizing it.

**Root cause (typical)**
- Front-end bug in docs code-tab selector.

**How refreshed docs address it**
- Docs PR fixes code-tab selector behavior and adds a lightweight regression test plan.
- Migration notes now include “verify code tab behavior” in publishing checklist.

## Known pitfalls (copy/paste callouts to include in customer replies)
Use these short bullets in support responses to reduce back-and-forth:
- **Tool args can be partial while streaming.** Don’t JSON.parse until the tool call is complete; buffer by tool_call_id.
- **Don’t parse streaming structured output mid-flight.** Buffer until the terminal event, then parse + validate.
- **Treat stream disconnect as failure unless you got a terminal event.** Retry or fall back to non-streaming.
- **Tool results must be sent back as tool-result messages** (not as assistant messages).
- **Check SDK versions**: older examples may not match the current tool-call / tool-result shapes.

## Recommended logging fields (what Support needs)
Ask customers to log the following (or provide to Support):
- request_id / trace_id
- model
- region
- streaming enabled (true/false)
- event types received (sequence)
- tool_call_id(s) and whether args were assembled across multiple events
- raw structured output text (redacted) prior to parsing
- SDK name and version

## Appendix: Customer response templates (short)
**Template A: “Tool args truncated”**
- “This is expected during streaming: tool call args are emitted as deltas. Please buffer args by tool_call_id and only parse after the tool call is complete (see updated examples). If you share your consumer loop, we can point out where it parses too early.”

**Template B: “Structured output parse errors”**
- “If you’re streaming, don’t parse JSON mid-stream. Buffer until the terminal event, then parse + validate against schema. If validation fails, retry with a repair prompt or fall back to non-streaming for that call.”

**Template C: “TS snippet doesn’t compile”**
- “Please confirm your redwood-sdk-typescript version. The updated tool result message shape is required; older snippet formats won’t typecheck. We can share the current canonical snippet for your version.”
