GPU CI dependency slimming and release stability playbook

Summary

This playbook describes a pragmatic, operational pattern for slimming CI/CD dependency graphs for GPU workloads and improving release stability for inference runtime changes. It combines build-time techniques (dependency pruning, delta-builds, content-addressable caching) with runtime release controls (canaries, staged rollout windows, flaky-test quarantine) and terraform/IaC contract checks to reduce CI latency, lower cost, and reduce release-induced regressions.

Goals
- Reduce median CI runtime for GPU-eval and runtime-integration pipelines by 30–50% without losing test coverage.
- Limit blast radius of runtime/kernel/orchestrator changes by enforcing staged rollouts, improved gating, and automated rollback.
- Provide clear triage and remediation runbook for CI-induced production regressions and infra flakiness.

Scope
- Applies to: GPU build and eval CI pipelines, e2e inference integration jobs, image promotion pipelines, and terraform modules used to provision GPU testbeds.
- Excludes: user-facing SDK unit tests (non-inference), low-cost CPU-only CI lanes.

High-level strategy
1) Dependency slimming: identify minimal graph of inputs required to validate a change and run only those shards.
   - Use change-file ownership mapping (CODEOWNERS-like) to map PRs to impacted integration shards (model, kernel, image, infra).
   - Build a fast static analyzer that inspects changed files and maps them to test shards via a YAML mapping table: {path_glob -> shards}.
2) Delta builds + content-addressable caches:
   - Use content-hash of source tree + toolchain -> cache key. Cache artifacts: wheel/tarball, container layers, kernel-build artifacts, quantized artifacts.
   - Promote cache hits to ephemeral registry/registry-snapshot for downstream jobs.
3) Parallel but prioritized scheduling:
   - Fast-preflight lane (unit tests, lint, small integration smoke) runs in <10m and gates PRs.
   - Full validation lanes (GPU-heavy) are scheduled with priority tokens and can be preempted for critical CI windows.
4) Release stability controls:
   - Canary windows: small percentage of traffic / small canary tenant pool hooked to new runtime image (config via rollout policy).
   - Canary SLOs: p99 latency, error-rate, per-tenant cost-per-token.

Detailed procedures
A. Author pre-merge flow (fast path)
1. Author opens PR. CI preflight triggers (unit tests, lint, build-sanity).
2. Static analyzer computes affected shards and annotates PR with expected CI lanes.
3. Fast-preflight lane must pass before any GPU job is scheduled.
4. If static analyzer or CODEOWNERS marks kernel/runtime changes, label PR with `runtime-impact`. This triggers additional IaC contract checks.

B. IaC contract checks (pre-merge)
- The TF contract test runs a dry-run plan against a synthetic sandbox account to verify network/egress changes do not violate tenant isolation policies.
- Contract failures must block the PR. The test emits: changed_resources.json (content-hash), impacted_subnets (list).

C. GPU-heavy validation lane (post-merge or gated pre-merge)
1. Use promoted cache snapshots for base images and kernel artifacts.
2. Run a minimal set of long-running tests first (smoke generation + kv-cache warmup) with strict timebox.
3. If minimal smoke fails, abort and notify author; do not proceed to full eval.
4. Full eval runs are queued; if queue time exceeds 30m, demote job priority and notify release manager.

D. Release gating and promotion
1. Image promotion flow: `build -> snapshot-registry -> staging -> canary -> production`. Each stage requires a sign-off from owner teams listed in `repository/MANIFEST/owners.yaml`.
2. Canary is automated: deploy to 5% of tenants or a dedicated canary tenancy. Monitor the canary for 24–48 hours before staged ramp.

Incident triage & rollback (oncall playbook)
1. Detection signals (any of): sudden p95/p99 latency jump >30%, 5xx increase >1% absolute, token-cost spike >20% vs baseline, or customer error reports.
2. Immediate mitigation steps:
   a. Pause rollout: flip rollout policy to route 100% traffic to previous image.
   b. If pause fails or cannot be toggled cleanly, fail open to a safe fallback model variant (lower-capacity but stable) using the smart routing fallback.
   c. If traffic is still degraded, trigger emergency image rollback to last known-good image (<2h target).
3. Post-rollback: collect artifacts (CI logs, kernel build logs, promoted-cache manifest, infra plan diff). Tag a postmortem ticket and attach artifacts.

Runbook checklist for CI flakiness (triage steps)
- Check the preflight static analyzer annotation for false-positives.
- Verify cache hit rate for recent builds (target: >60% for kernel artifacts).
- Inspect runner health: GPU driver version drift, CUDA mismatch, containerd or node disk pressure.
- If a pattern is detected across multiple PRs, open an RFC for changing static analyzer mapping.

Telemetry and alerting
- CI SLOs to track: median preflight runtime < 8m, 95th percentile GPU queue wait < 25m, cache hit-rate > 60% for kernel artifacts.
- Alerts:
  - CI: ci-preflight-latency-high (p95 > 12m) -> paged to ci-cd oncall.
  - GPU-queue-surge (95th > 45m) -> routed to eng-infra oncall.
  - Canary-regression-detected (error-rate delta > 0.5% absolute) -> paged to runtime owners + eng-sre.

Automated remediation playbooks (examples)
- Automated cache warming: when a promoted-cache snapshot is published, kick off warmers in each region to prime LRU caches for the next 1–2 hours.
- Job re-scheduler: if a GPU job fails due to transient infra (node reboot, preempt), automatically requeue once with backoff and annotate failure type.

Terraform/IAAC checks snippet (example)
  # pseudo-Terraform plan check for tenant isolation
  terraform init -input=false -backend-config=backend.hcl
  terraform plan -out=plan.tfplan
  terraform show -json plan.tfplan > changed_resources.json
  python tools/validate_tenant_isolation.py changed_resources.json || exit 1

Postmortem and continuous improvement
- Every CI incident that caused >30 minutes of release block or customer impact must have a postmortem with a timeline, RCA, and at least two corrective actions: one short-term (config change / hotfix) and one long-term (instrumentation / design change).
- Quarterly review: CI owners will run a SLA review of pipeline SLOs, cache economics, and shard mappings to identify >10% wins for runtime improvements.
