GPU Request Exchange & SLA Granting Playbook

Summary
-------
This playbook defines the "GPU Request Exchange" — a self-service marketplace and SLA-backed grant workflow that lets internal teams request, obtain, and manage GPU capacity with clear pricing/credits, safety checks, audit trails and emergency reclamation runbooks. It combines a lightweight approval marketplace UI, Terraform/IaC hooks for provisioning, CI/CD gating for policy changes, and an on-call runbook for capacity emergencies.

Goals and non-goals
-------------------
- Goals:
  - Enable fast, auditable self-service GPU requests with tiered SLAs (BestEffort / Burst / Reserved)
  - Enforce quota and egress guardrails via automated policy checks
  - Provide terraform module and CI/CD integration for safe, auditable provisioning
  - Offer a clear emergency reclamation procedure for capacity pressure
- Non-goals:
  - Not a long-term chargeback billing system (finance integrations are out of scope for v1)
  - Not intended for external / customer-facing provisioning (internal only)

Audience
--------
- Infra engineers who operate GPU fleets and Terraform modules
- Platform engineers and SREs who maintain autoscalers and placement
- ML / product teams requesting capacity
- Security and compliance reviewers for restricted workloads

Terminology
-----------
- Marketplace: The UI + API where teams submit GPU requests (request-exchange.redwood.internal)
- Grant: A confirmed allocation (tenant subnet + reservation/credits)
- SLA Tier: One of BestEffort / Burst / Reserved (defines preemption, billing and fallback policies)
- Grant Manifest: Signed Terraform variables blob used to instantiate capacity

High-level flow
---------------
1. Requestor submits a GPU request via Marketplace UI or API:
   - fields: team_id, project, requested_gpus, preferred_region, SLA_tier, expected_peak_hours, justification
2. Automated policy checks run (quota, egress, model sensitivity, placement constraints)
3. If checks pass and capacity is available, the Marketplace issues a Grant Manifest and triggers IaC pipeline
4. IaC pipeline (Terraform) provisions the allocation into the tenant's workspace; Marketplace records provenance and returns access links
5. On request edge-cases (no capacity) the request is queued and a capacity-sourcing task is opened (bursts, offload to partner cloud, or eviction candidates)

Policy checks (automated)
-------------------------
- Quota sanity: team has remaining credit/lease for requested GPU type
- Network egress: estimated egress in last 7 days + projected must be < team egress cap
- Placement compatibility: requested GPU type supported in region/availability-zone
- Security: If workload touches customer data with PII, set confidentiality=restricted and route for legal review
- Companion check: Check for preemptible vs reserved conflict (Reserve requests require 48h lead time)

SLA tier definitions
--------------------
- BestEffort: Preemptible, immediate if capacity exists; no SLA; auto-evictable
- Burst: Short-term reserved from warm pools for tenant; 2-hour warmup; preemption advisory
- Reserved: Commit-backed allocation; SLA: 99.9% availability; requires approval and capacity planning ticket

Terraform / IaC integration
--------------------------
- Pattern: Marketplace returns a Grant Manifest (signed-vars.json) blob. The IaC pipeline consumes the signed blob and runs an auditable apply in the tenant's workspace.
- Example module invocation (HCL snippet):

module "tenant_gpu_grant" {
  source = "git::ssh://git@github.com/redwood-iac/tenant-gpu-module.git//modules/grant"
  team_id = var.team_id
  grant_id = var.grant_id
  gpu_count = var.gpu_count
  gpu_type = var.gpu_type
  region = var.region
  apply_id = var.signed_manifest_id
}

- Required variables for module (table-like list):
  - team_id (string)
  - grant_id (string, UUID)
  - gpu_count (number)
  - gpu_type (string)
  - region (string)
  - signed_manifest_id (string)
  - start_time (RFC3339)
  - duration_hours (number)

CI/CD gating for granting
-------------------------
- All Terraform applies are executed in a restricted CI runner:
  - Pipeline steps:
    1. fetch signed-manifest
    2. terraform init + validate
    3. terraform plan -> upload plan artifact
    4. automated plan checker runs policy-as-code (OPA) – fails on egress/iam violations
    5. if plan passes, apply is scheduled; for Reserved tier apply requires SLA-reviewer approval in PR
- Approvals and audit: Every apply is linked to a Grant Manifest and stored in S3 for 365 days

Cost / credit model (summary)
-----------------------------
- Each grant consumes credits from the team's allocation. The Marketplace exposes a live credit balance.
- Simple rate table (illustrative):
  - a100-80gb: 50 credits / gpu-hour (Burst), 40 credits (Reserved)
  - v100-32gb: 18 credits / gpu-hour
- Teams can define auto-topups via finance-approved cards (out of scope for v1 — manual request)

Emergency reclamation runbook (on-call)
---------------------------------------
Trigger: Utilization > 95% on region X for 6 continuous minutes OR capacity demand queue grows past 20 pending requests

Immediate steps (0–10 minutes)
1. Pager notifies infra-capacity oncall (channel #infra-capacity). Acknowledge in 5 minutes.
2. Query current grants: 
   - CLI: curl -s https://request-exchange.redwood.internal/api/v1/grants?region=us-west-2 | jq '.'
3. Identify reclaimable grants using policy score (least recently active, BestEffort first):
   - CLI helper (example):
     request-exchangectl list --region us-west-2 --filter reclaimable --output table
4. If candidates exist, open an emergency reclaim ticket using the Marketplace API (creates signed revoke-manifest):
   - API: POST /api/v1/grants/{grant_id}/revoke?reason=capacity-pressure
5. Trigger Terraform apply that reduces grant (IaC run uses revoke-manifest). Monitor apply logs in CI console.

Escalation (10–30 minutes)
- If automated reclaim fails or insufficient capacity reclaimed:
  - Option A: Initiate cross-region overflow (see Cross-Region Overflow procedure below)
  - Option B: Enable temporary preemption window (notify affected teams with 30-minute grace)
- Notify Product Infra lead and Customer Success if any customer-facing workloads are at risk

Post-incident (30+ minutes)
- Create an incident summary and attach grant revoke manifests and pipeline logs
- Run capacity retrospective and update marketplace scores and throttles

Cross-Region Overflow procedure (short)
---------------------------------------
1. Check partner cloud capacity pools (documented in cloud-accounts-and-networking catalog)
2. If eligible, mark grant with "overflow_target=region:us-east-1" and trigger overflow provisioning via a partner module
3. Track egress and billing delta tags (overflow-tag: true)

Monitoring, metrics and SLOs
---------------------------
- Metrics to publish:
  - grant_queue_length (per-region)
  - average_grant_wait_seconds (per-tier)
  - region_gpu_utilization (5m/1h)
  - emergency_reclaims_count
- SLOs (infra internal):
  - Average grant wait (Burst): 10m
  - Average grant wait (Reserved): 48h (includes approval time)
  - Emergency reclaim successful within 15 minutes 90% of incidents

Safety, audit and compliance
---------------------------
- All manifests and signed-vars are stored in S3 with KMS encryption and write-once metadata for provenance
- Grant lifecycle events (create, modify, revoke) are logged to audit-log cluster (retention 1 year)
- Requests that touch PII or restricted datasets are marked confidentiality=restricted and require legal review before provisioning

Implementation checklist (phased rollout)
-----------------------------------------
1. Phase 0 (pilot): Marketplace UI + signed-manifests for BestEffort grants only (internal ML approx 4 teams)
2. Phase 1: Add automated policy checks (OPA), CI plan checks, and Burst tier with warm-pool integration
3. Phase 2: Add Reserved tier, SLA approval flows and finance integration for reserved commitments
4. Phase 3: Cross-region overflow and partner integrations + full audit retention

  package grant_policy

  deny[msg] {
    input.request.gpu_count > input.team_quota
    msg = sprintf("request exceeds quota: %v > %v", [input.request.gpu_count, input.team_quota])
  }

FAQ
---
Q: Can I request GPUs for open-source model evals? 
A: Yes. Open-source evals are BestEffort unless you request Burst/Reserved and obtain approvals.

Q: How long does a Reserved grant take? 
A: Typical approval+provisioning is 24–72 hours depending on capacity and finance commitments.
