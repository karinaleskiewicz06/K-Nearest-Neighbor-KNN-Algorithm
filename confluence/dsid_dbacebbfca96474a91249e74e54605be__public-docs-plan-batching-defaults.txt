Public Docs Plan: Workload-Aware Batching Defaults (Fast / Standard / Cost-Efficient)

## Overview
This document is the execution plan for updating Redwood’s external documentation to support “workload-aware batching defaults”: three customer-facing latency SLO tiers (fast / standard / cost-efficient) that map to recommended batching profiles.

The public docs must:
- Explain tier meanings clearly without over-promising.
- Document default behavior (what happens if a customer does nothing).
- Show how to select a tier and how to override/opt out safely.
- Provide examples (REST + SDKs) and troubleshooting guidance.
- Provide an FAQ that sets expectations for latency vs cost trade-offs and streaming.

## Goals (docs outcomes)
1) Reduce configuration confusion and support load during rollout.
- Customers can answer: “Which tier should I use?” and “How do I set it?” within 2 minutes.

2) Avoid customer foot-guns.
- Clear warnings around per-request overrides, Dedicated precedence, and overload/backpressure behavior.

3) Align messaging across product surfaces.
- Terminology and claims match Console copy and runtime behavior.

4) Support staged launch.
- Docs support: internal canary → Hosted subset → Dedicated opt-in → broad default.
- Clearly indicate availability by deployment mode (Hosted / Dedicated / Private).

Non-goals:
- Publishing internal knob values (e.g., exact max_wait_ms) or hardware-specific tuning tables beyond what Product approves.
- Promising fixed latency numbers for every workload; we will point to published tier targets and caveats.

## Audience and use cases
Primary audience:
- Application engineers integrating Redwood API (Hosted).
- Platform engineers operating Dedicated clusters.
- SRE/ops teams troubleshooting latency/cost regressions.

Key use cases:
- Choose a tier for a new route.
- Change tier for an existing route after observing p95/p99 or cost.
- Force fast tier for streaming endpoints.
- Verify which tier is currently effective (and why) in Console.
- Troubleshoot “why did my effective profile change?” (reason codes / overload mode).

## Messaging principles (public)
Use these consistent statements across all pages:
- “Tiers are a high-level intent (latency vs cost). Redwood picks safe batching defaults consistent with that intent.”
- “Defaults are workload-aware: prompt length distribution, streaming vs non-streaming, and concurrency signals influence how requests are batched.”
- “You can override per route (recommended). Per-request overrides are supported but should be used sparingly.”
- “In overload, Redwood prioritizes predictable behavior (backpressure/load shedding) over unbounded queueing.”

Avoid:
- Claims like “cost-efficient is always cheaper” without caveats.
- Suggesting customers tune low-level scheduler knobs as first-line guidance.

## Content outline (core page)
Page: “Batching defaults & latency SLO tiers”

1) What batching is (1–2 paragraphs)
- How batching improves throughput and cost.
- Why batching can affect tail latency (waiting to form batches).

2) What changed (workload-aware defaults)
- Redwood uses runtime heuristics and workload signals to pick safe batching behavior.

3) Tier definitions (high-level)
- **Fast:** prioritizes tail latency stability and streaming responsiveness.
- **Standard:** balanced default for most production workloads.
- **Cost-efficient:** prioritizes throughput / $/token; higher tolerance for queuing.

4) Decision table (choose a tier)
- If you stream user-facing chat: start with fast.
- If you run mixed workloads or general API: standard.
- If you run async/batch summarization or offline processing: cost-efficient.

5) Default behavior
- If a customer does not select a tier: explain which tier is applied by default per product policy (Hosted default) and how that may evolve during rollout.
- Provide a “How to pin your tier” callout.

6) Overload behavior (public-safe)
- Explain backpressure/load shedding at a high level.
- Clarify that cost-efficient may accept higher queueing than fast.

7) Observability
- Where to see effective tier in Console.
- “Why this profile?” explanation and reason codes (public-friendly phrasing).

## Opt-out / override guidance (public-safe)
We need a clear “Safety” section (applies across pages):
- Recommended: set tier per route in Console or config.
- Advanced: per-request override for A/B tests, migrations, or special endpoints.
- Opt-out: document the supported mechanism (e.g., pin legacy behavior or disable tiered defaults) only if Product approves exposing it publicly. If opt-out is intended to be support-assisted, say so explicitly.

Warnings to include:
- Don’t set per-request tier dynamically based on user identity (can increase variance and complicate debugging).
- If you change tier, observe p95/p99 and error rates for at least one peak window.

## FAQ (draft questions to publish)
We will publish answers aligned to policy and avoid internal implementation details.

1) “What happens if I don’t pick a tier?”
- Explain default tier behavior and how to pin it.

2) “Does fast mean real-time?”
- Clarify expected use (interactive) and that latency still depends on model size, output length, and region.

3) “Will cost-efficient increase latency?”
- Explain trade-off and who should use it (async/batch).

4) “Does tier selection affect output quality?”
- State: batching should not change model outputs; mention rare edge cases we monitor (e.g., truncation/limits) and recommend contacting support if quality regressions are suspected.

5) “Does tier selection change logging/retention or data handling?”
- State explicitly: no; tier only affects runtime scheduling and batching.

6) “Can I use fast tier for streaming only and standard for non-streaming?”
- Yes; recommend per-route configuration.

7) “How do Dedicated overrides work?”
- Provide precedence and a troubleshooting pointer (“if your override isn’t taking effect…”).

8) “How can I tell which tier is in effect and why?”
- Point to Console view and reason codes.

## Troubleshooting checklist (public)
Create a “Troubleshooting: tiered batching” section with:
- Confirm effective tier (Console / response headers if present).
- Check whether streaming is enabled (streaming endpoints benefit from fast).
- Compare prompt length distribution to expectations (very long prompts may change behavior).
- Look for concurrency changes (spikes can alter batching behavior).
- If p99 regresses: try fast tier, reduce concurrency, or contact support with request IDs.
- For Dedicated: confirm override precedence and config rollout status.

## Rollout-aware docs strategy
Because rollout is staged, docs need explicit availability notes:
- Hosted API: feature-flagged rollout; “Available in select regions/accounts during rollout” language until GA.
- Dedicated: “Opt-in during rollout; defaults available after upgrade to runtime 1.22+ (or equivalent).”
- Private: “Available in runtime 1.22+; configuration may be controlled by your deployment operator.”

We will maintain a small “Release & availability” callout box that can be updated without rewriting the entire page.
