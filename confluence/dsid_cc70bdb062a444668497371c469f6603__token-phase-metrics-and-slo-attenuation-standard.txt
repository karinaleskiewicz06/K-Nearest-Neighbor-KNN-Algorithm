Token Phase Metrics and SLO Attenuation Standard

This standard defines how Redwood Inference services must instrument per-token latency/cost by phase (prefix, prompt, generation, post-process) and how on-call alerting must apply SLO attenuation to reduce noise from known noisy phases (e.g., cold-start/prefix warmup) without hiding persistent generation regressions.
## 1. Purpose
Token-level latency and cost are frequently dominated by different parts of an inference invocation (e.g., prefix prefill vs generation). Historically we alerted on end-to-end latency and created noisy paging during cold-starts, cache churn, and post-processing spikes. This standard introduces:
- A consistent phase taxonomy for metrics and traces.
- A required baseline of Prometheus/OTel telemetry per phase.
- A standardized SLO attenuation policy that downweights known noisy phases while preserving high-signal generation regressions.

## 2. Definitions: token phases
All serving paths that emit token telemetry MUST map work into the following phases:
1) prefix: client prefix handling, routing, model load/warmup, and KV-cache acquisition (includes cold-cache overhead).
2) prompt: prompt processing / prefill work prior to streaming tokens.
3) generation: token generation / decode loop.
4) post: post-processing including formatting, tool invocation serialization, safety filters, and response finalization.

Notes:
- If a phase is not applicable, it MUST still be representable (e.g., record 0 duration or omit the span event, but maintain metric semantics consistently).
- Phase boundaries MUST be deterministic and consistent across languages.

## 3. Required telemetry
### 3.1 Metrics (Prometheus)
Services MUST emit the following metrics (names and label policy below are normative):

A) Per-phase token latency histogram
- Metric: redwood_token_latency_phase_seconds
- Type: histogram
- Semantics: duration attributed to phase work divided by tokens accounted to that phase, aggregated per scrape interval.
- Required labels:
  - phase: one of {prefix,prompt,generation,post}
  - region
  - model_family
- Optional labels (MUST be bounded; see cardinality policy):
  - tenant (if missing, exporter MUST set tenant="unknown" rather than dropping series)

B) Per-phase token cost attribution
- Metric: redwood_token_cost_phase_units_total
- Type: counter
- Semantics: monotonic units representing cost attribution (internal cost units) attributed to each phase.
- Required labels: phase, region, model_family
- Optional labels: tenant (same rules as above)

C) Per-phase cost fraction/ratio gauge
- Metric: redwood_token_cost_phase_ratio
- Type: gauge
- Semantics: ratio in [0,1] of total token cost attributed to the phase over a rolling window.
- Required labels: phase, region, model_family
- Optional labels: tenant

Recommended (not required) metrics:
- redwood_kv_cache_hit_ratio (by model_family, region, optional tenant)
- redwood_token_throughput_tps (by model_family, region)

### 3.2 Tracing (OpenTelemetry)
Services MUST annotate request traces with:
- Span events at phase start/end OR child spans per phase.
- Attributes:
  - phase (string; same taxonomy as above)
  - kv_hit (boolean; set when prefix work includes KV cache check)
  - model_family, region, and tenant where available

Minimum acceptable example attributes:
- phase="generation"
- kv_hit=true

## 4. Label cardinality policy (mandatory)
To prevent metric explosion:
- model label MUST be model_family (not full model id/version).
- tenant label is OPTIONAL; when used, it MUST be bounded via allowlist or sampling strategy in the exporter.
- Do not add request_id, user_id, or prompt hash labels.
- Any new label MUST be reviewed by SRE and Serving Runtime.

## 5. Dashboard standard
All teams MUST provide (or reuse) a Grafana dashboard that includes:
- Stacked per-phase p50/p95/p99 latency (token-normalized).
- Heatmap or distribution view split by phase.
- Token cost waterfall per invocation (aggregate view) and cost ratio by phase.
- Filters:
  - model_family (required)
  - region (required)
  - tenant (optional)

Reference implementation: token-phase-explorer (Grafana) maintained by SRE.

## 6. SLO attenuation: standard policy
### 6.1 Why attenuation exists
Cold-starts and cache churn can dominate prefix/post phases and cause paging that does not reflect persistent user-impacting regressions. Attenuation reduces alert noise from those phases while preserving detection for generation regressions.

### 6.2 Default attenuation rule (normative)
The global alerting layer applies attenuation when ALL conditions are met:
1) The alert is primarily attributable to a phase in {prefix,post}.
2) The phase cost ratio exceeds the threshold: redwood_token_cost_phase_ratio > 0.55 for that phase.
3) The condition occurs within the attenuation window.

Default parameters:
- attenuated_phases: prefix, post
- attenuation_window: 15m
- attenuation_factor: 0.25 (i.e., reduce alert score/weight to 25%)
- never_attenuate_phases: generation (generation-driven SLO violations MUST page)

Attribution rule (when multiple phases are noisy):
- Attribute an incident to the phase with the highest redwood_token_cost_phase_ratio.
- Apply attenuation only if the attributed phase is in {prefix,post} AND ratio threshold is exceeded.

### 6.3 Tenant opt-out / strict mode
Some tenants require strict paging even for cold-start behaviors.
- Opt-out mechanism: set tenant annotation/label slo.attenuation="false" in the tenant config registry.
- When opt-out is set, alerts MUST NOT be attenuated for that tenant.

### 6.4 When to tune
Teams MAY request tuned thresholds (ratio, window, factor) when:
- A model_family has known warmup behavior that lasts longer than 15m.
- A tenant runs batch workloads with predictable cold bursts.

All tuning MUST be documented in the service runbook and reviewed by SRE.

## 7. Testing and validation requirements
Before enabling attenuation in production:
- Unit tests MUST validate phase mapping and label-set bounds.
- Integration test MUST simulate warm vs cold prefix and assert that:
  - prefix-driven violations reduce alert firing rate under cold-start scenario
  - generation-driven violations remain unattenuated
- A canary or perf-canary run MUST demonstrate reduced alert noise without masking persistent regressions.

## 8. Rollout guidance
Recommended rollout sequence:
1) Enable phase metrics and trace annotations in staging.
2) Verify dashboards populate correctly; validate label cardinality.
3) Enable attenuation in logs-only mode for 72h (record what would have been attenuated).
4) Enable attenuation for opt-in tenant groups with >1 month usage history.
5) Review outcomes weekly for the first month; tune only if justified.

Observed reference outcomes (from initial deployment):
- Alert firing reduced by ~35–45% in synthetic cold-start workloads.
- Exporter overhead measured at ~0.4–0.7% CPU and ~2–3% memory increase depending on tenant label enablement.
