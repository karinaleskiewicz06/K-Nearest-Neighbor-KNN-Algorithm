Preemptive Drain Simulation Grid and Tenant Fallback Validation Runbook

Overview
--------
This runbook defines a repeatable simulation grid to validate Redwood's behaviour during preemptive GPU node drains and the tenant-level fallback policies that should keep hosted inference traffic within SLOs. It covers testbed topology, an automated orchestration harness, observable signals to monitor, pass/fail criteria, and post-run verification and rollback steps.

Goals
-----
- Validate graceful degradation when a subset of GPU nodes in a region are preemptively drained (planned maintenance / preemption forecast).
- Verify automatic tenant fallback routing: burst-to-dedicated, cross-region failover, and model-variant downgrade (quantized fallback).
- Catch regressions in KV-cache warmup, checkpoint replay, and request fusion under pressure.
- Ensure alerting and billing telemetry correctly attribute egress/burst credits and token billing.

Scope and exclusions
--------------------
Scope:
- Multi-tenant clusters that serve hosted API traffic (inference frontends + runtime pool).
- Plans with spot/preemptible-backed GPU pools and dedicated pools.
- CI/CD test runs and canary dry-runs in staging and preprod (not production without authorization).

Exclusions:
- Hardware failure injection (handled by separate HW-failover runbook).
- Private on-prem deployments (similar pattern but different network topology).

Prerequisites
-------------
1. A staging/preprod tenant configured to mirror production routing rules and quotas.
2. Terraform modules and test harness branch deployed (see "Testbed IaC" below).
3. Access: runbook executor role (infra-canary) and kube-cluster-admin for the test clusters.
4. Active dashboards for: "inference/p95_latency", "inference/error_rate", "kv_cache/hit_rate", and "egress/burst_credits".

Topology (text diagram)
-----------------------
- Region A (primary): 4 GPU pools (spot-1, spot-2, warm-reserve, dedicated).
- Region B (secondary): dedicated fallback pool + egress proxy.
- Control plane: canary-orchestrator (k8s job) + terraform test workspace.

Grid matrix (test vectors)
--------------------------
| Vector | Preempt % | Target pool | Fallback policy | KV-cache seeding | Expected p95 latency delta | Expected error rate |
|--------|-----------|-------------|-----------------|-------------------|---------------------------|---------------------|
| V1     | 20%       | spot-1      | spill -> warm   | full               | +10–20 ms                | <0.5%               |
| V2     | 50%       | spot-1+2    | spill -> dedicated; cross-region if >40% | partial | +30–80 ms       | <1.5%               |
| V3     | 80%       | spot-1+2+warm | model-variant-quantized -> dedicated | cold | +100–300 ms   | <3.0%               |

Note: p95 expectations are relative to baseline collected immediately prior to the run.

Orchestration steps (automated)
--------------------------------
1. Deploy test routing config: `kubectl apply -f manifests/test-routing.yaml` (owned by `infra-canary`).
2. Start telemetry baseline capture (60 minutes): `scripts/collect_baseline.sh --duration 60m --out baseline-<run-id>.tgz`.
3. Trigger terraform plan/apply to bring up canary mock tenants and lower burst credits if needed.
4. Schedule preemptive drains via the orchestrator: POST to /api/v1/orchestrate/drain with payload `{"pool":"spot-1","percent":50,"stagger_s":30}`.
5. The orchestrator will:
   - Cordone nodes (k8s) with annotation `redwood.infra/test-run: <run-id>`.
   - Gradually drain according to `stagger_s` while monitoring `inflight_requests`.
   - Enforce routing policy changes via the routing controller (canary endpoint).
6. Monitor dashboards and the canary validation script `scripts/validate_run.py --run-id <run-id>` which emits PASS/FAIL for each vector.

Manual commands (if automation fails)
------------------------------------
- Cordone and drain nodes: `kubectl cordon <node>` then `kubectl drain <node> --ignore-daemonsets --delete-local-data --grace-period=120`
- Force fallback routing: `curl -X POST https://routing.internal/api/v1/force-fallback -d '{"tenant":"staging-42","policy":"dedicated-first"}'`

Pass/Fail criteria
------------------
- PASS: For a vector, all of the following must hold during the run window (+10m stabilization):
  - p95 latency increase <= vector expected delta.
  - error rate < vector expected error rate.
  - KV-cache hit rate not less than 60% of baseline for V1/V2; V3 allows down to 30% during cold start.
  - No unexpected 5xx increase on control plane services (control-plane/500s < 0.1%).
- FAIL: Any of the above violated, or routing controller fails to update within 2m for critical changes.

Observability and telemetry (what to watch)
--------------------------------------------
- Dashboards: inference/p95_latency, inference/p99_latency, inference/error_rate, kv_cache/hit_rate, egress/burst_credits, routing/decision_latency
- Logs: routing-controller (INFO/ERROR), orchestrator (DEBUG when running), node kubelet logs for eviction spikes.
- Trace flags: enable `canary.run_id` on trace spans for easy slicing.

Alert thresholds to set for the run (temporary)
-----------------------------------------------
- TEMP-ALERT-1: inference/p95_latency > baseline*1.6 for >5m -> paging to infra-oncall.
- TEMP-ALERT-2: egress/burst_credits negative delta > 10% -> notify finops@ (billing spike).
- TEMP-ALERT-3: routing/decision_latency > 5s -> stop run and investigate.

Post-run verification checklist
------------------------------
1. Revert routed policies to baseline using `kubectl apply -f manifests/baseline-routing.yaml`.
2. Rehydrate KV cache warm seeds for affected tenants: `scripts/kv_seed.sh --tenants staging-* --parallel 4`.
3. Collect post-run artifacts (dashboard screenshots, logs, trace bundles): `scripts/collect_artifacts.sh --run-id <run-id>` and upload to the run ticket.
4. Run billing reconciliation: upload `egress/burst_credits` dump and run `scripts/recon_burst_credits.py --run <run-id>`
5. If any vector FAILED, open an incident ticket with severity per the incident taxonomy and attach artifacts.

Rollback and emergency stop
---------------------------
- Emergency stop endpoint: POST /api/v1/orchestrate/stop?run_id=<run-id> (idempotent).
- Immediate rollback action: re-enable drained nodes (if not permanently removed) with `kubectl uncordon <node>` and set routing to `baseline`.
- If routing controller is unresponsive, reconfigure edge LB to point to Region B manually (`lbctl set-backend ...`).

Known limitations and mitigations
--------------------------------
- Some tenant workloads have very long KV cache warm times (>30m) which can skew V3 results. Mitigation: tag long-warm tenants and run an isolated test.
- Egress billing attribution lags by up to 10m in staging. Mitigation: use synthetic accounting samples in the run to validate logic.
- Cross-region network flaps during concurrent network maintenance can cause false positives; schedule runs outside network change windows.
