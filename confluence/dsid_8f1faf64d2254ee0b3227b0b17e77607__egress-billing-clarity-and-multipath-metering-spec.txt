Egress billing clarity and multipath metering export spec

Summary:
This document defines the canonical telemetry model, export schema, and operational requirements for egress billing and multi-path metering across GPU tenant traffic. It standardizes how we measure, tag, and export egress usage for billing, cost attribution, and automated quota enforcement when requests traverse multiple routing paths (hosted, dedicated, private).

Scope:
- Applies to all outbound egress from Redwood-managed GPU fleets and gateway proxies (hosted/dedicated/private).
- Covers runtime emitters (egress-proxy sidecars and gateway logs), aggregator (billing-exporter), storage (BQ/S3), and consumer interfaces (billing ingestion, cost UI).
- Excludes: cross-region cloud provider internal transfer charges (handled by cloud-finance pipeline).

Goals:
- Single schema for meter events so finance, SRE, and product get identical numbers.
- Accurate multipath accounting: attribute a single request to the correct billable tenant even when routing falls back or copies traffic to multiple pools.
- Low-latency export for near-real-time quota enforcement (target: <= 30s ingestion-to-availability).
- Backwards-compatible with historical egress exports for 12 months.

Background and motivations:
- We observed discrepancies between per-tenant token-based billing and network egress reports (up to 8% variance) because some requests temporarily mirrored traffic for caching and shadow testing.
- This spec unifies labels and provides a deterministic tie-breaker for multi-path duplicates.

High-level architecture (textual diagram):
- egress-proxy sidecar -> local buffered log (loki/structured files) -> billing-exporter (k8s deployment) -> transform & dedupe -> BigQuery daily partitions + S3 raw archive -> billing ingestion job (finance).

Canonical event schema (CSV / newline-delimited JSON):
- Field list (order must be stable):
  1. event_id (uuid v4)
  2. timestamp_utc (ISO8601)
  3. tenant_id (string)
  4. route_id (string) -- e.g., /v1/generate or routing tag
  5. model_variant (string) -- e.g., redwood-alpha-7b-8k-quant
  6. path_tag (string) -- one of: hosted, dedicated, private, mirror
  7. bytes_sent (int) -- outbound bytes observed at egress PT
  8. tokens_estimate (int) -- best-effort token count from SDK wrapper
  9. dedupe_group (string) -- optional tie group for multipath (see rules)
  10. routing_decision (string) -- e.g. primary, fallback, probe, mirror-copy
  11. billing_charge_id (string) -- assigned by billing-exporter when finalized
  12. host_zone (string) -- region/zone tag
  13. request_id (string) -- original client request id if present
  14. origin_ip_cidr (string) -- /32 or /128
  15. raw_headers_hash (string) -- sha1 of headers used to detect duplication
  16. exporter_version (string)

Dedupe and multipath attribution rules (deterministic):
- Rule 0: Only events with the same dedupe_group and timestamp_utc within a 2s window are considered duplicates.
- Rule 1: If any event in the dedupe_group has routing_decision == "primary", attribute the charge to that event's tenant_id/right path_tag.
- Rule 2: If no primary exists, prefer routing_decision == "fallback" over "mirror".
- Rule 3: If still ambiguous, apply lexicographic ordering of path_tag (dedicated > hosted > private > mirror) as deterministic tie-breaker.
- Rule 4: The billing-exporter emits a single billing_charge_id for the dedupe_group and marks other events with billing_charge_id = "duplicate:<billing_charge_id>".

Transform & export pipeline expectations:
- billing-exporter component responsibilities:
  - Consume structured logs from loki or via gRPC stream from sidecars.
  - Normalize fields and compute tokens_estimate when missing using heuristics (UTF-8 token heuristic).
  - Group events into dedupe_group using request_id, raw_headers_hash and a sliding window.
  - Emit finalized records to BigQuery in partitioned tables and write raw NDJSON to s3://redwood-raw/egress/YYYY=... for forensic replay.
  - Provide an idempotent replay API to re-ingest raw files with the same dedupe rules.

Export formats and storage locations:
- Nearline (BQ): dataset = redwood_billing.egress_events, table = events_v1$YYYYMMDD partitioned by DATE(timestamp_utc).
- Raw archive (S3, for replay): s3://redwood-raw/egress/raw/YYYY/MM/DD/HH/partition-<shard>.ndjson.gz
- Short-term retention: BQ 90 days for fast queries, S3 raw 12 months.

Terraform and deployment notes (billing-exporter module example):
- Module name: module.billing_exporter (registry: internal/billing-exporter)
- Required IAM roles: s3:GetObject, s3:PutObject (raw archive), bigquery.tables.updateData, secretsmanager:GetSecret, logs:Subscribe
- Minimal snippet (HCL conceptual):

module "billing_exporter" {
  source = "git::ssh://git@github.com/redwood-infra/modules.git//billing-exporter?ref=v1.2.0"

Operational runbook (for delayed ingestion or duplication spikes):
1) Detect: Alert triggers when ingestion lag > 30s or dedupe rate > 5% of events/hour (see monitoring below).
2) Validate: Run quick query in BigQuery: SELECT COUNT(*) FROM redwood_billing.events_v1 WHERE _PARTITIONDATE = CURRENT_DATE AND billing_charge_id IS NULL LIMIT 1;
3) If many null billing_charge_id: check billing-exporter logs for "dropped-due-to-window" or OOM.
4) If backlog in S3: trigger replay job: curl -XPOST https://billing-exporter.redwood.internal/replay -d '{"s3_prefix":"egress/raw/2025/09/27"}'
5) Escalate to eng-infra oncall if replay fails or more than 10k unresolved events remain after two replays.

Monitoring & alerting (metrics & thresholds):
- Prometheus metrics emitted by billing-exporter:
  - billing_exporter_ingest_lag_seconds (gauge) -> Alert: P1 if > 60 (sev: page)
  - billing_exporter_dedupe_rate (ratio) -> Alert: P2 if > 0.05 over 1h
  - billing_exporter_failed_exports_total (counter) -> Alert: P1 if > 1000 in 1h
- Dashboards: Billing -> Egress: 1) ingest lag distribution 2) dedupe rate by tenant 3) cost divergence (BQ vs cloud provider).

SLOs and error budget impact:
- Near-real-time availability: 99.9% of events visible in BQ within 30s (sli: 30s ingestion latency).
- Deduplication correctness: target false-duplicate rate < 0.5% over rolling 7 days. Failures impact billing reliability and require manual reconciliation.

Migration and back-compatibility plan:
- v1 -> v2 exporter transition timeline: run exporter v2 in parallel (mirror path_tag=mirror) for 30 days while comparing aggregated totals.
- If divergence <= 0.5%, flip production traffic to v2 and retire v1 after 90 days.

Security and data handling:
- No PII should be recorded in raw_headers_hash or exported headers. origin_ip_cidr is limited to /32 for IPv4/IPv6 and redacted for requests flagged as GDPR-protected.
- Exporter must run with least privilege. Secrets are read from secretsmanager and the deploy CI job must attest module version.

Rollout checklist (high level):
1. Deploy billing-exporter v1.2 to staging with sample traffic.
2. Validate dedupe behaviour against known shadow traffic.
3. Enable BQ exports and confirm partitioning.
4. Turn on short-term alerting and dashboards.
5. Run parallel mirror in prod for 7 days.
6. Flip to active dedupe attribution and notify finance.
