gpu-traffic-synthesis-and-tenant-fingerprint-library

Overview

This page documents the GPU Traffic Synthesis and Tenant Fingerprint Library: a canonical set of synthetic tenant profiles, traffic scenario definitions, and CI/CD integration guidance used to exercise the fleet, account egress paths, and quota/egress throttles in preflight and continuous validation. The library enables repeatable capacity tests, regression detection, kernel-mix experiments, and telemetry-map validation without using customer data.

Goals
- Provide a concise, extensible fingerprint schema that describes tenant workload characteristics (token distribution, sequence length, KV cache reuse, model family, quantization profile).
- Offer a curated scenario catalog (bursting, long-seq tails, chat-like small messages, eval-eval concurrent workloads) that maps to operational risk categories.
- Define how to run the harness locally, in CI, and at scale against shadow endpoints (capacity-sentry / shadow-cluster).
- Ensure telemetry emitted during runs maps back to SLO signal names (p99_latency_ms, token_cost_usd, kv_cache_hit_rate).

Scope and non-goals
- Scope: infra testing that exercises serving runtime, egress fabric, allocator, and rate-limit controllers. Includes Terraform module shapes for synthetic-tenant provisioning and CI pipelines for nightly and PR checks.
- Non-goal: Final production load-testing of customer traffic — do not reuse production credentials or customer prompts.

Fingerprint schema (v1)
Each fingerprint is a small JSON document that describes a simulated tenant. Fields shown below are required unless noted. Keep entries under 2 KB.
- tenant_id: string (human-readable id used in metrics tags)
- model: string (e.g., gptj-6b-qlora, rwx-13b-8bit)
- seq_length_p50: integer (median sequence length)
- seq_length_p95: integer
- tokens_per_minute: integer (steady-state tokens/min)
- burst_profile: enum [none, short, medium, long] (describes burst duration patterns)
- kv_reuse_rate: float (0.0-1.0 fraction of requests that can reuse KV cache)
- concurrency: integer (parallel in-flight requests)
- call_type: enum [text_generate, chat_stream, embedding, rerank]
- quant_profile: string (e.g., q4_0, q8_0, fp16)
- egress_pattern: enum [low, balanced, egress_spike] (used to route synthetic egress)
- labels: list of strings (optional tagging)

Example fingerprint (JSON)
{
  "tenant_id": "search-svc-sim-01",
  "model": "rwx-13b-8bit",
  "seq_length_p50": 32,
  "seq_length_p95": 127,
  "tokens_per_minute": 15000,
  "burst_profile": "short",
  "kv_reuse_rate": 0.8,
  "concurrency": 4,
  "call_type": "chat_stream",
  "quant_profile": "q8_0",
  "egress_pattern": "balanced",
  "labels": ["indexing","search"]
}

Scenario catalog (select)
We keep a small, well-defined catalog that maps to operationally meaningful tests. Use the scenario id when scheduling runs.

| scenario_id | description | primary_risk | expected_metric_priority | run_target |
|-------------|-------------|--------------|-------------------------|-----------|
| sustained-burst-60m | Steady tokens/min with periodic short bursts, 60 minutes | throughput / allocator pressure | p95_latency, queue_length, token_cost_usd | shadow-cluster |
| long-seq-tail | Small number of tenants issuing sequences > 1k tokens intermittently | memory / KV cache fragmentation | kv_cache_miss_rate, memory_pressure, p99_latency | capacity-sentry |
| embed-blast | High-concurrency small embedding requests | egress cost and network throughput | egress_bytes/s, embedding_unit_cost | shadow-proxy |
| mixed-precision-roll | Mixed q4/q8/fp16 allocation churn | kernel degradation and flakiness | kernel_error_rate, quant_fallbacks | kernel-lab |

(ASCII table above intended for copy/paste; internal tooling will translate into Confluence table automatically.)

How to run the harness
1) Local quick check
- Prereqs: python3.11, virtualenv, docker (for local shadow proxy).
- Checkout repo: git clone git@github.com:redwood-inference/gpu-sim-harness.git
- Setup: make venv && .venv/bin/pip install -r requirements-dev.txt
- Run: python run_harness.py --fingerprint samples/search-svc-sim-01.json --scenario sustained-burst-60m --target shadow-local

2) PR-level smoke (CI)
- CI job name: ci/gpu-sim/pr-smoke. Minimal run: 5 minutes against mini-shadow deployed in the PR sandbox.
- Pass criteria: no kernel_error_rate > 0.5% and p95_latency within baseline +/- 30%.
- Failure action: raise the PR check and attach a telemetry dump at /artifacts/sim/{run-id}.tgz

3) Nightly full sweep
- Job: ci/gpu-sim/nightly-catalog. Runs full catalog across two regions (us-west-2 shadow, eu-west-1 shadow).
- Observability: automated diffs for these telemetry signals: p99_latency_ms, kv_cache_hit_rate, egress_bytes_per_min, token_cost_usd. Alerts created when any signal drifts > 10% vs 28-day baseline.

CI/CD integration details
- The harness lives in infra/ci/gpu-sim. A GitHub Actions workflow templates/gpu-sim.yml is used across repos to invoke the harness.
- The Terraform module for provisioning synthetic tenants is tfmodule/gpu-sim-tenant. Module inputs: tenant_count, allowed_egress_buckets, target_region, sandbox_account_id. Example snippet: 

# terraform usage (example)
module "sim_tenant" {
  source = "git::ssh://git@github.com/redwood-inference/tfmodules.git//gpu-sim-tenant?ref=stable"
  tenant_count = 3
  allowed_egress_buckets = ["sg-analytics-sim"]
  target_region = "us-west-2"
  sandbox_account_id = "111222333444"
}

Telemetry mapping and dashboards
- Metric tag conventions: sim.tenant_id, sim.scenario, sim.run_id. Use these tags for querying in Grafana/Influx.
- Canonical metrics emitted by harness: tokens/min, p50/p95/p99 latency_ms, kv_cache_hit_rate, kernel_error_rate, egress_bytes, cpu/gpu_util_pct.
- Dashboards: dashboards/gpu-sim/overview and dashboards/gpu-sim/{scenario}-breakdown. Each dashboard includes a baseline overlay (28-day rolling median).

Ownership and SLAs
- Owner: infra/gpu-team (primary), eng-platform (secondary).
- On-call: gpu-team oncall handles synthetic-run alerts during nightly windows (00:00-04:00 UTC).
- SLAs for the harness itself: nightly run must complete within 3 hours; if it fails 2 nights in a row, SEV-3 ticket with ops team.

Runbook: triage checklist when a simulation indicates regression
1) Validate run integrity: confirm run_id completed and that synthetic tenants were actually provisioned (check tfstate/artifact manifest).
2) Check kernel_error_rate and collect last 2 minutes of kernel logs from kernel-lab nodes: 
- CLI: ./infra_tools/collect_kernel_logs.sh --run ${RUN_ID} --out /tmp/kernel-${RUN_ID}.tgz
3) Verify allocator saturation: query allocator-operator: 
- kubectl -n allocator get pods -l app=allocator-operator -o wide
- curl -sS http://allocator-operator.internal/debug/metrics | grep queue_length
4) If egress_bytes spike is primary signal, check VPC egress proxy and NAT gateway metrics and correlate to tenant labels.
5) Open a postmortem if regression persists for > 6 hours or customer-facing traffic impacted. Include telemetry diff screenshot and run fingerprint JSON.

Extensibility patterns
- Add a fingerprint by creating a JSON under samples/fingerprints and incrementing catalog.json. Keep new fingerprints small and add reviewer.
- For new scenarios, add an entry to scenarios/catalog.yaml and include expected signal priority and baseline. New scenarios must be reviewed by GPU-runtime and Observability teams.

Security and safety constraints
- Do not store PII or customer prompts. All synthetic input content must be generated from the licensed synthetic corpus (repo: datasets/synthetic/README.md).
- Synthetic tenants must be isolated to sandbox accounts and use dedicated service accounts with limited iam:PassRole rights.
