GPU egress proxy failover and resilience patterns

Overview

This page describes our recommended patterns for making GPU-hosted inference traffic resilient to egress/proxy failures. It covers architectural patterns, Terraform/IaC module contracts, CI/CD test scenarios, runbook playbooks, and telemetry that the infra and SRE teams should use to achieve predictable failover with minimal customer impact.

Why this exists

- GPU inference workloads are latency-sensitive and often traverse company egress proxies (for policy, NAT consolidation, or egress inspection). Proxy failures or misconfigurations have historically led to broad degradation across inference clusters.
- This doc codifies a repeatable, testable approach so that we can: 1) contain blast radius, 2) fail fast to a degraded but functioning path, 3) make rollouts observable and reversible.

Goals and SLO alignment

- Target user-visible SLO during partial proxy outage: 99th percentile request latency increase < 2x baseline and error rate < 0.5% for critical tenants.
- Operator SLO for automated failover: complete configuration switch and verified healthchecks within 45s.
- Telemetry SLO: failover event must emit a correlated trace and an alert within 60s.

High-level patterns

1) Multi-path egress (primary/secondary)
- Maintain two proxy egress paths per region: primary (fast path, WAF/inspection) and secondary (minimal inspection, wider NAT pool).
- Use smart routing in the inference gateway to route according to observed p95/p99 or health flags.

2) Sidecar-aware routing and in-proc circuit breakers
- Runtime agents on GPU nodes maintain agent-level health of upstream proxies and expose local circuit-breaker state to the serving runtime.
- When local circuit breaker trips, traffic is re-routed to secondary egress without requiring cluster-wide config change.

3) Consistent hashing + sticky fallback for KV-cached sessions
- Use consistent hashing keys that include tenant+model to preserve KV locality where possible. When moving to secondary egress, allow a grace window for KV cache warmup (configurable TTL).

4) Scoped failover flags and gradual drift
- Failover is orchestrated via three levels: node-local agent decision, slice-level routing (subset of nodes), and global policy. Use progressive canarying to limit blast radius.

Terraform/IaC module contracts

- Module: rwi/gpu-egress-routing (inputs/outputs table)
| Input | Description | Default | Validation |
| tenant_allow_secondary | List of tenant IDs allowed to fallback | [] | optional |
| primary_proxy_endpoint | Primary proxy service FQDN/port | required | must resolve |
| secondary_proxy_endpoint | Secondary proxy FQDN/port | required | must resolve |
| healthcheck_path | HTTP path used by node agents to validate proxy | /healthz | regex |
| failover_cooldown_s | Minimum seconds between automated failovers per-node | 60 | >= 30 |
| canary_fraction | Fraction of nodes to route to secondary during canary | 0.05 | 0..1 |

- Outputs: primary_route_id, secondary_route_id, canary_policy_id (strings).

- Implementation notes:
  - Modules must support per-account overrides (cloud-account mapping) so each tenant account can opt-in to different secondary endpoints.
  - Avoid global managed resources that require manual edits during incident — prefer policy objects that can be updated via a single terraform variable and promoted by CI.

CI/CD gating and tests

Automated checks that must run on module and runtime changes before promotion to production:

1) Unit IaC policy checks (pre-commit): terraform validate, tflint, policy-as-code (OPA rego) ensuring no single-point egress resource is created without a secondary_endpoint property.
2) Integration test (staging): deploy module into a staging account and run a 'proxy failover' harness that simulates primary proxy blackhole for 90s and verifies:
   - Node agent flips to secondary within target cooldown window
   - No more than 5% request failures for canaried tenants; system-level p99 remains below threshold for canary slice
3) Chaos test (canary-candidate): scheduled chaos-week test in canary region that toggles rule sets and verifies rollback automation.
4) Telemetry regression: synthetic p99/p95 latency must not degrade more than 1.5x during failover in staging; if it does, gate promotion.

Runbook: rapid response for proxy egress failure

This is a concise playbook for oncall to follow; see step numbers for the quick path to resolution.

1) Detect:
- Automatic alerts: proxy_health_alert (node agent aggregated), p95_inference_latency_alert, region_egress_error_rate.
- First responder: eng-infra oncall.

2) Contain (0-2 minutes):
- If alert indicates primary proxy unreachable from >10% nodes, trigger per-region canary redirection: set canary_fraction=0.25 via "rwi-egressctl promote-canary --region=XYZ --frac=0.25"
- Check SLO dashboard: if error_rate > 2% for tenant-critical routes, escalate to full secondary cutover.

3) Mitigate (2-10 minutes):
- Promote full cutover using terraform variable (CI job: "promote-secondary"), or use emergency API to toggle sessions for affected tenants.
- Verify agent health and KV warming: run "rwi-agentctl nodes status --region=XYZ --filter=egress_state" and ensure >90% nodes report secondary.

4) Remediate (10-60 minutes):
- Coordinate with networking to triage primary proxy (firewall, BGP, WAF rule changes).
- If primary proxy config change caused outage, run diff and roll back change; register as a candidate for postmortem.

5) Restore (60+ minutes):
- Once primary is healthy, gradually shift traffic back with canary_fraction steps: 5% -> 25% -> 50% -> 100%, observing telemetry for 10 minutes per step.
- Run cache-warmup eviction and KV sync jobs as needed.

6) Post-incident actions
- Create a postmortem with causal chain, whether failover worked as designed, and improvement actions (e.g., reduce cooldown, add more secondary endpoints).
- Add any Terraform module changes to the change window and require an additional integration test.

Operational telemetry and dashboards

Minimum telemetry emitted on failover events:
- metric: egress.primary.up (bool per-proxy instance)
- metric: egress.secondary.up
- metric: inference.egress.failover.count (labels: region, tenant, node)
- span: failover.event (trace with tags: initiating_component, reason, latency_at_cutover)
- Logs: agent-level change events with node, old_endpoint, new_endpoint, and KV-cache-hit-rate at that moment.

Suggested dashboards:
- Regional egress matrix: grid of primary/secondary health by az + p95/p99 latencies
- Failover timeline: traces correlated to alerts and terraform promotions

Testing matrix (summary)

| Test | Environment | Failure mode simulated | Expected outcome |
| Module unit | CI | missing secondary_endpoint | fail CI with clear message |
| Integration | Staging | primary blackhole (TCP reset/blackhole) | node agents move to secondary; canary errors <= 5% |
| Chaos | Canary region | intermittent packet loss | progressive degradation observed; automated rollbacks triggered |
| Load | Performance lab | high connection churn | secondary path scales; p99 remains acceptable |

Implementation examples

- Node agent healthcheck snippet (bash):
  curl -sSf http://$PROXY_HOST:$PROXY_PORT/healthz || echo "proxy unhealthy" && exit 1

- Minimal Terraform snippet (module usage):
  module "gpu_egress" {
    source = "git::ssh://git@github.com/rwi/terraform-modules.git//gpu-egress-routing"
    primary_proxy_endpoint   = var.primary_proxy_endpoint
    secondary_proxy_endpoint = var.secondary_proxy_endpoint
    healthcheck_path         = "/healthz"
    failover_cooldown_s      = 45
  }

- rwi-egressctl quick commands (examples):
  # Promote a small canary in us-west-2
  rwi-egressctl promote-canary --region us-west-2 --fraction 0.05

  # Force immediate cutover for tenant t-123 (emergency path)
  rwi-egressctl force-cutover --tenant t-123 --region eu-central-1 --reason "primary proxy netpol change"

Appendix: example alert rules

- proxy_health_alert: triggered when egress.primary.up == 0 for >30s across >= 10% nodes in region.
- failover_mismatch_alert: triggered when inference.egress.failover.count spikes without a matching terraform promotion event.
