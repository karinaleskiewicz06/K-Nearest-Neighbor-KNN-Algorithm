Observability & Telemetry Unification Roadmap (2029 Q4 - 2030 Q2)

Summary:
This roadmap describes the plan to unify Redwood's telemetry surface across Hosted, Dedicated, and Private deployments. The goal is to deliver a single telemetry contract for logs, metrics, traces, and token-level event capture that powers Console, Optimize, and runtime routing while reducing observability costs and improving developer ergonomics.

Background and motivation:
- Current state: multiple telemetry collectors and pipelines are in use (hosted collector, sidecar-based collectors for Dedicated, and on-prem agents). Each consumer (Console, billing, Optimize) implements custom ingest adapters. This increases maintenance, makes cross-environment debugging hard, and inflates storage and query costs.
- Problem statements:
  1) Fragmented ingestion: different schemas and TTLs across environments create inconsistent dashboards and make root-cause analysis slow.
  2) Cost growth: duplicated events (raw token traces + derived metrics) are stored redundantly in multiple systems.
  3) Developer friction: product teams must instrument multiple SDKs and translate telemetry formats for the Console.

Objectives (outcomes we will measure):
- Single telemetry contract adopted by 80% of internal consumers by 2029-12-31.
- Reduce duplicated storage volume from telemetry by 45% within 6 months of rollout.
- Query latency: P95 console query time for cross-tenant traces <= 350ms for 90% of queries.
- Ingestion availability: 99.95% for hosted and dedicated collectors.
- Migration safety: no customer-facing incidents attributable to telemetry migration.

Scope:
In scope:
- Design and implementation of a unified telemetry contract (schemas + retention tiers + sampling policies).
- New SDK surface (single-line integration) for server SDKs and on-prem agents.
- Collector adapters for existing sidecars to emit the standard contract.
- Console ingestion pipeline changes and new cross-environment query layer.
- Cost-saving data lifecycle (hot/warm/cold retention tiers and rollup pipeline).
Out of scope:
- Third-party tenant telemetry hosted entirely outside Redwood (these will be supported via adapters in a later phase).

High-level approach and phases:
Phase A — Contract and pilot (2029 Q4):
1) Telemetry contract: publish V1 schema and sampling policy. Contract includes: event types (request, chunk, token_event, cache_hit, routing_decision), common fields (tenant_id, route_id, model_variant, request_id, timestamp, cost_estimate_usd), and minimal trace identifiers.
2) SDK alpha: lightweight Go/Java/Node SDK that can emit contract events with buffered async flush.
3) Pilot: onboard 2 internal services (Console ingestion and Optimize backfill) and one Dedicated customer for validation.
Milestones:
- 2029-10-15: Contract RFC published and open for review.
- 2029-11-05: SDK alpha v0.1 with integration tests.
- 2029-12-10: Pilot ingestion live and initial dashboards validated.

Phase B — Broad rollout (2029 Q4 -> 2030 Q1):
1) Collector adapters: ship adapters for standard sidecars and on-prem agent so customers do not need SDK changes.
2) Console migration: switch Console to query unified index and deprecate legacy adapters.
3) Storage lifecycle: implement hot/warm/cold tiers, rollups for per-route aggregates, and a daily offline aggregation pipeline to reduce raw retention.
Milestones:
- 2029-12-20: Collector adapters ready for staging.
- 2030-01-15: Console queries default to unified index; legacy toggles available for 60 days.
- 2030-02-01: Retention tiers and rollup pipeline in production for hosted.

Phase C — Optimization and hardening (2030 Q1 -> Q2):
1) Cost reduction initiatives: investigate smart drop/ingest-time compression and KV caching of token traces to reduce bytes stored.
2) Cross-tenant query heatmap and cost attribution per route to feed billing and Optimize.
3) SLA and runbook updates across SRE and Dedicated support.
Milestones:
- 2030-03-15: P95 console query latencies at target for 75% of queries.
- 2030-05-01: Storage reduction target (45%) achieved for onboarded services.

Non-functional requirements (NFRs):
- Security: telemetry payloads must not include customer PII. SDKs and agents must support envelope encryption and KMS integration for Private deployments.
- Privacy: provide opt-out controls for token-level capture per-tenant and per-route.
- Reliability: ingest path must be horizontally scalable and support backpressure with durable buffering (>= 24h local buffer for offline agents).
- Observability: self-monitoring dashboards (ingest rate, error rate, queue depth, processing lag) must be published and have alerts:
  - Ingest error rate > 0.5% sustained for 5m -> P2 alert.
  - Processing lag > 2m (P95) -> P1 alert.

Contracts and schema (excerpt) — Telemetry V1 (human-readable):
- Event types: request, token_event, cache_event, model_choice, routing_decision
- Common fields: tenant_id, environment (hosted|dedicated|private), service, route_id, request_id, model, model_variant, trace_id, span_id, timestamp_iso, sample_rate
- Token_event payload fields: position, token_text (optional hashed), token_embedding_ref (optional), latency_ms
- Retention policy: token_event -> hot 7d, warm 30d (rollup to token_count by route), cold 365d (aggregates only)

Migration plan and checklist (for each consumer):
1) Review RFC and map existing telemetry fields to contract.
2) Toggle SDK/adapter in staging and validate: a) roundtrip event counts, b) dashboard parity, c) no missing critical fields.
3) Run 48h parallel ingestion window (legacy + unified) and compare metrics.
4) Switch read default to unified index; keep legacy index in read-only for 60 days.
5) Deprecate legacy adapters after stakeholder signoff.

Risks and mitigations:
- Risk: Migration causes a temporary gap in alerting or dashboards.
  Mitigation: 48h parallel ingest + read-only legacy fallback and runbooks for quick rollback.
- Risk: Storage cost spike due to unforeseen duplication.
  Mitigation: Preflight simulation of ingest volumes and enforce hard sampling caps per-route in early rollout.
- Risk: Private/on-prem customers require custom compliance constraints.
  Mitigation: Provide agent-level configuration and KMS envelope options; consult security early in onboarding.

Cost and success KPIs (tracking):
- Telemetry storage bytes/day (baseline and target).
- Console query P95 latency.
- Percentage of internal consumers using Telemetry V1 contract.
- Number of incidents attributed to telemetry changes.

Operational runbook highlights (excerpt):
1) Alert: Ingest pipeline error rate spike -> page SRE -> check collector logs, backpressure metrics, and staging health.
2) Alert: Processing lag > 5m -> failover to read-only legacy index; open mitigation ticket; prioritize reprocessing backlog.

API and SDK example (pseudo):
- Node SDK quickstart (illustrative):
  const RedwoodTelemetry = require('@redwood/telemetry');
  const t = new RedwoodTelemetry({apiKey: process.env.REDWOOD_TELEMETRY_KEY, sampleRate: 0.1});
