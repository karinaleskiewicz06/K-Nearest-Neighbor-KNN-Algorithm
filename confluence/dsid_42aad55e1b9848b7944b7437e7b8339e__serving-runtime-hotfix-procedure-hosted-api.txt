Serving runtime hotfix procedure (Hosted API)

# Overview
This runbook describes how to execute an emergency hotfix or emergency rollback for the *Hosted API serving runtime*. It is optimized for speed while preserving safety (blast-radius control, verification, rollback readiness).

**Applies to:** runtime pods (model-server), runtime scheduler, runtime sidecars, runtime config/feature flags, and kernel selection/quant profiles when delivered via runtime image/config.

# Preconditions
- If there is active customer impact: declare an incident (Sev1/Sev2) and use the incident channel for coordination.
- Confirm EPC approvals per the Emergency production change policy.
- Identify the rollout target: region(s), tier(s), and route(s). Default is: one region canary first.

# Required dashboards (open before changing anything)
- Hosted API: request success rate (2xx/4xx/5xx) by region
- Runtime: p50/p95/p99 end-to-end latency and time-to-first-token
- Runtime: crash-loop rate / container restarts
- GPU fleet: utilization + queue depth
- Error taxonomy: top runtime error codes (oom, kv_cache_eviction, stream_disconnect)

# Decision tree (hotfix vs rollback vs mitigation)
1. If regression started after a known deploy and rollback is available: **rollback** is preferred.
2. If rollback is not available or doesnt address the issue: apply a **mitigation** (feature flag off, reduce max tokens, adjust batch limits).
3. If issue is correctness/security: prefer **hotfix** with minimal diff and targeted rollout.

# Step-by-step: emergency rollback
1. Identify last known good runtime version (tag) from: release notes, deploy history, or the incident timeline.
2. Validate rollback artifacts exist: image tag present in registry and deployment tool can reference it.
3. Roll back in this order:
   1) One canary cell in us-east
   2) Full us-east
   3) One canary cell in eu-west
   4) Full eu-west
4. Verification after each step (must pass before proceeding):
   - 5xx rate returns to baseline
   - p95 latency improves or is flat (no >10% regression)
   - restarts trending down
   - no new error signature dominates
5. Post in incident channel: what changed, where, and observed effect.

# Step-by-step: emergency hotfix
1. Reduce scope: minimal code/config change that addresses the issue. Avoid refactors.
2. Build + publish hotfix artifact per Release Engineering checklist (emergency path).
3. Deploy sequence:
   - Canary: 1 cell / 1 region / 10 minutes minimum observation
   - Expand: 25% of region
   - Expand: 100% of region
   - Repeat for next region
4. Monitoring gates (stop/rollback if any occurs):
   - error rate +0.3% absolute sustained for 5 minutes
   - p95 latency +15% sustained for 10 minutes
   - restart rate doubles for 10 minutes
   - GPU OOM events increase >20%
5. Record the following in the EPC record: version/tag, flags changed, cells/regions impacted, approvals, and verification evidence.

# Common mitigations (preferable to code changes when possible)
- Disable experimental scheduler features: `RW_SCHED_EXPERIMENTAL=0`
- Reduce max batch tokens: `RW_BATCH_MAX_TOKENS`
- Reduce max concurrent streams per pod
- Force conservative kernel selection (turn off fused attention for impacted arch)
- Temporarily lower max output tokens for affected routes

# Rollback triggers (hard)
Immediately rollback if any of the following are observed and attributed to the change:
- elevated 5xx correlated with rollout expansion
- widespread stream disconnects increase
- crash-loop / OOM increases
- customer escalations spike tied to the rollout region

# Customer comms reminders
- If the mitigation is visible (rate limits, reduced max tokens), coordinate with Support/CS and post status update when required.
- Avoid promising exact recovery times; provide next update cadence.

# Appendix: What to link in the incident timeline
- GitHub PR + merge SHA (or rollback tag)
- Deploy command / job link
- Dashboards used for verification
