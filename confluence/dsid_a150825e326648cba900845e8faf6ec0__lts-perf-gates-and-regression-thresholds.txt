Runtime LTS perf gates and regression thresholds

## Overview
This document defines the performance gating policy for **Runtime LTS** patch releases (e.g., `runtime-1.18-lts` → `1.18.1-lts`, `1.18.2-lts`). The intent is to ensure that backports and LTS-only stability changes do not introduce customer-impacting regressions in:
- End-to-end latency (p50/p95)
- Sustained throughput (tokens/sec)
- Tail behavior under mixed request shapes (prompt length distribution)
- Scheduler stability under overload / backpressure conditions

These gates are **release-blocking** unless a waiver is approved per the Waivers section.

## Goals
- Provide a stable, repeatable performance signal for LTS patches.
- Keep thresholds strict enough to prevent degradations but robust against expected measurement noise.
- Cover the GPU SKUs and request shapes that represent the majority of Dedicated/Private enterprise traffic.
- Standardize how results are reviewed and documented prior to publishing LTS artifacts.

## Non-goals
- This is not a replacement for full model-quality evals.
- This does not guarantee performance parity with mainline; LTS prioritizes stability and predictability.
- This does not attempt to benchmark every model in the catalog; we use representative canary models and workloads.

---

## Definitions
**Candidate (RC):** Release candidate build for an LTS patch.

**Baseline:** The previously published LTS patch on the same LTS line (e.g., baseline for `1.18.2-lts` is `1.18.1-lts`). If `1.18.1-lts` is the first patch, baseline is the branch cut commit tagged `1.18.0-lts`.

**Regression:** Candidate performs worse than baseline by more than an allowed threshold on any required workload/GPU combination.

**p50 / p95 latency:** Measured request latency at p50 and p95 for the workload-defined request shape. For streaming APIs, use “time-to-first-token (TTFT)” and “time-to-last-token (TLTT)” as specified per workload.

**Throughput:** Sustained generated tokens/sec (or embeddings/sec) under a fixed concurrency target.

**Noise:** Variation due to GPU clock variability, host contention, thermal conditions, and driver differences. We mitigate with dedicated runners, pinned clocks where supported, multiple runs, and robust statistics.

---

## Tooling and where results live
- **Perf runs** are executed via `perf-canary` release-branch workflows.
- Each run produces:
  - A human-readable Markdown summary artifact (`perf-gate-summary.md`).
  - A machine-readable summary (`perf-gate-summary.json`) used by CI gate evaluation.
  - Links to raw metrics dashboards (Grafana) for deeper investigation.

Required links for each patch release:
- Perf-canary workflow run URL(s)
- Summary artifact URLs
- Grafana dashboard snapshot URL(s) (24h retention minimum)

## Canonical workloads (required)
These workloads are designed to be representative and stable. They are also chosen to catch regressions from kernel changes (attention/kv-cache) and scheduling changes (batching/backpressure).

### W1: Chat generation (balanced)
- **API mode:** Chat completion (streaming ON)
- **Model:** `rw-instruct-8b` (stable canary)
- **Prompt tokens:** ~512
- **Output tokens:** 256
- **Concurrency:** 32
- **Metrics:** TTFT p50/p95, TLTT p50/p95, throughput tokens/sec

### W2: Chat generation (long context)
- **API mode:** Chat completion (streaming ON)
- **Model:** `rw-instruct-8b`
- **Prompt tokens:** ~4096
- **Output tokens:** 256
- **Concurrency:** 16
- **Metrics:** TTFT p50/p95, TLTT p50/p95, throughput tokens/sec

### W3: Mixed prompt length distribution (scheduler stress)
- **API mode:** Chat completion (streaming OFF)
- **Model:** `rw-instruct-8b`
- **Prompt tokens distribution:** 20% @ 256, 50% @ 1k, 20% @ 2k, 10% @ 4k
- **Output tokens:** 128
- **Concurrency:** 48
- **Metrics:** Request latency p50/p95, throughput tokens/sec, scheduler fairness (see S1)

### W4: High-throughput short generation (batching sensitivity)
- **API mode:** Text completion (streaming OFF)
- **Model:** `rw-instruct-8b`
- **Prompt tokens:** ~128
- **Output tokens:** 64
- **Concurrency:** 128
- **Metrics:** p50/p95 latency, throughput tokens/sec

### W5: Embeddings throughput
- **API mode:** Embeddings
- **Model:** `rw-embed-3-large`
- **Input length:** ~256 tokens
- **Batching:** runtime auto-batching ON
- **Concurrency:** 256
- **Metrics:** embeddings/sec, p95 latency

### S1: Scheduler overload and backpressure (smoke gate)
This is a targeted stability/perf test intended to catch regressions that do not show as pure throughput deltas.
- **Workload:** ramp concurrency from 32 → 256 over 10 minutes on W4 shape
- **Expected:** no sustained queue growth, no starvation (p95 bounded), no error-rate spikes
- **Metrics:** queue depth p95, request timeout rate, “oldest request age” p95

Notes:
- We keep canary models pinned and update them only with explicit approval from Runtime Architecture + Perf owner.
- If a change explicitly targets a different model architecture, we may add an *additional* ad-hoc workload for that patch. Ad-hoc workloads cannot replace W1–W5/S1.

## GPU SKU coverage (required)
The gate must run on the following SKUs at minimum. These represent current Dedicated/Private footprints and expected LTS adoption.

| GPU SKU | Required for LTS gate | Rationale |
|---|---:|---|
| NVIDIA H100 SXM (80GB) | Yes | Primary high-end Dedicated footprint; most sensitive to kernel selection changes |
| NVIDIA H100 PCIe (80GB) | Yes | Common in enterprise private clouds; perf differs from SXM under bandwidth constraints |
| NVIDIA A100 SXM (80GB) | Yes | Long-tail enterprise install base; regressions often show differently than H100 |
| NVIDIA L40S (48GB) | Conditional (pilot/GA target) | Growing mid-market footprint; include when runners are available |

Steady-state expectation (GA): H100 SXM + H100 PCIe + A100 are always required. L40S is required once runner capacity is provisioned and stable.

## Measurement methodology
To reduce false positives and ensure comparability:
1. **Environment controls**
   - Dedicated benchmark runners (no colocated CI workloads).
   - Fixed driver/runtime images per branch; record driver version in artifacts.
   - Where supported, pin GPU clocks to a standard benchmark profile.

2. **Runs and aggregation**
   - Minimum **5 runs** per workload per GPU SKU.
   - Compute regression vs baseline using **median-of-runs** for each metric.
   - If one run is clearly anomalous (e.g., >3σ from median and correlated with host alerts), mark it as “infra outlier” and rerun once. Document any excluded runs in the summary.

3. **Baseline selection**
   - Baseline is the latest published LTS patch on the same line.
   - Baseline must be rerun on the same runner pool within the last 30 days OR rerun alongside the candidate.

4. **Reporting**
   - Perf summary must include absolute values and deltas (%).
   - For any waiver request, include raw time-series and a short root-cause narrative.

## Regression thresholds (release-blocking)
Thresholds are intentionally tighter for LTS than for mainline release candidates.

### Primary thresholds (W1–W5)
All of the following must pass on **each required GPU SKU**.

| Metric | Allowed regression vs baseline | Notes |
|---|---:|---|
| TTFT p50 (streaming) | +5% | W1, W2 only |
| TTFT p95 (streaming) | +7% | W1, W2 only |
| TLTT p50 (streaming) | +4% | W1, W2 only |
| TLTT p95 (streaming) | +6% | W1, W2 only |
| Request latency p50 (non-streaming) | +4% | W3, W4, W5 p50 latency |
| Request latency p95 (non-streaming) | +6% | W3, W4, W5 p95 latency |
| Throughput tokens/sec | -3% | W1–W4 |
| Embeddings/sec | -4% | W5 |

Important:
- “Allowed regression” means the candidate may be slower than baseline by up to the threshold.
- Improvements are always acceptable, but must be called out if they are large enough to indicate a potential measurement artifact (e.g., >10% throughput improvement) and should trigger a sanity review.

### Tail protection for scheduler stress (W3)
W3 is meant to catch scheduler pathologies and fairness regressions.

| Metric | Allowed regression vs baseline |
|---|---:|
| W3 p95 latency | +5% |
| W3 throughput tokens/sec | -3% |
| “Long prompt cohort” p95 latency (4k prompts) | +5% |

### Overload smoke thresholds (S1)
S1 is a pass/fail stability gate.

Pass criteria (all required):
- Request timeout rate <= baseline + 0.05% absolute
- “Oldest request age” p95 does not exceed baseline by >10% for more than 2 consecutive minutes
- No increase in runtime 5xx error rate > baseline + 0.02% absolute during the 10-minute ramp
- No new scheduler assertion failures or watchdog-triggered restarts

If S1 fails, the release is blocked until fixed or waived (waivers for S1 are rare and require explicit SRE sign-off).

## Handling flaky signals and reruns
Benchmarks can be noisy. The goal is to distinguish infra noise from real regressions.

When a metric fails a threshold:
1. **Confirm runner health**
   - Check host alerts, GPU throttling, and background load.
   - If runner was unhealthy, rerun once after remediation.

2. **Rerun policy**
   - Max **1 rerun** per failing workload/GPU pair without escalation.
   - If the rerun flips pass/fail, mark as “unstable signal” and escalate to Perf owner + SRE to determine next steps (often: run 5 additional runs or move to a quieter runner pool).

3. **If still failing**
   - Treat as a real regression until proven otherwise.
   - Open a release-blocking issue and link the perf summary + relevant PR(s).

## Waivers / exceptions
Waivers exist to prevent blocking a release for known, acceptable tradeoffs, but should be rare for LTS.

### When waivers are allowed
A waiver may be considered if one of the following is true:
- The regression is tied to a fix for a Sev1 correctness/security issue and the regression is within a tolerable operational envelope.
- The regression is isolated to a non-primary SKU with a documented mitigation and low enterprise exposure.
- The metric is failing due to an infrastructure/measurement limitation that cannot be corrected in time, and other signals indicate no real regression.

### Waiver approval requirements
All waivers must include:
- A short written rationale (2–5 bullets)
- Impacted workload(s), GPU SKU(s), metric(s), and magnitude
- Mitigation plan (rollback guidance, configuration override, or follow-up patch)
- Explicit statement whether the patch is “optional” or “recommended/mandatory” for affected customers

Record waivers in:

## Review and sign-off process (per patch)
Before an LTS patch is published, the release manager must attach the perf gate summary and confirm the following:

1. **Coverage complete**
   - W1–W5 and S1 executed on all required GPU SKUs.

2. **Threshold evaluation**
   - Automated gate status is PASS.
   - Any anomalies (large improvements or unstable deltas) have a brief explanation.

3. **Human review**
   - Perf owner reviews summary and flags any suspicious changes.
   - SRE confirms no new operational risk (timeouts, error spikes) in S1.

4. **Documentation**
   - Release notes include:
     - Any performance-relevant change summaries
     - Known performance tradeoffs (if any)
     - Waivers (if any) with rationale

### Required sign-off comment template (copy/paste)
Use this in the release PR and link the perf artifacts.

- Perf gates: PASS/FAIL
- Baseline: <version/tag>
- Candidate: <version/tag>
- GPUs covered: H100 SXM / H100 PCIe / A100 80GB (and L40S if applicable)
- Workloads covered: W1–W5 + S1
- Notable deltas: <none | list>
- Waivers: <none | link>
- Reviewed by: <names>

## Change control for this document
Changes to thresholds, canonical workloads, or required SKUs are **change-controlled**.

Process:
1. Open a PR to update the perf-canary gate configuration.
2. Update this Confluence page.
3. Obtain approvals from Perf owner + SRE + Runtime release lead.
4. Announce in `#eng-releases` with the effective date (must be at least 1 patch cycle in the future unless urgent).
