GPU infra drift detection and safe remediation

Summary

This document describes our standard design and operational playbook for detecting configuration drift across the GPU fleet (multi-account, multi-region), safely remediating common classes of drift, and integrating detection into Terraform CI/CD pipelines. It focuses on drift that affects GPU infrastructure (instance types, network attachments, IAM roles, subnet mappings, node labels) and adjacent cloud networking that can silently break tenant isolation or cause cost/availability regressions.

Scope

- Resources covered: EC2/GCE GPU instances, autoscaling groups / instance templates, VPC subnets, route tables, NAT/GW, security groups, IAM roles/policies attached to GPU nodes, provisioned storage for warm pools, and Terraform modules under terraform/gpu-*.
- Out of scope: application-level config (K8s deployments/pods) unless they affect node-level attachments or node pools.

Motivation

Drift is a frequent source of production incidents: manual emergency fixes, cloud console edits, and ad-hoc scripts create state divergence between the canonical Terraform configuration and actual cloud resources. For GPU capacity, drift can cause noisy-neighbor issues, missed placement constraints, or unaccounted cost increases. We need a safe, auditable approach that: 

- Detects drift early (within 1–4 hours of change)
- Classifies severity and impact (safety tier)
- Allows fully automated remediation for low-risk drift, and human-in-the-loop for high-risk drift
- Integrates with existing GitOps flow (changes land in a branch/PR before being pushed to production)

Architecture overview

1) Detector pipeline (periodic):
   - A scheduled job (drift-detector-scheduler) runs terraform plan against the latest committed modules for each tenant/account using the most recent tfstate snapshot (read-only) every 2 hours for production-critical accounts and every 6 hours for dev/sandbox.
   - Plan diffs are parsed and normalized by the drift-normalizer service which maps resource names and module paths to our canonical inventory.
   - Findings are written to the drift-store (time-series) and emitted as alerts if thresholds are exceeded.

2) Signal sources:
   - Terraform plan diff (primary, deterministic)
   - Cloud provider change streams (AWS Config / CloudTrail, GCP Audit Logs) as an out-of-band detector for manual console edits
   - Kubernetes node annotations and nodepool reconciliation failures (for managed clusters)

3) Remediation paths:
   - Automated remediation (low risk): drift-remediator-runner opens a branch in the infra repo, applies a change that brings resources back in line (terraform import + plan + apply where applicable) and posts a short PR with generated rationale. A special pipeline gate runs a dry-run apply in a sandbox project and an approval step is required for anything that touches autoscaling groups or IAM.
   - Manual remediation (high risk): creates a ticket (Jira) assigned to the infra on-call with suggested remediation steps and a reproducible terraform plan artifact.

Detection signals and severity classification

We classify detected drift into three safety tiers:

| Tier | Typical examples | Auto-remediate? | Escalation window |
|------|------------------|----------------|-------------------|
| S1 (low) | Tag mismatches, description fields, non-critical security group description, cost-center tag missing | Yes (auto-commit) | N/A |
| S2 (medium) | Instance type drift (within same family), missing monitoring tags, subnet assignment mismatch for sandbox accounts | Conditional (auto to branch, manual PR approval) | 4 hours |
| S3 (high) | IAM role changes, ASG launch template replaced, route table delete, NAT gateway removal | No (manual) | 1 hour |

Rules that map plan diffs to tiers are stored in git: infra/terraform/policies/drift-rules.yaml and are used by the normalizer. Examples: resource address patterns, provider-specific heuristics, and whitelists per account.

Automated remediation policy (principles)

- Immutable-first: prefer reverting the drift by changing the cloud resource back to the declared state via Terraform, rather than modifying the configuration to match the live state, except when explicit exceptions exist and are recorded.
- Auditability: every automated remediation must create a PR and link to the originating drift detection event; drift history must be queryable for at least 90 days.
- Safety gates: autoscaling groups, instance replacement, and IAM changes must require human approval in the PR pipeline and cannot be auto-applied.
- Rate limits: no more than 5 automated remediations per account per hour to avoid cascades after a misconfiguration.

Implementation details

- Terraform execution environment:
  - Use ephemeral runners in our CI (gpu-tf-runner-pool) with service account credentials limited to a dedicated read-only tfstate viewer and an apply role used only for remediation tasks.
  - State is read from tfstate-bucket-redwood-gpu (SSE-KMS). Read-only access for detection runs, apply-role with explicit allow for terraform:Apply in remediation workflows.

- Plan parsing & normalization:
  - We use a small Go service (drift-normalizer) that canonicalizes resource addresses, collapses generated suffixes (e.g., size hashes), and tags the diff with module path and responsible team (from module metadata).

- Source of truth reconciliation policy: always use the latest committed module on main plus the TFVARS that match the account environment. For drift originating from manual console changes where there is an approved config change in a merged PR, the finding is closed automatically.

Terraform CI integration

1) Detection mode: every merge to main triggers a CI job terraform-plan-diff against a mirror of the account's tfstate to validate that merging the change does not introduce drift (fast sanity).
2) Remediation mode: the drift-detector service creates a branch named drift/<account>/<resource-path>/<short-hash> in the infra repo. The branch contains auto-generated tf changes or comments describing the desired import. A standard pipeline runs:
   - terraform init & plan with -out=planfile
   - static checks (tflint, checkov)
   - optional terraform apply in sandbox using ephemeral creds (if S1 or S2 auto path)
   - create PR with remediation notes and attach planfile artifact

Monitoring, dashboards & alerts

Key metrics to surface:
- drift.findings.count (by tier, by account)
- drift.time-to-detect (median, p95)
- drift.time-to-remediate (median, p95, by auto/manual)
- terraform.plan.failures (failed plan runs during detection)
- remediation.apply-failures

Alerting rules (examples):
- Fire an urgent PagerDuty if any S3 finding appears in production account.
- Create a high-priority ticket if drift.findings.count for S2+ in an account > 3 within 30 minutes.

Example PromQL (Grafana):

  sum by(tier, account) (increase(drift_findings_total[1h]))

Operational playbook (when drift is detected)

1) Low tier (S1) – automated:
   - Detector auto-generates remediation branch, CI validates, and merges the PR if automated tests pass. Post-merge, a follow-up detection run verifies drift is cleared.

2) Medium tier (S2) – gated automation:
   - Detector creates PR and notifies infra Slack channel (#infra-drift). An on-call engineer must review within 4 hours and either approve auto-apply or mark as manual. If no action, after 6 hours the PR is escalated to the team lead.

3) High tier (S3) – manual:
   - Immediate PD notification, triage call if needed, create incident if production impact. Use the emergency manual remediation checklist below.

Runbook: emergency manual remediation (quick checklist)

1) Freeze automated remediations for the affected account (runbook toggle: drift-autoremediation=false).
2) Capture reproducible artifacts: terraform plan -detailed-exitcode, provider audit logs (CloudTrail/GCP), current tfstate snapshot.
3) Open a remediation branch and add safe change that will not replace running instances unless explicitly approved.
4) If immediate rollback required for networking, attach a pre-authorized emergency reviewer and follow the emergency approval flow in PagerDuty.

Access controls and IAM table

| Principal | Purpose | Allowed actions | Notes |
|-----------|---------|----------------|-------|
| tf-detector-sa | Drift detection service | s3:GetObject, s3:ListBucket (tfstate), cloudwatch:Read | Read-only; KMS decrypt via grant |
| tf-remediator-sa | Automated remediation runner | ec2:ModifyInstanceAttribute, autoscaling:UpdateAutoScalingGroup, iam:PassRole (limited) | Scoped by account; requires apply-approval role for S2+ |
| tf-ci-runner | PR pipeline | terraform:Plan, terraform:Show, logs:write | Ephemeral tokens via OIDC |

Safety & testing strategy

- Canary remediation: new remediation types are first enabled on sandbox accounts and synthetic clusters. We run chaos tests that flip tags and simulate drift to validate both detector and remediator pipelines.
- Backout plan: every automated apply must generate a backout PR that re-applies the previous plan output. Backout artifacts stored for 30 days.
- Integration tests: Terratest suites for each module that mock cloud provider APIs where feasible; detection runs are validated against these suites nightly.

Ownership & on-call

- Primary owner: infra/terraform team (pagerduty: infra-terraform-oncall).
- Secondary: infra-sre for escalations involving network/routing.

Implementation checklist (minimum viable rollout)

1) Deploy drift-detector-scheduler to prod with read-only tfstate access.
2) Ship drift-normalizer and drift-store (Prometheus metrics + Postgres event store).
3) Implement rule set for S1/S2/S3 decisions and put in git.
4) Wire alerts to Slack and PagerDuty.
5) Onboard one pilot account (non-critical) and validate end-to-end auto-remediation for S1.
6) Expand to production accounts with staged enable toggles.

Appendix A — example terraform plan automation snippet

  # detect mode (read-only)
  terraform init -backend-config=\"bucket=tfstate-bucket-redwood-gpu\"
  terraform plan -out=detect.plan -var-file=prod.tfvars
  terraform show -json detect.plan | ./drift-normalizer --account prod | tee /tmp/plan-normalized.json

Appendix B — example sentinel-like rule (pseudocode)

  rule: no-iam-role-changes-on-prod
  when: plan.resources.any(resource.type == \"aws_iam_role\")
  action: fail if account == \"prod\"

Appendix C — common failure scenarios and mitigation

- Scenario: Console-bumped launch template causing instance-type mismatch.
  Mitigation: Open S2 PR (auto-branch), run plan in sandbox, if test passes approve with 2 reviewers.

- Scenario: NAT gateway removal (S3)
  Mitigation: Immediate incident, route traffic to standby NAT path and restore from tfstate snapshot.
