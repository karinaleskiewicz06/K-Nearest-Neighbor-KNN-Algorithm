Federated Enterprise Onboarding Playbook

Title: Federated Enterprise Onboarding Playbook

Overview:
This playbook outlines the recommended onboarding process for enterprise customers adopting Redwood Inference in federated deployment modes (Dedicated and Private). It covers pre-sales handoff, technical intake, network and security gating, initial runbook and health checks, first 90‑day success metrics, escalation paths, and QBR-ready artifacts. The intention is to standardize onboarding for customers who require private control plane, VPC peering, or on‑prem packaging while preserving predictable SLAs and operational readiness.

Goals:
- Establish production-ready deployment within 4–8 weeks for standard enterprise patterns.
- Verify SLO alignment: 99.9% availability for control plane; 95th‑pct latency SLOs documented per workload.
- Ensure secure connectivity, auditing, and access controls before traffic cutover.
- Provide documented runbooks and monitoring for customer-run teams and Redwood support.

Audience:
- Customer Success Manager (CSM)
- Solutions Engineer (SE) / Solutions Architect (SA)
- Customer platform / SRE contacts
- Redwood Onboarding Engineers and Support

Pre-Onboarding Checklist (to complete before kickoff):
1. Signed contract with deployment mode (Dedicated / Private / On‑prem) and capacity commitments.
2. Primary technical contact + secondary contact + Slack/Teams escalation channel.
3. Customer firewall / network point of contact and IP ranges for allowlist.
4. Confirmation of identity provider (IdP) for SSO (SAML/OIDC) and required attributes.
5. KMS/HSM ownership model and key lifecycle policy (if using customer-managed keys).
6. Data residency and retention requirements documented.
7. Initial expected token throughput and peak concurrency estimates.

Kickoff Agenda (1-hour):
- Introductions and roles
- High-level architecture and deployment variant
- Security and compliance signoffs required
- Network connectivity plan and timelines
- SSO and provisioning plan (SCIM)
- Rollout plan: pilot -> canary -> cutover
- Success metrics and QBR cadence (monthly first quarter)

Technical Intake (deliverables):
- Network diagram (customer side) with NAT/GW, proxies, and egress constraints.
- CIDR and static IPs for allowlist; expected ports (443, 8443 for control plane).
- Example SSH bastion or jumpbox requirements for on‑prem package installation.
- IdP metadata XML (SAML) or OIDC discovery endpoint.
- SCIM provisioning scope: groups mapping + service account email.
- KMS key ARN and rotation window (if applicable).

Network and Security Requirements (summary table):
| Item | Requirement | Notes |
|------|-------------|-------|
| Allowlist IPs | Customer must allow outbound to Redwood control plane CIDR | Provide final CIDR in pre-kickoff email |
| Ports | 443 (HTTPS), 5432 (optional for metrics forwarding) | Metrics forwarding optional via TLS |
| TLS | mTLS for private deployments recommended | TLS 1.2+; cert chain required for on‑prem installers |
| Audit logging | Syslog/Splunk endpoint or S3 bucket | Provide destination details and retention policy |

SSO and Provisioning Steps:
1. Customer provides IdP metadata and test user accounts.
2. Redwood SE configures SAML/OIDC in the customer tenant and shares test SP endpoints.
3. Validate attributes: email, name, groups. Ensure group names map to Redwood RBAC roles (admin, ops, developer).
4. Enable SCIM if available for automated provisioning; run dry‑run sync and validate.
5. Document expected session lengths and reauth policy for audits.

RBAC Mapping (recommended):
- admin -> full project and model management; allowed to create keys
- ops -> deploy/rollback and monitoring access
- developer -> inference keys, logs, and limited model management

Deployment Phases and Acceptance Criteria:
Phase 0 — Preparation (1–2 weeks):
- All network prerequisites completed; test connectivity verified.
- IdP integration validated with 2 test users.
- KMS and key policies agreed.

Phase 1 — Pilot (2–3 weeks):
- Deploy a single model endpoint (low QPS) to dedicated/private environment.
- Verify baseline metrics: latency P50/P95, token throughput, and error rate.
- End-to-end tracing enabled and validated.
- Customer sign‑off on functional correctness.

Phase 2 — Canary (1–2 weeks):
- Scale traffic to 10–20% of expected production load with autoscaling policies in place.
- Observe slow path behavior, cache warming, and batching efficiency.
- Perform failure injection: control plane restart and model fallback test.

Phase 3 — Cutover (1 week):
- DNS or routing change to send production traffic.
- Run ramp script (see "Ramp Plan" section).
- 72‑hour elevated monitoring window and daily touchpoint with SE/CSM.

Ramp Plan (example CLI verbs):
- Phase A: send 5% traffic for 12 hours, verify: error rate < 1%, P95 within target.
- Phase B: 25% traffic for 24 hours, run load profiling via /internal/loadtest endpoint.
- Phase C: 50% traffic for 24 hours.
- Final: 100% after green-checks.

First‑90‑Day Success Metrics (measured weekly):
- Availability: control plane and inference endpoints >= 99.9%
- Client observed latency: P95 must not exceed pre-agreed latency by more than 20%
- Cost per 1k tokens within 15% of estimated projection
- Number of critical incidents: 0; high-severity incidents <= 1

Operational Runbooks (examples):
- Rolling restart of model workers (Private):
  1. Put model variant into maintenance mode via admin UI/API: POST /admin/models/{id}/maintenance
  2. Scale down worker pool by 10% every 30s to drain connections
  3. Apply binary/OS patch on node; verify service health on /healthz
  4. Scale pool back up and run smoke test (sample prompts)

- Cache warming after deploy:
  1. Run batch warmup script: curl -X POST -H 'Authorization: Bearer <token>' "https://<endpoint>/internal/warmup" -d '@warmup_prompts.json'
  2. Monitor cache hit ratio in dashboard; target > 60% within first 1 hour for chat workloads

Common Known Issues & Workarounds (priority list):
1. Error: 429 Too Many Requests on control plane during peak onboarding traffic
   - Cause: rate limiter default thresholds on customer tenant
   - Workaround: SE can request temporary quota increase; advise staged ramp and use dedicated capacity reservations
2. SAML assertion mapping missing groups
   - Cause: attribute mapping mismatch in IdP
   - Workaround: add custom attribute map or use SCIM provisioning; test with a debug assertion tool provided by Redwood
3. Increased tail latency after canary deploy
   - Cause: new kernel/quantization profile mismatch for model variant
   - Workaround: rollback to previous model variant; open a performance triage with eng-serving-runtime and attach profile traces

Escalation Matrix (contact order + expected response SLAs):
- Level 1 (Customer SRE -> Redwood Oncall): 15 minutes to acknowledge, 1 hour to triage
- Level 2 (Oncall -> Onboarding + SE): 30 minutes to action plan, 4 hours to remediation plan
- Level 3 (Product + Eng + SRE): 2 hours to assembly, 24 hours for remediation window or agreed workaround

QBR Artifacts and Suggested Agenda (monthly first quarter):
- Rolling metrics: availability, P50/P95 latency, error budget burn, token usage, cost per 1k tokens
- Incident review (if any) and remediation status
- Model performance regressions and evals summary
- Roadmap alignment: upcoming infra changes that may affect SLAs
- Action items and owners for next quarter

Template: Health Check Checklist (to run at end of each week during onboarding)
- Control plane reachability: PASS/FAIL
- Inference endpoint smoke tests (5 prompts): PASS/FAIL
- Error rate last 24h < 1%: PASS/FAIL
- Disk and memory pressure on worker nodes: OK/WARN/CRITICAL
- Audit log delivery verified: PASS/FAIL

Post-Onboarding Handoff:
- Deliver runbooks and role-based access lists to customer SRE and CSM
- Schedule knowledge transfer session covering day‑2 ops and scheduled upgrades
- Agree on ongoing QBR cadence (monthly -> quarterly) and alert playbooks

Appendix C — Troubleshooting checklist for high tail latency:
1. Collect kernel traces and quantization profile ID from /internal/trace
2. Check batching metrics (tokens/batch, requests/batch) in dashboard
3. Confirm KV cache hit ratio and warmup status
4. If new model build: rollback to previous variant and open perf triage ticket
