H100 tuned hardware profile (reference)

## Purpose
This page describes the **H100 tuned hardware profile** shipped in the Hardware Tuning Profiles Pack. It is the default Redwood-validated preset for NVIDIA H100 fleets, intended to improve **throughput-per-GPU** while staying within a defined **tail-latency envelope** for common production workloads.

This is a reference page, not an API contract. The profile is **safe-by-default** and guarded by runtime validation; however, performance is workload-dependent and depends on fleet topology (SXM vs PCIe), driver stack, and request mix.

---

## Summary (what this profile is optimized for)
**Optimizes for:**
- High sustained tokens/sec under moderate-to-high concurrency
- Stable streaming behavior under mixed prompt length distributions
- Predictable GPU memory usage via KV-cache budgeting defaults
- Reduced config drift by pinning only knobs we have regression coverage for

**Not optimized for:**
- Lowest possible single-request latency at concurrency = 1
- Pathological long-context heavy mixes without request-level limits
- Ultra-low jitter environments where batching variance is unacceptable

---

## Profile names and maturity
**Maturity:** Production

**Profile IDs (as shipped):**
- `h100/balanced@1.x` (default): best overall trade-off for Hosted + Dedicated
- `h100/throughput-first@1.x` (opt-in): higher tokens/sec, more tail-latency risk under bursty traffic

> Note: The exact on-disk bundle version is separate (e.g., `profile_pack_version=2026.01.0`). Runtime logs print both.

## Compatibility and assumptions
### Hardware detection
Applies when the runtime detects an H100-class GPU (normalized SKU strings include: `H100 SXM`, `H100 PCIe`, `H100 NVL`). If SKU detection is ambiguous, the runtime falls back to **generic** profile selection.

### Software stack assumptions
Validated on the following baseline (see perf suite artifacts for exact pins):
- CUDA: 12.x line
- NVIDIA driver: 550+ line
- Runtime: `runtime-1.18+` (older releases may accept only a subset of keys)

### Deployment modes
Supported in:
- Hosted (fleet default + per-pool overrides)
- Dedicated (per-deployment / per-pool overrides)
- Private (Helm values + environment overrides; must remain supportable)

---

## Recommended use cases
Use `h100/balanced@1.x` when:
- Your workload is a mix of chat + long-form generation with concurrency >= ~8
- You care about both throughput and p95/p99 consistency
- You run streaming responses and want stable chunk cadence

Consider `h100/throughput-first@1.x` when:
- You are throughput constrained and can tolerate higher p95 under load
- You have strong admission control (queue limits / request timeouts)
- You are willing to monitor tail latency closely during rollout

Do **not** use `throughput-first` for:
- Latency-sensitive interactive chat with strict p95 SLOs during bursty traffic
- Pools with known noisy-neighbor behavior (oversubscribed CPU, unstable clocks)

## Key knobs (what we pin on H100)
The H100 profile intentionally pins only the knobs we can defend with:
1) workload matrix coverage, 2) perf-canary gates, and 3) operational rollback.

### 1) Scheduler and batching presets
**Goals:** increase GPU utilization via continuous batching, avoid prefill starving decode, and prevent queue explosions.

Pinned behaviors (high level):
- **Continuous batching:** enabled with H100-friendly limits to keep decode saturated
- **Prefill/decode fairness:** tuned to reduce tail spikes observed in early H100 rollout (see regression note below)
- **Backpressure + queue limits:** explicit caps to avoid unbounded latency under load

Common pinned parameters (names shown as conceptual; see `runtime config dump` for exact key names in your version):
- `scheduler.continuous_batching.enabled = true`
- `scheduler.batch.max_batch_tokens` (balanced: moderate; throughput-first: higher)
- `scheduler.queue.max_enqueued_requests` (hard cap)
- `scheduler.backpressure.target_queue_depth` (soft control)
- `scheduler.fairness.prefill_to_decode_ratio` (balanced favors decode stability)
- `scheduler.streaming.flush_interval_ms` (kept conservative to avoid jitter)

Operational intent:
- Balanced: improves tokens/sec without materially changing p95 for typical chat mixes.
- Throughput-first: pushes batch sizes up; this can increase p95/p99 when traffic is bursty or prompt lengths are bimodal.

### 2) Kernel selection heuristics (sequence-length buckets)
**Goals:** select stable kernels for common seq-length regimes and avoid cliff behaviors at bucket boundaries.

Pinned behaviors:
- **Seq-len bucketed kernel auto-selection:** different kernel preferences for short prompts vs long prompts
- **Conservative fallback kernels:** if microbench score is within margin, prefer more stable kernel

Conceptual knobs:
- `kernels.autoselect.enabled = true`
- `kernels.autoselect.seq_len_buckets = [0-512, 513-2048, 2049-8192, 8193+]`
- `kernels.autoselect.preference = stable_over_peak` (balanced)
- `kernels.autoselect.preference = peak_over_stable` (throughput-first)

Notes:
- We explicitly avoid pinning experimental kernels that lack multi-model coverage (Llama-family + Mixtral-class + rerank/embedding shapes).
- Kernel selection is one of the most common sources of “looks great in microbench, regresses in production.” The H100 profile keeps the heuristics simple and observable.

### 3) KV-cache budgeting and memory guardrails
**Goals:** prevent OOMs and reduce fragmentation-induced latency spikes while allowing high concurrency.

Pinned behaviors:
- Default KV-cache budgeting based on available HBM and expected concurrency
- Conservative headroom reservation for runtime overhead (graph capture buffers, allocator growth)

Conceptual knobs:
- `memory.kv_cache.max_fraction_of_hbm` (balanced: conservative headroom)
- `memory.kv_cache.evict_policy = lru_prefix_aware` (if supported)
- `memory.allocator.fragmentation_guard.enabled = true`

When this can hurt:
- If you run exclusively short-context requests and want maximum concurrency, conservative KV headroom may cap throughput slightly.

### 4) CPU-side runtime settings
**Goals:** reduce request scheduling jitter and avoid CPU becoming the bottleneck at high QPS.

Pinned behaviors:
- Worker thread pools sized to avoid oversubscription on common H100 node types
- Conservative default for request parsing / stream mux overhead

### 5) Collectives / NCCL (only when multi-GPU execution is enabled)
Most Hosted/Dedicated H100 pools run single-GPU per replica for common decoder-only serving. For multi-GPU model parallel shards:
- We avoid hard-pinning NCCL knobs unless the topology is known.
- Profile guards may require an explicit topology match before enabling aggressive tuning.

## Expected performance deltas (what you should see)
These deltas are based on the standardized workload matrix (see related page). Numbers are representative; do not treat as guarantees.

### Measurement baseline
- Baseline: runtime defaults with profile selection disabled (`profile=generic`)
- Compare: `h100/balanced@1.x` enabled
- Metric set: tokens/sec (decode), time-to-first-token (TTFT), p50/p95 end-to-end latency, GPU memory high-water mark

### Representative deltas (H100 SXM, common chat mix)
| Workload slice | Primary metric | Expected delta vs baseline | Notes |
|---|---:|---:|---|
| Chat, mixed prompts (p50 prompt ~400 tok, p95 ~2k), streaming | Sustained tokens/sec/GPU | +8% to +18% | Gains come primarily from higher effective batch occupancy in decode. |
| Chat, mixed prompts, streaming | p95 end-to-end latency | -3% to +7% | Balanced tries to keep p95 near-flat; increases can happen if traffic gets burstier than the test distribution. |
| Long-form gen (prompt ~2k, output ~1k), non-streaming | tokens/sec/GPU | +10% to +22% | Kernel heuristics help in mid-length bucket; larger effect when concurrency is high. |
| Tool-calling / short responses (prompt ~200, output ~80), streaming | TTFT p50 | -5% to +5% | Mostly unchanged; continuous batching variance can shift TTFT slightly under load. |

### Throughput-first expected deltas (opt-in)
| Workload slice | Primary metric | Expected delta vs baseline | Risk |
|---|---:|---:|---|
| High concurrency chat (>=32), streaming | tokens/sec/GPU | +15% to +30% | Higher batching variance can increase p95/p99, especially when bursts exceed queue caps. |
| Bursty chat traffic | p99 end-to-end latency | 0% to +25% | Tail can worsen if prefill spikes coincide with queue buildup. |

## Trade-offs (throughput vs tail latency)
### Why throughput can increase while p95 worsens
The dominant mechanism is **batching variance**:
- Larger / more aggressive batching increases GPU efficiency.
- Under bursty arrival patterns, requests wait longer to be batched, which shows up in p95/p99.

### Guardrails we ship to contain risk
- Hard queue caps to prevent runaway latency
- Backpressure triggers that slow admission before the queue becomes unstable
- Fairness tuning to avoid decode starvation (a common cause of long-tail)

### Practical guidance
- If you have strict p95 SLOs, start with `balanced` and keep queue caps conservative.
- If you need more throughput, prefer scaling replicas first; switch to `throughput-first` only with a canary + rollback ready.

## Known issues and mitigations (H100)
### 1) Tail latency regression from prefill/decode fairness (historical)
**Symptom:** p95/p99 latency increases after enabling the profile at similar throughput.

**Root cause (observed in validation):** prefill bursts could starve decode under certain prompt length mixes.

**Mitigation:**
- Ensure you are on a runtime release that includes the fairness regression fix (see runtime release notes / PR references in related pages).
- Use `h100/balanced@1.x` unless you have validated your traffic mix for throughput-first.
- Monitor `scheduler.decode_starvation_ms` (if exposed) and `queue_depth` alongside tail latency.

### 2) Streaming jitter under high load
**Symptom:** uneven token chunk cadence or longer gaps between streamed chunks.

**Mitigation:**
- Verify `scheduler.streaming.flush_interval_ms` is not overridden to an aggressive value.
- If you must reduce jitter, consider a lower max batch token cap (or switch to `balanced`).

### 3) Perf canary false positives due to workload mix drift
**Symptom:** perf canary flags regressions but production looks stable.

**Mitigation:**
- Confirm canary runs the current pinned workload matrix version.
- Prefer comparing on tokens/sec *and* tail latency together; isolated improvements/regressions can be misleading.

For the current, canonical list of H100 issues and mitigation playbooks, see: **hardware-profile-known-issues-and-mitigations**.

## How to enable, override, and debug
### Enablement (typical)
Most environments enable profile selection via fleet defaults. To force a profile for a canary pool or a private deployment, use one of the supported override mechanisms (in precedence order; exact order documented in the ADR):
1) Explicit per-deployment/per-pool override
2) Environment variable override
3) Fleet default
4) Auto-detected default

### Debugging (what to check)
At runtime startup, confirm logs include:
- detected GPU SKU (normalized)
- selected profile ID and bundle version
- override source (fleet default vs env vs per-pool)
- compatibility matrix (runtime version vs profile schema)

Useful commands/tools:
- `redwood-runtime config dump --effective` (prints effective config after merges)

Key metrics to view on dashboards:
- `runtime_profile_selected{profile_id=...}`
- `runtime_profile_override_source{source=...}`
- p50/p95/p99 end-to-end latency by route/model
- decode tokens/sec/GPU and GPU utilization
- queue depth, enqueue rate, and rejection rate (if backpressure triggers)

## Rollout recommendations (H100)
Use the rollout runbook for canonical steps. H100-specific guidance:
1) Canary with `balanced` in one low-blast-radius pool/region.
2) Require tail latency gates to be green for at least one full diurnal cycle.
3) Expand by region, then by pool.
4) Only after stable `balanced` rollout: consider a limited `throughput-first` experiment for throughput-constrained pools.

Rollback criteria (typical):
- Sustained p95 regression beyond agreed threshold for the pool’s SLO window
- Elevated timeout/retry rate correlated with queue growth
- Any increase in OOM/restarts attributable to memory guardrails being overridden

## Appendix: What we intentionally do NOT pin on H100 (and why)
- Highly experimental kernels without multi-model validation: too risky without coverage.
- Aggressive NCCL tuning across unknown topologies: can regress in non-SXM or mixed-network fleets.
- Customer-specific overrides that require bespoke support: handled via Solutions/Support with explicit documentation and support boundaries.
