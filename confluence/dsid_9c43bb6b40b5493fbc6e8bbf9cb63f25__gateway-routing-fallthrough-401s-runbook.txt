Gateway Routing Fallthrough Causing 401s (Runbook)

## Summary
This runbook covers a recurring failure mode where requests unexpectedly hit a fallthrough route and return **401 Unauthorized**. The most common trigger is a **routing predicate mismatch** (e.g., a header value such as `x-client-type: web-prod` not matching the intended primary route), which sends traffic to a default/fallback route with different auth settings.

This was first observed during staging traffic replays for `POST /v1/generate`, where 401 spikes appeared around a short interval (example: ~03:12 UTC) and traces showed requests landing on a fallthrough route.

## Impact
- Elevated 401 rate for one or more endpoints (often `/v1/generate`).
- Traffic routed to an unintended route (primary match fails, fallback or global fallthrough selected).
- In some cases, auth is either incorrectly enforced or incorrectly skipped depending on fallback route configuration.

## Symptoms / Detection
Use one or more of:
- Dashboards: spike in `http.responses{status=401, service=gateway-service}`.
- Tracing: spans show route selection = `fallthrough-route` or unexpected route id.
- Logs: route match failures mentioning a predicate miss on `x-client-type`.

Suggested quick query patterns:
- "route_match_failed" events clustered by `route_id` and `header:x-client-type` value.
- Compare `route_id` distribution before/after deploy.

## Common Root Cause
A routing policy defines multiple routes with the same `path_prefix`, but predicates narrow which one should be used. If a request header value is not exactly what predicates expect, neither route matches and the request falls through.

Example policy excerpt (sanitized) that caused fallthrough when clients sent `web-prod`:

routes:
  - id: generate-primary
    match: path_prefix: /v1/generate
    auth_required: true
    predicates:
      - header: x-client-type == "web"
  - id: generate-fallback
    match: path_prefix: /v1/generate
    auth_required: false
    predicates:
      - header: x-client-type == "internal"

Observed request header:
- `x-client-type: "web-prod"`

Result:
- Does not match `== "web"` and does not match `== "internal"`.
- Traffic hits fallthrough route.

## Immediate Mitigation Options (choose the least risky)
### Option A (Preferred): Broaden predicate match using starts_with
Update the primary route predicate to accept the known prefix.

Policy pattern (preferred over regex for performance):
- `header_starts_with: x-client-type starts_with "web"`

Notes:
- Standard operator is `starts_with` (avoid regex in the gateway planner unless explicitly approved).
- Keep matching logic explicit; do not silently widen beyond intended clients.

### Option B: Normalize header values at ingress
If you control ingress behavior, you can normalize `web-prod -> web`.

Tradeoffs:
- Pros: fixes routing and any downstream auth mapping expecting the canonical value.
- Cons: can hide client-versioning; must be coordinated with client/platform owners.

### Option C: Temporary safe fallback
If fallthrough is currently configured with weaker auth than the primary route, consider temporarily tightening fallthrough auth to reduce exposure while you fix routing logic.

## Step-by-Step Procedure
### 1) Confirm route selection in traces
1. Pick 3–5 sample 401 traces during the spike.
2. Verify the selected route id (primary vs fallback vs fallthrough).
3. Record the header values relevant to predicates (commonly `x-client-type`).

### 2) Dump the policy state from the affected environment
Run (adjust env/time window as needed):
- `./admin dump-policy --env=staging --since=<unix_ts>`

Checklist:
- Confirm the route table contains the expected ids.
- Confirm predicate values match what clients actually send.
- Look for recently introduced schema/key changes (see Rate Limit note below).

### 3) Apply the minimal policy change
Most cases require adding a starts_with predicate:
- Update `generate-primary` to match `x-client-type` values that begin with `web`.
- Ensure any internal-only fallback remains constrained.

### 4) Canary rollout
Recommended rollout for policy changes:
1. Deploy to 10% canary.
2. If dashboards are stable, increase to 20%.
3. Monitor:
   - 401 rate for affected route
   - route selection distribution
   - latency p95/p99 (header parsing + predicate checks)

### 5) Post-change validation
- Re-run staging traffic replay for the affected endpoint.
- Verify 401 spikes do not recur and the primary route is selected for `web-*` clients.
- If you see new fallthrough traffic, enumerate the unexpected header values and decide whether to broaden matching further or fix the caller.

## Rate Limit Configuration Note (frequently encountered alongside routing issues)
When validating policy dumps, confirm per-route rate limit keys are correct.

Canonical runtime key:
- `rate_limit.per_minute`

Backward-compatible alias (deprecated):
- `limits.per_minute`

Validator expectations:
- Accept both keys for now.
- Emit a deprecation warning when `limits.*` is used.

Default behavior:
- If a route omits per-route configuration, runtime falls back to the **global default**.
- Current global default (as of gateway-service v2.20+): **12k/min**.

## Testing Guidance
Add/verify the following tests:
- Route matching when header is `web-prod` (should select `generate-primary`).
- Route matching when header is `internal` (should select `generate-fallback`).
- Route matching when header is missing or unknown (should not silently select an unintended weak-auth route).
- Rate limit fallback when per-route config is missing (asserts global default is applied).

Optional load validation:
- Run replay or simulator bursts (e.g., 10k QPS burst) and compare:
  - 401 count
  - latency tail
  - route selection

## Escalation / Ownership
- Primary owner: Eng Platform (Gateway)
- If header normalization is required: coordinate with the client platform owner for the sending service/app.
