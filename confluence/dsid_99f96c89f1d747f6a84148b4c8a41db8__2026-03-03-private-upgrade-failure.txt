Postmortem: Private deployment upgrade failure (schema mismatch) causing 503s

h1. Summary
On 2026-03-03 Customer Nighthawk’s Redwood Private cluster experienced elevated 503s during an attempted upgrade from private-installer 1.7.4 to 1.8.0. The upgrade introduced a database migration ordering issue that caused the control plane to fail readiness checks.

*Customer impact:* Yes (service unavailable to customer traffic during upgrade window)
*Severity:* SEV-2
*Owning engineering team:* Private Deployments
*Primary components:* private-installer, control-plane, schema-migrator

h1. Impact
* Customer cluster: Nighthawk (single-tenant)
* Duration: 33 minutes of elevated 503s
* Workload: internal knowledge assistant (chat completions)
* No data loss; rollback successful

h1. Timeline (Customer local time converted to UTC)
* 16:02 - Upgrade started
* 16:07 - control-plane pods failing readiness
* 16:10 - 503s observed on customer side
* 16:14 - Support escalates to Private Deployments on-call
* 16:20 - Determined schema-migrator applied migration set B before set A
* 16:26 - Initiated rollback to installer 1.7.4
* 16:35 - Service restored

h1. Root cause
Installer 1.8.0 updated the migration plan to support a new audit-log table. For certain existing customer states, the dependency graph was incorrectly linearized, applying a migration that referenced a column not yet created. This prevented control-plane from starting and resulted in 503s at the ingress.

h1. Detection
Detected via customer report + support escalation. Our internal private-deployment telemetry was not configured to alert on this customer’s ingress 5xx.

h1. Action items
1) Add migration dependency validation in private-installer CI (Owner: Private Deployments; Due: 2026-03-25)
2) Ship preflight check to simulate migrations against current schema snapshot (Owner: Private Deployments; Due: 2026-04-05)
3) Update customer upgrade runbook to require telemetry + alert verification before upgrade (Owner: Solutions Eng; Due: 2026-03-20)
