GCP Marketplace: SKU & Billing Dimensions (v2)

## Overview
This document defines Redwood Inference’s GCP Marketplace SKU structure and the billing/metering dimensions used for GCP Marketplace reporting. It is the source of truth for:
- How GCP Marketplace “plans/SKUs” map to Redwood products (Hosted, Dedicated, Private) and add-ons.
- Which usage dimensions we report to Google, with units, rounding rules, and source-of-truth meters.
- Integration expectations for Procurement + Metering flows (subscription → entitlement → org provisioning → usage reporting → reconciliation).

This is GCP-specific; AWS offer structure and dimensions are covered separately.

## Goals
- Ensure Marketplace SKUs map cleanly to Redwood internal billing meters (no ambiguous dimensions).
- Keep billing semantics procurement-friendly (predictable invoicing, clear unit definitions).
- Define reporting cadence, idempotency, and reconciliation rules that satisfy GCP Marketplace requirements and reduce customer billing disputes.

## Non-goals
- Final price points, discounting, or private offer terms (owned by Partnerships + Finance/Legal).
- Detailed UI copy for listing pages.

## GCP Marketplace concepts (what we build against)
### Product + Plan model (SaaS)
For Redwood on GCP Marketplace (SaaS), the customer procures a plan that creates an entitlement. Redwood must:
1) Validate entitlement status during onboarding.
2) Map the entitlement to a Redwood org.
3) Report usage against the entitlement (for usage-based dimensions) OR rely on subscription charges (for fixed/contract dimensions).

### Key identifiers we store
During provisioning and ongoing metering, Redwood stores the following identifiers:
- GCP entitlement resource name ("gcp_entitlement_id"): the canonical key for metering attribution.
- GCP consumer billing account/project identifiers as provided by procurement payloads (for support + reconciliation).
- Redwood org_id and (optionally) a marketplace_subscription_id to support multi-subscription edge cases.

Notes:
- Entitlement propagation may be delayed; onboarding UX must provide retry guidance.
- Entitlement may be reassigned/updated (e.g., plan change); metering attribution must follow the current active entitlement.

## SKU / plan taxonomy (GCP)
We publish three primary purchase paths, aligned to internal packaging:
1) Hosted API (usage-based)
2) Dedicated (subscription + optional overage)
3) Private (subscription; usage may be “$0 metered” for auditability depending on plan)

Add-ons are attachable where allowed by GCP Marketplace plan structure:
- Compliance Pack (security/compliance features + evidence access + extended retention options)
- Observability Retention (extended logs/metrics retention)
- Premium Support (SLA/support tier)

Naming conventions (GCP-facing):
- Product family prefix: “Redwood Inference”
- Plan names: “Hosted”, “Dedicated”, “Private”, plus tier markers (e.g., Standard/Enterprise) where needed.
- Usage dimensions: lowercase snake_case; stable over time (do not rename once launched).

## Billing dimension catalog (GCP)
The table below is the authoritative set of GCP Marketplace billing dimensions and their mapping to Redwood internal meters.

Dimension requirements:
- Units must be unambiguous and consistent across docs, console, and invoices.
- Dimensions should be low-cardinality and stable (avoid per-model dimensions; model choice is a Redwood config, not a billing dimension).
- Where volume is large (tokens), we report in “1K” units to reduce event volume while preserving accuracy.

### Hosted API (usage-based) dimensions
| GCP dimension | Unit | What it covers | Redwood internal meter | Rounding/aggregation |
|---|---:|---|---|---|
| hosted_input_tokens_1k | 1 = 1,000 input tokens | Prompt/input tokens for chat/text generation, including system + developer messages | tokens_in | Aggregate hourly; round up to nearest 1K per hour per org+entitlement |
| hosted_output_tokens_1k | 1 = 1,000 output tokens | Completion/output tokens for chat/text generation (including streaming) | tokens_out | Aggregate hourly; round up to nearest 1K per hour per org+entitlement |
| hosted_embeddings_1k_tokens | 1 = 1,000 tokens embedded | Tokens processed by embedding endpoints (input text tokens) | embedding_tokens | Aggregate hourly; round up to nearest 1K per hour per org+entitlement |
| hosted_rerank_1k_items | 1 = 1,000 items reranked | Number of documents/items evaluated by rerank endpoints | rerank_items | Aggregate hourly; round up to nearest 1K per hour per org+entitlement |

Hosted notes:
- “Tokens” are counted using the serving model’s tokenizer, consistent with Redwood API usage analytics.
- For multi-part requests (tool calls, structured output), token counting follows the same accounting as existing Redwood hosted billing.
- If a request fails before inference begins (e.g., auth/validation), no usage is reported.
- If inference begins and fails mid-stream, usage is based on tokens actually generated and delivered (best effort); partial tokens are included.

### Dedicated (subscription + optional overage) dimensions
Dedicated on Marketplace is primarily subscription-priced (capacity reservation). We support optional overage/burst dimensions when contractually enabled.

| GCP dimension | Unit | What it covers | Redwood internal meter | Rounding/aggregation |
|---|---:|---|---|---|
| dedicated_capacity_month | 1 = 1 month | Reserved capacity subscription (GPU pool + isolation + SLA tier per plan) | dedicated_capacity_months | Charged via marketplace subscription; no usage reporting required for base reservation |
| dedicated_burst_gpu_hours | 1 = 1 GPU-hour | Approved burst usage beyond reservation (if enabled) | dedicated_burst_gpu_hours | Aggregate daily; report within 24h; round to 0.1 GPU-hour |
| dedicated_egress_gb | 1 = 1 GB | Customer-approved billable egress (rare; only if explicitly included in offer) | network_egress_gb_billable | Aggregate daily; round up to 0.1 GB |

Dedicated notes:
- By default, Dedicated plans should avoid surprise variable charges; burst/egress dimensions must be explicitly enabled in the offer and reflected in customer-facing FAQs.
- Capacity “size” (e.g., GPU type/count) is captured in the plan configuration, not as a usage dimension.

### Private (subscription) dimensions
Private is typically billed as a platform subscription (license + support). Some enterprise customers prefer “$0 usage reporting” for auditability; if used, those dimensions must remain non-billable and clearly documented.

| GCP dimension | Unit | What it covers | Redwood internal meter | Rounding/aggregation |
|---|---:|---|---|---|
| private_platform_month | 1 = 1 month | Private control plane subscription (VPC/on-prem package as scoped) | private_platform_months | Charged via marketplace subscription |
| private_compliance_pack_month | 1 = 1 month | Compliance add-on (controls, evidence access, audit log integrations, retention options) | compliance_pack_months | Charged via marketplace subscription |
| private_observability_retention_month | 1 = 1 month | Extended observability retention add-on | observability_retention_months | Charged via marketplace subscription |

Private notes:
- Any “usage” within Private (tokens, embeddings) is governed by the customer’s own infra capacity; we do not bill per token for Private unless explicitly structured as a hybrid offer.

## Metering integration expectations (engineering)
### Reporting cadence and windows
- Hosted dimensions: report aggregated usage at least hourly; target is within 2 hours of usage.
- Dedicated overage dimensions (if enabled): report daily; target within 24 hours.
- Backfill window: support at least 72 hours of late reporting for delayed event pipelines and reconciliation.

### Idempotency and retries
Metering events must be idempotent. Requirements:
- Use a deterministic idempotency key per (entitlement, dimension, time_bucket) to prevent double charges on retries.
- Retry on transient errors (429, 5xx) with exponential backoff and jitter.
- Hard-fail and alert on repeated authorization errors (401/403) or malformed payloads.

### Source of truth and auditability
- Redwood internal billing meters remain the source of truth for customer-visible usage analytics in the console.
- Marketplace reporting is a downstream projection; discrepancies must be explainable via logs and time buckets.
- Persist a metering ledger entry for every reported bucket with: entitlement id, org id, dimension, quantity, bucket start/end, report timestamp, response status.

### Entitlement state gating
Usage must only be reported when:
- Entitlement is ACTIVE, and
- Entitlement is linked to exactly one Redwood org (or an explicitly selected org in multi-org edge cases).

If entitlement is missing/unknown:
- Do not report usage.
- Console should show a blocking error with “Verify subscription” retry, and a path to support.

## Mapping Redwood usage → GCP dimensions (practical rules)
### Hosted: chat/text generation
- Compute tokens_in and tokens_out per request.
- Attribute usage to the request’s billing org.
- Resolve org → active gcp_entitlement_id.
- Aggregate into hourly buckets:
  - hosted_input_tokens_1k = ceil(sum(tokens_in) / 1000)
  - hosted_output_tokens_1k = ceil(sum(tokens_out) / 1000)

Rationale: rounding at the hourly bucket (not per request) reduces rounding error while keeping volume low.

### Hosted: embeddings
- Use embedding_tokens (tokenizer-consistent token count).
- Aggregate hourly:
  - hosted_embeddings_1k_tokens = ceil(sum(embedding_tokens) / 1000)

### Hosted: rerank
- Count rerank_items as the number of documents/items scored.
- Aggregate hourly:
  - hosted_rerank_1k_items = ceil(sum(rerank_items) / 1000)

### Dedicated: burst usage
Only applicable for offers that explicitly include burst overages.
- Measure burst_gpu_hours from scheduler/runtime utilization attribution (dedicated pool only).
- Aggregate daily:
  - dedicated_burst_gpu_hours = round(sum(burst_gpu_seconds) / 3600, 1)

### Add-ons
- Subscription add-ons (compliance/retention/support) should be represented as separate monthly subscription dimensions when supported by the plan structure.
- Do not attempt to meter add-ons by feature usage (e.g., “audit log exports”); keep procurement simple.

## Customer-visible billing semantics (what Support/Sales can claim)
- Marketplace charges are issued by Google under the customer’s GCP billing account.
- Redwood usage in the console is near-real-time; Marketplace invoicing may lag due to reporting and billing cycles.
- Token usage is reported in 1K-token units (input and output separately).
- Customers can reconcile by comparing:
  - Console usage export (tokens_in/tokens_out by day)
  - Marketplace invoice line items for the corresponding dimensions

## Reconciliation & dispute handling
When a customer reports a mismatch:
1) Confirm the entitlement id and billing org mapping (multi-subscription issues are the #1 cause).
2) Pull metering ledger entries for the disputed period (dimension + quantity + bucket timestamps).
3) Compare against console usage export for the same org and period.
4) If we under-reported: backfill within the allowed window.
5) If we over-reported due to duplication: identify duplicate idempotency key collision; coordinate correction path with Finance/Legal (see RevRec notes).

## Testing checklist (pre-submission)
- Subscribe in GCP Marketplace test environment; entitlement becomes ACTIVE.
- Link entitlement to a new Redwood org and to an existing org (both paths).
- Generate traffic for each Hosted endpoint type (chat, embeddings, rerank).
- Verify within 2 hours:
  - Usage appears in Redwood console
  - Metering ledger has reported buckets
  - GCP Marketplace shows expected dimensions
- Negative tests:
  - Entitlement inactive → usage not reported
  - Retry storms (simulate 429/5xx) → no duplication
  - Entitlement propagation delay → onboarding guidance is correct

- Approval from Product (Packaging), Finance (RevRec), and Engineering (Billing/Metering)
