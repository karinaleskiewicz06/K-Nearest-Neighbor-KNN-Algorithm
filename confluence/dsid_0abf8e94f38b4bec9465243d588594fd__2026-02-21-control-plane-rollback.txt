Postmortem: Control plane rollout rollback causing auth failures (policy sync)

h1. Summary
On 2026-02-21 we experienced intermittent authentication failures for API key validation immediately after a control-plane deployment rollback. The failures impacted hosted API traffic globally but were most visible in us-east due to higher throughput.

*Customer impact:* Yes (401/403 spikes, request failures)
*Severity:* SEV-2
*Owning engineering team:* Platform Engineering (Control Plane)
*Primary services:* control-plane, rbac-sync, api-key-verifier

h1. Impact
* Peak 0.9% of requests failed due to auth errors over 26 minutes
* Elevated support contacts from 3 enterprise customers
* Some clients exhausted retries and surfaced errors

h1. Timeline (UTC)
* 03:31 - Deploy initiated for control-plane 2.18.0
* 03:36 - Regression detected in tenant policy evaluation; rollback started
* 03:39 - Auth failure alert fired (api-key-verifier 401/403 spike)
* 03:43 - On-call identified rbac-sync lag and stale policy cache
* 03:49 - Forced full resync + cache invalidate across api-key-verifier
* 03:57 - Auth errors return to baseline

h1. Root cause
During rollback, rbac-sync reconnected to the previous policy schema but did not trigger a full resync. api-key-verifier instances continued to serve from a stale in-memory cache that referenced policy objects which no longer existed post-rollback. This produced intermittent auth failures depending on which verifier instance handled the request.

h1. Detection
Detected by automated alert on auth error ratio. The rollback itself was visible in deploy logs, but we did not have a guardrail alert tied to rbac-sync lag after rollbacks.

h1. Action items
1) Add rollback hook to force rbac-sync full resync + cache invalidation (Owner: Platform Eng; Due: 2026-03-15)
2) Add alert: rbac-sync lag > 60s sustained 5m (Owner: SRE; Due: 2026-03-10)
3) Update rollback runbook for control-plane to include verifier cache clear step (Owner: Platform Eng; Due: 2026-03-01)
