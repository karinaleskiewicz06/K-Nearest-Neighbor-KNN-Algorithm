Enterprise Compliance Pack — Product Definition (Pricing & Packaging)

## Purpose
The **Enterprise Compliance Pack** is a commercial packaging concept that standardizes what Redwood provides to enterprise buyers during security/compliance review and procurement—without promising roadmap items.

This page is the **single product definition** used by Product, Sales, Solutions Engineering (SE), Security/GRC, Legal, and Customer Success (CS) to:
- Align on what is included (capabilities, documentation, and support)
- Reduce deal-by-deal ambiguity in RFPs and questionnaires
- Ensure that customer-facing claims match current product behavior

> This doc defines *what we bundle and how we describe it*. It is not a feature roadmap.

---

## One-liner (GTM-facing)
**Enterprise Compliance Pack:** a bundled set of enterprise security capabilities plus compliance documentation access and defined response SLAs to streamline security review for Dedicated and Private deployments (and Hosted API under Enterprise plans).

---

## What the pack is (and is not)
### Included in the pack
The pack includes three categories:
1) **Enterprise security & governance capabilities** (authn/authz, logging, retention controls, etc.)
2) **Compliance documentation access** (under NDA where required) and standardized collateral
3) **Compliance enablement support** (defined SLAs for evidence requests and questionnaire support)

### Not included / not implied
The pack **does not**:
- Guarantee that Redwood meets every customer-specific control requirement (we provide standard control evidence + compensating controls where applicable)
- Include bespoke audits, custom attestations, or customer-specific certifications
- Promise HIPAA/BAA, FedRAMP, PCI-DSS, or other regulated-framework commitments unless separately contracted and approved by Legal + GRC
- Override regional/legal constraints around data residency and subprocessors

## Pack contents (what buyers get)
### A) Security capabilities (customer-facing)
These are capabilities we position as part of the compliance-ready enterprise offering. Always confirm mode-specific availability in the authoritative internal references.

1. **SSO (SAML 2.0)**
- SSO for Redwood Console (and admin surfaces as documented)
- Supported IdPs per internal reference

2. **Provisioning (SCIM)**
- SCIM provisioning for supported plans where enabled
- Group/role mapping behavior as documented

3. **Role-Based Access Control (RBAC)**
- Predefined roles with least-privilege defaults
- Coverage for Console and relevant API administration actions as documented

4. **Audit logging**
- Admin and security-relevant events (authentication, role changes, key actions, configuration changes)
- Export options where supported (e.g., SIEM/S3-style sinks) and retention controls per plan

5. **Data retention & deletion controls**
- Documented retention defaults and configurable options (where available)
- Support-assisted deletion requests process (where applicable)

6. **Encryption (in transit / at rest)**
- TLS for in-transit communications
- Encryption at rest for stored data components as documented
- Key management boundaries clearly stated by deployment mode (see below)

7. **Private deployment security options (Private only)**
- Customer-managed networking boundaries (VPC/on-prem)
- KMS/HSM integration options where supported
- Customer-controlled log routing/export where applicable

> Guardrail: Do not claim “full audit logging of all application data” or “all customer activity” unless the event taxonomy explicitly covers it. Use the audit logging overview.


### B) Compliance documentation and collateral
The pack standardizes which documents we provide and how they are requested.

**Included collateral (generally shareable without NDA unless marked):**
- **Enterprise Security FAQ** (current published version)
- Data retention & deletion overview
- Audit logging overview
- SSO/SCIM/RBAC capabilities overview (customer-facing excerpt or summarized view)
- Encryption & key management overview by deployment mode
- Subprocessor list (canonical, current)
- DPA template and security addendum (through Legal workflow)

**Controlled evidence (typically requires NDA, provided via evidence request process):**
- SOC 2 report (and/or bridge letter if applicable and approved)
- Pen test summary letter or executive summary (if available and approved for sharing)
- Vulnerability management and IR program summaries (sanitized)

Evidence distribution must follow: **SOC 2 / evidence request playbook**.


### C) Enablement support (response SLAs)
The pack includes defined support commitments for procurement and security review.

| Support item | Standard commitment | Owner team |
|---|---|---|
| Evidence request triage | Acknowledge within 1 business day | GRC |
| Standard evidence package delivery (under NDA, if required) | Target 5 business days after NDA is confirmed | GRC |
| Security questionnaire / RFP guidance using approved library | Target 5 business days for first pass (scope-dependent) | Solutions Engineering + Security/GRC |
| Live security review call | Scheduling support within 5 business days (subject to availability) | SE + Security |
| Exceptions / non-supported control requests | Escalation and approved alternative language within 3 business days after intake | Security/GRC + Product + Legal (as needed) |

> Commercial note: Any “expedite” commitments must be approved by GRC lead (Olga Petrov) and reflected in the deal’s order form / SOW if contractual.

## Deployment-mode specifics (required language boundaries)
When describing the pack, always include the deployment mode context.

### Hosted API (Enterprise plan)
- Position as: enterprise-grade controls + standardized compliance collateral + defined SLAs.
- Avoid implying: customer-managed keys/HSM, air-gapped operation, or full customer-controlled network boundaries.

### Dedicated
- Position as: data isolation via dedicated capacity + enterprise controls.
- Avoid implying: single-tenant control plane or on-prem equivalence unless explicitly true for the configuration.

### Private (VPC / on-prem where supported)
- Position as: strongest customer control boundary (networking, key management options, log routing).
- Avoid implying: “no subprocessors” or “customer owns every component” unless contractually and technically accurate.

## Commercial packaging rules (how it’s sold)
### How Sales should attach the pack
- The pack should be included on enterprise quotes as a **named line item** (or explicitly included in the Enterprise plan bundle) to avoid ambiguity.
- Use the canonical naming: **“Enterprise Compliance Pack”**.

### What it can and cannot change
- The pack can bundle **support + documentation access + enterprise controls** into a consistent offering.
- The pack cannot be used to override the **evidence request process**, confidentiality rules, or legal review requirements.

### Add-ons (separate from the pack)
These are frequently confused with the pack. They must be priced/approved separately if offered:
- Extended audit log retention beyond standard plan limits
- Premium evidence response SLAs (e.g., < 72 hours) or dedicated GRC support
- Custom attestations or customer-specific reports
- Regulated workload commitments (HIPAA/BAA, FedRAMP, etc.)

## Standard customer-facing phrasing (approved structure)
Use the following structure in emails, RFPs, and security questionnaires.

**Recommended blurb:**
“Redwood offers an Enterprise Compliance Pack that bundles enterprise access controls (SSO/RBAC), audit logging and export options (where supported), documented retention/deletion controls, and standardized compliance collateral. Under NDA, Redwood can provide audit reports and additional evidence through our formal evidence request process. The pack also includes defined response SLAs for evidence requests and security questionnaires to streamline procurement.”

**Avoid:**
- “ISO 27001 certified” (unless explicitly true and confirmed by GRC)
- “We never store prompts/logs” (retention varies by feature and configuration; use the retention overview)
- “We don’t use any customer data” (use the approved “training/data use” language in the Security FAQ)

## FAQ (internal)
**Q: Is the Enterprise Compliance Pack required for all enterprise deals?**
A: It is recommended for Dedicated/Private deals where procurement includes security/compliance review. For smaller enterprise Hosted deals, include only if the customer requests formal evidence/SLAs.

**Q: Does the pack guarantee SOC 2 report access?**
A: Access is provided **under NDA** and through the evidence request process. Eligibility and timing depend on NDA completion and request scope.

**Q: Can we promise a pen test report?**
A: Do not promise a full report. If a summary is shareable, it must be distributed via GRC with approved language.

**Q: Can we include customer-specific retention terms in the pack?**
A: The pack describes standard capabilities and options. Any bespoke retention obligations must go through Product + Legal and be written into contract terms.
