Console Help: Usage Insights (Route + Model Cost Drivers)

## Overview
Usage Insights helps you understand and reduce inference spend by breaking cost and usage down by **API route** and **model** (for example: `/v1/chat/completions` on `llama-3.1-70b`).

This page explains:
- How route/model breakdowns are computed and how to interpret the metrics
- What “Top cost drivers” and “What changed?” mean (and what they do not)
- Common pitfalls (streaming, retries, fallbacks, cache behavior, model aliases)
- How to reconcile Insights totals with billing
- What optimization levers to try next

> Note: Usage Insights is in beta. Some workspaces may not have access, and some dimensions may be partially populated depending on instrumentation and deployment mode.

---

## Who can see cost data?
Usage Insights surfaces cost data, which is controlled by workspace RBAC.

You can typically:
- View usage-only metrics (requests/tokens) with standard developer roles.
- View **cost** and **exports** only if your role includes cost visibility and export permission.

If you see a “Cost is hidden for this workspace” message:
1) Ask a workspace admin to enable cost visibility.
2) Confirm your role includes the **Cost: View** permission.
3) If exporting is blocked, confirm **Cost: Export** is enabled.

For restricted workspaces (regulated / private deployments), additional export controls and audit logging may apply.

## Key concepts
### Route (what we mean by “route”)
A route is the canonicalized API path used for grouping requests. Routes are **normalized** to avoid high cardinality.

Examples:
- Raw path: `/v1/files/abc123/content` → Normalized route: `/v1/files/{file_id}/content`
- Raw path: `/v1/organizations/42/keys` → Normalized route: `/v1/organizations/{org_id}/keys`

Why this matters:
- Normalization improves reporting stability and prevents a breakdown table with one row per ID.
- If a client uses unusual paths or proxies that alter the URL, the route may appear as `unknown` or be grouped unexpectedly.

See also: Route normalization ADR (internal): `adr-route-normalization-and-attribution`.

### Model (family, version, alias)
Usage Insights reports by a stable model identifier intended for billing and reporting (e.g., `llama-3.1-70b`).

Important:
- Some models have aliases (for example, a friendly name that maps to a pinned version).
- A single “model” in the UI may group multiple internal revisions if you have version bucketing enabled.

If you see what looks like duplicates, check whether you are filtering on a model alias vs family/version (see Troubleshooting).

### What is “cost” in Usage Insights?
Cost reflects usage-based charges attributable to inference requests (tokens and related compute overhead). It is designed to match billing totals within expected tolerance, but timing differences can occur.

Common cost contributors:
- Input tokens (“tokens in”)
- Output tokens (“tokens out”)
- Retries and fallbacks (additional requests that still incur usage)
- Streaming overhead (additional protocol + bookkeeping cost; usually small, but visible at scale)
- Cache misses (more compute per request when caching is ineffective)

## Understanding the main breakdown table
The primary view is a table grouped by **Route × Model** for a selected time range.

### Recommended workflow
1) Start with **Last 7 days**.
2) Filter to a single **project/environment** if totals look surprising.
3) Sort by **Cost** to identify top spend areas.
4) Drill into the largest row(s) to see drivers and distribution metrics.
5) Use “What changed?” to understand week-over-week shifts.

### Metrics you’ll see (definitions)
| Metric | Meaning | Why it matters |
|---|---|---|
| Requests | Count of successful request attempts attributed to the route/model group | Helps normalize per-request cost |
| Tokens in | Total input tokens sent to the model | Large prompts drive cost and latency |
| Tokens out | Total output tokens generated | Often the primary cost driver for chat routes |
| Avg context length | Average tokens in per request (or distribution buckets in drilldown) | Long-tail prompts can dominate spend |
| Cache hit rate | % of requests served using prefix/KV cache | Lower hit rate increases compute cost |
| Retry rate | % of requests that were retried (client or server) | Retries can double-charge usage patterns |
| Fallback rate | % of requests served by a fallback model/region/tier | Changes model mix and cost unexpectedly |
| p50/p95 latency | Latency percentiles for the group | High latency can correlate with higher unit cost |

> Attribution note: Retries and fallbacks are attributed to the route that initiated them. If a fallback changes the model, the spend will appear under the **actual model that served the response**, while the driver explanation will call out the fallback.

## Top cost drivers: how to interpret
Top cost drivers highlights the biggest contributors to spend and the likely reason(s).

### Common driver explanations
- **Output tokens increased**: tokens out per request grew (often due to higher `max_tokens`, more verbose prompts, or changes in system instructions).
- **Model mix shifted**: more traffic moved to a larger model (or a higher-priced deployment mode).
- **Cache hit rate dropped**: fewer requests benefited from caching (prompt prefixes changed, cache disabled, or traffic became more diverse).
- **Retries increased**: timeouts/rate limits caused repeated attempts.
- **Fallbacks increased**: capacity constraints or policy changes routed traffic to a different model/region/tier.
- **Context length drifted upward**: prompts got longer or included more history than expected.

### Guardrails (what drivers do NOT mean)
- A driver is not a root-cause diagnosis. It is a “best explanation” based on available telemetry.
- A change can be caused by product launches, prompt changes, SDK upgrades, retry policy changes, or traffic growth.
- If freshness is degraded, drivers may be incomplete (see Data freshness).

## What changed? (deltas) and common interpretations
The “What changed?” view compares the current period to a previous baseline (for example, this week vs last week).

Typical insights:
- **Cost up 35% WoW** with flat requests → per-request cost increased (tokens out, retries, or model mix).
- **Tokens in up, tokens out flat** → prompts got longer (possible history growth).
- **Cache hit down** with stable prompts → traffic became more varied, normalization changed, or cache settings changed.
- **Fallbacks up** alongside higher latency → capacity/routing issues; check model availability and routing policy.

Recommended next steps:
1) Confirm whether the change is isolated to one route or one model.
2) Check deployment mode/region filters.
3) Review recent prompt/template changes and SDK release notes.
4) If retries increased, review timeout and idempotency behavior in the client.

## Data freshness and partial data
Usage Insights is powered by aggregated telemetry. Some events may arrive late.

If you see a banner like “Data may be incomplete for the last N minutes/hours”:
- Treat totals and deltas as directional until the freshness window closes.
- For reconciliation vs billing, prefer time ranges that end at least **2–4 hours** before “now” (beta guidance).

## Reconciling Usage Insights with billing
Usage Insights is designed to match billing totals, but small differences can occur.

### Expected reasons for differences
- **Aggregation lag / late events** (especially near the current time)
- **Rounding** differences between line-item rollups and invoice totals
- **Time zone boundaries** (Insights uses workspace reporting timezone; invoices may use UTC or contract-defined timezone)
- **Model alias bucketing** (same underlying model counted under different labels if filters are inconsistent)

### Recommended reconciliation checklist
1) Use the same exact time window on both sides (including timezone).
2) Avoid “up to now” windows; end the range a few hours earlier.
3) Confirm the same workspace/project filters.
4) If exports are used for finance workflows, prefer the **CSV export** totals (they use the same rollup logic as billing reconciliation checks).

If you still see a mismatch:
- Capture the time range, workspace, route/model filters, and screenshot of totals.
- File a support ticket with the subject “Usage Insights vs invoice mismatch” and include your export CSV.

## Common pitfalls (and how to fix them)
### 1) Streaming responses look “more expensive”
Symptoms:
- Cost is higher for routes that use streaming vs non-streaming.

What’s happening:
- Streaming can add overhead and can also encourage longer completions (users wait less and allow longer outputs).

What to do:
- Check whether `max_tokens` increased.
- Compare tokens out/request between streaming and non-streaming traffic.
- Consider enforcing a server-side cap on output tokens for specific routes.

### 2) Retries inflate spend
Symptoms:
- Retry rate increases; cost rises without proportional user-visible success.

Common causes:
- Aggressive client timeouts
- Lack of idempotency keys (causing duplicated work)
- Backoff policy too fast

What to do:
- Increase client timeouts for long-context requests.
- Use idempotency keys where supported.
- Implement exponential backoff and stop retrying on deterministic errors.

### 3) Fallbacks change model cost unexpectedly
Symptoms:
- Model mix shifts toward larger (or more expensive) models; fallback rate increases.

What’s happening:
- Smart routing may fall back when capacity is constrained or policy changes.

What to do:
- Review routing policy for the project/environment.
- Consider pinning a model version/tier for critical routes.
- If the fallback is undesirable, contact your Redwood account team to review capacity options.

### 4) Cache hit rate drops after a prompt change
Symptoms:
- Cache hit rate decreases after a release; cost/latency increase.

Common causes:
- Prompt prefix changes in system instructions
- Dynamic headers/timestamps inserted early in the prompt
- Conversation history moved ahead of stable instructions

What to do:
- Keep a stable prompt prefix as early as possible.
- Move dynamic fields later.
- If you batch similar requests, ensure prompt formatting is consistent.

### 5) Missing route breakdown for OpenAI-compatible endpoints
Symptoms:
- Requests appear under `unknown` route or are grouped unexpectedly.

What to do:
- Confirm the client is calling a supported path and not rewriting the URL via proxy.
- Ensure the latest route normalization mapping is enabled for OpenAI-compatible endpoints.
- If the issue persists, export raw request logs (if available) and contact support with example paths.

### 6) Timeouts when querying long ranges (e.g., 30 days)
Symptoms:
- Insights page errors or times out on large time windows.

What to do:
- Start with 7 days and export CSV for longer time windows.
- Use additional filters (project, route, model) before expanding the date range.
- If you consistently need 30+ day interactive queries, contact support—your workspace may need additional pre-aggregation.

## Exporting reports (CSV) and sharing
### CSV export
Use CSV export for finance workflows (chargeback, budget tracking) and for BI ingestion.

Export behavior:
- Exports are generated server-side and may take time for large ranges.
- Downloads may require additional permissions and are audit logged.

Tips:
- Prefer daily or hourly buckets for large windows (rather than “all-time”).
- Keep route/model filters consistent with your internal reporting categories.

### Shareable reports (link)
If enabled for your workspace, you can generate a shareable link with RBAC enforcement.

Guidance:
- Share links only with users who should have access to cost data.
- If a viewer lacks permissions, they will see a “permission denied” state rather than partial results.

## Optimization levers (what to try next)
Use these levers after you identify the top spend rows in the breakdown.

### Prompt and output controls
- Reduce output verbosity (tighten instructions; lower `max_tokens`).
- Summarize or truncate long histories.
- Move dynamic content later in the prompt to improve caching.

### Caching
- Stabilize prompt prefixes to improve cache hit rate.
- Avoid embedding timestamps/UUIDs early in the prompt.
- If you’re unsure whether caching is active for a deployment mode, check the project’s serving settings.

### Batching
- For high-throughput routes (embeddings, reranking, short completions), batching can reduce unit cost.
- Watch latency SLOs—over-batching can increase p95 latency.

### Routing and model selection
- For routes with high volume and low complexity, consider a smaller model.
- Use a larger model only where quality requires it; keep an explicit allowlist of routes.
- If fallbacks are driving unexpected cost, consider pinning models or adjusting routing constraints.

### Retry policy hardening
- Add idempotency keys.
- Use exponential backoff.
- Treat timeouts as a signal to adjust client timeouts or request size.

## FAQ
### Why is cost higher even though requests are flat?
Per-request cost can increase due to tokens out, context length, retries, lower cache hit rate, or a model mix shift.

### Why does the same route appear with multiple models?
The route is grouped independently from model; if you changed models over time (or fallbacks occurred), you’ll see multiple rows.

### Are “Top cost drivers” recommendations automated actions?
No. Usage Insights provides guidance and links, but does not automatically change your batching/caching/routing settings.
