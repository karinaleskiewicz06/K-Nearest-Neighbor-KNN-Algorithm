model-quantization-pipeline-runbook

## Purpose and scope
This runbook captures the model selection, quantization choices, and prompt/pipeline tuning we use for customer POCs and early production deployments. The goal is a reproducible set of recommendations and an ops playbook that balances predicted unit cost and latency constraints while preserving required quality for customer queries.

This page is intentionally practical: benchmark numbers, tradeoffs, and step-by-step tests to run in follow-up engagements. Benchmarks are updated to reflect our current runtime builds and kernel support as of Mar 2026.

## When to use this runbook
Use this runbook when:
- A customer has an explicit latency SLO and a hard cost-per-response target.
- You are selecting between 7B–13B class models with quantization.
- You need a default deployment configuration plus a higher-quality fallback path.

## Customer constraints and profile (reference template)
Replace the following with customer-specific values:
- Latency SLO: p50 < 120ms, p95 < 350ms for short queries (< 256 tokens).
- Throughput: sustained 120 requests/minute with bursts to 500 RPM for peak events.
- Quality bar: retrieval-augmented answer correctness > 93% on the customer evaluation set (recommended minimum: 1k+ queries).
- Security: private deployment preferred (VPC); avoid external prompt logging for sensitive inputs.
- Budget: per-response cost target equivalent to a 7B-class int8 profile at ~0.75–0.85x the current hosted baseline.

## Testing harness summary (how we measure)
### Workloads
- Synthetic load generator: 3 profile types
  - Short chat (typical interactive)
  - Medium prompt (128 tokens)
  - Long generation (512 tokens)
- Run each workload under:
  - Cold start (fresh process or empty cache)
  - Warm cache (steady-state with KV/prefix cache enabled)

### Metrics captured
- Latency: avg, p50/p95/p99
- Throughput: requests/sec, tokens/sec
- Hardware: GPU utilization, memory headroom, queue depth
- Quality: accuracy on eval set; hallucination rate (manual review on a 150-item subset is recommended)
- Cost estimator: tokenized input+output token counts × profiled per-token inference cost per model/quant

### Reproducibility requirements
- Record: model hash, quant builder version, quant seed (if applicable), tokenizer version, runtime version, CUDA/driver versions.
- Persist: a golden eval set (>=1k) and a smaller “smoke” set (100–200) for quick regressions.

## Model family candidates and rationale (shortlist)
The shortlist below reflects what we see most often for latency- and cost-sensitive deployments.

- Mistral-7B Instruct (v0.3) + 8-bit equivalent (NF4/int8)
  - Strong instruction following, reliable latency when quantized, good default for cost-sensitive customers.
- Llama-3 8B Instruct (int8)
  - Typically higher quality than older 8B/7B baselines; can be used as the “high-quality” lane when 13B is too expensive.
- Llama-2 13B (4-bit/8-bit)
  - Still used in some private deployments due to existing validation; higher KV cost; consider migrating to Llama-3 where allowed.
- Falcon-7B Instruct (int8)
  - Predictable latency on older GPUs; quality may be lower on instruction-heavy tasks; use as a cost-first variant when already validated.
- Open-weights alternatives (7B/3B class)
  - Useful when customers require permissive licensing; quantization maturity varies by toolchain.

## Quantization profiles and quick guidance
### Profiles tested
- NF4 (8-bit equivalent, kernel-supported in our private runtime)
  - Best quality/size ratio in many 7B-class tests; recommended default for supported runtimes.
- Int8 (bitsandbytes-style or native int8 kernels with fp16/bf16 residuals)
  - Fast and stable on modern GPUs; generally predictable; occasionally sensitive to tokenizer/normalization edge cases.
- 4-bit (AWQ or GPTQ)
  - Largest cost wins (often ~1.6–2.5× over int8 depending on workload) but more brittle.
  - Current guidance: prefer AWQ when available; use GPTQ when AWQ kernels are not supported.
  - Use only when latency/cost is the uppermost priority and you can add a fallback to a higher-quality model for difficult queries.

### Practical guidance (default selection)
- If the customer has a strict correctness bar on retrieval-grounded QA: start with NF4 or int8.
- If the customer has a strict p95 latency bar and moderate quality tolerance: evaluate 4-bit with a fallback plan.
- If the environment is heterogeneous (mixed GPU families): prioritize the most predictable kernel path (often int8).

## Bench summary (representative numbers from lab runs)
These are representative of Redwood lab runs (not guarantees). Expect ±10–15% variance with different drivers, CUDA versions, and kernel builds.

- Mistral-7B Instruct v0.3 NF4 on L4:
  - p50=78ms, p95=190ms, tokens/sec=350, memory headroom=4.1GB
  - eval accuracy=94.2%
  - cost per 256-token response ~= $0.0016
- Llama-3 8B Instruct int8 on A10G:
  - p50=92ms, p95=235ms, tokens/sec=330, memory headroom=3.0GB
  - eval accuracy=95.0%
  - cost per 256-token response ~= $0.0021
- Falcon-7B int8 on T4:
  - p50=115ms, p95=275ms, tokens/sec=290
  - eval accuracy=91.3%
  - cost per 256-token response ~= $0.0014
- Mistral-7B 4-bit (AWQ) on L4:
  - p50=66ms, p95=175ms
  - eval accuracy=90.4% (regression vs NF4)

## Interpretation and recommended default deployment
### Default lane (balanced)
- Default deploy: Mistral-7B Instruct v0.3 with NF4 on a dedicated GPU pool.
- Rationale: meets typical latency and accuracy targets with acceptable cost and stable behavior.

### High-quality fallback lane
- Recommended fallback: Llama-3 8B Instruct int8 (or validated 13B-class model if required).
- Trigger: queries flagged as high-complexity by routing signals (see below).

### Aggressive low-cost lane (optional)
- Consider 4-bit AWQ for non-critical flows (batch summarization, classification, or low-stakes suggestions).
- Require: explicit fallback plan and quality gates.

## Prompting and pipeline tuning (practical recipes)
1) System + context framing
- Use a short system message tuned to reduce verbosity.
- Example: “You are a concise assistant for product search. Provide factual answers, one paragraph max unless asked for detailed steps. Cite product IDs when relevant.”

2) Retrieval augmentation
- Recommended: top-k=5 for most catalog-style QA.
- Include source metadata (title, price) in a structured block inside context.
- Keep a fixed-length context window (truncate older docs) to avoid variable latency.

3) Safety and guardrails
- Add explicit stop sequences and a short post-filter for PII.
- If privacy required: offload PII redaction to a lightweight service before calling the model.

4) Temperature and decoding
- Default temp=0.0–0.15 for deterministic answers.
- Use higher temperature (e.g., 0.6) only for creative flows.
- Typical settings: top-p=0.9, top-k=40; reduce for shorter completions to improve stability.

5) Few-shot patterns
- For structured output (e.g., JSON fields): prefer 2–3 short examples.
- Keep examples consistent with expected tokenization footprint.

## Prompt failure detection and routing
### Heuristic triggers (post-response)
- Length mismatch or truncation
- Repetition loops
- Verification failure vs retrieval (e.g., missing required citations)

### Classifier-based detection
- Use a small binary classifier to decide whether to rerun on the fallback lane.
- If flagged: synchronous retry to the fallback model with the same prompt + expanded context.
- Always cache first-run results for audit and debugging.

## KV/prefix cache and batching notes
- Prefix caching for common query prefixes can yield ~40–55% per-token latency improvements in warm-cache conditions on 7B-class models (varies by runtime and GPU).
- Cold-start p95 spikes can be 2–3× warm p95; measure both and plan capacity accordingly.
- Continuous batching guidance:
  - Interactive flows: max_batch_size=8, max_wait_ms=10–15
  - Async summarization: batch_size=32–64, max_wait_ms=80–120
- Tokenization alignment:
  - Canonicalize whitespace and punctuation before tokenization to reduce token count variance.

## Operational rollout and canary plan
1) Build quantized artifacts and validate in staging on the same GPU family planned for production.
2) Canary at 5% traffic for 24h; capture latency/error/cost metrics and run automated correctness checks on sampled requests.
3) Expand to 25% if no regressions; then 100% over 48–72h.
4) Auto-failover criteria:
- p95 latency degrades >20% vs baseline, OR
- eval accuracy drops >2% on sampled checks, OR
- 5xx error rate exceeds thresholds.

## Monitoring signals and alert thresholds (suggested)
- Latency:
  - p95 increase > 20% (10m window) -> page SRE
  - p99 increase > 40% (10m window) -> page
- Error rate:
  - 5xx > 0.5% for 10m -> page
- Quality regressions:
  - daily eval accuracy drop > 1.5% -> alert Applied ML + Solutions Engineering
- Cost drift:
  - 7-day rolling cost >10% above forecast -> alert Finance + owner team

## Runbook for common incidents (quick actions)
### High p95 after deploy
1) Check GPU utilization and queue depth.
2) Roll back canary by switching routing to previous model/quant profile.
3) If rollout must remain: increase pool capacity or reduce batch windows temporarily.
4) Validate warm-cache settings and confirm KV/prefix cache is enabled.

### Unexpected accuracy regression
1) Re-run a 200-sample eval against the exact quant artifact (not source fp16).
2) Run deterministic decode (temp=0.0) to isolate sampling variance.
3) If confirmed: roll back, open a quantization incident, and attach builder logs + seed.
