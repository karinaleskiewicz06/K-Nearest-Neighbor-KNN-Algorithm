Emergency secret rotation during an incident

# Goal
Provide a coordinated process for rotating secrets quickly during an active incident (suspected compromise or immediate containment need).

# Decision: do we rotate now?
Rotate immediately if any of the following are true:
- credible evidence of secret exposure
- abnormal access patterns consistent with key misuse
- vendor reports compromised credentials
- attacker has access to systems that can read secrets

If impact is purely availability (no compromise signal), prefer standard mitigation first; emergency rotation adds risk.

# Roles
- Incident Commander (IC): authorizes emergency rotation and prioritizes which secrets first
- Ops/SRE: executes changes and monitors service health
- Security: advises on scope and evidence capture
- Service owners: update consumers and validate functionality

# Procedure
1. Declare in incident channel: 'Emergency secret rotation in progress' and list candidate secrets (names/paths only).
2. Link the break-glass event (if used) and ensure audit logging is on.
3. Identify rotation order:
   - Tier 0 first (signing keys, privileged service tokens)
   - Tier 1 next (DB creds, message bus creds, third-party keys with broad scopes)
4. For each secret:
   - confirm consumers from the Credential Dependencies inventory
   - choose rotation pattern (dual-valid if available; cutover otherwise)
   - rotate issuer-side credential
   - update Vault/secret store
   - restart/redeploy consumers as required
   - validate per-service health (auth failures, latency, error rate)
5. If failures persist beyond 10 minutes and customer impact is increasing, pause and reassess: rollback vs continue rotation.
6. Record exact timestamps for issuer-side change and consumer rollouts.

# Communications
- Do not paste secret values in Slack, tickets, or docs.
- If customer impact is expected, coordinate with Support for messaging.

# After-action requirements
- Ensure break-glass access is revoked.
- File a post-incident review item that lists rotated secrets, impacted services, and any follow-up rotations needed (derived tokens, cached credentials).
