Production secret rotation runbook

# Purpose
This runbook provides a repeatable procedure for rotating production secrets used by Redwood services. It covers both planned and emergency rotation patterns.

# Preconditions
- Identify the secret name/path and all consumers (see Credential Dependencies page).
- Confirm rotation type: planned vs emergency.
- Ensure appropriate access (normal approvals or break-glass for emergencies).

# Rotation patterns
## Pattern A: Dual-valid window (preferred)
Use when the downstream system can accept two credentials temporarily (e.g., JWT verification keys, API keys with overlap).

Steps:
1. Generate new credential.
2. Store new credential in Vault under a new version (do not delete old).
3. Update consumers to read the latest version and accept both old+new if applicable.
4. Deploy changes.
5. Observe auth success metrics for at least 30 minutes.
6. Disable old credential at the issuer (or mark old as deprecated).
7. Remove old credential from Vault after the deprecation window (default 7 days unless otherwise specified).

## Pattern B: Cutover (use with caution)
Use when only one credential can be active (e.g., some database passwords).

Steps:
1. Schedule a short change window and ensure on-call coverage.
2. Reduce autoscaling noise where possible (avoid concurrent deploys).
3. Generate new credential but do not activate it yet.
4. Apply credential change at the issuer (DB/IdP/provider).
5. Immediately update Vault with new value.
6. Restart/redeploy all consumers to pick up the new value.
7. Validate service health; if failures persist, roll back or restore prior credential if possible.

# Emergency rotation procedure
If compromise is suspected:
1. Open an incident and declare emergency rotation.
2. Use break-glass if required; minimize secret exposure in chat (never paste secret values).
3. Rotate the highest-risk secrets first (Tier 0 then Tier 1).
4. For widely shared credentials, consider temporarily disabling the credential before cutover if safe.
5. After containment, enumerate all downstream consumers and rotate any derived tokens.

# Documentation requirements
- Planned rotation: create a change record with impacted services, steps, and validation.
- Emergency rotation: document in incident timeline and follow up with a postmortem action list.

# Common secret types
- Database credentials (Postgres): prefer dual-user approach (create new user, grant perms, migrate consumers, remove old user).
- Third-party API keys: keep overlap window, update key scopes to minimum required.
- Signing keys: rotate via key ring; services must trust both keys during overlap.

# Rollback guidance
- If you can revert consumers faster than reverting the issuer, revert consumers first.
- If reverting the issuer is required, coordinate carefully and document the exact timestamps of each change.
