Structured Output & JSON Schema Guidance (Examples + SDK Parity)

## Purpose
This page defines Redwood’s canonical guidance for **structured output** examples that use **JSON Schema constraints**. It is written for SDK authors and docs/example maintainers.

Goals:
- Ensure examples across Python/TypeScript/Go show the same mental model.
- Make “copy/paste” snippets resilient (validation, retries, safe fallbacks).
- Avoid implying stronger guarantees than the model/runtime provides.

Non-goals:
- Changing the underlying Hosted API protocol.
- Guaranteeing 100% valid JSON across all models without validation/retry.

---

## What we mean by “structured output”
In Redwood docs and examples, **structured output** means:
- You provide a **JSON Schema** describing the shape of the assistant’s response.
- The model is instructed (and, where supported, constrained) to return JSON matching that schema.
- The client **validates** the final output and applies a **repair/retry** path when validation fails.

Important: Structured output is a *best-effort constraint* and may vary by model family. Examples must include validation and an explicit fallback.

Terminology:
- Use: **Structured output** (preferred) and **JSON Schema**.
- Avoid: “guaranteed JSON” or “always valid JSON”.

---

## Recommended schema patterns (what to show in examples)
### 1) Keep schemas small and explicit
Prefer:
- `type: object`
- explicit `properties`
- `required` listing
- `additionalProperties: false`

Avoid for examples (unless the guide is specifically about these topics):
- Deeply nested polymorphism (`oneOf`/`anyOf` chains)
- Unbounded `patternProperties`
- Very large enums

Why: Examples should be robust and easy to validate consistently across SDKs.

---

### 2) Prefer “closed world” objects
Use `additionalProperties: false` to prevent drift and reduce parsing ambiguity.

Example (canonical):
```json
{
  "name": "support_ticket_summary",
  "schema": {
    "type": "object",
    "additionalProperties": false,
    "properties": {
      "title": { "type": "string" },
      "severity": { "type": "string", "enum": ["low", "medium", "high"] },
      "customer_impact": { "type": "string" },
      "next_actions": {
        "type": "array",
        "items": { "type": "string" },
        "minItems": 1
      }
    },
    "required": ["title", "severity", "customer_impact", "next_actions"]
  }
}
```

---

### 3) Use “stringly-typed” fields sparingly
If a field is inherently unstructured (freeform text), keep it as a `string`. Otherwise, prefer structured subfields.

Prefer:
- `"date": {"type":"string","format":"date"}` (if the validator supports it)
- `"confidence": {"type":"number","minimum":0,"maximum":1}`

Avoid:
- stuffing multiple pieces of data into a single string (e.g., “severity: high; owner: …”).

---

### 4) Arrays: constrain item shape and size
Always specify `items`. Consider `minItems`/`maxItems` for example schemas.

Example:
```json
{
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "steps": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "properties": {
          "action": { "type": "string" },
          "rationale": { "type": "string" }
        },
        "required": ["action"]
      },
      "minItems": 1,
      "maxItems": 10
    }
  },
  "required": ["steps"]
}
```

---

### 5) Optional fields: omit vs null (pick one)
In examples, prefer **omitting** optional fields rather than setting them to `null`.

If you allow `null`, do so explicitly:
- JSON Schema (2020-12 style): `"type": ["string", "null"]`

But for cross-language examples, omission is simpler and less error-prone.

---

## Prompting guidance (model-agnostic)
Even when using a schema, include a short system/developer instruction that clarifies:
- Output must be **valid JSON**.
- Output must **match the schema**.
- Do not wrap JSON in markdown code fences.
- Do not include commentary outside JSON.

Example instruction snippet:
- “Return ONLY a JSON object that matches the schema. Do not include markdown, code fences, or additional keys.”

---

## Validation requirements (all SDK examples)
Every structured-output example MUST:
1) Parse the final assistant message as JSON.
2) Validate it against the declared schema.
3) On failure, follow a documented fallback (repair/retry).

### Validator choices by language (recommended)
These are recommendations for examples; product usage may vary.

| Language | Recommended validator for examples | Notes |
|---|---|---|
| Python | `jsonschema` (Draft 2020-12 if available) | Clear errors; widely used. Keep dependencies minimal in examples repo.
| TypeScript | `ajv` | Fast, good errors; pin a stable version in runnable examples.
| Go | `github.com/santhosh-tekuri/jsonschema/v5` | Mature and supports modern drafts; validate after full JSON is assembled.

If an example must remain dependency-free (e.g., README snippet), it can do basic shape checks, but must clearly label it as **minimal validation** and link to the runnable example with full validation.

## Streaming caveats (incremental JSON + partial deltas)
### Key rule
**Do not attempt to `JSON.parse` on every chunk**.

Streaming responses can contain:
- Partial tokens that cut JSON strings mid-character.
- Partial objects that are syntactically invalid until completion.
- Model “self-correction” (earlier text is later contradicted) depending on the streaming event model.

Canonical approach in examples:
1) **Accumulate** text deltas into a buffer for the assistant message.
2) Wait for the **final** event indicating completion.
3) Then parse+validate the complete buffer.

### When to do incremental work during streaming
Allowed during streaming:
- Emit partial text to the console/UI.
- Track telemetry counters (e.g., bytes received, stream disconnects).
- Detect clear non-JSON prefixes early (optional): e.g., if the first non-whitespace char is not `{` or `[`.

Not recommended in examples:
- Incremental JSON parsing.
- Attempting to validate before completion.

### Handling disconnects
If the stream disconnects mid-response:
- Treat the buffer as incomplete.
- Retry the request with an idempotency key (where supported) or reissue with a short “continue” message (only if the model family reliably supports continuation; otherwise restart with the same inputs).
- Log the event with enough context: model, request_id, bytes received, and whether the buffer looked like JSON.

## Safe fallback patterns (repair + retry)
Examples should use one of the following fallbacks.

### Fallback A (preferred): one repair attempt, then full retry
1) Parse+validate.
2) If invalid, make a second call:
   - Provide the raw invalid output.
   - Ask the model to return a corrected JSON matching the schema.
3) Parse+validate the repair result.
4) If still invalid, retry the original request once with stricter instructions.

Repair prompt pattern (keep short):
- “The following JSON did not validate against the schema. Return ONLY corrected JSON that matches the schema. Do not add extra keys.”

### Fallback B: strict restart only
If the domain is sensitive and you do not want the model to “reinterpret” an invalid output, do a single restart:
- Reissue the same request with a stricter instruction and (optionally) a smaller schema.

### Fallback C: degrade to plain text
For user-facing apps that must remain responsive:
- If validation fails after N attempts, return the model’s best effort as plain text with a warning flag at the application layer.
- Docs/examples must clearly label this as “application fallback” and not a platform guarantee.

Recommended retry budget for examples:
- Max attempts: **2 total calls** (initial + one repair) for quickstarts.
- Max attempts: **3 total calls** (initial + repair + strict retry) for SDK guide examples.

## Error handling and logging guidance
### What to log (examples and quickstarts)
At minimum:
- `request_id` (if available)
- model name/version
- whether streaming was enabled
- validation errors (human-readable)
- whether a repair/retry was attempted

Do not log:
- customer secrets
- full prompts in production examples (OK in local-only quickstarts with explicit note)

### Common validation failure classes (and what to say)
- **Non-JSON output**: “Model returned non-JSON text. Retrying with stricter instruction.”
- **JSON parse error**: “Incomplete or malformed JSON. If streaming, wait for final event before parsing.”
- **Schema mismatch**: “JSON parsed but did not match schema; show the missing/extra keys.”

---

## Example conventions (for docs/SDK parity)
When writing structured output examples:
- Put the schema adjacent to the request.
- Name the schema (`name`) consistently (snake_case) so logs and golden tests are stable.
- Demonstrate a validation failure path at least once in runnable examples (not necessarily in README snippets).
- Keep the schema under ~40 lines for docs pages.

Golden tests:
- Tests should assert:
  - We only parse after the final event.
  - Validation failures trigger the expected fallback.
  - The final validated object is stable (snapshot/golden file).

## Known pitfalls (from support & field feedback)
These issues are common in tickets and should be addressed directly in examples:

1) **JSON parse errors due to streaming**
- Cause: parsing before completion.
- Fix: buffer deltas; parse on final.

2) **Trailing commentary outside JSON**
- Cause: insufficient instruction (“Respond in JSON” is not enough).
- Fix: explicitly require “ONLY JSON, no markdown/code fences”.

3) **Extra keys even with a schema**
- Cause: schema not “closed” (`additionalProperties` not false), or model drift.
- Fix: set `additionalProperties: false`; validate and repair.

4) **Schema too flexible**
- Cause: permissive `anyOf`/`oneOf` or missing `required`.
- Fix: tighten schema; make required fields explicit.

5) **Model-specific limitations**
- Cause: not all models honor schema constraints equally.
- Fix: docs should include a support matrix callout and a fallback path.

---

## Copy/paste checklist (Definition of Done for examples)
Before merging an example that claims structured output:
- [ ] Schema includes `type`, `properties`, `required`, and `additionalProperties: false`.
- [ ] Example buffers streaming deltas and parses only after completion.
- [ ] Example validates against schema (not just `JSON.parse`).
- [ ] Example includes one documented fallback path (repair or retry).
- [ ] Example avoids code fences in expected output.
- [ ] Snippet tested end-to-end against at least one Redwood-verified model.

## Appendix: Minimal “schema-first” template (language-agnostic pseudo)
```text
buffer = ""
stream = client.responses.stream(..., schema=SCHEMA)

for event in stream:
  if event.type == "response.output_text.delta":
    buffer += event.delta
  if event.type == "response.completed":
    break

obj = parse_json(buffer)
validate(obj, SCHEMA)
return obj
```

Notes:
- The exact event names vary by the streaming conventions page; examples must follow the canonical event model documented there.
- If tool calling is also enabled, treat tool call arguments similarly: accumulate until complete, then parse+validate.
