provisioning-latency-slo-and-failure-injection-fit-tests

Summary
-------
This document defines the provisioning latency SLOs for GPU-backed tenancy (warm and cold paths), describes a CI/CD-integrated fit-test suite that validates time-to-ready against those SLOs, and prescribes a failure-injection matrix and Terraform gating pattern to prevent regressing provisioning latency during platform or IaC changes. It is intended for infra engineers owning GPU provisioning modules, CI/CD authors, and SRE oncall.

Scope
-----
- Applies to all Terraform modules and orchestration pipelines that create or scale GPU worker pools across public cloud accounts used for: hosted inference, dedicated tenant pools, eval/CI sandboxes.
- Covers control-plane and data-plane readiness up to the point where nodes accept inference traffic (kubelet registration + network egress validated).
- Excludes long-term image bake times for airgapped customer flows (handled in eng-private-deployments).

Definitions
-----------
- Provisioning latency: wall-clock time from Terraform apply completing (API response OK) to a node reporting Ready and passing the network/keystore health probe.
- Warm path: attaching a pre-provisioned warm instance from a pool or snapshot restore. Target: low single-digit minutes.
- Cold path: provisioning a new instance from scratch (boot + attach + image init). Target: higher, expected minutes.

SLOs and Targets
-----------------
- Global SLO (per-region): 95th percentile provisioning-latency <= 6 minutes (warm path) over 30d and 99th percentile <= 12 minutes for cold path for non-critical test tenants.
- Canary SLO (per-change): 90th percentile <= 4 minutes for warm path on canary accounts during TF module promotion.
- Safety budget: any PR change that increases canary 90p by >20% blocks merge.

Measurement and Metrics
-----------------------
Key metrics we publish to the infra telemetry pipeline:
- gpu_provisioning_latency_seconds_bucket{path="warm|cold",region,account} (histogram)
- gpu_provisioning_success_total{region,account,reason} (counter)
- gpu_provisioning_failures{stage="boot|kube-register|network-probe|attach"} (counter)

Suggested PromQL queries (copy into dashboards):
- 95p warm path (30d): histogram_quantile(0.95, sum(rate(gpu_provisioning_latency_seconds_bucket{path="warm"}[30d])) by (le, region))
- failure rate over 1h: sum(rate(gpu_provisioning_failures[1h])) by (stage, region) / sum(rate(gpu_provisioning_success_total[1h])) by (region)

CI/CD Fit-test Design
---------------------
Goals: detect regressions in provisioning time introduced by changes to Terraform, cloud provider upgrades, or network templates before promotion to prod.
Principles:
1) Tests run in ephemeral canary accounts or dedicated canary namespaces (isolated billing tags).
2) Tests are deterministic for the warm path by reusing a standardized golden-launch-template and warm pool snapshot.
3) Measurements are recorded to the telemetry pipeline and compared against baseline stored in the canary-metrics bucket.
4) Non-deterministic flakes are tolerated but require triage; >3 consecutive CI failures block promotion.

Fit-test steps (example automated job):
1. Checkout PR branch and build TF plan for module under test.
2. Apply to a short-lived canary account using the canary workspace: terraform workspace select canary || terraform workspace new canary
3. Kick off a small warm-pool attach or scale-up (n=3).
4. Start a synthetic readiness-check agent that polls node ready state and runs a lightweight inference REST probe (curl POST /v1/predict) until success or timeout (20m).
5. Collect timing metrics and publish to telemetry via the ci-metrics API (job_id, region, module, path, latencies).
6. Compare the aggregated 90/95p to the baseline; if delta > threshold (default 20% for 90p), fail the job and attach the raw traces.

Sample GitHub Actions snippet (conceptual):
- name: Run provisioning fit-test
  uses: ./ci/actions/run-provisioning-fit-test@v1
  with:
    terraform_module: modules/gpu/worker-pool
    workspace: canary
    instances: 3
    path: warm
    timeout: 1200

Terraform Gate Integration
--------------------------
We gate module promotion with a lightweight adapter that:
- automatically runs the fit-test flow for changes touching resource types: aws_instance, aws_launch_template, aws_autoscaling_group, google_compute_instance_template, azure_virtual_machine_scale_set, local-exec customization blocks.
- requires a successful canary metric comparison before merging to the main module registry.

Recommended Terraform workflow (high level):
1) dev opens PR -> CI runs unit TF validate + plan + static checks (tfsec/opa).
2) CI applies canary workspace -> run provisioning fit-test -> publish metrics.
3) If fit-test passes, CI promotes a plan to staging for manual smoke verification.
4) Upon staging signoff, module is published to the module registry.

Failure Injection Matrix
------------------------
Inject faults during CI to validate robustness and alerting:
- Network egress delay (simulate 200–2000 ms latency) between instance and metadata endpoints. Expected detection: kubelet register failure, alert stage=network-probe.
- Control plane API throttling (HTTP 429) for cloud provider calls. Expected detection: attach/boot failures increment attach stage counter.
- Image pull timeouts (simulate corrupted image layer) to exercise timeout logic.
- IAM/role misbinding: simulate misapplied role to ensure failure surfaced as permission error.

Each fault injection variant must be run at least once per quarterly module release. CI configuration toggles injection via parameter: fault_injection_matrix = [none, network_delay, api_throttle, image_delay, iam_fail].

Monitoring, Alerts and Escalation
--------------------------------
Alerting rules (examples):
- P1: regional provisioning failure rate > 5% over 10m AND 95p provisioning latency (warm) > 8 minutes -> Pager on SRE oncall + channel #infra-paging.
- P2: canary fit-test delta > 20% for 90p on PR -> block merge, notify PR author via CI comments and #ci-failures.
- P3: repeated TF apply errors (3 applies in 1h) -> alert to owners of the module (see Ownership table).

Runbook: Oncall immediate steps
1) Acknowledge Pager and check the regional dashboard (Provisioning > Latency & Failures).
2) If failure rate spike: open a triage ticket and add runbook tag 'provisioning-latency'.
3) Identify whether the issue stems from: recent TF change (check merge timeline), cloud provider incident (check provider status pages), or warm-pool depletion (check warm pool metrics).
4) Mitigation steps (choose one based on root cause):
   - For warm-pool exhaustion: temporarily enlarge warm pool, set burst policy = true, notify customers.
   - For control-plane throttling: reduce parallelism in TF apply (TF_PARALLELISM=2), retry with backoff.
   - For image pull issues: roll pool to previous image ID and re-trigger warm seeding.
5) After mitigation, run a targeted CI fit-test against an isolated canary account to validate recovery.
6) Post-incident: fill postmortem template and include the canary job artifacts and telemetry snapshots.

Ownership and Escalation Paths
------------------------------

Policy for SLO evolution
------------------------
- SLOs are reviewed quarterly by infra capacity + SRE.
- To change a global SLO, run a proposal RFC referencing 6 months of historical telemetry and estimate impact on safety budget.
- Any SLO loosening requires approval by the Reliability Committee and Product if it affects customer SLA.

D. Acceptance checklist for module promotion:
- [ ] TF plan and validate (no diffs in unrelated resources)
- [ ] Fit-test canary run: 90p within threshold
- [ ] No new critical tfsec/opa findings
- [ ] Staging smoke verified (manual signoff)
- [ ] Module docs updated (upgrade notes)
