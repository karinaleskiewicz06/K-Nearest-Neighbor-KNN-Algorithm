GPU Tenant Bootstrap Checklist and IaC Contracts Cheat Sheet

Overview

Purpose: This page is a compact, actionable checklist and cheat sheet for onboarding a new tenant into Redwood's multi-tenant GPU fleet. It combines the minimum-safe Terraform/IaC contract, cross-account networking requirements, CI/CD gating, runtime observability knobs, and operational rollback patterns. Use this as the canonical pre-launch checklist for self-serve tenant provisioning and for operator-driven onboards.

Audience: infra engineers, platform SREs, DevEx, and solutions engineers running tenant onboards.

---

High-level flow (summary)
1. Create tenant identity and account scoping (AWS account or org namespace).
2. Provision networking & egress fences (VPCs, subnets, route tables, NAT/egress).
3. Apply Terraform tenant modules (IAM roles, service accounts, quota objects).
4. CI/CD: run preflight verification pipeline and image signing checks.
5. Canary enablement: attach tenant to a warm-pool slice with strict quotas.
6. Promote to production pool after 72h of telemetry and zero policy violations.

Key ownership
- Provisioning owner: infra-provisioning@redwood.com (oncall: infra-provisioning).
- Network owner: cloud-networking team.
- IAM & Secrets owner: security-keyops.

Minimum IaC contract (inputs & outputs)
- Purpose: Define the stable interface every tenant module must expose so we can audit, test, and route automatically.

Table: Required inputs and outputs
| name | type | description | example |
| tenant_id | string | Global tenant identifier (kebab-case) | tenant-acme-inc |
| account_id | string | Cloud account / billing id | 123456789012 |
| preferred_region | string | Primary region for GPU placement | us-west-2 |
| allowed_egress_ranges | list(string) | CIDR ranges that tenant may reach | [10.0.0.0/16] |
| burst_queue_size | number | Max concurrent burst slots | 32 |
| service_account_email | string | workload service account for runtime control plane | tenant-acme-sa@redwood.iam.gserviceaccount.com |
| owner | string | Slack/oncall pager for tenant | #tenant-acme |

Mandatory outputs (contract):
- infrastructure_id (string) -> canonical id used by orchestration
- iam_role_arn (string) -> role used by runtime sidecars
- subnet_ids (list) -> subnets attached to tenant pools
- egress_nat_id (string) -> NAT gateway or egress proxy id

Sample Terraform module signature (HCL snippet):
```
module "tenant_core" {
  source = "git::ssh://git@repo.redwood.com/infra/terraform-modules.git//tenant-core?ref=v1.8.0"

  tenant_id            = var.tenant_id
  account_id           = var.account_id
  preferred_region     = var.preferred_region
  allowed_egress_ranges = var.allowed_egress_ranges
  burst_queue_size     = var.burst_queue_size
  owner                = var.owner
}
```

Preflight CI/CD gate (recommended GitHub Actions + Buildkite pattern)
- Triggers: PR to tenant-iac repo or promote tag on infra module.
- Steps:
  1. terraform fmt & validate
  2. terraform plan (with state isolation in a sandbox backend)
  3. static policy evaluation (OPA/Conftest) against the IaC contract
  4. image provenance validation (cosign or sigstore) for any container images referenced
  5. network reachability simulation (see below)
  6. automated smoke deploy to a dedicated ephemeral sandbox and runtime e2e (10-minute smoke)

Example Buildkite job snippet (yaml-like):
```
steps:
  - label: ":terraform: plan"
    command: |
      terraform init -backend-config="bucket=sandbox-state-${BUILDKITE_COMMIT}"
      terraform plan -var-file="${PR_SPEC}.tfvars"
  - label: ":opa: policy-check"
    command: | 
      conftest test plan.out --policy ./policies/tenant
```

Network & egress fencing (must-haves)
- Each tenant MUST be placed behind a dedicated egress proxy or NAT pool with per-tenant rate limits and allow-lists.
- Route tables and subnet assignments must be labeled with tenant_id tags to help billing and quick isolation.
- Default-deny host egress at the subnet level; allow only platform-approved egress ranges.

Network verification checklist (runtime/verifications reported to CI):
1. BGP/private-link route presence between control-plane and tenant VPC (if cross-account).
2. Egress proxy reachable on required ports (443, 80) and responds to /health.
3. DNS resolution for internal endpoints within the tenant VPC.
4. Test curl to allowed egress endpoints; verify blocked endpoints return 403/connection-reset.

CLI verification commands (examples)
- Verify subnets and tags (AWS):
  aws ec2 describe-subnets --filters Name=tag:tenant-id,Values=tenant-acme-inc --query 'Subnets[*].[SubnetId,Tags]'
- Check NAT health:
  aws ec2 describe-nat-gateways --filter Name=tag:tenant-id,Values=tenant-acme-inc --query 'NatGateways[*].[NatGatewayId,State]'

Observability & SLOs (what we watch during canary)
- Latency P50/P95 for inference requests served to tenant: target P95 < 450ms.
- Token throughput: observe burst queue depth and error counts (HTTP 429/503).
- Egress events: blocked-egress-rate < 0.1% after whitelist tuning.
- Error budget policy: if error budget for tenant exceeds 5% in 24h during canary, auto-rollback.

Canary promotion policy (operator-guided)
1. Canary slice size: 2% of production capacity or max 4 GPUs, whichever is smaller.
2. Monitoring window: 72 hours continuous telemetry.
3. Acceptance criteria: P95 latency, no policy violations, <0.5% 5xx errors, no security findings.
4. Promote using promote script (see below) which updates the routing policy and adds tenant to production pool.
5. If acceptance fails: rollback by removing tenant from production pool and revert IaC to last-good state.

Promote/rollback CLI examples
- Promote: ./scripts/promote-tenant.sh --tenant tenant-acme-inc --target-pool production
- Rollback: ./scripts/rollback-tenant.sh --tenant tenant-acme-inc --reason "canary-failure"

Security & IAM fundamentals
- Principle of least privilege for service accounts. IAM roles granted to tenant workloads must be scoped to: logging write, metrics write, read-only config store, and temporary KMS decrypt via a bounded role session.
- All long-lived creds prohibited; must use short-lived STS tokens or workload identity federation.
- Key rotation: customer-managed keys rotated at least every 90 days or integrated with KMS auto-rotate.

Runbook: tenant canary failure triage (numbered steps)
1. Identify the failing signal (latency, errors, egress block, IAM error).
2. Capture last 60 minutes of traces and request logs for the tenant_id.
3. Verify network ACLs and egress proxy logs for denied connections.
4. If IAM errors: verify the role ARN in tenant output matches runtime role and inspect assume-role policies.
5. If image or supply-chain issues: check cosign signature and registry access logs.
6. If clear security breach or config drift: isolate tenant by detaching from routing table and notify security-keyops.
7. Execute rollback script and file a postmortem with timeline and remediation actions.

Common throttle & quota knobs (defaults and tunables)
| knob | default | description | owner |
| burst_queue_size | 32 | Max queued bursts per tenant | platform-allocator |
| concurrent_slots | 8 | Simultaneous runtime allocations per tenant | platform-allocator |
| egress_rate_limit_rps | 100 | Egress requests per second | cloud-networking |
| max_gpu_hours_per_day | 500 | Cost control soft limit | finance-ops |

Developer cheat-sheet: Quick commands during onboarding
- Run preflight locally: make tenant-preflight TENANT=tenant-acme-inc
- Generate plan and upload for review: terraform plan -out=plan.tfplan && terraform show -json plan.tfplan > plan.json && curl -XPOST -H 'Content-Type: application/json' --data @plan.json https://internal-ci.redwood.com/iac-lint
- Validate policies: conftest test plan.out --policy ./policies/tenant || true

Notes on testing & sandboxing
- Always run the smoke deploy using a sandbox backend (unique state per PR). Never plan/apply directly to shared state from a PR.
- Sandbox workloads must be explicitly time-limited and automatically destroyed after 1 hour unless promoted.

Appendix: Common OPA policy rules (examples)
- deny if resource "aws_instance" and tag["tenant_id"] == null
- deny if security_group ingress has 0.0.0.0/0 on port 22

Example conftest rule (rego):
```
package tenant

deny[msg] {
  input.resource_changes[_].type == "aws_security_group_rule"
  input.resource_changes[_].change.after.cidr_blocks[_] == "0.0.0.0/0"
  msg = "Disallow 0.0.0.0/0 on security groups"
}
```
