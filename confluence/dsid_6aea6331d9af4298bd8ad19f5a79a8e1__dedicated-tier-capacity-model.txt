Dedicated Tier Capacity Model (v1): Headroom, Overbooking, and Burst Pools

## Overview
This document defines Redwood’s capacity planning methodology for **Dedicated** tier commitments (Standard / Plus / Premium). It explains:
- How we translate **throughput SLO floors** into **provisioned GPU capacity**.
- Required **headroom targets** by tier (and why they differ).
- The **overbooking policy** (what is allowed vs prohibited).
- How we size and operate **burst pools**.
- Planning assumptions for **demand variability** (model mix, context length, traffic burstiness).

The intent is to make Dedicated commitments predictable for customers while keeping fleet utilization and unit economics manageable.

## Definitions
### Dedicated pool vs burst pool
- **Dedicated base pool**: customer-isolated GPU capacity sized to meet the contracted throughput floor for the eligible model/version(s).
- **Burst pool**: shared regional capacity used for temporary throughput above the floor (when entitled) and for controlled failover during incidents (tier-dependent).

### Canonical throughput unit (planning)
We plan and track commitments using a normalized unit to compare across shapes and model classes.

**Committed Throughput Unit (CTU)**
- **1 CTU = 100 tokens/sec of “effective output tokens/sec”** measured at the deployment boundary.
- “Effective” means post-routing, post-admission-control, using the Dedicated throughput metric semantics (see SLO doc). For streaming, tokens are counted as emitted to the customer.

Why CTU exists:
- It decouples customer commitments and quoting from exact benchmark numbers, while still mapping cleanly to capacity.
- It supports tier-aware burst accounting and sales-facing envelopes.

### Eligibility constraints (what the capacity model assumes)
This model is valid only under the contract/SLO eligibility conditions:
- Customer is pinned to **supported model/version(s)** for the purchased shape.
- Customer traffic stays within supported **max context / batch / concurrency** guidance for that shape.
- No customer-side throttling or misuse patterns that induce self-inflicted backlog.

If these assumptions do not hold, the base pool may be “correctly sized” yet the measured throughput floor can be missed; in these cases we treat as **out of scope for SLO remedy** and route to Support/CS per escalation playbook.

## Tier entitlements that impact capacity planning
Capacity planning differs by tier due to different requirements around headroom, burst, and failover posture.

| Tier | Throughput floor posture | Burst posture | Failover posture | Headroom target (base pool) |
|------|--------------------------|--------------|------------------|-----------------------------|
| Standard | Floor only (no latency target) | Best-effort burst from shared pool | No cross-region failover commitment | 20% headroom above modeled steady-state need |
| Plus | Floor with tighter measurement/operational response | Metered burst with priority | Same-region failover when capacity allows | 30% headroom |
| Premium | Floor with strongest operational response | Higher burst priority + larger burst envelope | Same-region HA expectation; controlled failover to spare nodes/pool | 40% headroom + N+1 (shape-dependent) |

Notes:
- Headroom is applied to the **base pool sizing** (customer-isolated capacity), not the shared burst pool.
- Premium’s “N+1” applies for shapes where a single node failure materially reduces throughput (e.g., multi-node sharded deployments). Infra owns the exact HA topology by shape.

## Inputs to the capacity model
### 1) Shape performance profiles
For each region + shape, Infra publishes:
- Supported model families and max context recommendations.
- Benchmark envelopes by **model class** and **workload profile**.

Capacity planning uses the **conservative** benchmark number:
- We use **P10 (10th percentile) tokens/sec** across benchmark runs for the relevant model class and workload profile.
- If P10 is not available, default to “mean - 1.0σ” with a manual review gate.

Rationale: prevents systematic under-provisioning when customer prompts skew longer or when kernel selection differs under production conditions.

### 2) Demand model parameters
We model customer demand in CTU using:
- **Steady-state CTU** (what they expect to sustain)
- **Burst CTU** (temporary peak above steady-state)
- **Burst duration** (minutes)
- **Burst frequency** (events per day)

We maintain default assumptions by segment (startup, mid-market, enterprise) but override with customer-specific data when available (POCs, hosted usage history, or discovery calls).

### 3) Operational risk factors
We apply additional multipliers for:
- **Model mix risk** (multi-model deployments are higher variance than single-model)
- **Long-context risk** (higher variance and higher sensitivity to batching)
- **Regional supply risk** (tight GPU markets reduce our ability to “rescue” commitments with spares)

## Base pool sizing methodology
### Step-by-step
1) **Determine committed floor** in CTU
   - Contractual floor (tokens/sec) → CTU = floor_tok_per_sec / 100.

2) **Select the benchmark profile**
   - Identify shape + model class + workload profile (e.g., chat short-context streaming).
   - Use conservative throughput: **shape_tok_per_sec_P10**.

3) **Compute required raw capacity at target utilization**
   - We plan for a target steady-state utilization of the base pool, by tier:
     - Standard: 70%
     - Plus: 65%
     - Premium: 60%

   Formula (single-model case):
   - required_tok_per_sec_raw = floor_tok_per_sec / target_utilization

4) **Translate to number of shape units (nodes) and GPUs**
   - nodes_needed = ceil(required_tok_per_sec_raw / shape_tok_per_sec_P10)

5) **Apply tier headroom**
   - nodes_final = ceil(nodes_needed * (1 + headroom_pct))

6) **Apply HA (Premium only, shape-dependent)**
   - If topology requires N+1: nodes_final = nodes_final + 1

7) **Validate against limits**
   - Ensure the resulting pool meets max context/batch guidance.
   - Ensure routing/admission-control settings can enforce the floor.

### Example (illustrative)
Customer wants a 12,000 tokens/sec throughput floor.
- floor_tok_per_sec = 12,000
- CTU = 120

Assume us-east, shape: H100x8. Conservative benchmark for the model class:
- shape_tok_per_sec_P10 = 18,000

**Plus tier**
- target_utilization = 65%
- headroom = 30%

Compute:
- required_tok_per_sec_raw = 12,000 / 0.65 = 18,462
- nodes_needed = ceil(18,462 / 18,000) = 2
- nodes_final = ceil(2 * 1.30) = 3

Result: provision **3 x H100x8 nodes** in the Dedicated base pool.

Interpretation:
- Without headroom, 2 nodes might “work” on paper but leaves no cushion for prompt mix variance, kernel regression, node maintenance, or reduced batching efficiency.

## Headroom targets (policy)
### Why headroom exists
Headroom absorbs:
- Demand variability within “steady-state” (diurnal patterns, workload mix changes)
- Benchmark drift (driver updates, kernel changes)
- Partial capacity loss (maintenance, transient GPU errors)
- Operational delays in scaling or rescue (especially in supply-constrained regions)

### Standard targets
- **Standard:** 20% headroom; no N+1 requirement.
- **Plus:** 30% headroom.
- **Premium:** 40% headroom plus shape-dependent N+1.

### When to increase headroom
Increase headroom above defaults when any apply:
- Multi-model deployments (>= 2 production models): +10%
- Long-context dominant traffic (p95 input context > 8k): +10%
- Known spiky demand (peak/avg > 2.5x): +10% or require explicit burst capacity purchase
- Regions with tight supply (Fleet declares “amber/red”): +10–20% or restrict quoting envelope

SRE Capacity Planning owns the call; Finance must approve if changes impact tier pricing floors materially.

## Overbooking policy
Dedicated commitments are only credible if we prevent “silent oversell.” This section is explicit about what is and isn’t allowed.

### Hard rule: do not overbook the Dedicated base pool
We **do not** overbook committed throughput floors across customers on the same physical GPUs.
- Every Dedicated base pool must have physically allocated capacity sufficient to meet the committed floor under this model.
- The only exception is during controlled incident response (see “rescue procedures”), where we may temporarily reassign spare capacity, but we still treat the base pool as a hard commitment.

### Allowed: pipeline (start-date) overbooking with controls
We allow limited overbooking of **future start dates** to reduce idle inventory, with strict guardrails:
- Overbooking is permitted only for **start dates >= 30 days out**.
- We cap pipeline overbooking by region/shape at:
  - Standard: up to **1.10x** of forecasted deliverable capacity
  - Plus: up to **1.05x**
  - Premium: **1.00x** (no pipeline overbooking)
- Overbooking is based on historical slip/cancel rates and procurement lead time confidence.

### Allowed: burst pool statistical multiplexing
Burst capacity is **shared** and is intentionally multiplexed.
- This is not considered overbooking of commitments because burst is explicitly “above the floor” and controlled by admission policies.
- We still maintain a minimum burst reserve per region (see next section) to prevent systemic burst denial.

### Deal desk triggers
Any deal that would:
- Consume > 25% of a region’s Premium envelope for a shape, or
- Require exceptions to headroom targets, or
- Require start date < 21 days in an amber/red supply region
must go through Deal Desk (Sales Ops + Finance + Fleet + SRE).

## Burst pool sizing and policy
### Goals
- Provide predictable burst behavior consistent with tier entitlements.
- Prevent burst traffic from causing SLO misses for base pools.
- Preserve margin by limiting how much premium “free burst” we must reserve.

### Burst pool sizing (regional)
We maintain a regional burst pool per GPU family (e.g., H100, A100, L40S) sized as a fraction of committed base capacity.

**Baseline sizing (per region, per GPU family):**
- burst_pool_capacity = max( 2 nodes, 0.15 * total_committed_base_nodes_equivalent )

Tier weighting (priority, not physical partition):
- Standard: weight 1.0
- Plus: weight 1.5
- Premium: weight 2.5

Meaning:
- In contention, Premium burst requests are admitted preferentially, but never at the expense of a Dedicated floor.
- Admission control sheds burst before it sheds committed floor traffic.

### Burst limits and metering
- Burst is metered separately from committed usage.
- Burst admission is governed by:
  - per-customer burst ceiling (CTU)
  - per-region burst saturation
  - tier priority

Finance note:
- If a customer consistently relies on burst to meet steady demand (e.g., > 20% of tokens for > 3 consecutive days), CS/Sales is notified for resizing or tier change.

## Demand variability assumptions (defaults)
These are defaults used for forecasting when customer-specific data is unavailable.

### Traffic shape assumptions
- Peak/avg factor (diurnal):
  - Standard: 1.8x
  - Plus: 2.0x
  - Premium: 2.2x (enterprise batch jobs + incident-driven spikes are common)

- Burst event assumptions:
  - Standard: 2 bursts/day, 10 minutes each, +50% above steady-state
  - Plus: 4 bursts/day, 15 minutes each, +75% above steady-state
  - Premium: 6 bursts/day, 20 minutes each, +100% above steady-state

### Prompt/context distribution
Unless otherwise specified:
- Short-context profile: p95 input context <= 2k tokens
- Mixed profile: p95 input context 2–8k tokens
- Long-context profile: p95 input context > 8k tokens

We assume “Mixed” by default for Plus and Premium unless customer commits to constraints.

### Model mix assumptions
- Standard: single model, pinned version
- Plus: 1–2 models, pinned versions
- Premium: 2+ models is common; requires explicit capacity review

Model mix increases variance because batching efficiency and KV-cache behavior differ by model and prompt type.

## Capacity envelopes and quoting guidance (internal)
Capacity Planning publishes a weekly “envelope” per region/shape/tier:
- total available nodes (now)
- nodes reserved for maintenance/spares
- nodes reserved for burst pool
- net sellable nodes by tier
- earliest start dates by tier

Sales-facing guidance:
- Quotes must use the envelope for the customer’s preferred region.
- Cross-region alternatives can be offered only if SRE confirms SLO measurement and routing posture meets tier expectations.

## Monitoring and control loops
### What we monitor (minimum)
Per region/shape/tier:
- Committed CTU sold vs provisioned (base pools)
- Burst pool saturation (% time > 80%)
- “Rescue events” count (times we had to allocate spares to prevent misses)
- Throughput SLO burn (by tier)
- Provisioning lead time distribution

### Review cadence
- Weekly: Capacity review (SRE + Fleet) — update envelopes and amber/red flags.
- Biweekly: Tier economics check (Finance + SRE) — verify headroom + burst reserves match GM targets.
- Monthly: Posture review (Product + SRE + Fleet) — adjust tier defaults and exclusions based on incident learnings.

---

## Rescue procedures (when reality deviates)
When a Dedicated floor is at risk (or already burning error budget):
1) Verify eligibility (model/version, context, customer throttling) per SLO doc.
2) Apply tier-aware overload protection (burst shedding first).
3) Allocate from regional spares (Premium first, then Plus).
4) If regional spares exhausted:
   - Premium: initiate controlled failover posture as defined (same-region HA first; cross-region only if contract allows).
   - Standard/Plus: communicate constraints; prioritize preserving floors for eligible traffic.

See escalation playbook for customer comms and credit triggers.
