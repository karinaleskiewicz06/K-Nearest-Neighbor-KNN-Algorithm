GPU CI flake-hunting and snapshot repro playbook

Summary
-------
This playbook describes the process for detecting, triaging, and resolving GPU-flaky CI failures ("flakes") and for producing deterministic snapshot reproductions. It applies to Buildkite pipelines and ephemeral GPU sandboxes used for model and runtime integration tests. The goal is to reduce CI noise, speed developer turnaround, and prevent flaky failures from reaching release branches.

Scope
-----
- Applies to any CI job that schedules GPU nodes or runs inference workloads (unit, integration, e2e).
- Covers detection rules, automated triage, manual reproduction steps, and follow-up tasks (fix/skip/tag).
- Excludes long-running benchmarking jobs and nightly evaluation batches (separate process).

Goals and success criteria
--------------------------
- Reduce long-term flake rate (jobs failing intermittently) by 60% in 6 months.
- Reduce mean time to reproduction (MTTR) for flaky failures to < 2 hours.
- Provide a reproducible snapshot archive for every flake containing logs, environment manifest, and VM image label.

Roles & ownership
------------------
- CI Reliability (primary): triage automation, metrics, and infra changes.
- GPU Runtime (secondary): investigate kernel/runtime failures and patch runtime.
- Team that owns the failing test: fix or permanently justify skip.
- On-call (if severity > P2): engage SRE for infrastructure incidents.

Detection & alerting
---------------------
1) Rule-based detection (pipeline-level):
   - Flake candidate: test fails on >1 commit but passes on subsequent retry (within 60 minutes).
   - Repro candidate: failure occurs on >3 non-consecutive builds across different agents in 24h.
2) Signal sources:
   - Buildkite job metadata: exit codes, agent id, node GPU type, image tag.
   - Telemetry: kernel oops, nvml errors, CUDA device reset, OOM_killer logs.
   - Test harness: timing out on device init, nondeterministic RNG seeds, race-sensitive asserts.
3) Alerts:
   - flake-detection-alert (pager only if flake rate > 20% for a job over 6 hours).
   - repro-suspected (email + slack CI-reliability channel with archive link).

Metrics to monitor
------------------
- Flake rate per pipeline: flake_count / total_runs (goal < 1.5%).
- Repro success rate: reproducible_snapshots / repro_attempts (goal > 75%).
- CI wasted GPU time: gpu-minutes_lost_to_flakes per day.
- Median time-to-first-repro attempt.

Automated triage pipeline (overview)
------------------------------------
When a flake candidate is detected the automation will:
1. Capture build artifacts (logs, stdout/stderr, test output, buildkite metadata).
2. Snapshot the container image tag and the node image label (AMI/GCE image).
3. Collect GPU-related kernel and driver logs: dmesg, /var/log/nvidia-installer.log, /var/log/syslog.
4. Run fast heuristic checks:
   - Check for common transient signals (NVML timeout, ECC error, driver mismatch).
   - Check for OOMs or host memory pressure.
   - Check for network blips (curl to artifact storage).
5. If heuristics indicate a likely infra cause, auto-create a ticket in the infra issue queue with tags: flake, gpu, infra-suspect.

Artifact archive format (required fields)
---------------------------------------
- build_id (string)
- pipeline_name (string)
- agent_id (string), node_gpu_type (string)
- container_image_tag (string)
- node_image_label (string)
- logs (list of files; compressed tar URL)
- dmesg.txt (text)
- nvml_dump.txt (text)
- test_output.txt (text)
- repro_instructions.md (autogenerated)

Manual reproduction playbook (step-by-step)
------------------------------------------
1) Validate archive: open repro_instructions.md and confirm image tags and GPU type.
2) Create ephemeral sandbox: follow the ephemeral playground terraform module below.
3) Re-run the exact failing command inside the same image and with same env vars.
4) If failure is non-deterministic, run repeated runs (n=20) logging timestamps and GPU telemetry.
5) If reproduces: collect full perf counters and a core dump (see steps).
6) If does not reproduce: escalate to CI Reliability for a cross-agent replay (see Automation).

Repro checklist (when you get a repro)
------------------------------------
- Attach full dmesg and nvml logs to the ticket.
- Capture a core dump: 
  - echo 1 > /proc/sys/kernel/core_uses_pid
  - ulimit -c unlimited
  - export CORE_DUMP_DIR=/tmp/cores && mkdir -p $CORE_DUMP_DIR
  - (re-run failing process)
- Run nvprof or Nsight for a single run to collect GPU counters.
- Identify whether seed/race/nondeterministic randomness contributed: check TEST_SEED log.

Non-repro / intermittent cases
-----------------------------
- Use the flake-bisector automation to run the test N times across different agents and capture per-agent metadata.
- If an agent-specific pattern appears (same agent_id/bucket): mark infra suspected and move to infra queue.
- If time-bounded (e.g., windowed network outages): correlate against network probe logs (see Network probes section).

Flake-bisector automation (how it works)
---------------------------------------
- Inputs: build_id, failing_test, container_image_tag, expected_gpu_type.
- Orchestrates 20 parallel replays across distinct agents and regions where the image exists.
- Produces a report mapping success/failure to agent metadata and timestamps.
- If > 60% failures on a single node_image label -> auto-assign infra bug.

Network probes and egress checks
-------------------------------
- For IO-sensitive tests (artifact fetches, model shards), the flake check will run curl/s3 probes to the artifact endpoints and compare latency percentiles to baseline.
- Baseline thresholds: 95th percentile latency < 400ms to artifact endpoint; packet loss < 0.1%.

CI gating and remedial actions
----------------------------
- Short-term: if a pipeline flake rate spikes over 10% during a release window, temporarily disable that test via a gate label and require a triage ticket for re-enablement.
- Long-term: tests with persistent nondeterminism should be refactored to determinism or moved to a flaky-only pool with rate-limited runs.

Recurring post-incident tasks
----------------------------
1. Root cause summary in the ticket: include repro steps and suggested fix.
2. Add a unit/regression test that asserts the fix (or a stronger assertion to prevent nondeterminism).
3. If infra-triggered, create follow-on infra task to remediate drivers/AMI or agent configuration.
4. Update the reproducibility checklist if new artifact types are needed.

Helpful scripts and commands
---------------------------
- Gather host telemetry quickly: 
  tar -czf /tmp/buildkite-telemetry-${BUILDKITE_BUILD_ID}.tgz /var/log/syslog /var/log/kern.log /var/log/nvidia-installer.log /tmp/test_output.txt dmesg.txt
- Quick nvml dump: 
  python3 - <<'PY'
import pynvml, sys
pynvml.nvmlInit()
for i in range(pynvml.nvmlDeviceGetCount()):
  h = pynvml.nvmlDeviceGetHandleByIndex(i)
  print(pynvml.nvmlDeviceGetName(h).decode(), pynvml.nvmlDeviceGetMemoryInfo(h))
PY

Preventative guidance for test authors
-------------------------------------
- Seed random generators and expose TEST_SEED in logs.
- Reduce reliance on host-global state (GPIO-like locks, system-wide tmp paths).
- Timeouts: prefer adaptive waits with clear error messages.
- Add idempotent cleanup steps for GPU resources.

Postmortem and continuous improvement
------------------------------------
- Every flake that required >4h of investigation or that triggered infra remediation requires a mini-postmortem (1 page) with owner, timeline, root cause, and corrective actions.
- CI Reliability publishes a monthly flake report with top noisy tests and remediation progress.

Appendix B: Common error signatures and immediate next steps
-----------------------------------------------------------
- "CUDA_ERROR_ILLEGAL_ADDRESS": collect core dump, enable address sanitizer on CPU code paths, escalate to runtime team.
- "NVML_DEVICE_RESET": suspect hardware or driver; tag as infra-suspect and trigger node_image rollback.
- "Connection reset by peer" during artifact fetch: investigate egress proxy and artifact CDN latency.
