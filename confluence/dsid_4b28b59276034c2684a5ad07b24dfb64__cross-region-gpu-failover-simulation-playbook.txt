cross-region-gpu-failover-simulation-playbook

Summary
This playbook describes a reproducible simulation and validation procedure for cross-region GPU failover for Redwood's inference clusters. The goal is to exercise our multi-region routing, model fallback, and capacity-autoscaling behaviors under realistic workload and network-failure conditions without impacting production traffic.

Scope
- Applies to Redwood-managed inference clusters in public cloud regions (AWS us-west-2, us-east-1, eu-west-1) and to Dedicated testing fleets used for canaries.
- Focuses on: routing failure, preemption (spot interruption), regional network partition, and cold-cache regeneration.
- Not covered: durable storage corruption, KMS key compromise, customer-data exfiltration tests. Those are handled by security incident drills.

Objectives and success criteria
- Verify that automatic routing fallback reduces 5xx error surface area to <= 0.5% during the sim window.
- Maintain p90 inference latency within 2x baseline and p99 <= 3x baseline for at least 80% of requests during the simulation.
- Confirm autoscaler ramps to expected capacity within defined timeouts (see thresholds).
- Validate telemetry (traces, logs, SLO burn) is recorded to long-term observability.

SLO & thresholds (baseline values are cluster-specific; replace placeholders)
- Baseline p90 latency: 80ms (threshold during sim: 160ms).
- Baseline p99 latency: 320ms (threshold during sim: 960ms).
- Error budget usage: simulations target <= 5% of monthly error budget per region.
- Autoscaler warmup: new GPU nodes should be Ready within 6 minutes; capacity target achieved within 10 minutes.

Prerequisites
1) Approvals: Incident commander (IC) and infra lead sign-off at least 48h prior. Notify Customer Success for Dedicated customers.
2) Simulation window: choose low-traffic 2-hour window or use isolated canary tenant and staging traffic.
3) Canary workload: synthetic prompt set with realistic token distribution and KV cache warmers.
4) Test cluster: tag a set of GPU instances with "chaos-sim=true" via Terraform variable to avoid impacting production tenants.
5) Observability: Grafana dashboards, tracing, and logs must be configured to retain sim data for 90 days.
6) Playbook owner and stakeholders listed in calendar invite.

Test scenario matrix
- Scenario A: Region outage simulation (BGP + route table blackhole) -> Validate smart routing and model fallback to remote region.
- Scenario B: Spot/preemption flood in primary region -> Validate autoscaler fallback to on-demand pools and model variant downgrade path.
- Scenario C: Network partition between control plane and worker pool (simulate high loss/latency) -> Validate KV cache invalidation and safe reconnect behavior.
- Scenario D: Cold-cache restart (full cache eviction) -> Measure cold-start latency and infer cache warmup policy effectiveness.

Step-by-step execution (high level)
1) Prep and soften traffic:
   - Direct 10–20% of canary traffic to test cluster (route via traffic-router with tag filter).
   - Enable sampling at 100% for request traces to capture detailed traces during sim.

2) Baseline capture (10 min):
   - Capture p50/p90/p99, token throughput, GPU utilization, KV cache hit rate, and autoscaler metrics.

3) Scenario run (ordered):
   - For each scenario, follow numbered sub-steps below. Run one scenario at a time and validate before moving on.

Scenario A (Region outage simulation):
1. Using the network test harness (see Appendix A), apply a route table rule to blackhole egress from the test cluster to regional endpoint (5 min window).
2. Monitor the smart router service: ensure policy routes traffic to next-preferred region as defined in policy config (policy id: routing.priority.policy.v2).
3. Verify that model fallback triggers for incompatible model variants and responses are still served with a compatible model shard.
4. Validation checks: error-rate <= 0.5%, traces show fallback hop, and cross-region egress costs recorded.

Scenario B (Spot/preemption flood):
1. Using the cloud provider API, trigger simulated interruptions for spot instance group tagged "chaos-sim".
2. Confirm autoscaler consolidates workloads onto reserved/on-demand pools and schedules new pods in fallback AZs.
3. Validation checks: new pod Ready time <= 6 minutes, request retry loops follow backoff policy (exponential up to 10s), and no burst of 429s beyond configured throttle (max 2% of requests).

Scenario C (Control plane partition):
1. Use traffic-control (tc) to introduce latency/loss between the control-plane subnet and worker nodes: 150ms added latency + 10% packet loss for 5 minutes.
2. Observe KV cache reauthorization, connection churn, and any model state sync errors.
3. Validation checks: state reconciliation completes within 3 minutes of recovery and no inconsistent model versions are served (version audit log).

Scenario D (Cold-cache restart):
1. Evict KV caches by restarting the cache process on the test fleet or rolling the runtime with an env var (RUNTIME_CACHE_FLUSH=true).
2. Send warmup traffic (see Warmup script in Appendix B) and measure time until 90% of requests hit cache.
3. Validation checks: cache hit rate reaches >=90% within the configured warmup window (15 min), and p90/p99 latencies return to baseline.

Validation checklist (run during and after each scenario)
- Monitoring: Grafana (inference-latency, rps, errors), Traces (distributed spans show fallback), Logs (router decisions).
- Alerts suppressed during sim: document alert IDs and hold with paging duty.
- Cost telemetry: estimate incremental egress and on-demand cost and report to finance tag manager.
- Safety kill-switch: an IC can abort simulation by running:
  - CLI: redwoodctl chaos abort --run-id <run-id>

Rollback and cleanup
1) If any validation fails beyond thresholds, abort using kill-switch and revert any Terraform or network changes immediately.
2) Run rollback tasks in this priority: routing config revert -> restart affected workers -> drain and reschedule canary traffic.
3) Post-cleanup verification: ensure all services are in a healthy state for 30 minutes before re-enabling normal traffic.

Observability and artifact collection
- Required artifacts to capture and attach to the run ticket: Grafana snapshots, Jaeger trace dumps, autoscaler event logs, Terraform plan/apply logs, cloud provider interruption logs, synthetic workload logs, and cost estimation CSV.
- Label all artifacts with run-id and scenario tag (e.g., run-20251018-A).

CI/CD integration and Terraform notes
- Use the chaos-sim Terraform workspace to provision and tag resources. Example variable in terraform.tfvars: chaos_sim_run = "run-20251018"
- All IaC changes must be limited to the test workspace. Do not modify production routing policies in the same plan.
- A helper script generates a dependency graph for affected infra resources; run before any apply:
  - ./tools/infra/dep-graph --workspace chaos-sim --output tf-deps.svg
- When automating scheduled drills in CI, gate the pipeline with approval and an oncall snooze window.

Appendix A — network test harness example (tc + iptables)\sudo tc qdisc add dev eth0 root netem delay 150ms loss 10%\sudo iptables -I OUTPUT -d <control-plane-ip> -j DROP --wait 300

Appendix B — warmup script (bash pseudo)
#!/usr/bin/env bash
for i in {1..1000}; do
  curl -s -X POST \
    -H 'Content-Type: application/json' \
    -d '{"prompt":"Tell a short story about a redwood tree","max_tokens":64}' \
    https://canary.api.redwood.internal/v1/generate &
  sleep 0.05
 done

Appendix C — example Terraform snippet (chaos workspace)
variable "chaos_sim_run" { default = "run-20251018" }
resource "aws_instance" "gpu_chaos" {
  ami = var.gpu_ami
  instance_type = "p4d.24xlarge"
  tags = { Name = "gpu-chaos-${var.chaos_sim_run}" ; chaos-sim = "true" }
}
