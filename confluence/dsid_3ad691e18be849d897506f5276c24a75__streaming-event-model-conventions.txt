Streaming event model conventions (canonical for SDK + docs examples)

## Purpose
This page defines the canonical *example-level* streaming event model used across Redwood docs, quickstarts, and SDK READMEs.

**Goals**
- Provide a single mental model for streaming across Python/TypeScript/Go.
- Make copy/paste examples robust to real-world issues (partial deltas, tool-call argument fragmentation, disconnects).
- Standardize naming and logging so support and Solutions Engineering can quickly interpret customer logs.

**Non-goals**
- This is not a product-level protocol redesign.
- This does not introduce new SDK APIs; it documents how examples should consume the events that already exist.

---

## Definitions
- **Stream**: A sequence of events emitted by the server for a single request.
- **Event**: A typed envelope with metadata plus a payload (delta/final/error).
- **Delta**: Partial data emitted incrementally (e.g., assistant text tokens, partial tool args).
- **Final**: A terminal representation for a logical unit (e.g., a completed message, completed tool call), or the end-of-stream marker.
- **Transcript**: The assembled conversation messages (user, assistant, tool, etc.) that the client maintains.

---

## Canonical event types (examples MUST use these names)
Examples must treat events as an envelope with at least: `type`, `request_id`, and a type-specific payload.

### Event type table
| Event type | When it appears | What examples do | Notes |
|---|---|---|---|
| `response.started` | First event for a stream | Initialize per-request state, record start time | Always expected for healthy streams |
| `message.delta` | Assistant is producing text (or other message content) | Append delta to the current assistant message buffer | Deltas may be empty or may arrive in bursts |
| `tool_call.delta` | Model is emitting tool call(s) with partial arguments | Accumulate tool call args as raw text; do not parse until final | Partial args are expected; must handle fragmentation |
| `tool_call.final` | A tool call is complete (name + args complete) | Validate + parse arguments; enqueue tool execution | Parsing should happen here, not on delta |
| `message.final` | Assistant message is complete | Freeze the assistant message, add to transcript | May arrive with or without prior `message.delta` |
| `response.completed` | Normal end-of-stream | Emit final assembled result; stop loop | The only “success terminal” event |
| `response.error` | Non-retryable failure (request rejected, validation error, etc.) | Surface error, stop loop, log structured error details | May appear after `response.started` |
| `response.interrupted` | Stream ended prematurely (disconnect, timeout, cancellation) | Trigger retry policy (if applicable) or fail with guidance | Examples should distinguish this from `response.error` |

**Important:** SDKs may internally expose slightly different shapes, but examples and docs must map to these canonical types for explanation, comments, and logging.

## Envelope and required fields (for examples + logging)
Examples should assume the following fields are available (or can be derived).

### Required fields to log
- `type`: canonical event type string
- `request_id`: stable identifier for the request (used for support correlation)
- `event_id`: monotonically increasing per stream if provided; otherwise maintain a local counter
- `model`: the model identifier used for the request (when available)
- `created_at`: server timestamp if available; otherwise local receive time

### Optional (recommended) fields
- `attempt`: retry attempt number (client-side)
- `stream_id`: if the backend provides a stream-level id distinct from request id
- `usage`: token usage summaries (often only present on final/completed)
- `warnings`: server-provided warnings (e.g., degraded mode, fallback model)

## Message assembly rules (assistant text)
Examples MUST assemble assistant content in a predictable way.

### State model
Maintain these per-request variables:
- `current_assistant_text` (string builder)
- `current_tool_calls` (map keyed by `tool_call_id` to a tool-call accumulator)
- `transcript_messages` (list of messages to show in examples)

### Assembly algorithm
1) On `response.started`:
   - Reset all per-request accumulators.
   - Log: `stream_start` with `request_id`, `model`, `attempt=0`.

2) On `message.delta`:
   - Append `delta.text` to `current_assistant_text`.
   - Print streaming output in examples only if it improves clarity (see “Logging guidance”).

3) On `message.final`:
   - If `final.text` exists, set `current_assistant_text = final.text` (final wins over delta accumulation).
   - Append an assistant message to `transcript_messages`:
     - `role = "assistant"`
     - `content = current_assistant_text`
     - If tool calls exist, attach them as part of the assistant message context as appropriate for the SDK.
   - Clear `current_assistant_text` (so a subsequent assistant message starts fresh).

4) On `response.completed`:
   - Stop consumption.
   - Return the finalized transcript and any usage details.

### Final-wins rule
If both deltas and a final are present:
- **Always prefer the final** as the canonical message content.
- Deltas are for streaming UX and intermediate logging only.

### Handling “no delta” streams
Some models/configurations may produce only `message.final` without deltas. Examples must still work.

## Tool calling assembly rules (partial args + finalization)
Tool call arguments may be streamed as fragments; examples must handle **partial JSON** safely.

### Tool call accumulator
Track per `tool_call_id`:
- `name` (string, may arrive early or late)
- `args_text` (string builder of raw argument text)
- `is_final` (bool)

### Assembly algorithm
1) On `tool_call.delta`:
   - Identify `tool_call_id`.
   - If `name` is present, set it.
   - Append `delta.args_fragment` to `args_text`.
   - **Do not parse JSON here.**

2) On `tool_call.final`:
   - Mark the tool call `is_final=true`.
   - Parse `args_text` as JSON.
   - Validate against the tool’s argument schema (or minimal required fields if no schema is available in the snippet).
   - If parsing/validation fails:
     - Log `tool_args_invalid` (include `tool_call_id`, tool name, and a truncated args preview).
     - Follow the example’s documented fallback (see “Error handling and fallbacks”).

### Partial-arguments guidance (must be explicitly called out in examples)
- Partial tool args are normal; they may be split across many events.
- Never assume a delta ends on a JSON boundary.
- Never run a tool until `tool_call.final` is received.

### Parallel tool calls
When multiple tools are requested:
- Accumulate each tool call independently.
- On each `tool_call.final`, enqueue tool execution.
- Examples may run tools in parallel *only if the language supports it ergonomically*; otherwise run sequentially but preserve ordering in logs.

### Tool result messages
After a tool is executed, examples should add a tool-result message into the transcript before requesting the model to continue:
- `role = "tool"`
- `tool_call_id = <id>`
- `name = <tool name>` (if required by the SDK)
- `content = <string result>` (JSON-stringified if structured)

## Structured output / JSON schema notes (streaming-safe)
Structured output is frequently requested alongside streaming, but incremental JSON is fragile.

### Canonical guidance for examples
- If you need reliable JSON validation: **prefer non-streaming** for the structured-output request, or stream but only parse at `message.final`.
- If streaming UI is required: stream deltas to the console, but validate only once the final message is received.

### Minimal safe parsing approach (examples)
At `message.final`:
1) Extract the candidate JSON string.
2) Parse JSON with a strict parser.
3) Validate against the schema.
4) If invalid: apply the fallback (see below).

## Error events, interruption, and retry conventions
Examples must distinguish between **terminal errors** and **interruptions** that may be retried.

### `response.error` (non-retryable by default)
Typical causes:
- Request validation error (bad tool schema, invalid parameters)
- Authentication/authorization failure
- Model not available / unsupported features for that model

Example behavior:
- Stop the stream consumer.
- Raise/return a clear error.
- Log `request_failed` with:
  - `request_id`, `type=response.error`, `status_code` (if present), `error_code`, `message`.

### `response.interrupted` (retryable depending on cause)
Typical causes:
- Client network disconnect
- Idle timeout
- Server-side transient disconnect

Example behavior:
- Stop the stream consumer.
- If safe to retry, retry with backoff.

### Retry rules used in examples
Examples should implement a small, deterministic policy:
- Max attempts: **2 retries** (total attempts = 3)
- Backoff: exponential with jitter (e.g., 250ms, 500ms)
- Retry only if:
  - The request is idempotent for the given example, AND
  - The failure is an interruption/transient network error, AND
  - The tool side effects are safe (see below)

### Idempotency + side effects
If the example executes tools with side effects (e.g., “send_email”, “create_ticket”):
- The example MUST either:
  - Use an idempotency key passed into the tool, OR
  - Disable auto-retry after tool execution begins, OR
  - Use a “dry_run” tool variant in the example.

Recommended convention for examples:
- Before running any side-effecting tool, generate `idempotency_key = <request_id>:<tool_call_id>`.

## Logging guidance (examples and supportability)
Examples should print enough to be educational *without* dumping sensitive payloads by default.

### Required log points (canonical keys)
Examples (and golden tests) should log the following events in a consistent shape:
- `stream_start`: `{request_id, model, attempt}`
- `stream_event`: `{request_id, attempt, type, event_id}` (only when running in debug)
- `tool_call_started`: `{request_id, tool_call_id, tool_name}`
- `tool_call_finalized`: `{request_id, tool_call_id, tool_name, args_bytes}`
- `tool_result_ready`: `{request_id, tool_call_id, tool_name, result_bytes}`
- `stream_completed`: `{request_id, attempt, duration_ms}`
- `stream_interrupted`: `{request_id, attempt, reason}`
- `request_failed`: `{request_id, attempt, error_code, status_code}`

### Redaction rules
- Never log raw authorization headers or API keys.
- Tool arguments: log a **truncated preview** (e.g., first 200 chars) only in debug mode.
- Structured output: log validation failures with a short reason + pointer to schema, not the full payload.

### Debug toggles
Examples should accept an env var or flag:
- `REDWOOD_DEBUG_STREAM=1` enables per-event logs.

## Golden test / fixture conventions (cross-language parity)
When examples are backed by “golden transcript” fixtures, they must:
- Assert a stable sequence of canonical event types (not raw provider-specific fields).
- Verify the **final assembled assistant message** text and tool-call arguments after `tool_call.final`.
- Include at least one fixture with:
  - fragmented tool args across multiple `tool_call.delta` events
  - an interruption and a successful retry

Recommended fixture naming:
- `streaming_text_only.<lang>.jsonl`
- `streaming_tool_call_fragmented_args.<lang>.jsonl`
- `streaming_interrupted_then_retry.<lang>.jsonl`

## Example snippets: reference pseudocode
These are not copy/paste SDK code; they represent the required control flow.

### Streaming consumer loop (canonical)
1. `start = now()`
2. `attempt = 0`
3. `while attempt <= 2:`
   - create stream
   - for each event:
     - switch on `event.type`
     - apply assembly rules
     - on `response.completed`: return
     - on `response.error`: raise
     - on `response.interrupted`: break and retry
   - `attempt += 1`
   - sleep(backoff(attempt))
4. raise “stream interrupted after retries”

### Tool calling loop (canonical)
- Consume stream until you have one or more `tool_call.final`.
- Execute tools.
- Append tool-result messages.
- Send a follow-up request (may be streaming) to allow the model to incorporate tool results.

## FAQ / common pitfalls (what examples must proactively address)
**Pitfall: Tool-call args look truncated mid-stream.**
- Expected behavior: args are fragmented across deltas.
- Fix: accumulate raw args text; parse only at `tool_call.final`.

**Pitfall: JSON parsing fails during streaming.**
- Expected behavior: incremental JSON is often invalid until complete.
- Fix: parse only at `message.final`; validate; retry with a stricter instruction if needed.

**Pitfall: Customers retry and accidentally double-execute a tool.**
- Fix: idempotency keys or disable retries after side-effecting tool execution begins.

**Pitfall: Mixing provider-specific event names in docs.**
- Fix: always present the canonical event types on this page; add a brief mapping note elsewhere if needed.
