Signal-driven GPU eviction wake patterns and mitigations

Overview

This playbook describes the observed "wake" patterns that precede GPU evictions in our multi-tenant fleet and prescribes signal-driven mitigations and IaC toggles to stabilize warm-pools. The intent is to give oncall and infra owners concrete detection thresholds, a prioritized mitigation ladder, and safe test steps to validate changes without broad impact.

Who should use this
- Oncall engineers in the GPU and capacity teams
- SREs responsible for deployment rollouts that affect burst/spot pools
- Infra engineers evolving Terraform modules for warm-pools and preemptible capacity

When this runbook applies
1. Spike in preemption_count or instance-termination events for a specific AZ or pool.
2. Warm-pool refill rate fails to meet baseline for 5 consecutive 1-minute windows.
3. Application latency degradation correlated with GPU reallocation events.
4. Scheduled cloud provider maintenance windows that historically cause cascading evictions.

Signals and thresholds to detect the "wake"
- telemetry/gpu/preemption_rate (1m avg) >= 0.05 for pool X for 3+ minutes.
- telemetry/warm_pool/refill_latency_p99 > 30s for 3 consecutive minutes.
- infra/instance/terminated_by_cloud_reason contains "preemptible" and count > 8 in 1m for an AZ.
- api/tenant/error_rate increase > 2x coincident with the above signals.

Recommended monitoring queries (PromQL examples)
- preemption rate:
  increase(cloud_instance_terminated_total{reason="preemptible"}[1m]) / 1m
- warm-pool refill latency p99:
  histogram_quantile(0.99, sum(rate(warm_pool_refill_latency_bucket[5m])) by (le, pool))

Diagnosis checklist (quick triage)
1. Confirm scope: which pools/pod labels/regions are affected.
2. Check cloud provider incident feed for the region.
3. Verify recent IaC changes affecting auto-scaling, eviction-protection tags, or warm-pool size.
4. Correlate tenant traffic spikes; tag tenant IDs for remediation if necessary.

Mitigation ladder (ordered, lowest-risk first)
1) Soft throttles and redirecting traffic
- Reduce best-effort load to bursty tenants by applying rate-limit rules for 10 minutes.
- Route new requests to lower-cost model variants if latency-sensitive requests are impacted.

2) Increase warm-pool warmup parallelism (safe config flip)
- Toggle warm_pool.refill_parallelism from 2 -> 6 for the affected pool.
- Expected effect: faster instance bring-up; risk: short-term API saturation to provisioning service.

3) Temporarily mark critical instances as protected (non-preemptible)
- Use the cloud API to add protection tag to 2-4 nodes in the affected AZ.
- Policy: only apply for < 6 hours and document the owner + reason.

4) Move noisy tenants to isolated pools
- Apply tenant affinity label and shift pod scheduling to an isolated burst pool.
- Requires coordination with the tenant-owner and may need an IaC promote.

5) Scale up on-demand capacity and drain spot pools gracefully
- Provision additional on-demand nodes into the target VPC subnet via Terraform variable override (see examples).
- Drain and cordon nodes in spot pools to reduce churn.

Operational steps (runbook)
1. Acknowledge incident and create an incident channel with the following subject line: "GPU Eviction Wake - <region> - <pool>".
2. Run detection queries (see Monitoring queries) and paste outputs to the channel.
3. Apply the lowest-risk mitigation in the ladder and wait 3 minutes for telemetry to stabilize.
4. If non-responsive, escalate through ladder items 2–5.
5. When resolved, run postmortem checklist and attach graphs for preemption_rate, refill_latency_p99, oncall actions, and IaC changes.

Terraform / IaC toggles (examples)
- Example: increase warm-pool parallelism via module variable override (HCL snippet):

resource "redwood_compute_warm_pool" "gpu_pool" {
  name                     = var.pool_name
  target_size              = var.target_size
  refill_parallelism       = var.refill_parallelism # default 2
  preemptible_preference   = var.preemptible_preference
  provider_zone            = var.zone
}

# To temporarily increase parallelism when oncall approves:
variable "refill_parallelism" { default = 6 }

- Example: promote small on-demand patch via tfvars override:

# cli: terraform apply -var-file=hotfix-20250120.tfvars
# hotfix-20250120.tfvars
# pool_target_size = 24
# provision_on_demand_percentage = 30

Testing changes safely
- Use the sandbox pool (pool label: "env:sandbox-warm") to test parallelism changes.
- Run a synthetic warmup job: curl -X POST https://warmup.internal.redwood/v1/seed -d '{"pool":"sandbox-warm","count":6}'
- Validate there is no cross-pool bleed: confirm metrics for non-sandbox pools unchanged (within ±5%).

Rollback guidance
- Always prepare a tfvars file containing previous values. Example rollback command:
  terraform apply -var-file=rollback-20250120.tfvars
- If cloud tags were added (protection tags), schedule automated removal via a ticket if not removed during the incident.

Automations and safe-guards to implement (recommended follow-ups)
- Auto-scale dampening: add a 1–2 minute cooldown for auto-scaler decisions affecting spot-to-on-demand transitions.
- Eviction circuit-breaker: a service that temporarily disables warm-pool refill_parallelism changes if preemption_rate spikes while provisioning.
- Tenant impact labels: automatically tag tenant traffic that experienced reallocation so CS can notify customers.

Ownership, SLAs and run frequency
- Primary owner: gpu-capacity team (oncall rotation)
- Secondary owner: infra-platform (Terraform changes and approvals)
- Runbook review cadence: quarterly or after any major provider incident
- Resolution SLO: for signals matching the thresholds above, the target time-to-stabilize is 20 minutes (measured as refill_latency_p99 returning to baseline).

Post-incident checklist
1. Record exact IaC changes and approvals.
2. Attach time-series graphs for preemption_rate, refill_latency_p99, instance_provisioning_error_count.
3. Create a follow-up ticket for automations with an owner and due date.
4. If tenant-impacting, coordinate a customer-facing summary with CSM and Legal (template below).

Customer communication template (short)
- Subject: Brief outage impact for <tenant-name> on <date>
- Body: We observed increased GPU preemptions in <region> causing elevated request latency between HH:MM and HH:MM UTC. We applied targeted mitigations and implemented a follow-up action to prevent recurrence. Contact <oncall-email> for details.
