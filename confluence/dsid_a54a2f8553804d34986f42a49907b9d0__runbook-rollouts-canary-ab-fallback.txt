Runbook: Canary, A/B, and Fallback for Model Version Rollouts

h1. Purpose
This runbook describes the operational steps to roll out a new model version using Redwood Router policies, including canary ramps, A/B experiments, and automatic fallback rules.

h1. Preconditions (must be met before any ramp >0%)
* A published rollout plan exists and links the dashboards and thresholds.
* The new version is registered in the model registry and is READY_FOR_PROD.
* The following toggles are confirmed available for the target alias: per-region traffic split, per-customer allowlist, and an immediate revert mechanism.
* Oncall coverage: Platform + SRE are present for the first ramp step.

h1. Key concepts
* Model alias: customer-facing name (e.g., rw-chat-default).
* Version: immutable artifact id (e.g., rw-chat-default@2025-09-28).
* Policy: routing rules, including traffic splits and fallback ordering.
* Fallback chain: ordered list of compatible versions used when the primary version fails admission or violates health checks.

h1. Required configuration elements
Every rollout MUST explicitly define these elements in the Router policy record:
1. Primary version id
2. Fallback versions (ordered)
3. Health check gate for automatic fallback (HTTP 5xx + timeout + saturation)
4. Blast radius controls
   * max_traffic_percent (global)
   * per_region_caps (list of regions + caps)
   * allowlist_customers (optional)
5. Rollback target policy id (the prior known-good policy)

h1. Procedure: canary ramp (recommended default)
1. Create a new Router policy POLICY_NEW referencing the new version as primary and the old version as first fallback.
2. Set initial split to 0.5% (or smaller) and restrict to a customer allowlist when possible.
3. Enable the rollout_slo_guard alert bundle for the alias/region.
4. Observe for at least 30 minutes (or the window defined in the rollout plan).
5. If all pass thresholds are met, ramp to 5%, then 25%, then 50%, then 100% with explicit decision points at each step.
6. Record each decision (time, step, owner, rationale) in the rollout plan.

h1. Procedure: A/B experiment (optional)
Use A/B only when you need quality or customer outcomes comparisons that are not captured by baseline guardrails.

Steps:
1. Create experiment id in the Router: experiment=MODEL_VER_<date>.
2. Configure assignment (sticky by org_id) to avoid flipping user experience.
3. Set success metrics (quality proxy, customer engagement, or task completion).
4. Ensure safety regressions still trigger immediate rollback regardless of A/B results.

h1. Automatic fallback rules
Fallback is permitted only to versions marked compatible for the request type.

Required fallback triggers (minimum):
* Sustained elevated 5xx rate above fail threshold
* Sustained timeouts above fail threshold
* Admission rejects due to saturation above fail threshold

Operational note: fallback reduces errors but can mask quality regressions; quality guardrails must still be evaluated.

h1. Rollback procedure
Rollback means restoring the prior policy (POLICY_OLD) as the active policy for the alias.

Steps:
1. Set active policy to POLICY_OLD for all regions.
2. Disable traffic to the new version (set split to 0%).
3. Confirm metrics return to baseline within 15 minutes.
4. If metrics do not recover, escalate to runtime oncall (possible broader incident).

h1. Customer-impact communications
If rollback or fallback occurs after any customer traffic >5% or any Dedicated/Private customer is impacted, follow the comms guide and consider a status page update per the incident comms doc.
