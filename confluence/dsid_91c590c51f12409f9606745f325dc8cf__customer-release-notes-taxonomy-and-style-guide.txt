Customer Release Notes Taxonomy & Style Guide (Models + Inference Runtime)

## Purpose
This guide standardizes *customer-visible* release notes for model/version promotions, variant changes (e.g., instruct vs base), quantization profile updates, and inference/runtime serving behavior changes surfaced in:
- Redwood Console (Release Notes feed + per-model history)
- Public docs-site release notes pages (versioned)
- Programmatic feeds (SDK/API consumption)

Goals:
1) Customers can quickly answer: **What changed? Why? How risky? What should I do?**
2) Notes are consistent across deployment modes (**Hosted**, **Dedicated**, **Private**) while acknowledging differences in availability.
3) Notes do **not** leak internal-only details (incident IDs, customer names, security-sensitive info, vendor/infra specifics).

Non-goals:
- Marketing announcements or “launch blog” narrative.
- Explaining how to use the API (link to docs instead).

---

## Audience and tone
Audience:
- ML engineers and software engineers shipping production LLM features.
- Enterprise security/compliance reviewers for Dedicated/Private.

Tone:
- Clear, factual, action-oriented.
- Avoid over-claiming. Prefer measurable statements with scope and constraints.
- Use active voice, short sentences, and concrete verbs.

Do:
- “Improves median time-to-first-token by ~8–12% for chat prompts under 1k tokens.”

Don’t:
- “Significantly faster for most workloads.”

---

## Release note entry structure (required)
Each release note entry must follow this structure in the customer-visible view.

### Required fields
1) **Title** (one line)
2) **Category** (exactly one primary category; optional secondary tags)
3) **Severity** (Low/Medium/High; definitions below)
4) **Summary** (2–4 sentences)
5) **Customer impact** (who is affected; when; what changes)
6) **Action / Guidance** (what customers should do; or “No action required”)
7) **Rollback / Mitigation** (how to revert or reduce risk; links allowed)
8) **Availability** (Hosted/Dedicated/Private and known staged rollout details)

### Optional fields (use sparingly)
- **Known issues / limitations** (if applicable)
- **Reference links** (docs, migration guide, compatibility page)
- **Evidence pointer** (high-level eval summary; no raw internal dashboards)

## Taxonomy: categories (customer-visible)
Choose one primary category that best represents the *customer-facing risk*.

### 1) Breaking change
Use when an update may cause:
- API/SDK behavior changes that require code/config changes
- Different required request shape or stricter validation
- Model output format constraints that can break parsers (e.g., JSON schema compliance changes)
- Removed functionality or removed parameter support

Notes must include:
- Exact behavior change
- Who is impacted
- Migration steps
- Rollback steps

### 2) Deprecation
Use when:
- A model version/variant/quantization profile is scheduled to be removed
- A feature remains available but will be removed after a date

Notes must include:
- Deprecation timeline (dates)
- Replacement recommendation
- What happens at end-of-life
- How to pin versions and/or prevent automatic promotions

### 3) Security
Use when:
- Change mitigates a security concern or hardens isolation/controls that could matter to customers

Customer-visible security notes must:
- Describe impact at a high level
- Avoid exploit details or attack recipes
- Avoid naming vulnerable dependency versions unless already publicly disclosed and approved
- Provide clear remediation/action if customers must respond

If the change is security-sensitive, consult Security & Compliance for public wording.

### 4) Quality
Use when:
- We changed the model version/weights, tokenizer, post-processing, safety policy, system prompt defaults, or decoding defaults in ways that affect outputs.

Quality notes must:
- Describe *directionally* what improved/changed
- Avoid promises of universally better outputs
- Include scope: which languages/tasks/prompts are most affected
- If referencing evals, include only statistically supported claims (see “Evals and metrics claims” section)

### 5) Performance
Use when:
- Latency, throughput, or cost-per-token characteristics changed due to serving/runtime updates, kernel selection, caching/batching behavior, or quantization/perf profile changes.

Performance notes must:
- Specify the metric (TTFT, tokens/sec, p95 latency, cost per 1M tokens)
- Specify conditions (prompt size, output length, streaming, region/hardware class where relevant)
- Avoid hardware/vendor specifics unless already part of publicly documented product tiers

### 6) Bugfix
Use when:
- Customer-visible incorrect behavior is fixed (wrong token accounting, incorrect stop sequence handling, incorrect tool-calling serialization, etc.)

Bugfix notes must:
- State the symptom and the fix
- Mention if any behavior changes could affect outputs (if so, consider “Quality” instead)

## Severity definitions
Severity communicates the *likelihood of requiring customer action* and the *blast radius*.

- **High**: Customer action is likely required OR risk of production disruption/regression is meaningful.
  - Examples: breaking API change; deprecation with <30 days; model promotion that materially changes structured output; security update requiring customer config changes.

- **Medium**: No mandatory action, but customers may need to validate or adjust prompts/configs; meaningful behavior/perf changes in specific scenarios.
  - Examples: default decoding tweak that impacts determinism; perf improvements that come with new recommended settings; quality change for certain languages.

- **Low**: Transparent informational changes, narrow impact, or purely additive changes with stable defaults.
  - Examples: documentation link updates; new availability region; internal stability improvements with no expected external impact.

Rule of thumb:
- If Support would proactively warn an enterprise customer during a rollout, severity is at least **Medium**.

## Breaking-change rules (when to label as “Breaking change”)
Label as “Breaking change” if *any* of the following are true:
1) A previously valid request becomes invalid without a compatible fallback.
2) A previously optional field becomes required.
3) Response fields change meaning or type.
4) Output formatting constraints change in a way that could break downstream parsing (including structured output / JSON mode behavior).
5) Default model behavior changes and customers are likely to have production assertions/expectations (e.g., deterministic decoding, function calling formats).

If uncertain, default to “Breaking change” and include mitigation/rollout guidance.

Required additional content for breaking changes:
- “How to validate” section with a basic smoke-test checklist.
- Explicit “If you are pinned…” and “If you track latest…” impact statements.

## Language and wording standards
### Use consistent verbs
Prefer:
- “Added”, “Fixed”, “Improved”, “Changed”, “Deprecated”, “Removed”, “Hardened”, “Adjusted”, “Corrected”, “Updated”, “Expanded availability”

Avoid:
- “Revolutionized”, “Massively improved”, “Best-in-class”, “Game-changing”

### Avoid ambiguous performance terms
Avoid:
- “Faster”, “Cheaper”, “Better” (without metric and scope)

Prefer:
- “Reduced p95 latency by ~10% for streaming chat requests under 1k prompt tokens (Hosted, us-east).”

### Avoid implying causality without evidence
Avoid:
- “This will reduce your incidents.”

Prefer:
- “Reduces the likelihood of transient 503s during burst traffic by improving queue backpressure behavior.”

## Evals and metrics claims (public-safe rules)
Quality and safety claims must meet these rules before being published:
1) **Scope**: Specify the evaluation scope (task set name/category; language coverage; general workload description).
2) **Direction + magnitude**: Provide approximate magnitude ranges and name the metric.
3) **Statistical caution**: Do not claim “significantly better” unless supported by agreed significance thresholds.
4) **No cherry-picking**: If improvements are limited to certain categories, say so.
5) **No raw internal IDs**: Do not include eval run IDs, experiment IDs, or internal dashboards/URLs in customer-visible text.

Allowed examples:
- “On Redwood’s internal summarization regression set, average preference win-rate increased by ~3–5% versus the previous default version.”
- “Safety refusal rate increased slightly on ambiguous self-harm prompts; no change observed on benign prompts in our monitored set.”

Disallowed examples:
- “Eval run 7f3a1 beat baseline by 6.2 points (see internal dashboard).”
- “Guaranteed better reasoning.”

When uncertain, use neutral wording:
- “We updated weights and performed regression testing; customers with strict output expectations should validate against their prompt set before broad rollout.”

## Public vs internal information (redaction guidelines)
Customer-visible release notes must *never* include the following:
- Customer names, account identifiers, or “customer-reported” details that are uniquely identifying
- Incident/channel/ticket references: Slack links, Jira IDs, PagerDuty incident numbers
- Internal-only service names if they reveal architecture/security posture (allowed only if already publicly documented)
- Exact region-to-customer routing rules, capacity tiers, or failover triggers
- Vulnerability exploit details, reproduction steps, or unpatched dependency versions (unless Security explicitly approves)
- Employee names outside of formal public spokespeople contexts (release notes are not credited)

Allowed with caution:
- General availability statements (e.g., “Hosted: rolling out globally over 48 hours.”)
- High-level root-cause phrasing without operational specifics (“Improved retry handling for transient upstream failures.”)

### Internal-only companion notes
If additional detail is needed for Support/SRE, it must be placed in internal-only fields and internal views. Customer-visible notes should link to public docs only.

## Availability and rollout wording
Release notes must clarify *where* and *when* the change applies.

Use this standard availability block (edit as needed):
- **Hosted:** (e.g., “Rolling out starting 2025-10-21; expect completion within ~48 hours.”)
- **Dedicated:** (e.g., “Available upon request; default rollout during next maintenance window.”)
- **Private:** (e.g., “Included in Private bundle 2025.10.3; see upgrade notes for installation steps.”)

Rules:
- Do not promise exact timestamps unless Release Engineering has committed.
- If a change is behind a rollout policy (canary/A-B), say so at a high level:
  - “This update is being canaried; some traffic may still be served by the previous version during rollout.”

---

## Deprecation policy wording standards
Deprecation notes must include:
- **Deprecation date**: when we announce it
- **End-of-support date**: last date we will support/roll back issues
- **Removal date**: when the model/version/profile will be unavailable (or will stop receiving security fixes)

Standard phrasing:
- “Deprecated as of YYYY-MM-DD. Scheduled for removal on YYYY-MM-DD.”
- “We recommend migrating to <replacement> before the removal date.”

If dates are not final, do not guess. Use:
- “Planned removal (date to be announced).” and file a follow-up to add dates.

## Examples (good)
### Example A: Performance (Low)
**Title:** Improved streaming TTFT for Redwood-Llama-3.1-70B (Hosted)
**Category:** Performance
**Severity:** Low
**Summary:** We improved time-to-first-token for streaming chat requests by optimizing request scheduling under mixed prompt sizes. No API changes.
**Customer impact:** Hosted customers using streaming chat may see lower median TTFT, most noticeable for prompts under ~1k tokens.
**Action / Guidance:** No action required.
**Rollback / Mitigation:** If you observe a regression, pin to the prior model version in Console → Model settings, or contact Support for assistance.
**Availability:** Hosted rolling rollout over ~48 hours starting 2025-10-21; Dedicated/Private unchanged.

### Example B: Quality (Medium)
**Title:** Updated default weights for Redwood-Mistral-Instruct-7B
**Category:** Quality
**Severity:** Medium
**Summary:** We promoted a new model version after regression testing across summarization and extraction workloads. Outputs may differ in phrasing and formatting.
**Customer impact:** Customers relying on strict phrasing or structured output should validate prompts; changes may be more noticeable in extraction tasks with long context.
**Action / Guidance:** Validate with your prompt set; consider enabling structured output constraints if you parse responses.
**Rollback / Mitigation:** Pin to the previous version in Console. If using Dedicated, request rollback via your TAM.
**Availability:** Hosted rolling rollout; Dedicated available upon request; Private in next bundle.

### Example C: Deprecation (High)
**Title:** Deprecation notice: `*-q4_0` quantization profile for Redwood-Llama-2-13B
**Category:** Deprecation
**Severity:** High
**Summary:** We are deprecating the `q4_0` profile due to stability and quality variability under high concurrency. A recommended replacement profile is available.
**Customer impact:** Requests pinned to `q4_0` will continue to work until removal, but will not receive further optimizations.
**Action / Guidance:** Migrate to `q4_k_m` (recommended) or `fp16` if you require maximum fidelity.
**Rollback / Mitigation:** If you observe issues after migrating, revert to the prior profile and contact Support for workload-specific tuning.
**Availability:** Hosted and Dedicated supported. Private customers should follow bundle upgrade guidance.
**Timeline:** Deprecated as of 2025-10-21. Scheduled for removal on 2025-12-15.

## Examples (bad) and why
1) “Improved quality across the board.”
- Problem: unscoped, over-claiming, not testable.

2) “Fixed a security issue in dependency X version Y.Z (CVE details…).”
- Problem: may disclose sensitive details; requires Security approval and coordinated disclosure.

3) “We changed stuff to reduce incidents.”
- Problem: vague; no customer action; no metric; unclear impact.

---

## Required review and approvals (publishing gate)
Before a customer-visible note is published:
1) **Author** (typically Release Eng, Model Catalog, or Docs) drafts the note.
2) **Engineering owner** reviews for technical accuracy (Control Plane/Console/Model Catalog as applicable).
3) **Product** reviews for clarity and category/severity.
4) **Security & Compliance** review is required if Category=Security or if wording touches audit, vulnerabilities, isolation boundaries, or access controls.
5) **Applied ML/Evals** review is required if quality claims include metrics.

If a note references customer impact in regulated contexts (HIPAA/PCI/financial), route to Security & Compliance for wording approval.

## FAQ
**Q: If a change is canaried/A-B tested, do we publish a note immediately?**
A: Publish when the change is promoted to a customer-visible state (e.g., eligible for “latest” or active rollout). During early canary, keep notes internal unless Product approves a customer-visible “rollout in progress” entry.

**Q: Should we mention that a change was triggered by a customer report?**
A: Not in customer-visible notes. Use “We fixed an issue where…” without attribution.

**Q: Can we mention specific regions or hardware?**
A: Only if it is customer-actionable and already aligned with our public tiering language (e.g., “Hosted: us-east”). Avoid vendor/hardware model specifics unless explicitly documented and approved.
