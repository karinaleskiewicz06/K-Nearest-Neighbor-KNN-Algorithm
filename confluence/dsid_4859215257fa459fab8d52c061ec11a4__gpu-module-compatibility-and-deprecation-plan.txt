GPU module compatibility and deprecation plan

Overview
--------
This page documents the compatibility matrix for Redwood's GPU Terraform modules, the automated tests we run to validate upgrades, and a concrete deprecation plan for older module versions. It is intended for infra engineers, platform owners, and module maintainers who are planning module upgrades, breaking changes, or sunsetting older variants.

Goals
- Provide a single source of truth for which versions of modules, Terraform and cloud providers are supported.
- Define an automated validation pipeline that prevents accidental breaking changes from reaching production.
- Establish a predictable deprecation timeline and communication checklist for module consumers.

Scope
- Includes: terraform-modules/gpu-pool, terraform-modules/gpu-instance, terraform-modules/gpu-network, and common helpers (tagging, iam, monitoring).
- Excludes: customer-specific forks in private repos and one-off PoC modules.

Compatibility matrix (current snapshot)
| Module | Min Terraform | Max Terraform | AWS provider tested | Notes |
|---|---:|---:|---|---|
| gpu-pool | 1.4.0 | 1.8.x | 4.60.0 | Supports fractional GPU tiling when "fractional_enabled=true"; 1.9+ untested. |
| gpu-instance | 1.3.0 | 1.8.x | 4.58.0 | Provides node bootstrap user-data scripts; uses local-exec hooks. |
| gpu-network | 1.2.0 | 1.8.x | 4.60.0 | Contains egress fencing submodule; careful with route propagation changes. |
| gpu-tags | 1.0.0 | 1.8.x | 4.60.0 | Simple tagging helper; no state. |

Matrix notes:
- "Max Terraform" reflects the latest version we run CI against; we keep this updated quarterly.
- AWS provider column is the pinned provider used in module CI tests. A mismatch at the customer level is supported but may require adaptation.

Automated validation pipeline (CI)
1) PR linting: validate TF fmt, tflint ruleset (redwood-tflint), and module docs.
2) Static checks: run terraform 0.15 upgrade checks (if PR contains upgrade), module input schema validation with custom scripts.
3) Unit plan tests: run terraform init/plan using terratest wrapper against a small sandbox account. Plan must be stable and show no unexpected replacements.
4) Integration smoke: apply to ephemeral account with minimal resources (1 node, small disk), run bootstrap smoke tests (SSH into instance or validate cloud-init finished), then terraform destroy.
5) Backwards-compatibility check: for any change that modifies state layout or resource addresses, run `terraform state pull` and a scripted diff to ensure state moves are explicit.

CI job names and targets (for repo: infra/terraform-modules)
- ci/lint-terraform (runs on every PR)
- ci/plan-unit-tests (matrix: [tf_version: 1.4.6, 1.5.7, 1.8.5])
- ci/integration-ephemeral (runs on merge to main for non-breaking changes)
- ci/compatibility-regression (runs nightly; compares latest main to last released tag)

Example compatibility test commands (developer run)
- terraform init -upgrade -backend-config=backends/ephemeral.tfvars\- TF_VAR_region=us-west-2 
- TERRATEST_ACCOUNT=ephemeral make test-plan MODULE=gpu-pool TF_VERSIONS="1.4.6 1.8.5"
- ./scripts/state-diff-check.sh --old-tag v1.12.0 --new-branch main --module gpu-pool

State-migration checklist (for changes that rename/move resources)
1) Prepare migration plan and add to PR description with explicit `terraform state mv` commands.
2) Add automated `post_upgrade` plan that runs in CI and demonstrates state move in ephemeral account.
3) Provide rollback `state mv` commands and a tested sequence to revert if failure occurs.
4) Coordinate with consumers: identify workspaces that use the module (see Module-usage inventory) and notify owners with a migration window.

Deprecation policy and timetable (example for v1.x -> v2.0)
- Announcement phase (Day 0): publish deprecation notice in #infra-update and add banner to module README.
- Soft-deprecation (Day 30): CI will flag but not block usage of deprecated versions. Add warning to `terraform init` via README and example.
- Hard-deprecation (Day 90): Remove automatic updates/compatibility guarantees for deprecated branch. New changes merged to main may not backport fixes.
- Sunset (Day 180): Tag deprecated versions as EOL in registry, and optionally remove modules from default published mirror.

Communication checklist (who to notify and how)
- Module owners: create GitHub issue with migration checklist and link to state-migration PR.
- Platform teams (kubernetes, eval infra): direct Slack mentions + brief runbook for migration during low-traffic window.
- Security/Compliance: ensure new IAM changes are reviewed; attach policy diffs to the PR.
- Customers (internal product teams): send short email and calendar invite for migration help session (if larger than 2 workspaces).

Rollout / Canary strategy for breaking changes
1) Publish a v2.0-preview tag and run `ci/integration-ephemeral` across a set of tagged non-prod tenants (testing accounts A,B,C).
2) After 7 days of successful runs, promote the preview to `canary` and run weekly plan checks against low-risk production workspaces (read-only plan run).
3) Require a manual approval gate in CI before any `apply` in production workspaces when the module major version increments.

Operational runbook (if migration fails)
1) Immediately open a Priority-1 GitHub issue and notify on-call infra via #infra-oncall.
2) Revert the merge that introduced the breaking change (if applicable) and run the rollback `state mv` sequence documented in PR.
3) If revert is impossible, run the pre-tested rollback steps listed in the state-migration checklist.
4) Perform postmortem within 7 calendar days and update this document with root cause and improved checks.

Module-usage inventory (how to find consumers)
- Use `scripts/find-module-refs.sh modules/gpu-pool` to locate workspaces in our monorepo and external repos that reference the module.
- Maintain a living spreadsheet (stored at /ops/module-usage/gpu-pool-usage.csv) with owner, workspace path, cloud account, and last-updated.
