Private VPC Customer Requirements Matrix (AWS) — Redwood Private (Alpha)

## Purpose
This page consolidates networking + security requirements observed across recent Redwood Private (AWS VPC) technical discovery, pilots, and POCs. The intent is to:
- Reduce discovery cycle time by standardizing questions and defaults.
- Inform the **VPC Terraform modules (alpha)** safe defaults and supported extension points.
- Provide Solutions Engineering and Infra with a single reference during architecture reviews.

**Scope:** AWS VPC-based deployments for Redwood Private (VPC + optional on-prem connectivity). Focused on foundational networking, DNS/TLS, endpoints, logging, and IAM/KMS integration points.

**Out of scope:** Kubernetes/cluster sizing, application install, and customer-specific security tool configuration beyond integration hooks.

## How to use this matrix
1) During discovery: Start with the “Baseline (supported)” column and confirm deviations.
2) For pilots: Map any deviations to module inputs/overrides (see “Terraform mapping” section).
3) For risk: Use the “Red flags / common failure modes” callouts.

**Legend:**
- **MUST** = required for a supported private deployment.
- **SHOULD** = strongly recommended; deviations require review.
- **OPTIONAL** = supported but not required.

## Summary: Baseline (supported) architecture
Baseline assumptions used by Redwood’s reference Terraform modules (alpha):
- One VPC with **3 AZs** preferred (2 AZs acceptable for alpha pilots with explicit acceptance of reduced HA).
- Private subnets for compute; limited/controlled public subnets only if required for ingress patterns.
- **Egress via NAT Gateway** (or customer-approved egress proxy) with explicit allowlists.
- **VPC endpoints** for core AWS services (ECR, S3, STS, CloudWatch Logs, etc.) to minimize internet egress.
- **Private DNS enabled** for Interface Endpoints unless customer DNS architecture requires an alternate pattern.
- Flow logs enabled by default, exported to customer-controlled log destination (CloudWatch Logs and/or S3).

## Industry-specific patterns (typical)
### Financial services (banks, brokerages)
Common constraints:
- **No direct internet egress** from private subnets (MUST).
- **Direct Connect preferred**; VPN acceptable for pilot if approved.
- **Centralized DNS** with Route 53 Resolver endpoints and split-horizon.
- **SIEM export required** with longer retention (often 1–7 years in S3).
- **Permission boundaries + SCP constraints** are the norm.

Implications for Terraform modules:
- Endpoint policy support becomes important (restrict to approved buckets/repos).
- Expect multi-account patterns; require clear role assumptions and documentation.

### Healthcare / Life sciences
Common constraints:
- Strict egress control + outbound proxy requirements are frequent.
- Log destinations often must be customer-owned and encrypted with CMKs.
- Auditability is emphasized; retention requirements vary by program.

Implications:
- Provide clear proxy integration hooks; document known AWS endpoint + proxy pitfalls.

### SaaS / Tech (mid-market)
Common constraints:
- Prefer minimal complexity; NAT-based egress acceptable.
- Lower barrier to entry; fewer centralized shared-services requirements.

Implications:
- Default modules should “just work” with minimal inputs; avoid over-exposing knobs.

### Public sector / regulated government (varies)
Common constraints:
- Strong preference for private connectivity and restricted egress.
- Documentation requirements: explicit data flow, logging, key management.

Implications:
- Provide a “compliance-ready” default posture and a clear list of customer responsibilities.

## Terraform mapping (alpha modules)
This section maps common requirement categories to expected module surfaces (names are descriptive; see module repo for exact variable names).
- **CIDR/subnet sizing:** `vpc_cidr`, `private_subnet_cidrs`, `public_subnet_cidrs`, `az_count`
- **NAT strategy:** `nat_gateway_mode` (one-per-az vs single), `enable_nat_gateway`
- **Endpoints:** `enable_endpoints`, `endpoints_enabled_list`, `enable_private_dns`, `endpoint_policy_json`
- **DNS integration:** `enable_route53_resolver_endpoints` (if supported), or outputs for attaching to shared services
- **Flow logs:** `enable_flow_logs`, `flow_logs_destination` (cwl|s3|both), `log_retention_days`, `s3_bucket_arn`, `kms_key_arn`
- **IAM/KMS:** `installer_execution_role_name`, `permission_boundary_arn`, `kms_key_arns`
- **VPN/DX placeholders:** outputs for route tables, TGW attachment hooks, and tagging conventions

## Discovery checklist (use in first technical call)
Collect the following early; these items are the most likely to block pilots:
1) **CIDR plan:** target VPC CIDR + confirm non-overlap with on-prem/peer VPCs.
2) **Egress policy:** is internet egress allowed from private subnets? If “no,” confirm endpoints + proxy requirements.
3) **DNS architecture:** default VPC resolver ok? If using custom DNS, confirm conditional forwarders for AWS private zones.
4) **Logging destinations:** CloudWatch vs S3 vs central logging account; required retention.
5) **IAM guardrails:** permission boundaries, SCPs, who can create IAM roles/policies.
6) **Connectivity:** VPN/DX required for pilot? Any TGW/shared-services constraints?

## Known common failure modes (from pilots)
- **ECR image pull failures** due to missing ECR endpoints or private DNS misconfiguration.
- **Intermittent DNS resolution** in private subnets when customers replace resolvers without correct forwarders/timeouts.
- **No egress + missing endpoints** leading to cascading failures (STS auth, S3 artifact fetch, logging).
- **KMS policy misalignment** preventing CloudWatch Logs encryption or S3 writes.
