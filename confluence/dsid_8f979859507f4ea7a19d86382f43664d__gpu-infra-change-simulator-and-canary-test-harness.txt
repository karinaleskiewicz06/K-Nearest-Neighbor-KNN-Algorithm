GPU infra change simulator and canary test harness

Overview
========
This document describes the design, implementation, and operational runbook for the GPU Infrastructure Change Simulator (GICS) and the Canary Test Harness that runs as part of CI/CD. GICS is a lightweight, deterministic simulator that runs synthetic change scenarios (Terraform mutations, kernel upgrades, egress-path changes, and preemption events) on a copy of our capacity model and orchestrates automated canary tests against a staging cluster. The goal is to provide fast, repeatable verification for infra changes that affect GPU capacity, networking, and tenant isolation before they reach production.

Goals
-----
- Detect capacity regressions and allocation oscillations introduced by Terraform or scheduler changes.
- Validate network egress and NAT gateway failover logic for multi-account bursting.
- Verify warm-pool seeding, KV cache rehydration, and preemptive snapshot replay behavior.
- Provide deterministic artifacts (report + golden metrics) that gate merges for infra changes.

Scope
-----
Includes: GPU fleet capacity model, provisioning Terraform modules, burst/orchestration operator manifests, and CI/CD pipeline integration.
Excludes: application-level load tests that require large-scale external tenants (those run in separate labs).

High-level architecture
-----------------------
1) Change detector: CI job that identifies which parts of the infra repo were modified (Terraform modules, scheduler, or operator manifests).
2) Simulator worker: containerized binary that loads the capacity model (small snapshot extracted from telemetry), applies mutation rules (e.g., tenant quota, node type mix), and produces a step-by-step event stream (node drains, preemptions, NAT failovers).
3) Canary harness: spins up ephemeral staging environment (ephemeral namespace + small GPU pool) using the patched Terraform plan (terraform apply --target=module.testing) and runs smoke and regression checks.
4) Verifier and artifact store: collects metrics and traces, compares against golden tolerances, and uploads a structured report (JSON + human-readable summary) to the CI artifacts bucket.

Design decisions and trade-offs
------------------------------
- Deterministic simulation: We trade absolute fidelity for reproducibility. The simulator uses a simplified topology (max 200 nodes equivalence) but reproduces key failure modes (preemption waves, eviction latency).
- Fast feedback: full-scale integration tests take hours. GICS aims for 10–30 minute feedback with the most likely failure patterns simulated.
- Golden metric thresholds: thresholds are intentionally permissive for fast feedback; failing canary requires human review and a secondary full-scale test run.

Simulator input and outputs
--------------------------
Inputs:
- terraform plan diff (module changes)
- small telemetry snapshot (last 6 hours): node counts by region, recent preemption rates, KV cache hit ratios
- change flags: kernel upgrade, quantization-kernel toggle, egress route change

Outputs:
- report.json (structured metrics, scenario timeline)
- s3://redwood-infra-ci/gics/artifacts/<run-id>/report.html (human summary)
- exit code: 0 = pass, 2 = non-deterministic warnings, 3 = fail thresholds breached

Test matrix (example)
---------------------
| Scenario | Trigger | Key metrics evaluated | Failure threshold |
|---|---:|---|---:|
| Node type mix change | Terraform instance_type update | Allocation latency, token-per-token throughput | allocation latency > 250ms increase vs baseline |
| NAT gateway rotation | egress path TTL change | 95th p95 egress latency, connection failures | >2% 5xx on egress or p95 latency > 1.5x |
| Kernel ABI bump | runtime kernel change | kernel OOMs, driver restarts | any kernel OOMs during canary |
| Preemptive snapshot flow | scheduler preemption policy tweak | KV cache rebuild time, cold-req error rate | KV cache rebuild > 45s or cold-req errors > 0.5% |

CI Pipeline integration
-----------------------
We run the simulator as an explicit stage in Buildkite (or GitHub Actions) for PRs touching infra/* or ops/* directories. Steps:
1) lint (tflint, terraform fmt)
2) unit tests for modules
3) terraform plan (safe) and plan-diff extractor
4) GICS run (simulator + canary harness)
5) if pass -> terraform apply (staging) and integration pipeline trigger (optional)

Sample Buildkite step (simplified):

```yaml
steps:
  - label: "terraform lint & plan"
    command: "scripts/ci/terraform-lint-and-plan.sh"

  - label: "gics - infra change simulator"
    command: "scripts/ci/gics-run.sh --plan plan.out --snapshot snapshot.json"
    agents:
      queue: gpu-ci
    timeout_in_minutes: 40
    artifact_paths: "artifacts/gics/*.json,artifacts/gics/*.html"
    retry:
      automatic:
        limit: 1
```

Terraform assertions and best practices
--------------------------------------
- Every module that changes resource counts must include a tfvars-driven small-scale test (count = 2) and a corresponding invariants test.
- Use terraform plan -out and the plan-diff extractor (scripts/ci/plan-diff.py) to create a deterministic mutation description for the simulator.
- Do not merge if the GICS report exit code is 3. If exit code is 2, assign owner and require explicit acknowledgement in PR.

Simulator internals (implementation notes)
------------------------------------------
- Language: Go binary (gicsd) for portability and single static binary in CI images.
- Capacity model: YAML snapshot with sections: regions, node_profiles, tenant_profiles, recent_telemetry. Example: 

```yaml
regions:
  - name: us-west-2
    nodes: 120
    preempt_rate_per_hour: 2.4
node_profiles:
  - name: a100-80g
    vcpu: 96
    gpu: 1
    qps_per_node: 2500
tenant_profiles:
  - name: eval-suite
    qps: 250
    cache_hit: 0.87
```

- Event stream: simulator applies events in fixed random seed order and emits timeline entries with timestamps and metric deltas.

Monitoring and verifier logic
-----------------------------
- Pull metrics from the staging Prometheus endpoint created by the harness (prefix: staging/gics/<run-id>).
- Compare against golden baseline stored in S3. Use relative delta and absolute thresholds.
- Key metrics collected: allocation_latency_p50/p95, preempt_rate, kv_cache_rebuild_seconds, egress_5xx_rate, node_restart_count.

Canary criteria and SLOs
------------------------
- Allocation latency p95 must not regress by more than 25% relative to baseline.
- KV cache rebuild 95th percentile must be < 45s.
- Egress 5xx rate must stay < 0.5% during the 10-minute canary window.
- Node restart count must be 0 during the canary run for kernel/driver upgrades.

Runbook: on canary failure (short)
---------------------------------
Trigger: GICS job exits with 3 or the verifier marks the run as failed.
1) Stop: add "gics-fail-<run-id>" tag to the PR and block merges.
2) Pager: page infra-oncall (Slack + PagerDuty) with run id and S3 artifact link.
3) Triage steps:
   1. Download report: gsutil cp s3://redwood-infra-ci/gics/artifacts/<run-id>/report.json ./
   2. Re-run simulator locally with --verbose and the same seed: \`gicsd simulate --plan plan.out --seed <seed> --snapshot snapshot.json\`
   3. If deterministic and suspicious, roll back the PR branch to isolate the change (git revert) and re-run.
   4. If non-deterministic (exit code 2), run extended integration test in the staging lab and escalate to scheduler team.
4) Communication: update PR with a summary table of failing metrics and assign owners.

Rollout and gradual adoption plan
--------------------------------
- Phase 1 (Q4 2025): Opt-in for teams making large Terraform changes (gpu-* modules).
- Phase 2 (Q1 2026): Make GICS a required check for all changes touching terraform/* and ops/* directories.
- Phase 3 (Q2 2026): Expand simulation scenarios (multi-region peering, multi-account bursting) and enable automatic mid-scale runs on nightly pipelines.

Operational ownership
---------------------
- Primary owner: infra-capacity team (oncall: infra-capacity@redwood.dev)
- Secondary: runtime-scheduling team for scheduler or kernel-related failures.
- CI integration: build-pipelines team maintains the Buildkite steps and container image.

#!/usr/bin/env bash

Appendix C: FAQ
---------------
Q: What if the simulator passes but the full-scale run fails?
A: The simulator is intentionally conservative in simulated scale. If full-scale fails, treat it as a new failure mode: capture traces and expand simulator scenarios to reproduce the failure (owner: infra-capacity).

Q: Can teams bypass the check for emergency fixes?
A: Only infra leads can approve a temporary bypass with a public justification in the PR and an explicit rollback window.
