Economizer Serving Recommendations Standard (Batching, Prefix Cache, Quantization)

This standard defines how Redwood Inference uses Economizer to generate, review, and safely apply automated serving recommendations for batching, prefix caching, and quantization on a per-route and per-model basis. It establishes required guardrails (SLO impact thresholds, rollback, audit logging), telemetry requirements, and the operator workflow in Console/CLI.
h1. Overview
Economizer is Redwood Inference’s recommendation engine for serving configuration changes. It analyzes historical request traces plus live telemetry summaries to propose per-route and per-model adjustments that reduce token spend while keeping latency and error-rate within policy.

Economizer produces three classes of recommendations:
* *Batching* (e.g., target batch size range, max queue delay)
* *Prefix caching* (e.g., enablement, TTL and admission thresholds)
* *Quantization profiles* (e.g., FP16 baseline to INT8/FP8 where validated)

This page is the canonical standard for how recommendations are generated, surfaced, validated, and applied.

h1. Scope
This standard applies to:
* All production serving routes in Redwood Inference clusters
* Console-based recommendation preview and canary application flows
* CLI export used for audit/on-prem workflows

Out of scope:
* Model quality evaluation methodology beyond the defined quantization gates (see related pages)
* Customer-facing product messaging and pricing (handled in product docs)

h1. Principles
1. *Advisory by default.* Recommendations are read-only until explicit org-level opt-in is enabled.
2. *Safety over savings.* Any change must pass canary guardrails with automatic rollback.
3. *Explainability.* Each recommendation must include a rationale, expected savings range, and primary risk.
4. *Least-privilege & auditability.* Applying recommendations requires permissions and produces audit logs.

h1. Inputs & Telemetry Requirements
Economizer relies on aggregated telemetry, not raw prompts.

h2. Required telemetry signals (aggregated)
* Request rate, concurrency, and queueing delay
* Token counts (prompt/completion), distribution summaries (p50/p95/p99)
* Prefix recurrence and estimated cache hit opportunity
* Model identifier, route identifier, and hardware class
* Latency (p50/p95/p99) and error rate

h2. PII and retention requirements
* PII scrubbing is mandatory at collection time (no raw user text in Economizer pipelines).
* Aggregation windows:
  * Online summaries: 5-minute rollups
  * Offline scoring windows: 7 days by default
* Retention:
  * Aggregated Economizer summaries retained for *14 days* (updated from earlier 30-day guidance)
  * Audit logs retained per platform audit policy (see related pages)

h2. Cardinality limits (required)
To prevent high-cardinality explosions:
* Route-level keys must be normalized (no user IDs, no per-session keys).
* Prefix signatures use hashed buckets with a fixed cap per route per window.
* Any new telemetry dimension added to Economizer must include an explicit cardinality budget and a test demonstrating bounded growth.

h1. Recommendation Types and Constraints
h2. Batching recommendations
Economizer may propose:
* Target batch size range (min/target/max)
* Max queue delay (ms)
* Per-route concurrency caps where required to protect tail latency

Hard constraints:
* Recommendations must not increase p95 latency beyond the policy threshold in canary (see Guardrails).
* Routes marked as "latency-critical" (SLO tier 0) must use the stricter latency threshold.

h2. Prefix cache recommendations
Economizer may propose:
* Enable/disable prefix cache per route
* TTL range for cached prefixes
* Admission threshold based on observed recurrence (e.g., only cache prefixes above a recurrence score)

Hard constraints:
* Cache memory headroom must remain above the service minimum (see Guardrails).
* Any recommendation that increases cache footprint must include an eviction-risk note.

h2. Quantization recommendations
Economizer may propose:
* FP16 (baseline)
* INT8 (validated models only)
* FP8 (validated models and hardware only; added in 2026-05 standard update)

Constraints and gates:
* Quantization recommendations are only surfaced if the Model Registry indicates the (model, quantization, hardware) combination is "validated".
* For models without validation, Economizer may suggest "candidate" quantization but it must be labeled *Requires QA* and cannot be auto-applied.
* A fallback profile must always be included (typically FP16) to enable safe rollback.

h1. Scoring Policy (Cost vs Latency)
Economizer ranks candidates using a utility score balancing cost savings and latency risk.

h2. Default policy weights (2026-05)
* Cost savings weight: 1.0
* Latency penalty weight: 1.3 (increased from 1.0 to reduce tail-latency regressions observed in early beta)
* Error-rate penalty: hard fail if error-rate increases above guardrails

Notes:
* The policy uses p99 latency as a primary risk signal for SLO tier 0 routes; p95 is the primary signal for other routes.
* Operators may tune sensitivity via approved configuration only. Any non-default weight set must be documented in the change ticket.

h1. Guardrails and SLO Thresholds
These guardrails are mandatory for any recommendation application.

h2. Canary eligibility checks (pre-flight)
A route is eligible for canary if:
* It has at least 72 hours of stable telemetry in the last 7 days
* Baseline error rate is below 0.5% over the last 24 hours
* The route is not under active incident mitigation

h2. Canary rollout guardrails (must pass)
Guardrails are evaluated against baseline for the same route.

Table: Default guardrails
* SLO tier 0 routes:
  * p99 latency change: <= +2%
  * p95 latency change: <= +1%
  * error rate change: <= +0.1% absolute
* SLO tier 1+ routes:
  * p95 latency change: <= +3%
  * p99 latency change: <= +5%
  * error rate change: <= +0.2% absolute

Cache safety:
* Cache memory headroom must remain >= 15% during canary (updated from 10% to reduce eviction storms)

Auto-rollback conditions:
* Any guardrail breach sustained for >= 10 minutes
* Any sudden error spike > 2x baseline for >= 5 minutes

h2. Rollout stages (standard)
1. 1% traffic for 30–60 minutes
2. 5% traffic for 60 minutes
3. 25% traffic for 2 hours
4. 100% if stable

Operators may extend stages for high-risk changes (quantization, large cache expansions).

h1. Operator Workflow (Console)
h2. Preview
1. Open *Console → Economizer → Recommendations*.
2. Filter by route, model, and time window.
3. Inspect each recommendation’s:
   * Expected savings range
   * Expected latency delta range
   * Primary risk factors
   * Compatibility notes (especially for quantization)

h2. Simulation (required for quantization; recommended otherwise)
The simulator replays anonymized trace summaries to estimate deltas.

Requirements:
* Simulations must reference the same scoring window as the recommendation.
* If the simulator output diverges materially from the recommendation rationale, do not proceed; investigate telemetry quality.

h2. Apply via canary
1. Select recommendation → *Create Canary*.
2. Confirm rollback target (fallback profile must be set).
3. Start canary with default stages unless an exception is approved.
4. Monitor guardrails in the Rollouts dashboard.
5. Promote to 100% only after all stages pass.

h2. Audit logging (required)
Every applied recommendation must record:
* Actor (user/service)
* Route and model
* Before/after configuration
* Canary stage timestamps
* Rollback events (if any)

h1. Operator Workflow (CLI Export)
CLI export is supported for audit and on-prem workflows.

Example:
redwood-cli economizer export --route <route-id> --window 7d --format json --out recommendations.json

Requirements:
* Exported artifacts must be stored in an approved audit location.
* Any manual application of exported recommendations must still follow the canary standard.

h1. Expected Impact (Updated Guidance)
Based on internal benchmarks and production-like traces, typical savings are:
* 10–30% token spend reduction for chat-heavy workloads when combining batching + prefix caching
* Additional savings from quantization vary widely and are gated by validation status

Latency impact:
* With default policy weights, expected p95 impact is usually within +0% to +3% for eligible routes.

This guidance updates earlier internal claims of 15–35% typical savings; the current range better reflects mixed workloads and stricter latency weights.

h1. Known Limitations
* Cold-start routes with limited telemetry can receive noisy recommendations.
* Some proprietary or newly onboarded models may lack quantization validation metadata.
* Prefix cache recommendations are sensitive to prompt normalization; changes in templating can invalidate recurrence estimates.

h1. Responsibilities
* Serving Runtime team: owns Economizer engine, scoring policy defaults, and rollout integration.
* SRE: owns telemetry retention, PII scrubbing enforcement, and observability requirements.
* Service owners: review recommendations, run canaries, and approve promotion to 100%.

h1. Change Management
Any change to:
* Default policy weights
* Guardrail thresholds
* Telemetry retention or aggregation windows

must be documented as a standards update and reviewed by Serving Runtime + SRE.
