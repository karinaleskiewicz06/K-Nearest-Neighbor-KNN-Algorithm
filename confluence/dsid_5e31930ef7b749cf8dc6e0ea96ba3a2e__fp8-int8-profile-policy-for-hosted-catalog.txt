FP8/INT8 Quantization Profile Policy for Hosted Model Catalog

## Summary
This page defines Redwood’s policy for enabling FP8 and INT8 quantization profiles in the **Hosted** model catalog. It covers:
- Default profile selection (FP8 vs INT8 vs BF16/FP16 baseline) by model family and GPU SKU.
- Calibration requirements and artifact handling.
- Known accuracy and behavior risks.
- Required evaluation and sign-off steps before enabling a profile **by default**.

This policy is intended to keep the hosted catalog fast and cost-efficient while preventing silent quality regressions and avoiding customer-impacting rollout mistakes.

---

## Definitions
**Profile:** A named serving configuration for a model variant (e.g., BF16 baseline, FP8, INT8), including kernel mode flags, quantization parameters, and guardrails.

**Default profile:** The server-side selection used when a customer does not explicitly pin a profile.

**FP8:** Primarily FP8 compute paths for eligible matmul/attention kernels (typically H100-class GPUs). In practice, FP8 is treated as “performance-first” with moderate quality risk, concentrated in long-context and numerically sensitive tasks.

**INT8:** INT8 quantization modes (often with tighter shape constraints and more calibration sensitivity). INT8 is treated as “cost-first” with higher quality and correctness risk unless the model family and workload are known-safe.

**Baseline:** BF16/FP16 (or equivalent) non-quantized kernels used as quality reference and fallback.

**Evals sign-off:** Written approval from **Jonas Weber** (Perf/Evals decision owner) or designated Applied ML on-call for enabling a profile as the hosted default.

## Goals (and non-goals)
### Goals
1. Provide predictable rules for when FP8/INT8 becomes the **default** hosted option.
2. Ensure we have a reproducible calibration and eval trail for every default change.
3. Encode conservative guardrails for long-context, tool-calling, and structured output workloads.
4. Standardize customer-safe rollout practices (flags + canary + rollback triggers).

### Non-goals
- This page does not define kernel microbench methodology (see methodology page).
- This page does not define scheduler tuning policy (owned by Serving Runtime Scheduling).

## High-level default policy
We default to the **most aggressive profile that is both (a) supported by runtime heuristics and (b) has passed quality gates for that model family**.

**Default preference order (subject to eligibility):**
1. FP8 (H100/H200-class only; when quality gates pass)
2. INT8 (cost-focused SKUs when quality gates + calibration requirements pass)
3. Baseline (BF16/FP16)

**Always required:**
- Baseline fallback must exist and be tested.
- Rollout must be behind server-side flags (per model + region + cohort).

## Eligibility matrix (what we allow by default)
The table below describes Redwood’s *default* posture. Individual models may be overridden (see Exceptions).

| GPU SKU | FP8 default allowed? | INT8 default allowed? | Notes |
|---|---:|---:|---|
| H100 (SXM/PCIe) | Yes (preferred) | Case-by-case | FP8 is primary path; INT8 used only when it provides meaningful $/token improvement without quality loss. |
| A100 | No (default) | Case-by-case | FP8 not default on A100; INT8 may be used for embeddings/rerankers if stable. |
| L4 (or similar cost SKU) | No | Yes (preferred for eligible small/medium models) | INT8 is often the primary cost lever; stricter calibration + eval gates apply. |

**Model family posture (default stance):**
- **General-purpose chat LLMs (70B class, long-context):** FP8 allowed on H100 with long-context gating; INT8 default is generally **not** allowed without explicit sign-off and expanded evals.
- **Mixture-of-Experts (MoE):** FP8 allowed only if routing/logits stability is verified; INT8 default is typically **not** allowed (sensitive to calibration and tail behaviors).
- **Embeddings/reranking models:** INT8 defaults often acceptable on A100/L4 if retrieval quality is within tolerance; FP8 is optional on H100.

## Calibration policy (INT8 and FP8)
### FP8 calibration requirements
FP8 enablement must use runtime-supported scaling/metadata and pass correctness tests. FP8 is generally less calibration-heavy than INT8 in our hosted setup.

**Required artifacts (FP8):**
- Model hash / revision identifier
- Runtime build SHA + kernel mode flags
- Kernel selection summary (from benchmark artifact metadata)

**Required validations (FP8):**
- Correctness smoke suite passes (golden prompts + structured outputs where applicable)
- Long-context sanity checks when the model advertises long context (>= 32k)

### INT8 calibration requirements
INT8 enablement requires explicit calibration and traceability.

**Calibration dataset requirements (INT8):**
- Must come from **Top Hosted Models Benchmark Suite v3** prompt distributions and/or a model-family-specific prompt set approved by Applied ML.
- Must include:
  - Short prompts (p50)
  - Medium prompts (p90)
  - Long prompts (p95/p99) where the model is offered for long-context
  - At least one structured-output/tool-calling slice if the hosted model advertises tool calling

**INT8 calibration run requirements:**
- Fixed random seed, deterministic tokenization settings
- Recorded sequence length histogram (prefill length + decode length)
- Minimum of **2 independent calibration runs** (different nodes) to catch environment instability

**Required artifacts (INT8):**
- Calibration config (prompt set version, sample count, truncation rules)
- Produced scale/zero-point artifacts (or equivalent) referenced by immutable storage URI
- A short “Calibration Notes” section in the profile change request including known quirks

**Retention:** Calibration artifacts must be retained for **90 days** minimum (or longer if the profile becomes the hosted default).

## Quality risk inventory (what can go wrong)
Quantization can change not only accuracy but also *behavior* (formatting compliance, tool-call selection, refusal boundaries). The following risks must be assessed for any default change.

### Common FP8 risks
- Long-context degradation (attention accumulation and numeric sensitivity)
- Subtle shifts in instruction-following on edge prompts
- Increased variance across GPU clocks/thermals if kernel selection changes frequently

### Common INT8 risks
- Larger behavioral shifts (summarization, factuality, multi-step reasoning)
- Format instability for structured outputs (JSON validity, schema adherence)
- Calibration overfitting (good on calibration distribution, worse in the tail)
- Model-family-specific brittleness (especially MoE and long-context)

### Workloads that require special attention
- **Long-context** (>16k; always include a long-context slice in evals)
- **Tool calling / structured output** (must include schema adherence checks)
- **Multilingual** (at least a light multilingual slice if the model is marketed as multilingual)
- **Code generation** (if the model is marketed for coding)

## Required eval gates before enabling a default
### Gate 0: Correctness + safety baseline
Required for FP8 and INT8.
- Runtime correctness tests pass (including any quantized-kernel correctness suite)
- No increase in server error rates in synthetic serving tests
- No known unsupported shape regimes for common hosted workloads (documented exceptions are allowed only with explicit fallback rules)

### Gate 1: Quality sanity suite (fast)
Required for FP8 and INT8.
- Run the **Quantization Quality Sanity Suite** (golden prompts + lightweight scoring)
- Any regression must be explained and accepted by Applied ML (or mitigated by gating)

### Gate 2: Benchmark Suite v3 (representative)
Required for any change to a hosted default profile.
- Run Top Hosted Models Benchmark Suite v3 slices relevant to the model’s advertised use cases
- Include structured-output/tool-calling slice when applicable
- Compare against baseline profile

**Default acceptance thresholds (unless model-specific exception is approved):**
- No statistically significant regression on primary quality metrics used for the model category.
- Any observed regression must be limited to non-default cohorts (e.g., long-context-only traffic) via routing/gating.

### Gate 3: Expanded evals (when required)
Expanded evals are required when any of the following is true:
- Model context length >= 32k and FP8/INT8 is being enabled by default
- Model is MoE
- INT8 is being proposed as default for a general-purpose chat model
- Customer-facing marketing claims will reference the new default

Expanded evals must include additional long-context prompts and at least one stress slice (formatting compliance or retrieval-augmented prompts).

## Sign-off rules (who must approve what)
### Changes that DO NOT require Evals sign-off
- Non-default profile added as an opt-in option (still requires Gate 0 + Gate 1)
- Canary-only enablement for internal testing cohorts

### Changes that DO require Evals sign-off (Jonas Weber or delegate)
- Any change that makes FP8 or INT8 the **default** profile for a hosted model
- Any change that expands eligible traffic cohorts (e.g., enabling FP8 for long-context prompts)
- Any change that changes calibration artifacts used by an existing default INT8 profile

### Additional required reviewers (depending on change)
- **Serving Runtime Kernel** (Hiro Tanaka or delegate): kernel support, shape guardrails, fallback correctness
- **Serving Runtime Scheduling** (Sofia Ivanova or delegate): confirms scheduler interaction is understood for end-to-end performance claims
- **SRE/Observability** (Rafael Mendes / Allison Grant): dashboards and canary alerts set up before broad rollout

## Model-level default guidance (practical defaults)
These are the default stances we use for hosted catalog decisions. Specific model IDs may differ; treat these as family-level rules.

### Large chat LLMs (high-traffic)
- **H100:** Default FP8 allowed after Gate 2 + sign-off; long-context gating required if any long-context regressions are observed.
- **A100:** Default remains baseline unless INT8 has proven stable *and* the model is not long-context sensitive.
- **L4:** Default INT8 for large chat LLMs is generally **not** allowed; L4 is used primarily for smaller models.

### MoE models
- Default FP8 only after expanded evals; default INT8 is generally disallowed unless a specific MoE model family has demonstrated stable behavior.

### Embeddings / reranking
- INT8 default is often acceptable on A100/L4 if retrieval metrics remain within tolerance and tail-latency improves.
- FP8 on H100 is allowed but not required; choose based on throughput and cost improvements.

## Required guardrails in runtime (must be present to enable defaults)
For any FP8/INT8 default enablement:
1. **Fallback policy:** baseline fallback must trigger on unsupported shapes and on error thresholds.
2. **Region + cohort flags:** enablement must be controllable per model + region.
3. **Perf canary gates:** TTFT and TPOT thresholds must be defined by GPU SKU and model tier.
4. **Metric tagging:** runtime metrics must include dimensions for model, GPU, and kernel mode to localize regressions.

---

## Rollout policy (hosted)
Default profile changes follow a staged rollout:
1. **Internal canary** (small cohort, 1 region): validate perf and error rates; spot-check quality.
2. **Perf canary expansion** (multiple regions, still limited traffic): watch TTFT/TPOT/tokens/s and error budget.
3. **Default enablement** (broad): only after sign-off + stable canary window.

**Minimum canary observation window:** 6 hours for high-traffic models, 24 hours for lower-traffic models (or until sufficient sample size).

**Rollback triggers (minimum set):**
- TTFT p95 regression beyond threshold for 15 minutes (after noise suppression)
- TPOT p95 regression beyond threshold for 15 minutes
- Error rate increase (5xx/timeout) beyond threshold
- Any confirmed quality regression reported by Applied ML or Customer Support correlated with profile enablement

## Documentation requirements (what must be written down)
Any default change PR/rollout request must include:
- Proposed default profile and motivation (perf/cost)
- GPU SKUs and regions affected
- Calibration artifacts (INT8) and links
- Eval summary (Gate 1/2/3 as applicable)
- Explicit risk statement (what could regress, how we’ll detect it)
- Rollback plan and owners

---

## Exceptions and overrides
Exceptions are allowed only with explicit documentation and time bounds.

**Valid reasons for exceptions:**
- Model-family sensitivity identified (e.g., long-context quality loss under FP8)
- Specific kernel shape regime instability or correctness bug
- Customer-impacting regression found during canary

**How to request an exception:**
- Open a profile override request and include an expiration date (default: 30 days)
- Notify Serving Runtime and SRE owners if it changes rollout behavior

## FAQ
### Can customers opt out of FP8/INT8 defaults?
Yes. Customers can pin a baseline or specific profile when exposed in the API/Console. Hosted defaults are server-side but should always have a documented fallback and supported pinning path for enterprise customers when needed.

### Do we ever enable INT8 by default for top-tier chat models?
Only with expanded evals, stable calibration, and explicit sign-off. Our default stance is that INT8 is higher risk for behavioral regressions in general-purpose chat.

### What if FP8 is faster but hurts quality on long-context only?
Prefer gating: keep FP8 default for short/medium contexts and route long-context requests to baseline (or a safer FP8 variant) until an FP8 fix or mitigation exists.
