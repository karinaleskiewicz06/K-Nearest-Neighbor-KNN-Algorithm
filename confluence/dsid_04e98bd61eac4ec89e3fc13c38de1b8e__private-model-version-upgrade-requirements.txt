Private Deployments: Model Version Upgrade and Rollback Requirements

h1. Overview
Private deployments (VPC and on-prem) introduce additional constraints for model version changes. This page lists requirements that MUST be included in any rollout plan that affects Private customers.

h1. Scope
Applies when any of the following is true:
* A Private customer will receive the new version as default
* A Private customer uses an alias that will be repointed
* The change modifies fallback/rollback behavior within the customer boundary

h1. Required content in the rollout plan (Private-specific)

h2. 1) Customer change window
* Document the customer-approved maintenance window(s) in local time.
* Identify customer approver name and date of approval.
* Confirm if the customer requires no-impact (zero downtime) upgrades.

h2. 2) Version pinning and opt-out
* State whether the customer currently pins a model version.
* Provide the opt-out path: pin prior version, disable alias updates, or custom routing rule.
* Define how long the prior version will remain available for rollback (minimum 30 days unless contract says otherwise).

h2. 3) Artifact availability and rollback package
* Confirm the rollback artifact is pre-staged in the customer environment (container images, model files, and config bundle).
* Confirm checksum/signature verification steps are documented.
* Confirm the previous version remains RUNNABLE with current runtime dependencies.

h2. 4) Data residency and retention checks
Rollout plan MUST state:
* Where logs/metrics are stored for the customer environment
* Whether any new telemetry fields are introduced
* Any changes to retention or export behavior

h2. 5) Network and identity dependencies
* If the new version requires new egress, endpoints, or KMS permissions, list them and get customer approval.
* Confirm RBAC changes (if any) are included in the customer change request.

h2. 6) Post-upgrade validation
At minimum, validate:
* health checks (router + runtime)
* smoke prompts provided by customer (if available)
* latency and 5xx rate within customer-specific thresholds

h1. Rollback triggers
Rollback MUST be initiated if any fail thresholds are hit during the customer window OR if customer requests rollback. The plan must explicitly state the decision-maker and the comms channel.

h1. Notes
* Private customers may have stricter requirements than the global rollout SLOs; the rollout plan must cite the stricter requirement.
* If the change touches regulated workloads, include Security review and document evidence collection steps.
