h1. Quickstart: minimal streaming example (JavaScript)

Below is the current recommended minimal snippet. It demonstrates partial tokens and cancellation while staying small.

{code:javascript}
const controller = new AbortController();
const stream = await client.responses.stream({
  model: "redwood-4.1-mini",
  input: "Summarize this paragraph in one sentence.",
  signal: controller.signal,
});
for await (const event of stream) process.stdout.write(event.delta ?? "");
// cancel if the user navigates away:
controller.abort();
{code}

Notes for maintainers:
* Keep the snippet runnable with minimal surrounding setup.
* Use “redwood-4.1-mini” as the default Quickstart model unless Product requests otherwise (it matches current onboarding guidance).

h1. Quickstart: minimal tool/function calling example (JavaScript)

This snippet shows a tool definition and how to handle a tool request. Keep the tool body intentionally trivial.

{code:javascript}
const tools = [{
  name: "get_time",
  description: "Return the current UTC time.",
  input_schema: { type: "object", properties: {} },
}];
const res = await client.responses.create({
  model: "redwood-4.1-mini",
  input: "What time is it?",
  tools,
});
if (res.tool_calls?.[0]?.name === "get_time") {
  const tool_output = new Date().toISOString();
  await client.responses.create({ conversation_id: res.conversation_id, tool_output });
}
{code}

Docs note: if the SDK uses a different method name or field names in the published release, update these identifiers to match the public API. The intent is: (1) define tools, (2) detect tool request, (3) send tool output.

h1. Combining streaming + tools (recommended narrative)

We have repeated user requests for “tool calling while streaming” with structured JSON output.

Recommended docs approach:
1. Show streaming alone (Quickstart).
2. Show tools alone (Quickstart or examples/tools.md).
3. In examples/tools.md, add an “Advanced: tools with streaming” section that explains event sequencing and how to buffer partial arguments.

Implementation guidance to include in the docs (no deep internals):
* Tool arguments may arrive incrementally; accumulate until a “tool_call.complete” (or equivalent) event before executing.
* Always validate tool arguments against the schema before running side effects.
* If emitting structured JSON to the UI, parse only after completion; during streaming show a placeholder state (“Working…”).

h1. Hosted vs Dedicated routing (FAQ-ready)

h2. Summary

* Hosted: simplest integration, shared fleet, best for fast onboarding.
* Dedicated: reserved capacity and stronger control over versions/rollouts, best for predictable latency and regulated workloads.

h2. Routing policy table (example)

|| Dimension || Hosted (shared) || Dedicated (reserved) ||
| Typical onboarding time | Minutes | Days (provisioning + contract/config) |
| Latency variance | Medium (depends on shared load) | Low (reserved capacity) |
| Version control | Model aliases managed by Redwood | Optional pinning + controlled rollout windows |
| Failover behavior | Managed automatically | Configurable (e.g., fallback to Hosted or smaller Dedicated model) |
| Cost model | Pay-as-you-go | Base reservation + usage (per contract) |

h2. Example headers / configuration

Docs must clearly separate what changes between Hosted and Dedicated. Prefer environment variables and a short table.

|| Setting || Hosted || Dedicated ||
| Base URL | https://api.redwoodinference.com/v1 | https://api.redwoodinference.com/v1 (same) |
| Routing selector | none (default) | set routing to a dedicated deployment (header or SDK config) |
| Model name | redwood-4.1-mini (alias) | customer-specific alias or pinned version |

Important: the exact header/config name for Dedicated routing should match the SDK release. Do not publish placeholder header names in the public docs.

h1. Batching examples (JS + Python)

Docs gap addressed: JS batching examples must be present alongside Python.

h2. Conceptual guidance

Use batching when:
* You have many small requests that can tolerate a small delay (e.g., embeddings, classification, short completions).
* You want improved throughput and cost efficiency.

Avoid batching when:
* You are streaming token-by-token to a user.
* The request is latency-critical and cannot wait for coalescing.

h2. Example configuration (pseudocode)

|| Parameter || Meaning || Suggested starting point ||
| max_batch_size | Maximum requests per batch | 8 |
| max_latency_ms | Max time to wait to fill a batch | 10–25 ms |
| enabled | Whether to batch at all | true for non-streaming |

h2. JS snippet (docs pseudocode)

{code:javascript}
const client = new Redwood({
  batching: { enabled: true, max_batch_size: 8, max_latency_ms: 15 },
});
{code}

h2. Python snippet (docs pseudocode)

{code:python}
client = Redwood(
  batching={"enabled": True, "max_batch_size": 8, "max_latency_ms": 15}
)
{code}

h1. Model versioning: pinning vs aliases (Dedicated)

Docs must include a short explanation:
* Model aliases: stable name that can move to a newer model revision as Redwood rolls out improvements.
* Pinned versions: fixed model revision for maximum repeatability.

Migration guidance (high level):
1. Test in staging with the new alias target.
2. Roll out with a small percentage of traffic (if supported by customer routing config).
3. Monitor latency and quality; rollback by repointing alias or reverting config.
