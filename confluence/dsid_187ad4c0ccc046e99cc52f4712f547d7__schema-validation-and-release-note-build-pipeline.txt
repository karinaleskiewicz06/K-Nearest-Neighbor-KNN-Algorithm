Schema validation + release note build pipeline (Model Metadata v1)

## Purpose
This document defines the required CI/CD checks and build steps used when changing Model Metadata Schema v1 or any model/version metadata records that feed customer-visible release notes.

The pipeline exists to ensure:
- Metadata is syntactically valid, semantically consistent, and compatible with serving/runtime constraints.
- Customer-visible release notes are always generated for promotions, consistently categorized, and appropriately redacted.
- There is a deterministic artifact trail from a specific metadata change to:
  - what was published publicly,
  - what was retained internally for audit/support,
  - and which model version was promoted.

## Scope
Applies to repositories and paths that influence model metadata and release notes:
- `redwood-model-registry` (schema + model records; fixtures)
- `redwood` (control plane event emission; promotion flows)
- `redwood-docs` (public release notes site generation)
- SDK repos consuming the release note endpoints (non-blocking for promotion, but required for SDK release train)

Out of scope:
- Customer notification subscriptions (email/webhook) beyond internal webhook plumbing
- Rewriting full historical release notes (we validate new and a small curated backfill only)

## Definitions
- **Metadata Schema v1**: The canonical structure defining required/optional fields for models/variants/quantization profiles.
- **Metadata record**: A single model version (or variant) entry stored in the model registry.
- **Change event**: Structured event emitted by the control plane on create/update/promote/deprecate actions.
- **Changelog artifact**: The generated release note payloads (public + internal) produced from events + metadata.
- **Promotion**: Marking a model version as eligible/active for a given deployment mode (Hosted/Dedicated/Private) and/or region.

## High-level flow (what happens on a metadata change)
1) Engineer updates schema and/or metadata records via PR.
2) CI validates:
   - JSON Schema conformance and invariants
   - redaction rules for public fields
   - deterministic release note preview generated from the diff
3) On merge to `main`, a build publishes updated registry data.
4) On promotion (typically a control plane operation), the control plane emits a `model.version_promoted` event.
5) The changelog generator ingests events and produces:
   - public release note entries (Console + docs)
   - internal release note entries (support/admin)
   - audit events (security/compliance)
6) Docs builds pull the public artifacts and render versioned pages.

## Required checks (PR gating)
The following checks are required and are configured as branch protections for `main` in the model registry repository.

### 1) `metadata-schema-validate`
**Trigger:** PR touching schema files or any `models/**/*.json` metadata.

**What it does:**
- Validates JSON syntax.
- Validates against the published JSON Schema (Schema v1).
- Runs additional semantic validation rules not expressible in JSON Schema (see “Semantic validation”).

**Failure examples:**
- Missing required fields (e.g., `version`, `deployment_availability`, `public.summary`).
- Invalid semantic version (`version` must be SemVer, `X.Y.Z` or `X.Y.Z-suffix`).
- Unknown deployment mode or invalid region code.

### 2) `metadata-schema-diff-policy`
**Trigger:** PR touching schema definition files.

**What it does:**
- Calculates a schema diff vs `main`.
- Enforces a compatibility policy:
  - Additive changes are allowed by default.
  - Removing or renaming fields requires explicit approval and a migration plan.
  - Tightening validation that breaks existing stored records requires a backfill job merged first (or same PR with backfill + verification).

**Policy outcomes:**
- PASS: additive / backward compatible.
- WARN: potentially breaking; requires `release-eng-approval` label.
- FAIL: breaking without an approved migration plan.

### 3) `release-note-preview`
**Trigger:** PR touching metadata records OR promotion-related templates.

**What it does:**
- Generates a release note preview artifact from the metadata diff using the standard templates and category mapping.
- Produces two outputs:
  - `public_preview.md` (customer-visible)
  - `internal_preview.md` (includes internal-only notes)
- Fails if required release note inputs are missing for changes that will be customer-visible.

**Required inputs for preview generation:**
- `public.summary` (1–3 sentences)
- `public.category` (one of: security | breaking | perf | quality | bugfix | deprecation)
- `public.customer_impact` (brief, plain-language)
- `public.rollback_guidance` (if category is breaking/security/deprecation)

### 4) `redaction-and-rbac-tests`
**Trigger:** PR touching templates, redaction rules, or any metadata fields flagged as internal.

**What it does:**
- Ensures fields classified as internal (e.g., internal incident links, vendor/hardware debug notes, customer-specific identifiers) cannot appear in public artifacts.
- Runs snapshot tests that render release notes under multiple roles:
  - `admin`
  - `support`
  - `standard_user`

**Hard rule:** public output must never contain:
- Internal-only fields (`internal.*`)
- Customer identifiers (account IDs, emails, contract names)
- Incident channel links or ticket IDs (unless explicitly approved in `public.references`)

### 5) `fixtures-and-examples-check`
**Trigger:** PR touching schema files.

**What it does:**
- Verifies example payloads/fixtures still validate.
- Ensures at least one fixture exists for each supported model family and at least one quantization profile example.

### 6) `audit-event-contract-check` (control plane repo)
**Trigger:** PR touching event emission for model metadata changes.

**What it does:**
- Verifies event payloads adhere to the event contract (required fields, idempotency key presence).
- Ensures the event includes:
  - actor (service principal or human)
  - timestamp
  - affected model id + version
  - environment and deployment mode
  - schema hash

## Semantic validation rules (beyond JSON Schema)
CI runs a semantic validator (`metadata-lint`) to enforce cross-field invariants.

### Versioning and compatibility
- `version` must be SemVer.
- `compatibility.min_runtime_version` must be set and must not regress for an existing major line unless the change is marked `public.category=breaking`.
- Tokenizer constraints:
  - `tokenizer.name` and `tokenizer.revision` must be set.
  - Tokenizer changes require `public.category` of `breaking` or `quality` (depending on impact), and must include `public.customer_impact` describing potential output drift.

### Deployment availability
- Each model version must declare availability by deployment mode:
  - Hosted: required regions list (even if single region)
  - Dedicated: eligibility policy reference (capacity tier constraints)
  - Private: packaging support (bundle name or “not supported”)
- If Hosted availability changes (region added/removed), release note preview is required.

### Deprecations
- Deprecations must include:
  - `deprecation.state` (announced | active | removed)
  - `deprecation.effective_date`
  - `deprecation.replacement` (if available)
  - public deprecation note with action required

### Quality claims
- Public quality improvements/regressions must not include unqualified statistical claims.
- If `public.category=quality`, the metadata must include at least one quality signal reference:
  - eval run id(s)
  - baseline version id
  - guardrail outcomes summary (allowed values only)

## Release note artifact formats
The changelog generator produces standardized artifacts consumed by Console and docs.

### Artifact outputs
- Public:
  - `release-notes/public/{model_id}/{version}.md`
  - `release-notes/public/feed.json`
- Internal:
  - `release-notes/internal/{model_id}/{version}.md`
  - `release-notes/internal/feed.json`

### Required fields surfaced in public artifacts
Public artifacts must include:
- Model name + version
- Category + severity language (per style guide)
- Summary (plain language)
- Customer impact
- Deployment availability notes (Hosted/Dedicated/Private where applicable)
- Rollback guidance when relevant
- References (docs links only; internal links are stripped)

### Idempotency and determinism
To prevent duplicate entries and drift:
- All generated notes are keyed by `(model_id, version, change_event_id)`.
- Template rendering must be deterministic given the same inputs; timestamps are sourced from event time, not build time.

## Promotion gates (before a model version can be promoted)
Promotion is a control plane operation, but it is gated by the following checks.

### Gate A: metadata readiness
A version cannot be promoted unless:
- Metadata record validates.
- `public.summary` and `public.category` are present.
- Availability is declared for the target deployment mode.

### Gate B: release note presence
For promotions in Hosted and Dedicated:
- There must exist a generated public release note entry for the promotion event.
- If the changelog generator is degraded, promotion may proceed only under a break-glass procedure (see below) and must generate notes within the defined SLA.

### Gate C: audit logging
Promotion cannot proceed unless audit event emission is healthy:
- Audit event must be emitted and acknowledged (async with retry; promotion call blocks until event is enqueued).
- If audit pipeline is down, promotion requires Security on-call approval.

### Gate D: rollout policy alignment
If promotion is tied to canary/A-B rollout:
- The version must declare rollout eligibility fields (e.g., allowlisted tiers/regions).
- Rollback policy must exist for breaking/security/deprecation categories.

## CI implementation details (GitHub Actions conventions)
### Standard jobs (model registry repo)
- `metadata-schema-validate`: runs on PR and `main` pushes
- `metadata-schema-diff-policy`: runs on PR when schema changes
- `release-note-preview`: runs on PR when metadata changes
- `redaction-and-rbac-tests`: runs on PR when templates/redaction rules change
- `fixtures-and-examples-check`: runs on PR when schema changes

### Artifacts uploaded by CI
- `schema-diff.txt`
- `metadata-lint-report.json` (machine readable; used by bot comments)
- `release-note-preview-public.md`
- `release-note-preview-internal.md`

### Bot commenting
CI posts a PR comment with:
- Validation status and errors
- A rendered release note preview snippet
- A checklist of missing required fields

## Required PR labels and approvals
The following labels are used to route approvals and enforce additional checks:
- `model-metadata-change` (required for any metadata record change)
- `schema-change` (required for schema changes)
- `release-notes-reviewed` (required when `public.category` is breaking/security/deprecation)
- `security-review-required` (automatically applied when internal/public boundary rules are touched)
- `release-eng-approval` (required for schema diffs flagged WARN by policy)

Approval requirements:
- Schema changes: must be approved by Model Catalog schema owner (Quentin Harris) and Release Eng (Connor O'Brien) when diff-policy is WARN/FAIL.
- Redaction rules or template changes: must be approved by Security (Naomi Feldman or delegate).
- Console/API contracts for release notes: must be approved by Console backend EM (Chloe Martin) if endpoints are impacted.

## Break-glass procedure (rare)
If the changelog generator or docs publishing pipeline is down, promotion can proceed only if all conditions are met:
- Incident is declared (or tracked) and linked in the internal-only promotion ticket.
- Release Eng on-call approves.
- Security on-call approves if audit emission is impacted.
- A manual public release note stub is created (public-safe, minimal) and later reconciled with the generated canonical artifact.

Post-incident requirement:
- Within 24 hours, a backfill job must generate the canonical release note artifact and replace the stub.

## Backfill and migration considerations
When migrating existing model records to Metadata Schema v1:
- Backfill jobs must run in staging first.
- CI must validate a representative sample of existing records (minimum 95% coverage by model family and deployment mode).
- A rollback plan is required, including:
  - revert commit instructions
  - DB migration rollback steps (if applicable)
  - monitoring dashboards to confirm health post-rollback

## Monitoring and SLOs (pipeline health)
We monitor:
- % of promotions with a public release note published within SLA
- Time from promotion event to release note availability in Console
- Redaction test failures and attempted leaks caught by CI

Target SLOs:
- 99.5% of promotions produce a public release note artifact within 10 minutes.
- 99.9% of promotions emit an audit event within 1 minute.

## Troubleshooting
### CI fails: "release note preview missing required fields"
- Ensure the metadata change includes required `public.*` fields.
- If change is internal-only and should not produce public notes, mark the change accordingly in metadata (internal-only change classification) and re-run CI.

### CI fails: "public artifact contains internal-only content"
- Search the template inputs for `internal.*` or restricted references.
- Ensure links in `public.references` point to docs-site URLs only.

### Promotion blocked: "audit enqueue failed"
- Check audit pipeline status in observability dashboards.
- If confirmed outage, follow break-glass procedure and obtain approvals.
