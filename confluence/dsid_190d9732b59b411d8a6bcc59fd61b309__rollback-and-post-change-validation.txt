Runbook: Rollback and Post-change Validation (Hosted API + Console)

h1. Purpose
This runbook defines the required steps to rollback a production change and the required post-change validation steps (including after a rollback). It applies to Hosted API and Console.

h1. Guiding principles
* Prefer fast rollback over extended debugging when customer impact is ongoing.
* Rollback should return the system to a known-good state with minimal risk.
* Always leave a trace: update the change record and incident timeline.

h1. Preconditions
* Identify the last known-good build (image digest or build number).
* Identify what changed: code deploy, config/policy bundle, schema migration, feature flags.

h1. Rollback decision criteria
Rollback immediately if:
* Canary or post-deploy gates fail (error/latency regression beyond thresholds)
* New Sev2+ customer impact appears plausibly correlated
* Data correctness, billing, auth, or routing correctness is in question

h1. Rollback steps (generic)
1. Stop further rollout
   * Pause deployments and disable automated promotions.
2. Revert highest-leverage toggles first
   * Disable or revert feature flags / routing policy bundles associated with the change.
3. Redeploy prior build
   * Redeploy the previous image digest to the impacted region(s).
   * For Hosted API, roll back region-by-region starting with the canary/most impacted region.
4. Validate health
   * Confirm service readiness and key smoke tests pass.
5. Document
   * Update change record with: trigger, rollback start/end time, and final state.

h1. Special cases
* Schema migrations:
  - If a forward-only migration was applied, rollback may require a compensating forward fix rather than reverting binaries.
  - Always involve the service owner and SRE on-call.
* Auth/RBAC changes:
  - Validate both positive and negative authorization outcomes after rollback.

h1. Post-change monitoring window (required)
For any production change (successful or rolled back):
* Enhanced monitoring for at least 60 minutes after the system is stable.
* Confirm: error rate, p95 latency, saturation metrics, and a representative customer workflow.

h1. Closure requirements
A change record is not closed until it includes:
* Final deployed build identifiers (or confirmation of rollback)
* Links to dashboards used and observed outcomes
* Follow-up tickets for any discovered issues
