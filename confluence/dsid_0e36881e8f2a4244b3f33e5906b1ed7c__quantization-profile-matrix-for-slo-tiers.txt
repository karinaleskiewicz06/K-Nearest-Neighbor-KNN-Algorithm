Quantization profile matrix for SLO tiers (fast / standard / cost-efficient)

## Purpose
This page defines Redwood’s *recommended quantization variants* per **latency SLO tier** (fast / standard / cost-efficient) and **model family**, and documents the **compatibility constraints** between quantization and the new workload-aware batching defaults.

This is intentionally a *matrix of supported, production-recommended choices* (not an exhaustive list of all quantizers). It is used by:
- Model catalog metadata ("recommended profiles")
- Runtime defaults for tiered batching (avoid unsafe/unsupported combos)
- Console “recommended tier/profile” explanations
- Perf canary and benchmark gating configuration

## Non-goals
- Per-tenant online auto-tuning (out of scope for initial tiered batching launch)
- Model-by-model micro-optimizations beyond the listed families

## Definitions
**Tier (customer-facing):**
- **fast**: prioritize tail latency and stable streaming cadence.
- **standard**: balanced latency and throughput.
- **cost-efficient**: maximize throughput / lowest $/1K tokens while remaining within published SLOs.

**Quantization variants (naming used in model catalog + runtime):**
- **bf16**: baseline high-quality, higher memory footprint.
- **fp16**: similar to bf16, used on some older kernels; prefer bf16 when supported.
- **w8a16 (int8 weight-only)**: weights int8, activations bf16/fp16.
- **w4a16 (int4 weight-only, AWQ/GPTQ-class)**: weights int4, activations bf16/fp16; best cost, higher risk.
- **fp8 (fp8 compute / or weight+activation fp8 depending on kernel)**: hardware-dependent (primarily H100); strong perf, can be sensitive on some tasks.
- **kv8 (KV cache fp8)**: KV cache stored in fp8 (or similar reduced precision), reduces memory pressure and improves batching headroom; may affect quality in edge cases.

**Batching defaults (scheduler knobs affected):** max_wait_ms, max_batch_tokens, max_batch_size, admission control/backpressure, prefill/decode balancing.

## Quick guidance (what to pick)
- **fast**: prefer **bf16** (or **w8a16** only when it does not regress p99/stream cadence on the target hardware/model).
- **standard**: prefer **w8a16** (or **bf16** when model is sensitive or kernels are unstable).
- **cost-efficient**: prefer **w4a16** *or* **fp8** (H100) *plus* optional **kv8** when needed to prevent memory-bound batching collapse.

## Compatibility constraints with tiered batching defaults
The tiered batching project makes some combinations either unsupported or strongly discouraged because they create “foot-guns” under mixed workloads.

### 1) Streaming stability (fast tier)
- Streaming endpoints are more sensitive to **decode-time jitter** (kernel variance + queueing).
- Quantization variants that introduce sporadic dequant overhead or kernel fallback can cause *visible token cadence variability* even when average latency is acceptable.
- **Rule:** For **fast + streaming**, only variants listed as “✅ fast-safe streaming” in the matrix are supported by default.

### 2) Prefill memory headroom (cost-efficient tier)
- Cost-efficient uses larger batches and higher max_batch_tokens; prefill is frequently memory-bound.
- Aggressive quantization can help (smaller weights), but **KV cache often dominates** for long contexts.
- **Rule:** If peak KV memory is the limiting factor (detected by runtime signals), allow **kv8** (KV cache reduced precision) only for model families marked “kv8-compatible”.

### 3) Kernel availability / fallback risk
- Some model families + quant modes require specific kernel paths; if a fallback path is triggered at runtime, latency SLOs become unpredictable.
- **Rule:** If kernel coverage is partial for a mode on a given GPU class, the runtime should not select it as a tier default; it may be available only as an explicit override with warnings.

### 4) Mixed prompt-length + concurrency
- Under mixed workloads, low-precision modes can change the “best” prefill/decode split and batch shaping.
- **Rule:** The scheduler assumes tier profiles were benchmarked against the quant variant. Do not mix unbenchmarked pairs (e.g., switching to w4a16 while keeping fast-tier wait budgets) without re-validation.

### 5) Observability and reason codes
When the runtime does not apply the recommended quantization for a tier, it must emit a reason code:
- `model_constraint` (mode unsupported by model family)
- `hardware_constraint` (mode unsupported by GPU class)
- `tier_safety` (disallowed for tier, e.g., fast+streaming)
- `overload_mode` (temporary safety behavior)
- `customer_override` / `route_override`

## Batching-default constraints by quant mode (operational checklist)
Use this when pairing tiered batching profiles with quantization.

### bf16 / fp16
- Safest for fast-tier streaming.
- Highest memory usage; can constrain max_batch_tokens in cost-efficient.
- **Recommended batching posture:** smaller max_batch_tokens for large models; rely on scheduler admission control under burst.

### w8a16 (int8 weight-only)
- Usually a strong default for standard tier.
- Potential risk: kernel fallback on some GPU/model combos; may introduce latency spikes.
- **Batching posture:** standard tier can increase max_batch_tokens moderately; keep fast tier conservative.

### w4a16 (int4 weight-only)
- Best cost/throughput when kernels are robust.
- Higher risk for quality regressions on strict formatting tasks and some multilingual edge cases.
- **Batching posture:** cost-efficient can use larger batches, but must enforce queue depth guardrails to prevent “batching runaway.”

### fp8 (H100)
- Strong throughput for both prefill and decode on H100-class hardware.
- Quality is generally acceptable but requires tier-specific prompt-set validation.
- **Batching posture:** cost-efficient can push larger batches; ensure decode-time jitter is acceptable if used with streaming.

### kv8 (reduced-precision KV cache)
- Primarily a memory headroom lever for long context.
- Can affect quality subtly (especially long multi-turn chats); requires targeted evals.
- **Batching posture:** enables higher max_batch_tokens without OOM; must be paired with strict regression detection (quality + latency).

## Quality and safety requirements (must pass to be “✅ Recommended”)
A quant mode is marked ✅ only if it passes:
- **Perf gates:** tier-specific latency targets in the benchmark methodology (p95/p99 as defined in SLO tier doc), plus streaming cadence stability checks where applicable.
- **Correctness:** no increased error rate (timeouts, OOMs, invalid outputs) beyond guardrail thresholds.
- **Quality guardrails:** see linked “quality checks” page. At minimum:
  - Structured output / tool-call format pass rate (no regression beyond agreed threshold)
  - Prompt-set win-rate or score regression below the allowed delta per task type
  - No increase in truncation-related failures attributable to batching/quant changes

## How this matrix is used in product/runtime
1) **Catalog metadata:** each model advertises allowed quant profiles per GPU class.
2) **Tier default selection:** runtime chooses a tier profile that is valid for (model family, GPU class, endpoint mode [streaming/non-streaming]).
3) **Fallback behavior:** if a recommended profile is not available, runtime falls back in this order unless overridden:
   - cost-efficient: fp8 → w4a16 → w8a16 → bf16
   - standard: w8a16 → bf16
   - fast: bf16
4) **Telemetry:** always emit selection reason codes when falling back or applying overrides.

## Open items / known limitations (as of 2026-02-20)
- MoE families: limited recommended low-precision defaults due to higher variance and kernel coverage gaps.
- L4 cost-efficient: w4a16 supported only with conservative caps on max_batch_tokens; otherwise OOM risk under long contexts.
- kv8: allowed only on selected dense families; still collecting more long multi-turn chat eval evidence.

## Appendix: FAQ
**Q: Does choosing a batching tier automatically change quantization?**
A: Not in the first release. Tier selects batching defaults; quantization follows model catalog “recommended profile” defaults and compatibility rules. Console may suggest a quant mode for cost-efficient but will not auto-apply without explicit configuration.

**Q: Why is fast tier mostly bf16?**
A: Fast tier prioritizes predictable tail latency and stable streaming cadence. Even small kernel fallback risk or decode jitter can violate user-visible expectations.

**Q: Can enterprise customers override this matrix?**
A: Yes, via route/tenant overrides (Dedicated/Private). Overrides are supported but must still satisfy “allowed” constraints for the hardware/model; otherwise runtime will reject or fall back with reason codes.
