Oncall Runbook: GPU Egress Surge Mitigation and Traffic Shaping

Summary
-------
This runbook describes steps for oncall engineers to triage and mitigate sudden GPU-driven egress surges that threaten network bandwidth limits, cause NAT/egress gateway saturation, or create large cross-region transfer costs. It covers detection thresholds, quick mitigations (traffic shaping, tenant throttles, egress policy changes), scaling actions, and post-incident restores.

Scope and applicability
-----------------------
- Applies to Redwood-managed GPU workloads using shared egress/NAT gateways (hosted/Dedicated pools and private deployments).
- Covers tenant-visible symptoms: elevated egress billing rate, slow downstream APIs, increased packet drops, and NAT exhaustion.
- NOT a replacement for long-term capacity planning; follow-up action items are listed under Postmortem & Remediation.

Ownership
---------
- Primary oncall: Infra Network oncall (infra-oncall rotation)
- Secondary: GPU Fleet oncall
- Escalate to Network Reliability (pager) after 30 minutes if service-affecting or L3 intervention required

Runbook triggers (automated + manual)
------------------------------------
Automated alerts that should immediately invoke this runbook:
1) EGRESS_QPS_SURGE (> 3x baseline for 5m)
2) NAT_PORT_UTILIZATION > 90% for > 2m
3) Cross-region egress cost burn rate > 50% of daily budget within 1h
4) GPU tenant flow drop rate > 1% and user-facing error rate increase > 0.5%

Also: oncall might be paged by product SRE when user-reported latency correlates with egress errors.

Preflight checks (first 3 minutes)
--------------------------------
- Check centralized telemetry:
  - kubernetes cluster egress metrics (egress_bytes_total, egress_flow_errors)
  - NAT gateway metrics in cloud console (bytes/sec, port utilization)
  - Billing burn dashboard (egress-by-tenant last 60m)
  - Model-serving pods KV cache latencies and recent sequence length distribution
- Identify affected tenants: filter egress-by-tenant and tenant metadata (team, workspace, plan).
- Determine blast radius: single tenant vs. pool-wide vs. multi-region

Immediate mitigation (fast, reversible)
-------------------------------------
Follow these numbered steps in order until user impact is controlled:
1) Apply tenant-level rate limit via egress-proxy
   - Rationale: fastest surgical mitigation that preserves other tenants.
   - Command example (Traefik/Envoy control plane):

   curl -X POST https://egress-api.internal/v1/limits 
     -H 'Authorization: Bearer $RUNBOOK_TOKEN' 
     -H 'Content-Type: application/json' 
     -d '{"tenant_id":"tenant-1234","egress_bps": 250000000}'

2) If tenant unknown or surge is pool-wide, enable prefix-based traffic shaping on egress gateway
   - Add a shaping rule that caps GPU-pool-prefix to 60% of peak bandwidth for 15 minutes.
   - Example iptables tc command on Linux NAT hosts (apply carefully):

   # limit outgoing to 600Mbps for GPU-pool prefix\   tc qdisc add dev eth0 root handle 1: htb default 10
   tc class add dev eth0 parent 1: classid 1:1 htb rate 600mbit
   tc filter add dev eth0 protocol ip parent 1:0 prio 1 u32 match ip dst 10.200.0.0/16 flowid 1:1

   - NOTE: prefer using the egress controller API when available.

3) Scale NAT/egress gateway capacity (if automated scaling available)
   - Trigger autoscale: aws autoscaling set-desired-capacity --auto-scaling-group-name nat-gw-asg --desired-capacity 6
   - If using managed gateway (Cloud NAT), increase NAT IPs: set natIPCount to +2 via platform console.

4) Restrict cross-region transfers via temporary routing policy
   - Push a BGP/route policy that forces traffic to remain in-region for bursty prefixes (for private deployments work with network-admin).
   - Example: change route-map GPU-BURST to prefer local egress next-hop.

5) Apply quick model-serving controls (if egress caused by eval/large-token runs)
   - Use the runtime control-plane to throttle long-sequence inference jobs: reduce max_sequence_length and enforce per-request token ceiling 2048.
   - Example runtime CLI: redwoodctl runtime update --pool gpu-fast --max-tokens 2048 --apply-immediate

Observability and communication
-------------------------------
- Post mitigation, maintain 1-minute checks for 30 minutes: NAT port util, egress bps, tenant errors.
- Notify stakeholders (Slack #infra-ops, #customer-impact) with: incident id, affected tenants, mitigation steps, ETA for full restore.
- Use incident-template: 
  - Summary, Timeline, CurrentStatus, NextSteps, POC.

Scaling and durable responses (30–120 minutes)
--------------------------------------------
If immediate steps insufficient, escalate to one of the following durable responses:
- Provision an additional egress VPC gateway (apply IaC module):
  - Terraform snippet (module usage):

  module "egress_gateway" {
    source = "git::ssh://git@repo/internal-iac//modules/egress-gateway"
    name   = "gpu-egress-extra-01"
    nat_ips = 2
    instance_type = "c6g.large"
  }

  terraform init && terraform apply -var-file=secrets.tfvars -auto-approve

- Create a temporary tenant credit hold: mark tenant in billing system as "egress-paused" to stop heavy jobs. Follow finance policy and notify customer success.
- Schedule per-tenant quota increases only after root-cause analysis and authorization.

Restore and cleanup (post-incident)
----------------------------------
- Gradually revert traffic-shaping rules after 45–90 minutes of stable metrics. Use staged removal: 75% -> 90% -> 100% over three 10-minute intervals.
- Remove any emergency NAT capacity after idle for 2h and confirm no regressions.
- If tenant credit hold applied, coordinate with Customer Success for controlled release.

Postmortem & remediation actions (owner + timeline)
--------------------------------------------------
1) Within 24h: Incident owner (oncall) files a 1-page incident summary with timelines and metrics.
2) Within 72h: Network team adds or adjusts guardrails in egress controller: per-tenant burst budget, default hard cap for sandbox tenants.
3) Within 7 days: Infra-planning to evaluate adding an automated detection -> mitigator pipeline (Alert -> Apply tenant cap -> Notify).
4) Longer term: If frequent, create a reserved egress tier for large-eval customers and update pricing & self-serve controls.

Required access and runbook tokens
----------------------------------
- Required roles: infra-network-admin, infra-oncall, gpu-fleet-ops
- Runbook token environment variable: RUNBOOK_TOKEN (stored in Vault, path: secret/infra/runbooks/egress-mitigation)
- Playbook service accounts: egress-api-service-account@redwood-internal (must have RBAC to modify limits)

Forensics checklist and artifacts to collect
------------------------------------------
- Snapshot graphs: egress-by-tenant (60m), nat-port-utilization (60m), cross-region egress (24h)
- List of iptables/tc rules added and removed (save as runbook artifact)
- Terraform apply logs if new capacity was provisioned
- Runtime trace logs for heavy model requests (request_id list)

Appendix: quick reference thresholds and commands
------------------------------------------------
Thresholds (example):
| Metric | Trigger threshold | Action |
|--------|-------------------:|--------|
| NAT port utilization | 90% for >2m | Run this playbook, scale NAT |
| Egress bytes (pool) | +300% over 5m | Apply pool-level shaping |
| Tenant egress (bps) | > 2 Gbps sustained for 10m | Tenant hard cap, contact CS |

Common commands
- Check NAT ports (AWS): aws cloudwatch get-metric-statistics --namespace AWS/NATGateway --metric-name BytesOutToDestination --start-time $(date -u -d '10 minutes ago' +%Y-%m-%dT%H:%M:%SZ) --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) --period 60 --statistics Sum
- Apply tenant limit (egress-api): curl -X POST https://egress-api.internal/v1/limits -H 'Authorization: Bearer $RUNBOOK_TOKEN' -d '{"tenant_id":"<id>","egress_bps":250000000}'
- Scale ASG (example): aws autoscaling set-desired-capacity --auto-scaling-group-name nat-gw-asg --desired-capacity 6 --profile infra-admin

Notes and best practices
- Prefer controller APIs over host-level iptables/tc for consistency and observability.
- Keep runbook token usage audited; every emergency limit change must be recorded in incident artifacts.
- For private deployments, follow customer SLA and coordinate with the account's network contact before cross-region routing changes.
