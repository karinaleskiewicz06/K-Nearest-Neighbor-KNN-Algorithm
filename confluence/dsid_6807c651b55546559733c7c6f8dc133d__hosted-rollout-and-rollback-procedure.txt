Hosted Rollout + Rollback Procedure (Runtime and Gateway Changes)

h2. Scope
This procedure applies to production rollouts on the Hosted API fleet for:
* serving runtime image updates
* request router changes
* gateway config changes

h2. Preconditions
* Runtime hotfix built and signed (see /eng-infra/ci-cd-and-build/hotfix-build-and-signing)
* Emergency approvals recorded if this is a hotfix (see /policies-and-process/change-management/emergency-change-policy-v3)
* Rollout owner identified (Platform on-call or delegated engineer)

h2. Rollout order
Default order for runtime hotfix rollouts:
# Canary: us-west-2a (10% traffic)
# Expand: us-west-2 (50% traffic)
# Expand: us-east-1 (50% traffic)
# Expand: eu-central-1 (50% traffic)
# Global: all regions

If incident indicates region-specific issue, canary in an unaffected region first to validate no regressions.

h2. Canary criteria (must be explicitly checked)
Monitor for 15 minutes minimum:
* Request success rate (2xx/stream completes)
* p95 latency for top 3 routes
* GPU OOM rate
* Router fallback rate
* Error budget burn rate

Canary pass thresholds:
* No sustained error rate increase > 0.2% absolute
* p95 latency not worse than +10% vs previous runtime
* No new crash-looping pods

h2. Rollout execution
1. Announce in incident channel (or #eng-releases) that rollout is starting + tag being deployed.
2. Update deploy config:
   * runtime_image_tag = <new-tag>
3. Apply via ArgoCD: 'hosted-runtime' app
4. Wait for steady state before expanding traffic weight.

h2. Rollback triggers
Roll back immediately if any occur:
* elevated 5xx/stream aborts above threshold for > 5 minutes
* GPU OOM rate spikes > 2x baseline
* p95 latency regression > 20% for > 10 minutes
* customer reports correlate strongly with rollout start

h2. Rollback procedure
1. Set runtime_image_tag back to last known good tag.
2. ArgoCD sync 'hosted-runtime'.
3. Confirm steady state and error reduction.
4. Post in incident channel: rollback executed + brief reason + next step.

h2. Post-rollout
* Update incident timeline and comms per /oncall-and-incident-response/incident-process/sev1-communication-requirements
* Create follow-up task to promote hotfix into the next regular release branch
