gpu-rollback-simulations-and-chaos-ci-playbook

Overview:

This playbook defines the policy, CI/CD jobs, and runbook for scheduled rollback simulations and GPU-focused chaos experiments we run against Redwood's serving and infra stacks. The goal is to validate automated rollback paths, alerting, and mitigation behavior when we experience partial GPU capacity loss, node preemption, or network segmentation. Run frequency: scheduled monthly for non-production clusters; quarterly for staging; ad-hoc for production only with executive approval (see "production gating" section).

Scope and audience:

- Audience: infra engineers, SRE, release engineers, and oncall responders.
- Scope: GPU node preemption, spot/interrupt scenarios, tenant routing fallbacks, autoscaler rollbacks, terraform module destroy/recreate simulations, and CI/CD pipeline rollback verification.
- Out of scope: model-level quality regressions, app-layer functional tests (these are covered in app test suites).

Why we run these simulations:

1. Validate that rollout automation will perform an automated rollback that meets SLOs (latency and availability) when the serving fleet loses X% of GPU capacity.
2. Ensure alerting and escalation pages fire with correct runbook links and runbook ownership.
3. Detect gaps in terraform/IaC drift detection and module dependency teardown during rollbacks.
4. Verify that network policies and egress controls do not silently block fallback routing or control-plane operations.

Success criteria (pass/fail):

- Critical: automated rollback completes within configured target window (default 15m for staging, 30m for production), traffic fallback to healthy variants completes with <2x latency degradation, error budget burn limited to <10% of daily budget for the service under test.
- Secondary: no Terraform state corruption or locked remote state; CI job artifacts are preserved; alert noise limited to expected pages only.

Test types and primitives:

1) Preemption simulation (node-level):
- Action: use cloud provider API or simulator to inject a graceful preemption on N GPU nodes.
- Targets: 5%, 15%, 40% of pool capacity (table below).
- Expected outcome: autoscaler marks nodes NotReady -> pods rescheduled; serving routing removes instances and uses fallback policy.

2) Spot eviction storm (batch):
- Action: terminate spot instances with matching GPU labels across AZs to simulate correlated failures.
- Expectation: cross-AZ fallback routes engage; dedicated fallback (reserved pool) absorbs critical traffic.

3) Network partition (control plane):
- Action: add iptables rules on a subset of nodes or use network-chaos to throttle control-plane egress to provisioning API and remote-state store.
- Expectation: rolling updates should pause; coordination leader election remains healthy; operators notified.

4) Terraform destroy/recreate simulation (IaC):
- Action: run a controlled terraform apply that taints and recreates a small set of resources (e.g., GPU nodegroup autoscaling group) in a test workspace with the same modules used in production.
- Expectation: remote state remains intact, module dependencies recreate correctly, no leaked resources, and rollback of the apply (terraform apply -var execute=false equivalent) restores previous pointers.

Simulation matrix (examples):

| Scenario | Target cluster | Capacity impact | Run job | Who owns |
|---|---:|---:|---|---|
| Small preempt | dev-a | 5% | ci/gpu-sim/small-preempt | release-eng

Automation: CI job definitions

We define a set of GitHub Actions workflows and Jenkins jobs that orchestrate the simulation. Each CI job must:
- run against a tagged cluster (env var CLUSTER=),
- execute in a sandbox project/account, never production unless explicitly approved (APPROVED_BY list),
- create a short-lived issue and update it with progress logs,
- produce artifacts: events dump, terraform plan, and cluster node/pod snapshots.

Example GitHub Actions snippet (pseudo):

name: GPU Rollback Simulation - Moderate Preempt
on: workflow_dispatch
inputs:
  cluster:
    description: 'Cluster tag to run against'
    required: true
    default: 'staging'
  approval_token:
    description: 'Required for production runs'
    required: false

jobs:
  run-simulation:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Authenticate to cloud
        run: ./scripts/auth.sh ${{ inputs.cluster }}
      - name: Trigger preempt (cloud api)
        run: ./scripts/inject_preempt.sh --cluster ${{ inputs.cluster }} --pct 15
      - name: Collect artifacts
        run: ./scripts/collect_snapshot.sh --out artifacts/staging-$(date +%s).tar.gz

Chaos tooling recommendation:

- Use litmuschaos or kube-chaos for in-cluster pod/network faults.
- Use provider SDKs for node/spot termination events to capture realistic behavior (AWS EC2 Spot/Google Preemptible).
- Do not use kubelet -–kubeconfig manipulations that bypass cloud provider behavior; we want realistic signals (node NotReady, eviction API calls).

Observability and metrics to capture:

- SLOs: p50/p95/p99 latency, requests per second, error rate (5xx), and tail latency on critical routes.
- Infra metrics: node count, pod evictions, pod restart counts, pod scheduling latency, autoscaler scaling events, and kube-controller-manager leader election metrics.
- Alerting: ensure pages tied to these alerts include the runbook link: 'GPU rollback simulation runbook'.

Threshold examples (defaults):

- p99 latency < 2x baseline for < 30 minutes: warning
- error-rate > 1% for 5m: page to oncall
- autoscaler cooldown > 10m without activity: investigate
- terraform plan unexpectedly non-empty after rollback: page iac-owners

Run schedule and approvals:

- Non-prod (dev, test): automated monthly; job triggered by release-eng with standard checkout approval.
- Staging: automated quarterly; SRE must be in review list.
- Production: manual only. CD/Release lead must add APPROVED_BY signature and security review.

Pre-run checklist (must pass):

1. Backup remote state and snapshot critical resources (terraform state snapshot + cluster etcd backup).
2. Notify Slack channel #infra-chaos at least 48 hours in advance and include the issue link.
3. Confirm oncall shift for the window and assign a dedicated observer from SRE.
4. Verify smoke tests for control-plane and API gateways pass pre-sim (baseline).

Runbook: immediate steps when a simulation causes unexpected regression

1. Stop the CI job and pause simulation orchestrator.
2. Revert traffic to fallback model/version using runtime routing controls (owner: serving-runtime oncall).
3. If autoscaler misbehaves, force scale with documented safe counts: kubectl scale --replicas=<safe-count> or use cloud console to add nodes.
4. If Terraform state shows drift or lock is stuck, contact infra-iac and run remote-state unlock procedure: terraform force-unlock <LOCK_ID>.
5. Collect artifacts and open postmortem issue with 'high-priority' template.

Ownership and escalation:

- Primary owner: infra-sre (runbook exec, oncall).
- IaC owner: infra-iac (terraform state recovery).
- Serving/runtime owner: serving-runtime team (fallback routing and model pinning).
- Network owner: network-eng (if network partitioning is simulated).

Post-run analysis and reports:

- Each simulation must produce a concise report within 48 hours: summary, pass/fail against success criteria, timeline of events, lessons learned, recommended config changes, and follow-up action items with owners and due dates.
- Metric baselines must be persisted and compared via the metrics-diff tool.

Implementation notes and snippets:

- Terraform module example (taint-only simulation):
  # terraform snippet (pseudo)
  module "gpu_nodegroup" {
    source = "git::ssh://git@repo/terraform-modules//gpu-nodegroup"
    cluster = var.cluster
    desired_count = var.desired_count
  }

  # Taint resource to force recreate
  terraform taint module.gpu_nodegroup.aws_autoscaling_group.this[0]

- kubectl collection commands:
  kubectl get nodes -l "node-role.kubernetes.io/gpu=true" -o wide > artifacts/nodes-$(date +%s).txt
  kubectl get pods --all-namespaces --field-selector=status.phase=Failed > artifacts/failed-pods-$(date +%s).txt

Risk matrix and mitigations:

- Risk: Accidental production run. Mitigation: CI gate requires an "APPROVED_BY" list and a production lockfile stored in a protected S3 bucket; jobs will fail if lockfile not present.
- Risk: Terraform remote state locked. Mitigation: pre-run snapshot and a documented force-unlock path with contact list.
- Risk: Alert fatigue. Mitigation: simulation jobs set an alerting context label so that downstream alerting systems suppress non-essential noise and tag pages as "simulation".
