GPU IaC deployment gate manifest and rollback playbook

Summary
-------
This document defines the authoritative manifest and operational playbook for promoting GPU-related Terraform/Helm/Operator changes through our CI/CD lanes: dev -> staging -> canary -> prod. It codifies promotion gates, automated preflight checks, SLO/metric thresholds for automated promotion, and the explicit rollback manifest to follow on degradations or regressions.

When to use this manifest
------------------------
- Any IaC change that impacts GPU fleet allocation, node images, kernel/driver versions, or inference serving runtime bundles.
- Changes to Terraform modules that will be promoted across multiple cloud accounts or regions.
- Any change that modifies warm pools, preemptible/spot fallback policies, or tenant QoS knobs.

Goals and constraints
---------------------
- Goal: Avoid widespread capacity regressions or tenant impact during IaC rollout.
- Constraint: Promotion must not require manual full-cluster restarts; aim for rolling, idempotent changes.
- Safety principle: If an automated gate is ambiguous, require human approval (fail closed).

Promotion gates (summary)
------------------------
1) Static checks (CI lint + policy): Terraform fmt/validate, OPA/Gatekeeper policy checks, module pinning verification.
2) Unit/plan review: Terraform plan diff includes (explicit list of resources and delta size). Reject plans that add or change > 20% of warm-pool nodes for a single region without an approved change ticket.
3) Canary deploy: Controlled apply in canary region/account with shadow traffic profile.
4) Observability gate: 30m observation window with specific metric thresholds (see Metrics & SLOs).
5) Auto-promotion: If canary is healthy and metrics pass, pipeline can auto-promote to staging. Manual approval required for cross-account production promotion if delta > 10% fleet.

Pre-flight checklist (CI job tasks)
----------------------------------
- terraform/fmt, terraform/validate
- terraform/plan with `--out` artifact uploaded to artifact store
- OPA policy scan: no deny policies
- Module-compatibility check: verify downstream module pin versions for each tenant folder
- Image provenance: signed image digest verified (cosign or similar)
- Egress/CNI quick simulation: ensure new NAT/egress rules keep < 5ms median additional latency in synthetic probe

Canary promotion flow (step-by-step)
-----------------------------------
1) Create a canary run: `ci promote --target canary --plan-plan-artifact=ARTIFACT_ID`
2) Apply with `TF_VAR_canary=true` and region=us-west-2-canary-account
3) Wait for apply to finish. CI records plan/apply output and diffs.
4) Start synthetic traffic: small tenant subset (1–2%) against canary instances with tokenized traffic mix for 45 minutes.
5) Observe metrics window (30–45m). If all gates pass, CI sets canary status = pass.
6) If pass, pipeline may auto-promote to staging (or create manual approval step for prod).

Metrics & SLO thresholds (canary observation)
---------------------------------------------
| Metric | Threshold (pass) | Action on fail | Rationale |
|---|---:|---|---|
| API p50 latency (inference) | <= baseline + 10% | Rollback canary | Latency sensitive for interactive customers |
| Token throughput | >= baseline - 5% | Rollback canary | Avoid throughput regressions |
| Error rate (5xx) | < 0.25% absolute | Rollback canary & open incident | Small absolute increases are significant |
| KV cache miss rate | <= baseline + 8% | Rollback canary | KV miss correlates to cost & latency |
| Disk/network attach failure | 0 occurrences | Immediate rollback & pager | Hard failure symptom |

Note: Baseline comes from a synthetic pre-promotion snapshot recorded by the pipeline. The pipeline calculates rolling baseline percentiles (p50/p95/p99) from the last 6 hours of staging traffic.

Rollback manifest (explicit steps to revert an IaC promotion)
-------------------------------------------------------------
1) If canary or staging fails, mark promotion as failed in CI and block further promotions.
2) Trigger rollback job: `ci rollback --from-plan=ARTIFACT_ID --to-tag=previous-stable`
3) Apply rollback to affected canary region first. Monitor 15 minutes.
4) If rollback stabilizes, schedule rolling rollback to staging / prod with staged waves (region-by-region) following the same canary windows.
5) After rollback, open postmortem and record root cause within 48 hours (owner assigned).

Operational runbook (incident-oriented)
--------------------------------------
- Pager triggers: any increase in 5xx > 0.5% absolute, disk/network attach failures, or SLO SLI breaches for two consecutive 5-minute windows.
- On-call responder (SRE) steps:
  1) Assess scope: which AWS accounts/regions and which tenant groups are impacted.
 2) If change recently promoted, check CI promotion status and plan diffs.
 3) If change caused capacity churn (nodes terminating/creating) — run `aws ec2 describe-instances` and correlate with Terraform plan outputs.
  4) If noisy auto-scaler triggered unexpected drains, consult the Autoscaler audit log: `s3://redwood-telemetry/autoscaler/audit/YYYY/MM/DD`
  5) Decide: rollback (preferred) or mitigations (e.g., add temporary warm pool) with engineering approval.

Quick commands (examples)
------------------------
- Generate plan: `terraform plan -out=tfplan-${CI_RUN_ID}.bin`
- Show diff: `terraform show -no-color tfplan-${CI_RUN_ID}.bin | sed -n '1,200p'`
- Apply canary: `TF_VAR_canary=true terraform apply tfplan-${CI_RUN_ID}.bin`
- Rollback: `ci rollback --to-tag v2025.01.02-stable --regions us-west-2,eu-central-1`

Terraform module tagging & release policy
---------------------------------------
- Modules must use semantic versions (vMAJOR.MINOR.PATCH) and changelogs.
- Breaking changes require an ADR and a scheduled maintenance window.
- Module release procedure:
  1) Cut a release branch: `release/<module>/vX.Y.Z`
  2) Run `ci module-integration` across tenant module consumers in shadow mode
  3) Tag and sign release artifact.
  4) Start promotion from canary to staging per the manifest.

CI job layout (lane responsibilities)
-----------------------------------
- ci/validate: runs linting, fmt, unit tests, OPA checks. Fails fast.
- ci/plan: creates a plan artifact and uploads to artifact store; posts plan summary to PR.
- ci/canary-apply: applies in canary account and starts synthetic probe job.
- ci/promote: gated promotion job that requires either auto-pass from canary or manual approver.
- ci/rollback: handles automated and manual rollback runs.

Ownership, contacts and run cadence
----------------------------------
- Primary owner: infra-deployments@redwood.com (Infra - CI/CD team).
- Secondary: gpu-fleet@redwood.com (GPU fleet team).
- Weekly cadence: automated dry-run promotions run every Sunday 03:00 UTC against non-production accounts to validate pipeline health.

Post-promotion evidence and audit
--------------------------------
- CI stores: plan artifact, apply logs, console/output snapshots, and synthetic probe results in artifact-store for 90 days.
- Mandatory post-promote checklist (to attach to changelog): plan-id, canary-result, metrics-snapshot (p50/p95/p99), and sign-off (if manual).

Appendix: Example CI YAML snippet
--------------------------------
pipeline:
  jobs:
    - name: ci/plan
      steps:
        - run: terraform init
        - run: terraform plan -out=tfplan-${CI_RUN_ID}.bin
        - run: ci upload-artifact tfplan-${CI_RUN_ID}.bin --bucket=ci-plans
    - name: ci/canary-apply
      when: pipeline.var.canary_enabled == true
      steps:
        - run: ci download-artifact tfplan-${CI_RUN_ID}.bin
        - run: TF_VAR_canary=true terraform apply tfplan-${CI_RUN_ID}.bin
        - run: ./scripts/start-canary-probes.sh --plan ${CI_RUN_ID}

Appendix B: Common failure modes and suggested mitigations
--------------------------------------------------------
- Failure: Terraform plan unexpectedly replaces warm-pool instances.
  Mitigation: Inspect plan; if replacement count > 5% and unapproved, abort promotion and seek architecture sign-off.
- Failure: Kernel/driver mismatch causes attach failures.
  Mitigation: Pin driver versions in node bootstrap image and use staged canary with single-az applies.
