Docs Refresh Migration Notes (Streaming, Tool Calling, Structured Output)

## Summary
This page captures the docs-site migration notes for the **Streaming + Tool Calling + Structured Output** examples refresh.

It is intended for:
- Docs engineering and content owners updating **redwood-docs** pages.
- SDK owners ensuring docs remain accurate across **Python/TypeScript/Go**.

## Deprecations and banner language
We are deprecating (docs-only) a set of outdated patterns that caused support load and copy/paste failures.

### Deprecated patterns (what and why)
1) **Streaming examples that concatenate only `delta.content` and ignore final assembly events**
   - Why: leads to missing final message / truncated output in edge cases.

2) **Tool calling docs that show tool arguments arriving fully formed in a single chunk**
   - Why: in streaming, arguments may arrive incrementally; examples must buffer and parse only when complete.

3) **Structured output examples that parse JSON mid-stream without an incremental-safe strategy**
   - Why: causes intermittent JSON parse errors; encourages incorrect assumptions.

4) **Older payload shapes described as “OpenAI compatible” without Redwood callouts**
   - Why: compatibility is not perfect; we must explicitly state differences where relevant.

### Standard deprecation banner copy (use verbatim)
**Deprecated:** This page reflects an older example pattern and may not match current SDK behavior. For an up-to-date, copy/paste-ready example (Python/TypeScript/Go), see: 
- Streaming: /guides/streaming-responses
- Tool calling: /guides/tool-calling
- Structured output: /guides/structured-output

### Deprecation policy for these pages
- Keep deprecated pages accessible for at least **90 days** post-launch for search/backlinks.
- Remove from primary navigation immediately.
- Ensure the deprecated page contains:
  - Banner at top
  - A single pointer to the canonical page
  - No “new” code additions (to avoid drift)

## How we keep docs in sync with SDK versions
This refresh is only successful if docs remain accurate as SDKs evolve. Our approach is to make examples **version-aware** and backed by **automated checks**.

### Canonical compatibility contract (docs-level)
Docs must reflect behavior in:
- redwood-sdk-python: latest released minor version
- redwood-sdk-typescript: latest released minor version
- redwood-sdk-go: latest released minor version

If a feature is present in one SDK but not another, docs must:
- Call it out explicitly (“Available in Python and TypeScript as of X.Y; Go support pending”).
- Provide an alternative snippet that works today, or link to the relevant SDK issue.

### Version pinning conventions (docs)
- Every code sample should include:
  - A model name placeholder that matches our recommended defaults (no internal-only models).
  - A minimal set of required imports.
  - A note on required SDK version when the snippet relies on new behavior.

Recommended footer line for recipes:
> Tested with redwood-sdk-<lang> v<MAJOR.MINOR> and Redwood API <YYYY-MM> behavior.

### “Docs ↔ SDK” sync mechanisms
1) **Snippet sync check (CI)**
   - We run a CI check to keep docs snippets aligned with example fixtures and SDK behavior.
   - If a snippet changes in an SDK PR, a docs PR must be linked.

2) **Golden transcripts for streaming/tool calls**
   - Streaming + tool-calling examples rely on golden fixtures to catch regressions in event sequencing and final assembly.
   - Any change to the event model must be approved by SDK parity + docs owners.

3) **Release coordination requirement**
   - SDK releases that update public semantics must include:
     - Changelog entry
     - Docs update PR (or explicit “no docs change” justification)
     - Support enablement blurb if user-visible

### When to document behavior vs. caveat it
- Document as “guaranteed” only when:
  - SDK behavior is stable across languages, and
  - We have tests/fixtures, and
  - PM has approved messaging.

- Otherwise use “best practice” language and include a fallback pattern.

## Known pitfalls addressed by this migration (for reviewers)
- **Partial tool-call arguments** arriving across multiple streaming events.
- **Stream disconnect/retry** guidance that does not double-apply deltas.
- **Structured output JSON validity**: validation + retry pattern instead of assuming perfect JSON.
- **Terminology drift** (“function calling” vs “tool calling”; “JSON mode” vs “structured output”).

## FAQ
### Why do we prefer “tool calling” over “function calling” in docs?
PM-approved terminology is “tool calling” to match our platform semantics (tools may call external services, not only local functions). We keep “function calling” as a redirect and search alias.

### Are these redirects breaking changes for customers?
No. Redirects preserve old URLs; canonical pages provide stable targets going forward.

### What if an SDK lags behind and can’t support the canonical example yet?
Docs must call out the limitation and provide an alternative snippet (or omit the snippet for that language and link to the tracking ticket). Do not publish a snippet that fails to compile or run.
