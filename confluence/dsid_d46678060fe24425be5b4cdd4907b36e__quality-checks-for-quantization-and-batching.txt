Quality checks and guardrails for quantization + workload-aware batching

## Overview
This page defines **quality guardrails** and **evaluation thresholds** used to approve changes to:
- **Quantization profiles** (e.g., FP8/INT8/AWQ/GPTQ variants) used by Redwood-hosted and Dedicated deployments.
- **Workload-aware batching defaults** (fast / standard / cost-efficient tiers), including scheduler heuristics that may change request grouping, prefill/decode balancing, streaming chunking, and overload behavior.

The intent is to prevent “silent” product regressions (quality, formatting, correctness, safety) while still allowing runtime improvements for latency and cost.

These checks are used as:
1) **Pre-merge gates** (where feasible) and
2) **Pre-rollout gates** (canary + perf/quality canary), and
3) **Post-rollout monitors** with explicit rollback criteria.

## Definitions and scope
### What counts as a “quality regression”
A quality regression is any statistically meaningful or practically material increase in:
- Incorrectness (factual errors, wrong tool/function calls, broken code outputs)
- Formatting failures (invalid JSON/structured output, broken function call schemas)
- Behavioral drift that breaks downstream assumptions (shortened answers due to truncation, increased refusals, repetition)
- Safety violations (content policy issues)

### Change types covered
- Runtime scheduler knobs per tier (max wait, max batch tokens, admission control, overload behavior)
- Kernel/quantization changes that affect numeric precision and decoding
- Any combination of the above (highest-risk category)

### Known mechanisms by which batching/quantization can affect quality
Batching itself should be semantically neutral, but we have observed quality impact via:
- **Truncation edge cases:** max batch token caps can interact with max_new_tokens and long prompts, causing earlier stop conditions.
- **Streaming chunking:** changes in chunk size and flush cadence can alter client-side parsing and perceived completeness.
- **Overload mode:** load shedding or aggressive batching can raise timeout rates or change stop reasons.
- **Quantization numerical drift:** may increase repetition, reduce instruction-following on certain model families, or worsen structured output adherence.

## Guardrail framework (what we gate on)
We gate on three layers of signals:
1) **Hard failures (must not regress):** parse errors, invalid schemas, timeouts, empty outputs, tool call failures.
2) **Task quality (must be non-inferior):** preference win-rate, task-specific metrics (exact match / unit test pass / retrieval relevance where applicable).
3) **Behavioral health (bounded drift):** verbosity distribution, stop reasons, repetition, refusal rate.

### Severity levels
- **SEV-0 (blocker):** any hard-failure regression over threshold; any safety regression over threshold; any major customer-facing behavior break (e.g., JSON mode invalid rate spike).
- **SEV-1 (high):** statistically significant quality regression beyond non-inferiority margin; must fix or obtain explicit exception.
- **SEV-2 (moderate):** small degradation that is within margin but trending; requires monitoring plan and owner sign-off.

## Required evaluation suite
All candidate changes must run the following suite **per impacted model family** and **per affected tier** (fast/standard/cost-efficient).

### A) Structured output / tool-calling conformance
**Purpose:** Detect formatting and schema issues that disproportionately impact production customers.

Datasets:
- `structured-json-v2` (mixed JSON schemas)
- `function-calling-router-v3` (tool selection + args)

Metrics (hard-failure oriented):
- JSON parse success rate
- Schema validation success rate (strict)
- Tool call selection accuracy (where labeled)
- Tool argument validation success rate

**Thresholds (must pass):**
- JSON parse success rate: **no more than +0.20 percentage points (pp)** absolute regression vs baseline.
- Schema validation success rate: **no more than +0.30 pp** regression vs baseline.
- Tool argument validation failures: **no more than +0.20 pp** regression vs baseline.

Notes:
- For streaming endpoints, evaluate both streaming and non-streaming decoding paths (streaming adds client parsing risk).

### B) “Golden” determinism and correctness checks
**Purpose:** Catch regressions that are not well measured by subjective preference.

Datasets (examples; select based on model family coverage):
- `code-compile-smoke` (language-specific compile/run tests)
- `sql-generation-checked` (query equivalence or unit tests)
- `extractive-qa-short` (exact match / F1)

**Thresholds:**
- For pass/fail style tests (compile/unit tests): **no more than +0.30 pp** regression in failure rate.
- For exact match / F1: **no more than 1.0% relative** regression (unless the metric is near ceiling; then use absolute pp bound of **0.3 pp**).

### C) Preference-based quality (non-inferiority)
**Purpose:** Capture broader instruction following and helpfulness changes.

Method:
- Pairwise comparisons of baseline vs candidate (same prompts), judged by Redwood’s standard judge configuration (`judge-rig/v5`).
- Stratified sampling by workload: chat, summarization, code assistance, extraction.
- Stratified by prompt length bucket (short/medium/long) because batching heuristics often interact with length.

Metric:
- Win-rate of candidate vs baseline (ties allowed).

**Thresholds (non-inferiority):**
- Candidate win-rate lower bound (95% CI) must be **>= 0.49** overall.
- For any single category slice (chat/sum/code/extract), lower bound must be **>= 0.48**.

Minimum sample sizes:
- Overall: **N >= 2,000** prompt pairs per (model family × tier × quantization profile)
- Per slice: **N >= 300**

### D) Behavioral health checks (bounded drift)
**Purpose:** Ensure changes don’t create operationally expensive or product-breaking behavior.

Monitored signals (offline eval + online canary telemetry):
- Empty completion rate
- Average completion tokens and p95 completion tokens
- Stop reason distribution (e.g., `stop`, `length`, `timeout`, `error`)
- Repetition score (n-gram repetition proxy)
- Refusal rate (policy refusals)

**Thresholds (blockers where noted):**
- Empty completion rate: **SEV-0** if +0.10 pp regression.
- Stop reason `length` share: **SEV-0** if +0.30 pp regression (often indicates truncation/config interplay).
- Refusal rate: **SEV-0** if +0.20 pp regression unless explicitly explained by a policy update.
- Completion token p95: **SEV-1** if > +10% increase (cost risk) unless tier intentionally changes verbosity and PM sign-off exists.

## Tier-specific considerations
These do not change the thresholds above; they define what must be included in the eval matrix.

### Fast tier
Risk profile: tail latency protections can change admission behavior and stop reasons under concurrency.
Required additions:
- Include high-concurrency simulation prompts (burst patterns).
- Validate streaming conformance explicitly (streaming is common in fast tier).

### Standard tier
Risk profile: broadest default; must be most stable across workloads.
Required additions:
- Ensure dataset weighting matches expected production traffic mix from `slo-tier-promptset-selection`.

### Cost-efficient tier
Risk profile: aggressive batching/quantization interplay; highest risk of truncation/timeouts.
Required additions:
- Include long-prompt buckets and longer generation settings.
- Include at least one structured-output dataset (JSON) even if the model is “chat-focused”.

## Quantization profile approval rules
Quantization variants are approved per (model family × hardware class) and may be tier-restricted.

### Compatibility and restriction rules
- If a quantization profile is known to reduce structured-output adherence for a model family, it may be allowed only for **standard/cost-efficient** but not **fast**.
- If a quantization profile increases refusal rate or schema invalidity, it must be either:
  - fixed, or
  - explicitly excluded via model catalog constraints and documented in the quantization matrix.

### Required comparisons
Each new quantization profile must be compared against:
- The current production quantization for that model family (baseline), and
- FP16/BF16 reference on at least one representative hardware class (to detect drift that baseline-to-baseline comparison could hide).

## Rollout gates and rollback criteria (quality)
### Canary gates (hosted API / Dedicated)
During staged rollout, monitor per-tier and per-model family:
- `hard_failure_rate` (aggregate of parse/schema/tool-call failures)
- `empty_completion_rate`
- `stop_reason_length_rate`
- `refusal_rate`

**Abort / rollback conditions (SEV-0):**
- Hard failure rate: +0.20 pp regression sustained for **>= 15 minutes** in any region for any top-5 model.
- Empty completion rate: +0.10 pp sustained for **>= 15 minutes**.
- Stop reason `length`: +0.30 pp sustained for **>= 15 minutes**.
- Any confirmed safety regression attributed to the change.

**Investigation-but-continue (SEV-1) conditions:**
- Preference proxy regressions (where available online) or behavioral drift that exceeds bounds but without hard failures. Require runtime + Applied ML owner acknowledgment and an explicit “continue” comment in rollout channel.

### Exception process
Exceptions are allowed only when:
- There is a compelling product reason (e.g., large cost reduction) AND
- The regression is bounded and understood AND
- Additional monitoring/guardrails are added.

## Common failure modes and how to diagnose
1) **Spike in stop_reason=length**
   - Likely cause: max_new_tokens / max_total_tokens interaction with batch token caps; or overload fallback path.
   - Action: verify effective limits; check scheduler reason codes; validate prompt length buckets.

2) **JSON/schema failures increase (streaming routes)**
   - Likely cause: streaming chunk segmentation, client-side parser assumptions, or increased repetition from quantization.
   - Action: run structured output suite in streaming mode; inspect partial chunks; check client SDK versions in impacted tenants.

3) **Refusal rate increases**
   - Likely cause: quantization drift on safety boundary; unrelated policy changes; increased truncation causing misinterpretation.
   - Action: compare refusal text clusters; verify safety policy version held constant; run targeted preference eval on refusal-heavy prompts.

4) **Tool argument validation failures increase**
   - Likely cause: numerical drift affecting delimiter accuracy; or longer latency causing downstream timeouts and partial outputs.
   - Action: inspect tool-call formatting; check stop reasons; verify tool schema strictness.
