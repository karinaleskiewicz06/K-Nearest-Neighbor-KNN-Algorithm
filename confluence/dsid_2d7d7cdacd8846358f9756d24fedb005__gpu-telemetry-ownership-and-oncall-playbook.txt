GPU telemetry ownership and oncall playbook

Overview
========

Purpose
-------
This playbook defines ownership, instrumentation standards, alerting thresholds, and oncall procedures for GPU fleet telemetry at Redwood Inference. It covers the telemetry pipeline components, required metrics, sampling and retention guidance, Terraform/Helm configuration snippets, and a clear incident-response checklist for SREs and infra engineers.

Scope
------
- GPU fleet health and capacity signals (node, GPU, driver, temperature, power)
- Serving runtime-specific telemetry (inference latency, batch sizes, KV cache hit/miss rates)
- Ingest pipeline (prometheus exporters, metric forwarders, ingest queues)
- Dashboard, alert, and runbook ownership for incidents impacting metric fidelity or visibility

Audience
--------
- Infra SREs and Platform engineers running GPU pools
- Observability engineers who manage the ingest pipeline and dashboards
- Oncall responders and incident commanders

Key components and owners
========================

Table: Component ownership
- Component: gpu-metrics-collector (daemonset on GPU nodes) — Owner: infra/gpu-fleet
- Component: redwood-telemetry-ingest (k8s deployment) — Owner: eng-observability
- Component: kv-cache-exporter (sidecar for runtime) — Owner: eng-serving-runtime
- Component: prometheus-longterm (remote write + Cortex) — Owner: eng-observability
- Component: grafana-dashboards/gpu-fleet (dashboards library) — Owner: infra/gpu-fleet

Standard signals and required labels
- node/gpu_utilization_pct (per device) — labels: cluster, pool, tenant_id, model_family
- node/gpu_temperature_celsius — labels: device_index, zone
- gpu/driver_errors_total — labels: driver_version, node_id
- runtime/inference_p95_latency_ms — labels: route, model_version, batch_size
- runtime/kv_cache_hit_rate — labels: model_version, prefix_hash
- telemetry/ingest_backlog_seconds — labels: shard, region

Quality and retention expectations
- Metric correctness: 99.9% of expected telemetry series should be present in Cortex rollup (defined per tenant)
- Ingest latency SLO: 95% of metrics available in Grafana within 10s of emission; 99.9% within 120s
- Retention: hot Prometheus data retained for 14 days; long-term compressed for 365 days

Alerting and thresholds (Prometheus alert rules examples)
-----------------------------------------------------
Operational alerts (page-one, paging)
1) GPU telemetry ingest backlog high (page): telemetry/ingest_backlog_seconds > 300 for 5m 
   - Severity: P1
   - Pager: infra-oncall
   - Runbook: follow "ingest-backlog" procedure below
2) Missing fleet heartbeat (page): absent(node/gpu_utilization_pct{pool!~"test.*"}) for 15m
   - Severity: P1
   - Pager: infra-oncall
3) KV cache exporter crashlooping (page): increases in kube_container_restart_count for kv-cache-exporter > 3 restarts in 10m
   - Severity: P2
   - Pager: runtime-oncall

Informational alerts (ticket)
- GPU temperature > 85C for single device but <5% of pool for 10m — creates ticket for hw-ops
- Gradual rise in inference_p95_latency exceeding baseline by 30% for 1h — creates ticket for runtime team

Sample Prometheus alert rule (YAML)
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: gpu-telemetry-rules
spec:
  groups:
  - name: gpu-ingest.rules
    rules:
    - alert: GPUIngestBacklogHigh
      expr: telemetry_ingest_backlog_seconds > 300
      for: 5m
      labels:
        severity: page
      annotations:
        summary: "Telemetry ingest backlog > 5m"

Telemetry pipeline terraform/helm examples
-----------------------------------------
Note: we maintain a central observability Terraform module (registry: internal/observability/telemetry-ingest) that exposes parameters used by teams. Below is an illustrative snippet used by infra/gpu-fleet to provision the gpu-metrics-collector and remote-write config.

Terraform module usage (HCL snippet):
module "gpu_metrics_collector" {
  source = "internal/observability/gpu-metrics-collector"
  namespace = "gpu-metrics"
  prometheus_remote_write = {
    url = module.cortex.remote_write_url
    headers = { "X-Cluster" = var.cluster_name }
  }
  scraping_interval = "10s"
  relabel_rules = ["tenant_id:__meta_kubernetes_pod_label_tenant_id"]
  owners = ["team:infra/gpu-fleet"]
}

Helm values excerpt for gpu-metrics-collector daemonset:
metrics:
  enabled: true
  scrapeInterval: 10s
  resources:
    requests:
      cpu: 200m
      memory: 150Mi

Best-practice instrumentation pattern
- Emit metrics at the source with tenant_id and model_version labels where feasible. Avoid high-cardinality labels on high-frequency metrics (e.g., batch_id).
- Use histograms for latency metrics with standard buckets: [10, 25, 50, 100, 250, 500, 1000, 2500] (ms).
- Expose a /metrics-health endpoint for heartbeat checks that returns 200 when the exporter is healthy.

Sampling and cardinality guidance
- High-volume series (e.g., per-prefix kv hits) should be aggregated at the exporter, producing summary metrics (kv_cache_hit_rate) rather than a per-prefix time series unless explicitly needed for an eval.
- If you need high-cardinality traces, use a sampling policy: 1% baseline + 100% on error. Configure in otel-collector config for the runtime.

Dashboards and queries (Grafana)
- Core dashboard: GPU fleet overview (panels: fleet utilization, active nodes, avg inference latency, KV cache hit rate, driver errors) — maintained in grafana/dashboards/gpu-fleet.json (repo: infra/grafana-dashboards)
- Example query for p95 inference latency:
  histogram_quantile(0.95, sum(rate(runtime_inference_latency_bucket[5m])) by (le, route, model_version))

Oncall runbook: step-by-step incident triage\==================================================
1) Triage (5 min):
   a) Confirm alert source and severity in PagerDuty.
   b) Check GPU fleet overview dashboard and telemetry ingestion health dashboard.
   c) Identify whether the issue is (i) ingest pipeline, (ii) exporter on nodes, (iii) runtime regression, or (iv) infrastructure networking.
2) Initial containment (10 min):
   a) If ingest backlog high: check redwood-telemetry-ingest pod logs, pods status, and remote write endpoints.
      - kubectl -n observability logs deploy/redwood-telemetry-ingest
      - kubectl -n observability get pods -l app=redwood-telemetry-ingest -o wide
   b) If node exporters missing: query k8s for daemonset status and node taints; run: kubectl -n gpu-metrics get daemonset gpu-metrics-collector -o jsonpath='{.status}'
3) Remediation (varies):
   - If redwood-telemetry-ingest CPU is saturated: scale the deployment (temporary scale command): kubectl -n observability scale deploy/redwood-telemetry-ingest --replicas=4 && open a ticket to increase HPA target.
   - If Cortex remote_write is rejecting: check remote_write error counter and auth headers; coordinate with eng-observability to rotate credentials if necessary.
   - If exporters are crashlooping: collect logs, capture core dump (if configured), and roll a hotfix image to a canary subset.
4) Post-incident (within 24–48h):
   a) Create a postmortem if P1 or if visibility was impaired for >1h.
   b) Update runbook steps and dashboard panels if gaps were discovered.

Runbook playbooks: common failure modes and actions
- Ingest backlog due to Kafka/Cortex pressure:
  - Action: Increase redwood-telemetry-ingest replicas; check disk pressure on ingest nodes; throttle non-critical exporters via relabel rules.
- Large cardinality flood (bad exporter label):
  - Action: Identify offending series via /api/v1/series?match[]=...; add relabel rule at gpu-metrics-collector to drop the offending label; roll exporter update.
- Gradual metric drift in inference latency:
  - Action: Check runtime release rollouts (canary), inspect kernel logs on nodes, and validate model version traffic split. Rollback if correlated with a release.

Runbook checklist for oncall responders (quick reference)
- Pager acknowledged in PD within 2 min
- Ownership declared (infra-oncall / runtime-oncall)
- Initial hypothesis captured in incident channel
- Evidence collected: links to dashboard panels, relevant pod logs, and metric queries
- Followup ticket created if not resolved within 30m

Testing and validation playbook
- Synthetic probe: a Grafana synthetic job emits a small workload every 60s to validate pipeline. Check sample queries return values within 10s.
- Canary rollout process for exporter changes: 1) prepare image and config; 2) deploy to single AZ canary (1–2 nodes); 3) run smoke probe for 30m; 4) promote via Helm to remaining nodes using [helm upgrade --namespace gpu-metrics ...].

Telemetry as code: templates and examples
- Dashboard provisioning: dashboards in infra/grafana-dashboards are managed as JSONnet templates. PR template requires: description, related alert rules, reviewer from eng-observability.
- PrometheusRule and ServiceMonitor manifests must include an annotation: "telemetry.owner" with team contact and Slack channel.

Ownership and escalation matrix
- Primary owners: infra/gpu-fleet (pager for hardware and exporters), eng-serving-runtime (pager for runtime metrics), eng-observability (pager for ingest and Cortex).
- Escalation: If primary does not respond within 10 min, notify secondary (team leads) and page infra-lead.

Appendix: example queries and troubleshooting commands
- List series emitted in last 15m for a tenant: curl -G "https://prometheus.internal/api/v1/series" --data-urlencode 'match[]=node/gpu_utilization_pct{tenant_id="t-123"}' --data-urlencode 'start='$(date -d '15 minutes ago' +%s)
- Check exporter container logs: kubectl -n gpu-metrics logs -l app=gpu-metrics-collector -c exporter --tail=500
- Re-deploy exporter daemonset (safe rolling): kubectl -n gpu-metrics rollout restart daemonset/gpu-metrics-collector

Document maintenance
- Owner team (infra/gpu-fleet) should review annually and after any P1 that affected visibility.
- Use label updates and PRs to infra/docs for changes to thresholds or required signals.
