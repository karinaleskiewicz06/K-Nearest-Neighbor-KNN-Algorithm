Emergency Change Policy (Production) — v3

h2. Purpose
This policy defines minimum requirements for *Emergency Changes* to Redwood production systems. Emergency changes are allowed to restore service or mitigate critical customer impact, but they must remain safe, auditable, and reversible.

h2. Scope
Applies to Hosted API, Dedicated capacity, control plane, serving runtime, routing, and any customer-impacting production service or configuration change.

h2. Definitions
*Emergency Change* = a change needed immediately to address: (a) Sev-1 incident, (b) active security exploit, (c) data loss/corruption risk, or (d) widespread outage/severe degradation.
*Hotfix* = emergency patch to a released component intended for expedited rollout.

h2. Required approvals (cannot be skipped)
All emergency changes must have *two-person approval* before production impact:
# *Incident Commander (IC)* for the active incident OR *On-call SRE* if not in incident mode
# *Service Owner* (or delegate) for the component being changed

Additional approvals based on scenario:
* Security-related or suspected exploit: *Security on-call*
* Customer-visible behavior change (responses/routing/model selection): *Product on-call* or responsible PM
* Any change requiring customer maintenance coordination (Dedicated/Private): *Customer Success escalation manager*

h2. Minimum checklist
Record in ticket/PR/incident timeline:
* Hypothesis for the fix
* Blast radius (Hosted regions; Dedicated clusters/customers; model families)
* Rollback plan with explicit trigger (metric or customer symptom)
* Risk assessment: data integrity, security, performance
* What is changing (code vs config vs infra)
* Owner for post-change monitoring

h2. Documentation and audit requirements
* Create/link a ticket (Linear preferred; Jira acceptable).
* Open a GitHub PR (even if fast-tracked) OR link to an existing PR and commit SHA.
* Record approvals in PR review, incident thread, or change record comment.
* Update incident timeline with: start time, change time, outcome.

h2. Rollout constraints
* Use a canary wherever possible (one Hosted region or a single Dedicated cluster) before broad rollout.
* If canary is not possible, document why and get IC sign-off.
* Do not deploy unrelated changes under one emergency change record.

h2. Post-change requirements
Within 2 business days:
* Create follow-up in incident review (root cause, change made, why it worked).
* Document any deviations from normal release procedures and corrective actions.
* Remove any temporary flags/throttles (owner + deadline).
