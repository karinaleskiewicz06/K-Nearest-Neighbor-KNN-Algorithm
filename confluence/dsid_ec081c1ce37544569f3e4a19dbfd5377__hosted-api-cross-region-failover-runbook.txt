Hosted API: Cross-Region Failover Runbook (Emergency)

h1. Purpose
This runbook describes the emergency procedure for failing over the Redwood Hosted API (gateway + inference routing) from a primary region to a secondary region during a severe partial or full regional outage.

*Scope:* Hosted API production traffic (api.redwoodinference.com) and associated control-plane dependencies needed for serving.
*Out of scope:* Customer-specific Dedicated clusters and Private deployments (see Dedicated/Private runbooks).

h1. When to use this
Use cross-region failover when ANY of the following are true for >10 minutes and mitigation is not working:
- P0: >20% 5xx on /v1/chat.completions or /v1/embeddings in a single region
- P0: p95 latency > 4x baseline for >15 minutes and capacity actions are exhausted
- Control-plane degradation prevents scheduling/serving new requests in primary

*Do not use failover* for localized model issues (use model fallback policy / route-level rollback).

h1. Preconditions
- Incident declared and an Incident Commander (IC) assigned (see IC checklist).
- Confirm secondary region is healthy for core dependencies:
  1) gateway
  2) routing service
  3) token accounting
  4) model registry read path
  5) auth/JWKS fetch
- Confirm the secondary region has at least 60% of expected peak capacity OR confirm we are comfortable with rate limiting.

h1. Roles and approvals
- IC: owns the decision to fail over and communicates status externally.
- Ops lead (SRE): executes steps (or delegates) and records every action/time.
- Comms lead: status page + customer updates.
- Eng oncall (Gateway + Runtime): supports validation and rollback.

Approval requirements:
- Emergency changes are allowed during a declared incident. Follow "Emergency Change Policy" for required sign-off recording.
- For global traffic cutover, obtain at least one additional approver from: SRE oncall OR Infra oncall OR Platform oncall.

h1. Procedure overview
The failover is executed in three phases:
1) Stabilize and prepare
2) Cut over global traffic
3) Validate and monitor; decide whether to rollback or stay failed over

*Important:* The exact traffic routing mechanism (GSLB/DNS, weights, TTL) and the current commands are maintained in: "Global traffic routing controls" (Eng Infra). This runbook intentionally references that page to avoid stale cutover instructions.

h1. Phase 1: Stabilize and prepare
1. Declare incident severity (P0/P1) and open an incident channel.
2. Freeze non-essential deploys:
   - Disable scheduled rollouts
   - Pause canaries if currently running
3. Reduce load before failover (optional but recommended):
   - Temporarily tighten global rate limits to protect the secondary region
   - Turn on aggressive cache settings for high-hit prompts (if safe)
4. Pick the target region:
   - Prefer the pre-designated secondary for the affected primary (see routing controls doc)
5. Pre-flight health in target region:
   - Gateway /healthz
   - Routing /readyz
   - Sample inference request for top 3 models
   - Billing token accounting write test (if feasible; otherwise monitor lag)
6. Confirm observability dashboards are available for BOTH regions.

h1. Phase 2: Cut over global traffic
1. Ensure you understand the *rollback plan* before cutting over.
2. Announce in incident channel: "starting global traffic failover" and who is executing.
3. Execute the cutover using the steps in "Global traffic routing controls".
   - Use *weighted cutover* unless the primary is hard down.
   - Typical pattern: 10% -> 50% -> 100% over 10-20 minutes.
4. During each step, validate:
   - Error rate
   - p95 latency
   - GPU saturation and queue depth
   - Rate limiting events

h1. Phase 3: Validation checklist (must-pass)
Within 15 minutes of reaching 100% traffic to secondary:
- /v1/chat.completions success rate >= 99% (excluding customer auth errors)
- p95 end-to-end latency within 2x baseline for the current traffic mix
- Streaming responses stable (no spike in client disconnects)
- Token accounting not accumulating >5 minutes of backlog
- No evidence of auth/JWKS failures due to region-local networking

If any must-pass check fails, consider immediate rollback to weighted mode or partial rollback.

h1. Rollback criteria and rollback steps (summary)
Rollback if:
- Secondary region saturates (sustained queue growth for >10 minutes)
- Auth failures spike after cutover
- Token accounting write path fails
- Latency remains >4x baseline after rate limiting

Rollback steps:
- Use the rollback procedure in the routing controls doc (reverse weights or restore previous record set).
- After rollback, re-enable only the minimum required features; keep deployments frozen until stability.

h1. Post-failover (within 24 hours)
- Create an incident review and include: decision timeline, exact weights/records, and validation results.
- Open follow-ups for missing runbook steps found during incident.

h1. Notes / common pitfalls
- TTLs: changes can appear "done" but clients may still be pinned for minutes; do not declare success until metrics reflect the distribution shift.
- If the primary is flapping, keep it at 0% until a clear recovery signal exists.
- Do not forget to update rate-limit policy back to normal once stable.
