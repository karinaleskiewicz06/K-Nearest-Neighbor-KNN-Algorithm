mixed-precision-kernel-rollout-playbook

Summary
This playbook describes the end-to-end process for rolling out mixed-precision (FP16/INT8) inference kernels and quantization-enabled runtime changes across Redwood's hosted, dedicated and private GPU fleets. It covers CI/CD pipeline artifacts, Terraform/IaC touches, networking and cross-account rollout choreography, canary strategies, observability guardrails, and an operational runbook for rapid rollback or mitigation.

Scope
- Changes covered: kernel binaries, cuDNN/kernel-shim variants, quantization glue (runtime flags), and model-compatibility patches.
- Environments: staging-cpu, staging-gpu, canary-gpu (fractional tenants), production-hosted, production-dedicated, production-private (VPC).
- Exclusions: hardware firmware/driver upgrades (separate process).

Goals
- Deploy kernels with 95th-percentile latency regression < 5% for P50-target routes and error rate delta < 0.5% for generation failures.
- Ensure deterministic rollback within 15 minutes of a critical alert.
- Prevent noisy neighbor regressions by preserving per-tenant latency SLOs.

Prerequisites
1) Kernel binary artifacts published to our artifact registry: artifact path format artifacts.redwood/nn-kernels/{version}/{platform}/{sha}.so
2) Runtime image promotion pipeline green: image tag format rh-runtime:{version}-k{kernel_version}
3) Terraform module changes reviewed in modules/gpu-runtime-variants and a promoted plan in the module registry.
4) Smoke and perf suites present in CI: perf/kernels/smoke.yml and perf/kernels/regression.yml.

Ownership
- Release lead: eng-infra release engineer (Primary)
- Kernel maintainers: serving-runtime team (Secondary)
- Tenant communications: customer-success (Notify for Dedicated/Private customers)
- IaC changes: infra-terraform owners

Test Matrix (minimum)
- Functional: run model sanity (token-by-token equality for FP32 baseline) on a 50-case prompt-set.
- Perf: 1k sample streaming gen with representative prompt distribution; measure P50/P95 latency and throughput.
- Memory: max KV cache size verification with sequence length 4096.
- Quantization (INT8): quality regression A/B eval (BLEU/ROUGE or custom embed-sim) on 200 prompts.

CI/CD Pipeline (high level)
1) PR to runtime repo triggers: unit tests -> smoke perf (one small node) -> integration on staging-gpu.
2) If green, artifacts built and uploaded: kernels/{version}/{platform}.so and image rh-runtime:{ver}-k{kv}.
3) Promotion job: ci/promote-kernel -> creates PR to IaC repo with version bump in modules/gpu-runtime-variants.
4) IaC plan job: runs terraform plan with cloud-account matrix (hosted, dedicated, private) and posts plan output.
5) Manual approval gate for canary rollout with checklist items (see Canary Gate).

Canary Strategy
- Canary scope: route selection by tenant tag (canary=true) and 5% of host-routed requests for hosted. For dedicated/private, use single low-impact tenant or customer-provided staging VPC.
- Stages:
  1) Single pinned node (1 GPU) running new kernel under low load for 30m (sanity + smoke).
  2) 3-node warm pool at 10% of normal scale for 2 hours (stress + perf).
  3) 20% traffic split against a matched baseline model variant for 4 hours (A/B).
  4) Gradual ramp to 50% then 100% over 24 hours if metrics stable.
- Canary telemetry: P50/P95 latency, error_rate, OOM counts, kernel-crash-rate, GPU_utilization, queue-depth.

Canary Gate (manual approval)
- Required checks before moving to next stage:
  - No kernel crashes in last 30 minutes.
  - P95 latency change <= 7% relative to baseline.
  - Error rate delta <= 0.5% absolute.
  - GPU memory pressure <= 85% steady-state.
  - No regression alerts firing for quality-monitoring (embedding-sim drift).
- Approvers: release lead + serving-runtime tech lead + infra oncall. Document approval with PR comment and CI job signature.

Rollback Criteria and Immediate Mitigations
- Automatic immediate rollback triggers (CI/CD hooks or autoscaling):
  - kernel-crash-rate > 0.1% sustained for 5m.
  - P95 latency regression > 15% or P50 > 25% for 5m.
  - Error rate increase > 2% absolute.
  - OOMs observed on > 1% of requests in 10m window.
- Manual mitigations:
  1) Shift traffic to baseline variant via router flag (runtime route override).
  2) Evict canary nodes and mark image as quarantined in the artifact registry.
  3) Revert IaC change and run terraform apply to restore pinned node pools.

Operational Runbook (incident play)
1) Detection: Pager triggered for P95 latency or kernel_crash alerts.
2) Triage (5 minutes): assess scope (tenants impacted, fleet region, node image). Use query:
   - metrics: query(kernel_crash_count[10m]) by node_image
   - logs: grep for SIGSEGV or cuBLAS error signatures in /var/log/runtime/kernel.log
3) Containment (10 minutes): set routing override to baseline: curl -X POST https://admin.redwood/api/routes/override -d '{"route":"/v1/generate","variant":"baseline"}'
4) Remediation (15-45 minutes): rollback IaC if needed, drain affected nodes, redeploy baseline image.
5) RCA and corrective action (24-72 hours): create postmortem, add test case to perf/regression suite, or pin kernel variant compatibility in model onboarding.

Terraform / IaC Guidance
- Module: modules/gpu-runtime-variants should receive only: kernel_version (string), kernel_artifact_sha (string), runtime_image_tag (string), allowed_quant_modes (list-of-strings)
- Plan checks: use terraform plan with -out and record plan diff; require that any change which touches auto-scaling policies or network ACLs is escalated.
- Example (pseudo-terraform snippet inserted in PR body):
  resource "redwood_gpu_runtime_variant" "canary" {
    kernel_version = "k2026-02-mpk-1"
    kernel_artifact = "artifacts.redwood/nn-kernels/k2026-02-mpk-1/x86_64/sha256:abcd1234"
    runtime_image = "rh-runtime:2026.02-k2026-02-mpk-1"
    quant_modes = ["fp16"]
  }
- Promotion rule: do not modify production default variant in the same PR as a kernel bump. Use explicit canary-only variant until validated.

Networking and Cloud Accounts Considerations
- For private/VPC deployments ensure kernel artifacts are mirrored into the private registry or accessible via signed URL. Add a manifest entry in customer-managed artifact list.
- Cross-account role: IaC plan must verify that the ci-promote role has read-only access to target accounts for plan only; apply must be performed by the account owner account.
- Egress: artifact pulls during rollout may spike egress; schedule large mirror jobs in maintenance windows for Private customers.

Observability and Alerting (minimum rules)
- Alert: kernel_crash_rate > 0.05% for 3m -> PAGER oncall-runtime
- Alert: p95_latency_delta > 10% for 5m -> PAGER infra-oncall + release lead
- Alert: gpu_memory_pressure > 90% -> PAGER infra-oncall
- Dashboards: per-kernel-version heatmap for p95 and error_rate, per-tenant perf scatter.

Quality Monitoring
- Add a permanent A/B eval flag for canary traffic: sample 0.5% of requests to run both baseline and new kernel when feasible to measure output drift. Store results in quality-monitoring index for post-deploy analysis.

Post-release Verification Checklist (24/72hr)
- 24hr: no critical alerts, rolling 24h A/B drift within target thresholds.
- 72hr: perf stable and customer telemetry clear.
- If issues: open change to pin kernel version per model and include compatibility matrix entry.

Appendix: Useful Commands
- Promote artifact: ci-tools promote-artifact --artifact artifacts.redwood/... --to registry.private.redwood/customers/
- Apply IaC (account owner): terraform init && terraform apply -auto-approve plan.tfplan
- Router override example: curl -u $ADMIN_USER -X POST "https://admin.redwood/api/routes/override" -H "Content-Type: application/json" -d '{"route":"/v1/generate","variant":"baseline"}'
