Quickstart Templates: Docs Information Architecture (IA) Update Proposal

## Summary
This page proposes an information architecture update to integrate **Quickstart Templates** (RAG + agents) into the Redwood docs in a way that:
- Reduces time-to-first-success for PLG engineers.
- Makes templates discoverable from SDK and API reference pages.
- Clearly explains the difference between **Hosted**, **Dedicated**, and **Private** deployments without duplicating large parts of product documentation.
- Establishes a durable pattern for versioning (latest vs pinned) and template maintenance.

This proposal covers:
1) Where templates live in the docs nav
2) The page structure and cross-linking strategy
3) How deployment-mode guidance is presented (Hosted/Dedicated/Private)
4) Migration plan and ownership

---

## Goals
- **Discoverability:** Templates should be reachable within 1–2 clicks from the docs homepage and directly from SDK docs.
- **Clarity:** Users should immediately understand: “Is this a tutorial? an example? a production-ready scaffold?”
- **Low duplication:** Keep Hosted/Dedicated/Private details canonical in product docs; templates should link out and only include delta guidance.
- **Operational readiness:** Observability, safe defaults, and troubleshooting should be first-class in IA (not buried).
- **Version integrity:** Docs should make it obvious which template version a walkthrough corresponds to, and how to get updates.

## Non-goals
- Rewriting the entire docs homepage IA.
- Creating separate docs sets per language; language selection should be consistent and lightweight.
- Documenting every deployment provider recipe (Fly/Render/K8s/etc.) as first-class docs pages in v1; we will link to repo recipes.

---

## Target audiences and entry points
### Persona A: PLG engineer (self-serve)
- Entry points: docs home, “Get started”, SDK docs, GitHub search
- Needs: quick working app, clear env vars, sane defaults, troubleshooting, cost controls

### Persona B: platform/infra team
- Entry points: Dedicated/Private docs, security/compliance docs, observability docs
- Needs: deployment-mode specifics, OTel conventions, network/security notes, reproducibility, pinned versions

### Persona C: solutions engineer / internal enablement
- Entry points: internal playbooks, troubleshooting, known issues
- Needs: consistent error taxonomy, supportable instrumentation, “what to ask for” checklists

## Page-level structure and required elements
### 1) Quickstart Templates → Overview
Purpose: explain what templates are and what “production-minded by default” means.

Required content blocks:
- What you get: opinionated defaults (timeouts/retries, streaming robustness, cost controls, guardrails)
- What you still need to decide: model choice, vector store, deployment target
- Compatibility promise: “Works with Redwood Hosted; guidance for Dedicated/Private included”
- Security note: secrets handling and redaction are built-in; user must still avoid logging PII

### 2) Install & Create a project
Purpose: a single canonical place for setup steps.

Required:
- CLI install steps (if shipped) and GitHub template alternative
- Prereqs: runtime versions, Docker (optional), OTel collector (optional but recommended)
- Minimal “doctor” workflow: validate API key, base URL, model, collector

### 3) Template walkthrough pages (RAG + Agents Python / TypeScript)
Purpose: the happy path walkthrough with clear “checkpoints” users can verify.

Standard sections (consistent across languages):
1. What you’ll build
2. Architecture at a glance (diagram + short explanation)
3. Prerequisites
4. Configure environment variables
5. Run locally
6. Verify correctness (sample query + expected behavior)
7. Verify observability (what metrics/spans/logs to look for)
8. Cost controls (limits, batching/caching knobs where applicable)
9. Guardrails (tool schema validation, max iterations)
10. Next steps (deployment recipes, eval harness, custom tools)

### 4) Observability page
Purpose: show users how to confirm they have “supportable” telemetry.

Must include:
- Required spans and key attributes (high-level, not exhaustive)
- Required metrics list and cardinality guidance
- How to view data in Redwood Console (where available) and/or local dashboards
- Redaction behavior and what never to emit

### 5) Deployment modes page (within Templates section)
Purpose: answer the question: “I’m using a template—what changes if I’m on Hosted vs Dedicated vs Private?”

Design principle: **delta-only guidance** (avoid duplicating product deployment docs).

Template Deployment Modes page sections:
- Hosted: defaults work out of the box; rate limits; base URL; minimal networking notes
- Dedicated: capacity predictability, recommended concurrency settings, SLA/throughput notes; link to Dedicated docs
- Private (VPC/on-prem): networking/DNS, egress restrictions, collector endpoints, KMS/HSM references; link to Private docs

### 6) Troubleshooting & Common errors
Purpose: deflect support tickets and reduce time-to-resolution.

Structure:
- Symptom → likely cause → fix → what to include in a support request
- Explicit mapping to error taxonomy categories (auth/quota/network/tool/retrieval/otel)
- Guidance for streaming disconnects and proxy-related header issues

### 7) Template versioning & upgrades
Purpose: set expectations that templates evolve and users can pin.

Must cover:
- “Latest” vs “pinned release” docs links
- How templates embed a version stamp
- How to upgrade safely (manual steps; no promise of in-place automated migration in v1)
- Deprecation policy and security updates

## Cross-linking strategy (SDK reference and API docs)
### SDK docs → Templates
Add a “Start from a template” callout on:
- Python SDK quickstart page
- TypeScript SDK quickstart page

Callout text guidelines:
- One sentence value statement
- Link to the relevant language walkthrough
- Link to “Install & Create a project”

### Templates → SDK docs
In each template walkthrough:
- Link to the relevant SDK reference for advanced usage.
- Link to instrumentation guidance (OTel integration patterns).

### API Reference → Templates
In the endpoints most commonly used by templates (chat/generate, embeddings, tool calling/structured output):
- Add a short “See a production-ready template” link.

Guardrail:
- Keep reference docs pure; do not embed multi-step tutorials.

## Presenting Hosted vs Dedicated vs Private guidance (recommended pattern)
### Pattern: “Common core + deployment deltas”
- The walkthrough pages should assume **Hosted** by default (lowest friction).
- A prominent callout near setup should say:
  - “Using Dedicated or Private? See: Deployment modes for templates.”
- Provide a compact table of what changes across deployment modes.

### Proposed “What changes by deployment mode?” table (example)
Include a small table on each walkthrough page:
- Base URL / networking
- Auth / key management
- Rate limits / concurrency guidance
- Observability exporter endpoint
- Compliance / audit logging notes

Avoid:
- Duplicating full Private deployment instructions inside template docs.

## Versioning approach in docs
### Requirements
- Walkthrough content must reference a template release line.
- Users must be able to follow “latest” without surprises, and also pin to a known-good template release.

### Proposal
- Docs default to **latest stable template version**.
- Add a version selector (if supported by docs site tooling) OR a simple callout:
  - “This guide tracks template version: vX.Y (latest). For vX.(Y-1) docs, see …”
- For each release, maintain:
  - Changelog link
  - Breaking change notes
  - Minimal migration notes

## Risks and mitigations
1) **Docs drift from templates**
   - Mitigation: release checklist + CI link checks + version stamp.

2) **Over-documenting deployment modes inside templates docs**
   - Mitigation: enforce delta-only; link to canonical deployment docs.

3) **Confusion between “examples” and “templates”**
   - Mitigation: consistent naming and a short “contract” section in Overview.

4) **High-cardinality observability tags**
   - Mitigation: observability page explicitly documents allowed dimensions and redaction rules.
