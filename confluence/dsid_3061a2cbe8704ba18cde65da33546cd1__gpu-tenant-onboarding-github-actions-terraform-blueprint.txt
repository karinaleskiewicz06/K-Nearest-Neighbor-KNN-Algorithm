gpu-tenant-onboarding-github-actions-terraform-blueprint

Summary
-------
This document defines a reproducible blueprint for onboarding a new tenant (team or customer) onto Redwood's GPU infrastructure using a self-service GitHub Actions + Terraform workflow. It covers the high-level architecture, module interfaces, CI gating, cost and tagging requirements, networking constraints, security/IAM patterns, and operational runbook steps required for day-1 through day-14 stabilization.

Goals
- Provide a safe, audited path for creating tenant GPU environments that enforces guardrails (egress, tagging, quotas).
- Automate repeatable provisioning via Terraform modules invoked from GitHub Actions.
- Integrate CI checks and policy gates to prevent misconfiguration and cost spikes.
- Make ownership and rollback explicit (who signs off, how to destroy).

Non-goals
- This blueprint does not replace full enterprise on-prem deployments for regulated customers.
- It does not prescribe exact GPU SKU selection—those are provided as variables.

Scope
- Applies to: ephemeral/sandbox and reserved tenant environments in public cloud accounts managed by Redwood.
- Not covered: on-prem packaging, Private VPC air-gapped installs, or dedicated hardware transplant procedures.

Architecture overview
---------------------
Textual diagram:
- Developer/SE -> GitHub repo (tenant-onboard) -> Pull Request -> GitHub Actions workflow -> Terraform module invocation -> Cloud Account (Tenant sub-account) resources:
  - VPC (tenant-subnet) + Egress NAT/proxy
  - GPU node pool(s) (warm-pool + preemptible/spot fallback)
  - IAM roles/service accounts scoped to tenant
  - Monitoring/metrics exporter (Prometheus/OTel sidecar)
  - Cost tagging and billing export config

Core design principles
- Least privilege: Terraform state, service accounts, and CI runners have scoped permissions.
- Idempotence: Modules are safe to rerun; resources are owned by short immutable IDs.
- Observability: Each onboarding run registers a tracing id and creates a short-lived dashboard link.
- Cost-safety: Default quotas and spend alerts are applied at creation time.

Terraform module design (interfaces)
-----------------------------------
Recommended modules (packaged in our internal registry):
- redwood-gpu-landing-zone (v1.4+): creates VPC, subnets, route tables, NAT/proxy endpoints.
- redwood-gpu-node-pool (v2.0+): creates autoscaling-managed GPU node group with warm-pool.
- redwood-gpu-iam (v1.2+): tenant IAM roles, service accounts, policy bindings.
- redwood-gpu-monitoring (v1.0+): metrics exporter, alerting policies, dashboards.
- redwood-cost-tagging (v1.1+): tagging, billing export, cost center link.

Module input matrix (example)
| variable | description | example | required |
|---------|-------------|---------|----------|
| tenant_id | canonical tenant short name | team-aurora | yes |
| environment | sandbox|dev|staging|prod | sandbox | yes |
| gpu_profile | gpu flavor label (nvidia-a100-80gb.s) | a100-80 | yes |
| max_monthly_spend | soft cap for initial alerting (USD) | 2500 | no |
| allowed_egress_ranges | list of CIDRs allowed for outbound | [10.0.0.0/16] | no |

The modules return stable outputs used by platform services: vpc_id, node_pool_id, monitoring_endpoint, service_account_email. Always map those outputs into GitHub deployments and RBAC.

GitHub Actions workflow (recommended pattern)
--------------------------------------------
- repo: infra/tenant-onboard-template
- protected branches: main (requires 2 approvers for prod)
- secrets: GH_ACTIONS_TF_STATE_SA, TF_BACKEND_GCS_BUCKET, TF_LOCK_SA (scoped)

Example workflow (description, not exhaustive):
1. on: pull_request (paths: 'tenants/**')
2. jobs:
   - fmt-check: run terraform fmt and validate
   - plan: runs terraform plan using ephemeral workspace, uploads plan as PR comment, registers plan fingerprint in monitoring
   - policy-check: run conftest/OPA against plan; gates on deny results
   - approve-and-apply (manual for non-prod; required approvers for prod): apply step uses locked backend and limited SA

YAML snippet (apply step)
```yaml
jobs:
  apply:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v2
      - name: Terraform Init
        run: terraform init -backend-config="bucket=$TF_BACKEND_GCS_BUCKET"
      - name: Terraform Apply (locked)
        run: terraform apply -auto-approve
        env:
          GOOGLE_APPLICATION_CREDENTIALS: ${{ secrets.GH_ACTIONS_TF_STATE_SA }}
```

Policy gates and automated checks
- OPA policies (rego) must enforce:
  - Required tags: tenant_id, cost_center, owner_email
  - No public ingress allowed on GPU subnets
  - Maximum node_pool_size <= 200 (soft rule; can be overridden with approval)
  - Egress destinations limited to allowlist for sandbox by default
- Conftest runs on plan output; any DENY must be fixed or require explicit elevated approval.

Security and IAM recommendations
--------------------------------
- Terraform state stored in a locked backend (GCS/AzureBlob) with bucket-level IAM limited to TF_LOCK_SA and platform-admins.
- Apply service account (TF_APPLY_SA) must have narrow privileges: create/list/describe for resources only in the tenant sub-account. Avoid blanket owner/iam roles.
- Use Workload Identity (GKE) or OIDC in GitHub Actions to mint short-lived credentials instead of long-lived tokens where possible.

Network and Egress patterns
--------------------------
- Tenant VPCs should be created with private subnets; all egress goes through a centralized egress proxy maintained by cloud-accounts-and-networking.
- Default sandbox egress policy: block all internet except container registries and Redwood telemetry endpoints.
- For production tenants that require external endpoints, require a signed justification and security review.

Cost controls and telemetry
--------------------------
- redwood-cost-tagging module enforces tags and wires billing export to tenant-specific BigQuery dataset.
- On creation, create budget alert at 25%/50%/75%/100% of the max_monthly_spend variable and a PagerDuty escalation on 100%.
- Emit onboarding-run metric with labels (tenant_id, env, git_sha) to platform metrics.

Testing and validation suite
---------------------------
1. Unit: terraform validate + fmt in CI.
2. Integration (preprod): plan + apply to ephemeral account with mocked endpoints; run smoke tests that exercise node_pool scaling and basic inference path.
3. Post-provision validation checks (automated):
   - Can reach internal container registry (egress path OK)
   - Node pool registers with runtime autoscaler within 10 minutes
   - KV cache warming script completes in < 7 minutes for baseline prompt set

Day-1 runbook (post-create checklist)
------------------------------------
1. Verify Terraform apply completed without error and outputs are persisted.
2. Confirm VPC subnets and route tables match expected CIDR allocations.
3. Confirm node-pool size and that warm-pool instances are healthy (use platform dashboard).
4. Confirm monitoring exporter reports metrics; a short-lived dashboard link is created in outputs.
5. Ensure cost export dataset exists and the first export has succeeded.
6. Send onboarding notification to tenant owner with runbook link and Slack channel.

Day-7 stabilization tasks
-------------------------
- Review actual spend vs forecast; adjust max_monthly_spend and set stricter alerts if needed.
- Review network flows captured by VPC flow logs for unexpected egress.
- Run a workload simulation at 30% expected QPS to validate autoscaler behavior.

Rollback and teardown
---------------------
- If critical misconfiguration is discovered, follow the revert path:
  1. Open an incident and tag with onboarding-run id.
  2. Run terraform destroy using the same locked backend in a controlled apply environment.
  3. Notify billing and reclaim the cost dataset.
- For accidental large-cost errors, the finance escalation matrix should be triggered (see related_pages).

Owner and escalation matrix
--------------------------
- Primary owner: infra-provisioning team (oncall alias: infra-provisioning-oncall).
- Oncall escalation: pager -> infra-provisioning senior -> networking team -> security if egress policy violated.

Operational best practices and tips
----------------------------------
- Prefer increasing warm-pool capacity in small increments and observe 15-minute windows before further scaling.
- Use base images with signed attestations (image promotion CI) to reduce boot time variability.
- Keep terraform module versions pinned in the tenant repo; use dependabot to propose updates.

Auditability and compliance
--------------------------
- Every onboarding PR must include: a completed checklist, required tags, justification for non-default egress (if any), and a signed approver for prod environments.
- Audit logs for the backend state must be retained for 365 days and exported to the central audit project.

  gpu_profile = "a100-80"
  desired_size = 4
}

Appendix B: Useful CLI commands
-------------------------------
- Inspect plan: terraform plan -out=plan.tfplan && terraform show -json plan.tfplan | jq '.resource_changes'
- Lock backend: gcloud storage buckets set-iam-policy --bucket $TF_BACKEND_BUCKET policy.json
- Force destroy (rare): terraform destroy -target=module.node_pool --auto-approve

Appendix C: Troubleshooting checklist
-------------------------------------
- Plan fails: check provider plugin version and variable interpolation; run terraform init -reconfigure.
- Apply hangs on resource creation: check cloud quota (GPUs) and allocation logs; contact gpu-fleet-and-capacity team.
- Unexpected egress: check NAT gateway config and proxy ACLs, then escalate to cloud-accounts-and-networking team.
