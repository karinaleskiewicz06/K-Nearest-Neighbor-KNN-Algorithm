Production rollout approvals (change management)

# Policy summary
All production changes that can affect customer traffic must follow this approval policy. Model rollouts for the Hosted API qualify as production changes.

# What requires a change record
A change record is required for:
- new model version rollouts
- changing routing policies (including enabling or tuning automatic fallback)
- changing serving configuration that affects output, latency, or cost (e.g., quantization profile)

# Required information in the change record
- Change title and description
- Impact radius (routes, regions, customer pins)
- Rollout plan and rollback plan
- Owner/DRI and on-call coverage during execution
- Links to relevant runbooks and dashboards
- Evidence of readiness (eval report or reference to Applied ML gates)

# Approval matrix
Approvals required before execution:
- **Low risk** (default canary, no new regions, no new API features):
  - Platform Eng DRI approval
- **Medium risk** (fast canary, change to fallback triggers, large traffic share shift):
  - Platform Eng DRI approval
  - SRE approval
- **High risk** (new model family, tokenizer change for default route, major behavior change):
  - Platform Eng DRI approval
  - SRE approval
  - Applied ML approval
  - Product approval

# Timing
- Changes should be executed during defined business-hours windows for the owning region unless there is an incident response need.
- Avoid executing at the same time as known fleet maintenance events.

# Post-change requirements
- Monitor for at least 60 minutes after reaching 100% traffic.
- Record outcome (success, partial rollback, full rollback) and attach dashboard screenshots or links.
- File follow-ups for any anomalies observed, even if rollback was not required.
