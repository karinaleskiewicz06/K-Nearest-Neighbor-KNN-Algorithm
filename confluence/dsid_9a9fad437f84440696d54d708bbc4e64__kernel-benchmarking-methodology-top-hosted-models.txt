Kernel benchmarking methodology (top hosted models): FP8/INT8 vs baseline

## Purpose
This page defines the benchmark methodology we use to compare kernel paths (baseline FP16/BF16 vs FP8 and INT8 variants) for Redwood’s top hosted models. The intent is to produce results that are:
- **Reproducible** across clusters and over time
- **Representative** of production traffic (prompt + generation distributions; concurrency; prefill/decode mix)
- **Actionable** for runtime decisions (kernel auto-selection, scheduler tuning, quantization profile policy)

This methodology is mandatory for results that will be used to:
- Change kernel dispatch/auto-selection defaults
- Gate rollouts via perf canary thresholds
- Update internal/external performance narratives

---

## Key definitions (what we measure)
We distinguish **kernel-level** results from **end-to-end serving** results.

### Kernel-level (microbench)
Measures isolated kernel performance and/or tight operator sequences (e.g., attention, matmul) under controlled shapes.
- Pros: low noise; shape-specific insight; faster iteration
- Cons: does not capture scheduler interaction, request arrival patterns, KV-cache behavior under load

### End-to-end (serving bench)
Measures the runtime in a realistic serving loop with batching, KV cache, scheduler behavior, and realistic request mix.
- Pros: what customers feel (TTFT/TPOT/throughput); captures interaction effects
- Cons: higher noise; more confounders (thermals, clocks, contention)

### Primary metrics (serving)
- **TTFT (time to first token)**: from request enqueue to first generated token (includes prefill + scheduling delays)
- **TPOT (time per output token)**: average per-token latency during decode (reported as ms/token)
- **Tokens/s (throughput)**: aggregate output tokens per second at a given load
- **Error rate**: non-2xx / model errors / correctness fallbacks engaged

### Primary metrics (microbench)
- **Kernel latency** (us / call) and derived **TFLOP/s** where applicable
- **Achieved memory bandwidth** (GB/s) where applicable
- **Occupancy / launch configuration** (for diagnosis, not for win criteria)

## Workload taxonomy (prefill vs decode)
We always report at least these workloads per model/GPU/mode.

### W1: Prefill-only (prompt processing)
Goal: measure prompt ingestion speed and attention/matmul behavior at larger sequence lengths.
- Input: prompt tokens sampled from the prompt-length distribution (see below)
- Output: **0 generated tokens** (or minimal fixed output = 1 token) to isolate prefill
- Report: TTFT proxy (prefill time) and prefill tokens/s

### W2: Decode-only (KV-cache heavy)
Goal: measure steady-state decode performance and KV-cache behavior.
- Input: fixed prompt (small, e.g., 32–64 tokens) to establish KV cache
- Output: generation length sampled from distribution (see below)
- Report: TPOT and decode tokens/s

### W3: Mixed prefill + decode (representative)
Goal: capture the production-like interaction where prefill and decode compete for GPU time, and where scheduler knobs can dominate realized wins.
- Input: prompt + output lengths sampled from the distributions below
- Concurrency: varies by GPU SKU (see “Load levels”)
- Report: TTFT p50/p95, TPOT p50/p95, tokens/s, queue depth, and backpressure counters

### W4 (optional but recommended): Long-context stress slice
Goal: catch shape regimes known to be fragile (e.g., long-context attention, alignment edge cases).
- Input prompts at the 95–99th percentile prompt lengths (bounded by model context)
- Report: same as W1/W3 plus error/fallback counters

## Representative sequence-length distributions (top hosted models)
We use Redwood’s “Top hosted models benchmark suite v3” as the source of truth for prompt selection and traffic mix. The distributions below are the **methodology defaults**; deviations must be called out in the result notes.

### Prompt length distribution (tokens)
Used for W1 and W3.
- p50: **256**
- p75: **768**
- p90: **2,048**
- p95: **4,096**
- p99: **8,192** (only for models/variants that support it)

Sampling rule:
- Use a **mixture distribution** so we do not under-sample long prompts:
  - 50% from [64, 512]
  - 30% from [513, 2,048]
  - 15% from [2,049, 4,096]
  - 5% from [4,097, max]

### Generation length distribution (output tokens)
Used for W2 and W3.
- p50: **128**
- p90: **512**
- p95: **1,024**

Sampling rule:
- Cap output to model max and benchmark suite constraints.
- Always include a fixed-length decode slice (e.g., 256 tokens) for apples-to-apples TPOT comparisons.

### Tool-calling / structured-output variants
For models where these are common in hosted traffic, the suite includes:
- JSON/structured output prompts (higher formatting pressure)
- Tool-call style prompts (function signature + schema)

Methodology rule:
- Include these variants only in **end-to-end** runs (W3), not microbench.
- Report them as a separate slice if they move TTFT/TPOT by >3%.

## Batch size, concurrency, and load levels
Kernel wins can disappear (or invert) depending on batching and arrival patterns. We therefore standardize load levels.

### Load levels (serving)
We report 3 load points per GPU SKU:
1) **Low load**: minimal queuing (target queue depth ~0; e.g., 1–2 concurrent requests)
2) **SLO load**: typical production utilization (target GPU util ~60–75%)
3) **High load**: near saturation (target GPU util ~85–95%, controlled)

Methodology rule:
- Do not tune the system per kernel mode to “make it look good.”
- Scheduler knobs must be held constant across compared modes unless the explicit purpose is scheduler tuning (in which case document the knobs and treat as a separate experiment).

### Batching rules
- Keep continuous batching enabled.
- Fix batching window / max batch tokens for the run (record exact values).
- If a kernel requires shape constraints that change effective batching, record the fallback rate and impacted slices.

## Warmup, steady-state, and measurement windows
### Warmup requirements (mandatory)
For each (model, GPU, mode, workload, load level) run:
- **Warm up for either 60 seconds or 200 requests**, whichever is longer.
- Discard warmup measurements.
- Ensure KV-cache is exercised before recording decode metrics (i.e., include enough decode steps in warmup).

Rationale:
- Stabilizes clocks/thermals, JIT/compile paths (if any), allocator state, and cache behavior.

### Measurement window
- Minimum: **10 minutes** of measurements for end-to-end serving runs.
- Minimum: **2,000 requests** recorded (after warmup) for W3 at SLO load.
- For microbench: minimum **2,000 iterations per shape**, and at least **3 independent process launches**.

### Outlier handling
- Do not delete outliers unless there is an identified instrumentation artifact.
- If excluding samples, document the rule (e.g., “dropped first 30 seconds after GPU clock lock applied”).

## Environment pinning (driver/CUDA/container) and clocking guidance
Variance from environment drift is the top failure mode. Every run must include environment metadata and follow the pinning rules below.

### Container and dependencies
- Use the benchmark runner container version pinned for the sprint.
- Record:
  - Runtime git SHA
  - Benchmark runner git SHA
  - Container image digest
  - CUDA version (runtime)
  - NVIDIA driver version
  - NCCL version (if relevant)

### GPU clocking (recommended for bench clusters)
If permitted by the benchmark cluster policy:
1) Enable persistence mode:
   - `sudo nvidia-smi -pm 1`
2) Lock graphics and memory clocks (exact values depend on SKU):
   - `sudo nvidia-smi -lgc <min,max>`
   - `sudo nvidia-smi -lmc <mem_clock>`
3) Verify clocks and throttling reasons:
   - `nvidia-smi -q -d CLOCK,POWER,TEMPERATURE`

Methodology rule:
- If clocks cannot be locked (shared environment), you must run additional repetitions and report higher error bars.

### Thermal and contention controls
- Prefer dedicated nodes for benchmarking.
- Do not run benchmarks on nodes with unrelated GPU workloads.
- If MIG/partitioning is in use, record MIG configuration and do not compare across different MIG profiles.

## Run counts, repetitions, and error bars
### Minimum run counts (mandatory)
For each configuration:
- End-to-end serving (W3): **3 independent runs** (fresh process launch), each meeting the measurement window requirements.
- Microbench: **3 independent runs** per shape set.

### Summary statistics
We report:
- p50 and p95 for TTFT and TPOT
- tokens/s (mean and p50)
- Error/fallback rate (mean)

### Error bars / uncertainty
For each reported metric, compute uncertainty using one of:
- **Bootstrap 95% confidence interval** over request samples (preferred for serving)
- Or **mean ± 2× standard error** across independent runs (acceptable if sample sizes are large and stable)

Methodology rule:
- Always show error bars in internal result tables.
- Any claim of “win” must clear the win thresholds below **and** be stable across independent runs.

## Win/regression interpretation rules (what counts as real)
### Practical win thresholds
A change is considered a win only if it satisfies BOTH:
1) Magnitude threshold:
   - **>= 5% improvement** in the primary metric for the workload slice (TTFT for W1, TPOT for W2, both for W3), OR **>= 8% improvement** in tokens/s at the same load level.
2) Statistical/variance threshold:
   - Improvement is **greater than the larger of**:
     - 2× the 95% CI half-width, OR
     - 3% relative change

### Regression thresholds (triage-required)
Flag as regression if any of the following hold (for W3 at SLO load):
- TTFT p95 worsens by **>= 5%**
- TPOT p95 worsens by **>= 5%**
- tokens/s drops by **>= 5%**
- Error rate or fallback rate increases by **>= 0.2 percentage points** (absolute) or doubles, whichever is smaller

### Mixed results
It is common to see:
- TTFT improve while TPOT regresses (or vice versa)
- Microbench wins not realized end-to-end due to batching/scheduling

Interpretation guidance:
- Prefer end-to-end W3 results for kernel default decisions.
- Use microbench to explain “why” and to narrow shape regimes for heuristics.

## Correctness, fallbacks, and quality guardrails
### Correctness validation (mandatory)
For each new kernel mode:
- Run the correctness suite for representative shapes before performance runs.
- In serving runs, collect and report:
  - Kernel fallback counters (by reason)
  - Any NaN/Inf counters
  - Output determinism checks where applicable

### Quality considerations (FP8/INT8)
Performance results are not sufficient to ship defaults.
- Applied ML/Evals must sign off on any default change for hosted catalog models.
- If a mode shows quality regression for long-context prompts, gate by seq-len regime and/or keep as opt-in.

Methodology rule:
- Performance tables must include a “quality status” column: {Not evaluated | Pass | Conditional | Fail} with a link to the eval artifact.

## Required artifact logging (what must be attached to results)
Each benchmark run must upload artifacts containing:
- Run metadata: SHAs, image digests, driver/CUDA, GPU clocks, model hash, kernel mode, scheduler config, region/cluster
- Raw time series (request-level latencies or histograms with sufficient resolution)
- Aggregated summary (p50/p95, tokens/s, error/fallback)
- Notes on anomalies (e.g., thermal throttling, cluster maintenance, noisy neighbor)

Naming convention (recommended):
- `fp8int8_<model>_<gpu>_<workload>_<loadlevel>_<mode>_<date>_<gitsha>`

## Reporting template (how to present results)
Every results write-up (doc, sheet, or PR description) must include:
1) Configuration matrix (model/GPU/mode/workload/load)
2) Environment metadata (driver/CUDA/container/clocks)
3) Summary table with error bars
4) Notable anomalies and what was done
5) Recommendation (ship / gate / do not ship) and rationale

Minimum summary table columns:
- Model
- GPU SKU
- Mode (baseline / FP8 / INT8)
- Workload (W1/W2/W3)
- Load level
- TTFT p50/p95 (ms)
- TPOT p50/p95 (ms/token)
- Tokens/s
- Fallback rate
- 95% CI (or run-to-run stddev)
- Quality status

## Common pitfalls and how to avoid them
- **Clock drift / thermal throttling:** lock clocks where possible; verify throttle reasons; extend warmup.
- **Driver/CUDA mismatches across clusters:** pin images; record versions; avoid cross-cluster comparisons unless identical.
- **Hidden scheduler changes:** hold scheduler knobs constant across compared runs; record config in artifacts.
- **Comparing different effective batch regimes:** ensure max batch tokens and arrival process are consistent; report fallback rates.
- **Microbench overfitting:** do not pick kernels based solely on microbench; use W3 for dispatch decisions.
