GPU Hardware Profile Inspector and IaC Validator

Summary:
This document describes the GPU Hardware Profile Inspector (GHPI) — a lightweight collector and Terraform/plan-time validator that verifies GPU instance capabilities, driver/runtime compatibility, and tenancy/networking constraints before a tenant or CI job is allowed to provision accelerator capacity. GHPI is intended to reduce costly misprovisions, shorten incident triage for capacity mismatches, and provide a machine-readable compatibility database for other infra systems (autoscaler, warm pools, and placement engines).

Why we built GHPI:
- Frequent onboarding failures due to mismatched CUDA/GPU microcode and runtime expectations in CI and Dedicated clusters.
- Silent performance regressions when a model expects tensor-core availability or specific fp16 support.
- Manual checks are slow and error prone for cross-account or partner-hosted GPU resources.

Scope and non-goals:
- In scope: plan-time Terraform validation, CI preflight step, runtime node probe for inventory, compatibility DB (JSON), and error-mode templates for operators.
- Out of scope: kernel-level patching, automatic node remediation, and scheduler rebalancing logic (these are handled by runtime/orchestration).

Goals and success criteria:
- Prevent >90% of class A misprovisions (wrong GPU type or missing drivers) at plan/apply time.
- Fail-fast in CI preflight with deterministic messages, reducing oncall pages related to provisioning by 30% in first quarter post-launch.
- Provide a canonical, queryable hardware profile for use by placement and cost tooling.

High-level architecture:
1) Inspector agent (go binary): runs as ephemeral job or daemonset; collects GPU properties via nvidia-smi/rocm-smi and small sysfs probes. Produces a signed JSON profile.
2) Compatibility DB: a versioned JSON/YAML store kept in s3 (or internal artifact store) with schema and compatibility rules (driver ranges, feature flags: tensor-cores, bf16, mig).
3) Terraform Validator: Terraform external data provider + pre-apply hook that fetches target instance type metadata and matches against desired profile.
4) CI integration: a pipeline task that runs GHPI against the target image (or simulated profile) and blocks merges on hard failures.

Compatibility DB schema (described as a table):
- field: description (example)
- gpu_family: vendor model family (A100, H100, MI250)
- min_driver_version: lowest driver version known-good (e.g., 535.54)
- required_features: list of features or booleans (tensor_cores, bf16, cuda_version>=12.1)
- instance_matchers: regex or cloud SKU set used by Terraform matching
- recommended_kernel_params: list of kernel args recommended for best throughput

Terraform validator integration pattern:
1) Module author declares a desired hardware profile object in a module input variable: desired_gpu_profile.
2) validator runs as null_resource/ external data provider that queries Compatibility DB and optionally the cloud provider SKU metadata API.
3) On mismatch, validator returns a non-zero exit with a human readable report and a machine parseable code for automation.

Terraform example (snippet):

variable "desired_gpu_profile" {
  type = object({
    gpu_family = string
    min_cuda = string
    require_tensor_cores = bool
  })
}

data "external" "ghpi_validator" {
  program = ["/usr/local/bin/ghpi-validator", jsonencode({
    gpu_family = var.desired_gpu_profile.gpu_family,
    min_cuda = var.desired_gpu_profile.min_cuda,
    require_tensor_cores = var.desired_gpu_profile.require_tensor_cores
  })]
}

resource "null_resource" "fail_on_mismatch" {
  provisioner "local-exec" {
    command = "test \"${data.external.ghpi_validator.result.status}\" = \"ok\" || (echo \"GHPI validation failed: ${data.external.ghpi_validator.result.message}\" && exit 1)"
  }
}

CI/CD integration pattern:
- Add a pipeline stage `ghpi-preflight` that runs for PRs touching infra modules or deployments that request GPU SKUs.
- The stage runs the inspector in emulation mode (using the compatibility DB) or against a small test instance in a sandbox account.
- On failure: fail the pipeline and post an actionable comment with remediation steps.
- On soft-mismatch (policy warning): annotate the PR, but do not block.

Inspector CLI example (flags):
- ghpi collect --output profile.json --sign-with k8s-key --probe nvidia-smi,sysfs
- ghpi verify --profile profile.json --compat-db s3://redwood-infra/ghpi/compat-v2.json 
- ghpi emulate --sku AWS:P4d.24xlarge --output expected-profile.json

Validator error categories and typical remediation:
1) HARD_MISMATCH: requested features not available (e.g., tensor_cores required but model is V100). Remediation: change SKU or adjust model runtime to not require feature.
2) DRIVER_OLD: driver < min_driver_version. Remediation: schedule driver bump or pick a different image.
3) NETWORK_EGRESS_RESTRICTED: instance would be placed in subnet without required NAT/egress; remediation: ensure egress route/NAT or use a dedicated VPC gateway.
4) POLICY_WARN: feature available but outside recommended performance window. Remediation: accept risk and track with runbook or pick alternate SKU.

Operational runbook (on validator failure in a production apply):
1) Review Terraform validation report and GHPI result ID.
2) If HARD_MISMATCH: open an incident with tagging `prov-mismatch`; notify capacity-owner and propose SKU swap.
3) If DRIVER_OLD: schedule node update via golden-image pipeline; add a warm-pool swap to reduce downtime.
4) If NETWORK_EGRESS_RESTRICTED: validate subnet routing rules/egress NAT gateways and fix via IaC change; use `apply --target` for emergency workaround to update route table.
5) If unknown or signature mismatch: escalate to infra-oncall; capture profile.json and upload to artifact store for triage.

Metrics and SLOs for GHPI service and validator:
- Validator latency (target): < 3s for plan-time cached queries, < 20s for live SKU API checks.
- Accuracy: false-positive rate < 1% (important to avoid blocking developers), false-negative rate < 0.5% for class A mismatches.
- Adoption: 100% of Terraform GPU modules integrated within 6 weeks of release; GHPI stage must run in CI for any PRs that reference gpu SKUs.

Rollout plan:
1) Phase 0 (canary): deploy GHPI collector to staging and run in `emulate` mode for 2 weeks, gather telemetry.
2) Phase 1 (beta): integrate with two critical TF modules and enable CI preflight in developer sandboxes.
3) Phase 2 (GA): make validator required for all gpu-related modules in `main` branch; publish compatibility DB v1.0 and automate DB updates via scheduled collectors.

Security and signing model:
- Profiles are signed using a KMS-backed signing key in the private control plane. Validator verifies signature when using live profiles.
- CI emulate mode accepts unsigned profiles but marks them as heuristic.

Open decisions (ADR pointers):
- Whether to allow automatic driver upgrades vs. a manual change (see ADR-2025-09-driver-upgrades).
- Storing compatibility DB in S3 vs. an internal metadata service for lower latency.
