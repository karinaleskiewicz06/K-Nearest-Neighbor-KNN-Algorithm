Tenant GPU warmup & proactive seeding patterns

Overview

Purpose: This page documents recommended patterns for keeping tenant GPU allocation (warm pools, KV caches, and model state) in a hot/ready state for latency-sensitive inference workloads. The guidance spans architecture, Terraform/IaC primitives, CI/CD steps to seed and validate warm state, expected observability signals, cost trade-offs, and runbook steps for remediation.

Scope: Applies to Redwood Dedicated and hosted GPU pools used for production inference where 95th/99th percentile latency SLOs are impacted by cold starts, model cold-weights loading, and KV-cache misses. Not intended for ad-hoc evaluation or ephemeral CI clusters.

Background

- Problem: Cold GPU instances and empty KV caches can add 100s of milliseconds to seconds of tail latency on first requests. This impacts user-facing features and can cascade into retries and higher cost.
- Goal: Reduce cold-start tail latency to < 50ms contribution for warmup-sensitive endpoints while keeping steady-state cost per token predictable.

Design principles

1. Fast recovery over perfect coverage: prefer economical proactive seeding rather than trying to keep every possible model+context fully resident.
2. Tenant-prioritized warming: allocate warm budget per tenant based on business priority and SLA.
3. Workload-aware seeding: select seed prompts and KV seeds that represent typical request prefixes and sequence-length distribution.

Terminology

- Warm pool: a pre-provisioned set of GPU instances with serving runtime bootstrapped and model weights loaded (optionally quantized variant).
- KV-seeding: populating model KV cache (prefix caching) with representative token streams to avoid first-request generation overhead.
- Snapshot: serialized model and runtime state that can be restored faster than cold weight load.

Ownership and roles

- Infrastructure (eng-infra): maintain Terraform modules, autoscaler hooks, and observability dashboards.
- Serving runtime (eng-serving-runtime): provide snapshot format, warm restore API, and safe seeding APIs (idempotent).
- Tenant platform/product engineers: provide seed prompt sets and business-priority mapping.

Patterns (high level)

- Tiered warm pools
  - Hot: always-resident minimal number of GPUs per high-priority tenant (affects SLA).
  - Soft-warm: shared multi-tenant machines with preloaded common models and candidate KV-seeds for medium-priority tenants.
  - Cold-on-demand: standard autoscaling; first requests use fallback shorter SLO or lower-cost model.

- Proactive seeding strategy
  - Select seed prompts: top-10 prefixes per tenant (derived from sampled traffic, privacy-sanitized).
  - Scheduled re-seeding: run light-weight seeding jobs during off-peak windows and after deploys.
  - Event-driven seeding: trigger seeding when a cold launch is detected (automated feedback loop).

Terraform / IaC primitives

We provide modular constructs to express warm pools, seeding jobs, and lifecycle policies. Recommended inputs:

| Module input | Type | Example | Notes |
|---|---:|---|---|
| warm_pool_size | int | 2 | Minimum hot nodes for tenant X |
| model_variant | string | llama-3-small-q4 | Image/model to preload |
| seed_job_schedule | string | cron(0 3 * * *) | Off-peak re-seed window |
| snapshot_retention_days | int | 7 | How long warm snapshots are kept |

Terraform snippet (example usage)

```hcl
module "tenant_warm_pool" {
  source = "git::ssh://git.example.com/modules/tenant-warm-pool.git//terraform"
  tenant_id = "tenant-42"
  warm_pool_size = 2
  model_variant = "rdi/llama-3-small-q4"
  seed_job_schedule = "cron(0 3 * * *)"
  snapshot_retention_days = 7
}
```

CI/CD: seeding & validation pipeline

1. After model promotion or warm-pool scaling, run an automated `seed-and-validate` job:
   - Step 1: Submit seeding tasks with tenant-specific prefix list to serving runtime.
   - Step 2: Run smoke requests (health + latency) against warmed instances.
   - Step 3: Validate deterministic artifacts (snapshot checksum and metadata).
2. If validation fails, keep nodes in drain state and route traffic to fallback models.

Seeding job implementation (example CLI)

```bash
# seed prefixes (idempotent)
redwoodctl warm-seed --tenant tenant-42 --pool warm-a --seed-file seeds/tenant-42-top10.json
# run quick smoke check
redwoodctl smoke-check --endpoint /v1/generate --timeout 200ms --expect-max-latency 120ms
```

Observability & SLOs

Key metrics to track:
- warm_pool_utilization (gpus in warm pool / configured warm pool)
- kv_seed_hit_rate (percentage of requests with a cache prefix hit)
- cold_start_latency_p50/p95/p99 (delta from baseline that indicates cold impact)
- seed_job_success_rate and seed_job_duration

Alerting thresholds (suggested):
- kv_seed_hit_rate < 85% for 15m -> P1 alert to infra oncall.
- cold_start_p95 > 250ms for 10m -> P1.
- seed_job_success_rate < 95% for 1h -> P2.

PromQL examples

- kv_seed_hit_rate (15m rolling):
  avg_over_time(kv_seed_hit_rate[15m]) < 0.85
- spike in cold starts:
  increase(cold_start_count[10m]) > 50

Cost model and budgeting

- Budget inputs: warm pool instance-hours, seed job runtime, snapshot storage.
- Example rule: cap warm pool spending per tenant to X% of monthly committed budget; autoscaler reduces warm pool and switches to soft-warm when budget breached.

Runbook: cold-warm incident (P1)

1. Detect: Pager alert fired for kv_seed_hit_rate < 85% or cold_start_p95 elevated.
2. Triage: Check seed_job_success_rate and recent deploys in the last 30 minutes.
3. Immediate mitigation (5–15 min):
   - If seed jobs are failing: restart seed-job pod(s): `kubectl rollout restart deployment/seed-worker-tenant-42` and inspect logs: `kubectl logs -f job/seed-tenant-42`
   - If warm pool scaled down unexpectedly: scale up warm pool via Terraform autoplanner override OR run `redwoodctl warm-pool scale --tenant tenant-42 --size 2`
   - Route heavy read traffic to canary-hot nodes if available.
4. Recovery validation (15–45 min):
   - Confirm kv_seed_hit_rate and cold_start_p95 returning to baseline.
   - Re-run smoke-checks.
5. Post-incident: Create a short postmortem with root cause, system changes, and action items (owners and deadlines).

Troubleshooting checklist (quick)

- Are seeding jobs scheduled and recent? `kubectl get jobs --selector=seed-job,tenant=tenant-42`
- Are snapshots available in object store? Check `s3://warm-snapshots/tenant-42/` for timestamps.
- Serving runtime errors: `kubectl logs -l app=serving-runtime --tail 200` to identify restore failures.
- Network egress issues: verify VPC egress and object-store access via cloud audit logs.

Safety and failure modes

- Idempotency: seeding must be safe to run repeatedly. Jobs should detect in-progress seeding and avoid overlapping heavy requests that could thrash GPU memory.
- Snapshot checksum/version mismatch: pipeline must abort and fallback to cold-on-demand if snapshot incompatible with runtime version.
- Cost runaway: implement guardrail that auto-drains non-critical warm pools when spend delta exceeds threshold.

Operational playbook for new tenant onboarding

1. Define SLA tier and warm budget during onboarding.
2. Provide sample seed prompts (privacy-reviewed).
3. Provision warm pool via Terraform module with `warm_pool_size` and `seed_job_schedule` set.
4. Run initial full seeding job and validate smoke tests.
5. Monitor 24–72 hours and adjust seed set and warm_size based on real traffic patterns.

Appendices

A. Example seed selection heuristic

- Use sampling of 0.1% of traffic over a 7-day window. Group prefixes by the first 8 tokens, rank by frequency and latency impact. Pick top-K distinct prefixes where K=10 by default.

B. Snapshot storage layout (recommended)

- s3://warm-snapshots/{region}/{tenant}/{model_variant}/{snapshot-id}.metadata
- retention policy: LRU by last-access -> move to Glacier after 30 days.
