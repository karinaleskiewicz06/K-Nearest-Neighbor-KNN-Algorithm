Incident-bot: Telemetry Correlation Graph + Instant Playbook (Runbook)

h1. Overview
The telemetry correlation graph and instant playbook features help first responders quickly answer two questions in the first few minutes of an incident:

* What *other* signals correlate with the incident (traces, metric anomalies, deploys/config changes)?
* What is a short, safe first-pass set of remediation and debug steps to run in Slack/WarRoom?

This capability is implemented as a lightweight correlation service within incident-bot that generates:

* a *correlation graph artifact* attached to the incident context
* a *draft playbook preview* (ranked top actions + “why” reasoning + provenance)

The system surfaces suggestions only. It does *not* auto-execute actions.

h2. When to use
Use these features when:

* Incident severity is high and responders need to triage multiple services quickly.
* There is suspicion of a recent deploy/config change or cross-service dependency failure.
* A responder needs a safe, shareable set of commands/links for the WarRoom.

Do *not* rely on the draft playbook as a replacement for canonical runbooks for regulated or customer-sensitive clusters; use it as a triage accelerant.

h1. Components
h2. Correlation graph
The correlation graph links:

* recent deploys (service releases and rollouts)
* metric anomalies (time-windowed)
* traces/spans (obfuscated identifiers by default)
* inferred dependencies (service graph + heuristics)

The join logic is time-windowed and intentionally conservative.

h2. Instant playbook drafter
The playbook drafter produces a ranked list of up to three suggested next steps:

1. A recommended action (safe default)
2. One or more debug command templates (placeholders by default)
3. A short “why this helps” sentence

All output includes provenance headers so responders can see which signals drove the recommendation.

h1. How it works (high-level)
1. incident-bot receives an incident update.
2. If enabled, incident-bot computes a correlation graph over a bounded time window.
3. The graph is serialized and attached to the incident context as an artifact.
4. When requested (UI button or Slack action), incident-bot drafts a playbook preview derived from the graph and templates.

h1. Enablement & configuration
h2. Feature flags
These features are gated so they can be rolled out gradually.

* Default behavior is *read-only suggestions*.
* Full raw identifiers remain *disabled by default* (see Safety & privacy).

h2. Configuration reference
| Key | Type | Default | Notes |
| --- | ---- | ------- | ----- |
| correlation.enabled | boolean | true | Global enable/disable for correlation graph generation. |
| correlation.window_seconds | integer | 300 | Maximum join window. Updated from 600s (10m) to 300s (5m) after rollout feedback to reduce noise during fast-moving incidents. |
| correlation.max_nodes | integer | 75 | Caps graph size attached to the incident. |
| playbook.enabled | boolean | true | Enables playbook drafting endpoint and Slack action. |
| playbook.max_suggestions | integer | 3 | Max ranked items returned. |
| playbook.placeholders_only | boolean | true | When true, the drafter emits command *templates* (no assumed cluster context). |
| incident_bot.debug.allow_raw_ids | boolean | false | When true, permits raw IDs *only* with explicit operator confirmation (see below). |
| http.healthz_enabled | boolean | true | Exposes /healthz for readiness/liveness. |

h1. Interfaces
h2. Incident annotation trigger
If your incident management pipeline supports annotations, set:

* correlation.graph=true

This triggers correlation graph generation and attachment to the incident context.

Note: In some environments the pipeline sets this automatically for SEV-1/SEV-2 incidents.

h2. HTTP endpoints
* GET /healthz
  * 200 OK when correlation and playbook subsystems are ready.

* POST /playbook-preview
  * Input: incident identifier + optional scope parameters
  * Output: ranked suggestions with confidence scores and provenance

Operational note: During March 2026 rollout, the endpoint was updated to reject requests missing an incident context (prevents accidental “free-form” prompting and keeps outputs grounded).

h2. Slack integration
A Slack action labeled “Draft Playbook”:

* requests a /playbook-preview
* posts a short list of suggested actions to the WarRoom thread
* includes confidence and provenance (signals referenced)

h1. Confidence scoring (operator interpretation)
Each suggestion includes a confidence score intended for triage prioritization.

Interpretation guideline:

* 0.80–1.00: strong correlation signals (recent deploy/config change + anomaly alignment)
* 0.50–0.79: moderate correlation (partial alignment or weaker dependency evidence)
* <0.50: informational; verify via canonical runbooks and service owners

Confidence scores are not probabilities and should not be used as an automated decision threshold.

h1. Safety & privacy
h2. Data minimization
By default, the correlation graph stores only:

* obfuscated trace identifiers
* normalized metric identifiers (no raw high-cardinality labels)
* deploy identifiers (build ID / release tag)

h2. Raw identifiers
Raw identifiers are disabled by default.

To temporarily allow raw IDs for a time-boxed debugging session:

1. Ensure the incident is marked internal and the WarRoom is appropriately restricted.
2. Obtain explicit on-call lead approval.
3. Enable incident_bot.debug.allow_raw_ids=true.
4. Re-run correlation generation for the incident.
5. Turn the flag off after triage.

Change note (newer than the original PR text): the flag name in production is incident_bot.debug.allow_raw_ids (renamed from earlier incident_bot.debug.show_raw_ids during rollout standardization across services).

h2. No secrets collection
The system does not collect or store secrets, tokens, or key material.

h1. Rollout notes and operational constraints
* The join window default is 5 minutes (300s). This was reduced from 10 minutes to lower false correlations during high-churn deploy periods.
* Graph size is capped to prevent large incident payloads.
* Templates default to placeholders to avoid incorrect cluster-context commands.

h1. Troubleshooting
h2. No graph attached to incident
Check:

1. correlation.enabled is true.
2. The incident annotation correlation.graph=true is present (or your pipeline sets it for the severity).
3. Telemetry sources are reachable (traces/metrics/deploy feed).
4. correlation.max_nodes isn’t set too low for the environment.

h2. Playbook preview returns generic suggestions
This usually means correlation evidence is weak.

Actions:

1. Confirm the time window aligns with incident start (correlation.window_seconds).
2. Verify deploy feed is reporting recent releases.
3. Use canonical runbooks and page the owning team if dependency inference is uncertain.

h2. Slack action fails but /playbook-preview works
Check:

* Slack app permissions for interactive actions
* incident-bot logs for request signing verification errors
* network egress from the Slack action handler to the playbook endpoint

h2. CI/integration test flakiness (historical)
During initial adoption, integration tests were flaky due to telemetry client startup timing. The recommended approach is to mock telemetry clients for deterministic tests and keep /healthz as the readiness gate.
