GPU image promotion and canary CD playbook

Summary
-------
This playbook describes the end-to-end process for building, validating, promoting, and performing controlled canary rollouts of GPU node images and accelerator runtime artifacts across Redwood Inference clusters and cloud accounts. It codifies CI/CD jobs, Terraform/IaC interactions, safety gates, metrics to observe during canaries, and runbook steps for fast rollback. Purpose: reduce runtime regressions, improve reproducibility, and make image promotion auditable across accounts and regions.

Scope
-----
Applies to:
- GPU node AMIs/VM images and container images that include: kernel modules, NVIDIA drivers, CUDA/CUDNN, runtime libraries, custom accelerator optimizations (e.g., Triton init hooks), and the Redwood node agent.
- Promotion across: staging -> qa -> production (regional) accounts and Dedicated/private customers when applicable.
Excludes: model container images and user payloads (handled by model release pipelines).

Key concepts and definitions
----------------------------
- Image build: CI job that composes OS base, driver packages, accelerator firmware, and final configuration.
- Promotion: tagging/publishing an image version and updating Terraform image IDs in environment state.
- Canary: controlled rollout to a small percentage of fleet for a specified validation window.
- Gate: a set of automated and manual approvals required before moving to next stage.

Prerequisites
-------------
1) IaC: Terraform modules for node pools must accept image_id, image_version, and image_metadata tags.
2) CI: Build pipeline must publish artifacts to an image registry (AMI/OCI) and create a signed release record in the artifact store.
3) RBAC: CI service identity and release engineers have access to image promotion job in each cloud account.
4) Observability: dashboards and alerts defined (see Metrics and SLOs).

Promotion pipeline (high level)
------------------------------
1) Build & unit tests (CI): produce image vX.Y.Z and run deterministic smoke tests in hermetic environment.
2) Integration tests: spin ephemeral GPU instance in isolated VPC; run driver compatibility, NVML, and small inference workload.
3) Publish to staging registry and create release metadata (SHA256, bill-of-materials).
4) Canary deploy to 2% of nodes in staging cluster for 2 hours. Verify gates.
5) If pass, promote to QA account for cross-account tests and network egress validation.
6) After QA, create Terraform plan diff for production node pools and open canary rollout MR.
7) Apply canary: update 1–5% of production nodes by rolling-replace with image version, observe, then increment per policy.
8) Full promotion: once canary passes all gates, merge and apply across remaining nodes by region.

Detailed Canary Strategy
------------------------
- Canary cohorts: small subsets selected by label: role=worker-gpu and tag=canary-eligible. Prefer underutilized availability zones.
- Canary size progression: 1% -> 2.5% -> 5% -> 10% (each step minimum observation window 30–120 minutes depending on workload).
- Safety windows: if any critical alert fires (see alert list), immediate pause and rollback.
- Auto-rollback policy: CI job sets canary TTL; if failing thresholds are met, automation triggers Terraform to revert changed instances or triggers node replace with previous image.

Automated Gates and Tests
-------------------------
Automated gates run in CI/CD and during canary:
- Driver sanity: nvidia-smi returns expected GPU list and driver version.
- NVML memory test: allocate & release 90% of a test device repeatedly.
- Model inference smoke: run 5 end-to-end small samples through locally-deployed model server and validate outputs against golden set.
- Kernel oops regression scan: kernel message buffer scanned for new oops/panic line patterns post-boot.
- Boot time and readiness: node must register with k8s within 4 minutes and pass node-exporter liveness.

Example CI job snippets
-----------------------
YAML for promote job (simplified):

  jobs:
    build-image:
      steps: [checkout, build, unit-tests, publish-artifact]
    image-integration-tests:
      steps: [spin-gpu, install-image, run-nvml-tests, run-smoke]
    promote-to-staging:
      steps: [register-release, tag-image, notify-team]
    kick-canary:
      steps: [terraform-plan-canary, terraform-apply-canary, monitor-canary]

Terraform and IaC interactions
-----------------------------
- Image metadata: every image must have tags: image_version, build_id, sha256, built_by, base_os. These are written to SSM/ParameterStore and the artifact registry.
- Promotion process: CI writes a release JSON to a central S3 bucket: release-(image_version).json. A Terraform data source in infra modules reads the release JSON to populate image IDs for Terraform plan.
- Immutable references: production Terraform state must reference immutable image IDs (AMI_ID or digest). Avoid referencing mutable tags for production pools.

Configuration table (required fields)
------------------------------------
| field | purpose | example |
| image_version | human-readable version | v2025.01.09-rc1 |
| image_digest | immutable image digest | sha256:abcdef... |
| build_id | CI build identifier | circleci/12345 |
| canary_window_minutes | observation window per step | 60 |
| canary_cohort_label | node label used to select canary nodes | canary-eligible=true |
| rollback_thresholds | thresholds causing rollback | cpu_err_rate>0.5% or gpu_oops=true |

Metrics and SLOs to watch during canary
--------------------------------------
- Node registration latency: target < 4 minutes.
- GPU driver error-rate (rate of nvml/device-failure logs): target < 0.01% per minute.
- Inference p50/p95 latency vs baseline: p95 must not regress more than 15%.
- Scheduler pod eviction rates and OOM events: zero tolerated for canary cohort.
- Cost anomalies: unexpected GPU-hours spike -> pause rollout.

Alert list (examples)
---------------------
- GPU_DRIVER_CRIT: nvml errors >= 5 within 10m in canary cohort.
- NODE_UNREGISTERED: node fails to register within 6m post-boot.
- INFERENCE_REGRESSION: p95 latency > 15% vs baseline or error rate increases by +0.5%.
- KERNEL_OOPS_DETECTED: new oops lines matching regex in syslog.

Manual checkpoints and approvals
-------------------------------
- Promotion from QA -> Production requires at least one on-call sign-off and documentation that all automated gates passed.
- For Private/Customer-dedicated clusters, Customer Success must consent to image changes that affect underlying runtime.

Runbook: Rapid rollback (step-by-step)
-------------------------------------
1) Pause pipeline: cancel further Terraform applies and stop CI promote jobs.
2) Isolate canary cohort: taint node pools or cordon nodes to avoid scheduling.
3) Trigger rollback job: CI invokes terraform apply with previous immutable image id.
4) Monitor: watch node registration and key alerts for 30 minutes.
5) Postmortem: collect boot logs, dmesg, journalctl, driver logs, and attach to incident ticket.

Ownership and escalation
------------------------
- Owners: Infra - GPU Platform team (primary), SRE on-call (secondary).
- Pager escalation: 20 min internal response SLA for canary-critical alerts.
- Post-incident: GPU Platform lead owns the postmortem within 5 business days.

Appendix A: Validation checklist (pre-promotion)
------------------------------------------------
- [ ] Release JSON exists and is signed in S3.
- [ ] Integration tests pass (exit code 0).
- [ ] Canary cohort label applied and nodes available.
- [ ] Observability dashboards added to runbook view.
- [ ] Terraform plan reviewed and MR opened with canary policy.

Appendix B: Example troubleshooting commands
-------------------------------------------
- Check driver: ssh node && sudo nvidia-smi -q
- Check node join logs: kubectl describe node <node>
- Inspect kernel messages: journalctl -k -b | tail -n 200
- Re-image single node: terraform taint module.node_pool.aws_instance.example[3] && terraform apply -target=module.node_pool.aws_instance.example[3]

Appendix C: Frequently asked questions
-------------------------------------
Q: Why use immutable image ids for production?
A: Prevents accidental drift, simplifies rollback, and makes audits reproducible.

Q: What if a canary fails intermittently across regions?
A: Pause global rollouts and split by region; diagnose base OS/driver combo differences using the compatibility matrix in team wiki.
