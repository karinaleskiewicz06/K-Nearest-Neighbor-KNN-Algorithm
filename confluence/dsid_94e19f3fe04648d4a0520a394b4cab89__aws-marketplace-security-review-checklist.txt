AWS Marketplace Security Review Checklist (Sales Enablement)

## Purpose
This page is the field-ready checklist and FAQ for answering common security/compliance questions during **AWS Marketplace** evaluations (e.g., SOC 2, encryption/KMS, audit logging, data retention, residency).

It is written to help AEs/SEs run a consistent security review call and to ensure we send the exact follow-up artifacts customers and AWS reviewers ask for.

---

## Quick talk track (use on calls)
- Redwood supports AWS Marketplace procurement; the **commercial wrapper changes**, but customers still receive a Redwood org/tenant with standard enterprise controls.
- We maintain a **SOC 2 Type II** report (NDA-gated). We provide a **marketplace security packet** (architecture + data flow + encryption + logging + shared responsibility).
- We separate retention into three categories: **(1) request/response payloads**, **(2) operational metadata/metrics**, **(3) audit logs**. These have different defaults and knobs.
- For encryption: **TLS in transit**, **encryption at rest**, and **KMS/CMK options differ by deployment mode** (Hosted vs Dedicated vs Private).

---

## Before the call: minimum discovery questions
1) **Deployment mode target** (and acceptable interim): Hosted via Marketplace, Dedicated, or Private/VPC.
2) **Regions/residency** requirements (US-only, EU, multi-region, any restrictions on cross-region processing).
3) Whether they will send **regulated/customer data** in prompts/outputs.
4) Their “must-have” controls: CMK, SSO/SAML, RBAC, audit export to SIEM, retention caps, private connectivity.
5) Procurement constraints: **AWS Marketplace only**? private offer required?

---

## What to send after the call (standard follow-up packet)
Send these within **2 business days**.

1) **SOC 2 Type II access instructions** (portal, NDA-gated)
- Include: access steps, named-user policy, and (if requested) a **bridge letter** when their auditor requires it.
- Do **not** email the full SOC report as an attachment.

2) **AWS Marketplace Security Packet index**
Include links to:
- High-level architecture and **data flow diagram**
- Encryption overview (in transit / at rest)
- Data handling and retention statement
- Audit logging overview + export methods
- Shared responsibility matrix (Hosted vs Dedicated vs Private)
- Subprocessors list

3) **Retention defaults (exact days) + configurable ranges**
Provide the values below (keep them verbatim unless Security/Compliance updates them).

4) **Audit log event taxonomy + sample exports**
- Include a sample CSV and JSON line example, plus field definitions.

5) **KMS/CMK support matrix by deployment mode**
- Include the current “supported today” statement (see below) and any constraints by Marketplace SKU.

6) **Cross-region behavior statement**
- Confirm that cross-region fallback is **off by default** and only occurs if explicitly enabled.

## Data handling & retention (what to say + what to put in writing)
### Content usage
- By default, Redwood does **not** use customer prompts/outputs to train foundation models.
- Customer content is not shared across tenants.

### Payload storage (prompts/outputs)
**Default (Hosted, Marketplace):** payload logging is **OFF**.
- When OFF: prompts/outputs are processed to generate a response and are not retained as stored request/response bodies (beyond transient processing).
- Customers can enforce payload logging OFF **org-wide** via admin policy.

**If customer enables payload logging / request sampling:**
- Default retention: **7 days**
- Configurable range: **0–30 days** (including immediate expiry/disable)
- Optional redaction: available for configured fields before storage.

### Operational metadata / metrics (non-payload)
- Examples: latency, token counts, error codes, request IDs, model/version identifiers.
- Default retention: **30 days**
- Configurable range: **7–90 days** (plan-dependent)

### Audit logs (customer admin/control plane events)
- Default retention: **365 days**
- Configurable retention: **365 days (default) up to 7 years** (enterprise option)

### Deletion & backups (how to answer)
- If payload logging is OFF, there is no persisted payload content to delete (beyond transient processing).
- If payload logging is enabled, stored artifacts expire per retention; deletion requests can remove stored samples sooner.
- Backups are encrypted and lifecycle-managed; deletion/retention statements describe backup interaction at a high level (we do not provide backup internals).

## Encryption & key management (KMS/CMK) — current support
### In transit
- TLS **1.2+** (TLS 1.3 supported where available).

### At rest
- Data stored in Redwood-managed systems is encrypted at rest (cloud KMS-backed encryption).

### Customer-managed keys (CMK) support by deployment mode
Use this table language in emails. If a customer asks for “auditor-grade” clarity, paste this section.

**Hosted API (via AWS Marketplace)**
- At-rest encryption: **Redwood-managed KMS keys**
- CMK: **Not supported** for the multi-tenant Hosted Marketplace offering today.
- Mitigation: keep payload logging OFF; sensitivity is primarily in metadata/audit/config artifacts.

**Dedicated (single-tenant compute)**
- Option A (most common): Dedicated in Redwood-managed cloud account
  - At-rest encryption: Redwood-managed KMS
  - CMK: **Supported via customer-provided AWS KMS key** using cross-account grants (availability is region/offer dependent)
- Option B: Dedicated in customer AWS account (where applicable)
  - At-rest encryption: customer-controlled
  - CMK: **Supported** (customer owns keys and policies)

**Private/VPC deployment**
- Runs in customer-controlled environment/VPC.
- CMK: **Supported** (customer-owned KMS/HSM; customer-defined key policies).

**Important notes**
- CMK availability can vary by Marketplace SKU/offer type and region. If a customer requires CMK, confirm SKU feasibility with Solutions Engineering + Security/Compliance before committing.

## Residency & cross-region processing
### Hosted region selection
- Customers select a region endpoint; inference processing occurs in that region.
- Supported Marketplace regions (as of 2026-03-10): **us-east-1, us-west-2, eu-west-1**.

### Cross-region fallback
- Default: **OFF**.
- If enabled: requests may fail over cross-region based on customer policy.

### Control plane “global” data (how to phrase)
- Some account-level data (e.g., billing records, user identity/email, entitlement/provisioning records) may be stored/processed in globally operated control plane systems.
- Prompt/response payloads follow the selected endpoint region (and are not persisted by default).

## Audit logging (what customers ask for)
### What is logged (customer-facing)
Typical customer-facing audit events include:
- Authentication events (login/SSO enforcement changes)
- User invites, user deactivation
- Role/RBAC changes
- API key create/revoke
- Org/workspace settings changes
- Retention policy changes
- Model/deployment configuration changes (where applicable)
- Marketplace entitlement/provisioning events (subscription validation and org provisioning actions)

### Export options (customer SIEM)
Supported export patterns:
- API pull (customer pulls audit events)
- Scheduled export to **S3** (preferred for AWS-native workflows)
- Forwarding to **Splunk** (HEC) via customer-managed connector

### Immutability
- Audit events are append-only from a customer perspective (no edit capabilities).
- For stronger immutability guarantees, recommend exporting to the customer SIEM/object storage with their own WORM/immutability controls.

### Employee access logs (common question)
- Redwood logs internal access to production systems and reviews access under least privilege controls.
- We do **not** stream raw employee access logs to customers.
- Evidence is provided via SOC 2 controls/testing and the evidence pack.

## SOC 2 / ISO questions (script-ready)
- Redwood maintains a **SOC 2 Type II** report.
- We can share the report via secure portal after NDA.
- We maintain an internal control mapping aligned to ISO 27001-style control families; this is **alignment/mapping**, not an ISO certification claim.

## SSO, MFA, RBAC (standard answers)
- SSO/SAML supported for enterprise plans; customers can enforce SSO and block password login.
- MFA is supported and can be enforced (SSO typically inherits customer IdP MFA policies).
- RBAC is supported; role changes are auditable.

## Field checklist: customer questionnaire “hot items” (copy/paste)
- TLS version: TLS 1.2+.
- At-rest encryption: yes (KMS-backed).
- CMK: Hosted Marketplace = not supported; Dedicated/Private = supported (see matrix).
- Audit logs: admin/control plane events; export to S3/API; 365-day default retention.
- Data retention: payload logging OFF by default; if enabled 7-day default, configurable 0–30 days.
- Residency: region endpoint processing; cross-region fallback OFF by default.
- Training: no training on customer prompts/outputs by default.
- Evidence: SOC 2 Type II via portal; bridge letter as needed; subprocessors list available.
