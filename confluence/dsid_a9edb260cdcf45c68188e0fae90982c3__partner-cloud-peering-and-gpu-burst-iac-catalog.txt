partner-cloud-peering-and-gpu-burst-iac-catalog

Summary:

This document describes Redwood Inference’s recommended pattern for brokered GPU bursting into partner or cloud provider accounts via transit peering, NAT gateways, and a small set of reusable Terraform modules. It is intended for infra engineers setting up short-lived, auditable GPU capacity expansions (preemptible/spot) without exposing tenant networks or credentials.

Goals:
- Enable rapid, automated bursting to partner or second‑cloud GPU pools with predictable networking and observability.
- Maintain strong isolation: no cross-tenant L3 routing except proxy/NAT; all control plane operations use cross-account IAM roles and short-lived credentials.
- Provide reusable IaC modules and CI/CD patterns for deploy/test/rollback.
- Define runbook steps and SLOs for failed bursts, network flaps, and credential revocation.

Non-goals:
- Replacing existing Dedicated pools for long-running reserved workloads.
- Full multi-tenant transit fabrics (this pattern is bridging for controlled bursts only).

Background and motivation:

We periodically need extra GPU capacity to absorb eval runs, scheduled heavy inference loads, or to run temporally-limited promotions. Buying permanent reserved capacity in multiple clouds increases cost and complexity. Bursting to partner clouds or separate provider accounts allows cost-efficient scaling, but introduces networking, security, and auditing challenges. This pattern standardizes the architecture to reduce operational risk.

High-level architecture:

- Control plane lives in Redwood-root account. Burst requests create ephemeral worker pools in partner accounts.
- A transit peering (provider-specific: VPC Peering, Transit Gateway, or Shared VPC) is established per partner on a pinned /22 (or smaller for single-tenant partners) that is only used for control-plane egress and observability streams.
- Data-plane inference requests use outbound NAT/proxy through a dedicated egress subnetwork; no inbound routes to Redwood private subnets are added in partner accounts.
- Centralized logging & metrics use a secure forwarder (TLS + mTLS) over the transit link.

Design details and constraints:

- Network isolation: Partner subnets are segmented. Only the following flows are allowed:
  - Control plane (HTTPS) from Redwood control IPs to worker management endpoints (port 443).
  - Metrics/log forwarder (TCP 1514 or 443) to central endpoints.
  - Egress-only traffic from worker VMs to customer-facing NAT addresses when required; inbound from customer networks is blocked.

- Security: Use cross-account roles with short-lived STS tokens. All IaC changes require PR review and signed commits for partner onboarding. KMS keys for dataset encryption live in the partner account when required by contract.

- IP addressing: Reserve a /22 per partner pool to avoid overlapping with customer IPs; document the allocation in partner onboarding sheet.

Minimal Terraform example (AWS-style) - skeleton:

```hcl
module "partner_transit" {
  source = "git::ssh://git.internal/redwood/iac/modules//partner-transit-attachment"
  provider = aws.partner
  partner_account_id = var.partner_account_id
  peer_vpc_cidr = var.peer_vpc_cidr
  transit_gw_id = data.aws_ec2_transit_gateway.main.id
}

module "partner_workers" {
  source = "git::ssh://git.internal/redwood/iac/modules//partner-gpu-worker-set"
  provider = aws.partner
  worker_count_min = 0
  worker_count_max = var.burst_max
  instance_type = var.preferred_gpu_instance
  image_id = var.gpu_worker_image
}
```

CI/CD and testing patterns:

- Repo organization: store modules in monorepo under infra/modules/partner-*. Each module has its own terratest folder.
- Pull request gates: 
  1) terraform fmt and validate
  2) static security scan (tfsec, checkov)
  3) unit-style terratest integration in a sandbox account (creates a tiny set of resources, verifies route tables and IAM roles)
  4) canary deploy: staged apply in a disposable partner sandbox account, then staged apply to real partner account with manual approval.
- Secrets and credentials: use short‑lived CI roles via OIDC rather than long-lived cloud keys. All secrets used by staging runs are ephemeral.

Observability and SLOs:

- Network SLO for bursts: 99% of worker control-plane operations (bootstrap/signaling) succeed within 30s during a burst ramp phase (first 300s after request).
- Logging latency: 95% of logs forwarded to central logging appear within 45s.
- Cost guardrail: Auto-shutdown if average per-GPU hourly spend exceeds configured threshold for the burst tag.

Runbook: Burst failure and network flap (short checklist)

1) Detect: Alert fires when >20% of new workers fail bootstrap or transit attachment status = pending for >2m. Alert routed to infra-oncall and partner-ops.
2) Immediate mitigation (first 10 minutes):
   - Confirm control-plane role STS tokens are valid: CLI example (AWS):
     aws sts assume-role --role-arn arn:aws:iam::PARTNER:role/redwood-burst-role --role-session-name check --external-id "PARTNER_EXTERNAL"
   - Check transit attachment status:
     aws ec2 describe-transit-gateway-attachments --filters Name=resource-id,Values=<attachment-id>
   - If attachment is DOWN, run attachment repair script: infra/scripts/repair-transit-attachment.sh <attachment-id> (this script retries re-association and re-creates missing route propagation).
3) Fallback: If transit attachments cannot be repaired within 12 minutes, trigger fallback to alternate partner or to Redwood-hosted burst pool (policy: ttl-based retry with exponential backoff).
4) Post-incident: Collect: VPC flow logs, control-plane audit logs, worker bootstrap logs, terraform state from workspace; open an incident with severity "S2 Burst Impact" if >30% job failure.

Troubleshooting (common symptoms):

- Symptom: Workers boot but cannot reach central metrics endpoint.
  - Verify security groups/NACLs allow outbound to metrics endpoint (TCP 1514/443).
  - Verify NAT rule and egress IP pool has entries in partner firewall whitelist.

- Symptom: Transit attachment shows "associated" but no routes propagated.
  - Check route table propagation; run terraform state show to confirm. On AWS, re-enable route propagation on the route table and re-run a small apply of partner-transit-attachment module.

Ownership and contacts:

- Primary owner: infra-networking team (triage inbox: infra-networking@redwood.ai).

- Partner onboarding: Private Deployments / Eng Private Deployments PMs handle contract and KMS decisions.

Onboarding checklist for a new partner:

1) Legal/Contract signoff with data residency and KMS responsibilities.
2) Assign partner /22 and register in partner-ip-alloc spreadsheet.
3) Create cross-account role and share external_id.
4) Run terraform apply in partner sandbox using the partner modules with 1-2 workers and verify egress/logging.
5) Complete security review: tfsec findings addressed, KMS key policies confirmed.
6) Schedule live burst smoke test (with traffic mirrors enabled).

Rollout plan for IaC module improvements:

- Phase 1: Unit tests and tfsec checks in PR.
- Phase 2: Integration test in partner-sandbox account via CI (automatic).
- Phase 3: Gradual rollout: enable feature flag and run 3 small bursts across 3 partners over 2 weeks.
- Phase 4: Post-rollback window of 48 hours with additional logging.
