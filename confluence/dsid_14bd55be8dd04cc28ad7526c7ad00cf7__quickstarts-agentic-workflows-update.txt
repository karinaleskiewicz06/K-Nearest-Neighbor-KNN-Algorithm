Quickstarts Update Spec: Agentic Workflows (Streaming + Tool Calling + Structured Output)

## Purpose
This document specifies the refresh to Redwood Inference quickstarts/templates to ensure every “agentic workflow” starter demonstrates the current best-practice interface for:
- Streaming responses (consistent event model + delta assembly)
- Function/tool calling (single + parallel tool calls + tool-result messages)
- Structured output (JSON schema-constrained output + validation + safe retry)

The deliverable is a set of quickstarts that are:
- Copy/paste runnable end-to-end
- Consistent across Python/TypeScript/Go
- Explicit about environment variables, model selection, and failure handling

## Non-goals
- Introducing new API semantics beyond existing streaming/tool calling/structured output behavior
- Building a full agent framework or long-lived state store
- Adding complex hosting/deploy infrastructure (these remain local-first quickstarts)

## Repositories and target locations
- Repo: `redwood-quickstarts`
  - `templates/agentic-workflows/node/`
  - `templates/agentic-workflows/python/`
  - `templates/agentic-workflows/go/`
- Repo: `redwood-docs` (links and “Next steps” blocks only; canonical docs live there)

## Canonical behavior requirements (applies to all templates)
### 1) Streaming (event model)
Templates MUST follow the event conventions described in `streaming-event-model-conventions`.

Implementation requirements:
- Maintain an accumulator for assistant text deltas.
- Treat tool-call arguments as potentially partial during streaming.
- Only parse/validate tool arguments and structured JSON when the SDK signals the tool call / message is complete.
- Handle and log disconnects with a single retry strategy that is safe by default.

Minimum logging (stdout):
- Request ID (if available from SDK)
- Model name
- Stream lifecycle: start → tool_call (if any) → tool_result → final_message
- Any retry occurrence including the reason (disconnect vs validation failure)

### 2) Tool calling
Templates MUST demonstrate:
- Defining tools with names + JSON schema for arguments
- Handling one tool call and one parallel tool call
- Sending tool results back as tool-result messages
- A bounded loop (max tool turns) to avoid infinite cycles

Required guardrails:
- Validate tool arguments against schema before executing.
- Time-bound tool execution with a per-tool timeout.
- Never execute unknown tools (explicit allow-list).

### 3) Structured output
Templates MUST demonstrate:
- Providing a JSON schema for the model output
- Validating the final JSON against the schema (after the model completes)
- A safe fallback when validation fails:
  - 1 automatic retry with a “repair” instruction OR
  - degrade to non-structured output and display raw text with an explicit warning

Important: streaming + structured output should not rely on incremental JSON parsing. Validation should happen on the final assembled message.

## Template inventory and what changes
The following templates will be updated/added under `templates/agentic-workflows/*`.

### A) Template: “Support Triage Agent” (primary agentic workflow)
Goal: Demonstrate a realistic multi-step agent loop that uses tools and produces schema-constrained output.

**Languages:** Node (TypeScript), Python, Go

**Tools demonstrated (minimum):**
- `search_knowledge_base(query: string) -> { results: [{ title, url, snippet }] }`
- `create_ticket(subject: string, description: string, severity: "low"|"medium"|"high") -> { ticket_id: string }`

**Structured output schema:**
- Final output must be a JSON object containing:
  - `summary` (string)
  - `customer_impact` (string)
  - `probable_root_causes` (array of strings)
  - `recommended_next_steps` (array of strings)
  - `ticket_to_create` (object with `subject`, `description`, `severity`) OR `null`

**Parallel tool calling requirement:**
- The agent should be able to call `search_knowledge_base` twice in parallel with two different queries (e.g., error message + product area).

### B) Template: “Data Enrichment Agent” (tool calling + structured output, minimal streaming)
Goal: Show the simplest tool-call → tool-result → schema-constrained summary flow.

**Languages:** Node (TypeScript), Python

**Tools demonstrated (minimum):**
- `lookup_company(domain: string) -> { name, industry, size, notes }`

**Structured output schema:**
- `company_brief` (string)
- `risk_flags` (array of strings)
- `follow_up_questions` (array of strings)

**Streaming requirement:**
- Streaming is enabled and displayed, but the template keeps the UI minimal (console-only). This template is explicitly positioned as the “hello world” for tools + schema.

### C) Template: “Meeting Notes to Action Items” (structured output focus)
Goal: Show robust schema validation, failure modes, and repair retry.

**Languages:** Node (TypeScript), Python, Go

**Tools demonstrated:**
- None required (this template is structured-output-only), but SHOULD include a commented “optional tool calling extension” block.

**Structured output schema:**
- `title` (string)
- `attendees` (array of strings)
- `decisions` (array of strings)
- `action_items` (array of objects: `owner`, `task`, `due_date` (ISO date string or ""))

**Validation behavior:**
- If JSON is invalid or fails schema: print a clear error, run one repair retry, then exit non-zero if still invalid.

## Required environment variables and configuration
All templates MUST document environment variables in the template README and provide `.env.example`.

### Common environment variables (all templates)
| Variable | Required | Default | Notes |
|---|---:|---|---|
| `REDWOOD_API_KEY` | Yes | (none) | API key with Hosted API access. |
| `REDWOOD_BASE_URL` | No | `https://api.redwoodinference.com` | Support staging via alternate URL. |
| `REDWOOD_MODEL` | No | language-specific default (see below) | Used for chat/generation + tool calling. |
| `REDWOOD_TIMEOUT_MS` | No | `60000` | Overall request timeout. |
| `REDWOOD_MAX_TOOL_TURNS` | No | `4` | Hard cap to prevent infinite tool loops. |
| `LOG_LEVEL` | No | `info` | `debug` enables event-level logging. |

### Template-specific environment variables
**Support Triage Agent**
| Variable | Required | Default | Notes |
|---|---:|---|---|
| `KB_SOURCE` | No | `local` | `local` uses bundled fixtures; `remote` calls a sample endpoint. |
| `TICKETING_MODE` | No | `dry_run` | `dry_run` prints ticket payload; `create` performs the call (still mocked by default). |
| `TOOL_TIMEOUT_MS` | No | `5000` | Tool execution timeout. |

**Data Enrichment Agent**
| Variable | Required | Default | Notes |
|---|---:|---|---|
| `ENRICHMENT_DATASET` | No | `sample` | `sample` uses a local JSON file of company records. |

**Meeting Notes to Action Items**
| Variable | Required | Default | Notes |
|---|---:|---|---|
| `NOTES_FILE` | No | `./sample-notes.txt` | Input text file path. |
| `SCHEMA_STRICT` | No | `true` | If `false`, accepts best-effort JSON but still warns. |

### Model defaults and compatibility notes
Each template README MUST:
- Name a default model known to support tool calling and structured output well.
- Provide a “If you see tool-call/JSON issues” troubleshooting block pointing to the Known Pitfalls section in docs.

Recommended defaults (subject to PM support matrix language):
- `REDWOOD_MODEL` default: `redwood/atlas-instruct` (or current recommended tool-capable instruct model)

If a model does not reliably support schema-constrained output:
- Template must still run, but should switch to “repair retry + degrade to text” mode and explicitly log that structured guarantees are model-dependent.

## Expected outputs (what the user should see)
All templates MUST include a README section titled “Expected output” showing representative console output.

### Example: Support Triage Agent (abridged)
1) The user sees streaming tokens for the assistant’s thought process (user-facing explanation only; no private chain-of-thought).
2) The user sees tool call(s) and tool results logged.
3) The final line prints validated JSON.

Representative output:
- `Streaming started (model=redwood/atlas-instruct, request_id=...)`
- `tool_call: search_knowledge_base {"query":"..."}`
- `tool_call: search_knowledge_base {"query":"..."} (parallel)`
- `tool_result: search_knowledge_base (2 results)`
- `tool_result: search_knowledge_base (3 results)`
- `tool_call: create_ticket {"subject":"...","severity":"high",...}` (or `dry_run`)
- `Final (validated JSON): { ... }`

### Example: Meeting Notes → Action Items
- `Loaded notes from ./sample-notes.txt`
- `Structured output validation: OK`
- `Action items: 5`
- `Wrote ./out/action-items.json`

If invalid JSON:
- `Structured output validation: FAILED (missing required field: action_items)`
- `Attempting one repair retry...`
- `Structured output validation: OK`

## README requirements (per template)
Each template README MUST include:
1) Prerequisites
- Runtime version (Node/Python/Go)
- How to obtain/set `REDWOOD_API_KEY`

2) Setup
- `cp .env.example .env`
- Install steps (package manager commands)

3) Run
- One command to run (plus alternates)

4) Expected output
- Representative output snippet (see above)

5) Troubleshooting (minimum set)
- Streaming disconnects: how to rerun, what logs show, retry behavior
- Partial tool args: expected during streaming; only parse on completion
- Structured JSON errors: schema validation + repair retry behavior
- OpenAI-compat differences: link to compat notes if applicable

## SDK version pinning and compatibility
Quickstarts must not depend on unreleased SDK APIs.

Each template will pin/validate minimum SDK versions known to support the canonical examples:
- Python: `redwood-sdk>=0.14.0` (placeholder; align to released version during rollout)
- TypeScript: `@redwood/sdk>=0.18.0`
- Go: `github.com/redwoodinference/redwood-sdk-go >= v0.9.0`

Notes:
- If exact versions differ at release time, update `.tool-versions`/package files and READMEs together.
- If a template includes a workaround for older SDKs, it MUST be clearly labeled as “Legacy behavior” and placed at the bottom of the README.

## Smoke tests (definition of done)
Each template MUST have a documented smoke test and a CI-friendly mode using local fixtures (no external dependencies besides Redwood API).

### Required smoke test steps
- Ensure `.env` contains `REDWOOD_API_KEY` (and optionally `REDWOOD_BASE_URL`).
- Run the template command.
- Confirm:
  - Exit code is 0
  - For tool templates: at least one tool call + tool result is observed
  - For structured output templates: schema validation passes and JSON is written/printed

### CI mode requirements
- A “fixtures only” mode MUST exist to avoid flakiness:
  - Tools operate on local fixture data
  - The prompt input is deterministic
- Where the model output is non-deterministic, tests should validate:
  - Output parses as JSON
  - Required fields exist and types match schema
  - No forbidden extra fields (if strict)
