GPU CI/CD: Quarantine lane and Fast-Forward Promotion

Summary:
This document describes the GPU-focused CI/CD quarantine lane and a controlled fast-forward promotion path for GPU runtime artifacts (images, kernels, quantized model packages and scheduler plugins). The goal is to reduce production regressions caused by binary/kernel mismatches, scheduling regressions, and quantization/perf regressions while preserving high velocity for safe releases.

Why this exists:
- GPU artifacts have a higher blast radius (hot thermal/power issues, device driver incompatibilities, runtime OOMs).
- Standard CI pass is insufficient: artifacts can pass unit tests but fail at scale or under heterogeneous hardware.
- We need an automated quarantine lane with deterministic simulation, per-tenant smoke checks, and a documented fast-forward path for low-risk artifacts.

Scope:
- Applies to artifacts produced by the GPU build pipeline: runtime images (gpu-runtime:*), quantized-model bundles (qmodel-*.tar.gz), kernel libraries (libkern-*), and GPU operator plugins.
- Integrations: Buildkite pipeline (gpu-build-runner), Registry (private-artifacts.redwood.ai), Terraform/IaC modules (gpu-warmpool-module), and Canary traffic orchestrator (burst-orchestrator).
- Excludes unrelated non-GPU services.

Goals and success metrics:
- Reduce production L3 incidents caused by new GPU artifacts by 70% compared to 2025 baseline.
- Surface regressions during quarantine before any tenant receives traffic (target detection rate >= 95%).
- Median time to promote a low-risk artifact via fast-forward <= 2 hours (automated path).

High-level design:
1) Standard CI produces artifact and a metadata bundle (SHA, image:tag, kernel-version, supported-GPUs, quantization-profile).
2) Artifact enters the Quarantine Lane where a matrix of simulated workloads run in an isolated ephemeral cluster (quarantine-grid) across representative hardware (A100, H100, L4).
3) Automated gates: perf regression tests, KV cache correctness, OOM/leak detection, driver compatibility checks, and infrastructure smoke tests (egress, logging).
4) If quarantine passes, artifact becomes eligible for Fast-Forward Promotion. If it fails, artifact is quarantined for triage with auto-created issue and retained logs.

Quarantine matrix (default):
- Hardware: A100-40GB, H100-80GB, L4-32GB (one node each)
- Workloads: short-chat (latency), long-infer (tokens>=2k), batch-embed (throughput), kv-cache-replay (session-resume)
- Duration: 30m per workload per hardware
- Parallelism: up to 6 simulations concurrently per artifact

Automated gate thresholds (must all pass):
- Latency P95 increase <= 8% vs baseline artifact
- Token-per-dollar change <= 12% (cost regression)
- No sustained GPU memory growth > 3%/min for 10 consecutive minutes
- > 99% KV cache hit parity with baseline test corpus
- No driver-level errors logged (nvml, dmesg) more than 3 entries in 30 minutes

Pipeline stages (concrete):
- build: compile artifacts, produce image and metadata JSON (artifact-metadata.json)
- unit tests: standard unit and integration tests in Buildkite stage 'unit-gpu'
- quarantine: run quarantine-grid job (agent: quarantine-runner). This job provisions an ephemeral cluster using terraform apply --target=module.quarantine_grid && uses gpu-warmpool-module to allocate nodes.
- quarantine-eval: run perf harness (tools/inference-harness) and collect telemetry to quarantine-bucket (gs://redwood-quarantine/${artifact_sha})
- triage-or-promote: automatic decision function (triage-bot) marks the artifact as 'eligible' or 'quarantine-failed' in Registry UI

Fast-Forward Promotion paths:
A) Automated Fast-Forward (no human step) - Criteria:
  - Quarantine: all automated gates green
  - Canary window: small synthetic canary in staging cluster for 20 minutes with production-like metadata
  - No regressions in canary metrics (95th latency, error-rate, GPU-thermal events)
  - Security scan: SCA and SBOM checks passed
  - Ownership: owner_team automated approval (owner-team configured in artifact-metadata.json)

  Steps (automated):
  1) triage-bot sets artifact status -> eligible/ff-auto
  2) pipeline triggers terraform plan and terraform apply against canary workspace: terraform workspace select canary && terraform apply -var artifact_sha=... -auto-approve
  3) burst-orchestrator shifts 1% of synthetic traffic for 20m; telemetry flows to quarantine-bucket
  4) If canary pass -> promotion job tags image:promoted and triggers a gradual rollout policy (see rollout policy below)

B) Human-mediated Fast-Forward - Use when artifact is low-risk but automated gates inconclusive or when owner requests manual QA. Requires two approvers: build-owner + infra-oncall. Triage ticket created with attached logs and replay commands.

Rollout policy (post-promotion):
- Stage 0: promoted -> shadow for 1% production traffic (1h)
- Stage 1: 5% (3h)
- Stage 2: 20% (6h)
- Stage 3: 100% (24h)

Automatic rollback triggers (if any stage exceeds thresholds):
- Error-rate > 1% absolute increase vs baseline for the stage window
- Latency P95 increase > 25% absolute
- GPU OOMs or driver faults > 0.1% of requests
- Alert from SRE (pager duty)

Runbook: Quarantine failure triage (high level)
1) triage-bot creates issue in Sentry/Backlog and posts Slack in #gpu-quarantine with artifact metadata and link to bucket.
2) First responder: owner_team (defined in metadata) acknowledges ticket within 30m.
3) Capture golden-traffic replay: run tools/inference-harness --replay gs://redwood-quarantine/${artifact_sha}/trace.json --compare baseline_trace.json
4) If regression is isolated to model bundle vs runtime, tag artifact as 'model-only-fix' and notify MLOps.
5) If regression is runtime/kernel, escalate to Runtime team and file a kernel-bisect run (link to kernel-bisect job).
6) If fix needs image rebuild, block matching releases and set embargo flag in Registry until a new candidate passes quarantine.

Terraform / IaC considerations:
- Quarantine grid is provisioned by module: module.quarantine_grid from modules/gpu/quarantine_grid (see example usage). Keep module inputs minimal: supported_gpus, test_user_count, region.
- Warmpool usage: module.gpu_warmpool accepts lease=ephemeral and ttl_minutes=90. Use spot pools with fallback to ondemand when required: allow_spot_fallback=true.
- State handling: quarantine workspaces are ephemeral and use a dedicated remote state bucket: gs://redwood-iac-quarantine-{env} with lifecycle rule to remove state after 7 days.

Example Terraform snippet (ci integration):
```
module "quarantine_grid" {
  source = "git::ssh://git@repo.redwood.ai/modules/gpu/quarantine_grid.git//?ref=v1.3.0"
  supported_gpus = ["A100","H100","L4"]
  region = "us-west1"
  test_user_count = 12
}
```

CI snippet: Buildkite step for quarantine (example):
```
steps:
  - label: ":shield: quarantine"
    key: quarantine
    command:
      - scripts/ci/quarantine/run_quarantine.sh $BUILT_IMAGE $ARTIFACT_SHA
    agents:
      queue: quarantine-runner
    timeout_in_minutes: 60
```

Telemetry and data retention:
- Quarantine artifacts and logs are stored for 90 days in quarantine-bucket. Short-lived traces (heavy pcap/trace files) are archived to coldstore after 14 days.
- Telemetry schema: include artifact_sha, test_matrix, hardware_type, workload_name, measured_metrics. This must match the telemetry contract documented in eng-infra/runbooks/kv-cache-consensus-and-warmup-coordination-runbook (link).

SLOs and Alerts triggered during quarantine:
- Quarantine pipeline availability SLO: 99.5% monthly
- Quarantine-eval job success rate target: 98% (failures should be actionable)
- Alerts: Slack + PagerDuty if pipeline failures exceed 10% in an 1h window or any kernel-level faults are observed for two artifacts within 24h.

Operational roles and ownership:
- Pipeline owner: eng-infra-ci (pager rotation: eng-infra-ci-oncall)
- Runtime owner: serving-runtime
- MLOps owner (model bundles): applied-ml-and-evals
- Oncall escalation: eng-sre pager (primary) -> runtime (secondary)

Security and compliance notes:
- All quarantine clusters must run with restricted service accounts and no external egress except to telemetry sinks. KMS keys used to sign artifacts during promotion.
- SBOM and SCA scans run in the 'quarantine-eval' stage. Failure blocks promotion.

Appendix A: Quick commands for triage responders:
- Fetch logs: gsutil cp -r gs://redwood-quarantine/${artifact_sha} ./
- Replay trace (local): docker run --rm -v $(pwd):/data quay.io/redwood/inference-harness:latest replay --trace /data/trace.json --baseline /data/baseline.json
- Force re-run quarantine: ./scripts/ci/quarantine/trigger_quarantine.sh --artifact $ARTIFACT_SHA --force
