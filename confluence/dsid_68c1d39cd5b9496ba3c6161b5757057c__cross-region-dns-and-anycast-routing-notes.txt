Cross-Region DNS TTL + Anycast Routing Notes (Standards + Provider Behaviors)

## Purpose
This page documents Redwood Inference’s networking notes and operating standards for cross-region failover as it relates to:
- DNS TTL strategy (how quickly we can safely shift traffic via DNS)
- Anycast/edge routing behavior (what we can and cannot control)
- Practical constraints observed during real provider incidents

This is not a runbook. For operational steps during an event, see:
- Routing policy + failover controller: confluence://eng-platform/runbooks/routing-policy-failover-controller-runbook
- Hosted API on-call failover: confluence://eng-sre/runbooks/hosted-api-regional-failover-runbook

## Scope
Applies to:
- Hosted API global endpoints (customer traffic entering Redwood)
- Dedicated customer endpoints that use Redwood-managed DNS/edge (if applicable per contract)

Out of scope:
- Customer-managed DNS or customer-owned Anycast prefixes
- Private/on-prem deployments (see confluence://eng-private-deployments/day-2-ops/private-region-failover-guidance)

## Background: how traffic steering works at Redwood
Redwood uses multiple layers of steering; not all layers react at the same speed.

1) **Application routing (fastest, preferred)**
   - The smart routing layer and policy engine can shift traffic between regions using policy evaluation (seconds-scale) once the controller decides to act.
   - Controlled by the failover controller and guarded by ADR-042/ADR-043.

2) **Edge/load balancer behavior (fast but limited control)**
   - Managed load balancers and CDN/edge POPs can shift based on their own health checks and control planes.
   - Can be faster than DNS for some clients, but not deterministic across providers and client networks.

3) **DNS (slowest and least reliable during incidents, but still critical)**
   - DNS changes can redirect initial connection establishment but are bounded by TTLs, resolver caching, negative caching, and client connection reuse.
   - DNS is best treated as a “coarse steering” mechanism and as a recovery tool when application routing cannot be trusted (e.g., control plane partition).

## Standards (what we configure by default)
### Standard TTLs
We use TTLs that balance:
- Fast enough to support regional failover
- Stable enough to avoid resolver stampedes and excessive authoritative QPS
- Predictable enough for incident response and game days

**Default TTL targets:**

| Record category | Examples | Default TTL | Notes |
|---|---|---:|---|
| Global customer entry records | api.redwoodinference.com, *.api.redwoodinference.com | 60s | Primary steering should be via routing policy; DNS is fallback. |
| Regional endpoints (explicit) | us-east.api.redwoodinference.com | 300s | Regional endpoints are not expected to flap. |
| Control plane endpoints | console.redwoodinference.com, control.redwoodinference.com | 60–300s | Keep higher TTL if failover is not automated; coordinate with control plane SRE. |
| Internal service discovery (infra) | region-health-service, routing-controller | per platform standard | Not governed here; use platform service discovery guidance. |

**Important:** Some resolvers ignore TTLs (or clamp them). In practice, a “60s TTL” often behaves like 60s–10m depending on client networks and enterprise resolvers.

### TTL change management
Lowering TTLs is itself a production change and can cause load spikes at the authoritative layer.

Rules:
1) Avoid emergency TTL reductions during a live incident unless there is no alternative. TTL changes do not retroactively affect cached answers.
2) TTL reductions must be rolled out gradually (days) with authoritative QPS monitoring.
3) Any TTL below 30s requires explicit Infra approval (risk of resolver stampede + marginal real-world benefit).

Checklist for TTL reduction rollout:
- Confirm authoritative capacity and rate limits (including DDoS protections and query limits).
- Confirm monitoring: authoritative QPS, SERVFAIL rate, NXDOMAIN, and p95 DNS response latency.
- Roll out by zone / record group, not all-at-once.

## Anycast notes (what it is, what it isn’t)
### What Anycast gives us
Anycast (via CDN/edge or provider Anycast IPs) can:
- Improve latency by routing clients to a nearby POP
- Provide some resilience to POP-level failures
- Absorb volumetric attack traffic by distributing load

### What Anycast does NOT guarantee
Anycast does not guarantee deterministic region selection or fast, consistent failover behavior. In practice:
- BGP convergence can be slow or asymmetric
- Client ISP routing decisions vary widely
- During partial provider incidents, “closest POP” can be unhealthy while still receiving traffic
- Long-lived connections (HTTP/2, streaming, SSE) may not move until reconnect

Operational takeaway: **treat Anycast as an optimization layer, not the primary failover mechanism.** The primary mechanism remains application-level routing policy with clear guardrails.

## Known constraints during regional incidents
### 1) DNS propagation is not the limiting factor; resolver behavior is
Common behaviors observed in production:
- Some enterprise resolvers cache beyond TTL (intentional performance optimization).
- Some public resolvers clamp very low TTLs upward.
- Negative caching (SOA minimum / RFC 2308) can make “newly created records” slow to appear.

Implication: DNS changes are best at shifting new sessions over minutes, not seconds.

### 2) Connection reuse masks steering
Even if DNS changes quickly:
- Clients with keep-alives continue to send traffic over existing connections.
- Streaming responses (SSE) can keep a connection pinned to an impaired path.

Implication: to get real failover behavior, application routing and gateway behavior must:
- Support redirect / retry-after semantics
- Encourage client reconnect on specific errors
- Avoid aggressive retries that amplify overload during re-steering

(See also: gateway circuit breaker tuning and streaming reconnect work tracked under the Reliability Program.)

### 3) Provider health checks can fail “open”
During some provider outages:
- Health check control planes lag behind real data-plane impairment.
- Health checks themselves can be impacted (false negatives/positives).

Implication: We should not rely on a single provider health check product as the authoritative trigger. This is reflected in ADR-042 signal hierarchy.

### 4) Split-brain and partial reachability are common
We frequently see partial impairment patterns:
- Some ISPs cannot reach a region/POP while others can.
- IPv6 and IPv4 can diverge.
- Cross-region backbone issues can make “region looks healthy internally” while customer ingress fails.

Implication: reachability probes must be multi-vantage and must measure:
- External ingress reachability (from diverse networks)
- Cross-region connectivity (region-to-region)
- Control plane reachability

## Recommended record patterns
### Hosted API global entry
We standardize on:
- A/AAAA records for the global customer entrypoint (or provider-managed equivalents)
- Regional CNAMEs for explicit region endpoints
- Avoid “chains” longer than 2 records deep (CNAME->CNAME->A) to reduce resolver quirks during incidents

Example (illustrative):
- api.redwoodinference.com -> A/AAAA (edge Anycast VIP)
- us-east.api.redwoodinference.com -> CNAME us-east.edge.redwoodinference.com
- eu-west.api.redwoodinference.com -> CNAME eu-west.edge.redwoodinference.com

### Dedicated endpoints
Dedicated customer DNS patterns vary by contract and data residency requirements.

Standard guidance:
- Prefer customer-specific hostnames with explicit region naming when residency constraints exist.
- Do not enable cross-region CNAME failover for tenants with residency restrictions unless Security has signed off.
- Always maintain an “escape hatch” record or config that pins traffic to a single region if automation misbehaves.

Reference: confluence://security-and-compliance/incident-response-security/failover-and-security-boundaries

## DNS and traffic steering during a failover event
### What we expect to change during a failover
During a regional impairment, we typically do NOT change DNS as the first action.
Preferred sequence:
1) Failover controller flips routing policy for impacted routes/tiers (guardrails apply).
2) API gateway and runtime enforce overload behavior (retry-after, shedding) to prevent cascading overload.
3) Only if the impairment includes control plane/routing inability, consider DNS-level steering as a recovery tool.

### When DNS steering is appropriate
DNS-level steering is appropriate when:
- Control plane cannot safely evaluate or execute routing policy changes.
- A region is “blackholing” traffic at network level and we need to redirect new connections quickly.
- We are executing a planned, controlled test with explicit comms and rollback.

DNS steering is risky when:
- The incident is partial (some networks reach, some don’t) and DNS changes would move healthy clients unnecessarily.
- There is limited capacity in the target region; DNS can cause a large, poorly controlled surge.

## Provider-specific notes (observed behaviors)
These are operational notes, not guarantees. They are based on past incidents and game days.

### Managed DNS (general)
- Authoritative systems may rate-limit during bursts (stampede risk after low TTL rollout).
- DNS control planes can lag; record updates might take longer than UI/API indicates.

### CDN/Edge Anycast
- POP-level issues can persist while BGP still routes to that POP.
- “Failover within the edge” can be opaque (provider may shift within their network without clear signals).
- Some providers prioritize availability over latency by routing to a far POP; expect tail latency spikes after failover.

### Cloud load balancers
- Regional load balancers can remain reachable while backends are degraded (connection succeeds, requests fail).
- Health checks may not match real production paths (headers, auth, request size).

Action: keep Redwood-owned synthetic probes (multi-vantage) as the authoritative input into Region Health.

## Testing guidance (game days)
For controlled failover tests:
- Do not use DNS-only steering as a success metric. Use application-level routing metrics (policy flips, request success rate, tail latency).
- Validate from at least three client vantage points (public internet, enterprise resolver network, and a mobile network) to capture resolver variance.
- Include IPv6 in the test matrix where supported; v4/v6 divergence is common.

Recommended measurements to capture:
- Time-to-detect and time-to-failover (from Region Health + controller audit events)
- Client-visible error rate (5xx) and elevated retry volume
- DNS query rates and authoritative SERVFAILs during the test window

## Guardrails and change safety
Rules of thumb:
- Do not stack steering mechanisms at the same time unless explicitly planned. If you change routing policy and DNS simultaneously, attribution becomes impossible.
- If DNS changes are required, prefer reversible changes (record weights) over destructive changes (record deletions).
- Maintain a clear rollback plan with explicit hold-down timers to avoid oscillation.

- confluence://architecture-and-standards/decision-records/adr-042-failover-trigger-signal-hierarchy

## Operational quick reference
### DNS TTL defaults
- Global API entry: 60s
- Regional endpoints: 300s

### “Do not do this” list
- Do not drop TTL to 0–10s expecting instant failover.
- Do not change TTL during an incident as the primary mitigation.
- Do not rely on provider status pages as the primary trigger signal.
- Do not use DNS changes to compensate for insufficient capacity headroom in the target region.

## Appendix: glossary
- **Anycast:** multiple servers advertise the same IP; routing picks a “nearest” route by BGP policy.
- **TTL:** time-to-live; how long a resolver caches a DNS answer.
- **Negative caching:** caching of NXDOMAIN/no-data responses governed by SOA minimum values.
- **Stampede:** sudden surge of DNS queries when many clients/resolvers re-resolve at once, often caused by low TTL or synchronized expiry.
