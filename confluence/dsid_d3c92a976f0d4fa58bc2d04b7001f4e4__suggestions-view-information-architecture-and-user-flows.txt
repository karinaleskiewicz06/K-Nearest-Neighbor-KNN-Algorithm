Suggestions View (Optimize) — Information Architecture & User Flows (Beta)

## Purpose
Define the information architecture (IA) and end-to-end user flows for the **Optimization suggestions (Beta)** experience in the Redwood Console.

This spec focuses on:
- Navigation entry points into Suggestions
- The list + details pattern (table + right-side drawer)
- Filtering/sorting patterns
- The end-to-end flow from discovery → understanding → applying config changes (manual + safe rollout)

Out of scope (Beta):
- Quantization recommendations UI (may be referenced but not launched here)
- Auto-apply without user confirmation/rollout controls
- Any savings “guarantee” language

---

## Product principles (UX)
1. **Actionable**: Always provide a clear next step (deep link + what changes + where it applies).
2. **Trustworthy**: Show assumptions, confidence inputs, staleness, and conservative risk labels.
3. **Comparable**: Enable quick ranking across routes/models (sorting + filters) without losing context.
4. **Safe**: Reinforce that changes should go through rollout controls; avoid “one-click apply” in beta.

---

## Primary users & jobs-to-be-done
### Personas
- **ML/Platform Engineer**: Owns inference configuration, cares about cost/perf tradeoffs and safe rollouts.
- **SRE/On-call**: Wants to avoid regressions; cares about risk clarity, staleness, and rollback paths.
- **Product Engineer** (secondary): Wants quick savings wins but needs guidance and guardrails.

### Key jobs
- Identify top cost-saving opportunities by **route + model**
- Understand “why” and “what could go wrong” (latency/reliability risk)
- Apply changes via the appropriate config surface (batching/caching) with rollout controls

---

## Navigation entry points (IA)
### Left navigation
- **Optimize → Suggestions (Beta)**
  - Visible only when feature flag is enabled for the org (see “Gating & permissions”).

### Contextual entry points (deep links)
These should route into the Suggestions view with pre-applied filters:
- **Route details → Cost** panel: “View suggestions for this route”
- **Model deployment/version page**: “View suggestions for this model”
- **Optimize overview** (if present): “Top suggestions” module (beta)

### URL structure (recommended)
- `/console/:org/:project/optimize/suggestions`
  - Query params for state:
    - `?route_id=` (optional)
    - `&model_id=` (optional)
    - `&region=` (optional)
    - `&type=` (batching|caching)
    - `&risk=` (low|medium|high)
    - `&confidence=` (low|medium|high)
    - `&sort=` and `&dir=`
    - `&cursor=` (pagination)

Rationale: supports sharable URLs + support debugging without requiring users to repeat filter steps.

## Gating & permissions
### Feature flag gating
- Org-level flag: `optimize_suggestions_beta`
- UI behavior:
  - If not enabled: show an “Access required” state with CTA to request access (links to internal/beta request flow for Redwood-managed accounts).

### RBAC
- Permission required to view Suggestions:
  - `optimize:suggestions:read`
- Permission required to follow apply CTAs (config pages may have additional scopes):
  - Example: `inference:config:write` (actual scope may vary by surface)

### Multi-project/org scoping
- Suggestions are **project-scoped** by default.
- If the Console supports org-wide views, the Suggestions view must be explicit about scope (“Project: X”) and never mix cross-tenant data.

## Page layout overview
### 1) Suggestions list (table)
- Main content: a table of suggestions (default sorted by “Highest estimated savings/day”).
- Right-side details drawer opens when a row is selected.
- Sticky header contains:
  - Page title + beta badge
  - Filter chips
  - Search (route name / route id)
  - “Last computed” timestamp + staleness indicator

### 2) Details drawer (right panel)
- Contains:
  - Summary (savings + perf impact + risk)
  - “Why we recommend this” explanation
  - Assumptions + confidence explanation
  - “How to apply” steps + deep links to config surfaces
  - Guardrails / warnings
  - Action footer: “Mark as dismissed” + “Give feedback”

### 3) Secondary panels
- Inline empty states (no telemetry, not eligible, etc.)
- Inline error state (API failure)

## List view: table definition
### Table columns (beta)
1. **Route**
   - Route name + route id (secondary)
   - Optional: environment badge (prod/staging) if available
2. **Model**
   - Model name/version currently pinned for the route (or “Multiple” if route varies)
3. **Suggestion**
   - Type: Batching or Caching
   - Short label, e.g.:
     - “Increase max batch size”
     - “Enable prefix/KV caching”
4. **Est. savings**
   - Primary: `$ / day` (or `$ / month` if user toggles timeframe)
   - Secondary: `%` savings relative to current spend on that route/model
   - Must include tooltip: “Estimated, not guaranteed”
5. **Perf impact (est.)**
   - p50 and p95 latency delta (ms, +/-)
   - If unknown: “—” with tooltip explaining insufficient confidence
6. **Risk**
   - Badge: Low / Medium / High
   - Tooltip copy per risk guidelines page
7. **Confidence**
   - Low / Medium / High (or numeric 0–100 later; beta uses levels)
   - Tooltip: inputs included + what’s missing
8. **Last computed**
   - Timestamp, used to spot staleness

Notes:
- Keep the list skimmable: prefer short labels and tooltips over long inline explanations.
- Column visibility: on smaller screens, collapse Model + Last computed into secondary row, but keep Savings/Risk visible.

### Table row behavior
- Clicking a row opens the details drawer.
- Keyboard support:
  - Up/down to move row focus
  - Enter/Space to open drawer
  - Esc to close drawer
- Selected state persists across pagination where possible (by stable suggestion id).

## Sorting and filtering
### Default sort
- Sort by **Estimated savings ($/day) descending**.

### Supported sorts (beta)
- Est. savings ($/day)
- Est. savings (%)
- Risk (Low → High or High → Low; default: show highest savings first)
- Confidence (High → Low)
- p95 latency delta (ascending)
- Last computed (newest first)

### Filters (beta)
Filter chips appear beneath the header; selected filters display as removable chips.

1. **Suggestion type**: Batching, Caching (multi-select)
2. **Risk**: Low, Medium, High (multi-select)
3. **Confidence**: Low, Medium, High (multi-select)
4. **Region**: if applicable to the project (multi-select)
5. **Model**: model id/name (single or multi; if too many, use typeahead)
6. **Route**: typeahead search by route name/id

Recommended (if telemetry supports it without confusion):
- **Traffic tier** (e.g., High/Medium/Low QPS) to help large customers focus.

### Filter persistence
- Persist filters in URL query params.
- Remember last-used filters per user (local storage) for the project.

## Details drawer: content structure
Drawer sections should follow a consistent order to reduce cognitive load.

### Header (always visible)
- Route name + route id
- Model name/version
- Suggestion type icon (Batching/Caching)
- Status badges (as applicable):
  - “Stale” (if computed beyond staleness threshold)
  - “Insufficient telemetry” (if partial)

### Section A — Summary (at-a-glance)
- **Estimated savings**
  - `$ / day` and `%`
  - Confidence band if available (beta may show “Range: $X–$Y/day” when estimator provides it)
- **Estimated performance impact**
  - p50 delta, p95 delta
  - If estimator provides only p95, show p95 prominently and p50 as “—”
- **Risk level**
  - Low/Medium/High with 1–2 lines of “why” (not generic)

### Section B — Why we recommend this
- 3–5 bullet explanation grounded in observed telemetry (examples):
  - “High concurrency during peak hours; batching can improve GPU utilization.”
  - “Repeated prompts detected; caching could reduce repeated compute.”
  - “Current cache hit rate is low; enabling prefix caching is expected to increase hit rate by ~X% (est.).”

### Section C — Assumptions & confidence
Must show the inputs used and what might make the estimate wrong.
- Inputs used (examples):
  - request rate window (e.g., last 7 days)
  - sequence length distribution
  - current batching/caching configuration
  - observed cache hit rate (if applicable)
  - token price/cost basis used for estimate
- Confidence explanation:
  - “High” if enough traffic + stable distribution + low variance
  - “Low” if sparse traffic, high variance, or missing cache metrics

### Section D — How to apply (no auto-apply in beta)
- Step-by-step guidance:
  1) Review recommended configuration values (show current vs recommended)
  2) Navigate to the relevant config page (deep link)
  3) Apply change using a safe rollout (canary) and monitor latency/error rate

Deep link targets (beta):
- Batching suggestion → “Route config → Batching”
- Caching suggestion → “Route config → Caching”
- If user lacks permissions: show disabled CTA + “Request access” link.

### Section E — Guardrails / warnings
- Explicitly call out constraints from guardrails doc (examples):
  - “Low-latency route: avoid increasing batch size beyond X; monitor p95 closely.”
  - “If your prompts include highly dynamic prefixes, caching gains may be limited.”

### Section F — Actions
- “Dismiss suggestion” (requires confirmation)
  - Prompt: “Dismiss for this route/model for 30 days” (beta default)
  - Optional reason dropdown (for feedback taxonomy):
    - Not applicable
    - Savings too small
    - Risk too high
    - Estimate seems wrong
    - Already implemented
- “Give feedback” link (opens feedback modal or external form)

## End-to-end user flows
### Flow 1 — Discover → Evaluate → Apply
1. User opens **Optimize → Suggestions (Beta)**.
2. User sorts by **Est. savings** (default) and applies filters (e.g., Risk: Low).
3. User clicks a suggestion row; details drawer opens.
4. User reviews:
   - Estimated savings + perf impact
   - Risk explanation
   - Assumptions/confidence
5. User clicks **“Go to config”**.
6. On config page, user updates settings.
7. User applies via rollout controls:
   - Create canary (e.g., 5–10% traffic)
   - Monitor key metrics
   - Increase rollout if stable
8. User returns to Suggestions and marks as “Applied” (beta behavior below).

Beta note on “Applied”:
- We will not automatically detect applied state reliably in beta unless config surfaces expose a canonical signal.
- UX behavior:
  - Provide an **“Mark as applied”** optional action in drawer (records user intent) OR
  - Provide a banner: “After applying, monitor and we’ll refresh estimates in up to N hours.”
- Final decision depends on backend support (see ADR suggestions API contract).

### Flow 2 — From Route page deep link
1. User is investigating cost for Route A.
2. User clicks “View suggestions for this route”.
3. Suggestions opens with `route_id=RouteA` filter applied and drawer optionally pre-opened on top suggestion.
4. User proceeds with evaluation/apply.

### Flow 3 — Dismiss
1. User opens a suggestion.
2. User clicks “Dismiss”.
3. Confirmation modal:
   - Explains dismissal hides suggestion for a period (default 30 days)
   - Optional reason
4. User confirms.
5. Row disappears from default list; can be re-shown via “Include dismissed” toggle (internal-only for beta / support).

### Flow 4 — Insufficient telemetry
1. User opens Suggestions.
2. System detects missing required signals (e.g., cache metrics not enabled).
3. Show empty state:
   - “We don’t have enough telemetry to generate suggestions yet.”
   - Requirements checklist
   - CTA: “View setup instructions”
4. Once telemetry flows, Suggestions populates.

### Flow 5 — Estimate looks wrong (trust recovery)
1. User opens drawer and sees savings that conflict with their expectations.
2. User expands “Assumptions & confidence”.
3. User clicks “Give feedback” and selects “Estimate seems wrong”.
4. Feedback captures:
   - Suggestion id
   - Route/model context
   - User-provided note
5. UX confirms: “Thanks — we use this to improve estimator quality. Estimates are not guaranteed.”

## Empty states & error states (link to detailed spec)
This page references: “Suggestions empty states and onboarding”.

Summary of required behaviors:
- **Feature not enabled**: access required + request access
- **No permission**: RBAC denied message + request access / contact admin
- **No data / insufficient telemetry**: requirements checklist + setup CTA
- **No suggestions available**: neutral empty (“No suggestions right now”) + tips on expanding scope (change time range, check filters)
- **API error**: retry button + “Check status” link (internal) + error id for support

## Key microcopy requirements (beta)
- Always say **“Estimated savings”** and **“Estimated performance impact”**.
- Do not use guarantee language (“will save”, “guaranteed”, “promised”).
- Risk badge tooltips must clarify:
  - Risk refers to **performance/reliability tradeoffs**, not security risk.
- Staleness labels must include a timestamp:
  - “Last computed: 2026-02-20 14:00 UTC”

---

## Accessibility & interaction notes
- Risk badges must meet contrast requirements; do not rely on color alone (include label text).
- Tooltips must be keyboard accessible.
- Drawer must trap focus when open; Esc closes.
- Table rows must have visible focus states and screen-reader row/column labeling.

---

## Analytics (UX instrumentation points)
Event taxonomy is defined elsewhere, but UX must provide the following triggers:
- Page impression (Suggestions view)
- Filter change (type/risk/confidence/model/route)
- Sort change
- Row select / drawer open
- “Go to config” click
- Dismiss initiated + confirmed + reason
- Feedback submitted

UX requirement: ensure that analytics collection does not block rendering; failures should be silent.

## Open questions (needs final alignment)
1. **Applied state**: Do we add “Mark as applied” in beta, or wait until config detection is reliable?
2. **Time window selection**: Should users select 7d/30d windows for estimates on this page, or keep fixed for beta?
3. **Multi-model routes**: How do we represent routes with dynamic model routing? (Show “Multiple” + drawer details?)
4. **Confidence display**: Levels only (Low/Med/High) vs showing a numeric score + inputs.
