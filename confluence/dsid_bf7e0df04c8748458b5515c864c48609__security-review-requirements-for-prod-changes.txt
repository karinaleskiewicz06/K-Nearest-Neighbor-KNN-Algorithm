Secure SDLC: Security Review Requirements for Production Changes

h1. Summary
This standard defines when a production change requires Security review and what evidence must be captured in the change record. The goal is to prevent regressions in authentication, authorization, auditability, and customer data handling.

h1. Scope
Applies to all production changes for Hosted API and Console, including control plane and data plane services.

h1. When Security review is required
Security review is *required* when a change impacts any of the following:
* Authentication or session management (API keys, OAuth, SSO, cookies, tokens)
* Authorization/RBAC policy evaluation or enforcement
* Secrets handling (creation, storage, rotation, access patterns)
* Encryption in transit or at rest; KMS/HSM integrations
* Audit logging behavior, retention, or integrity guarantees
* Data classification changes (PII, customer content, prompt/response logs)
* Network exposure (public endpoints, ingress rules, CORS)
* Dependency upgrades that patch or introduce security-relevant behavior (auth libraries, TLS stacks)

h1. When Security review is recommended
Security review is recommended (but not required) when:
* Introducing a new external integration or webhook destination
* Changing rate limiting/abuse protections in ways that could increase DoS risk
* Changing observability pipelines that may leak sensitive fields

h1. Required evidence in the change record
If Security review is required, attach or link to:
1. Threat summary: what could go wrong and what is the mitigated outcome
2. Affected assets: endpoints, data fields, secrets, and logs
3. Verification plan: tests or steps validating authz decisions, audit events, and data redaction
4. Rollback plan: how to revert without leaving the system in an insecure intermediate state
5. Reviewer approval: Security reviewer name + timestamp captured in the ticket

h1. Special cases
* Audit logging changes: must include a plan to validate event completeness and tamper resistance.
* RBAC changes: must include at least one negative test demonstrating denial works as intended.
* Data retention changes: must reference the approved retention policy and include migration/backfill details.

h1. SLA for review
* Normal changes: request review at least 2 business days before planned deployment.
* Emergency changes: Security participates in incident channel when possible; post-change review is required within 24 hours.
