self-hosted-eval-grid-deployment-and-gpu-affinity-gitops-playbook

Overview

Purpose: This playbook describes the recommended architecture, IaC modules, and CI/CD/GitOps workflow for deploying and operating a self-hosted evaluation grid of heterogeneous GPU nodes that supports reproducible model evals, controlled cost accounting, and safe promotion of benchmark images. The goal is to provide consistent, audit-able eval runs across cloud accounts and on-prem nodes while minimizing blast radius for CI failures and noisy neighbors.

When to use

- You need a persistent, repeatable eval environment for nightly/CI model benchmarks that must run on specific accelerator families (A100, L4, H100, etc.).
- You want GitOps-driven promotion of eval images with preflight safety checks and tenant isolation.
- You require fine-grained affinity (fractional GPUs, device selection) and chargeback attribution per-eval.

High-level architecture

1) Fleet fabric: a federated set of GPU node pools across accounts/regions, managed via the GPU allocator operator and an orchestration plane. Pools are tagged by profile (e.g., a100-40g-l4, h100-mem-160g) and a pool-level trust boundary (prod-eval, sandbox, restricted).
2) GitOps control plane: a central repo per-eval-grid that houses Kubernetes overlays, Terraform workspace configs, and image promotion manifests. ArgoCD (or equivalent) reconciles cluster overlays to per-cluster namespaces.
3) CI/CD pipeline: a Buildkite/Concourse pipeline that builds eval images, runs a set of isolated preflight checks in ephemeral sandboxes, and promotes artifacts via signed provenance to the GitOps repo on success.
4) Chargeback & ledger: lightweight sidecar that emits claim events to the GPU lease ledger (see related page) to record per-eval allocation, wall-clock, and tokenized cost signals.

Preconditions and safety constraints

- Account and VPC network peering set up with egress controls and NAT accounting (see network peering playbooks).
- Node images must be signed and attested by the runtime signing pipeline.
- RBAC: only CI pipeline service accounts and core-sre may merge promotion PRs. Branch protection and signed commits enforced.
- Quotas: each eval repo must declare a wallet (budget) and concurrency limit. Pipeline will abort when budget exhausted.

Terraform & IaC modules (recommended inputs)

Below is a compact table of the core Terraform modules and required inputs for the grid. Use these as canonical names in repo modules.

Module | Purpose | Required inputs
--- | --- | ---
gpu-pool | Provision node pools (autoscaling groups / instance templates) | region, instance_profile, accelerator_type, pool_policy
gpu-network-fence | Egress & NAT fencing per-pool | vpc_id, egress_account_whitelist, nat_gateway_id
namespace-allocator | Namespace + quota templates | namespace_prefix, cpu_quota, memory_quota, gpu_quota
gitops-overlay | Cluster overlay bootstrap | cluster_name, argo_application_namespace, sync_policy
claim-ledger | Lightweight per-eval ledger | ledger_endpoint, auth_token, default_rate_card

CI/CD pipeline outline

1) Build stage (Buildkite): build eval image, run unit tests, perform static security scan.
2) Preflight sandbox (ephemeral): deploy image to an ephemeral sandbox namespace with a single replica on a small GPU node; run a curated, low-cost evaluation subset (5–10 prompts) to detect early regressions.
3) Performance smoke test: use a small synthetic load to ensure token latency < 400ms p50 for this profile.
4) Cost & telemetry smoke: validate exported cost tags and ledger claim call.
5) Promotion gate: if all checks pass, create a signed promotion PR in the gitops repo. Merges require 1 approver from core-sre.

GitOps patterns and safety gates

- Image pinning: overlays must reference image digests, not tags. Promotion PRs update digest references only.
- Sync windowing: ArgoCD sync windows restrict overnight promotions to prod-eval pools; sandbox pools accept 24/7.
- Canary overlays: default promotion creates a canary overlay enabling 5% of pool capacity for the new image for 24h before full rollout.
- Auto-rollback: if rollout triggers >5% error rate or latency regression over 6h, ArgoCD annotation triggers an automated rollback to last-known-good digest.

Affinity & scheduler policies

- Device selection policy: prefer whole-GPU placement for throughput evals and fractional (MPS/virtual GPU) for interactive evals.
- Topology-aware packing: the allocator tries same-socket affinity for multi-GPU experiments; fallback to cross-socket when necessary.
- Fair-share & preemption: sandbox pools are low-priority and preemptible; prod-eval pools have a soft-SLO and are only preempted by critical system tasks.

Operational runbook (on-call play flows)

1) Alert: "eval-grid-pool-saturation" (p90 queue wait > 3m for > 15m)
   - Owner: infra-gpu-oncall
   - Steps:
     a) Check GPU pool autoscaler events (kubectl get hpa, aws/compute autoscale logs).
     b) If preemption backlog high, escalate to cost control to request short-term burst credits or enable additional warm pool nodes.
     c) If autoscaler failing, run terraform apply to scale minimal nodes or roll forward last working module commit.
2) Alert: "eval-preflight-failure-rate" (>10% preflight failures in last 30m)
   - Owner: ci-infra
   - Steps:
     a) Inspect buildkite logs, check image signing step, verify artifact registry health.
     b) If a recent promotion PR merged, immediately annotate ArgoCD to pause sync to prod-eval and trigger rollback.
3) Alert: "ledger-claim-errors" (>1% of claims failing)
   - Owner: infra-finops
   - Steps:
     a) Check ledger sidecar logs and auth token expiry.
     b) Switch to emergency fallback ledger endpoint (env var flip) and requeue failed events.

Troubleshooting checklist (quick commands)

- Check pool capacity: kubectl get nodes -l accelerator_type=A100 -o wide
- Inspect ArgoCD app syncs: argocd app list ; argocd app history eval-grid-app
- Replay claim events: curl -X POST ${LEDGER_ENDPOINT}/replay -d '{"since":"1h"}'
- Promote a hotfix: create promotion branch in gitops repo, bump digest, merge with core-sre approval.

Cost controls and quotas

- Every eval repository must include a wallet identifier. The CI/CD pipeline decrements the wallet by the configured cost rate card per-minute during preflight and production runs.
- Concurrency limits: per-repo default concurrency = 3. Increase requires approval and vault-based budget adjustment.
- Warm pool budget: maintain a 10% warm buffer paid from centralized burst credits; daily reconciliation run reports to finance.

Ownership and SLAs

- Owner: infra-gpu-platform (primary) — Pager/Oncall
- Supporting: ci-infra (pipeline + image signing), infra-network (VPC/egress), infra-finops (chargeback reconciliation)
- SLOs: pool-provisioning time 95th <= 8 minutes for warm pool replenishment; preflight latency p50 <= 1s for small prompts in sandbox.

Notes and references

- This playbook is intentionally conservative: prefer canary-first, digest-pinned promotions and strong RBAC on promotion merges.
