GPU shadow-account promotion and rollback spec

Summary
-------
This document specifies the design, Terraform module contract, CI/CD promotion pipeline, and operational rollback runbook for the GPU Shadow Account Promotion pattern. The pattern is used to test infrastructure changes (networking, IAM, instance profiles, allocation policies) in a fully-configured, isolated shadow account that mirrors production GPU topology and egress routing, and to safely promote validated changes into production accounts via GitOps.

Goals
- Enable automated, low-risk promotion of IaC changes that affect GPU capacity and tenant egress.
- Provide a reproducible canary/promotion pipeline that validates IAM, VPC peering, egress policy, and GPU node profiles at scale.
- Automate safe rollback when telemetry or gating tests fail.
- Keep drift remediation auditable and reversible.

Audience
- Infra engineers who author Terraform modules for GPU fleet and networking.
- SREs running promotion gating and oncall.
- Security and cloud teams validating cross-account IAM.

Terminology
- Shadow account: an isolated cloud account that mirrors production configuration but uses synthetic traffic/tenants.
- Promotion: automated process that applies validated TF changes from shadow -> staging -> production via GitOps.
- Promotion gate: evaluation suite (integration tests + telemetry checks) that must pass before promotion continues.
- Rollback window: time window after promotion where automatic rollback is permitted.

Design overview
- Topology: The shadow account is provisioned from the same Terraform modules used for prod with a small set of overridden variables (account_id, prefix, test_subnets, synthetic_tenants).
- Drift detection: A dedicated reconciler compares module outputs between prod and shadow (tags, route tables, IAM bindings) daily and raises drift PRs.
- Promotion path: feature branch -> merge to "shadow-main" (applies to shadow account) -> run gates -> merge to "canary-main" (applies to 5% prod traffic/account segment) -> monitor 2h -> merge to "prod-main".

Terraform module contract (required inputs/outputs)
| Module | Required vars (name:type:notes) | Critical outputs | Owner |
| --- | --- | --- | --- |
| networking/gpu-vpc | account_id:string:target account | vpc_id, subnet_ids | infra-networking |
| iam/gpu-roles | account_id:string, tenant_tag:string | role_arn_map | infra-security |
| compute/gpu-node-pool | pool_size:number, instance_profile:string | instance_group_id, scaling_policy_id | gpu-fleet |
| routing/egress-shaper | egress_bucket:string, nat_gateway_id:string | egress_policy_id, peering_route_id | cloud-net |

Required TF var overrides for shadow accounts
- prefix: "shadow-{team}-{env}"
- synthetic_tenants: ["sandbox-1","sandbox-2"]
- pool_size: scaled to 10–20% of prod equivalent (configurable)
- telemetry_export: enabled=true, sink=promethus-shadow

CI/CD promotion pipeline (GitOps adapter)
- Pipeline stages:
  1) Lint & unit-validate (tflint, terraform validate)
  2) Plan (shadow account) and post plan as PR comment with diff and plan-summary.json
  3) Apply to shadow via automation account (assume-role into shadow)
  4) Integration tests run against shadow (synthetic traffic, network probes, IAM smoke tests)
  5) Telemetry gating: collect latency, pod churn, node registration, egress-per-tenant; evaluate against thresholds
  6) Canary promotion: if gates pass, create PR into canary-main which triggers apply to canary accounts (5% traffic)
  7) Monitor canary for N hours; if green, PR into prod-main for full rollout

Example GitHub Actions snippet (abbreviated)
```yaml
name: GPU-Promote
on:
  workflow_call:
    inputs:
      promote_target:
        required: true
jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Install tf
        run: curl -fsSL https://releases.hashicorp.com/terraform/1.5.0/terraform_1.5.0_linux_amd64.zip -o tf.zip && unzip tf.zip && sudo mv terraform /usr/local/bin/
      - name: TF Init
        run: terraform init -backend-config="bucket=${{ secrets.TFSTATE_BUCKET }}"
      - name: TF Plan (shadow)
        run: terraform plan -var-file=vars/shadow.tfvars -out=plan.shadow
      - name: Comment Plan
        uses: marocchino/sticky-pull-request-comment@v2
        with:
          message: "Plan summary for ${{ github.ref }}"
```

Promotion gating thresholds (initial)
- Node registration latency: < 60s per node (95th percentile) during initial apply
- Peer route convergence: all peering routes present within 5m
- Synthetic tenant latency regression: < 3% vs shadow baseline
- Egress policing: no tenant exceeds burst credit of 120% during first 30m
- TF plan drift ratio (lines changed / total lines): < 0.5% for control modules

Automated rollback policy
1) If any gating threshold is violated during shadow apply, the pipeline aborts and files an incident PR with plan artifacts.
2) If canary experiences sustained SLO violation > 0.5% above baseline for 30m, automation reverts the canary-main PR (creates revert PR) and applies revert to canary accounts.
3) If prod rollouts show critical regressions (node panics, egress routing blackholes), automation triggers immediate rollback to the last known good state and notifies oncall.
4) Rollback window is 3 hours after a promotion by default; after that, rollbacks require a human-approved mitigation RFC.

Operational runbook (oncall steps)
1) Pager triggers: critical alerts for node flapping, egress blackhole, failed IAM assume-role errors.
2) Triage: check the promotion pipeline activity in GitOps UI; identify last merged PR, collect plan artifact and apply logs from shadow and canary.
3) If gating failure from shadow: do not promote; revert the source branch and notify change author.
4) If canary failure: revert canary PR and open incident; run kubectl describe on affected nodes and gather core dumps.
5) If prod failure: execute emergency revert by merging the most recent revert PR and run prioritized remediation (see Remediation checklist).

Remediation checklist (fast path)
- Re-recover peering: run 'scripts/repair-peering.sh --account <id> --route-table <id>'
- Re-create node-pool: terraform apply -target=module.compute/gpu-node-pool -var="pool_size=<safe>"
- Re-attach IAM role bindings: aws iam attach-role-policy --role-name <name> --policy-arn <arn>
- Drain problematic nodes: kubectl drain <node> --ignore-daemonsets --delete-local-data

Testing and validation matrix
- Unit tests: tflint, terraform validate, module contract checks (every PR)
- Integration tests: network connectivity probes, IAM assume-role matrix (shadow only)
- Scale test: synthetic workload ramp to 120% of shadow pool capacity for 30m (nightly)
- Chaos test: scheduled disruption of a random NAT gateway and validate egress failover (weekly)

Ownership and SLAs
- Owners: gpu-fleet (primary), infra-networking (secondary), infra-security (auditor)
- SLOs for promotion pipeline: 95% successful shadow applies within 12m of queued job; 99% plan generation success rate; incident MTTR for promotion-related outages < 60m

Rollforward vs rollback decision matrix
| Symptom | Severity | Action |
| --- | --- | --- |
| Transient increase in pod restart rate (<= 3%) | Low | Observe and continue; escalate if persists > 30m |
| Node registration failure (>= 3 nodes) | Medium | Abort promotion, revert canary, run remediation scripts |
| Egress blackhole for a tenant | High | Immediate rollback to previous TF state; open incident;|
| IAM assume-role failure across accounts | Critical | Immediate stop, manual rollback and security review |

Audit and postmortem guidance
- Record the promotion PRs, plan artifacts, and telemetry snapshots (prometheus:prometheus:shadow) as incident attachments.
- Postmortem must include: timeline, responsible PRs, golden config diff, and a remediation plan.

Migration notes (for teams adopting pattern)
1) Convert existing production modules to accept account_id and prefix overrides without branching behavior.
2) Add telemetry_export toggles to all modules for shadow/export sinks.
3) Implement a small synthetic tenant harness in the shadow account that exercises egress shaper policies.
