ADR: Example-Level Payload Shape for Streaming Tool Calls

## Status
Published (applies to examples in docs, quickstarts, and SDK READMEs).

## Decision summary
For **developer-facing examples** that demonstrate *streaming tool calls*, Redwood will standardize on a **minimal, stable event envelope** and a **canonical tool-call object shape**:

- Streaming events shown in examples MUST include:
  - `event` (string)
  - `data` (object)
- Tool call identity MUST be represented as `tool_call_id` everywhere (stream deltas, final tool call, and tool-result messages).
- Tool call arguments MUST be treated as **an opaque string during streaming**:
  - partial updates: `arguments_delta` (string)
  - final: `arguments` (string)
  - parsing happens **only after** the tool call is complete.

This ADR intentionally defines the **example-level** payload shape (what we show and teach), not the full internal wire format.

## Context / problem
Across Python/TypeScript/Go and the docs site, streaming tool-calling examples diverged in:

- Field naming (`id` vs `tool_call_id`, `function.name` vs `name`).
- Whether arguments were shown as JSON objects vs strings.
- How partial arguments were represented during streaming.
- How parallel tool calls were assembled when deltas interleave.

These inconsistencies contributed to:

- Copy/paste failures and type mismatches (e.g., TS example failures).
- Confusion about “truncated” arguments mid-stream (SUP-18421): users attempted to parse JSON before the stream completed.
- Support load due to unclear guidance on delta assembly and tool-result linkage.

The refresh project requires a single mental model that is consistent across SDKs and documentation.

## Goals
1. Provide a simple, consistent model for assembling tool calls from streaming deltas.
2. Avoid encouraging fragile behavior (incremental JSON parsing, relying on internal fields).
3. Make examples resilient to model variability (argument emission timing, interleaving).
4. Keep parity with common industry patterns (OpenAI-style semantics) without claiming strict wire compatibility.

## Non-goals
- Redesigning Redwood’s underlying streaming protocol.
- Defining every field available in the raw streaming payload.

## Decision details
### 1) Canonical event names used in examples
Examples will use the following `event` names. SDKs may expose richer objects; examples should map to these concepts.

| Event | When it fires | Required fields in `data` | Notes |
|------|---------------|---------------------------|-------|
| `message.delta` | Assistant message text arrives incrementally | `message_id`, `content_delta` | `content_delta` is appended to a per-message buffer. |
| `message.done` | Assistant message is complete | `message_id`, `content` | Examples may omit if the SDK returns final content elsewhere; if present, it is authoritative. |
| `tool_call.delta` | Tool call arguments arrive incrementally | `tool_call_id`, `name` (optional), `arguments_delta` | Deltas may interleave across multiple tool calls. Do not parse JSON here. |
| `tool_call.done` | Tool call arguments are complete | `tool_call_id`, `name`, `arguments` | `arguments` is a complete JSON string (still validate before use). |
| `response.done` | No more events for the response | `response_id` (optional) | Marks end-of-stream for the example loop. |
| `error` | Stream fails or server returns an error | `code`, `message` | Examples should demonstrate a single retry policy or a clear abort. |

Rationale: dot-separated names are readable in logs, consistent across languages, and avoid leaking internal event taxonomies.

### 2) Canonical tool call object shape
Examples will represent a tool call as:

- `tool_call_id` (string): stable identifier for the call
- `name` (string): tool/function name
- `arguments_delta` (string): partial JSON text during streaming
- `arguments` (string): complete JSON text when done

**Arguments are always strings** in streaming examples.

Rationale: during streaming, the JSON is frequently incomplete and not parseable. Representing deltas as strings prevents users from writing broken “parse on every chunk” logic.

### 3) Tool-result messages MUST reference `tool_call_id`
When returning tool output back to the model, examples must send a tool-result message that includes the `tool_call_id`:

```json
{
  "role": "tool",
  "tool_call_id": "call_01HZZ...",
  "content": "{\"temperature_f\": 71, \"conditions\": \"clear\"}"
}
```

Rationale: a stable link is required for parallel tool calls and avoids ambiguity when multiple tools share the same name.

### 4) What examples should *not* show
To keep examples stable and avoid implying unsupported semantics, examples should not depend on:

- Internal IDs unrelated to tool execution (e.g., per-token counters, shard IDs).
- Incremental JSON parsing of arguments.
- Assuming tool call `name` arrives before `arguments_delta` (models differ).
- Assuming tool calls cannot interleave.

If the SDK exposes a richer native event type, examples may log it behind a debug flag, but the canonical logic should operate on the minimal fields above.

## Example transcript (canonical)
Below is the reference shape used in docs/quickstarts for streaming tool calls.

### Tool definitions (request)
```json
{
  "model": "redwood/sonoma-3",
  "messages": [{"role": "user", "content": "What is the weather in Seattle right now?"}],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "Fetch current weather for a city.",
        "parameters": {
          "type": "object",
          "properties": {
            "city": {"type": "string"},
            "units": {"type": "string", "enum": ["metric", "imperial"]}
          },
          "required": ["city"]
        }
      }
    }
  ]
}
```

### Streaming events (response)
```json
{"event":"message.delta","data":{"message_id":"msg_1","content_delta":"Let me check that for you."}}
{"event":"tool_call.delta","data":{"tool_call_id":"call_1","name":"get_weather","arguments_delta":"{\"city\":\"Sea"}}
{"event":"tool_call.delta","data":{"tool_call_id":"call_1","arguments_delta":"ttle\",\"units\":\"imperial\""}}
{"event":"tool_call.delta","data":{"tool_call_id":"call_1","arguments_delta":"}"}}
{"event":"tool_call.done","data":{"tool_call_id":"call_1","name":"get_weather","arguments":"{\"city\":\"Seattle\",\"units\":\"imperial\"}"}}
{"event":"response.done","data":{"response_id":"resp_1"}}
```

Notes:
- `name` may be omitted on subsequent `tool_call.delta` events; examples must cache it if needed.
- The arguments are intentionally shown as JSON text, not a JSON object.

## Assembly rules (normative for examples)
Examples (across languages) must implement the following assembly rules:

1. Maintain a map keyed by `tool_call_id` with:
   - `name` (string, optional until first seen)
   - `arguments_buffer` (string)
2. On `tool_call.delta`:
   - Append `arguments_delta` to `arguments_buffer` for that `tool_call_id`.
   - Do not parse.
3. On `tool_call.done`:
   - Prefer `arguments` from the done event if provided.
   - Parse once (`JSON.parse` / `json.loads`) and validate against the tool schema.
4. If the stream ends without `tool_call.done`:
   - Treat as incomplete.
   - Either retry the request (if safe and idempotency is configured) or surface a clear error.

This directly addresses the “arguments truncated” support issue: arguments are expected to look incomplete mid-stream.

## Parallel tool calls
Examples must assume:

- Multiple tool calls may be active.
- Deltas may interleave across tool calls.

Canonical behavior:
- Use `tool_call_id` as the sole key.
- Never assume “the latest tool call” is the target of a delta.

## Compatibility guidance (docs copy)
Docs should include a short callout:

- “Streaming tool-call arguments are emitted as text deltas and may not be valid JSON until the tool call is complete. Always assemble and parse after `tool_call.done`.”

If a page discusses OpenAI-compatibility, it must clarify that:

- The Redwood examples use OpenAI-like semantics (tool definitions + tool result messages), but the raw streaming payload may contain additional fields and may not be byte-for-byte identical.

## Alternatives considered
1. **Expose the full raw streaming payload in examples**
   - Pros: transparent.
   - Cons: noisy, unstable, encourages reliance on non-contractual fields.

2. **Represent arguments as JSON objects in deltas**
   - Pros: “feels typed.”
   - Cons: not feasible when JSON is incomplete; encourages incremental parsing and fragile merge logic.

3. **Standardize on OpenAI’s exact streaming schema**
   - Pros: familiarity.
   - Cons: limits Redwood’s ability to evolve payloads; risks implying strict compatibility where edge cases differ.

We chose a minimal envelope that is stable, teachable, and implementation-agnostic.

## Consequences
### Positive
- Cross-language parity improves (shared mental model and fixtures).
- Examples become more robust to model variability and interleaving.
- Reduced support burden from premature JSON parsing and ID confusion.

### Negative / tradeoffs
- The example-level shape is a simplification; docs must avoid implying it is the full wire contract.
- SDKs may need small adapter helpers to map native stream types to the canonical fields used in examples.

## Rollout plan
- Apply this ADR to:
  - Docs code tabs (Python/TS/Go)
  - Quickstarts “agentic workflow” template
  - `redwood-examples` runnable samples
- Add golden transcript tests that validate:
  - `tool_call_id` stability
  - interleaving correctness
  - presence of `tool_call.done` before parsing

## Open questions
- Whether `message.done` should be mandatory in the example envelope for all SDKs (some SDKs provide final message out-of-band). For now it is optional, but `response.done` is required in transcript-style examples.
