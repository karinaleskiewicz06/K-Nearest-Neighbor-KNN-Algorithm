Edge GPU OTA Onboarding and Rollback Runbook

Overview

Purpose: This runbook describes the recommended, production-safe process for onboarding an edge GPU node (physical or cloud-hosted edge instance) into Redwood's inference fleet with an over-the-air (OTA) update path and a tested rollback procedure. It focuses on private/air-gapped or partially connected edge sites where upgrades must be staged carefully to avoid model-serving regressions and customer impact.

Scope: Applies to edge GPU nodes that will run Redwood Private runtime for inference, managed via our edge agent and fleet-controller. Covers IaC changes, CI/CD packaging, preflight checks, staged OTA rollout, telemetry validation, and rollback mechanics. Not a hardware procurement guide.

SLOs and safety thresholds

- During OTA window, target p95 latency degradation < 20% compared to baseline for the node group.
- Per-node GPU utilization should not exceed 85% sustained for > 10 minutes post-upgrade.
- Error rate increase (5xx from runtime) must remain < 0.5% relative.
- If any threshold breached, automated rollback is triggered.

Prerequisites and environment checks

1) Inventory: ensure node appears in Fleet Inventory with correct tags (edge-site:<site-id>, tenant:<tenant-id>, gpu-type:<A100/T4>).
2) Connectivity: node must have outbound TLS connectivity to the control-plane endpoints or to a local relay (relay version >= 1.3.0). If air-gapped, ensure relay manifest previously validated.
3) Disk and GPU health: nvml query shows no ECC errors and free disk >= 30 GiB.

Commands (sanity checks):

- Check fleet registration: redwoodctl node status --node-id NODE_ID
- GPU health: nvidia-smi --query-gpu=memory.total,memory.used,utilization.gpu --format=csv
- Disk: df -h /var/lib/redwood | awk 'NR==2{print $4}'

Terraform/IaC considerations

- Use the edge-node module: modules/edge-node (see synopsis below). All module changes must follow the IaC module review checklist and be accompanied by a `plan` that passes the policy engine (policy checks: network egress, host-path mounts, kms-integration).

CI/CD and OTA packaging

- Build artifact: each runtime and agent release produces an archival bundle (signed .tar.gz) and a container image. The CI pipeline creates two artifacts: `edge-agent-vX.Y.Z.tar.gz` and `edge-runtime-container:sha256-...`. Both are published to the artifact registry and a signed manifest stored in the release channel bucket.
- Channel model: channels are `canary` | `staged` | `stable`. By default, onboarding uses `staged`.

Pipeline steps (high level):
1) Merge IaC changes (if any) and run `terraform plan`. Ensure plan is approved and policy checks pass.
2) Ship agent/runtime build to `staged` channel using `ci/edge/release` pipeline.
3) Create a rollout plan in the Fleet controller UI or via `redwoodctl rollout create --channel staged --node-selection "tag:site=site-42 and tag:role=edge-inference" --batch-size 5`

Staged rollout procedure

1) Preflight batch selection: choose a small pilot group (batch-size 1-5 nodes) in a non-production tenant or a low-traffic partition. Prefer nodes with identical hardware to target fleet.
2) Preflight checks (automated):
   - Helm health for local relay and kube-proxy (if deployed)
   - Agent heartbeat > 5 minutes
   - Prometheus scrape success for node exporter and gpu exporter
3) Initiate OTA: push artifacts to the node by triggering the rollout. The edge agent will: download, verify signature, stop runtime, unpack, and start the new runtime inside a containerd snapshot.
4) Post-install validation (automated):
   - Runtime healthcheck endpoint /health returns OK within 60s.
   - Canary inference job (provided in repo `ci/edge/canary`) runs 100 requests with expected response shape and latency.
   - Telemetry sanity: cpu/gpu utilization and memory within expected ranges.
5) Wait 30 minutes for production-like traffic to flow (or until canary job completes). If all checks pass, expand to next batch.

Automated safety gates

- Gate 1 (signature verification): abort if artifact signature mismatch.
- Gate 2 (healthcheck): abort and mark node for rollback if /health fails 3 times in a row.
- Gate 3 (SLOs): abort entire rollout if aggregated p95 latency across the rolling batch increases > 20% or error rate > 0.5% for five consecutive minutes.

Telemetry and dashboards to watch

- Dashboards: Edge -> Node Health, Edge -> OTA Rollouts, Serving -> Model Latency by Node.
- Key metrics: node.agent_last_seen, node.ota_status, runtime.5xx_count, runtime.p95_latency, gpu.utilization, disk.available_gb.
- Alert thresholds mapped to gates (configured in Grafana/Alertmanager).

Rollback procedure (manual and automatic)

Automatic rollback triggers: any of the safety gates fail during or within the rollback window (30 minutes after upgrade). The edge agent supports two rollback mechanisms: image-level rollback to previous container image, and full artifact reinstall to previous signed bundle.

Manual rollback steps (if automation failed):
1) Halt rollout expansion: `redwoodctl rollout pause ROLLOUT_ID`
2) Mark affected nodes and run the rollback command: `redwoodctl node rollback --node-id NODE_ID --to-version vX.Y.Z`
3) Verify node returned to RUNNING and /health OK.
4) Re-run the canary inference job locally against the node and validate outputs.
5) If rollback succeeds, add node to quarantine group for deeper postmortem and hardware checks.

Rollback verification checklist:
- /health OK for 3 consecutive scrapes spaced 30s apart
- runtime.5xx_count back to baseline within 10 minutes
- No new disk or ECC errors reported
- Agent logs show successful image revert and start sequence

Post-deployment validation and postmortem

- After a full rollout completes, the owner must run a regression suite (see `ci/edge/regressions`) that validates model outputs on a standard prompt set. Any semantic regressions must be triaged by Applied ML and may trigger a model pin or hotfix.
- If rollback occurred, create an incident in the incident tracker with tags `edge-ota`, `rollback`, and link to the rollout ID. Include the full `redwoodctl` logs exported via `redwoodctl logs --node-id NODE_ID --since 2h > node-N.log`

Operational tips and common failure modes

- Network flakiness: edge nodes behind cellular or intermittent links may stall during artifact download. Use the relay appliance or pre-warm artifacts to local caches.
- Disk pressure: older nodes with < 50 GiB available can fail unpacking. Ensure minimum disk reservation in IaC.
- Incompatible kernel or drivers: validate nvidia-driver and docker/containerd versions before scheduling. A migration matrix is maintained in the team wiki.

FAQ

Q: Can we upgrade runtime and agent separately?
A: Yes, but prefer upgrading the agent first on edge sites to ensure the OTA protocol supports the new runtime image. See compatibility matrix in the release notes.

Q: How long is a safe maintenance window?
A: Typical staged rollout for a 200-node site takes 3–6 hours with batches of 10 and 30-minute observation windows.
