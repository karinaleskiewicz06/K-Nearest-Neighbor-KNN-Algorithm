Bastionless GPU Access and IaC Playbook

Summary
-------
This playbook defines the recommended architecture, Terraform/IaC modules, and runbook for *bastionless* access to on-prem or VPC-isolated GPU nodes. The goal is to enable secure, auditable, ephemeral developer and operator access without a permanent bastion host, lowering attack surface while preserving fast interactive debugging.

Scope and applicability
-----------------------
- Applies to on-prem GPU clusters and private VPC deployments used for inference or evaluation where SSH/RDP-like access is required for debugging, profiling, or emergency remediation.
- Intended for GPU infra owners, SREs, and platform eng who manage node images, networking, and access tooling.
- Not a replacement for fully automated remediation; use for short-lived investigative sessions only.

Assumptions
-----------
- Central identity provider supports OIDC and short-lived certificates (e.g., Okta/GCP/Azure AD).
- Customers/operators can run a small control-plane service in the perimeter (K8s, VM) that acts as an access broker.
- Terraform module repository is available at git::ssh://git@github.com/redwood/terraform-modules.git//bastionless-tunnel

High-level architecture
-----------------------
1) Access broker (control-plane): mTLS-protected service in a public subnet that exchanges OIDC tokens for ephemeral SSH certs and injects ephemeral routes for a specific session.
2) Short-lived overlay tunnels: IPSec/WireGuard or TLS-based tunnels created per-session. Tunnels are timeboxed (default 15m) and automatically torn down.
3) Node-side agent: lightweight agent on GPU node (or sidecar) that accepts ephemeral certs and enforces ALLOW lists at process/user level.
4) Audit pipeline: all grants, cert issuance, and session metadata are written to the centralized audit log (immutable S3/GCS bucket + SIEM ingest).

Architecture diagram (text)
- User -> (OIDC) -> Access Broker -> (WireGuard mTLS tunnel) -> Node Agent -> GPU Node
- Audit -> S3 bucket + Dataflow -> Security team SIEM

Design goals and constraints
----------------------------
- No long-running bastion VMs or permanently open SSH ports.
- Least-privilege: every session scoped to a single node or node-set, single command scope optional.
- Short-lived credentials and network paths (default 15 minutes; min 5m, max 1h with approval).
- Full audit trail: who, when, command list (where legal), session duration, and outbound egress origin.

Terraform module & config table
-------------------------------
Below are the core variables and recommended defaults for the *bastionless-tunnel* module. Apply per-region.

| variable | type | default | notes |
|---|---:|---:|---|
| region | string | us-west-2 | cloud region or datacenter identifier |
| onprem_subnet_cidr | string | 10.50.0.0/24 | CIDR for ephemeral tunnel endpoint on the customer side |
| broker_instance_count | number | 2 | HA pair recommended (keep odd for leader election) |
| oidc_provider_url | string | <required> | OIDC issuer used for short-lived cert exchange |
| max_session_ttl_minutes | number | 15 | enforcement ceiling for ephemeral tunnels |
| allowed_user_groups | list | ["infra-operators"] | IAM groups allowed to request sessions |
| audit_bucket | string | redwood-infra-audit | S3/GCS bucket for session logs |

-------------------------
```hcl
module "bastionless_tunnel" {
  source            = "git::ssh://git@github.com/redwood/terraform-modules.git//bastionless-tunnel?ref=v0.3.1"
```

Network firewall / NAT rules (minimum)
-------------------------------------
- Allow outbound 443 from broker to OIDC provider and SIEM endpoint.
- Allow broker -> node control port (WireGuard UDP 51820 or configured TLS port).
- Restrict management plane to known IP ranges and tenant tags.

Operational runbook: typical session flow
---------------------------------------
1) Request: Operator runs CLI/console to request a session. Example:
   - redwoodctl access request --node gpu-node-123 --ttl 15m --reason "perf-debug"
2) Broker validates OIDC token, group membership, and optional 2nd factor.
3) Broker provisions ephemeral WireGuard keypair and injects a temporary route via SDN controller (or BGP session) scoped to the node for the session TTL.
4) Node agent accepts the ephemeral key and starts a lightweight tunnel endpoint bound to localhost:2222.
5) Operator connects: ssh -i /tmp/session.key -p 2222 operator@gpu-node-123 (proxying through local tunnel).
6) On session expiry or manual termination, broker signals node agent to tear down tunnel and revokes certs; audit event recorded.

Emergency remediation (when ephemeral path fails)
------------------------------------------------
1) If automated tunnel creation fails:
   - Step 1: Re-run `redwoodctl access request` with `--debug` and capture broker logs.
   - Step 2: Verify SDN controller accepted the route (check BGP/route-update logs).
   - Step 3: If node-agent failed to bind, use the control-plane API to push the agent status patch or rebootstrap the agent via: `kubectl -n infra-tools rollout restart daemonset/gpu-node-agent`.
   - Step 4: If immediate access still required and security-approved, escalate to oncall and temporarily open port 22 from your IP with a short TTL rule in the perimeter firewall (manual exception tracked in ticket).

Canary rollout checklist (how we deploy this capability safely)
---------------------------------------------------------------
1) Deploy broker and Node Agent in non-prod region. Verify session lifecycle end-to-end.
2) Add telemetry: session_issued_total, session_failed_total, tunnel_create_latency_seconds.
3) Enable audit export to staging SIEM.
4) Run 50 low-risk sessions (15m each) and validate no data-plane leakage.
5) Gradually enable in prod for a subset of tenants (feature flag) with 24/7 oncall coverage for first 72 hours.

Monitoring, SLOs and alerting
-----------------------------
- SLOs (access flow):
  - Mean tunnel creation latency < 5s (95th percentile < 15s).
  - Cert issuance success rate >= 99.5%.
  - Unauthorized access attempts < 0.5% of total requests.
- Key alerts:
  - FIRING: session_failed_total > 5 in 5m (severity P2)
  - FIRING: cert_issue_latency_seconds:95th > 30s (P2)
  - FIRING: audit_sink_write_errors > 0 (P1)
- Suggested PromQL examples: `sum(rate(session_failed_total[5m])) by (region) > 5`

Security & compliance notes
--------------------------
- All session metadata must be retained for at least 365 days in the audit bucket.
- Node agents must run as unprivileged processes; do not give direct root shells by default. Use sudo policies limited to a pre-approved command list.
- Approvals for session TTL > 1h must be recorded with a time-stamped signature in the ticket system.
- Periodic automated penetration tests should validate that ephemeral tunnels cannot be extended past TTL.

Testing & CI/CD guidance
-----------------------
- Add unit tests for the Terraform module variables and a plan-stage check that denies if `max_session_ttl_minutes` > 60.
- Integration tests: a small VM-based harness that performs a full session lifecycle (request -> connect -> run command -> teardown) as part of the CI pipeline. Use ephemeral GPU testbeds in the CI environment.
- Release gating: require `tfsec` and `checkov` scans, plus e2e session probe success >= 95% before promote.
