Postmortem: SEV-2 API gateway rate-limit regression (2026-01-12)

A configuration regression in the rate-limit service caused several paid tenants to be evaluated against the default (stricter) tier. The regression was introduced during a config refactor and was not caught by canary validation.
~18% of requests to /v1/chat/completions returned 429 for paid tenants that should have been within quota. Some customers retried aggressively which increased p95 latency by ~120ms.
09:41 UTC: Alert triggered for elevated 429s (api-gateway).
09:44 UTC: On-call acknowledged; initial hypothesis was customer traffic spike.
09:50 UTC: Correlated spike to rate-limit-service config deploy 2026.01.12.3.
10:02 UTC: Rolled back config bundle; 429 rate began dropping.
10:10 UTC: Verified tenant tier mappings restored for top affected tenants.
10:33 UTC: Incident resolved; monitoring stable for 20 minutes.
Automated alert on 429 rate per route (api-gateway) paged on-call.
During a refactor of tenant tier lookup, the fallback path incorrectly defaulted to self_serve for tenants missing a cache entry. A cache warming job was also disabled in the same change, increasing misses.
Rolled back the rate-limit config bundle and re-enabled the cache warming job. Manually purged and rebuilt the tier mapping cache.
Alerting fired quickly and rollback was safe. Customer Success had a ready message template for transient 429s.
Canary checks validated only aggregate 429 rate, not per-tier correctness. The cache warming job disablement was not flagged in review.
Add canary validation that checks tier mapping for a fixed set of tenant IDs (Platform Engineering; due 2026-02-05).
Create an automated check that ensures the cache warming job is enabled in prod after config deploy (SRE; due 2026-02-12).
Update rate-limit-service runbook with a section on cache miss symptoms and remediation (Platform Engineering; due 2026-01-28).
