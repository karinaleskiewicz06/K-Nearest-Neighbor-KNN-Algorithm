GPU placement: SLO-driven provisioning and tenant throttling playbook

Overview

This playbook defines Redwood's SLO-driven GPU placement and provisioning patterns for multi-tenant workloads. It describes how we translate latency/cost SLOs into placement decisions, automated Terraform/IaC flows, CI/CD promotion for placement policy changes, and step-by-step runbook actions when placement or tenant throttling is required. This doc intentionally spans operational guidance (runbooks) and infra engineering patterns (modules, variables, alerts) so platform and infra teams can operate consistently.

Goals

- Ensure tenant request latency 95th percentile (P95) meets the configured SLOs per tier (see SLO table).
- Bound per-tenant cost by applying quota, batching, and throttles when capacity is constrained.
- Make placement decisions deterministic and observable: policies are codified in Terraform + placement service config, and decisions surface via traces and audit logs.
- Enable safe, auditable rollouts for placement policy changes via CI/CD and canary promotion.

Ownership and escalation

- Primary owner: GPU Fleet & Capacity (eng-infra)
- Secondary owners: Serving Runtime, SRE (oncall for incidents)
- Pager escalation: follow standard infra oncall escalation; if capacity shortage persists >30m, escalate to Head of Infra.

SLOs and Capacity Targets

| Customer tier | Latency SLO (P95) | Target CPU/GPU margin | Placement urgency | Cost limit per 1k tokens |
|---|---:|---:|---|---:|
| free | 800ms | 25% | low | $0.50 |
| standard | 300ms | 20% | medium | $1.50 |
| business | 150ms | 15% | high | $3.50 |
| enterprise (SLA) | 100ms | 10% | critical | negotiated |

Notes: margin = target headroom on provisioned capacity to absorb bursts. Placement urgency controls fallback order (e.g., prefer warm-pool, then heterogeneous pools, then burst to cloud spot).

Placement decision flow (high-level)

1. Ingest request metrics: seq_len, model, token_rate, tenant_tier, historical latency distribution.
2. Evaluate placement policy engine: policies defined by (model, tenant_tier, req_size, prefer_local) rules.
3. Score candidate pools by expected latency (inference_model_profile), available GPU slots, eviction risk, and cost score.
4. Apply throttles/quota if score indicates risk of SLO violation and insufficient pool capacity.
5. Emit decision with reason code and send trace + event to observability.

Policy model (codified config)

- policy_id: string
- match: { tenant_tiers: [..], models: [..], seq_len_range: [min,max], prefer_local: boolean }
- placement_order: [warm_pool, spot_pool, burst_cloud, remote_pool]
- throttle: { enabled: bool, qps_limit: int, token_rate_limit: int }
- sla_overrides: { latency_ms_target: int }

Example policy YAML (stored in Git and applied via Terraform as data):

```
# modules/placement/policies/enterprise-low-latency.yaml
policy_id: enterprise-low-latency
match:
  tenant_tiers: [enterprise]
  models: [redwood-xl, redwood-quant-8]
  seq_len_range: [0,4096]
  prefer_local: true
placement_order:
  - warm_pool
  - dedicated_pool
  - cross_region_pool
throttle:
  enabled: false
sla_overrides:
  latency_ms_target: 100
```

Terraform/IaC module pattern

We maintain a small placement module that converts YAML policy files into cluster placement objects (k8s CRs or control-plane records) and wires required IAM roles and network attachments. The module is intentionally minimal: it does not contain runtime secrets or per-tenant keys.

Example (tfvars + module invocation):

```
# modules/placement/usage.tf
module "placement_policy" {
  source = "git::ssh://git@github.com/redwood-inference/infra-modules.git//modules/placement?ref=main"
  name   = "enterprise-low-latency"
  policy_yaml = file("${path.module}/policies/enterprise-low-latency.yaml")
  owner = "gpu-fleet"
}
```

Module responsibilities checklist

- Validate policy YAML against JSON schema (CI step).
- Render placement CRs and optional RBAC bindings.
- Emit outputs: placement_id, affected_clusters, change_hash.
- Create a reversible change set (terraform plan shows exact CR changes).

CI/CD promotion and safety nets

1. All policy changes must be authored in feature branches and include unit tests that validate schema and simple decision expectations.
2. CI pipeline runs: lint -> unit tests -> plan. Plan must be reviewed by at least one reviewer from GPU Fleet.
3. Canary promotion flow: apply policy to a small canary namespace (temperature: 2% of traffic or 1-2 tenants) and monitor latency + error rates for 1 hour.
4. Automatic rollback: if canary P95 increases >20% relative to baseline or error rate increases >0.5% absolute, revert change and open a rollback PR.

Example GitHub Actions job names

- validate-policy-schema
- terraform-plan-placement
- terraform-apply-canary
- monitor-canary-and-promote

Runbook: immediate actions for placement SLO breach

Trigger: Alert -> placement_slo_breach_{tier} fired.

Steps:
1. Acknowledge alert oncall and capture current dashboard (time window: last 15m, 1h).
2. Identify affected placement pools: run `rictl placement list --filter status=degraded` and `rictl placement describe <placement_id>`.
3. Temporarily divert new requests to fallback pools that preserve SLO where possible: `rictl placement set-preference <tenant_id> --fallback=dedicated_pool` (exec by SRE).
4. If no fallback exists, apply emergency throttle to low-priority tenants: `rictl tenant throttle --tenant-group=free --qps=5 --duration=30m`.
5. If capacity shortage caused by runaway jobs, identify pods with high GPU utilization: `kubectl -n eval top pods --sort-by=cpu` and trigger eviction on offending pods after confirmation.
6. Open internal incident and tag owners: gpu-fleet, serving-runtime, and oncall.
7. If capacity is exhausted and expected to remain >1h, trigger burst policy to cloud (see "Burst to cloud" section) and notify CostOps.
8. Post-incident: run retrospective template (see section).

Burst to cloud policy (safety conditions)

- Allowed for standard & free tiers only if expected shortage <4h and cost delta < 2x baseline.
- Enterprise tenants require explicit approval.
- Use pre-authorized cloud accounts labeled `burst-pool-<region>` with constrained IAM role and egress firewall rules.

Terraform snippet for burst cluster attachment (example vars):

```
resource "aws_eks_cluster" "burst_pool" {
  name = var.burst_cluster_name
  # minimal nodegroup config with spot preferred
}

module "placement_attachment" {
  source = "git::git@github.com:redwood-inference/infra-modules.git//modules/placement-attachments"
  placement_id = var.placement_id
  target_cluster = aws_eks_cluster.burst_pool.id
}
```

Throttling strategy (tenant fairness)

- Prefer dynamic token-bucket throttles: tokens replenished per second owned by tenant.
- Apply progressive backoff: 100% -> 90% -> 75% -> 50% qps at 5m intervals when overloaded.
- Keep a low-priority tenant blacklist for urgent capacity freeing; blacklisted tenants are notified and transferred to best-effort queue.

Key metrics and alert thresholds

- placement_p95_latency_ms (per-tier): alert if > SLO * 1.2 for 10m
- placement_available_slots_ratio: alert if < margin threshold for 5m
- tenant_throttle_rate: alert if > 5% sustained over 15m
- eviction_rate: alert if > 1/min for 10m

Instrumentation and observability

- Emit decision logs with fields: placement_id, candidate_pools, chosen_pool, reason_code, evaluated_latency_ms, cost_estimate_cents.
- Correlate traces with request ids and tenant ids; add tags for policy_id and change_hash.
- Dashboard should expose hot path latencies (P50/P95/P99), slot utilization per pool, and per-tenant quota consumption.

Chaos and preflight validation

Before any placement module change is promoted to prod runbook:

1. Run preflight chaos for 2h on staging: simulate 25% GPU node loss and validate P95 for standard tier remains within 1.5x baseline.
2. Run tenant fairness smoke tests: launch synthetic low/standard/enterprise workloads and verify throttles apply deterministically.

Post-incident retrospective template

- Summary: short incident narrative (1 paragraph)
- Timeline: key events with timestamps
- Root cause: technical and human factors
- Action items: owner, target date, and verification steps
- Learnings and documented policy changes

Appendix A: CLI snippets and common commands

- List placements: `rictl placement list --json | jq .`
- Describe placement: `rictl placement describe <id> --verbose`
- Throttle tenant: `rictl tenant throttle --tenant-id <id> --qps 10 --duration 30m`
- Attach burst cluster: `terraform apply -target=module.placement_attachment`

Appendix B: JSON schema (high-level overview)

- policy_id: string
- match: object (tenant_tiers: [string], models: [string], seq_len_range: [int,int])
- placement_order: [string]
- throttle: object (enabled: bool, qps_limit: int)

Appendix C: Change control and audit

- All terraform applies for placement modules require 2 approvers for production environment.
- Changes are tagged with change_hash and stored in the change-audit index for 90 days.
- Emergency changes should be followed within 24h by a normal PR explaining the emergency and retro notes.
