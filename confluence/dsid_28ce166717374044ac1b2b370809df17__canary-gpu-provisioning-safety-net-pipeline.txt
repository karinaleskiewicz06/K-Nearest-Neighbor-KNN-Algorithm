Canary GPU provisioning and safety-net pipeline

Overview

This document describes the canonical canary provisioning pipeline we use to introduce new GPU node pools and IaC changes into production. It combines Terraform module contracts, CI/CD promotion, automated smoke validation, and automated safety-net rollback to reduce blast radius when provisioning GPUs (spot or on-demand) across accounts and regions. The intended audience is infra engineers, SREs, and platform owners.

Goals

- Reduce risk of large-scale GPU provisioning incidents by phasing changes into small canaries.
- Provide automated safety nets (health gates, quota checks, cost caps) that fail fast.
- Maintain reproducible IaC artifacts and promote golden images with traceable provenance.
- Integrate with cost and quota tooling so provisioning respects budgets and SLAs.

Scope

Applies to: GPU node pools managed by our Terraform modules (gpu-node-pool), node bootstrap and golden-image pipelines, and CI/CD pipelines that run terraform apply in customer or infra accounts. Excluded: ephemeral CI-only pools created inside ephemeral test clusters.

Design overview

High-level components:
- terraform modules: gpu-node-pool, node-bootstrap, iam-gpu-guards
- CI pipelines: gpu-provisioner-canary (short-lived), gpu-provisioner-promote (full rollout)
- services: node-bootstrapper, gpu-provisioner, spot-fallback-autoscaler
- observability: gpu-provisioning-metrics (Prometheus), cluster-health (Grafana), deployment-trace (Jaeger)

Pipeline stages (end-to-end)

1) Authoring and unit tests
   - Engineers update gpu-node-pool Terraform module or environment overlay.
   - Run local unit tests (terratest) and linters: terraform fmt, tflint, checkov.

2) Build artifact and image promotion
   - Golden image builder produces AMI/container images with versioned tags (e.g. golden-gpu:2025-01-10-1).
   - Images are immutably stored in the image registry with SBOM and build provenance metadata.

3) Plan & canary apply (CI)
   - CI job gpu-provisioner-canary runs terraform plan against the canary workspace and posts plan to PR.
   - On approval, CI runs terraform apply into the canary account/namespace which provisions a single small canary pool (1-2 nodes).

4) Smoke validation (automated) — must pass within 15 minutes
   - Node readiness: all nodes Ready in < 5 minutes.
   - GPU driver probe: nvidia-smi returns valid output and expected compute capability.
   - Baseline inference test: run a 512-token generation on the canary node; p95 completion < 350ms for microbench workload.
   - Image and bootstrap verification: verify hostname, bootstrap logs, and KMS key attachment.

5) Observability hold and health gates (10–30 minutes)
   - CI waits for observed metrics to be within thresholds. If any gate fails, automatic rollback triggers.

6) Promotion to staged rollout
   - If the canary passes, promotion pipeline gradually increases pool size by 20% every 30 minutes (max concurrency configurable).

7) Full rollout and audit
   - On final promotion, Terraform state is merged to the main workspace and tagging/labels applied for billing and owner tracking.

Safety gates and guardrails

- Quota pre-check: Query Cloud Quota API and internal quota DB. If projected GPU-hours > 90% of account quota, block.
- Cost threshold: Abort if estimated cost delta > environment cost cap (default $4,000/day per org).
- IAM approval: Any change that modifies iam-gpu-guards or adds new cross-account roles requires at least two approvers from Security and Platform.
- Node health thresholds (sample):
  - Node readiness failure rate <= 1% during canary window.
  - Driver probe success >= 99%.
  - Inference smoke p95 latency regression <= +15% vs baseline.

CI/CD pipeline (condensed)

- gpu-provisioner-canary (runs for PRs on main):
  - steps: checkout -> terraform init -> terraform validate -> terratest -> terraform plan -> notify PR -> on approval terraform apply (canary workspace) -> run smoke tests -> hold for gates -> notify success/failure

Sample GitHub Actions job snippet:

```
jobs:
  canary:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v2
      - name: terraform fmt && validate
        run: terraform fmt -check && terraform validate
      - name: terratest
        run: go test ./test/ -run TestCanary
      - name: terraform apply
        run: terraform apply -auto-approve -var-file=env/canary.tfvars
```

Observability & SLOs

- Metrics to monitor (Prometheus):
  - gpu_provisioning.apply_duration_seconds (SLO: p95 < 15m for canary apply)
  - node_exporter.gpu_driver_ok (SLO: >= 99.9%)
  - gpu_inference.smoke_latency_ms (SLO: p95 < 400ms for microbench)
  - terraform_plan_drift_detected_total (alert if > 0 after rollout)

Dashboards:
- Canary Overview (shows canary pools, node readiness, smoke test results)
- Cost Delta (shows estimated vs actual projected spend)

Rollback & remediation runbook (automated + manual)

1) Automated rollback (triggered by pipeline):
   - CI calls terraform destroy on canary workspace or executes module rollback plan.
   - Notify #infra-ops with panic links and runbook link.

2) Manual remediation (if automated fails):
   1. Pager to oncall for infra with priority SEV-2.
   2. Check Prometheus dashboards for node readiness, kubelet logs, and cloud provider events.
   3. Run `kubectl describe node <name>` and `journalctl -u node-bootstrapper` on affected node(s).
   4. If node bootstrap failed, re-run bootstrap job: `aws ssm start-session` -> `/opt/node/bootstrap.sh --replay` (see bootstrapper docs).
   5. If driver installation failed, mark pool as cordoned: `kubectl cordon` and `kubectl drain` then revert image or kernel.
   6. After fix, re-run smoke tests against the isolated pool before re-enabling rollout.

Troubleshooting matrix

- Symptom: Node remains in NotReady > 10 minutes.
  - Likely cause: bootstrap timeout, missing CNI plugin, or cloud provider provisioning lag.
  - Actions: check cloud provider events -> check bootstrap logs -> verify AMI region availability.

- Symptom: Smoke test latency spike on canary.
  - Likely cause: misconfigured kernel, NUMA, or GPU ECC mode.
  - Actions: compare nvidia-smi output vs baseline, re-run microbench with perf counters, roll back pool image.

Access and IAM guardrails

- Principle of least privilege: terraform apply role (arn:aws:iam::PROD:role/gpu-provisioner) limited to specific resource prefixes.
- Example policy (condensed):
```
{
  "Version": "2012-10-17",
  "Statement": [
    {"Effect":"Allow","Action":["ec2:RunInstances","ec2:CreateTags"],"Resource":"arn:aws:ec2:us-west-2:123456789012:instance/*"},
    {"Effect":"Deny","Action":["iam:CreateRole"],"Resource":"*"}
  ]
}
```

Cost and quota controls

- Estimated cost delta is calculated during plan stage using the `cost-estimator` action. If delta exceeds env cap, pipeline fails with a soft-block requiring manual approval.
- Tagging policy: Every pool must include tags: owner, billing_code, team, purpose, cost_center. Missing tags cause post-create remediation.

Testing & validation strategy

- Regular canary rehearsals: monthly exercises where we provision identical canaries in staging and validate rollback timings.
- Chaos validation: simulate instance termination and network partitions to verify spot-fallback-autoscaler and fleet rebalancing.
- Integration tests: terratest suites exercise IAM and quota pre-check code paths.

Ownership and SLA

- Primary owner: infra/gpu-platform (oncall rotation). Secondary owner: eng-sre.
- SLA for remediation of a failed canary is 2 business hours for rollback or mitigation.

Runbook quick commands

- Query quota: `python tools/quota_check.py --account prod --region us-west-2 --gpu-type p4d`
- Trigger rollback (CI): `gh workflow run gpu-provisioner-canary --field action=rollback`
- Re-run smoke tests: `scripts/run_gpu_smoke.sh --kubecontext prod-canary`
