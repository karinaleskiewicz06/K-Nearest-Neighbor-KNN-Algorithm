Runbook: Deploying Hosted API Services to Production

h1. Overview
This runbook describes how to deploy Hosted API services (router, inference-gateway, streaming-gateway, embeddings) to production. Follow this in conjunction with the Production Change Management Standard and Prod Deployment Gates.

h1. Ownership
* Primary owner: Eng Platform
* On-call escalation: #eng-oncall and #eng-platform

h1. Preconditions
Before you begin, confirm the following are true:
1. A change record exists and includes summary, risk assessment, verification plan, and rollback plan.
2. Approvals are captured (peer + service owner; add SRE/security as required).
3. CI is green; image digests are pinned (no "latest" tags).
4. You have access to the deployment toolchain and production kube contexts.

h1. Identify the target
* Service(s): router / inference-gateway / streaming-gateway / embeddings
* Region(s): us-east-1, us-west-2, eu-central-1 (deploy canary first)
* Deployment mode: canary then full

h1. Step-by-step procedure
1. Announce intent (internal)
   * Post in #eng-releases with: change record link, services, canary region, start time, rollback trigger.

2. Pre-deploy checks
   * Check current error rates and p95 latency dashboards for the target services.
   * Confirm no active incidents affecting the same services.
   * Confirm error budget posture allows change (see Change Freeze and Risk Assessment).

3. Canary deploy
   * Deploy to canary region (default us-west-2) or 1% traffic slice if supported.
   * Commands (example):
     - "deployctl promote --service inference-gateway --env prod --region us-west-2 --image-digest sha256:..."
     - "deployctl status --service inference-gateway --env prod --region us-west-2"
   * Wait until rollout completes and pods are ready.

4. Canary validation (15 minutes minimum)
   * Run smoke tests:
     - /v1/chat/completions (streaming + non-streaming)
     - /v1/embeddings
   * Validate: error rate, p95 latency, saturation signals, and request timeouts.
   * If metering changed, validate token counts on test account in canary region.

5. Full rollout
   * If canary passes criteria, deploy remaining regions in order: us-east-1 -> eu-central-1.
   * Deploy one region at a time; do not run concurrent region rollouts for router + gateway changes unless explicitly approved.

6. Post-deploy validation (60 minutes)
   * Confirm global dashboards are stable.
   * Confirm no new alerts firing (or document expected alerts and resolution).
   * Confirm logs/traces are visible for the new build.

7. Closeout
   * Update the change record with: canary results, rollout times, dashboard links, and final build identifiers.

h1. Rollback triggers
Rollback immediately if any occur during canary or full rollout:
* Error rate increases by \u003e 0.2% absolute sustained for 5 minutes
* p95 latency increases by \u003e 10% sustained for 10 minutes
* Elevated timeouts or queue depth indicates saturation
* Customer-reported incident plausibly tied to the change

h1. Rollback (quick path)
* Use the previous known-good image digest and redeploy to the impacted region(s).
* If the router policy config changed, revert the config bundle first.
* Follow the dedicated Rollback and Post-change Validation runbook for full steps and post-rollback monitoring.

h1. Notes and tips
* Prefer deploying router changes separately from inference-gateway changes to reduce blast radius.
* If deploying a schema migration, verify backward-compatibility by running mixed-version canary for at least 30 minutes.
