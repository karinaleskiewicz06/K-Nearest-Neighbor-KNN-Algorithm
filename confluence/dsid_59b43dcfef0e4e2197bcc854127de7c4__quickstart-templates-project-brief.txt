Quickstart Templates (RAG + Agents) — Project Brief

h1. Summary
Redwood Inference’s Developer Experience (DevEx) org is building *production-minded Quickstart Templates* for *RAG + agents*.

These templates are opinionated scaffolds that help developers go from *sign-up → running locally → deployed app → observable in production* with safe defaults. The goal is to reduce onboarding friction while ensuring templates are reliable, secure, and maintainable.

This brief defines goals, non-goals, target personas, initial template lineup, and the definition of success (including time-to-first-success, template retention, and support deflection).

h1. Problem Statement
Developers evaluating Redwood often ask for “a working, production-ready RAG app” rather than isolated SDK snippets. Current gaps:
* Too many choices early (models, frameworks, infra) without guardrails.
* Lack of consistent instrumentation makes debugging and cost attribution hard.
* Examples are not always resilient to real-world failure modes (streaming disconnects, proxy behavior, rate limits).
* Support tickets repeat the same setup issues (401s, 429s, OTel exporter configuration).

h1. Goals
h2. Primary goals (v1)
1) *Fast activation:* Provide a guided path to a first successful, observable request.
2) *Production-minded by default:* Safe timeouts/retries, sensible token/cost limits, guardrails for agent loops and tool calls.
3) *Operational hooks:* Standard metrics, traces, and logs that align with Redwood Observability/SRE standards.
4) *Maintainability:* Versioned releases, CI smoke tests (streaming/tool-calling), dependency pinning, and a consistent template structure across languages.

h2. Secondary goals
* Keep *vendor lock-in minimal* via provider abstraction and “drop-in” replacement patterns.
* Provide deployment recipes covering common paths for Hosted API users and a clear bridge to Dedicated/Private guidance.

h1. Non-Goals
The following are explicitly out of scope for v1:
* Building a full-featured end-user product UI (templates may include a minimal web endpoint or simple UI, but not a complete app).
* Supporting every vector database and every framework (we will start small with one local default and optional adapters).
* Shipping a fully managed ingestion service; templates will include basic ingestion/indexing and clear extension points.
* Creating a new Redwood product feature branded as “Agents.” Templates demonstrate agent loops using existing API/SDK primitives.
* Supporting in-place auto-upgrades of existing apps. We will support “generate a new version” + documented migration steps.

h1. Target Personas
h2. Persona A: PLG engineer (self-serve)
*Profile:* Full-stack or backend engineer evaluating Redwood for a new feature.
*Needs:*
* Get running quickly with minimal setup.
* Clear defaults and guardrails that avoid footguns.
* Troubleshooting guidance that maps to common errors.
* Observability they can verify locally.
*Success looks like:* “I can answer questions over my docs in <1 hour, and I can see latency/token metrics and traces.”

h2. Persona B: ML/Platform engineer (enterprise)
*Profile:* Platform team standardizing inference; cares about reliability, compliance posture, and operability.
*Needs:*
* OTel-compatible telemetry with clear naming conventions.
* Secure patterns for secrets handling, logging redaction, and PII safety.
* Deployment options (Docker/k8s) and compatibility with Dedicated/Private.
* Model pinning and rollout-safe configs.
*Success looks like:* “This template is a credible starting point for a production service and aligns with our standards.”

h2. Persona C: Solutions/Support engineer (internal)
*Profile:* Helps customers adopt Redwood and needs reproducible reference implementations.
*Needs:*
* Predictable template behavior.
* Standardized error taxonomy and logs.
* A ‘doctor’ workflow for environment validation.
*Success looks like:* “I can diagnose issues quickly using the same signals across customers.”

h1. Scope and Deliverables
h2. What we are shipping (v1)
1) *Template repositories*
   * Python: RAG + agent quickstart (default)
   * TypeScript: RAG + agent quickstart (parity-focused)

2) *Core template capabilities*
   * Retrieval pipeline: ingestion → chunking defaults → indexing → retrieval interface
   * Agent loop with tool calling:
     * Tool schema validation
     * Max-iterations guard
     * Tool output size limits
     * Clear tool error handling
   * Streaming robustness:
     * Safe timeouts
     * Retry/backoff (including guidance for streaming reconnect)
     * Circuit breaker behavior for repeated failures
   * Config via environment variables (documented schema + validation on startup)
   * Example “golden prompts” and eval hook points for regression testing

3) *Observability instrumentation (standardized)*
   * OpenTelemetry traces, metrics, and structured logs
   * Required attributes/fields and redaction rules
   * Correlation IDs and Redwood request ID propagation
   * Prebuilt dashboards and recommended alert rules (via Observability Pack)

4) *Template CLI / scaffolder*
   * `init`: create a new project from a chosen template + write a version stamp
   * `doctor`: validate env vars, API connectivity, and local collector health with actionable remediation

5) *Documentation integration*
   * Docs IA updates: Quickstart Templates section + navigation
   * Walkthrough: RAG + agents template
   * Troubleshooting: common errors and how to interpret signals
   * Instrumentation guidance (language-specific patterns)

h2. Initial template lineup
We will launch with a deliberately narrow set to reduce maintenance risk:
* *RAG + Agents (Python)* — reference implementation and first-class support.
* *RAG + Agents (TypeScript)* — parity implementation with streaming and middleware patterns.

Planned follow-ons (post-v1, not launch blockers):
* “Batch embeddings” template (cost-focused ingestion)
* “RAG API only” minimal backend template
* Optional hosted vector DB adapter (one selection based on partner/customer demand)

h1. Design Principles (v1)
* *Secure by default:* no secrets in repo, no keys in logs, redaction enabled.
* *Resilient by default:* safe timeouts/retries; explicit backpressure and concurrency guidance.
* *Observable by default:* OTel-first with stable naming conventions and low-cardinality dimensions.
* *Opinionated but extensible:* clear interfaces and “replace this module” extension points.
* *Minimal vendor lock-in:* provider abstraction, model pinning configuration, and portability across Hosted/Dedicated/Private.

h1. Definition of Success (Metrics)
We will measure success using a mix of product analytics, operational signals, and support outcomes.

h2. KPI 1: Time-to-first-success (TTFS)
*Definition:* elapsed time from template start (CLI init or repo clone) to first successful, tagged Redwood response from a template run.

*Measurement approach:*
* Funnel events (opt-in telemetry):
  * `template_init` → `template_config_valid` → `template_first_request_started` → `template_first_request_succeeded`
* Use a template tag/header convention that does not include user content (privacy-safe).

*Targets (v1, 30 days post-launch):*
* Median TTFS: *≤ 20 minutes* (Python), *≤ 25 minutes* (TypeScript)
* 75th percentile TTFS: *≤ 45 minutes*

h2. KPI 2: Template retention (developer re-use)
*Definition:* the percentage of template-initialized projects that generate traffic again after initial day.

*Measurement approach:*
* `template_first_request_succeeded` followed by any `template_request_succeeded` in subsequent windows.

*Targets (v1, 60 days post-launch):*
* D7 retention: *≥ 25%*
* D30 retention: *≥ 10%*

h2. KPI 3: Support deflection
*Definition:* reduction in repetitive onboarding tickets attributable to improved templates + docs.

*Measurement approach:*
* Track volume and resolution time for top issues:
  * Auth misconfig (401)
  * Rate limits (429)
  * Streaming disconnects
  * OTel exporter misconfiguration
  * Tool schema/structured output parse errors
* Compare against a pre-launch baseline and monitor with Support Ops.

*Targets (v1, 60 days post-launch):*
* 15–25% reduction in tickets for the top 3 template-related categories
* ≥ 20% reduction in median time-to-resolution for template-tagged tickets

h2. Engineering quality gates (must-have)
* CI smoke tests for:
  * streaming stability
  * tool-call parsing + schema validation
  * basic retrieval correctness
* Dependency pinning + vulnerability scanning workflow
* Docs completeness checklist met for each template release

h1. Dependencies
* SDK changes (blocking or high leverage):
  * TypeScript: streaming reconnect behavior and improved error types
  * Python: trace context propagation helpers, standardized timeouts/retry policy
* Gateway support for a small, validated set of telemetry headers/tags (opt-in, privacy-safe)
* Observability Pack: dashboards/alerts and collector config examples
* Docs team bandwidth for IA and new content

h1. Risks and Mitigations
| Risk | Impact | Mitigation |
|------|--------|------------|
| Streaming instability across proxies | Poor UX, support load | Conservative defaults; reconnect guidance; CI smoke tests; documented proxy considerations |
| High-cardinality telemetry dimensions | Cost/perf issues in metrics backend | Enforce naming/dimension allowlist; review by Observability; default to low-cardinality attributes |
| Telemetry headers blocked by corporate proxies | Requests fail; adoption metrics incomplete | Make telemetry opt-in; fall back to query param or SDK tag where possible; document workaround |
| Template maintenance burden grows | Slow releases; quality regressions | Narrow v1 scope; shared utilities; versioned releases; CI gates; standard README structure |
| Security regressions (secrets/PII) | Compliance risk | Redaction by default; secure SDLC checks; dependency scanning; explicit logging guidance |
| Confusion around “agents” terminology | Misaligned expectations | Clear glossary and positioning (“agent loop example,” not a Redwood product feature) |

h1. Appendix
h2. Glossary
* *Template:* Opinionated starter project that compiles/runs, includes tests, observability, and deployment notes.
* *Quickstart Templates section:* Docs site area that links to templates, CLI, walkthroughs, and troubleshooting.
* *TTFS (time-to-first-success):* Time from init/clone to a first successful, observable request.

h2. Notes on privacy and telemetry
Template telemetry is *opt-in* and must never include:
* user prompts, retrieved document text, tool outputs, or customer identifiers
* raw API keys or secrets

Template tagging is limited to:
* template name, template version, language, and high-level deployment mode (local/docker/k8s) when explicitly configured.
