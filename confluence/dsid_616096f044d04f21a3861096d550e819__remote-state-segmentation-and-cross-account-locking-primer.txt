Remote state segmentation and cross-account locking — primer

SUMMARY
-------
This document defines Redwood Inference's recommended approach for Terraform remote state segmentation across accounts and teams, and the cross-account locking model we use to prevent concurrent state mutations. It consolidates security constraints, migration steps, CI/CD integration, and an operational runbook for state-related incidents.

GOALS
-----
- Prevent accidental state corruption by enforcing strong locking for all remote backends.
- Limit blast radius by segmenting state into logical units (environment, team, application).
- Enable safe cross-account operations for customers and infra teams (e.g., dedicated GPU accounts, shared networking accounts).
- Provide a repeatable migration path from monolithic state to segmented backends.
- Integrate state operations into CI/CD with automated approvals and observability.

NON-GOALS / OUT OF SCOPE
------------------------
- Replacing Terraform Cloud/Enterprise — this doc covers S3/DynamoDB and GCS/Cloud KMS patterns used today.
- Detailed module design — see iac-module-lifecycle-and-migration-guidelines for module-level guidance.

BACKGROUND / RATIONALE
----------------------
Historically we've seen a handful of incidents caused by large, shared tfstate files: long plan/apply cycles, accidental resource deletion during state moves, and occasional lock contention. To improve safety and scalability as the infra footprint grows (multi-region GPU fleets, private deployments), we standardize on small, environment-scoped state files with strong server-side locking and cross-account IAM roles for authorized operators.

STATE SEGMENTATION PRINCIPLES
-----------------------------
- Ownership boundary: each state file should map to a clear ownership boundary (team or product), not to person-level ownership.
- Environment isolation: prod/staging/dev must never share a backend bucket prefix. Use separate state files and (preferably) separate buckets.
- Resource surface: group resources that are operated together (networking, core infra, gpu-fleet) so changes are small and reviewed.
- Naming: terraform/state/<account-alias>/<env>/<component>.tfstate
- Least privilege: IAM roles that access state backends should follow least privilege and be audited.

RECOMMENDED BACKEND PATTERN (AWS example)
-----------------------------------------
- Backend: S3 bucket with server-side encryption (SSE-KMS) and versioning enabled.
- Locking: DynamoDB table with single-item locks using "LockID" key.
- Access model: S3 bucket owned by a central infra account; each consumer account assumes a "tf-state-access" role to read/write state for its assigned prefixes.
- Bucket policy: limit PutObject/DeleteObject to the infra role and prevent public access.

Example backend block (terraform):

terraform {
  backend "s3" {
    bucket = "redwood-tfstate-prod"
    key    = "terraform/state/account-gpu/prod/gpu-network.tfstate"
    region = "us-west-2"
    encrypt = true
    kms_key_id = "arn:aws:kms:us-west-2:111122223333:key/abcd-1234-efgh"
    dynamodb_table = "redwood-tfstate-locks"
  }
}

SAMPLE S3 BUCKET POLICY SNIPPET
-------------------------------
- Allow only the central infra account and authorized roles from consumer accounts to Get/Put objects.
- Deny s3:DeleteObject unless requester matches an escalation role.

IAM CROSS-ACCOUNT ROLE (consumer account -> infra account)
----------------------------------------------------------
- Role name: InfraStateWriter
- Trust policy: allow consumer account's CI/CD execution role to assume
- Attached policy: limited to s3:PutObject/GetObject/ListBucket on the state prefix and dynamodb:PutItem/GetItem for the lock table.

Example trust policy (conceptual):
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::CONSUMER_ACCOUNT_ID:role/ci-cd"},
      "Action": "sts:AssumeRole",
      "Condition": {}
    }
  ]
}

MIGRATION PLAYBOOK — MONOLITHIC -> SEGMENTED (high level)
---------------------------------------------------------
Preconditions:
1) Identify logical components and owners. Create a migration plan spreadsheet with old keys and target keys.
2) Ensure target S3 buckets and DynamoDB locks exist and are configured (encryption, versioning, lifecycle rules).
3) CI/CD pipelines must have access to assume the InfraStateWriter role for the target prefix.

Migration steps:
1. Lock the source state by performing a no-op apply from a controlled operator machine (ensures the state is stable).
2. On a machine with the operator's AWS credentials, run:
   - terraform state pull > legacy.tfstate
   - terraform state list (inspect to confirm)
3. For each component to split:
   a) terraform state mv -state=legacy.tfstate -state-out=component.tfstate 'module.network.aws_vpc.vpc' 'aws_vpc.vpc'
   b) Upload component.tfstate to the new backend via `aws s3 cp` using the infra account role (or use `terraform init -migrate-state`).
4. Validate by initializing Terraform in the consumer workspace and running `terraform plan`.
5. Remove moved resources from legacy state once all components are verified.
6. Repeat until legacy state is empty; keep a read-only archived copy with strict retention.

NOTE: Prefer using `terraform init -migrate-state` with remote backends when possible — it performs a coordinated move with automatic locking. Manual state mv is the fallback for complex moves.

ROLLBACK AND EMERGENCY PROCEDURES
---------------------------------
- If an apply corrupts a resource, restore a previous state version from the S3 object version history to a new key suffixed with `.recovery` and re-run `terraform plan` against that file.
- If locks are stuck (e.g., DynamoDB item never cleared), follow the Lock Escalation Runbook (below) before manually deleting the lock item.

LOCK ESCALATION RUNBOOK
-----------------------
1) Verify there are no running Terraform processes in CI/CD (check recent pipeline history within last 30 minutes).
2) If none, inspect the DynamoDB lock table for the LockID entry for the key prefix.
3) Check the lock item's "Info" field to see owner identity and timestamps.
4) If owner is an active session, wait or coordinate. If the owner is stale (e.g., > 2 hours), escalate to infra-oncall.
5) Infra-oncall to annotate the lock item with a comment, and if approved, delete the item. Record the deletion in the incident tracker and notify affected teams.

CI/CD INTEGRATION
-----------------
- Pipeline practice: Do not allow direct human-initiated terraform apply in prod. All applies must flow through an approved pipeline with an approver gate.
- Plan step: terraform init; terraform plan -out=tfplan; upload plan artifact.
- Apply step: gated; performs assume-role (InfraStateWriter) and terraform apply tfplan.
- Secrets: Use KMS-wrapped Terraform variables in the pipeline. Do not store raw credentials in repo.
- Drift detection: run scheduled plan jobs nightly for prod prefixes and alert on non-empty diffs.

OBSERVABILITY AND ALERTING
--------------------------
- S3: enable object-level logging via CloudTrail and send write/delete events to an ElasticSearch index for quick auditing.
- DynamoDB: CloudWatch alarm for ConditionalCheckFailed events (indicating lock conflicts > threshold).
- CI: failed lock acquisition more than 5 times in 10 minutes triggers an oncall page.

ACCESS CONTROL AND AUDIT
------------------------
- All state write roles are required to be assumed via an OIDC-connected CI principal or a long-lived service principal with MFA enforced for human-driven actions.
- Periodic audit: quarterly review of who can assume InfraStateWriter roles; automate via IAM Access Analyzer reports.

SECURITY HARDENING CHECKLIST
----------------------------
- [x] S3 bucket encryption with KMS
- [x] Versioning enabled on buckets with MFA delete for critical prefixes
- [x] DynamoDB lock table SSE enabled
- [x] Bucket policies restricting access to infra account and named roles
- [x] CloudTrail logging of s3:GetObject/PutObject/DeleteObject
- [x] Automated retention policy for archived tfstates (7 years for compliance cases)

EXAMPLE CI PIPELINE (conceptual YAML)
-------------------------------------
- name: terraform-plan
  steps:
    - checkout
    - setup-terraform
    - assume-role: infra-state-writer
    - terraform init -backend-config=key=terraform/state/${ACCOUNT}/${ENV}/${COMPONENT}.tfstate
    - terraform plan -out=tfplan
    - upload-artifact: tfplan
- name: terraform-apply (manual approval required for prod)
  steps:
    - assume-role: infra-state-writer
    - terraform apply tfplan

OPERATIONAL OWNERSHIP
---------------------
- State namespace ownership is assigned to the team listed on the state file path. Example: terraform/state/account-gpu/prod/* -> GPU Platform team.
- Central Infra team owns the S3 bucket, DynamoDB table, and central IAM roles.
- Oncall escalation: infra-oncall -> infra-sre lead -> head of infra.

VALIDATION & TESTING
--------------------
- Test migration in a synthetic account before real move. Maintain a test harness that simulates concurrency.
- Run chaos tests that simulate lost locks and concurrent applies in staging.

FREQUENT PITFALLS AND MITIGATIONS
---------------------------------
- Problem: Long terraform plans due to large state files. Mitigation: split state and reduce resource counts per state.
- Problem: Stale locks due to CI crashes. Mitigation: implement ownership metadata and shorter TTLs with automatic alerting.
- Problem: Cross-account role assumptions failing due to trust policy drift. Mitigation: include automated integration tests that validate assume-role flows weekly.

--------
