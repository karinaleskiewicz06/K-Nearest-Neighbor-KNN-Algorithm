Golden GPU Worker Images: Build, Versioning, Patch Cadence, and Rollbacks

## Overview
Golden GPU worker images are the default OS + driver/toolkit baseline for Redwood’s Kubernetes GPU fleets (Hosted, Dedicated, and internal perf clusters).

This page defines:
- The end-to-end image build pipeline and promotion flow
- Versioning and pinning policy (per pool / per region)
- CVE patch cadence and emergency patch handling
- Supported driver/CUDA/NCCL matrix by GPU type
- Rollback procedure with blast-radius controls and auditability

**Goals**
- Reduce provision-to-ready time and post-provision break/fix work by standardizing node configuration.
- Ensure repeatable fleet bring-up across regions/GPU types with explicit compatibility contracts.
- Make changes safe: staged promotion, rapid rollback, and clear operator visibility.

**Non-goals**
- Defining Kubernetes cluster architecture or scheduler behavior.
- Customer-facing documentation (this is internal).

## Definitions
- **Golden image**: A versioned machine image used for GPU worker nodes (OS + kernel + NVIDIA driver + CUDA userspace + container runtime + kubelet config + hardening).
- **Image channel**: Promotion tier used to control blast radius.
  - **candidate**: Newly built; used only for staged rollouts.
  - **stable**: Approved for broad rollout; default for new capacity.
  - **pinned**: Explicitly pinned version (bypasses channel following).
- **Pool**: A logical group of nodes (e.g., Dedicated customer pool, shared capacity pool) that shares rollout controls.

## Image build pipeline (high level)
We build images in a reproducible pipeline with provenance. Builds are triggered by:
- Scheduled patch cadence (weekly/monthly)
- Dependency bumps (driver/CUDA/NCCL/kernel)
- Emergency security response
- Explicit request (approved by Infra + Release Eng)

### Pipeline stages
1) **Source and change control**
   - Image definitions live in Git (infra-images repo) and are reviewed via PR.
   - Required approvals:
     - Release Eng (required)
     - Infra/Fleet (required)
     - Security (required for kernel, sshd, auth, hardening deltas)

2) **Build (packer/AMI) with locked inputs**
   - Base OS: Ubuntu LTS (currently 22.04) unless otherwise noted.
   - Kernel: pinned minor release per train (see versioning below).
   - NVIDIA driver: pinned version (no “latest”).
   - CUDA userspace: pinned minor version.
   - NCCL: pinned version matching CUDA + driver policy.

3) **Provision baseline configuration**
   The bake applies the baseline from **Node Configuration Baseline (GPU Workers)**, including:
   - containerd + registry/cgroup settings
   - kubelet flags (eviction thresholds, reserved resources)
   - time sync (chrony) and NTP sanity
   - ulimits and sysctl (file descriptors, conntrack where applicable)
   - disk layout + mount options (noexec where appropriate)
   - log forwarding agent + node validation agent bootstrap

4) **Hardening + security checks**
   - CIS-aligned SSH configuration (no password auth, restricted ciphers)
   - OS package minimization; remove unused services
   - Image-level vulnerability scan + SBOM generation
   - Secrets check: ensure no credentials/keys baked into image

5) **Smoke tests in an isolated test cluster**
   Before publishing to **candidate**, we run:
   - `nvidia-smi` health and driver enumeration
   - Container runtime GPU passthrough test
   - CUDA sample kernel run (sanity)
   - Network and storage reachability checks required for cluster join
   - K8s node join test (kubelet + CNI) in a staging environment

6) **Publish artifacts + provenance**
   For each build we publish:
   - Image ID(s) per region
   - SBOM (SPDX or CycloneDX)
   - Build attestation (builder identity, commit SHA)
   - Release notes (what changed; compatibility notes)

7) **Promotion workflow**
   - Build outputs land in **candidate**.
   - Promotion from **candidate → stable** is gated by fleet readiness metrics and validation success rates (see “Promotion criteria”).

## Naming, versioning, and pinning policy
### Image naming
Images are named for quick inspection and traceability:

`rwi-gpu-worker-ubuntu2204-nv<DRIVER>-cuda<CUDA>-nccl<NCCL>-k<kernel>-<YYYYMMDD>.<build>-<gitsha>`

Example:
`rwi-gpu-worker-ubuntu2204-nv550.54.14-cuda12.4-nccl2.21.5-k6.5.0-20251012.2-a1b2c3d`

### Version semantics
- **Date/build**: identifies the release train build.
- **gitsha**: identifies the exact image definition commit.
- Dependencies are explicitly recorded in image metadata tags.

### Pinning and rollout controls (per pool)
Pools select images using one of the following:

1) **Follow a channel (default)**
- Most pools track **stable**.
- Staged rollouts track **candidate** explicitly (time-boxed).

2) **Pinned version**
- Used when a pool must remain on a known-good image during an investigation or customer freeze.
- Pinning requires an owner and an unpin date or review checkpoint.

### Where pinning is configured
- Terraform module outputs expose:
  - `image_channel` (stable/candidate)
  - `image_version` (optional explicit pin)
- The provisioning orchestrator reads these settings and selects the correct regional image ID.

## Promotion criteria (candidate → stable)
An image may be promoted to **stable** when all are true:
- Bake-time tests passed in staging.
- Provision-to-ready validations show acceptable success rates on staged capacity.
- No open P0/P1 incidents attributed to the image.

**Minimum rollout exposure before promotion**
- At least one region and one GPU type in staged rollout.
- At least 200 node-hours of runtime in production-like conditions.

**Quality thresholds (promotion gates)**
- Post-provision validation success rate: **≥ 99.0%** over the staged window.
- NCCL smoke test pass rate: **≥ 98.5%** (flakes tracked; consistent failures block promotion).
- No regression in time-to-ready P95 greater than **+15%** compared to current stable.

**Approvals**
- Release Eng (Sahana Iyer) confirms artifacts + provenance.
- Infra/Fleet (Vanessa Ortiz or delegate) confirms operational readiness.
- Security sign-off required when:
  - Kernel changes
  - SSH/auth changes
  - Base OS bump

## CVE patch cadence and emergency response
### Regular cadence
- **Weekly (every Tuesday)**: patch Tuesday-style rebuilds for:
  - High/critical CVEs in kernel, OpenSSL, glibc, sshd, container runtime
  - NVIDIA driver security updates (when applicable)
- **Monthly (first full week of the month)**: full dependency refresh window for:
  - OS package updates (non-critical)
  - Monitoring/agent updates
  - Minor kubelet/containerd config improvements

### Emergency patch policy
If a critical vulnerability is identified with practical exploitability:
- Target **candidate build within 24–48 hours**.
- Target promotion to **stable within 72 hours**, assuming staged validations pass.
- If validations cannot be completed safely, we will:
  - Pin pools to last-known-good stable
  - Apply compensating controls (e.g., network policy, package removal) where feasible
  - Communicate risk + mitigation to stakeholders

### Scanning and evidence
- Image scan results are retained per build.
- SBOM is generated for every release and stored alongside build artifacts.
- Exceptions (known vulns accepted temporarily) require:
  - Owner
  - Expiration date
  - Documented mitigation

This matrix is the compatibility contract for fleet images.

**Notes**
- We avoid mixing GPU families in a single pool when possible.
- For multi-tenant/shared pools, we prioritize stability and deterministic perf.
- Driver upgrades are staged and must pass NCCL + perf canary checks.

### Current supported combinations (2025-Q4)
| GPU type | Image train | NVIDIA driver | CUDA userspace | NCCL | Intended use | Notes |
|---|---|---:|---:|---:|---|---|
| A100 (80GB) | stable | 550.54.14 | 12.4 | 2.21.5 | Dedicated + shared | Default stable train. |
| H100 (80GB) | stable | 550.54.14 | 12.4 | 2.21.5 | Dedicated (high-throughput) | Requires fabric/NCCL validation; stricter canary thresholds. |
| L4 | stable | 535.161.07 | 12.2 | 2.20.5 | Cost-optimized / burst | Keeps older driver for compatibility with fleet baseline. |
| A10 | candidate | 535.161.07 | 12.2 | 2.20.5 | Legacy capacity | Candidate only until join/validation flake rate is reduced. |

### Upgrade principles
- Upgrade only one major axis at a time when possible:
  - driver OR CUDA minor OR kernel
- NCCL changes require:
  - NCCL all-reduce smoke test
  - Perf canary (inference throughput/latency) comparison vs current stable

## Rollback strategy (blast-radius controlled)
Rollbacks must be safe, fast, and auditable. There are two rollback types:

1) **Channel rollback** (preferred)
- Move **stable** pointer back to previous stable version.
- Pools following stable will converge automatically on next node cycle.

2) **Pool pin rollback** (targeted)
- Pin a specific pool (or region/GPU slice) to a known-good image version.
- Used when an issue is isolated (single region, single customer pool).

### Rollback triggers
A rollback is recommended when any are true and attributable to the image:
- Provision-to-ready validation failure rate increases by **> 2x** baseline.
- Nodes are stuck in **Validating** or **Provisioning** with a common signature linked to the image.
- NCCL smoke test shows consistent failures (not flakes) in a region/GPU type.
- Kernel/driver regressions: elevated GPU Xid errors, ECC error spikes, or repeated device resets.
- Metric/telemetry regressions that block safe operations (e.g., cardinality explosion).

### Blast-radius controls
- Candidate rollouts are limited by policy:
  - Max **5%** of nodes per pool OR **20 nodes**, whichever is smaller.
  - Single region + single GPU type during first stage.
- Stable rollout is phased:
  - 25% → 50% → 100% per region/GPU type, with a minimum observation window between steps.

### Automated rollback hooks (guardrails)
When enabled for a staged rollout, the orchestrator will auto-stop and recommend rollback if:
- Validation failure rate exceeds threshold for 30 minutes (configurable per stage).
- Time-to-ready P95 exceeds threshold for 1 hour.
- Quarantine count exceeds a fixed cap (to prevent capacity shortfalls).

## Rollback procedure (operator playbook)
Follow this process to minimize impact and preserve evidence.

### Step 0 — Confirm scope and symptom
1. Identify affected slice:
   - region, GPU type, pool ID, image version
2. Check readiness dashboards and validation artifacts:
   - failure reasons by step
   - quarantine reasons and counts
3. Confirm whether the issue reproduces on new nodes only (provisioning) or also on existing nodes (runtime).

### Step 1 — Stop the bleeding
Choose the smallest effective intervention:
- If issue is limited: **pin the affected pool** to last-known-good stable.
- If issue is broad: **rollback stable pointer** to previous stable.

Operational notes:
- Prefer pinning a single pool before moving stable for the entire fleet.
- If a customer Dedicated pool is impacted, coordinate with Capacity Ops and Support on expected throughput impact.

### Step 2 — Control node churn safely
- For nodes already serving traffic:
  - Do not mass-reboot unless required.
  - Use standard drain/cordon procedures.
- For nodes failing readiness:
  - Quarantine automatically after retry budget is exceeded.
  - Reimage only after pin/rollback is in place (to avoid reintroducing the bad image).

### Step 3 — Verify recovery
- Provision a small batch (e.g., 5–10 nodes) on the rolled-back image and confirm:
  - time-to-ready returns to baseline
  - validation pass rate returns to normal
  - NCCL smoke tests pass
- Keep staged rollout flags disabled until root cause is understood.

### Step 4 — Preserve evidence and follow up
- Attach logs/artifacts to the tracking ticket:
  - image version and build metadata
  - validation outputs and failure signatures
  - GPU health stats (Xid, ECC)
- File follow-ups:
  - fix forward PR
  - test coverage gaps
  - promotion gate adjustments (if needed)

## Operational FAQs
### How long do we keep old images?
- Keep at least **N-2 stable** images per region (minimum) for rapid rollback.
- Keep **all candidate images for 30 days** for forensics.

### Can we have different stable images per region?
- Yes, but only with an explicit reason (region-specific driver/fabric constraints).
- Document the divergence and plan to converge.

### What if validations are flaky and block promotion?
- Do not lower gates by default.
- Instead:
  - isolate flakes by region/GPU type
  - tune timeouts/backoff
  - fix root causes (network jitter, disk warm-up, NCCL timeouts)

### Who can change image channel/version for a pool?
- Restricted to Infra/Fleet and Release Eng roles.
- All changes must emit an audit event (see control-plane audit logging) and include:
  - requester
  - reason
  - scope (pool/region/GPU)
  - rollback plan
