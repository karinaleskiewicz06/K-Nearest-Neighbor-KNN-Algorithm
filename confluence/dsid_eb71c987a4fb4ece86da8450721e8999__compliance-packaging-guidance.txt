Compliance packaging guidance (Base vs Enterprise add-ons)

## Purpose
This page is internal guidance for AEs/SEs on how to describe what’s included in Redwood’s **base offerings** versus **enterprise/compliance add-ons**, and when to escalate to Security/GRC, Legal, or Finance.

This is intentionally written to be **quote-safe** and **RFP-safe**. Do not promise roadmap items or non-standard SLAs without approvals (see “Escalations + approvals”).

**Last reviewed:** 2026-02-12 (Security/GRC + Legal + PM)
**Next review due:** 2026-05-15

---

## Definitions (internal)
**Base offering**
- What is included in the standard plan for Hosted API and in standard Dedicated/Private contracts.
- Includes baseline security controls, standard support, and standard documentation.

**Enterprise add-ons** (commercial)
- Contracted features/support that increase audit readiness, operational assurance, and response SLAs.
- Examples: extended audit log retention, evidence support SLAs, security review sessions, enhanced support.

**Redwood Dedicated**
- Reserved capacity (dedicated GPU pools) with isolation and predictable throughput.

**Redwood Private**
- Customer-isolated deployment in a customer VPC or on-prem environment (regulated/air-gapped eligible depending on scope).

## Packaging overview (what’s in base vs add-on)
The table below is the **field-ready** summary for procurement and security reviewers.

### 1) Security program + compliance evidence
| Topic | Included in base | Enterprise / Compliance add-on (when needed) | Notes / how to say it |
|---|---|---|---|
| SOC 2 report access | **Available under NDA** via the evidence request process | **Priority evidence handling SLA** + packaged security review support | Say: “SOC 2 Type II report available under NDA. We use a gated evidence request process.” Do not email reports directly. |
| Security questionnaire support | Best-effort via SE + Security/GRC as capacity allows | **Defined turnaround SLA** for questionnaires (e.g., standard language + redlines) | Use add-on when the customer requires fixed turnaround dates in the contract. |
| Customer security review call | Available as needed (scheduled) | Packaged: **security review session(s)** + named contacts during procurement | Use add-on for accelerated enterprise timelines and RFP-heavy deals. |
| ISO 27001 | Not claimed as “certified” unless explicitly confirmed by GRC | N/A (do not sell “ISO certification”) | Say: “We align our security program to common frameworks; we can share details under NDA.” Use approved ISO alignment language only. |

### 2) Audit logging + retention
| Topic | Included in base | Enterprise / Compliance add-on (when needed) | Notes / how to say it |
|---|---|---|---|
| Audit logs (Console/API events) | Included with **standard retention window** | **Extended retention** and/or **export integrations** packaged with support | Say: “Audit logs are available; retention and export options depend on plan and deployment.” Confirm exact retention in the current customer-facing retention overview. |
| Export to customer SIEM / storage | Supported where documented; may require SE assistance | Packaged: implementation support + longer retention + accelerated troubleshooting | Use add-on when security requires a committed delivery timeline and ownership. |
| Log access controls | RBAC governs access to logs | Packaged: additional governance reviews / access policy documentation support | Do not promise custom log schemas without SE validation. |

### 3) Identity + access management
| Topic | Included in base | Enterprise / Compliance add-on (when needed) | Notes / how to say it |
|---|---|---|---|
| SSO (SAML) | Typically included for enterprise plans; confirm customer’s SKU | Packaged: SSO + SCIM + enhanced admin controls if not already included | Say: “SSO via SAML is supported for the Console; SCIM is available for automated provisioning (plan-dependent).” |
| RBAC | Included | Packaged: policy review support / role mapping workshop | Avoid “fine-grained down to every field” language unless validated by the RBAC capabilities page. |

### 4) Deployment + isolation options
| Topic | Included in base | Enterprise / Compliance add-on (when needed) | Notes / how to say it |
|---|---|---|---|
| Hosted API (multi-tenant) | Included | N/A | Standard choice for fastest time-to-value. |
| Dedicated capacity | Contracted product | N/A | Use for predictable throughput + stronger isolation. |
| Private deployment (VPC / on-prem) | Contracted product (Enterprise) | May include additional compliance support + architecture review | Private is often paired with compliance add-ons for regulated industries. |
| Customer-managed keys (KMS/HSM) | Supported in certain Private/Dedicated configurations (scope-dependent) | Packaged: implementation support + documentation + security review | Never commit to CMEK/HSM without Solutions Engineering + Security signoff for the specific deployment. |

## Recommended packaging plays (when to attach what)
Use these rules of thumb to keep packaging consistent and avoid ad hoc promises.

### A) “Standard enterprise security review” (no hard deadlines)
**Use when:** customer is doing a typical security questionnaire, no fixed procurement deadline.
- Base offerings + SE support
- Evidence request via GRC process
- 1 security review call as needed (scheduled)

**Positioning:** “We’ll support the review using our standard evidence process and approved questionnaire language.”

### B) “Compliance Pack” (accelerated review + evidence SLA)
**Use when:** customer procurement requires **committed SLAs** for evidence/questions, or volume of artifacts is high.
Include:
- **Evidence response SLA** (see next section)
- **Questionnaire turnaround SLA** for the approved response library + redlines
- Scheduled **security review session(s)** with Security/GRC
- Optional: extended audit log retention and export enablement if that is a stated requirement

**Positioning:** “This package is designed for regulated procurement workflows where timelines and evidence handling need to be contractually reliable.”

### C) Private/Dedicated + Compliance Pack (regulated / residency constrained)
**Use when:** customer requires stronger isolation boundaries, data residency commitments, or customer-managed networking.
Include:
- Dedicated or Private deployment
- Compliance Pack for review SLAs
- Optional: KMS/HSM integration (only if validated), audit log export implementation support

**Positioning:** “We can support Dedicated or Private deployments with a shared responsibility model and the documentation/security review process your procurement team expects.”

## Evidence support SLAs (what we can contract vs what we cannot)
**What we can contract (with Compliance Pack + approvals):**
- Response SLAs for:
  - initial evidence request acknowledgment
  - providing the standard artifact set under NDA
  - questionnaire redlines using approved language
  - scheduling a security review call within a defined window

**What we do NOT contract as absolutes:**
- “Unlimited” bespoke artifact creation
- “Same-day” turnaround for large, custom audits without prior approval
- Sharing restricted artifacts outside the formal process (no direct emailing of reports)

**Internal routing:** All SOC 2 report requests and evidence requests must follow the GRC intake process (see related page: SOC 2 evidence request playbook).

## Audit log retention add-on (how to describe it without overcommitting)
Use the phrasing below to stay consistent:

**Approved customer-facing phrasing (use verbatim where possible):**
- “Redwood provides audit logs for key administrative and access-related events. Retention and export options depend on your plan and deployment mode, and can be configured to support common enterprise requirements.”

**Avoid:**
- “We retain audit logs for X days for all customers” (retention varies)
- “We can log everything you need” (implies unlimited scope)

**When to attach the add-on:**
- Customer requires **≥ 1 year** audit log retention
- Customer requires **SIEM integration** with an implementation deadline
- Customer requires **contractual commitments** on audit log availability/exports

## Private deployment options (how to package + common traps)
**Common customer asks (and how to handle):**
1) **“We need VPC / private networking.”**
- Offer: Redwood Private (customer VPC) or Dedicated with private connectivity options (scope-dependent).
- Escalate to SE lead to confirm the exact network pattern.

2) **“We need on-prem / air-gapped.”**
- Offer: Redwood Private on-prem package is available for certain regulated environments.
- Do not commit to air-gap details (artifact delivery, patching cadence, monitoring) without SE + Security alignment.

3) **“We need customer-managed keys (CMEK/HSM).”**
- Treat as a solution design item; confirm supported patterns and boundaries.
- Only position as available if SE confirms for the specific deployment.

**Approved positioning:**
- “Private deployments provide stronger isolation and customer-controlled networking. The exact architecture and responsibilities are defined during solution design.”

## Data residency + retention (how it affects packaging)
**Rule:** Data residency and retention commitments vary by deployment mode and region. Use the canonical customer-facing retention/residency overview when responding.

**Approved phrasing:**
- “We support region selection and can discuss residency requirements by deployment mode. Retention controls and log retention are configurable within documented boundaries.”

**Avoid:**
- “We guarantee EU-only processing for every service by default.”
- “We never store any customer data.” (oversimplifies; metadata/logging may exist)

**When to attach Compliance Pack:**
- Customer requires explicit residency language in the contract + evidence timelines.

## Pricing/quote hygiene (internal)
**Do:**
- Align the order form language to the selected packaging play (Base vs Compliance Pack vs Private/Dedicated + add-ons).
- Include only commitments that have an owner and can be delivered (SLAs, retention windows, export destinations).
- Use approved RFP library snippets for all security claims.

**Don’t:**
- Add bespoke security promises in email threads.
- Commit to specific retention windows, export formats, or key management patterns without confirming current capability.

## Quick FAQ
**Q: Is SSO included in base?**
A: For enterprise SKUs, SSO (SAML) is typically included; confirm the customer’s plan/SKU and cite the SSO/RBAC capabilities page for exact scope.

**Q: Can we offer ‘unlimited’ evidence requests?**
A: No. Evidence support is capacity-constrained. Use Compliance Pack with defined SLAs and scope.

**Q: Can we say we’re ISO 27001 certified?**
A: Do not claim certification unless explicitly confirmed by GRC for the current period and scope. Use the approved “ISO alignment” language only.

**Q: Customer wants 7-year audit log retention.**
A: Escalate. Do not commit. Determine whether this is required for audit logs vs business records and whether export-to-customer storage solves it.
