Tenant Ingress Filter Operator - Terraform & Operator Spec

Summary

This document specifies the design, Terraform module contract, operator runtime behaviour and CI/CD lifecycle for the Tenant Ingress Filter Operator (TIFO). TIFO enforces per-tenant ingress policies at the edge and inside inference clusters to protect GPU pools and model-serving paths from noisy or malformed traffic patterns. The goal is safe, automated, and auditable ingress shaping and blocking with minimal latency impact.

Why we need TIFO

- Inference workloads have bursty, short-lived flows; malformed or intentionally abusive ingress can cause KV cache churn, GPU kernel amplification, or controller overload.
- Existing per-tenant egress/egress-shaper tooling protects downstream costs; we need an equivalent for inbound traffic (rate/fanout/payload constraints) tied to tenant identity.
- Tightening ingress improves reliability and enables safe multi-tenancy in shared warm/pinned GPU pools.

Scope and non-goals

- In scope: policy declaration (Terraform), operator control plane, dataplane enforcement (Envoy filter + iptables fallback), observability metrics, rollout/rollback and CI tests.
- Out of scope: full L7 request rewrite, per-model NLP content filtering, or tenant-authentication semantics (TIFO relies on upstream auth to provide tenant ID).

Design overview

1) Policy model (declarative Terraform contract)

TIFO policy is represented as a Terraform-managed CRD manifest. High level fields: tenant_id, max_rps, max_concurrent_requests, max_payload_bytes, token_bucket_rate, fanout_limit, kv-cache-affinity (preferred warm pool tag), blocklist_patterns (optional).

Example Terraform snippet (module contract):

module "tifo_policy_acme" {
  source = "git::ssh://git.redwood/internal-modules.git//tifo-policy?ref=v1.0.0"

  tenant_id               = "acme-corp"
  max_rps                 = 200
  max_concurrent_requests = 50
  max_payload_bytes       = 65536
  token_bucket_rate       = 200
  fanout_limit            = 3
  kv_cache_affinity       = "warmpool-west-1"
  blocklist_patterns     = ["^/internal/", "^/debug/"]
  tags                    = { cost_center = "acme" environment = "prod" }
}

Terraform outputs (required):

- tifo_crd_yaml: YAML string of the generated CRD applied to the cluster
- policy_id: unique id for cross-referencing with billing/telemetry

2) Operator responsibilities

- Watch TIFOPolicy CRDs, validate against schema and tenant quotas (call quota service).
- Translate policies into dataplane rules: Envoy HTTP filters (rate-limiter, size-limiter), and service mesh route constraints.
- Maintain a fallback iptables-based limit for services not in the mesh (best-effort).
- Propagate policy to per-node agents for early-local-drop when safe.
- Emit structured telemetry for each enforcement decision with labels: tenant_id, rule_id, decision (allow/soft_drop/hard_drop), reason, matched_pattern, timestamp, host, pod.

3) Enforcement modes

- Monitor mode: collect telemetry but do not enforce. Used for initial rollout per-tenant.
- Soft-fail (probabilistic sampling) mode: drop a percentage of matching traffic to validate false positive impact.
- Enforce mode: strictly apply rate/size/fanout limits.

4) Safety & rollout semantics

- All changes to TIFOPolicy should be gated via a Terraform PR and require a link to an evaluation run in CI (see CI section).
- New policies default to monitor mode for 24–72 hours unless the tenant is on an opt-in hard-enforce contract.
- Operator automatically backs off enforcement when global node CPU or request-latency SLOs exceed thresholds (configurable):
  - cpu_utilization > 85% for 2m => operator switches affected tenants to soft-fail for 5m.
  - p99 request latency increase > 30% over baseline => operator switch to monitor mode and raise alert.

Operational SLOs and alerts

- TIFO operator control-plane availability: 99.95% monthly.
- CRD apply-to-enforce latency: < 10s for control path; < 60s for full propagation to dataplane in normal conditions.
- Telemetry delivery: 99% of enforcement events within 60s to the telemetry ingestion pipeline.

Alerting (first responder: infra-networking oncall):

- Control-plane crashlooping > 5min -> Pager (sev2)
- Enforcement error rate > 5% of policy updates -> Pager (sev2)
- Telemetry backlog > 10m lag -> Pager (sev3)

Terraform module design and constraints

Module inputs (required):

| name | type | description | default |
|---|---|---:|---:|
| tenant_id | string | canonical tenant identifier | n/a |
| max_rps | number | soft threshold for incoming requests per second | 100 |
| max_concurrent_requests | number | concurrent in-flight request cap | 20 |
| max_payload_bytes | number | size limit for request body | 65536 |
| fanout_limit | number | max downstream subrequests spawned | 5 |
| kv_cache_affinity | string | preferred warm pool label | "" |
| enforcement_mode | string | monitor|soft|enforce | "monitor" |
| tags | map(string) | freeform tags for billing/owner | {} |

Module outputs (required):

- policy_id (string)
- tifo_crd_yaml (string)
- applied_namespace (string)

IAM and cloud account constraints

- Terraform module will require a service account with the following minimal IAM bindings: apply/update CRDs, list/watch pods/nodes, annotate pods, write to ConfigMaps for per-node agent config.
- Cross-account policy: when tenants are in a different cloud account, module will create a signed policy blob that is verified by the operator's keypair. The Terraform module must not create cross-account long-lived credentials.

Dataplane design details

- Primary path: Envoy rate-limiter + local token-bucket filter applied at the mesh ingress.
- Secondary path: Node-level agent applies nftables rules for L4 drops and early circuit-breaking.
- Fanout control: operator monitors tree of outbound subrequests via passthrough headers (X-Redwood-Subreq-Chain) and enforces a max depth/children rule.

Example Envoy filter fragment (applied by operator):

apiVersion: v1
kind: EnvoyFilter
metadata:
  name: tifo-rate-limit-acme
spec: |
  filters:
    - name: envoy.filters.http.ratelimit
      config:
        domain: tifo/acme
        descriptors:
          - key: path
            value: "/api/v1/generate"

Node agent config (YAML excerpt):

agent:
  local_limiters:
    - name: nft-early-drop
      max_conn: 150
      max_rps: 1000

Telemetry and observability

- Metrics (prometheus):
  - tifo_policy_applied_total{tenant_id}
  - tifo_enforcement_decisions_total{tenant_id,decision,rule_id}
  - tifo_enforcement_latency_seconds_bucket
  - tifo_operator_reconcile_duration_seconds

- Distributed tracing: operator adds trace context to any policy change events and enforcement sampling decisions. Sampled traces must be available in Jaeger for 7d.
- Logging: structured JSON enforcement logs written to stdout with keys listed above. Logs must include policy_id and a short reason code.

CI/CD and testing matrix

- Terraform module tests (unit): validate schema, deny-list dangerous configs (e.g., max_rps > 100k) with terratest.
- Integration tests (canary stage): deploy TIFOPolicy in a cluster running a sandboxed inference service with synthetic tenants. Verify enforcement decisions match expectations given load profiles and modes. Use k6 load tests and a kv-cache access verifier.
- Chaos tests: simulate ephemeral node pressure and ensure operator backoff logic triggers correctly.
- CI gating: merge to main for module requires passing unit tests + integration proposals; production promotion requires a signed release and cross-team signoff.

Rollout procedure (recommended)

1) Create Terraform change in platform repo with monitoring mode and evaluation tag.
2) Run integration harness (k6 scenario) for 48h scoped to tenant traffic pattern.
3) Review telemetry for false positives (target < 0.05% good traffic drops).
4) If acceptable, promote enforcement_mode to soft for 24h, then to enforce with step-up checks.

Rollback checklist (fast path):

- Terraform apply revert (apply previous module version) -> operator will detect old spec and restore previous dataplane rules.
- If control plane is unhealthy, toggle operator global-safety flag (via console) to move all tenants to monitor mode.

Security considerations

- Operator must verify signed policy blobs for cross-account tenants. Keys stored in KMS and rotated quarterly.
- All enforcement logs sent to central logging must be scrubbed for PII; blocklist_patterns must be redacted in logs.
- Policy authoring requires role-based permissions; only platform-admin and tenant-owners can create enforce-mode policies.

Operational runbook (for oncall)

1) Is the operator running? kubectl -n redwood-system get pods -l app=tifo-operator
2) Check control-plane logs: kubectl logs -n redwood-system deploy/tifo-operator | jq .reason -r | tail -n 200
3) Confirm CRD health: kubectl get tifoPolicy -A
4) If enforcement is failing, look for dataplane application errors in envoy xds logs and node-agent logs.
5) To force degrade to monitor mode: kubectl annotate deployment tifo-operator --overwrite safety-mode=monitor

Key CLI snippets

# Render policy YAML from Terraform module output
terraform output -json | jq -r '.tifo_crd_yaml.value' > policy.yaml
kubectl apply -f policy.yaml

# Query recent enforcement events for tenant
kubectl logs -l app=tifo-operator -n redwood-system --since=10m | jq -c 'select(.tenant_id=="acme-corp")' | less

Open questions and future work

- Integration with model-aware routing: could enforce different ingress allowances per model signature to allow heavier batches for small-token models.
- Per-tenant adaptive throttling driven by model latency sensitivity signals from Redwood Optimize.
- Support for automated policy suggestion from historical telemetry (ML-driven recommendations).
