ephemeral-credentials-and-service-account-rotation-patterns-for-gpu-workloads

Overview

This document describes recommended patterns for issuing, rotating, and auditing ephemeral credentials for GPU-backed workloads across our multi-account, multi-cloud infrastructure. It focuses on Kubernetes service accounts, short-lived cloud credentials, and integration with Vault/KMS to reduce blast radius from leaked secrets and to meet audit/compliance requirements for Private and Dedicated deployments.

Goals

- Reduce risk surface by minimizing lifetime of high-privilege credentials used by GPU jobs and CI/CD runners.
- Standardize patterns across AWS, GCP, and Azure so ops runbooks and alerting are uniform.
- Provide operational runbooks for emergency rotation and for routine automation.
- Ensure the approach is compatible with bursty ephemeral pools (ephemeral GPU sandboxes and CI eval clusters).

Scope

Includes: GPU tenant workloads, ephemeral CI/eval jobs, warm-pools that run customer-side onboarding tests, image build pipelines.
Excludes: Long-lived control-plane credentials (account admin/root) — those remain handled by corporate security and are outside this playbook.

High-level patterns (summary)

1) Principle of Least Privilege + Short TTLs
   - Use cloud provider short-lived STS/OIDC tokens or Vault-issued dynamic creds instead of embedding long-term keys.
   - Default lifetimes: workloads (15m – 2h), CI runners (1h – 6h), image builders (up to 12h only when strictly necessary). See TTL table below.

2) Identity bridging via Workload Identity / IRSA / Managed Identities
   - Map Kubernetes ServiceAccounts to cloud identities (AWS IRSA; GCP Workload Identity; Azure AD Pod Identity) and avoid node-level credentials.

3) Vault as the central issuance & audit hub
   - All cross-account elevated credentials must be minted via HashiCorp Vault or cloud KMS-backed short-lived tokens with audit logging.

4) Automated revocation hooks and ephemeral pool draining
   - If Vault detects anomalous minting patterns or a compromised SA, automation triggers: revoke tokens, cordon + drain affected nodes, and rotate dependent resources.

Recommended TTLs and cadence (table)

| Credential class       | Default TTL | Max TTL | Refresh cadence | Typical consumer |
|------------------------|-------------:|--------:|----------------:|------------------|
| Pod-level workload token| 15m         | 2h      | auto-renew if job long-running (15m) | user-facing low-latency workloads |
| CI/eval ephemeral token | 1h          | 6h      | 1h             | nightly/real-time CI runners |
| Image-build elevated token | 4h       | 12h     | manual renew with approval | trusted build agents |
| Operator/infra task token | 30m       | 2h      | 30m            | infra automation tasks (drain, reconfigure) |

Platform architecture (text diagram)

- Kubernetes cluster (EKS/GKE/AKS)
  - Pod (service-account) -> projected token (k8s tokenRequest API or OIDC)
  - IRSA/Workload Identity maps token to cloud role -> STS temporary credentials
- HashiCorp Vault (central)
  - Vault issues database/cloud credentials on-demand, records audit log, supports dynamic leases and revocation
- KMS/HSM for signing and key material storage

AWS IRSA example (short snippet)

1) Create OIDC provider for the cluster (one-time per account/cluster).
2) Terraform fragment (IAM role for SA):

```
resource "aws_iam_role" "gpu_job_role" {
  name = "rdr-gpu-job-role-${var.cluster_name}"
  assume_role_policy = data.aws_iam_policy_document.irsa_assume_role.json
  tags = { team = "infra" }
}

resource "aws_iam_role_policy_attachment" "gpu_job_policy" {
  role       = aws_iam_role.gpu_job_role.name
  policy_arn = aws_iam_policy.gpu_job_policy.arn
}
```

3) Kubernetes ServiceAccount annotation (example):

```
apiVersion: v1
kind: ServiceAccount
metadata:
  name: gpu-inference-runner
  namespace: eval
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/rdr-gpu-job-role-clusterA
```

GCP Workload Identity example (summary)

- Bind KSA to Google Service Account and limit roles to Storage/Secrets/AI Platform minimal scopes.
- Use short-lived OAuth access tokens from metadata server with explicit audience restrictions.

HashiCorp Vault patterns

- Mount cloud provider secret backends (aws, gcp, azure) per-account.
- Configure roles with minimal policy, TTLs, and maximum TTL enforcement.
- Use response_wrapping for bootstrap secrets and rotate wrapping tokens at 5m.

Example Vault role (AWS):

```
path "aws/creds/gpu-ci-role" {
  capabilities = ["read"]
}
```

Operational runbooks

A) Routine credential refresh (automation)
1) Job requests credential via SA->OIDC or Vault API.
2) Issuer validates SA identity and scope.
3) Vault returns credentials & lease id.
4) Pod uses credentials and records lease id as annotation for easier revocation.
5) Sidecar (or node agent) renews lease automatically if job is long-lived; otherwise allow TTL expiry.

B) Emergency credential revocation (compromise suspected)
1) Trigger: alert from audit (unusually frequent minting, geo anomaly, or security report).
2) Oncall runs `rdr-infra revoke-credential --lease <lease-id>` (automated script).
3) Vault revokes lease; cloud provider STS credentials are invalidated.
4) Automation cordons affected nodes and drains pods that relied on the revoked lease.
5) Re-issue new roles/patch SA annotations if role policy was rotated.
6) Post-incident: run access re-evaluation, rotate related images and any cached secrets.

C) CI/Eval runner rotation pattern (recommended)
1) Runners boot with a short-lived Vault token (wrapped).
2) Runner unwraps to get a Vault client token with a 1h TTL.
3) Runner mints cloud creds for job execution.
4) At job end or TTL expiry, runner calls Vault lease revoke.

Implementation checklist (step-by-step)

- Inventory: list all clusters, accounts, and existing long-lived keys used by GPU workloads.
- Create one Vault mount per cloud account and enforce policy separation.
- Deploy OIDC providers for clusters and adopt IRSA/Workload Identity in all new clusters.
- Migrate workloads: start with non-critical CI jobs, then staged rollout to eval and production GPU pools.
- Instrument logging: emit lease_id and role_name as structured log fields for every mint.
- Add dashboards: number of active leases, average TTL, minting rate per role.

Monitoring, alerting, and SLOs

- Metric: vault_mint_rate by role (alert if > 10x baseline over 5m).
- Metric: percentage of workloads using ephemeral creds (target 95% for new clusters within 90 days).
- Alert: failed revocation call rate > 1% sustained for 10m.
- SLO: critical infra tokens must be revoked within 90s of an automated revoke command (measured in staging).

Security considerations and caveats

- Node compromise: If a node is compromised, projected SA tokens reduce risk vs node-level keys, but an attacker on that node can still call cloud APIs until TTL expires. Use short TTLs and automatic node quarantining on suspicious activity.
- Auditing: Vault audit logs are primary source-of-truth. Forward them to secure long-term storage (30–90 days depending on customer contract).
- Rate limiting: Set per-role rate limits in Vault to prevent credential-scraping attacks.
- Backups: Do not backup dynamic credentials. Only backup vault policies and plugin configs.

FAQ (short)

Q: Why not use node IAM roles?
A: Node roles are long-lived and increase blast radius if nodes are compromised. Workload-to-identity mapping reduces privilege exposure.

Q: What about GPU batch jobs that run for days?
A: Break into smaller jobs where possible. If multi-day runs are unavoidable, use an operator-managed renewal mechanism with explicit approval and extended auditing.
