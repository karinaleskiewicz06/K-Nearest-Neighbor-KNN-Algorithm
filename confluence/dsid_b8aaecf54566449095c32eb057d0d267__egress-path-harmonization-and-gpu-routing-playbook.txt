egress-path-harmonization-and-gpu-routing-playbook

Summary
-------
This playbook describes Redwood's recommended approach for harmonizing egress paths and routing GPU inference traffic to minimize cross‑region egress costs, reduce packet hairpins, and preserve latency SLOs. It covers policy design, Terraform module patterns, CI/CD considerations, telemetry, and an incident runbook for egress cost or routing regressions.

Scope
-----
Applies to: all GPU-serving clusters (hosted, dedicated) and the private‑deployment networking patterns.
Not covered: application layer routing choices (e.g., model selection logic) except where they affect traffic egress.

Goals and success criteria
-------------------------
- Decrease cross‑region egress spend from GPU workloads by >= 35% for multi‑region customers over 90 days after rollout.
- Keep 95th percentile model request latency change <= +10ms when rerouting to preferred egress.
- Maintain observability: per‑tenant egress breakdown and route attribution in Console dashboards.

Background and rationale
------------------------
GPU inference workloads commonly cross region boundaries when model variants, cold cache hits, or routing fallbacks target a region without data locality. This introduces: higher per‑GB egress costs, variable latency, and operational complexity for billing and debugging. Redwood's platform supports routing policies (latency/cost/region preference). To operationalize cost‑aware routing we standardize egress paths and provide an IaC module that enforces preferred egress regions, NAT placement, and transit attachments.

Network architecture (logical)
-----------------------------
- Customer VPCs (private deployment) or Redwood tenant subnets (hosted) in region R.
- GPU clusters exist in one or more regions (GPU pool per region).
- Egress candidates: local NAT gateway, regional egress VPC with egress optimizer, or transit gateway to a low‑cost egress region.
- Control plane contains routing policy service that returns a preferred region + egress_hint with every allocation decision.

Key concepts and policy fields
-----------------------------
- egress_preference: one of [local, regional, cost-optimized, legacy]
- egress_hints: free‑form string (e.g., "egress-region-us-west-2-nat-1") attached to request routing metadata
- route_ttl_s: how long a cached routing decision is valid (default 300s)
- cost_threshold_per_gb_usd: if estimated egress cost > threshold, prefer fallback route

Recommended default policy (multi‑region customers)
--------------------------------------------------
1. Try local: if model and cache present in same region, use 'local' egress.
2. Else if cross‑region traffic is inevitable, prefer 'regional' egress in the receiving region to avoid hairpin through customer network.
3. If policy allows cost optimization and cost model indicates savings >= 15%, route through 'cost-optimized' egress in strategic low‑cost region.
4. If 'legacy' flag set (customer override), preserve historical behaviour.

Terraform module: egress-optimizer (pattern)
------------------------------------------
This is a minimal example showing the pattern used by the infra team. The production module includes tagging, IAM bindings, and audit logging.

```hcl
module "egress_optimizer" {
  source = "git::ssh://git@github.com/redwood-inference/infra-modules.git//egress-optimizer?ref=v1.4.0"

  name_prefix          = "egress-optimizer-${var.env}"
  primary_region       = var.primary_region
  low_cost_region      = "us-west-2" # example
  nat_subnet_ids       = var.private_subnets
  transit_gateway_id   = var.transit_gateway_id
  flow_logs_bucket     = aws_s3_bucket.egress_flow_logs.id
  enable_cost_analytics = true
}
```

Module responsibilities:
- Create regional NATs and attach to a centralized egress VPC.
- Create route table entries and propagate to GPU VPCs via TGW or VPC Peering.
- Publish tags and a small set of metrics to CloudWatch/Datadog: egress_bytes, egress_cost_estimate_usd, routed_to_low_cost_region.

CI/CD checklist for module promotion
------------------------------------
1. Lint and static checks: terraform fmt, tflint, policy checks (OPA).
2. Unit plan step: run terraform plan against a small test account with mock variables.
3. Integration canary: apply module in a preprod region; deploy a single GPU cluster and run synthetic traffic.
4. Cost safety gate: run cost model for 7 days; if egress cost per GB changes > 30% abort.
5. Promote to staging and then to prod with a canary percentage.

Monitoring and observability (required metrics & dashboards)
-----------------------------------------------------------
Metrics to emit per cluster / tenant:
- infra.egress.bytes (tags: cluster, tenant, source_region, dest_region, egress_hint)
- infra.egress.estimated_usd (tags: tenant, billing_account)
- infra.routing.decision_latency_ms
- infra.egress.routed_low_cost_percentage

Suggested dashboards:
- Egress cost waterfall (tenant -> region -> route).
- 95th/99th latency delta pre/post routing change.
- Alert panel: sudden spike in infra.egress.estimated_usd or routed_low_cost_percentage drops below threshold.

Alerting thresholds (examples)
-----------------------------
- Alert: egress_cost_delta_high - when a tenant's 24h egress estimated cost increases by > 40% compared to the 7d median (sev P2).
- Alert: routing_failures - > 0.5% of routing requests returning error codes in 5m window (sev P1).
- Alert: low_cost_routing_vs_expected - if routed_low_cost_percentage deviates from target by > 20% for 30m (P2).

Runbook: egress cost spike or unexpected routing
------------------------------------------------
1. Triage and scope: identify tenant(s) with cost spike using Console billing view.
2. Check routing attribution: query egress bytes by egress_hint and dest_region for the tenant.
   - Datadog/PromQL example: sum by(egress_hint) (increase(infra_egress_bytes{tenant="TENANT_ID"}[24h]))
3. If routing unintentional: rollback routing policy change via the Control Plane — use the routing policy UI or API: 
   curl -X POST https://control-plane.internal.redwood/api/v1/routing/policies/{policy_id}/rollback 
4. If egressed to unexpected region due to missing NAT/TGW attachment, check IaC drift: run `terraform plan` in infra account and inspect for missing route table associations.
5. Temporary mitigation: attach emergency NAT in local region and add a high‑priority route (route priority: 100). Document the change in Incident ticket.
6. Postmortem: capture root cause, cost impact, and remediation steps in incident template.

Rollout plan (recommended phased approach)
-----------------------------------------
1. Discovery: run 14‑day analysis of cross‑region egress patterns by tenant and model.
2. Pilot: pick 3 tenants with predictable workloads; deploy egress-optimizer module in a single region pair; validate telemetry and runbook.
3. Canary: enable cost‑aware routing for 10% of cross‑region requests platform‑wide for 7 days with automated rollback on cost or latency regressions.
4. Scale: increment canary to 50% then 100% with monitoring gates at each step.

Security & compliance considerations
-------------------------------------
- Ensure egress flow logs are retained for the required retention window for customers with compliance needs.
- KMS keys for flow log buckets must be customer‑managed when requested.
- Route changes that affect customer data locality must be manually approved for restricted customers (see policy: security-and-compliance/data-residency-and-retention).

Frequently asked questions
--------------------------
Q: Will cost‑optimized routing ever move model execution to another region?
A: No — routing only changes egress hop. Model execution locality remains controlled by model placement policies. If model execution migration is required, the change must go through model‑onboarding and runtime teams.

Q: How do tenants opt out?
A: Tenants can set routing flags via the tenant config API: `egress_policy=legacy` which preserves prior behavior. Opt‑out must be approved for enterprise customers if it violates SLA.
