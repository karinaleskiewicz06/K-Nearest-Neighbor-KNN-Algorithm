Serving Runtime Feature Flag Cleanup Plan

h1. Overview
This page describes the plan to clean up and remove legacy feature flags in the Serving Runtime related to experimental batching and KV-cache heuristics. The goal is to reduce configuration surface area, remove dead code paths, and simplify rollout logic without regressing latency, throughput, or correctness.

This work originated as *ENG-5842* and has been updated to reflect the 2025H2/2026Q1 serving architecture changes (Adaptive Micro-batching v2 and KV-cache policy unification).

h1. Goals
* Remove unused or permanently-enabled flags.
* Replace “behavioral” flags with explicit, versioned runtime configuration where needed.
* Eliminate rollout branching that is no longer exercised.
* Maintain safe canarying and rollback hooks during the removal window.

h1. Non-goals
* Redesign batching scheduling (owned by the batching roadmap).
* Change default model-level cache settings (owned by Model Perf).
* Rework customer-exposed API parameters.

h1. Scope
The cleanup targets flags that historically controlled:
* Experimental batching (now superseded by *Adaptive Micro-batching v2*).
* KV-cache heuristic selection and fallback behavior (now consolidated into a single policy engine).

h2. Repos / services affected
* serving-runtime (core runtime)
* gateway (request shaping / headers)
* fleet-config (runtime config distribution)
* console (admin UI surfacing of flags)

h1. Flag inventory and decisions
The table below lists the most common legacy flags and the current disposition.

|| Flag || Previous use || Decision (2026) || Notes ||
| enable_experimental_batching | Toggle early micro-batching experiment | *Remove* | Adaptive Micro-batching v2 is the only supported path. |
| experimental_batching_max_tokens | Limit batch size in experiment | *Replace* | Move to fleet-config key: runtime.batching.max_tokens (validated range, no branching). |
| experimental_batching_max_delay_ms | Scheduler delay cap | *Replace* | Move to fleet-config key: runtime.batching.max_delay_ms. |
| kv_cache_heuristics_mode | Select heuristic set (A/B) | *Remove* | Policy engine now selects based on model profile; legacy modes unused since 2025-10. |
| kv_cache_force_recompute | Force bypass cache for debugging | *Keep (restricted)* | Remains available only in restricted admin tooling; not a general runtime flag. |
| kv_cache_skip_reuse_on_miss | Fallback behavior in early cache | *Remove* | Redundant with unified policy engine; code path deleted. |

h2. Notes on what changed since the original ticket
* Experimental batching flags were originally planned for canary removal only; as of *2025-11*, the runtime defaults to Adaptive Micro-batching v2 and the legacy implementation is no longer exercised in production.
* KV-cache heuristics have been unified; selection is now driven by model profile + runtime policy rather than ad-hoc flags.

h1. Deprecation and removal timeline
* 2025-12 to 2026-01: Mark flags as deprecated in runtime logs and console.
* 2026-02: Stop reading deprecated flags (soft removal) while still accepting them in config payloads to avoid hard failures.
* 2026-03: Delete legacy code paths and remove flags from config schemas.
* 2026-04: Remove any remaining UI surfacing and docs references.

h1. Implementation plan
# Audit and enumerate flags
## Search for reads and writes across repos; produce a single source-of-truth list (this page).
## Identify flags that are:
* Dead (never read)
* Always-on
* Equivalent to a stable config knob
# Deprecation notices
## Runtime:
* Emit a warning when deprecated flags are present.
* Include a single-line migration hint to the replacement fleet-config keys.
## Console:
* Mark as deprecated with removal date.
* Hide deprecated flags from default view.
# Removal patches behind feature branches
## Land changes in small PRs:
* Introduce replacement fleet-config keys (validated, documented).
* Stop reading legacy flags (soft removal).
* Delete dead/legacy modules (hard removal).
# Testing and validation gates
## Microbenchmarks:
* Throughput (tokens/sec) must not regress > 1%.
* p95 end-to-end latency must not regress > 2%.
## End-to-end smoke tests:
* Streaming and non-streaming inference.
* Multi-turn sessions (cache reuse).
* High-concurrency workloads.
# Rollout and coordination
## Coordinate canary rollout with Eng-SRE and QA.
## Use dedicated canary pools and automatic rollback hooks.

h1. Rollout procedure
h2. Canary pools
* sr-canary-a (1% traffic)
* sr-canary-b (5% traffic)

h2. Success criteria
* Error rate increase <= 0.1% absolute (5xx and runtime-level failures).
* p95 latency increase <= 2% relative.
* Cache hit-rate does not drop > 3% relative for cache-eligible routes.

h2. Rollback
* Roll back by reverting to last known good runtime build and re-enabling legacy read path only if necessary.
* Note: once hard removal lands (code deletion), rollback requires reverting the runtime commit; this is why soft removal precedes hard removal by at least one release.

h1. Risk assessment
Overall risk is *low*, but requires careful canarying due to:
* Configuration drift across dedicated pools.
* Hidden dependencies in older customer deployments that may still set deprecated flags.

Mitigations:
* Soft removal phase (warn + ignore) before hard deletion.
* Canary pools with automated regression detection.
* Clear rollback path while soft removal is active.
