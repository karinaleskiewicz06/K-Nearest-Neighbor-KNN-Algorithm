module-stability-testing-and-rollback-catalog

Overview

This document catalogs our recommended stability testing and rollback practices for Terraform modules that affect GPU fleet, VPC/networking, and tenant IaC. It consolidates CI/CD checks, validation stages, ephemeral integration environments, and precise rollback playbooks so module changes can be promoted safely across dev -> staging -> production.

Goals
- Minimize blast radius of module changes to GPU clusters, shared VPCs, and cross-account networking.
- Provide repeatable, automated checks that catch config drift and regression before production promotion.
- Define clear manual and automated rollback paths with owners and SLAs.

Scope
Applies to: GPU-related modules (node pool, instance templates, device plugin), cross-account VPC modules, egress/NAT modules, IAM roles attached to infra, and shared Terraform library modules used by multiple services.

Quick summary of the pipeline (high level)
1) Author creates a feature branch and pushes a module change (semver minor or patch).
2) CI runs static checks (tflint, terraform validate, policy engine).
3) CI creates a short-lived test workspace and applies the module in a sandbox project (ephemeral env).
4) Integration tests run: node boot + kubelet check, container image pull, runtime smoke (inference hello world), and capacity probe.
5) Canary promotion: apply change to a single non-critical tenant or small dedicated GPU pool.
6) Observability window: 30–120 minutes depending on change type. SLOs must hold.
7) Promote to staging then production using module registry with pinned version. If regressions observed, run rollback playbook.

CI and policy checks (detailed)
- Static analysis: terraform fmt, terraform validate, tflint with provider rules, tfsec for common misconfigurations.
- Policy-as-code gate: Sentinel / Open Policy Agent rules for: disallowed instance types, required tags, encryption at rest, IAM least privilege, and required KMS keys.
- Unit & module tests: kitchen-terraform / terratest where applicable; tests must run in < 30m for PR gating.
- Drift detection: post-apply drift check that compares expected resources with cloud provider state.

CI job names and minimum timeouts
| Job name | Purpose | Timeout |
|---|---:|---:|
| module-lint | fmt/validate/tflint | 10m |
| module-policy | policy-as-code checks | 8m |
| module-apply-ephemeral | apply to ephemeral sandbox | 20m |
| module-integration | run terratest / smoke tests | 30m |
| module-canary-promote | orchestrate canary apply | 45m |

Ephemeral sandbox pattern (how-to)
- Each PR creates a workspace naming convention: pr-{repo}-{branch}-{shorthash}.
- Sandbox project uses isolated billing account and restricted network with a mirrored subset of prod subnets (no public egress except to package registries).
- Clean-up: automated destroy job (module-destroy-ephemeral) runs on PR close or after 6h.

Integration test checklist (must pass to promote)
1) GPU node boots and registers to cluster within 4 minutes.
2) kubelet reports Ready state for node within 6 minutes.
3) Container image pulls succeed (private registry auth tested).
4) Inference smoke endpoint returns expected response within 200ms 99% of the time for 100 requests.
5) Prometheus metrics for node: GPU memory available > 90% baseline, no OOM events.
6) No newly created security group or firewall rules that allow 0.0.0.0/0 access outside approved ports.

SLOs and alert thresholds during canary
- API error rate increase (relative): < 0.5% above baseline.
- p95 latency: no more than 20% increase from baseline.
- Node registration failure rate: < 1% for the canary pool.
- Rollback window: if any SLO violated for > 5m, immediate rollback recommended.

Promotion rules and semantic versioning
- Patch release: bug fixes, non-breaking changes. No canary required for low-risk modules (owner discretion).
- Minor release: adds backward-compatible features or optional parameters. Require ephemeral integration + canary apply.
- Major release: breaking changes to module interface; requires design doc, runbook, staged migration plan, and manual approval from infra owners.
- Registry: publish tag as vMAJOR.MINOR.PATCH and update module registry manifest. Consumers must pin exact version in production.

Rollback catalog (actionable playbook)
Each rollback entry below is a single-line canonical command (examples assume Terraform Cloud workspace or CI runner credentials are available). Owners must follow the post-rollback checklist.

1) Rollback: revert module to previous published version (module registry)
- Command example: 
```
# update caller repo to pin previous module version
sed -i 's/v1.4.0/v1.3.2/' modules/terraform-module-foo/versions.tf
git commit -m "pin(module-foo): rollback to v1.3.2"
git push && open-pr-to-main
# CI will trigger apply; if manual apply needed:
cd infra-live/tenant-abc && terraform init && terraform plan && terraform apply -auto-approve
```
Owner: module author / service owner. Response SLA: 15 minutes to start rollback once decision made.

2) Emergency network fix (e.g., new firewall rule opened to public)
- Command example:
```
# quick revert via cloud provider CLI to close rule
gcloud compute firewall-rules delete allow-new-inbound-rule --project=prod-shared-vpc
# then pin module change in VCS and run controlled apply to reintroduce safe rule
```
Owner: networking oncall. Response SLA: 5 minutes to mitigate, 30 minutes to full revert and validate.

3) GPU node template regression (bad boot script causing kubelet crash)
- Command example:
```
# roll instance template used by autoscaler to previous image
gcloud compute instance-templates describe gpu-template-v7 --format=json > /tmp/cur.json
gcloud compute instance-templates create gpu-template-v6 --source-instance-template=gpu-template-v6 --project=prod-gpu
# trigger rolling replacement via workload controller or autoscaler policy
kubectl rollout restart deployment/gpu-node-daemonset -n kube-system
```
Owner: gpu-fleet team. Response SLA: 10 minutes to begin, 60 minutes to complete rolling recovery.

Post-rollback checklist (mandatory)
- Confirm terraform state matches desired pin (terraform state list + remote-state check).
- Run integration smoke tests in staging for 30m.
- Open a post-incident ticket documenting root cause, timeline, and mitigation steps.
- Schedule an RCA with module owner within 3 business days.

Migration and state-handling patterns
- Remote state segmentation: one workspace per customer/tenant for dedicated pools; shared backend for global infra with strict ACLs.
- State locking: always enabled. Keep lock TTL < 1h for long-running applies via the CI job that periodically extends the lock.
- State migrations: publish a migration plan doc in the module PR for any change to resource addresses. Use terraform state mv in an ephemeral environment first.

Best-practices checklist for module authors
- Keep modules < 300 lines where possible; split infra concerns (networking vs compute vs iam).
- Provide examples/consumers in the module repo.
- Include migration notes in CHANGELOG.md and bump semver appropriately.
- Add at least 2 terratest cases covering create/destroy and one mutation path.
- Add annotated diagram of network flows when module modifies firewall/egress.

Operational runbook snippets (copyable)
- Canary promote (manual):
```
# in CI: tag module and create canary workspace
gh release create v1.5.0 --notes "canary: gpu node template update"
# create a temporary workspace that uses v1.5.0 in tenant-canary project
# wait 30m, run smoke checks
```
- Automated rollback threshold (example policy):
```
# monitoring alert language pseudocode
IF (p95_latency / baseline > 1.20) OR (error_rate - baseline > 0.005) FOR 5m THEN alert: infra.module-regression
```

Appendix: Quick checklist for PR reviewers
- Has the module author added terratest or kitchen-terraform tests?
- Is there a migration plan and CHANGELOG entry?
- Does policy-as-code pass locally? (tflint + tfsec)
- Are all outputs and variables documented with examples?
- Is the semantic version bump correct?
