SDK docs triage: quick wins sprint plan (streaming tutorial + payments demo + docs lint CI)

## Overview
This page captures the Developer Experience team’s quick wins sprint plan for improving SDK documentation quality and onboarding speed. It consolidates the original scratchpad plan into an actionable, reviewable checklist with clear scope, owners, and acceptance criteria.

**Primary outcomes:**
- First-time users can complete the streaming tutorial with a working example in under 10 minutes.
- A fully worked payments demo sample app exists (Node + Python), including environment setup and a minimal test harness.
- The top recurring doc lint issues are reduced and enforced via CI to prevent regression.

## Background / Why we’re doing this
Support tickets and Slack feedback indicate that users are most likely to get stuck at two points:
1) Streaming: example code diverged from the currently supported hosted API behavior, and curl buffering created the impression that streaming was broken.
2) Evaluations: teams want a concrete, end-to-end sample app demonstrating a common workflow (payments + LLM), but our examples are currently fragmented.

Small documentation fixes also have outsized impact: missing parameter types, incorrect code fences, and inconsistent naming repeatedly cause user confusion.

## Scope (this sprint)
### In scope
- Streaming tutorial updates (Getting Started → Streaming) including Node + Python snippets.
- A new payments demo sample app with README, environment variables, and sanity-check commands.
- Remediation of 10 high-signal docs lint findings across the SDK reference.
- CI integration for docs linting on PRs.

### Out of scope (explicitly deferred)
- Caching layer examples in payments demo.
- Full e2e UI demo (browser-based) for payments.
- Large-scale reference restructuring (handled as separate initiative if needed).

## Plan and timeboxes
The work is intended to fit into focused blocks (1–2 hours) with PR-based increments.

**Suggested schedule (example day):**
- 09:30–11:00: reproduce streaming issue + patch tutorial
- 11:30–13:30: scaffold payments-demo (initial commit)

## Task breakdown (prioritized)
### 1) Streaming tutorial fix
**Goal:** a new user can run streaming successfully via both SDK and curl without ambiguity.

**What changed since the original draft:**
- Confirmed with Marco that hosted API v2 standardized streaming behavior and the docs must reflect the v2 request shape.
- The main user-facing issue was not only the parameter name drift, but also curl output buffering and missing guidance around it.

**Actions:**
- Update code blocks to match the current hosted API v2 signature used by the official SDKs.
- Add an explicit note that for curl streaming, users should use `-N` (no-buffer) and avoid tools that re-buffer stdout.
- Add minimal client snippets for Node and Python that demonstrate:
  - enabling streaming
  - iterating chunks/events
  - printing partial output safely

**Acceptance criteria:**
- Tutorial steps succeed in a fresh environment using a new API key.
- Both Node and Python snippets are lint-clean and tested.

**Implementation note:**
If there are multiple API versions in the wild, call out versioning explicitly in the tutorial with a single recommended path (v2) and a short migration note (do not maintain two full parallel tutorials).

### 2) Payments demo sample app (Node + Python)
**Goal:** provide a “known-good” end-to-end example for payment-related flows that teams can adapt.

**Required components:**
- Node app: minimal HTTP service (Express or equivalent) that accepts a prompt, calls the Redwood API, and returns structured JSON.
- Python example: equivalent request path using `requests` (and a short section on common pitfalls).
- README that includes:
  - prerequisites
  - `.env` usage and security warnings
  - environment variables
  - local run steps
  - expected output example
  - sanity-check commands

**Security note (updated):**
The README must include explicit guidance not to embed API keys in client-side code and to keep keys in `.env` / server-side only.

**Optional (recommended) test harness:**
- Keep it minimal: one smoke test per language (e.g., `pytest` for Python, `node` script for Node) that verifies non-empty output and handles network errors clearly.

### 3) Docs lint sweep (10 quick wins)
**Goal:** reduce recurring micro-friction in SDK reference pages.

**Targets (examples):**
- Missing parameter types
- Incorrect or inconsistent naming (e.g., `model` vs `model_name`) where applicable
- Broken or mislabeled code fences
- Missing “minimal example” blocks in frequently visited reference pages

**Process:**
- Run the linter locally.
- Fix the top 10 issues that are:
  - high confidence
  - low risk
  - user-visible
- If any fix requires structural refactoring, open a dedicated PR per area.

### 4) CI lint integration
**Goal:** prevent regressions by running docs lint on PRs.

**Updated rollout decision:**
- Week 1: CI check runs and reports status (non-blocking).
- After 1 week (probation), convert to a required check for docs repo PRs.

**Implementation details:**
- Add a GitHub Actions workflow to run the docs linter on pull requests.
- Scope to changes in docs and examples paths to keep runtime low.

### 5) Quick UX copy improvements
**Goal:** address two recurring confusion points with small, targeted edits.

- Clarify “token cost” note with a concrete worked example.
- Rewrite the most confusing paragraph on rate limiting (keep it short, with one example and one link to the deeper page).

## Commands / snippets
**Local docs lint:**
- `yarn docs:lint`
- `./scripts/docs_lint.sh`

**Run sample app (Node):**
- `PORT=3000 API_KEY=xxxxx node payments-demo/index.js`

**Curl streaming example (ensure unbuffered output):**
- `curl -N -H "Authorization: Bearer $API_KEY" -H "Content-Type: application/json" -d '{"model":"gpt-redwood-1","stream":true,"input":"Hello"}' https://api.redwood.ai/v2/generate/stream`

Note: endpoint and payload should match whatever the SDK uses in its latest stable release; update this snippet if the SDK changes.
