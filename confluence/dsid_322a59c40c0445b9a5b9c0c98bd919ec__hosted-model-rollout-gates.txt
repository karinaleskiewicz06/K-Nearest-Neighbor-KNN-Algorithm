Hosted API model rollout gates (eval readiness)

# Overview
This page defines the **evaluation readiness gates** required before shipping a new **Hosted API** model version (or changing serving configuration that can impact outputs). The goal is to prevent quality regressions while keeping rollout velocity predictable.

These gates apply whether the rollout is performed as a normal canary or as part of a fallback-enabled deployment.

# Scope
**In scope:** chat/completions models exposed via the Hosted API, model version bumps, tokenizer changes, system prompt changes, safety policy changes, quantization/profile changes that materially alter outputs.

**Out of scope:** embeddings-only model refreshes (see Embeddings Rollout Gates), internal-only experimental endpoints.

# Required artifacts (must be attached in the release ticket)
1. **Model build identifier** (registry tag) and release candidate name.
2. **Prompt set selection**: which prompt sets were run and why they are representative.
3. **Eval report** (export link) including summary metrics, failures, and deltas vs current prod version.
4. **Known limitations**: any known degraded categories, and mitigations.
5. **Fallback compatibility statement**: confirm the candidate is compatible with the configured fallback path (see section below).

# Gate checklist (pass/fail)
## Gate A — Coverage
- Run at least **one** tier-1 prompt set for the product surface you are shipping:
  - `hosted-api/general-chat-tier1` for general chat
  - `hosted-api/tool-calling-tier1` if tool calling is enabled
  - `hosted-api/structured-output-tier1` if JSON/grammar constraints are enabled
- Run at least **one** customer-representative prompt set if the model is pinned for a dedicated customer route.

## Gate B — Regression thresholds
Compare candidate vs **current prod** on the same prompt sets. Candidate must satisfy:
- **Hard failures:** 0 increase in “critical” failures (crashes, empty outputs, malformed structured output where required).
- **Tool calling:** no increase in invalid tool schemas; function name mismatch rate must not increase by > **0.3% absolute** on tier-1 tool set.
- **Safety policies:** no new disallowed content categories vs baseline; safety classifier deltas must be reviewed if any category increases by > **0.2% absolute**.
- **Quality composite score:** must be within **-1.0%** of baseline or better on the tier-1 set. If worse, the Applied ML reviewer must explicitly approve with rationale.

## Gate C — Spot checks
- Minimum **20** human spot checks across:
  - top 10 highest-traffic prompt archetypes
  - top 5 “historically brittle” archetypes (from regression triage)
  - 5 tool-calling examples (if applicable)

## Gate D — Fallback compatibility
If the rollout is configured with **automatic fallback enabled**, confirm:
- Candidate and fallback share a compatible API surface (tool calling/structured output flags, max output token behavior, stop sequence semantics).
- Candidate does not rely on a feature not supported by fallback (e.g., strict JSON grammar enforcement if fallback cannot guarantee it).
- Candidate’s tokenizer changes do not break downstream structured parsing assumptions used in production routes.

# Exceptions
If any gate is not met, the release can proceed only via an **exception** documented in the release ticket with:
- explicit risk description
- impact radius (routes/tenants)
- monitoring plan
- rollback plan
- approving reviewer from Applied ML

# Roles
- **Primary owner:** Applied ML on-call (or model onboarding DRI) verifies gates.
- **Consulted:** Product (if user-visible behaviors change), Runtime (if profile/quantization changes), Support (if known limitations require proactive comms).

# What done looks like
A release ticket exists with the artifacts above, gates marked pass/exception, and a link to the eval report export.
