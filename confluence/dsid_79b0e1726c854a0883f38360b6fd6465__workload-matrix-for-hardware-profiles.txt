Workload Matrix for Hardware Tuning Profiles (H100/B200/L40S)

## Purpose
This page defines the benchmark methodology and **standard workload matrix** used to validate Redwood’s **hardware tuning profile pack** across NVIDIA **H100**, **B200**, and **L40S** fleets.

The matrix is designed to:
- Provide a **representative but bounded** set of request patterns that capture real production behavior.
- Make performance deltas attributable to profile changes (scheduler + kernel selection + KV cache + CPU/runtime knobs).
- Produce artifacts that are stable enough for **perf-canary gating** and regression triage.

## Non-goals
- Exhaustively modeling every customer workload.
- Proving absolute “best possible” performance per SKU.
- Long-running soak tests (covered in separate reliability qualification).

## Definitions (used throughout)
- **Prefill**: prompt ingestion / context processing stage.
- **Decode**: token-by-token generation stage.
- **TTFT**: time-to-first-token (streaming) or time-to-first-byte-equivalent (non-streaming).
- **TPOT**: time-per-output-token.
- **Concurrency**: number of in-flight requests per replica (not cluster-wide).
- **Profile**: versioned runtime configuration pack selected by GPU SKU + optional overrides.

## Guiding principles
1) **Workload realism > synthetic peak**: we include tool-calling/structured output shapes and streaming.
2) **Tail-aware**: acceptance criteria always include p95 (and sometimes p99) for TTFT and end-to-end latency.
3) **Repeatable**: fixed prompt set IDs, fixed sampling params, controlled warmup, pinned harness version.
4) **Comparable across SKUs**: the same logical workloads run on H100/B200/L40S; scale/guardrails may differ.

## Matrix dimensions
The matrix is the cartesian product of a small set of standard dimensions, with explicit pruning rules to keep total runs manageable.

### 1) Model families (serving runtime coverage)
We validate across these families because they stress different kernel paths and KV/cache behavior:

| Family | Representative models (internal aliases) | Why it matters |
|---|---|---|
| Llama-style dense | `llama-3-8b`, `llama-3-70b` | Baseline for most traffic; stable comparison across SKUs |
| MoE | `mixtral-8x7b` | Router + expert sparsity changes compute/memory balance |
| Long-context variants | `llama-3-8b-longctx` | KV cache pressure and fragmentation sensitivity |
| Small instruction-tuned | `instruct-7b` | Scheduler fairness and batching behavior under high QPS |

Notes:
- Model names above are for benchmark harness routing; the actual pinned model IDs are maintained in the perf-suite repository config.
- We do not include embeddings/rerank in this matrix (separate suite), except for a small smoke test in CI.

### 2) Sequence-length buckets
We bucket by **prompt tokens** and **output tokens**; buckets are chosen to reflect observed production mixes and known inflection points in kernel selection.

**Prompt token buckets (P):**
- **P1 (short):** 32–256
- **P2 (medium):** 256–1,024
- **P3 (long):** 1,024–4,096
- **P4 (xlong):** 4,096–16,384 (only for long-context-capable model variants)

**Output token buckets (O):**
- **O1 (short):** 16–128
- **O2 (medium):** 128–512
- **O3 (long):** 512–1,536

Pruning rules:
- P4 runs only on designated long-context models.
- O3 is excluded for L40S in high-concurrency runs unless explicitly marked safe (to avoid turning the matrix into a memory stress test).

### 3) Concurrency levels
We use concurrency tiers that expose scheduler trade-offs and batching behavior.

| Tier | In-flight requests / replica | Intended effect |
|---|---:|---|
| C1 | 1 | Single-request latency path; kernel selection sanity |
| C2 | 4 | Light batching; common interactive load |
| C3 | 16 | Throughput-oriented; highlights fairness/backpressure |
| C4 | 32 | Stress tier; used selectively (H100/B200 only unless stated) |

Implementation note:
- Concurrency is enforced at the harness client layer with a target arrival process (see “Load shape”).

### 4) Streaming vs non-streaming
We always test both because profiles can improve throughput but degrade streaming TTFT due to queueing/backpressure.

Modes:
- **S0 (non-streaming):** response buffered, metrics taken at completion.
- **S1 (streaming):** SSE/streaming enabled; TTFT and TPOT computed from token timestamps.

### 5) Request patterns (scenario presets)
We group runs into a small set of “scenarios” that map to production archetypes.

| Scenario ID | Name | Mix | Notes |
|---|---|---|---|
| W1 | Chat interactive | P1/P2 + O1/O2 | Primary gating scenario; tail-sensitive |
| W2 | Agent/tool-calling | P2/P3 + O1/O2 | Includes JSON/structured output constraints |
| W3 | Summarization | P3 + O2/O3 | Prefill-heavy + sustained decode |
| W4 | Long-context Q&A | P4 + O1/O2 | KV/cache stress; selective concurrency |
| W5 | Batchy offline | P2 + O2 | Throughput-biased, non-streaming only |

Tool-calling/structured output approximation:
- We emulate tool-calling by using a fixed subset of prompts that request JSON outputs and enforce a strict schema in the client checker.
- Sampling is deterministic (see “Sampling params”).

## Standard workload matrix (what we actually run)
The “standard matrix” is the required set for each profile version. Additional exploratory runs can be appended, but must be labeled as non-gating.

### Gating matrix (per GPU SKU)

**H100 (baseline + tuned):**
- Models: llama-style dense (8B + 70B), MoE
- Scenarios: W1, W2, W3, W5
- Concurrency: C1, C2, C3, plus C4 for W5
- Streaming: S0 + S1 for W1/W2/W3; S0 only for W5

**B200 (experimental gating until promoted):**
- Models: llama-style dense (8B + 70B)
- Scenarios: W1, W3
- Concurrency: C1, C2, C3 (C4 optional if fleet is stable)
- Streaming: S0 + S1
- Additional requirements: explicit driver/CUDA compatibility checks must be green before results are considered valid.

**L40S (memory-constrained):**
- Models: llama-style dense (8B), small instruction-tuned
- Scenarios: W1, W2, W5 (W3 optional and flagged “memory-risk”)
- Concurrency: C1, C2, C3 (C4 not run by default)
- Streaming: S0 + S1 for W1/W2; S0 only for W5

### Explicit exclusions
- Multi-GPU tensor-parallel runs are excluded from the standard matrix unless the profile explicitly targets collectives/NCCL tuning.
- MIG partitioning is not part of the gating matrix; see “Environment requirements” for how we treat MIG.

## Load shape and run structure
### Load shape
We use a fixed arrival model per run:
- **Closed-loop**: maintain N in-flight requests (N = concurrency tier) with think-time sampled from a fixed distribution.
- Think-time distributions:
  - W1/W2: median 150ms, p95 600ms
  - W3/W5: median 50ms, p95 200ms

Rationale: closed-loop produces stable replica-local saturation curves and reduces sensitivity to minor client-side jitter.

### Warmup and measurement windows
Per (model, scenario, concurrency, streaming) run:
1) **Warmup:** 2 minutes (discard metrics)
2) **Measure:** 8 minutes
3) **Cooldown:** optional 1 minute (collect final memory/fragmentation stats)

Minimum sample sizes:
- Target ≥ 2,000 completed requests per run for W1/W2 at C2/C3.
- For long-context scenarios (W4), target ≥ 200 completed requests.

### Sampling params (pinned)
To reduce variance, we pin decoding parameters:
- temperature: 0.0 (greedy)
- top_p: 1.0
- frequency_penalty: 0.0
- presence_penalty: 0.0
- stop sequences: none (except structured-output prompts where required)

Notes:
- Greedy decoding is deliberate for perf gating; quality evals are tracked separately.

## Metrics collected (required)
For each run, we capture request-level and token-level metrics:

### Primary metrics
- **TTFT p50/p95** (S1 streaming; S0 approximated from server timestamps)
- **End-to-end latency p50/p95**
- **Throughput:** output tokens/sec (replica-local) and requests/sec
- **TPOT p50/p95** (streaming)

### Resource and stability metrics
- GPU utilization (avg + p95)
- HBM usage (avg + peak)
- KV cache allocated/used; eviction events
- OOM count, retry count, fallback count
- Scheduler queue depth (avg + p95), queue wait time
- CPU-side runtime: p95 request enqueue latency, thread pool saturation

### Required tags (for segmentation)
Each datapoint must include:
- gpu_sku (normalized)
- profile_name, profile_version
- profile_override_source (default / pool / deployment / env)
- model_id
- scenario_id
- concurrency_tier
- streaming_mode

## Acceptance criteria (regression gates)
Acceptance is defined relative to a pinned baseline (previous profile pack version or runtime defaults), using bounded regressions and minimum improvements.

### Default regression policy (unless profile doc states otherwise)
For gating scenarios (W1/W2/W3):
- **No regressions > 3%** in p95 end-to-end latency at C2 and C3.
- **No regressions > 5%** in p95 TTFT (streaming) at C2.
- **No increase** in OOM/retry rates (must remain at 0 for the standard matrix).

For throughput scenarios (W5):
- Must demonstrate **≥ 5% throughput improvement** at C3 or C4 *or* keep throughput flat while reducing tail latency.

### SKU-specific notes
- **L40S:** memory guardrails are part of the product value; any profile that increases peak HBM by > 2% in W1 at C3 requires explicit review by Runtime Scheduling + Memory owners.
- **B200:** results are considered “non-blocking” until the profile is promoted out of experimental; however, any detected severe regression (TTFT p95 +10% or any OOM) blocks enabling the profile in that pool/region.

### When to override the default policy
If a profile intentionally trades tail latency for throughput (e.g., “throughput-first”), the profile reference page must:
- Declare the intended envelope (scenario + concurrency)
- Provide an explicit rollback trigger
- Provide a safe “balanced” alternative

---

## Environment requirements (to keep runs comparable)
### Hardware + firmware
- GPUs must report consistent SKU strings (normalized via runtime detection).
- Power limit and clocks must be left at fleet defaults (no manual overclock).

### Software stack
- Runtime build SHA pinned per experiment.
- Driver/CUDA versions recorded in the run artifact.
- B200 runs require the minimum driver/CUDA versions specified in the B200 profile reference.

### MIG and multi-GPU nodes
- **MIG:** not part of the standard gating suite; if MIG is enabled in the fleet, runs must label `mig_mode=true` and are treated as separate baselines.
- **Multi-GPU nodes:** standard suite assumes 1 GPU per replica unless otherwise stated. If 2+ GPUs are used, tensor-parallel degree must be declared and results are not comparable to 1-GPU baselines.

## Reproducibility and artifacts
### What gets stored per run
Each run produces a single “summary bundle”:
- `run.json`: environment + config + pinned workload identifiers
- `metrics.parquet`: request/token-level metrics (tagged)
- `summary.md`: human-readable table (deltas vs baseline)
- `plots/`: TTFT/latency curves, throughput vs concurrency, HBM over time

### Prompt set and dataset pinning
Prompt sets are referenced by immutable IDs in the benchmark harness:
- `promptset_w1_v3`
- `promptset_w2_json_v2`
- `promptset_w3_sum_v2`
- `promptset_w4_longctx_v1`
- `promptset_w5_batch_v2`

Any change to prompt sets requires:
- Bumping the prompt set ID
- Re-baselining the acceptance thresholds (or explicitly marking as “methodology change”)

## How to run (standard)
The harness supports local (single node) and managed runner modes.

### Local single-run example
1) Select GPU and profile:
- Ensure the runtime selects the intended profile (check startup logs / profile metrics).

2) Execute a single matrix cell:
- Example (W1, llama-3-8b, C2, streaming):

Command template:
- `bench run --model llama-3-8b --scenario W1 --concurrency 4 --streaming true --duration 8m --warmup 2m --out ./artifacts/W1_llama3-8b_C2_S1`

3) Verify:
- OOM/retry count is zero
- Tags include profile_name/profile_version

### Full matrix execution
- `bench matrix --sku H100 --matrix standard --out s3://redwood-bench/artifacts/<date>/<build_sha>/`

Operational note:
- Full matrix runs are scheduled off-peak for shared runners; on dedicated perf runners, follow the runner reservation policy.

## Reporting format (what reviewers expect)
Every profile candidate must include a short report (auto-generated + 3–6 bullets of commentary):
- Delta tables per scenario
- Throughput vs concurrency curves
- TTFT and tail latency breakdown
- Any failures with links to logs and mitigations

Minimum commentary fields:
- What improved and why (tie to scheduler/kernel/KV knobs)
- What regressed (if anything) and whether it’s within the declared envelope
- Risk assessment (esp. tail latency and memory)

---

## Common failure modes (and how the matrix catches them)
- **Tail latency regression from fairness/backpressure changes:** shows up in W1/W2 at C3 with streaming TTFT p95.
- **Memory fragmentation / KV cache over-allocation:** shows up as rising peak HBM or eventual OOM in W3/W4.
- **Kernel mismatch by seq bucket:** shows up as throughput dip for specific P-buckets in W1/W3; requires bucketed plots.
- **Noisy perf-canary gates:** addressed by minimum sample sizes, warmup windows, and pinned prompts.
