## Deployment modes referenced in this FAQ
Redwood supports multiple deployment modes. Security controls and responsibility boundaries differ by mode.

**Redwood API (Hosted):** Multi-tenant managed service. Best for fastest time-to-value. Not the default recommendation for regulated/PHI/strict residency workloads.

**Redwood Dedicated:** Single-tenant dedicated GPU pools with customer isolation and predictable throughput; managed by Redwood.

**Redwood Private:** Customer-controlled deployment in a **customer VPC** or **on-prem** environment (regulated/air-gapped patterns). Network and key ownership can be customer-managed.

When a prospect says “regulated,” default to qualifying for **Dedicated** or **Private**.

## Compliance & assurance

**Answer (approved):** Yes. Redwood maintains a **SOC 2 Type II** report. We can share the report under NDA via our evidence pack process.

**Notes for sales:**
- Offer a “security review call” and propose a fast path for questionnaires.

**Answer (approved):** Redwood operates an information security program aligned with ISO 27001 controls. If ISO 27001 certification is a hard requirement, we will confirm current certification status and scope via Security and provide the appropriate evidence or program materials.

**When to escalate:** If the prospect requires ISO certificate number/scope statement.


### Q: Can Redwood support HIPAA / PHI workloads?
**Answer (approved):** Redwood supports **PHI-adjacent and regulated healthcare deployment patterns** using **Dedicated** and **Private (VPC/on‑prem)** options, with encryption, audit logging, and enterprise access controls. Contractual and configuration requirements (e.g., retention, access, logging, and permitted uses) should be confirmed during a security review.

**Do not say:** “HIPAA compliant” or “HIPAA-ready” in isolation.


### Q: Can you support GDPR / DPA requirements?
**Answer (approved):** Yes. Redwood can support common DPA requirements (confidentiality, security measures, subprocessor transparency, and deletion/return terms). We will align the deployment mode, retention configuration, and residency requirements during contracting and security review.

**Notes:** Route DPA redlines to Legal (Michael Grant / Sofia Mendes).


### Q: Do you support PCI / payment data workloads?
**Answer (approved):** Redwood can support regulated security controls, but PCI scope depends on the customer’s use case and data flows. If the workload involves cardholder data, we should run a security review to confirm the correct deployment mode and control boundaries.

## Data handling, privacy, and model training

### Q: Do you train on customer data?
**Answer (approved):** Redwood does **not** use customer prompts or outputs to train foundation models by default. Data handling depends on the product configuration and contractual terms; we can confirm the specific terms during security review.

**Notes:** If a prospect requests a “no training/no retention” clause, loop in Legal + Security.


### Q: What customer data do you store, and for how long?
**Answer (approved):** Retention is **deployment- and configuration-dependent**. Redwood can support minimal retention patterns and align with regulated requirements.

Typical retention categories to clarify:
- **Inference request/response content** (prompts, outputs)
- **Operational metadata** (timestamps, latency, token counts, model version, request IDs)
- **Audit logs** (admin/auth/config changes)

**Positioning guidance:**
- For strict retention controls, recommend **Private** or **Dedicated** and confirm exact settings in the pilot plan.


### Q: Can we request deletion of customer data?
**Answer (approved):** Yes. Redwood supports deletion workflows consistent with contractual terms. In Private deployments, customers often control storage endpoints directly, which can simplify deletion and retention enforcement.

**Escalate if:** The buyer requests deletion SLAs or certification statements.


### Q: Do you support data residency / regional processing?
**Answer (approved):** Yes. Residency options depend on deployment mode.
- **Hosted:** regional availability is limited to supported cloud regions; confirm current regions with Sales Engineering.
- **Dedicated:** capacity can be provisioned in supported regions, with isolation.
- **Private:** customer selects the region/environment (VPC/on‑prem), enabling the strongest residency control.

**Notes:** If the buyer requires “no cross-border processing,” default to **Private**.

## Encryption and key management

### Q: Is data encrypted in transit?
**Answer (approved):** Yes. Redwood uses TLS for data in transit. Specific TLS versions/cipher requirements can be validated during security review and implementation planning.


### Q: Is data encrypted at rest?
**Answer (approved):** Yes. Redwood encrypts data at rest for supported storage systems used in Dedicated/Hosted. For Private deployments, encryption at rest can be implemented using customer-managed infrastructure controls.


### Q: Do you support customer-managed keys (KMS) or HSM?
**Answer (approved):** Yes, for **Private** deployments we can integrate with customer key management requirements (e.g., cloud KMS). HSM requirements and exact integration patterns should be confirmed during a technical deep dive.

**Notes for SEs:** If the buyer asks for “BYOK everywhere,” clarify whether they mean:
- Encryption keys for persistent storage
- Envelope encryption patterns
- TLS termination keys
- Signing keys for audit log integrity

## Network security and isolation

### Q: Can Redwood run in our VPC with no public ingress?
**Answer (approved):** Yes. **Redwood Private (VPC)** supports private networking patterns where ingress/egress can be restricted according to customer policies.


### Q: Do you support on-prem or air-gapped environments?
**Answer (approved):** Redwood Private includes an on‑prem option for regulated or restricted environments. Feasibility depends on hardware requirements and operational constraints; we validate this during discovery.


### Q: How is tenant isolation handled?
**Answer (approved):**
- **Dedicated:** customer receives isolated capacity (single-tenant GPU pool).
- **Private:** customer controls the environment boundary (VPC/on‑prem) and isolation is enforced by customer infrastructure plus Redwood deployment architecture.
- **Hosted:** multi-tenant with logical isolation.

## Identity, access control, and admin security

### Q: Do you support SSO (SAML) and enterprise access controls?
**Answer (approved):** Yes. Redwood supports enterprise authentication patterns including **SSO (SAML)** and role-based access controls for Console and administrative access, depending on plan and deployment.

**Notes:** If the buyer asks about SCIM provisioning or specific IdP edge cases, route to SE + Support for validation.


### Q: Do you support RBAC?
**Answer (approved):** Yes. Access to the Redwood Console and administrative actions can be controlled via roles/permissions. For regulated customers, we recommend least-privilege roles and periodic access reviews.


### Q: Do you support MFA?
**Answer (approved):** Redwood supports MFA/strong authentication patterns, and SSO enforcement can be used for centralized policy control.

**Escalate if:** Buyer requests “phishing-resistant MFA only” requirements.


### Q: How do you control internal access to customer environments/data?
**Answer (approved):** Redwood limits internal access following least privilege and operational need. For regulated deployments, we can align support access procedures (approval workflows, time-bounded access, logging) during security review.

## Audit logging and monitoring

### Q: Do you provide audit logs?
**Answer (approved):** Yes. Redwood provides **audit logs** for security-relevant administrative events (e.g., authentication events, user/role changes, configuration changes). Audit log availability and export options depend on the deployment mode.


### Q: What fields are included in audit logs?
**Answer (approved):** Typical audit log records include:
- Timestamp, actor identity, actor type (user/service)
- Action/event type (e.g., login, role update, key/config change)
- Target resource identifiers
- Result (success/failure) and failure reason (where applicable)
- Request correlation ID / trace ID (where applicable)
- Source IP / user agent (where applicable)

**Note:** Exact schema varies by product area; provide the latest schema from the evidence pack or SE reference example.


### Q: Can we export audit logs to our SIEM?
**Answer (approved):** Yes. Redwood supports audit log export patterns for regulated environments. The recommended export approach depends on whether you’re using Dedicated or Private.

**If asked for a quick technical reference:** Point to the internal example reference and offer an SE-led deep dive.


### Q: Do you log customer prompt/output content?
**Answer (approved):** Logging of prompt/output content is **configurable** and should be minimized for regulated workloads unless explicitly required. Redwood can support operational logging that focuses on metadata (latency, token counts, request IDs) rather than payload content.

**Notes:** If a buyer requires “no payload logging,” confirm configuration and contract language with Security/SE.
