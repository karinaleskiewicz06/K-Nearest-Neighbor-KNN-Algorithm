GPU rolling reboot, network bridge & IaC pipeline playbook

Summary
-------
This playbook describes the safe, automated procedure Redwood uses to perform planned rolling reboots of GPU node pools across multiple cloud accounts/VPCs while preserving model-serving SLOs. It covers the operational strategy, preflight checks, Terraform/IaC changes and code workflow, CI/CD steps for the rollout, validation smoke tests, rollback criteria, and post-maintenance verification.

Scope and goals
----------------
- Scope: GPU nodepools and associated networking (VPC peering, ENIs, route tables, and transit gateway bridges) used by Redwood serving clusters (hosted + dedicated). Includes multi-account setups and clusters behind TF-managed load balancers.
- Goal: Perform rolling reboots/upgrades without exceeding target SLOs: 99.9% availability per serving-route and median tail latency degradation <= 20%.
- Constraints: Must be executable from the central infra CI pipeline and must require manual approval for cross-account network changes.

When to run
-----------
- Planned maintenance, kernel CVE mitigation, GPU firmware driver updates, or cloud-hosted OS patch windows.
- NOT for emergency security patching (see incident response runbooks).

Prerequisites
-------------
1. Owner assigned (primary and secondary).
2. Open maintenance ticket in JIRA with runbook link and CI change request.
3. Minimum 48 hours notice for customers affected by Dedicated capacity.
4. Current capacity and scaling headroom: total spare GPUs >= 15% of active serving capacity.
5. All Terraform plans have been reviewed and approved in the target repo.

Preflight checks (automated & manual)
------------------------------------
Automated checks (CI job: infra-maintenance/preflight):
- Verify nodepool autoscaler is healthy and enabled (kubectl get hpa, k8s metrics).
- Check cluster pod disruption budgets (PDBs) >= desired for routes flagged as high-priority.
- Query utilization: token-per-second vs GPU count for last 6 hours; ensure headroom.
- Validate network path health for peered VPCs (ping targets via bastion, traceroute).
- terraform plan --var-file=maintenance.tfvars produces zero drift for non-intended resources.

Manual checks (owner):
1. Confirm customer notification is sent and acknowledged for Dedicated customers.
2. Confirm SRE on-call availability windows.
3. Confirm fallback capacity: a warm spare cluster or burst policy is ready.

Rolling strategy (golden path)
-----------------------------
- Node-level rolling: reboot one GPU node at a time within a replication group, wait for stabilization, then continue.
- Batch size: default 1 node per AZ per region; configurable to 2 for low-util windows.
- Delay window: 10 minutes after node rejoins then 30-min observation; extend if error rate rises above thresholds.
- Inter-region cadence: complete whole AZ in region A before starting region B for multi-region traffic-sensitive workloads.

Circuit breakers and SLO thresholds
----------------------------------
- Error rate increase > 2x baseline over a 10-minute window -> pause rollout and notify SRE.
- Tail latency (95p) increase > 50% -> pause and rollback last batch.
- /health endpoint failure rate > 0.5% for critical routes -> immediate pause.
- If > 10% of nodes in a pool are reprovisioning at once -> abort and rollback.

Terraform / IaC considerations
-----------------------------
- Use the maintenance branch in infra-gpu-modules repo. Make only additive changes.
- Preferred pattern: module-level boolean flags enable_rolling_reboot = true and maintenance_window = "2026-03-xxTYY:ZZ" to avoid diffing unrelated resources.
- When changing network (VPC peering/transit gateway) require multi-sig approval and cross-account IAM reviewers.
- Always run terraform plan in a disposable bootstrap workspace and attach plan to PR.

Recommended Terraform snippet (example for nodepool lifecycle override):

```hcl
module "gpu_nodepool" {
  source = "git::ssh://git@github.com/redwood/terraform-gpu-nodepool.git//modules/nodepool"
  name   = "gpux-large-${var.region}"
  size   = 24
  enable_rolling_reboot = true
  maintenance_window = var.maintenance_window
}
```

CI/CD pipeline flow (infra-maintenance)
--------------------------------------
1. Developer creates maintenance branch with the IaC/helm changes and opens PR.
2. infra-maintenance/preflight job runs automated checks.
3. After green, merge requires two infra approvers and a cross-account reviewer if networking changed.
4. Post-merge: infra-maintenance/execute job creates a Terraform plan in the central bootstrap workspace and posts the plan artifact to the ticket.
5. Manually approve run in the pipeline (for network changes) or automatic with time-based gate for node reboots.
6. Orchestrator job sequentially calls the cluster agent to drain, reboot, and uncordon nodes using the chosen batch size.

Pipeline commands (examples)
- terraform workspace select maintenance-2026-03 || terraform workspace new maintenance-2026-03
- terraform apply -auto-approve "planfile"
- ./infra-scripts/drain-and-reboot.sh --cluster $CLUSTER --node $NODE_ID --timeout 1800

Cluster agent orchestration behavior
-----------------------------------
- The orchestrator uses the following sequence for each node: 1) cordon, 2) drain (respecting PDBs), 3) wait for <N> healthy replicas via readiness probes, 4) ssh/reboot or cloud provider reboot, 5) ensure kubelet reconnects and node becomes Ready, 6) uncordon.
- If step 4 fails (node does not come back within 30 minutes) the node is marked for reprovisioning and a separate job reprovisions the instance instead of further reboots.

Validation and smoke tests
--------------------------
- Smoke tests run after each batch:
  - Liveness and readiness checks for model-serving pods.
  - End-to-end token generation latency sampling against a synthetic workload (10 qps for 2 minutes).
  - Embedding pipeline sample throughput check (run tiny batch job).
- Example HTTP check: curl -sS -w "%{http_code} %{time_total}\n" https://api.redwood.prod/model/health

Rollback procedures
-------------------
- Soft rollback: pause further batches, increase autoscaler target and route traffic to unaffected clusters.
- Hard rollback (IaC revert): revert the merged commit and run terraform apply with the previous state; reprovision nodes to prior image.
- Emergency reprovision: mark failing nodepool and invoke reprovision job: ./infra-scripts/reprovision-nodepool --cluster $CLUSTER --pool $POOL --force
- Post-roll back validation: run the same smoke tests and monitor SLOs for 2 hours.

Notifications and runbook logging
--------------------------------
- All actions must be tracked in the maintenance JIRA with attached pipeline artifacts and plan diffs.
- Notify #infra-ops and the Dedicated customer channel at each major step (start, per-region complete, complete).
- Logging: orchestrator writes per-node audit events to kinesis stream infra-maintenance-audit with tags: maintenance_id, node_id, batch, outcome.

Ownership, roles and escalation
-------------------------------
- Run owner: oncall infra engineer (primary).
- Approvers: infra leads (2) + cross-account reviewer for network changes.
- SRE escalation: if circuit breaker triggers, page SRE L2 and on-call platform engineer.
- Post-mortem: if outage > 30m or SLO breach occurs, open postmortem and link to the maintenance ticket within 48 hours.

Appendix: handy commands & snippets
-----------------------------------
- Drain node: kubectl drain $NODE --ignore-daemonsets --delete-local-data --timeout=30m
- Uncordon: kubectl uncordon $NODE
- Check node ready: kubectl get nodes $NODE -o jsonpath='{".status.conditions[?(@.type==\"Ready\")].status"}'
- Terraform plan: terraform plan -out=planfile -var-file=maintenance.tfvars
- Reboot via cloud CLI (example GCP): gcloud compute instances reset $INSTANCE --zone=$ZONE

Post-maintenance checklist
--------------------------
- Confirm all nodes show Ready and kubelet version matches expected image.
- Confirm all PDBs are honored and no pods in CrashLoopBackOff.
- Confirm 2 hours of SLO telemetry shows no regression above thresholds.
- Close maintenance ticket and attach artifacts: terraform plan, pipeline logs, smoke test outputs, and audit stream ids.

Notes and operational tips
-------------------------
- Prefer smaller batches in high-traffic windows; increase batch size for off-hours.
- Keep a dedicated warm spare cluster for Dedicated customers to reduce blast radius.
- Document any manual deviations as a separate ticket and include rationale.
