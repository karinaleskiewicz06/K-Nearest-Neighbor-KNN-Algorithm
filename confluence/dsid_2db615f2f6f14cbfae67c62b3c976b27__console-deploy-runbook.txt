Runbook: Deploying Redwood Console to Production

h1. Overview
This runbook describes how to deploy the Redwood Console (console-web and console-api) to production with minimal user disruption. Follow the Production Change Management Standard and Prod Deployment Gates.

h1. Components
* console-web: static assets + edge caching
* console-api: backend service used by the web app
* feature-flag service: governs availability of new functionality

h1. Preconditions
1. Change record exists with rollback + verification plans.
2. Approvals captured (peer + service owner; add security review if auth/session handling changes).
3. Release artifact prepared: build IDs for console-web and console-api.
4. If UI copy changes could confuse customers, prepare comms text for Support (internal).

h1. Deployment approach
* Prefer: deploy console-api first, then console-web.
* Use feature flags to dark-launch new features; avoid releasing a UI that depends on a backend not yet deployed.
* Canary: enable for internal staff cohort before broad release when feasible.

h1. Step-by-step procedure
1. Announce (internal)
   * Post in #eng-releases: change record, affected components, start time, canary plan, rollback trigger.

2. Pre-deploy checks
   * Confirm console-api error rate and p95 latency are within baseline.
   * Confirm auth provider status is healthy (if applicable).
   * Confirm no active incidents affecting login/session.

3. Deploy console-api
   * Deploy to production using deployctl with pinned image digest.
   * Validate readiness and basic health endpoint.

4. Canary validation
   * Validate login, org switching, API key creation, usage dashboard loads, and a representative settings page.
   * Confirm feature-flag evaluations are succeeding; check for increased 401/403.

5. Deploy console-web
   * Publish the new static bundle and confirm cache invalidation completes.
   * Keep prior bundle available for rapid rollback.

6. Post-deploy validation (60 minutes)
   * Monitor: web error rate, console-api 5xx, auth failures, UI performance metrics.
   * Confirm customer support has no spike in access/login tickets.

7. Closeout
   * Update the change record with rollout timestamps, build IDs, and dashboard links.

h1. Rollback
* console-web: revert to prior bundle and re-run cache invalidation.
* console-api: redeploy prior image digest.
* Feature flags: disable the newly launched flag(s) first if they are implicated.
* Follow the Rollback and Post-change Validation runbook for confirmation steps and monitoring.
