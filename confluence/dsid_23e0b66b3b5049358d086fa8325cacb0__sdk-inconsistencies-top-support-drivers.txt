SDK inconsistencies: top support drivers (auth, retries, timeouts, streaming)

h1. Summary
This page summarizes the most common support drivers attributable to cross-language SDK inconsistencies (Python/TypeScript/Go). The goal is to (1) reduce recurring tickets caused by mismatched defaults/behavior, (2) improve time-to-triage by standardizing surfaced fields (request_id, retry_count, timeout_ms, streaming_disconnect_reason), and (3) ensure customers get consistent, safe guidance regardless of language.

This page is used by Support + DevEx to prioritize fixes and to validate that the SDK Parity initiative (ENG-5120) addresses real customer pain.

h2. Scope
* In scope:* Hosted API usage via Redwood SDKs (Python/TS/Go) for chat/text generation and streaming.
* Out of scope:* Customer app logic bugs, model-specific output complaints, and general network instability not exacerbated by SDK behavior.

h2. Executive takeaways
# The highest-volume issues are *retry/429 handling*, *timeout semantics*, and *streaming disconnect behavior*.
# The largest “severity” escalations tend to come from:
## retries on non-retryable requests (duplicate side effects / billing concern)
## streaming disconnects behind proxies with unclear guidance
## missing request_id in SDK-thrown errors (blocks platform-side log correlation)
# Most issues are mitigated by standardizing defaults + typed errors + consistent docs/snippets. Some require gateway consistency (Retry-After, request_id propagation).

h1. Ticket references (support-facing)
Below are the highest-signal tickets and what we learned.

h2. 1) SUP-29410 — Python SDK: timeouts not honored in streaming
* Symptoms:* Customer configured timeouts but streaming read appeared to hang; application thread pool exhausted over time.
* Repro pattern:* Long-lived streaming connection with intermittent proxy buffering; timeout applied to initial request but not subsequent read loop.
* What Support needed but didn’t have:* request_id consistently attached to the thrown exception.
* Fix path:* Align timeout model and ensure streaming iterator honors overall timeout/cancellation; surface typed StreamingDisconnectError with request_id.
* Tracking:* ENG-5123 (Python timeout), ENG-5125 (streaming reliability), ADR: sdk-timeout-model.

h2. 2) SUP-29438 — TS SDK retried on 400 (duplicate billing concern)
* Symptoms:* Customer observed retries on a 400-class error and reported possible duplicate charges.
* Root cause:* Retry middleware classification too permissive (treated some fetch errors / response parsing errors as retryable without status guard).
* Mitigation:* Restrict retries to explicit retryable codes and network errors; ensure idempotency guidance for user-initiated retries.
* Tracking:* ENG-5126 (error taxonomy) + TS retry middleware refactor; add conformance test for “no retry on 400”.

h2. 3) SUP-29477 — Go SDK missing Retry-After handling
* Symptoms:* Under sustained 429s, Go SDK retried too quickly and amplified throttling; customer saw rate limiting “never recovers.”
* Root cause:* Header parsing not implemented; backoff algorithm didn’t include server-directed cooldown.
* Mitigation:* Parse Retry-After (int seconds + RFC 7231 date), clamp to max delay; exponential backoff with jitter.
* Tracking:* Go retry PR + gateway consistency work (emit Retry-After reliably).

h2. 4) SUP-29505 — Streaming disconnects behind proxy; retry guidance needed
* Symptoms:* Enterprise proxy closes connections mid-stream; customer receives truncated content and inconsistent errors between TS and Python.
* Root cause:* Inconsistent streaming event model; disconnect surfaced as generic network error with no standardized fields.
* Mitigation:* Standardize disconnect error type and fields: request_id, bytes_read/tokens_received (when available), disconnect_reason, retry_recommended flag.
* Tracking:* ENG-5125 (Go streaming), cross-language streaming guide update, examples w/ safe retry patterns.

h2. 5) INT-1182 — request_id not visible in SDK errors
* Symptoms:* Support repeatedly asked for HTTP traces because request_id wasn’t attached to SDK-thrown exceptions.
* Impact:* Increases TTR; raises customer frustration; leads to escalations.
* Mitigation:* Always propagate request_id from headers for both non-streaming and streaming errors; include in typed error objects and message.
* Tracking:* ENG-5126 + platform request_id propagation standardization.

h1. Root cause themes
h2. A) Differences in defaults become “bugs” at scale
Even when behavior is technically configurable, customers overwhelmingly rely on defaults. Divergent defaults across SDKs lead to:
* “works in TS but not Python” incidents
* hidden load amplification (retry storms)
* subtle hangs (streaming read loops without an overall timeout)

h2. B) Lack of typed, structured errors increases support burden
Common missing fields in current escalations:
* request_id
* status_code (or undefined for network errors)
* retryable (boolean)
* retry_after_ms (parsed and surfaced)
* retry_count / attempts
* timeout_ms (effective)
* streaming_disconnect_reason

h2. C) Streaming is the hardest parity surface
Streaming issues often include partial outputs, cancellation, and proxy behavior. The standard must be conservative about retries to avoid duplication.

h1. Proposed mitigations (what Support should expect to change)
This section is intentionally phrased in support/customer terms so we can update macros and troubleshooting steps.

h2. Standardized behavior that should reduce tickets
* 429 handling:
** All SDKs respect Retry-After and use exponential backoff with jitter.
** Default max attempts are capped and visible via config.
* Timeouts:
** A single documented timeout model exists across languages.
** Streaming honors cancellation/overall timeouts (no “hang forever” read loops).
* Error objects:
** request_id is present on all server responses and attached to all SDK errors.
** retryable flag is consistent.
* Streaming:
** Partial output semantics are consistent.
** Errors identify disconnects vs user cancellation.

h2. Support macro updates (preview)
When requesting information from customers, ask for:
# SDK language + version
# request_id (from error object; customers should not need HTTP traces)
# Whether streaming was enabled
# Retry + timeout config (effective values, not just code)
# Environment (corporate proxy/VPN; region)

Tracking: ENG-5132 “Support playbook: SDK retry/timeout”.

h1. Validation plan (Support + DevEx)
We will consider these drivers improved when:
* Conformance tests cover the behavior (retries/timeouts/errors/streaming) and are gated in CI for each SDK.
* Support macros link to a single canonical doc page for retry/timeout tuning.
* We see a measurable decrease in:
** tickets mentioning 429 retry loops or missing Retry-After
** tickets mentioning “timeout ignored” for streaming
** tickets requiring HTTP trace capture due to missing request_id
