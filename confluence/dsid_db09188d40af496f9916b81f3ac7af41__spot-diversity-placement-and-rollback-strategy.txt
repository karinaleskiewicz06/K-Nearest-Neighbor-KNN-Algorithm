Cross-region spot diversity, placement, and rollback strategy

Summary

This page defines Redwood's recommended approach for running a cost-optimized, resilient GPU fleet using a mix of spot/preemptible and reserved instances across multiple regions and instance types. It describes placement strategies, Terraform/IaC patterns, CI/CD considerations for node image promotion, expected SLO impacts, monitoring metrics, and an explicit rollback/runbook for spot preemption storms. Use this as the canonical guidance for teams provisioning GPU capacity for inference, training experiments, and batch workloads.

Goals and constraints

- Primary goals: 
  - Maintain production throughput SLOs (median token latency per request, and per-model QPS) while minimizing unit GPU cost.
  - Keep unplanned user-visible degradation below the reliability error budget (see SLOs section).
  - Provide deterministic rollback and failover steps when spot markets cause capacity loss.
- Constraints:
  - Some workloads (inference tail-latency-critical) must never run on preemptible instances; training and batch workloads can tolerate preemption.
  - Network egress/regional compliance restrictions may limit placement to specific regions for certain customers (see Private deployments).

Service-level objectives (SLOs) and thresholds

- Availability SLO for inference control-plane: 99.95% monthly.
- P99 generation latency SLO (hosted tier): < 550ms.
- Queue depth (pending model requests) must be < 75 requests per node-class during steady-state.
- Preemption rate alert thresholds:
  - info: 0.5% 1h rolling
  - warning: 2% 30m rolling
  - critical: 5% 15m rolling -> triggers runbook below

Placement strategy overview

1) Region diversity by workload class
   - Reserved/Guaranteed: Provision minimal reserved pools in 1 primary region per customer/tenant (for Dedicated). All latency-sensitive inference replicas must be pinned to reserved pools.
   - Spot/Preemptible pools: Maintain spot pools in at least 3 regions (primary, secondary, tertiary) with varied instance types to avoid correlated pre-emption.
   - Edge/nearby regions: For regional customers with residency constraints, run spot fallback only within allowed regions.

2) Instance type diversity
   - For each spot pool, configure 2–3 GPU instance families (e.g., A100-80GB, A10G, H100 where supported) prioritized by cost-performance profiles.
   - Use the autoscaler to prefer lower-cost types but allow substitutions up to +15% latency degradation (configurable per model).

3) Fractional capacity split (example)
   - Reserved/Guaranteed: 40% of steady-state capacity for production inference.
   - Spot: 50% (spread across regions/types).
   - Burst/on-demand: 10% for immediate scale-up while provisioning on-demand replacements.

Terraform / IaC patterns

- Use the gpu-spot-pool module pattern: a single module that exposes:
  - regions: list(string)
  - instance_families: list(string)
  - desired_capacity: number (per-region desired)
  - min_capacity, max_capacity
  - preemption_policy: {drain_timeout_seconds, fallback_priority} (string or map)

Example module invocation (pseudo-Terraform HCL inside YAML for readability):

module "gpu_spot_pool_us_east" {
  source = "git::ssh://git.redwood/internal/infra-modules.git//gpu-spot-pool"
  regions = ["us-east-1", "us-east-2"]
  instance_families = ["a100-80gb","a10g","h100"]
  desired_capacity = 120
  min_capacity = 30
  max_capacity = 300
  preemption_policy = {drain_timeout_seconds = 45, fallback_priority = "region_first"}
}

Module implementation notes:
- Keep each module idempotent and safe to run in CI pipelines.
- Use remote state keyed by region and environment.
- Tag instances with: service=gpu-inference, team=${var.team}, pool_type=spot, stack=${var.env}
- Don't hardcode quotas; surface quotas in outputs for quota checks in CI (see CI checks).

CI/CD and node image promotion

- Image pipeline: build -> unit tests -> GPU smoke tests -> canary bake -> promote to regional channels.
- Promotion channels: staging -> canary -> production. Each channel corresponds to a Terraform workspace and image channel tag.
- Canary policy: deploy new node-images to 2% of spot instances in secondary region and run the perf/compat test-suite for 2 hours before wider rollout.
- Blockers: kernel mismatches, CUDA/cuDNN version regressions, driver OOMs. If any are detected, block promotion and auto-open an incident.

Autoscaling and draining behavior

- Continuous batching and GPU-sharing require graceful node drains: set kubectl drain timeout to 90s and grace period to 120s on inference pods that support checkpointable KV caches.
- Drain policy for spot preemption: drain -> re-route traffic -> wait (drain_timeout) -> terminate. For non-drainable workloads (some training jobs), enable checkpointing or migrate to reserved nodes.

Monitoring, dashboards, and alerting

Key metrics (per region/pool/type):
- GPU utilization (avg, p95), GPU memory utilization, host CPU steal/time, node preemption_count, node_boot_time, pod_eviction_count, queue_depth, pending_pods

Suggested dashboard panels:
- Pool health: desired vs available nodes, preemption rate heatmap across regions
- Latency impact: P50/P95 gen latency versus pool capacity
- Cost panel: $/GPU-hour by region and instance family

Alerting rules (examples):
- preemption_rate >= 5% over 15m -> PagerDuty SEV2 -> trigger runbook A (preemption storm)
- available_capacity < 60% of desired for > 10m -> PagerDuty on-call -> trigger scale-up to on-demand and start capacity-rebalance (see runbook)

Runbook A: Spot preemption storm (critical)

1) PagerDuty alert fires with tag : preemption-storm. On-call acknowledges within 5 minutes.
2) Triage (10 min): check preemption_rate by region, identify primary impacted pools using the spot preemption heatmap dashboard.
3) Immediate mitigations (automated where possible):
   - Increase fallback priority to prefer lower-cost on-demand types in secondary region.
   - Trigger terraform apply for on-demand fallback pools (pre-created IaC but scaled to 0) using the image channel currently marked 'production'.
   - Reduce scheduling of non-critical batch training: mark training queue to paused (CI/CD job label: resource:noncritical).
4) If latency SLOs are breached (p99 > SLO):
   - Move traffic to reserved pools and regional replicas via smart routing (console route override).
   - If reserved pools are insufficient, escalate to SEV1 and activate emergency capacity purchase (finance-approved commit).
5) Recovery: once preemption rate < 1% for 30m and queue depth back to < 50 per node-class, begin rebalancing spot pools back to target and restore batch schedules.
6) Post-incident: open a postmortem and update the tokenized cost registry with the additional on-demand spend.

Rollback playbook: image-related instability during wide spot rollout

- Trigger: canary-to-prod rollout causes driver OOMs on 3% of new nodes within 90 minutes.
- Steps:
  1) Promote previous stable image into the production image channel (CI rollback job).
  2) Terraform apply to update node pool launch template to stable image (use rolling_update_strategy: 5% parallel).
  3) Monitor: verify GPU smoke tests pass on new nodes, check p99 latency and pod restart counts.
  4) If errors persist, revert configuration changes and schedule an emergency freeze on image promotions.

Ownership and run cadence

- Ownership: infra capacity team (eng-infra/gpu-fleet) owns modules, dashboards, and runbooks. Service owners own model-level fallback settings.
- Weekly cadence: 30-minute architecture sync to review spot availability changes and cost targets. Monthly: revisit capacity split and reserved commitments against usage trends.

Operational checklist for new pool creation

1) Submit IaC change with module invocation and required tags.
2) Run terraform plan in CI and wait for quota-checks to pass.
3) Create image channel and run canary bake for 2 hours.
4) Scale pool to min_capacity and validate node registration and smoke tests.
5) Set alerts and dashboards for new pool (use templated dashboard JSON).
6) Announce in #infra-gpu with runbook link and owner.
