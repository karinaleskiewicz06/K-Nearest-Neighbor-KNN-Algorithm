Status Page and Incident Comms: Guidance for Rollout-Related Issues

h1. Purpose
This page explains when a rollout issue should be communicated via the status page and how to coordinate communications during a rollback or prolonged fallback.

h1. Definitions
* Rollout issue: any degradation caused by a planned model version change, routing change, or runtime configuration update.
* Incident: a customer-impacting event that meets the incident declaration criteria.

h1. When to post a status page update
Post a status page update if any of the following occur:
* Any widespread Hosted API impact lasting > 15 minutes (elevated 5xx, timeouts, or severe latency)
* Any Dedicated customer experiences SLA-impacting degradation and requests formal comms
* Any Private customer experiences impact outside the approved change window
* A rollback is initiated after > 25% traffic ramp OR after any customer notification has been sent

h1. Required content of a rollout-related status update
Include:
* What users are experiencing (symptoms)
* Impacted surfaces (Hosted/Dedicated/Private, regions, request types)
* Current mitigation (automatic fallback active, manual rollback in progress, traffic capped)
* Next update time (commit to a timestamp)
* Where customers can get support

h1. Coordination model
* Incident Commander (IC): owns the status page message content and cadence.
* Customer Success: owns account-specific communications for Dedicated/Private.
* Engineering owner: provides technical updates and ETA for rollback.

h1. Rollback comms
If rollback is initiated:
1. Notify #incidents and #support with a short summary and mitigation step.
2. Update the rollout plan with the rollback trigger and time.
3. If the status page is used, explicitly state that we reverted to the prior model version (avoid internal ids unless customers pin versions).

h1. After-action requirements
If a rollout issue required status page comms, the associated postmortem MUST link to:
* the rollout plan
* router policy ids (old/new)
* the thresholds that triggered rollback
* customer communications artifacts (tickets/emails)
