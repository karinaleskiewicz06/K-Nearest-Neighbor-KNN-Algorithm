Break-glass and emergency access (production)

# Overview
This policy governs **break-glass access** to production systems for emergencies, including emergency secret rotation. Break-glass is intended for rare events and must be auditable.

# When break-glass is permitted
Break-glass may be used only when:
- there is an active customer-impacting incident, or
- there is a credible suspicion of credential compromise requiring immediate containment, or
- an operational safety issue requires urgent mitigation and normal approvals are too slow

# What break-glass grants
Break-glass grants time-limited access to:
- Tier 0 / Tier 1 secret read and rotate capabilities
- production configuration changes required to restore service
- restricted logs needed for incident diagnosis

# Controls
- Access is time-bound to **60 minutes** (extensions require explicit SRE + Security approval).
- All actions must be logged (audit trails cannot be disabled).
- Any secret retrieved via break-glass must be treated as compromised and rotated if exposure scope is uncertain.

# Required steps
1. Open or link an incident record.
2. Announce in the incident channel that break-glass is being used (who, why, and what systems).
3. Acquire break-glass role via the approved workflow.
4. Execute the minimum set of actions necessary.
5. Revoke break-glass role immediately after use.
6. Post-incident: file a summary of actions taken, including which secrets were rotated and which services were touched.

# Prohibited
- Using break-glass for routine maintenance
- Sharing break-glass credentials or session tokens
- Exporting sensitive logs outside approved storage

# Post-usage review
Security reviews all break-glass events weekly. Any noncompliance triggers corrective actions and may result in access changes.
