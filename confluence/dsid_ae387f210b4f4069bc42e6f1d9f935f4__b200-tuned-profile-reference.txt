B200 tuned profile reference (experimental)

## Purpose
This page documents the **B200 tuned hardware profile** shipped as part of the Hardware Tuning Profiles Pack. It is intended for Runtime, Infra, SRE, and operators (Dedicated/Private) who need to understand:
- Current **maturity level** and rollout constraints
- **Required CUDA/driver/NCCL assumptions**
- **Kernel-selection differences vs H100** (what’s pinned vs adaptive)
- A clear, operator-friendly **fallback / rollback plan**

This document describes *expected behavior* and safe operating envelopes. It is not a customer-facing guarantee.

---

## Maturity level (read first)
**Status:** Experimental, gated.

**Why experimental:** B200 fleet access is still partial and heterogeneous (provider SKU strings, clocks, topology). The profile is tuned against the current benchmark workload matrix, but we have limited long-run production hours and fewer “weird” prompt distributions than H100.

**Default behavior:**
- **Hosted / Dedicated:** B200 profile is **NOT enabled by default**. Enable only in explicitly approved pools.
- **Private:** Shipped in the pack, but **requires explicit enablement** (Helm value or config override). If B200 detection is ambiguous, runtime falls back to the default “generic” profile (or H100-compatible baseline).

**Gating mechanism:**
- Runtime feature flag: `runtime.profiles.experimental_b200_enabled` (default: `false`)
- Profile ID: `gpu-nvidia-b200/v0` (see “Profile identifiers & compatibility” below)

**Known rollout posture:**
- Start with a single region/pool per provider.
- Canary for 2–5% traffic (or per-node canary in Dedicated).
- Promote only after perf-canary and production SLOs are stable for a full business day.

---

## Supported environments
### Deployment modes
- Hosted: supported **only** in explicitly allowlisted pools.
- Dedicated: supported with staged rollout per customer pool.
- Private (VPC / on-prem): supported; operators must satisfy the software stack requirements below.

### Hardware assumptions
- NVIDIA Blackwell B200 GPUs.
- Multi-GPU nodes are supported; however, see “Collectives & topology notes” for when we apply NCCL settings.
- MIG: **unsupported** for B200 profile at this time. If MIG is detected, runtime **must not** select `gpu-nvidia-b200/v0`.

---

## Required software stack assumptions
> The profile loader enforces minimum versions. If requirements aren’t met, the runtime will refuse to activate the B200 profile and will fall back.

### Minimum versions (current)
| Component | Minimum | Notes |
|---|---:|---|
| Redwood Runtime | `runtime-1.18.0` | First release with B200 experimental gating + compatibility checks. |
| NVIDIA Driver | `>= 570.xx` | Must support Blackwell features used by kernel set. |
| CUDA | `>= 12.6` | Required for the current kernel/autotune set. |
| NCCL | `>= 2.23` | Only relevant for tensor-parallel / multi-GPU serving configs. |
| Linux | `>= 5.15` | Required for observed stability under high IO + CPU pinning. |

### Hard failure / soft failure behavior
- **Hard fail (profile not activated):** driver/CUDA too old, MIG detected, unknown GPU name that cannot be normalized to B200, or runtime version mismatch.
- **Soft fail (profile activated with reduced scope):** topology unknown → we avoid applying any NCCL/topology-specific overrides; kernel selection remains active.

## Profile identifiers & compatibility
### Profile ID
- `gpu-nvidia-b200/v0` (experimental)

### Compatibility contract
- Compatible with runtime minor releases `1.18.x` and `1.19.x` unless explicitly revoked.
- Runtime logs a compatibility matrix at startup and emits metrics for the selected profile and override source.

### Profile selection order (summary)
Selection is controlled by the override-order ADR. Operationally:
1) Explicit per-process override (env var / CLI)
2) Deployment-level config (Helm values / runtime config file)
3) Fleet/pool default (Hosted/Dedicated)
4) Hardware auto-detection default
5) Safe fallback profile

## What this profile is optimizing for
### Primary goals
- Better end-to-end throughput (tokens/sec) for mixed workloads with **moderate concurrency**.
- Stable p95 latency for typical streaming chat distributions (not worst-case long-context stress).
- Reduced kernel mismatch risk by constraining B200 to a known-good kernel set.

### Workload envelope (where we expect it to help)
- Sequence length buckets: 1–2k prompt tokens, 256–1k generated tokens (streaming and non-streaming).
- Concurrency: medium-high (continuous batching on), but not queue-saturated.
- Model families: Llama-3.x-class decoder-only; Qwen2.5-class; similar attention patterns.

### Where we do NOT expect improvements (or may regress)
- Extremely long-context prompts (8k–32k) with low concurrency: tail latency can regress if we over-prioritize throughput.
- Tool-calling with bursty stop/start generation patterns: can increase scheduler churn.
- Unusual tokenization patterns with high variance in decode lengths: can destabilize fairness knobs.

## Kernel-selection behavior (B200 vs H100)
B200 differs from H100 in two important ways:
1) **Kernel set**: B200 uses a different set of best-performing attention kernels and preferred data types.
2) **Heuristic thresholds**: sequence-length bucket boundaries and “switch points” differ.

### Key differences vs H100
- **Attention kernel preference:**
  - H100 profile leans on stable FlashAttention variants tuned for Hopper.
  - B200 profile enables Blackwell-optimized attention kernels (where available) and is more conservative about fallback paths.

- **Datatype / quantization posture:**
  - H100: common wins with FP16/BF16 + selective FP8 paths.
  - B200: profile prefers FP8 execution paths when the model + runtime have validated calibration metadata; otherwise stays BF16.
  - Applied ML note: FP8 enablement is gated by model metadata and is not forced by the hardware profile alone.

- **Sequence length buckets:**
  - H100: tuned buckets emphasize 0.5k/1k/2k/4k transitions.
  - B200: buckets shift to reduce oscillation around mid-length prompts (observed “thrash” in early canaries). The B200 profile pins bucket boundaries and reduces runtime adaptation frequency.

- **Prefill vs decode split:**
  - B200 profile biases toward prefill efficiency when concurrency is high, but caps decode starvation via stricter fairness limits (see Scheduler section).

### Practical operator implications
- If you compare B200 vs H100 and see lower microbench wins but better end-to-end throughput, that’s expected: B200’s heuristics are tuned to stabilize production batching rather than maximize isolated kernel throughput.

## Scheduler & batching knobs (B200 preset)
> Exact key names may differ slightly by runtime minor version; rely on `dump-effective-config` (see “Debugging & observability”).

### Preset intent
**Mode:** `balanced` (single preset for now; throughput-first is not approved on B200).

### Summary of notable defaults
- Continuous batching: enabled
- Queue backpressure: enabled with conservative caps to protect p95
- Prefill/decode fairness: stricter than H100 throughput-first; tuned to prevent p95 regressions we saw in early canaries
- Streaming: conservative flush cadence to avoid long buffering under backpressure

### Guardrails
- Maximum effective batch size is capped based on observed KV cache pressure.
- If runtime detects high reject/retry rate, it auto-reduces batching aggressiveness (adaptive safety layer remains on; the profile does not disable it).

---

## Memory & KV-cache behavior
B200 has ample bandwidth, but production regressions have come from **KV-cache fragmentation** and **overcommit under long-context mixes**.

### B200 defaults (high level)
- KV cache budgeting is **enabled** and uses a conservative safety margin.
- Long-context workloads (8k+) are allowed, but we do not expect “best possible” throughput; we prioritize avoiding OOM/restarts.

### Known risk pattern
If your workload has:
- long prompts (>= 8k),
- high concurrency,
- and high variance in decode length,

…you may hit sudden memory pressure spikes. Use the fallback plan or force the generic profile until workload-specific tuning is validated.

---

## Collectives & topology notes (multi-GPU)
The B200 profile only applies NCCL/topology overrides when:
- The node is in a known topology class (e.g., NVLink-connected group), AND
- tensor-parallel serving is enabled.

If topology is unknown or mixed, the profile **does not** apply NCCL overrides (safe default).

## Expected performance deltas (guidance)
Performance varies by model and prompt distribution. Use the workload matrix report for validated numbers.

**Directional expectation (when in envelope):**
- Throughput: +5–15% vs generic baseline on B200-enabled pools
- p50 latency: flat to slightly improved
- p95 latency: should remain within guardrail thresholds; if p95 regresses >10% sustained, treat as rollback-worthy

If you observe significant p95 regressions without throughput gains, do not “tune around it” in production—rollback and escalate (see contacts).

## Observability & debugging
### Required metrics (must be present before any rollout)
- `runtime_profile_selected{profile_id=...}` (gauge)
- `runtime_profile_override_source{source=...}` (gauge)
- Key latency percentiles segmented by profile_id (p50/p95)
- Tokens/sec (prefill and decode) segmented by profile_id
- OOM / restart counters segmented by profile_id
- Retry/reject counters (queue full, backpressure)

### Debug tools
- Runtime endpoint: `/debug/runtime/profile` (returns selected profile, compatibility status, and a redacted view of key knobs)
- CLI: `redwood-runtime dump-effective-config --redact-secrets` (capture output in incidents)

### What to capture for incident triage
1) Selected profile + override source
2) Runtime version, driver version, CUDA version (from startup logs)
3) GPU name string(s) as reported by NVML (to catch normalization bugs)
4) Last 30–60 minutes of p95 and tokens/sec by route/model
5) Any signs of queue saturation (queue depth, reject reasons)

## Fallback / rollback plan (explicit)
### When to rollback (recommended thresholds)
Rollback is recommended if **any** of the following are true after enabling the B200 profile:
- p95 latency regression **> 10%** sustained for **15 minutes** on canary traffic (same workload slice), OR
- Error rate (5xx / timeouts) increases **> 0.3% absolute**, OR
- OOM / restart events occur at a rate above baseline (any clear step-function increase), OR
- Perf-canary gate fails for two consecutive runs and the failure is not attributable to runner noise.

### Rollback options (in order of fastest)
1) **Disable experimental flag** (preferred)
   - Set `runtime.profiles.experimental_b200_enabled=false`
   - Expected effect: runtime will stop selecting `gpu-nvidia-b200/v0` and fall back.

2) **Force fallback profile explicitly**
   - Set `RUNTIME_HARDWARE_PROFILE_ID=gpu-generic/v1` (or the fleet-approved baseline profile)
   - Use when detection/selection logic is suspected.

3) **Pool-level disable (Hosted/Dedicated)**
   - Remove B200 profile from pool defaults (fleet config)
   - Drain and restart canary nodes first, then the pool.

4) **Region/pool hotfix disable**
   - If only one pool is affected, disable there and leave other canaries running.
   - Use to minimize blast radius and preserve signal.

### Hosted specifics
- Disable at the pool default first; do not rely on per-process overrides unless coordinated with Infra.
- Ensure dashboards are segmented by pool and profile_id.

### Dedicated specifics
- Disable per customer pool using the pool override mechanism.
- If a single customer reports regressions, disable for that pool first; do not disable global canaries unless signal indicates a systemic issue.

### Private specifics (Helm)
Recommended operator actions:
- Set Helm value `hardwareProfiles.experimentalB200Enabled: false` (name may differ by chart version; see chart docs).
- Or set `hardwareProfiles.forceProfileId: gpu-generic/v1`.
- Redeploy and confirm selection via `/debug/runtime/profile`.

### Post-rollback steps
- File a regression issue with:
  - before/after graphs,
  - effective config dump,
  - GPU string/topology info,
  - workload description (sequence distribution + concurrency).
- If rollback was triggered by tail latency, attach the per-route p95 and streaming stability plots.

---

## Operational notes and cautions
- Do not “mix and match” B200 kernel toggles with H100 scheduler presets. If you need a one-off config, work with Runtime Scheduling + SRE and document it as a temporary override with an expiry.
- If GPU detection is ambiguous (provider SKU string variants), treat it as a bug. Do not patch around it with permanent per-node overrides.
- This profile is intentionally conservative: we prefer stable p95 and predictable operations over maximizing peak throughput.
