GPU checkpointing and ephemeral session operations

Overview

This doc describes the operational pattern we use at Redwood for managing ephemeral GPU-backed inference/eval sessions that require periodic checkpointing. It covers architecture patterns, recommended Terraform/IaC primitives, CI/CD integration, an on-call runbook for session failures, cost-reclamation practices, and a lightweight migration checklist for existing pools. The audience is infra engineers, SREs, and platform owners responsible for GPU fleet lifecycle and tenant isolation.

Goals

- Ensure long-running ephemeral sessions (e.g., stateful eval runs, human-in-the-loop debugging, and customer debug sessions) survive transient preemptions and node drains.
- Minimize per-tenant cost leakage from stranded GPU-backed state.
- Provide repeatable IaC + CI/CD patterns for checkpointing and session recovery.
- Give oncall runbook steps that allow rapid recovery and safe reclamation without data loss.

Scope

Included: Inference/eval jobs that run on dedicated or shared GPU pools, our ephemeral sandbox pools, and the orchestration pieces that interact with tenant storage (S3/GCS) or block snapshots.
Excluded: Model training jobs larger than 24 hours (see training runbook).

Terminology

- Session: a single ephemeral process bound to a GPU instance (Pod, VM, or container).
- Checkpoint: periodic serialization of session state to durable storage (S3/GCS).
- Grace window: configured time to attempt graceful save-and-exit before forced termination (default 90s).
- Reclamation: automated process to detect abandoned sessions and free associated GPU resources.

Ownership

- Primary owner: infra/gpu-fleet team
- SRE oncall: infra/sre rotation
- Product escalation: platform-solutions team for tenant-impacting incidents

SLOs and Alerts

| Metric | SLO | Alert threshold | Pager? | Owner |
|---|---:|---:|---:|---|
| Successful checkpoint within grace window | 99.5% | >0.5% failures per 1h | Yes | infra/gpu-fleet |
| Session reclamation latency (detected -> reclaimed) | 10m P90 | P90 > 15m | Yes | infra/sre |
| Orphaned-GPU hours (per day) | < 5 GPU-hrs/day | > 10 GPU-hrs/day | Yes | infra/finops |

Instrument these metrics with the checkpoint-controller and GPU-allocator exporters (see Monitoring section).

Architecture patterns and rationale

1) Lightweight periodic checkpointing (recommended default)
- Sessions write snapshots to tenant object storage every N minutes (configurable per workload).
- Checkpoints must be idempotent and versioned (timestamp + session-id).
- Agent pattern: embed a small checkpoint agent in the session container that handles upload, retry/backoff, and health reporting.

2) Fast preemption handler (kernel-level/agent)
- Hook into the node preemption/drain lifecycle: systemd/daemon or SIGTERM handler must trigger a final checkpoint synchronously during the grace window.
- If the final checkpoint cannot complete within grace window, persist a compact resume token and let reclamation resume state.

3) Externalized session registry and lease model
- A central registry service (lightweight key-value table in our control plane DB) stores session metadata: session-id, owner, last-checkpoint, checkpoint-uri, node, lease-expiry.
- A short-lived lease (default 5m) is renewed by the running agent to signal liveness. Lease expiry triggers reclamation logic.

4) Reclamation worker (stateless, horizontally scalable)
- Periodically scans the registry for expired leases.
- Attempts to reconcile state: if checkpoint exists and is recent enough, mark session reclaimable and free GPU; otherwise attempt forced final checkpoint via remote agent (if node reachable) or run a resume-worker to reconstruct minimal state and persist a recovery checkpoint before reclaiming.

Recommended Terraform / IaC primitives

- Use a resource module pattern: gpu-session-controller (K8s deployment + ConfigMap), checkpoint-agent image, and a tenant-policy CRD.
- Example snippet (Terraform using k8s provider):

```hcl
module "gpu_session_controller" {
  source = "git::ssh://git@github.com/redwood-inference/infra-modules.git//gpu-session-controller?ref=main"

  namespace = "gpu-sessions"
  replica_count = 3
  image = "ghcr.io/redwood/gpu-checkpoint-agent:v1.4.0"
  s3_bucket = var.session_checkpoint_bucket
  grace_window = 90
}

resource "kubernetes_config_map" "checkpoint_policy" {
  metadata {
    name = "checkpoint-policy"
    namespace = module.gpu_session_controller.namespace
  }
  data = {
    default_interval_minutes = "5"
    max_checkpoint_size_mb = "1024"
  }
}
```

- IaC validations: unit test the module with terratest to ensure RBAC rules do not grant broad permissions to tenant service accounts and that the S3/GCS bucket has proper encryption and lifecycle rules.

CI/CD integration and image promotion

- Build pipeline (Buildkite/GitHub Actions) steps:
  1. Build agent image and run unit tests.
  2. Run image-size and vulnerability scan stage.
  3. Deploy to staging cluster with canary replicas and run an e2e that simulates preemption and checkpoints.
  4. On success, promote image to production tag and trigger Terraform apply via a gated pipeline job.

- Gate rules: requires two approvers from infra/gpu-fleet or infra/security for production promotion.

Runbook — immediate remediation (oncall)

Priority: Pager when checkpoint failure rate > 0.5%/1h or orphaned-GPU-hours alert fires.

1) Triage: Identify scope
- Query session registry: `SELECT * FROM session_registry WHERE last_checkpoint < now() - interval '10 minutes'`
- Look up affected nodes: `kubectl get pods -o wide -n gpu-sessions --selector=app=gpu-session | grep <session-id>`

2) If node alive and reachable
- Exec into pod and trigger a manual checkpoint: `kubectl exec -n gpu-sessions <pod> -- /usr/local/bin/checkpointctl save --sync`
- Check agent logs: `kubectl logs -n gpu-sessions <pod> -c checkpoint-agent --since=1h`

3) If node not reachable or pod terminated
- Launch a resume-worker on same pool: `kubectl run resume-<session-id> --image=ghcr.io/redwood/gpu-resume:v1 -- /resume --session-id <session-id>`
- Resume-worker will attempt to reconstruct minimal state from artifacts in ephemeral node storage and produce a recovery checkpoint.

4) Force reclamation (if no recovery possible after 30m)
- Add session to reclamation queue: POST /internal/reclaimer/sessions {session_id: <id>, reason: "unrecoverable"}
- Increase eviction safety tags so cluster autoscaler can free the node without hanging other tenants.

5) Post-incident actions
- Create a JIRA and tag infra/sre + infra/gpu-fleet. Add postmortem template link.

Troubleshooting playbook (common failure modes)

- Checkpoint upload throttled: Inspect network egress QPS; confirm bucket policy and per-tenant rate limits. Temporary mitigation: lower checkpoint frequency, enable compact checkpoints.
- Agent OOM: Increase agent memory in ConfigMap, promote smaller checkpoint chunking.
- Reclaimer flooding: Reclaimer should backoff; if not, scale down worker counts and investigate cause (registry storm, clock skew).

Cost reclamation and finops integration

- Reclamation window: default tenant grace + retention = 48 hours. After 48 hours without checkpoints or lease renewal, mark as abandoned and move to cost-reclamation billing state.
- Reclamation reporting: daily report exported to BigQuery with columns: date, tenant_id, reclaimed_gpu_hours, checkpoint_count, reclaim_reason. This feeds finops alerts and chargebacks.

Testing and observability

- E2E tests include:
  - preemption simulation test that kills node with SIGTERM and asserts a final checkpoint was saved and uploaded.
  - lease-expiry test that ensures reclaimer reclaims within 10m P90.

- Dashboards (Grafana):
  - Checkpoint success rate by tenant (1m, 5m windows)
  - Reclaimer queue length and processing latency
  - Orphaned GPU hours (daily)

- Logs: structured JSON from checkpoint-agent (fields: session_id, step, duration_ms, bytes_uploaded, result).

Migration plan for existing pools

1) Add checkpoint-agent as sidecar to existing session pod spec with a compatibility feature flag.
2) Deploy controller in canary mode to 10% of namespaces and monitor checkpoint success.
3) Ramp to 50% then 100% after 72h stable.

Audit and compliance considerations

- Encryption: do not allow plaintext checkpoints. Enforce SSE-KMS for S3 buckets.
- Retention: default 30-day checkpoint retention; tenants can request longer retention if justified.
- RBAC: checkpoint-agent service account must only be able to put objects to the tenant-prefix in the shared bucket.

Appendix — useful commands and snippets

- Check registry for stale leases
  `curl -sS -H "Authorization: Bearer $TOKEN" https://control-plane.internal/api/v1/sessions?state=leased&last_checkpoint_lt=$(date -u -d "10 minutes ago" +%Y-%m-%dT%H:%M:%SZ)`

- Resume-worker invocation example
  `kubectl run --rm --restart=Never resume-abc123 -n gpu-sessions --image=ghcr.io/redwood/gpu-resume:v1 -- /resume --session-id=abc123 --write-checkpoint s3://session-checkpoints/tenant-42/abc123.ckpt`

- Example S3 lifecycle policy (JSON) to expire unreferenced checkpoints after 30 days:

```json
{
  "Rules": [
    {
      "ID": "expire-unused-checkpoints",
      "Prefix": "session-checkpoints/",
      "Status": "Enabled",
      "Expiration": {"Days": 30}
    }
  ]
}
```
