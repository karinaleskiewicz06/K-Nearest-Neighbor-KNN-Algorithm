GPU environment churn management and IaC strategy

Overview

This document defines recommended patterns, Terraform/IaC primitives, CI/CD controls, and operational runbooks for managing high-churn GPU environments used for short-lived workloads (experiments, evals, CI jobs, ephemeral dev sandboxes). The goal is to limit cost leakage, maintain predictable capacity for production tenants, and provide safe automated lifecycle operations that are auditable and reversible.

Scope

- Applies to all GPU pools that allow automated provisioning or destruction at runtime, including: ephemeral CI pools, eval clusters, developer sandboxes, and short-lived tenant environments.
- Does NOT replace long-lived Dedicated GPU reservations for production traffic; interactions with Dedicated are covered in a separate policy.

Motivation

High churn on GPU environments creates three recurring problems: unexpectedly high spend, fragmented topology leading to reduced packing efficiency, and cascading preemption events that impact production SLOs. This doc prescribes explicit IaC patterns and operational controls to mitigate those risks while preserving developer velocity.

Key principles

1. Declarative minimums: Environments should be provisioned using small, composable Terraform modules that expose a minimal surface area (size, ttl, labels, owner).
2. Short-lived by default: TTLs and automated teardown are enabled for non-production environments.
3. Observability-first: Every environment must register metrics and lifecycle events to the infra telemetry pipeline.
4. Safe defaults: Provisioning pipelines must require approvals beyond cost/size thresholds and support fast rollback.
5. Ownership & accountability: Each environment has a single responsible owner (user or service account) recorded in tags and audit logs.

Definitions

- Churned environment: any GPU instance/pool created and destroyed more than 4 times in a 24h window.
- Ephemeral pool: a logically grouped set of GPU nodes created for a single CI job, eval run, or ad-hoc developer session with expected life < 24h.
- Persistent pool: long-lived GPU pool used for production serving or reserved capacity.

Design patterns and IaC primitives

1) Module composition pattern
- core/gpu-node: defines node shape (gpu type, disk image, taints, kube labels)
- core/gpu-pool: orchestrates autoscaler, capacity provider, and placement strategy
- control/teardown: TTL controller, lifecycle hook, and notification sink
- governance/labels: standardized tags for owner, cost-center, stack-id, purpose

2) Single-responsibility variables
- variables exposed by modules must be small and typed: size, max_count, min_count, ttl_hours (default 6), tenant, owner_email, cost_center, provisioning_reason

3) Tagging and audit boundary (must):
- tag.owner = owner_email
- tag.stack_id = ${var.stack_id}
- tag.env_purpose = ephemeral|dev|ci|eval|prod
- tag.policy_profile = low-cost|high-availability|gpu-sensitive

Terraform interface matrix (example)

| Input name | Type | Default | Notes |
|------------|------|---------|-------|
| stack_id | string | (required) | Unique short id used for naming and deletion policy |
| owner_email | string | (required) | Primary contact for alerts and approvals |
| ttl_hours | number | 6 | TTL after which automated teardown runs |
| max_count | number | 4 | Upper bound to protect capacity |
| gpu_type | string | a100-80gb | Allow only approved gpu types via validator |

CI/CD pipeline patterns

- All environment creation is controlled via a single pipeline template: infra/ephemeral/gpu-create.yml. Pipelines must:
  1. Validate HCL with tflint/terraform validate
  2. Run module-level policy checks (policyengine/opa) enforcing tag and size constraints
  3. Simulate plan and generate a human-readable diff artifact
  4. Apply in a dedicated control account using an ephemeral service principal
  5. Emit lifecycle event to infra.telemetry.gpu.events

Sample pipeline snippet (illustrative):

# pipeline: infra-gpu-create > steps
- name: validate
  run: terraform validate && tflint
- name: policy-check
  run: opa test /policies/gpu-size.rego
- name: plan
  run: terraform plan -out plan.tfplan
- name: human-approval
  when: conditional(contains(var.owner_email, "@redwood.com") == false || var.max_count > 8)
- name: apply
  run: terraform apply plan.tfplan

Operational runbook: preflight checklist

Before provisioning an ephemeral GPU pool:
- Confirm owner_email, cost_center, and stack_id are set.
- Confirm ttl_hours <= 72 (enforced by policy).
- Confirm gpu_type is allowed for the region.
- Confirm max_count <= account_quota_limit (CI will query account quota API).
- Verify alert hook (pager/slack) configured for lifecycle failures.

On-provision steps (automated)

1) Create pool via CI/CD pipeline (outputs cluster_id, nodegroup_id).
2) Wait for cluster registration: monitor kube-system readiness (target 90% nodes Ready within 10 minutes).
3) Emit event: infra.telemetry.gpu.events -> {action: created, stack_id, owner, expires_at}

Scale-up procedure (manual/automated)

1) Automated autoscaler increments min_count up to max_count when pending pods > 2 for > 2 minutes.
2) If pending pods persist for > 5 minutes, alert ops (severity: P2).
3) If ops approve, pipeline will update Terraform variable max_count and reapply (procedure documented in change approval).

Scale-down and teardown (numbered procedure)

1. TTL controller triggers when expires_at <= now.
2. Controller annotates cluster with teardown_pending and notifies owner via email and slack (48h, 12h, 1h cadence).
3. If owner requests extension: owner updates stack_id.ttl_hours via self-service UI (if allowed) or raises a support ticket.
4. If no extension, controller drains nodes (kubectl cordon + drain with grace period 120s) and deletes node groups.
5. Terraform destroy is executed in the control account with confirmation token recorded in audit log.

Escalation and rollback steps

- If teardown collides with an active production pod (unexpected taint leak):
  1) Immediately halt destroy (cancel destroy job).
  2) Re-label affected pods and cordon affected nodes.
  3) Notify Platform SRE and product owner; create incident if production SLOs are impacted.
  4) Restore cluster from snapshoted node images if deletion partially completed.

Monitoring and alerts (recommended SLOs/thresholds)

- Metric: ephemeral_gpu.node_ready_ratio -> SLO: >= 0.9 within 10 minutes of creation. Alert P2 if below.
- Metric: ephemeral_gpu.creation_rate -> Alert if > 3x baseline for 30m (possible runaway provisioning).
- Metric: ephemeral_gpu.destroy_failures -> Alert P1 if > 3 failures in 1h.

Cost controls and billing integration

- Every ephemeral stack_id is billed to a cost_center string; infra billing pipeline charges back weekly.
- Auto-mitigation: if projected daily spend for ephemeral pools exceeds $X (configurable), new ephemeral create requests are blocked until quota uplift is approved.

Security and networking constraints

- Ephemeral pools are created in a shared tenant VPC namespace with restricted egress via NAT gateway.
- Default network ACL denies external SSH; all access mediated via jump-host bastions with session recording.
- Subnet selection is restricted by policy to avoid cross-account peering that bypasses egress control.

Policy enforcement (examples)

- OPA rego snippets enforce: ttl_hours <= 72, max_count <= 16 for non-prod accounts, required tags present, gpu_type in allowed list for region.
- Terraform Cloud runs use policy sets with blocking checks; self-hosted CI uses opa gate jobs.

Migration checklist (moving ad-hoc pools to controlled IaC)

1) Identify unmanaged GPU instances from cloud inventory (last updated > 24h).
2) Reach out to owners discovered via tags; offer migration plan and eviction timelines.
3) Create IaC stack_id that models current configuration and run a dry-run migrate (terraform import where feasible).
4) After validation, enable TTL and observe for one lifecycle before enforcing automated teardown.

Risks and trade-offs

- Strict TTLs reduce developer friction in the long run but can block long-running experiments; mitigations include controlled extension requests and temporary persistent staging pools.
- Aggressive automated teardown needs robust detection of production labeling mistakes to avoid accidental deletion.
