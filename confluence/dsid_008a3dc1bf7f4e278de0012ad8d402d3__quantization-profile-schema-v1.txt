Quantization Profile Schema (v1)

## Summary
This document defines the **v1 Quantization Profile** schema used by the Quantization Profile Library. Profiles are **versioned, auditable** configuration objects that describe *how* a given model variant may be executed in a quantized mode under specific hardware/runtime constraints.

**Primary consumers:**
- Model Registry (storage, validation, signing)
- Control Plane / Policy Engine (compatibility checks, route-level enablement)
- Serving Runtime (deterministic selection + application)
- Console (display, warnings, changelog)

**Non-goals (v1):**
- Auto-tuning per customer or dynamic, in-production calibration
- Default-on enablement
- Implicit profile upgrades without explicit customer/admin action

---

## Terminology
- **Profile**: A published, immutable configuration for quantized execution of a specific model variant.
- **Profile reference (profile_ref)**: What routes store. Typically points to an exact `profile_id@profile_version` (recommended for determinism).
- **Quant method**: The algorithm/approach (e.g., GPTQ, AWQ) and/or runtime path (e.g., FP8).
- **Compatibility**: Whether a profile can be applied given model, runtime version, GPU class/SKU, and serving constraints (context length, batching mode, etc.).

---

## Schema overview
A v1 quantization profile is a single JSON document with:
- Stable identity (`profile_id`) and semantic version (`profile_version`)
- Target model binding (`model_id`, `model_variant`)
- Quantization configuration (`quant_method`, precision settings)
- Calibration provenance (`calibration`)
- Compatibility constraints (`constraints`)
- Known caveats and operational notes (`caveats`)
- Deprecation and lifecycle metadata (`lifecycle`)

**Determinism principle:** when a route enables a specific `profile_id@profile_version`, the runtime must apply that exact profile or deterministically fall back to baseline (per compatibility/fallback standard).

## Canonical JSON shape (v1)
The following is the canonical shape. Field order is illustrative.

```json
{
  "schema_version": "1.0",
  "profile_id": "qpl_redwood.llama3-70b-instruct.int8w_fp16a.gptq",
  "profile_version": "1.2.0",
  "display_name": "Llama3 70B Instruct INT8 weights (GPTQ), FP16 activations",
  "description": "Cost-optimized decode path for A100/H100 class GPUs with bounded max context.",

  "model_id": "redwood.llama3-70b-instruct",
  "model_variant": "v2025-02-10",

  "quant_method": "gptq",
  "precision": {
    "weight": "int8",
    "activation": "fp16",
    "kv_cache": "fp16",
    "accumulation": "fp16"
  },

  "artifacts": {
    "registry_uri": "registry://quant-profiles/redwood.llama3-70b-instruct/v2025-02-10/qpl_redwood.llama3-70b-instruct.int8w_fp16a.gptq/1.2.0/",
    "manifest_file": "manifest.json",

  },

    },
    "serving": {
      "max_context_tokens": "8192",
      "max_batch_size": "64",
      "continuous_batching_required": "true"
    }
  },

  "caveats": [
    "May degrade exact-match formatting on some JSON-structured outputs; run route-level A/B evals before scaling.",
    "Not recommended for max_context_tokens > 8k due to observed tail-latency increase."
  ],

  "lifecycle": {
    "status": "published",
    "published_at": "2025-02-12",
```

**Note:** The library and registry treat profiles as **immutable** once published. Updates require bumping `profile_version`.

## Field reference (v1)
All fields are required unless explicitly marked optional.

| Field | Type | Required | Description |
|---|---:|:---:|---|
| `schema_version` | string | yes | Must equal `"1.0"` for v1. Used for validation and forwards-compat parsing. |
| `profile_id` | string | yes | Globally unique identifier. **Stable across versions**. Format: `qpl_<publisher>.<model>.<profile-suffix>` (see Naming). |
| `profile_version` | string | yes | SemVer (`MAJOR.MINOR.PATCH`). Increment MAJOR for breaking constraint/behavior changes. |
| `display_name` | string | yes | Human readable name for Console and docs. |
| `description` | string | yes | Short description of intent and key constraints. |
| `model_id` | string | yes | Canonical registry model identifier (matches Model Registry). |
| `model_variant` | string | yes | Model variant/build identifier. Profiles are **bound** to a variant to avoid silent behavior changes. |
| `quant_method` | string | yes | One of: `gptq`, `awq`, `fp8`, `int8_dynamic`, `int4`. (See Enumerations.) |
| `precision.weight` | string | yes | Weight precision: `int4`, `int8`, `fp8`, `fp16`, `bf16`. |
| `precision.activation` | string | yes | Activation precision: `fp16`, `bf16`, `fp8`. (INT activations not supported v1.) |
| `precision.kv_cache` | string | yes | KV cache precision: `fp16`, `bf16`, `fp8`. |
| `precision.accumulation` | string | yes | Accumulation precision: `fp16` or `bf16` (runtime-dependent). |
| `artifacts.registry_uri` | string | yes | Registry URI to the profile artifact directory (manifest + any quantized weights/scales). |
| `artifacts.manifest_file` | string | yes | Manifest filename within artifact directory (typically `manifest.json`). |
| `artifacts.integrity.profile_digest_sha256` | string | yes | SHA256 digest of the canonicalized profile JSON for audit + cache safety. |
| `artifacts.integrity.signature_key_id` | string | yes | KMS/HSM key id used to sign artifacts in registry. |
| `calibration.dataset_id` | string | yes | Calibration dataset identifier (internal). Must be resolvable by Applied ML tooling. |
| `calibration.dataset_revision` | string | yes | Immutable revision tag/date/commit for dataset. |
| `calibration.method` | string | yes | `static` (v1). Reserved for future (`dynamic`). |
| `calibration.notes` | string | optional | Freeform notes on calibration composition and known limitations. |
| `constraints.runtime.min_runtime_version` | string | yes | Minimum Serving Runtime version required to safely apply this profile. |
| `constraints.runtime.supported_backends` | list[string] | yes | Allowed runtime backends. v1 expects `cuda`. |
| `constraints.runtime.kernel_family` | string | optional | Kernel family/feature flag used to gate kernel selection (e.g., `rw-attn-v4`). |
| `constraints.hardware.gpu_sku_allowlist` | list[string] | yes | Explicit GPU SKU allowlist (e.g., `A100-80GB`). |
| `constraints.hardware.gpu_arch_allowlist` | list[string] | optional | GPU arch allowlist (e.g., `sm80`, `sm90`) for more portable matching. |
| `constraints.hardware.min_vram_gb` | string | yes | Minimum VRAM required, integer encoded as string. |
| `constraints.serving.max_context_tokens` | string | yes | Hard maximum context tokens for which profile is supported. |
| `constraints.serving.max_batch_size` | string | optional | Upper bound for batch size used in validation/perf characterization. |
| `constraints.serving.continuous_batching_required` | string | optional | `true`/`false`. Some profiles rely on continuous batching behavior. |
| `caveats` | list[string] | optional | Customer-facing caveats and limitations. Keep actionable. |
| `lifecycle.status` | string | yes | One of: `draft`, `published`, `deprecated`, `blocked`. |
| `lifecycle.published_at` | string | yes | ISO date `YYYY-MM-DD`. |
| `lifecycle.deprecated_at` | string | optional | ISO date or empty string. |
| `lifecycle.superseded_by` | string | optional | Reference to another profile `profile_id@profile_version`. |
| `lifecycle.sunset_at` | string | optional | ISO date when registry may stop serving artifacts. |
| `owners.applied_ml` | string | yes | Owning org/team label. |
| `owners.runtime` | string | yes | Owning org/team label. |
| `owners.registry` | string | yes | Owning org/team label. |

## Enumerations
### `quant_method`
Allowed values in v1:
- `gptq` (static weight-only quantization, typically INT8/INT4 weights)
- `awq` (static weight-only quantization)
- `fp8` (FP8 execution path, typically FP8 weights + activations; hardware/kernel constrained)
- `int8_dynamic` (dynamic int8 path; limited support, requires explicit kernel family)
- `int4` (reserved; publish only if runtime explicitly supports for the target model family)

### Precision fields
Allowed values:
- `weight`: `int4`, `int8`, `fp8`, `fp16`, `bf16`
- `activation`: `fp16`, `bf16`, `fp8`
- `kv_cache`: `fp16`, `bf16`, `fp8`
- `accumulation`: `fp16`, `bf16`

---

## Naming rules
### `profile_id`
- Must be lowercase with separators `.` and `-` only.
- Must start with `qpl_`.
- Must include model identifier and a concise suffix describing the quant mode.

Recommended pattern:
- `qpl_<publisher>.<model_id>.<wX>a<Y>.<method>`
  - Example: `qpl_redwood.redwood.llama3-70b-instruct.int8w_fp16a.gptq`

### `profile_version`
- Must be SemVer and **must change** for any modification.
- `PATCH`: metadata/caveat edits, artifact path changes with identical behavior.
- `MINOR`: behavior-preserving improvements or expanded allowlists (subject to regression policy).
- `MAJOR`: behavior changes, different quantization scheme, different context constraints, different calibration source, etc.

---

## Validation rules (registry-side)
Model Registry validation MUST reject profile documents that violate the following.

### Structural validation
1. JSON must parse and contain only known top-level keys for `schema_version = 1.0`.
2. Required fields must be present and non-empty (unless explicitly allowed to be empty string).
3. List fields must be arrays of strings; must not contain empty strings.

### Identity and binding validation
1. `profile_id` must be unique within the registry namespace.
2. `model_id` must exist in Model Registry.
3. `model_variant` must exist for that `model_id`.
4. A profile must bind to exactly one `model_id` + `model_variant` (no wildcards in v1).

### Method/precision compatibility validation
1. If `quant_method` is `fp8`, then `precision.weight` and `precision.activation` must be `fp8`, and `constraints.hardware.gpu_arch_allowlist` must include `sm90` (Hopper-class) unless explicitly waived by Runtime sign-off.
2. If `precision.weight` is `int4`, `constraints.hardware.gpu_sku_allowlist` must be explicit and narrow (no broad families) and `constraints.serving.max_context_tokens` must be set.
3. `precision.activation` must not be `int8`/`int4` (unsupported v1).

### Artifact integrity validation
1. `artifacts.registry_uri` must resolve to a registry path under the quant-profile artifact root.
2. `artifacts.manifest_file` must exist at publish time.
3. `profile_digest_sha256` must match the canonicalized profile JSON (canonicalization: UTF-8, sorted keys, no insignificant whitespace).
4. Signature key must be in the approved key allowlist for the target environment.

### Lifecycle validation
1. `lifecycle.status` must be one of the allowed values.
2. If `lifecycle.status = published`, `published_at` must be non-empty.
3. If `lifecycle.status = deprecated`, `deprecated_at` must be non-empty and `superseded_by` should be set.

---

## Validation rules (policy engine / control plane)
At resolution time (route config → resolved execution plan), the policy engine MUST enforce:
1. **Exact match** on `model_id` and `model_variant`.
2. Runtime version compatibility: runtime must be `>= constraints.runtime.min_runtime_version`.
3. Backend compatibility: current backend must be in `supported_backends`.
4. GPU compatibility: SKU must be in `gpu_sku_allowlist` (and arch in `gpu_arch_allowlist` when present).
5. Serving constraints:
   - Requested `max_context_tokens` must be `<= constraints.serving.max_context_tokens`.
   - If `continuous_batching_required = true`, route/runtime must have continuous batching enabled.

If any check fails, the system MUST apply deterministic fallback behavior (baseline precision) and emit the standard resolution outcome signals (see Runtime + Observability docs).

---

## Known caveats guidance
When populating `caveats`, keep statements:
- Specific and testable (what changes, where, and what to do)
- Aligned with the Quantization Regression Thresholds policy
- Suitable for customer display (no internal-only jargon)

Examples:
- Good: “Not supported for context > 8k; enabling may increase p95 decode latency by >15%.”
- Avoid: “Sometimes weird.”

## Backward/forward compatibility notes
- Consumers MUST gate parsing by `schema_version`.
- Additive fields may be introduced in `1.x` only if they are optional and safely ignored.
- Breaking changes require `schema_version = 2.0` and a new parser/validator.

---

## Change control
- Schema changes: owned by **Model Registry** (Quentin Harris) with reviews from Applied ML (Arjun Desai) and Runtime (Noah Patel).
- New profile publication: owned by **Applied ML**, requires passing the quantization regression gates and runtime compatibility checks.
- Deprecation: requires a published successor or explicit justification, plus customer-impact assessment for any widely enabled profile.

---

## Appendix: Common validation failures
- `model_variant` mismatch (profile built for different pinned model build)
- GPU SKU not allowlisted (especially Dedicated customers with mixed fleets)
- Runtime version too old (min_runtime_version not met)
- Context length too high (max_context_tokens exceeded)
- Missing/incorrect `profile_digest_sha256` (prevents caching + audit invariants)
