GPU demand forecasting and ML-backed scaling playbook

Overview

Purpose: This playbook describes the end-to-end system Redwood uses to forecast GPU demand (short-term and medium-term), convert predictions into actionable provisioning and reservation decisions, and close the loop with CI/CD-driven IaC to keep capacity aligned with product demand. The goal is to reduce overprovisioning by 18–30% while maintaining a 99.9% request success rate for hosted and dedicated customers.

Scope and audience:
- Audience: infra engineers, capacity planners, SRE, platform product managers, finance (cost forecasting).
- Services in scope: inference-gw (edge+api), serving-pool (hosted), dedicated-pool-manager, batch-training-queue.
- Time horizons: short-term (0–6 hours), medium-term (6–72 hours), planning horizon (1–8 weeks).

Definitions and key signals

- Utilization: GPU device compute utilization sampled at 60s cadence (metric: gpu.util_percent).
- Queue depth: number of pending inference jobs per pool (metric: serving.queue_depth).
- Request latency P95: per-model route P95 latency (metric: request.latency_p95).
- Reservation coverage: fraction of predicted peak minutes covered by reserved capacity.
- Prediction error: mean absolute percentage error (MAPE) on the forecast window.

Data sources

We combine the following signals to form features for forecasting and for decision rules: 
- Telemetry: Prometheus (gpu.*, serving.*), aggregated to 1m/5m/1h windows.
- Billing and allocation: cost_center tagging from Terraform/tags API and cloud billing exports.
- Job metadata: model_type, sequence_length_percentile, average_tokens_per_request (from tracing).
- Calendar/seasonality: day-of-week, business-hours flag, launch windows (from product calendar).
- External triggers: scheduled canary rollouts, marketing events (manual annotations).

Architecture overview

1) Ingestion and feature store:
- Metric ingesters pull Prometheus time series into feature-store (ClickHouse-based TS store).
- Job-level features are enriched from tracing (X-Ray) and stored as time-series keyed by pool/model labels.

2) Forecasting model and training:
- Model: gradient-boosting (LightGBM) model for short/medium-term and a separate transformer-based sequence model for anomaly-aware forecasting for 0–72h.
- Training cadence: daily retrain, with incremental re-fit every 6 hours for the short-term model.
- Evaluation: holdout windows, weekly backtests; target metrics: MAPE < 12% (short-term), MAPE < 18% (72h).

3) Decision engine (policy layer):
- Converts forecasts into actions: scale-up (provision on-demand VMs), scale-down (decommission spot / rightsizing), reserve procurement (commit to reserved contracts) and routing policies (move certain routes to dedicated pools or fallbacks).
- Safety policies: overlay a minimum capacity buffer (configurable default: 15% + predicted variance band) to avoid underprovisioning.

4) IaC/Execution:
- Terraform modules + custom operators handle making capacity changes (see IaC section).
- CI/CD: capacity-plan pipeline validates changes, runs a dry-run plan, and applies via an approved oncall account.

IaC modules and recommended patterns

- Module naming: infra-gpu-pool (public), infra-gpu-reservation (reserved-contracts), infra-gpu-autoscaler. Keep modules idempotent and parameter-driven.

Example Terraform usage (snippet):

```hcl
module \"infra_gpu_pool_bert\" {
  source = \"git::ssh://git.redwood.com/infra/modules//infra-gpu-pool?ref=v2.4.0\"
  name   = \"serving-pool-bert\"
  account = \"gpu-hosted-prod\"
  region  = \"us-west-2\"
  gpu_type = \"a100-80gb\"
  min_nodes = 4
  max_nodes = 120
  node_labels = { pool = \"serving\", model_family = \"bert\" }
}
```

- Reservation module example (generates Purchase/Commit resource for cloud provider):
```hcl
module \"infra_gpu_reservation_3m\" {
  source = \"git::ssh://git.redwood.com/infra/modules//infra-gpu-reservation?ref=v1.2.0\"
  account = \"gpu-hosted-prod\"
  region  = \"us-west-2\"
  sku     = \"a100-80gb-hour\"
  commit_hours = 24 * 90
  quantity = 20
  approval_team = \"capacity-planning\"
}
```

CI/CD integration and gating

- Pipeline: capacity-plan -> terraform-validate -> terraform-plan (dry) -> cost-simulate -> manual-approval (if reserved capacity or > $25k/month delta) -> terraform-apply (run by automation identity).
- Git branch policy: capacity changes must be opened against the `capacity/` prefix and include a simulation artifact (CSV of predicted peak vs current coverage).
- Automated tests: unit test modules using terratest, cost sanity checks, and a smoke test that waits for new nodes to become Ready and run a model-inference canary.

Autoscaler and real-time control plane

- Autoscaler (service: gpu-autoscaler) listens to predictions API and Prometheus. It enforces scaling decisions respecting: min_nodes, max_nodes, spot_fallback_percent, and per-tenant isolation constraints.
- Safety hooks: pre-scale-run validation checks current node churn, recent incident windows, and maintenance flags. Autoscaler will delay non-critical scale-downs for 15 minutes after an incident window.

Decision rules (example)

1. If predicted pooled utilization > 78% for next 2h and queue_depth > 40 for any 10m sliding window, trigger scale-up to meet predicted 95th percentile demand + 15% buffer.
2. If predicted utilization < 30% for 6h window and spot_hit_rate > 95%, plan a scale-down of spot nodes subject to a 2-step cooldown (dry-run + apply).
3. If MAPE(6h) > 25% for two consecutive runs, fallback to conservative policy: increase buffer to 30% and notify capacity-team Slack channel #capacity-alerts.

Runbook: capacity shortage incident (severity: P1)

Summary: This runbook is executed when client-facing requests start failing due to insufficient GPU capacity (symptoms: request.latency_p95 spikes > 3x baseline, request.errors.rate > 0.5%, queue_depth sustained > 100).

Owner: oncall-infra (primary), capacity-planning (secondary).

Immediate actions (0–10 minutes):
1. Acknowledge incident and open an incident thread in #incidents-gpu with short summary and link to this page.
2. Check current pools: `kubectl get nodes -l pool=serving -o wide` and `promql: max_over_time(serving.queue_depth[10m])`.
3. If autoscaler is healthy: `systemctl status gpu-autoscaler` and check last action in autoscaler logs.
4. Trigger emergency on-demand provisioning: run `./scripts/provision-emergency.sh --pool serving --count 20 --reason "P1 shortage"`. This script calls Terraform with `-var emergency=true` and an approved emergency key.
5. If provisioning fails, move critical traffic to fallback smaller models via routing rules in inference-gw: `POST /admin/routing/switch` (JSON payload example below).

Routing switch payload example:
```json
{ \"route\": \"chat\", \"fallback_model\": \"gpt-small-v2\", \"duration_minutes\": 30, \"reason\": \"capacity-shortage\" }
```

Recovery and follow-up (10m–24h):
- Monitor latency and errors; once latency P95 < 1.3x baseline for 30m, begin controlled scale-down of emergency nodes with 30m cooldown windows.
- File a post-incident note to the incident tracker with root cause, forecast accuracy at time of incident, and recommended policy changes (e.g., increase training cadence, adjust buffer).

Escalation matrix

- 0–15m: oncall-infra (pager)
- 15–60m: capacity-planning lead (pager)
- >60m: Director of Infrastructure and Product owner notified

SLOs and monitoring

Primary SLOs:
- Request success rate (hosted inference): 99.9% monthly
- Scale action time-to-provision (on-demand): median 4m, 95th percentile 12m
- Forecast horizon MAPE (6h): target < 12%

Key dashboards and alerts:
- Dashboards: GPU capacity overview, Forecast accuracy, Reservation coverage, Autoscaler actions feed.
- Alerts: high queue depth (> 50 sustained 5m), forecast MAPE rising above 25% (on two runs), reservation shortfall warnings (predicted reserve deficit > 48h).

Operational metrics to track (examples):
- gpu.device_count, gpu.util_percent, serving.queue_depth, request.latency_p95, autoscaler.action_rate, forecast.mape_6h, reservation.coverage_hours

Testing and validation

- Backtest repository: `git::ssh://git.redwood.com/infra/capacity/backtests` with notebooks and datasets (1y of telemetry).
- Canary test: After any IaC apply that increases pool size by more than 10%, run inference canary that executes 1k sample requests per model family and asserts latency/accuracy thresholds.

Cost controls and finance integration

- Cost threshold gating: any reserved procurement > $5k/month requires finance approval. Changes producing > $25k/month delta escalate to VP Finance.
- Tagging discipline: every node must be tagged with cost_center, team, product, sku to allow accurate chargeback. Failure to apply tags causes CI check to fail.

Operational notes and tips

- Use `forecastctl` (internal CLI) to query prediction snapshots: `forecastctl get --pool serving --window 6h --as-of now`.
- Keep conservative buffers around large model rollouts (e.g., model-family-name changes) for at least 48 hours after rollout.
- Prefer reserved commitments in long-term steady pools (e.g., dedicated-customer pools) and on-demand/spot for short, spiky workloads.

Appendix: small utilities and scripts

```bash
#!/usr/bin/env bash
POOL=${1:-serving}
COUNT=${2:-20}
reason=${3:-\"manual-emergency\"}
cd infra/terraform/${POOL}
terraform init -backend-config=backend.hcl
terraform apply -var \"emergency=true\" -var \"emergency_count=${COUNT}\" -auto-approve
# post apply: publish event to /events/capacity
```
