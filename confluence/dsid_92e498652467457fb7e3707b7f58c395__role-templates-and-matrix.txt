RBAC v2 Role Templates and Permission Matrix

## Summary
This page defines Redwood’s **built-in RBAC v2 role templates** and the **explicit permission matrix** backing each template. The intent is to provide:
- Strong default roles for enterprise deployments (Hosted, Dedicated, and Private).
- Clear **separation of duties** (Security vs Billing vs Operations).
- A predictable starting point for customers, Solutions Engineering, and Support.

These templates are shipped as part of the **policy bundle** and can be assigned at the appropriate scope (Org / Project / Environment / Cluster). Customers may also create custom roles, but the templates below are the recommended baseline.

## Design principles
1. **Deny by default.** Role templates grant only what is explicitly listed.
2. **Separation of duties.** No single non-admin role should cover identity + billing + sensitive security operations.
3. **Auditability first.** Permissions that expose sensitive data or change security posture are limited and logged with authz decision context.
4. **Scoped assignment.** Prefer Project/Environment/Cluster scoping over Org-wide whenever feasible.
5. **Safe ops defaults.** Operational roles can keep services running without granting user/role administration.

## Scope model (how templates are intended to be assigned)
RBAC v2 supports binding roles at multiple scopes:
- **Org scope**: organization-wide administration, identity, billing, security posture.
- **Project scope**: app/team boundary for model usage and configuration.
- **Environment scope**: e.g., dev/staging/prod separation for routing policies, model pinning, and operational controls.
- **Cluster scope** (Dedicated/Private): infrastructure-level operational controls for a specific deployment cluster.

Guideline:
- Use **Org Admin** sparingly (typically 1–3 people).
- Use **Security Admin** for compliance/security team members; avoid coupling with day-to-day operations.
- Use **Deployment Operator** at **Environment or Cluster** scope for SRE/platform operators.

## Permission naming convention (abridged)
Permission strings follow the conventions in ADR-014. Summary format:
- `<domain>.<resource>.<verb>`
- Verbs are explicit: `read`, `list`, `create`, `update`, `delete`, `rotate`, `export`, `impersonate`.
- Some actions are treated as “privileged verbs” and should rarely be granted: `rotate`, `export`, `impersonate`, `delete` (for certain resources).

## Role templates (proposed)
The following templates are included in the policy bundle (versioned). “Recommended scope” indicates where the template is usually bound.

### 1) Org Admin
**Purpose:** Full administrative control of Redwood account, including identity and configuration.
- Recommended scope: **Org**
- Intended users: primary platform owners
- Notes: Includes the ability to grant roles; treat as highly privileged.

### 2) Security Admin
**Purpose:** Security and compliance administration without billing ownership.
- Recommended scope: **Org**
- Intended users: security engineering, compliance administrators
- Notes: Can manage SSO/SAML settings, audit log exports, retention controls, API key governance, and org/user/role administration (except billing).

### 3) Billing Admin
**Purpose:** Billing and usage visibility; manage payment and invoices.
- Recommended scope: **Org**
- Intended users: finance ops, procurement admins
- Notes: No access to audit exports, secrets, API keys, routing policies, or user/role admin.

### 4) Read-only Auditor
**Purpose:** Read-only access for auditors and risk teams.
- Recommended scope: **Org** (or Project if customer wants to limit visibility)
- Intended users: internal audit, external auditors, GRC
- Notes: Read-only across org configuration and audit logs. **No export by default** (export is its own permission).

### 5) Project Admin
**Purpose:** Project-level admin for application teams; can configure models and routing in their project environments.
- Recommended scope: **Project**
- Intended users: engineering leads for a product/team
- Notes: No org-wide identity/billing. Can manage project-level API keys (if enabled) and rollout policies.

### 6) Developer (Project Member)
**Purpose:** Build and operate within a project without sensitive administration.
- Recommended scope: **Project**
- Intended users: most engineers
- Notes: Read-only config + ability to create/manage personal or project API keys is customer-dependent; see the matrix.

### 7) Deployment Operator (Dedicated/Private)
**Purpose:** Operate Dedicated/Private infrastructure and service health, without identity or security posture changes.
- Recommended scope: **Environment** or **Cluster**
- Intended users: platform/SRE/operator staff
- Notes: Can manage deployment lifecycle operations (scale, roll, restart), view operational logs/metrics, and adjust non-security runtime settings. Routing policy edits may be optional based on customer separation-of-duties.

### 8) Deployment Auditor (Dedicated/Private)
**Purpose:** Read-only operational visibility for Dedicated/Private deployments.
- Recommended scope: **Environment** or **Cluster**
- Intended users: auditors, incident review participants

### 9) Support (Redwood internal) — restricted
**Purpose:** Internal Redwood support access for troubleshooting with strict controls.
- Recommended scope: **Org/Project** only when explicitly granted and time-bound
- Notes: Typically granted via **break-glass** mechanism; see break-glass doc. Not intended as a customer-facing template.

## Rationale by template (why these permissions are grouped)
### Org Admin
- Must be able to recover from misconfiguration (including role/role binding changes).
- Includes billing and security posture changes because it is the “owner” role.
- Expected to be tightly limited and monitored.

### Security Admin
- Owns access control, auditability, and compliance settings.
- Includes `iam.*` and `audit_log.export` because these are common enterprise requirements.
- Excludes billing payment method changes to preserve separation-of-duties.

### Billing Admin
- Needs invoices, payment method, budgets, and usage visibility.
- Explicitly does **not** include permissions to view secrets, manage users/roles, modify routing/model behavior, or export audit logs.

### Read-only Auditor
- Needs read-only access to demonstrate controls and perform audits.
- Excludes export by default to reduce data exfiltration risk; Security Admin can enable export if required.

### Project Admin
- Owns the project’s model configuration and rollout/routing behavior within allowed scopes.
- Can manage project-scoped role bindings (optional; recommended for self-service teams).
- Should not have org-wide visibility into other projects’ secrets/keys unless explicitly granted.

### Developer
- Minimal config read + ability to do day-to-day work.
- Optional self-managed API keys depends on customer preference; if enabled, constrained to self-owned keys and audited.

### Deployment Operator / Deployment Auditor
- Focused on Dedicated/Private operational stability.
- Update/execute actions are limited to infra lifecycle and runtime operations; security posture changes (KMS config, SSO, retention) remain with Security Admin.

## Recommended default assignments (enterprise)
A common least-privilege setup for regulated customers:
- 1–2 users: **Org Admin** (Org)
- Security team: **Security Admin** (Org)
- Finance/procurement: **Billing Admin** (Org)
- External auditors / internal audit: **Read-only Auditor** (Org)
- App team leads: **Project Admin** (Project)
- Engineers: **Developer** (Project)
- SRE/platform operators (Dedicated/Private): **Deployment Operator** (Cluster/Environment)
- Incident review participants: **Deployment Auditor** (Cluster/Environment)

## Operational notes
- Role templates are generated from YAML in the policy bundle and released as a versioned artifact (consumed by Gateway/Control Plane/Console).
- Authorization decisions (allow/deny) MUST be logged for sensitive actions with: subject, action, scope, policy version, and denial reason code.
- Console “Role Templates” UI should render:
  - Template description + intended scope
  - Explicit permission list
  - Diff view if customer edits/extends a template into a custom role
