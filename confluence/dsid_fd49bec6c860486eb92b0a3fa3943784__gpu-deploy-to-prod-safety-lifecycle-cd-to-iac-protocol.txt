GPU deploy-to-prod safety lifecycle: CD-to-IaC protocol

Summary
------
This playbook defines the canonical lifecycle and safety controls for deploying GPU-related artifacts (inference runtime images, kernel modules, driver bundles, and Terraform/IaC plans) from continuous integration into production GPU fleets. It ties together CI pipelines, artifact attestation, IaC planning, staged canaries, telemetry gates, and rapid rollback procedures. The goal is to make every production GPU deployment auditable, low-risk, and reversible while preserving developer velocity.

Scope and applicability
----------------------
- Applies to any change that affects: runtime container images, GPU kernel drivers, systemd startup artifacts on GPU nodes, Terraform modules that modify GPU pools (creation/scaledown/taints), and rollout policies that change warm-pool seeding.
- Excludes user-space model weights and non-runtime model artifacts (those are handled by model-onboarding).

Ownership and SLAs
------------------
- Primary owner: eng-infra CI/CD team (oncall: cd-oncall rotation)
- Secondary owner: gpu-fleet team
- Verification owner: runtime-safety (applies to attestation and cryptographic signing)
- Target gated rollout SLO: 99.9% successful canary seed within 30 minutes; mean time to detect regressions in canary: < 10 minutes.

Key concepts (quick definitions)
--------------------------------
1. Attested artifact: container image or driver bundle with a tamper-evident signature and provenance metadata (cosign, SBOM link, build git commit).
2. IaC plan: Terraform plan that will be applied to cloud accounts to create/modify GPU pools. Plans are stored in the release candidate artifact and must be reviewed and approved by the IaC gate.
3. Canary tranche: a small subset of GPU nodes (per-region, per-az) that receive the new runtime image or IaC change first.
4. Warm-seed: proactive loading of commonly used model KV caches to reduce latency SLO blips during rollout.

High-level lifecycle (executive flow)
------------------------------------
1) Developer creates change -> CI builds artifacts and SBOM.
2) CI signs artifacts and uploads provenance to artifact registry.
3) CI generates an IaC plan (terraform plan) using pinned provider versions and records plan fingerprint.
4) Automated integration tests run against a synthetic, cost-emulated GPU sandbox (see section Test Emulation).
5) If tests pass, the pipeline creates a release candidate (RC) with references to artifacts, plan, and canary policy.
6) Release candidate goes to gated rollout: manual approval required for production by IaC approvers, unless the change is below the low-risk threshold (documented in Appendix A).
7) Canary rollout: RC is applied to a 3-node per-region canary tranche with telemetry gates.
8) Observability checks run for a minimum window (default 20 minutes). If gates pass, staggered expansion continues; on failure, automatic rollback and incident playbook execution.

Detailed pipeline gates and checks
----------------------------------
- Pre-merge CI checks (fast block): unit tests, lint, minimal integration smoke that runs against commit-built runtime in a CPU emulation harness.
- Post-merge CI checks (slow): full integration matrix including: container runtime startup, CUDA driver compatibility verification, small-batch generation correctness, KV cache warm up smoke.
- Attestation gate: cosign signature present, SBOM URL resolvable, build commit hash matches linked source.
- Terraform gate: plan fingerprint must match approved RC plan; diff must contain a changelog entry and an owner tag.
- Canaries only proceed if: node health metrics baseline is stable, egress budget headroom > 20%, and CI SLA metrics (error-rate, latency P95) for the RC on synthetic tests match baseline within defined tolerance (Appendix B).

Operational runbook: Canary rollout step-by-step
------------------------------------------------
1. Initiate RC: CD pipeline triggers terraform apply in a staging workspace that maps to the target region's canary pool.
2. Wait for node provisioning: expected time 6–18 minutes (depends on cloud spot vs reserved). If provisioning exceeds 40 minutes, abort and open TICKET-GPU-PROV.
3. Node attestation and agent enrollment:
   - On first boot, the node posts a TPM-backed CSR to the attestation service.
   - Attestation service verifies image signature, kernel module fingerprints, and returns a node identity token with TTL = 8 hours.
   - Enrollment agent attaches node tags: canary=true, rc_id=<rc-id>, owner=ci-cd.
4. Deploy runtime image to canary nodes via rollout controller with concurrency=1 per az.
5. Warm-seed common model prefixes (background job). Do not exceed warm-seed RPS of 50 to avoid egress bursts.
6. Run verification suite (automated): health checks, load-light inference, memory leak detector, KV cache correctness, and telemetry spike detection. Expected run: 10 minutes.
7. Telemetry gates evaluate: custom metric thresholds, error-rate delta, latency delta, CPU/GPU utilization anomalies. If any gate trips, the pipeline performs a fail-fast rollback.
8. If gates pass for the configured window, expand to tranche-2 (10% of targeted capacity). Repeat gate checks with throttle ramp of 5 minutes between steps.

Rollback and remediation policy
------------------------------
- Automatic rollback: triggered when any telemetry gate violates a critical threshold (defined in Appendix B). The rollback includes: stop new request routing to canary nodes, revert fleet service config to previous image tag, run a fast node drain, and mark RC status=failed.
- Manual rollback: if automated rollback fails, follow incident remediation playbook (section Incident Playbook).
- Post-rollback: create postmortem within 72 hours if rollback occurred in production. Owner: change author + gpu-fleet lead.

Terraform/IaC specifics and conventions
-------------------------------------
- Workspaces: every RC must create a disposable terraform workspace for canary changes (naming: rc-{rc-id}-{region}).
- Immutable module versions: module versions used in RC must be pin-referenced using the module registry hash.
- Change policy: any plan that scales down or removes warm-pools must include a migration plan for KV checkpoints.
- Terraform plan storage: store plan JSON and human diff in the release artifact with checksum.

Security & attestation details
------------------------------
- Required artifacts: cosign signature, SBOM (CycloneDX), git commit, build logs.
- Attestation flow (summary):
  1) Build signs image with ephemeral key stored in CI KMS.
  2) Cosign public key is rotated monthly; rotation applied to attestation verifier service.
  3) Nodes validate image signature at boot via firmware-assisted verifier (if available) or via ephemeral verifier container.
  4) If verification fails, node aborts enrollment and raises an alert.
- Secret handling: node identity tokens are short lived and stored in node local vault; long-lived credentials are never provisioned to nodes.

Test Emulation and Synthetic Workloads
-------------------------------------
- Purpose: emulate production token costs and egress patterns in a cost-limited sandbox so regressions are caught without incurring production expenses.
- Implementation: a small fleet of fractional-GPU instances with deterministic workload generator that mimics request shape distribution.
- Example CI command to run emulation: 
  ./ci/emulate_workload.sh --profile=prod-lite --duration=10m --seed=2025
- Acceptance criteria: latency P95 within +10% of baseline; token consumption distribution matches target quantiles.

Observability gates (metrics & traces)
--------------------------------------
- Core metrics collected during rollout:
  - infra.node.provision_time (s)
  - infra.node.attestation_status (OK/FAIL)
  - runtime.inference.latency.p95 (ms)
  - runtime.inference.error_rate (req/s)
  - runtime.kvcache.hit_rate (prefix)
  - infra.egress.bytes_per_min (per node)
- Tracing: sample 10% of requests going to canary nodes with full span tagging rc_id and node_id.
- Gate engine: a small service that evaluates time-windowed metric rules and emits verdicts (pass/warn/fail) to the CD pipeline via webhook.

CI/CD pipeline snippets (example)
--------------------------------
- Example GitHub Actions step (simplified):
  - name: Build and Sign
    run: |
      docker build -t registry.redwood.dev/rc/${{ env.RC_ID }} .
      cosign sign --key ${{ secrets.COSIGN_KEY }} registry.redwood.dev/rc/${{ env.RC_ID }}
      ./ci/generate_sbom.sh registry.redwood.dev/rc/${{ env.RC_ID }} > sbom.json

- Example Terraform CI check (pseudo):
  terraform init -get=true
  terraform workspace new rc-${RC_ID}-${REGION}
  terraform plan -out=plan.tfplan
  terraform show -json plan.tfplan > plan.json
  ./ci/validate_plan.py --plan plan.json --allowed-diffs allowlist.yaml

Canary escalation matrix (who is notified)
-----------------------------------------
- Warning gate (non-blocking): notify rc-author, gpu-fleet-oncall via Slack #gpu-canaries, create lightweight incident in PagerDuty (severity P3).
- Fail gate (automated rollback): trigger PagerDuty P1 to gpu-fleet-oncall and cd-oncall; create an automated ticket in Jira with logs bundle.

Incident playbook (quick steps if rollback occurs)
--------------------------------------------------
1. Confirm rollback completed and mark nodes as isolated.
2. Collect artifacts: terraform plan, cosign metadata, sbom, node logs (systemd, agent, docker), and relevant traces.
3. Run health sweep on baseline fleet to ensure residual impact is contained.
4. Assign triage owner and create postmortem template (link: /confluence/eng-infra/postmortems/template).

Appendices
----------
Appendix A — Low-risk change thresholds
- Non-sensitive label-only changes to IaC variables (e.g., documentation tags) where no infra delta occurs.\- Runtime image re-tag where image hash identical to previous release.

Appendix B — Gate thresholds (examples)
- latency.p95 delta > +15% -> FAIL
- runtime.error_rate delta > +0.5% absolute -> FAIL
- kvcache.hit_rate drop > 8 percentage points -> WARN
- infra.node.provision_time > baseline + 300s -> WARN

Appendix C — Example plan metadata table (text table)
| field | example | notes |
| rc_id | rc-20250207-17 | unique release id |
| plan_checksum | sha256:abcd... | used to validate applied plan |
| module_versions | registry/modules/gpu@v1.3.2 | pinned module refs |

Checklist before marking RC as promoted
---------------------------------------
- [ ] Attestation signatures verified and SBOM uploaded
- [ ] IaC plan stored and checksum matches applied plan
- [ ] Canary tranche telemetry gates passed for configured window
- [ ] Warm-seed completed without egress spikes
- [ ] Observability traces sampled and available in tracing system
- [ ] Post-deployment health sweep completed

FAQ and rationale highlights
---------------------------
- Why short-lived node tokens? Minimizes blast radius if a node is compromised and aligns with our attestation-first posture.
- Why require terraform plan fingerprints in RC? Prevents drift between what was reviewed and what is applied in production.
