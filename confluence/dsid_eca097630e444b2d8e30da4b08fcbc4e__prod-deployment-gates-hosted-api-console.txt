Production Deployment Gates: Hosted API and Console

h1. Summary
This standard defines the minimum pre-deploy and post-deploy gates for production changes to the *Hosted API* and *Console*. It is intended to be used alongside the relevant runbooks and change management policy.

h1. Applies to
* Hosted API services (request router, inference gateway, streaming gateway, embeddings service, auth edge)
* Console services (console-web, console-api)
* Shared dependencies when changed as part of a release (feature flags, policy configs)

h1. Required release artifacts
For every production release you must be able to provide:
* Build identifier (image digest and/or build number)
* Release notes snippet (even internal-only)
* Link to change record (ticket)
* Link to PR(s) and test results

h1. Pre-deploy gates (all required unless explicitly exempted)
1. *Unit tests:* Green CI for all touched packages.
2. *Integration tests:* Green for service-level integration suite; exceptions must be approved by service owner.
3. *Perf sanity:* If request path or caching/batching changed, run perf-canary baseline or attach a prior comparable run.
4. *SLO posture:* Confirm current p95 latency and error rate are within normal bounds for the region(s) being deployed.
5. *Capacity posture:* If changing concurrency, batching, autoscaling, or kernel settings, confirm headroom ≥ 20% in target regions or include an SRE-approved plan.
6. *Schema/migration gate:* Any schema migration must be backward compatible and have a documented rollback/forward plan.
7. *Security gate:* Required when any of auth/RBAC/secrets/audit logging/PII retention is touched.

h1. Canary requirements
Canary is mandatory for traffic-bearing services unless the change is doc-only or explicitly exempted.
* Canary scope: 1 region OR 1% traffic (whichever is supported by the service)
* Canary duration: minimum 15 minutes of steady-state traffic
* Canary pass criteria:
  - Error rate does not regress by > 0.2% absolute
  - p95 latency does not regress by > 10%
  - No sustained saturation signals (GPU queue depth, CPU throttling, memory pressure)

h1. Post-deploy gates
1. *Verify functional health:* key endpoints return expected responses (smoke tests).
2. *Verify observability:* dashboards show data, alerts are not muted unexpectedly, and logs can be queried.
3. *Verify billing/usage integrity:* if metering touched, validate token counts on a test account and at least one production cohort.
4. *Watch window:* maintain enhanced monitoring for 60 minutes after full rollout.

h1. Required dashboards (minimum set)
* Hosted API: Request success rate, p50/p95 latency, token throughput, saturation (GPU/CPU), router 5xx by route
* Console: Web error rate, console-api 5xx, auth failures, UI load time, feature-flag evaluation errors

h1. Exemptions
Exemptions are allowed only when:
* The change is truly non-impacting to production behavior
* The exemption is documented in the change record
* The service owner approves the exemption
