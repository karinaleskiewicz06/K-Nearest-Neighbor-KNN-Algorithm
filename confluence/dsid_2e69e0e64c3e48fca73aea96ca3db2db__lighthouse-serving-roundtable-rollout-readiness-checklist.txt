Lighthouse Serving Roundtable: Rollout Readiness Checklist (Canary A / Quantized v2)

## Overview
This page standardizes what we review in the Lighthouse Serving Roundtable before changing the Canary A rollout percentage for the quantized v2 serving path. It is intended to keep the weekly discussion focused on decision-quality inputs: customer impact risk, capacity readiness, instrumentation coverage, and rollback safety.

This document replaces ad-hoc personal prep notes and should be used as the pre-read template for the roundtable thread.

---

## Meeting format
**Cadence:** Weekly (Tuesday) 30 minutes

**Expected attendees:**
- Serving runtime core
- Infrastructure (capacity / cluster)
- Console (route configuration / UX)
- SRE on-call (rota)
- Product PM (as needed for release gating)

**Primary goal:** Make (or defer) a clear decision to (a) proceed to the next canary step, (b) hold at current %, or (c) roll back.

---

## Scope
**In scope**
- Canary A (quantized v2) rollout readiness and gating checks
- High-risk regressions that could change rollout decisions (latency tail, error rates, warm-start behavior)

**Out of scope**
- Deep debugging during the 30-minute slot (schedule a dedicated 60-minute deep dive with traces/logs preloaded)

## Decision gates (must pass to increase canary percentage)
### 1) Customer impact gates
Proceed only if all are true for the last 24 hours in each primary region (at minimum: us-west-2, us-east-1):
- **p99 latency:** ≤ **900 ms** for small-sequence workloads (median ~128 tokens) OR no more than **+20%** versus float32 control on matched traffic.
- **Error rate (5xx + timeouts):** ≤ **0.30%** and not increasing week-over-week.
- **Retry rate:** no anomalous increases attributable to quantized path.

Notes:
- The p99 tail is the primary customer-risk metric. If p99 is above gate but p50/p95 are healthy, treat as a hold condition and require a concrete remediation plan.

### 2) Capacity gates (Infra/SRE)
- Confirm **≥ 20% spare capacity** in the dedicated canary pool for the full rollout window.
- Confirm an **emergency scale** procedure is on-call owned and tested within the last 30 days.
- Confirm cluster autoscaling safeguards do not conflict with pinned canary nodes.

### 3) Observability gates (Runtime/SRE)
- 7-day latency histograms are available and reviewed (p50/p95/p99), segmented by:
  - region
  - workload size (short vs long sequences)
  - model variant (quantized v2 vs float32)
- Canary dashboards include:
  - token cost metrics (avg and distribution)
  - memory pressure signals (RSS, OOM events)
  - queueing time vs compute time breakdown
- Alerts exist and are actionable for:
  - p99 latency regression
  - warm-start throughput degradation
  - error rate spikes

### 4) Rollback and fallback gates (Console/Runtime)
- Rollback plan has been reviewed and is executable in **< 15 minutes**.
- Route-level fallback behavior is documented and tested:
  - Manual fallback to float32 variant is validated.
  - Auto-fallback is allowed only if telemetry is sufficient to avoid oscillation (see below).

## Known issues and current status
### RED-2147: HTTP/2 p99 latency spike
**Original symptom (observed early March):** p99 for small-seq workloads increased substantially under HTTP/2 traffic.

**Updated status (as of 2026-03-21):**
- Root cause narrowed to an HTTP/2 connection management interaction in the sidecar/proxy path.
- Mitigation implemented via runtime + proxy tuning; fix tracked in **GH PR 497**.
- Current p99 in us-west-2 for the same segment is down from the earlier peak and has been stable over the last 48 hours.

**Roundtable requirement:**
- Mikael (runtime) confirms the fix is in the candidate build for 0.9.3 and shares a short before/after comparison.

### RED-2199: KV cache invalidation after quantized warm-start
**Original symptom:** stalled throughput for multiple minutes after node restart.

**Updated status (as of 2026-03-21):**
- Instrumentation added for warm-start duration and cache rebuild time.
- Throughput drop duration reduced; remaining issue is variance during peak queue depth.

**Roundtable requirement:**
- Priya (runtime) confirms alerting thresholds and links to the dashboard panel used for the gate.

## Metrics snapshot (what to include in the roundtable pre-read)
Provide the following bullet summary (one line each) plus links to dashboards:
- **Latency (quantized v2 vs float32):** p50 / p95 / p99, by region
- **Cost:** avg token cost delta (target: negative) and any variance by workload class
- **Errors:** 5xx, timeouts, retries (absolute + change)
- **Stability:** OOMs, restarts, warm-start duration

Recommended one-liner format:
- "Canary A: token cost -20%, p50 +6%, p95 +9%, p99 +14% (stable), error rate 0.18% (flat), no new OOMs."

## Fallback policy (route-level)
### Policy intent
Fallback exists to preserve customer experience if the quantized path regresses (tail latency, errors) while limiting churn and avoiding oscillation.

### Current stance (updated)
- **Manual fallback:** Supported and required to be tested each rollout step.
- **Auto-fallback toggle:** Not GA by default until we have:
  1) per-route telemetry surfaced in Console (error/latency deltas), and
  2) a cooldown mechanism to prevent flip-flopping.

### Console requirements
- Add a route-level quick link to canary metrics (dashboard deep link).
- Display the current model variant and canary status on the route page.
