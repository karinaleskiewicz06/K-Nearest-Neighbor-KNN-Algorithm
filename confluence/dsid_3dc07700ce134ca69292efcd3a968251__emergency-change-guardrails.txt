Emergency change guardrails (SLO + error budget)

# Summary
These guardrails define how to make emergency changes safely during active incidents and/or while error budgets are constrained.

# Core principle
**Stabilize first, then optimize.** Prefer rollbacks and low-risk mitigations to large behavioral changes.

# Required monitoring checks (before + after any emergency change)
- Request success rate (2xx/5xx) by region for Hosted API
- p95 end-to-end latency by region
- Streaming disconnect rate
- Runtime crash-loop / restart rate
- GPU queue depth

# Risk tiers for emergency changes
- **Tier 0 (lowest risk):** rollback to last known good, turning off a feature flag, traffic shift within same model family
- **Tier 1:** runtime config changes that affect batching/caching limits
- **Tier 2:** code changes to scheduler/kernels; changing default kernel selection
- **Tier 3 (highest):** changes that affect request semantics, auth, billing, or cross-region routing

# Approval escalation by risk tier
- Tier 01: approvals per EPC policy (IC/SRE + Runtime/Platform)
- Tier 2: requires explicit Runtime EM approval in addition to IC/SRE approval
- Tier 3: requires VP Engineering (or delegate) approval unless it is a pure rollback

# Error budget constraints
If the Hosted API SLO error budget burn is above 2x normal (week-to-date):
- default to Tier 0 mitigations
- require canary in one cell for at least 10 minutes before expanding
- require explicit rollback readiness confirmation (tag + command)

# Change sequencing rules during active Sev1
1. Only one change in flight per region at a time (avoid confounding).
2. Every change must have a named owner and a named verifier.
3. Expand rollout only after the verifier states the gate metrics are improving or flat.

# Documentation requirements
- The incident timeline must capture the change time and observed effect
- EPC record must include: risk tier, approvals, and verification evidence
