Hotfix Build + Signing Procedure (Containers, SBOM, Provenance)

h2. Summary
This page defines how to build and sign production hotfix artifacts for Redwood services, with emphasis on the serving runtime. Hotfixes must meet supply-chain requirements even during incidents.

h2. Requirements
For any production hotfix artifact:
* Container image must be signed (cosign)
* SBOM must be generated and uploaded
* Provenance attestation must be generated (SLSA level target: L3)
* Artifacts must be stored in the production registry (no personal namespaces)

h2. Supported build pipelines
* GitHub Actions: 'release-hotfix.yml' in repo redwood
* Internal Buildkite: 'runtime-hotfix-build' (use only when GitHub Actions is degraded)

h2. Procedure (GitHub Actions)
1. Ensure PR is approved per emergency policy.
2. Add label: hotfix-ready
3. Trigger workflow: 'Release Runtime Hotfix'
4. Provide inputs:
   * base image tag (previous production runtime)
   * new tag suffix (e.g., hotfix-2026-02-02a)

Artifacts produced:
* ghcr.io/redwoodinference/runtime:<tag>
* SBOM: s3://redwood-release-artifacts/sbom/runtime/<tag>.json
* Provenance: s3://redwood-release-artifacts/provenance/runtime/<tag>.intoto

h2. Signing verification
Before rollout, verify signatures:
* cosign verify --key k8s://prod/signing/runtime ghcr.io/redwoodinference/runtime:<tag>
* cosign verify-attestation --type slsaprovenance ghcr.io/redwoodinference/runtime:<tag>

h2. Emergency exception handling
Exceptions are rare and require Security on-call approval recorded in the incident channel. Acceptable exception: temporary delay in SBOM upload *only* if the SBOM is generated and attached to the incident within 4 hours. Image signing cannot be skipped.
