External researcher GPU onboarding playbook

Purpose

This playbook documents the end-to-end process for onboarding external researchers and partner labs to Redwood internal GPU evaluation infrastructure. It covers access controls, Terraform/IaC patterns, network & egress constraints, budgeted billing, CI/CD sandboxing, telemetry requirements, and day-2 operations. This is intended for infra engineers, partner ops, and security reviewers.

Scope and assumptions
- Applies to temporary or recurring access granted to non-Redwood employees for research, benchmarks, or paid collaborations.
- Targets ephemeral evaluation pools and sandbox namespaces only. Production tenant enrollment follows the standard tenant onboarding flow.
- Assumes partner has signed the required MSA/NDA and a cost-bearing agreement (billing or credit).

High-level flow (summary)
1. Intake and legal clearance (People Ops / Finance)
2. Create partner account and allocate budget token (Billing)
3. Network scoping and egress policy construction (Cloud Networking)
4. Terraform-based sandbox provisioning (Infra)
5. CI/CD gating and image promotion (CI teams)
6. Observability, billing exports, and telemetry (Platform)
7. Day-2 support and offboarding (Oncall/Infra)

Ownership matrix
- Intake & contract validation: partnerships@ (Revenue Operations)
- Account creation & budget token: finance-ops@redwood.com
- Sandbox provisioning (IaC): eng-infra/team (owner: Eng Infra - Sandbox)
- Network & egress policy: eng-infra/cloud-accounts-and-networking
- Security review & approved controls: security@redwood.com
- Oncall / incident response: eng-sre oncall

Preflight checklist (must be complete before any provisioning)
- Signed MSA/NDA (Legal).
- Billing method (credit card, PO, or internal charge account) verified (Finance).
- Partner contact and technical lead identified with 2FA-enabled account (Partner Ops).
- Minimum acceptable security posture agreed: allowed IP ranges, data handling constraints, PII restrictions (Security).

Network and egress constraints (requirements table)
| Item | Required value / guidance | Owner |
| ----- | ------------------------ | ----- |
| VPC placement | Sandbox VPC (isolated tenant VPC peering) | Cloud Networking |
| Egress destinations | Only allow pinned egress set; block external code repositories unless pre-approved | Security/Networking |
| NAT / Proxy | All egress must traverse the partner egress proxy with per-tenant ACLs and request tagging (X-Partner-Id) | Cloud Networking |
| IP allowlist | Short-term allowlist (CIDR) for partner management hosts; no CIDR > /24 | Security |
| Private DNS | Split-horizon DNS for internal artifacts | Cloud Networking |

Terraform / IaC pattern (recommended)
- Use the sandbox-iac module: eng-infra/terraform-modules/sandbox-tenant (version pin required).
- Every partner environment must be created from a branch-based promotion flow: feature branch -> integration -> canary -> prod-like (sandbox).

Minimal Terraform snippet (example usage)
```hcl
module "partner_sandbox" {
  source  = "github.com/redwood-infra/terraform-modules//sandbox-tenant"
  version = "v1.4.2"

  partner_id        = "partner-acme-2026"
  budget_token      = "budget-acme-2026"
  region            = "us-west-2"
  allowed_cidrs     = ["203.0.113.0/28"]
  max_gpu_count     = 8
  tenancy_profile   = "ephemeral"
  egress_profile    = "pinned-proxy"
}
```

Terraform gating and CI/CD rules
1. All changes must be proposed via PR with the sandbox policy checks enabled (policy-as-code OPA checks).
2. Run the IaC simulator job (ci/infrastructure/sandbox-sim) to ensure no broad CIDR or wildcard IAM statements are introduced.
3. Terraform plan outputs must be attached to the PR and reviewed by the infra owner.
4. Promotion to the partner sandbox requires a signed approval from both the Cloud Networking and Security reviewers.

Quota and billing model
- Default quota: 8 GPUs concurrently per partner (burst request to 16 subject to approval).
- Per-minute billing exported to finance exports under tag partner:partner-acme-2026.
- Budget token enforcement: a cloud lambda monitors the burn rate and triggers soft-eviction at 85% of monthly budget and hard-eviction at 100%.

Quota table (example)
| Metric | Default | Burst (approval) |
| ------ | -------:| ----------------:|
| GPUs | 8 | 16 |
| vCPUs | 64 | 128 |
| Storage (ephemeral) | 1 TB | 2 TB |

Telemetry & SLOs (what to collect)
- Metrics: GPU utilization, enqueue latency (ms), p95 token latency, pod restart count, egress request count per external host, billing burn-rate.
- Logs: audit logs for IAM actions, provisioning events, user SSH access (if allowed), and egress proxy logs with X-Partner-Id tag.
- Alerts: budget_burn_rate > 0.85 (warning), gpu_eviction_triggered (critical), network_blocked_egress_attempts > 10/min (warning).

Security controls (mandatory)
- No persistent PII should be processed unless expressly allowed in the contract.
- Partner accounts are provisioned under a short-lived role: partner_<id> with STS-backed ephemeral credentials (max 24h).
- All SSH access to nodes is disabled by default; jump-hosting via bastion with session recording is allowed only with Security approval.
- Container images must come from a Redwood-approved registry sign-signed using the internal supply-chain signer. CI will reject unverified images.

Day-2 operations and runbook snippets
- Routine maintenance window: weekly Tuesday 0200-0400 UTC. Notify partner 72 hours in advance.
- If a partner reports degraded performance:
  1) Check the partner-specific dashboard: infra.sandbox.metrics/partner-acme-2026 (owner: Eng Infra).
  2) Verify GPU utilization and OOM events.
  3) If enqueue latency high and GPUs saturated: scale up (if budget available) using the autoscaler: infra-cli partner scale --id partner-acme-2026 --gpus +2
  4) If billing soft-eviction is active, contact finance and partner to top up or request a temporary increase.

Incident escalation matrix (high level)
- Sev3 (performance regression, single-user impact): oncall infra -> engage eng-sre -> notify partner technical lead.
- Sev2 (widespread degradation or egress policy failures): paged eng-sre -> page Cloud Networking -> security@ if traffic deviates.
- Sev1 (data exposure or major compromise): immediate security@alert, exec-notify, isolate VPC, revoke partner credentials.

Offboarding procedure (automated + manual)
1. At contract end: set a scheduled job to disable new job submissions at T-7 days.
2. Run a snapshot job: create a transient snapshot of ephemeral storage for customer retrieval for 14 days.
3. Revoke all partner roles and rotate shared secrets.
4. Retain billing archives for 12 months (Finance).
5. Run a network sweep to remove allowlist entries.
6. Delete sandbox resources via: infra-cli partner destroy --id partner-acme-2026 --confirm.

Safety checks and common pitfalls
- Don’t grant persistent IAM roles or cross-account full-access to external partners.
- Be cautious with wide CIDR ranges and public ECR/Container access.
- Ensure OPA policy checks are not bypassed in the CI pipeline — a common failure mode is stale policy versions.

Appendix A: Example commands
- Provision: infra-cli partner create --id partner-acme-2026 --profile sandbox --region us-west-2
- Scale: infra-cli partner scale --id partner-acme-2026 --gpus 4
- Evict workloads (emergency): infra-cli partner evict --id partner-acme-2026 --reason "budget-overrun"

Appendix B: Minimal audit checklist for Security reviewer
- Confirm STS role duration <= 24 hours.
- Verify egress proxy filters and per-tenant logging.
- Check that images are signed and registry ACLs are scoped.
- Ensure bucket policies for snapshots do not allow public access.
