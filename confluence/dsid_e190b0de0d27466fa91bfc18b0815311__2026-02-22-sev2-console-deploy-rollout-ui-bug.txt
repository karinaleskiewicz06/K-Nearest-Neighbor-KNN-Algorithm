Postmortem: SEV-2 Console rollout UI bug triggered rollback loop (2026-02-22)

A Console UI change caused repeated client-side retries on a non-idempotent rollback endpoint, putting rollouts-service into a rollback loop for a subset of deployments.
Operators could not reliably pause or promote canary rollouts via Console. Some actions displayed as successful but were not applied, leading to confusion and delayed mitigations for unrelated rollouts.
19:05 UTC: Internal user reported Console rollout controls unresponsive.
19:10 UTC: Eng on-call saw elevated 5xx and increased write QPS to rollouts-service.
19:20 UTC: Isolated to Console release 2026.02.22.2 with a new retry wrapper.
19:28 UTC: Disabled feature flag for retry wrapper in prod.
19:40 UTC: Rollouts-service write QPS returned to normal; rollback loops stopped.
19:58 UTC: Incident resolved.
The Console’s new retry wrapper treated 409 conflict responses as retryable and retried POST /rollback automatically. The endpoint was not idempotent and could re-trigger rollback actions.
Internal report and rollouts-service error/QPS alerts.
Disabled the retry wrapper via feature flag and added a server-side idempotency key requirement for rollback actions.
Feature flag allowed immediate mitigation. Service-level alerts were actionable.
The UI change was not tested against the real rollouts-service conflict behavior; endpoint idempotency was assumed but not documented.
Document idempotency requirements for rollouts-service endpoints (Platform Engineering; due 2026-03-10).
Add integration tests in Console CI that simulate 409 and ensure no retries on non-idempotent endpoints (Console & Tooling; due 2026-03-15).
Introduce a standard client retry policy library with an allowlist of safe endpoints (DevEx; due 2026-04-01).
