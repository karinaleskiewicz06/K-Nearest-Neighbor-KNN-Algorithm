Tenant GPU Network Onboarding and IaC Patterns

Summary
-------
This doc prescribes a repeatable onboarding pattern for new tenant teams that require dedicated GPU capacity, VPC connectivity, and Terraform-managed resources. It unifies network topology choices, account boundaries, and CI/CD patterns so infra and platform teams can provision, observe, and operate tenant GPU pools with predictable security and cost controls.

Scope
-----
- New tenant accounts requesting Dedicated GPU pools (G4/RTX, A100, H100) behind Redwood’s shared networking guardrails.
- Cross-account VPC peering / PrivateLink patterns for control-plane integration.
- Terraform module usage, remote state strategy, and CI/CD pipeline templates.
- Day-2 runbook highlights (capacity alerts, maintenance, reclaiming idle nodes).

Goals and non-goals
-------------------
- Goals:
  - Secure network isolation while allowing management/control-plane traffic from Redwood control accounts.
  - Standard IaC modules with clear inputs/outputs for GPU node pools, SGs, subnets, and cross-account IAM.
  - Minimal manual steps to go from request -> provisioned pool (target TTM: 2 business days).
- Non-goals:
  - Detailed tuning of model-serving runtime (covered in eng-serving-runtime/docs).

Motivation
----------
Previously we saw ad-hoc account setups that caused inconsistent egress rules, duplicated NAT gateways, and manual IAM exceptions. Those patterns increased blast radius and delayed onboarding. This document standardizes a secure, repeatable workflow that:
- Reduces network complexity by providing a curated VPC pattern.
- Enforces remote-state and locking conventions to prevent accidental drift.
- Integrates autoscaler and cost metrics into observability pipelines.

High-level network topology
--------------------------
The recommended topology uses a tenant VPC with dedicated private subnets for GPU hosts, egress through a shared NAT/egress VPC managed by infra, and a control-plane peering link to the Redwood management VPC.

ASCII Diagram:

  Tenant Account VPC                      Redwood Control VPC
  ------------------                      --------------------
  | Private Subnet | <--- VPC Peering ---> | Management Subnet|
  | GPU Hosts (ASG)|                       | Validator, STS    |
  ------------------                      --------------------
           |                                     |
           +--> Route to Shared Egress VPC (NAT)  +--> Monitoring/Tracing

Subnet and routing table summary:
| Name                    | CIDR         | Purpose                          |
|-------------------------|--------------|----------------------------------|
| private-gpu-subnet      | 10.40.32.0/19| GPU instance tenancy, no public IP|
| management-subnet       | 10.40.64.0/26| Jumpbox, kube-control-plane VPN  |
| shared-egress-subnet    | 10.50.0.0/22 | NAT gateway & egress e2e policies |

Security controls and SLOs
--------------------------
- Security groups:
  - sg-gpu-node: allow 22 (restricted), 443 to control-plane CIDRs, health-check ports 9090/9100 only from infra monitoring account.
  - sg-ctrlplane: allow ingress from Redwood control VPC on TLS port 443 and management ports (2022).
- Egress rules: deny 0.0.0.0/0 by default; allow via shared egress VPC and enforced proxy (outbound-allow-list).
- SLOs and thresholds (for provisioning flow):
  - Provision success within 4 hours (automation); manual fallback within 2 business days.
  - GPU node provisioning failure rate < 3% per month.
  - Idle GPU reclaim threshold: 72 hours of < 5% utilization triggers alert.

Terraform module surface and conventions
--------------------------------------
We provide a small catalog of modules in modules/ (monorepo):
- modules/vpc-tenant (inputs: cidr_block, management_cidrs, tags; outputs: vpc_id, private_subnet_ids)
- modules/gpu-node-pool (inputs: instance_type, desired_capacity, max_capacity, ssh_key, ami_id, subnet_ids; outputs: asg_id, launch_template_id)
- modules/iam-cross-account (inputs: principal_account_ids, role_name_suffix; outputs: role_arn)
- modules/egress-endpoint (creates S3/STS VPC endpoints and NAT route to shared egress)

Conventions:
- Module variables must be typed and documented. Use explicit lists/maps, avoid dynamic interpolation of region/account in module root.
- All modules return a "name_tag" output for standard tagging (team, tenant, env).
- State: use encrypted S3 bucket with per-tenant prefix and DynamoDB lock table. Naming: state-redwood-infra-<aws-account-id>-<env>.

Remote state pattern
--------------------
- Each tenant account maintains a single Terraform workspace per environment (dev/stage/prod).
- Remote state keys: tenant/<tenant-id>/<env>/<component>.tfstate
- Access control: cross-account IAM role with least privilege for the pipeline service account to read/write state. See IAM example below.

CI/CD pipeline blueprint (recommended)
-------------------------------------
- Repository layout:
  - infra/<tenant-id>/main.tf (module calls)
  - modules/* (shared modules)
- Pipeline stages (CI):
  1. fmt & validate (terraform fmt, tflint, checkov)
  2. plan (terraform plan -out=plan.tfplan) with a PR comment from the pipeline including a plan summary and diff
  3. apply (manual approval for prod, auto for dev/stage) - terraform apply plan.tfplan

Example GitHub Actions snippet (high-level):
```yaml
name: terraform
on: [pull_request, push]
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v2
      - run: terraform fmt -check
      - run: tflint --module
  plan:
    runs-on: ubuntu-latest
    needs: validate
    steps:
      - uses: actions/checkout@v3
      - run: terraform init -backend-config=\"key=tenant/${{ matrix.tenant }}/prod/infrastructure.tfstate\"
      - run: terraform plan -out=plan.tfplan
      - run: terraform show -json plan.tfplan > plan.json
      - run: ./scripts/post-pr-plan-comment.sh plan.json
```

IAM examples (cross-account role)
--------------------------------
Terraform pseudo-snippet for the role (high level):
```hcl
resource "aws_iam_role" "pipeline_state_writer" {
  name = "redwood-terraform-writer-${var.tenant_id}"
  assume_role_policy = data.aws_iam_policy_document.pipeline_assume.json
}

data "aws_iam_policy_document" "pipeline_assume" {
  statement {
    principals {
      type = "AWS"
      identifiers = ["arn:aws:iam::${var.pipeline_account_id}:role/ci-pipeline-executor"]
    }
    actions = ["sts:AssumeRole"]
  }
}
```

Onboarding procedure (step-by-step)
-----------------------------------
1. Request intake: tenant files onboarding form (Confluence template) with expected vCPU/GPU, disk, and region. Owner: Customer Infrastructure (infra-request).
2. Account creation: platform creates tenant AWS account and seeds SSO groups. Owner: cloud-accounts team.
3. Network bootstrap: run bootstrap pipeline which invokes modules/vpc-tenant and modules/egress-endpoint. Outputs: vpc_id, private_subnet_ids. Owner: infra automation.
4. GPU pool deploy: tenant infra repo references modules/gpu-node-pool; pipeline runs plan/apply. Owner: tenant team with infra review.
5. Control-plane peering and IAM: modules/iam-cross-account creates role for control-plane. Infra validates and approves peering.
6. Observability and alerting: enable node prometheus exporters and forward metrics to central Prometheus/Thanos. Alert: GPUIdle > 72h triggers ticket to tenant.

Day-2 runbook highlights
-----------------------
- Capacity alerts:
  - Metric: gpu_utilization_percent (per-host average). Alert at < 10% for 72h labelled "gpu-idle". Play: Notify tenant, propose scale-down or autoscaler adjustment.
- Node provisioning failures:
  - Check AMI compatibility (kernel modules), subnet ENI limits, available instance quota in account. Commands: aws ec2 describe-instances, aws service-quotas get-service-quota.
- Re-image/upgrade nodes:
  1. Cordone node from ASG: kubectl drain <node> --ignore-daemonsets --delete-local-data
  2. Update launch template AMI and perform rolling restart via ASG with maxUnavailable=1

Cost and quota governance
-------------------------
- Per-tenant monthly GPU quota is enforced via Service Quotas and an automated quota monitor that raises a Slack notification when usage reaches 80% of quota.
- Billing tag enforcement: every GPU instance must be tagged with {tenant, team, project, cost_center}. A nightly job rejects untagged resources.

Troubleshooting checklist
-------------------------
1. Networking: verify routes in tenant route tables to the shared-egress VPC and peering status (aws ec2 describe-vpc-peering-connections).
2. IAM: confirm pipeline role can assume the tenant state role (aws sts assume-role --role-arn <role_arn>).
3. ENI limits: check account limits (aws ec2 describe-account-attributes / service-quotas).
4. Node startup logs: SSM session to instance, check cloud-init logs (/var/log/cloud-init.log).
