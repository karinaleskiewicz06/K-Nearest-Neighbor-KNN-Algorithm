Modular GPU Landing Zone Patterns — IaC, CI/CD and Egress Fencing

Summary

This document defines recommended patterns for provisioning modular GPU landing zones using Terraform modules, gating CI/CD pipelines for secure promotion, and implementing egress-fencing to control cross-account/Internet egress for inference workloads. The goal is to standardize multi-account onboarding for teams that require GPU capacity while minimizing blast radius, ensuring predictable egress billing, and enabling safe CI/CD promotion of GPU images and IaC changes.

Why this matters

- GPU resources are high-cost and multi-tenant by nature; inconsistent network/egress controls quickly create cost and security risk.
- A modular landing-zone approach lets teams self-serve while keeping account and network invariants enforced centrally.
- Tight CI/CD gates prevent poorly scoped Terraform changes from opening egress or escalating IAM.

Scope and assumptions

- Applies to new or migrating GPU tenant accounts (cloud accounts or cloud projects).
- Assumes central cloud-ops ownership for root landing-zone modules; tenant teams own per-tenant overlays.
- Covers: Terraform module patterns, IAM and tagging conventions, VPC and egress design, CI/CD gating (pipeline templates), and an operational runbook for common failure modes.

Desired invariants

1) Every tenant GPU account must have a standardized VPC and subnet naming convention.
2) All outbound traffic must traverse a controlled egress path (NAT/Proxy/PrivateLink) with cost accounting tags.
3) GPU pools are represented as explicit IaC resources with immutable identifiers and lifecycle policies.
4) CI/CD can only promote image or IaC changes after automated security and quota checks pass.

High-level pattern overview

- Central modules (owned by cloud-ops): account-bootstrap, shared-network, egress-gateway, iam-foundations.
- Tenant modules (consumed by product/platform teams): gpu-pool, tenant-network-overlay, batch-scheduler-config.
- CI/CD template: lint -> terraform plan (with policy checks) -> image build -> canary apply -> automated tests -> promote.

Module contract examples

The following table shows the recommended surface for two key modules (expressed in prose):

- module.account-bootstrap: inputs — account_id, billing_tag, allowed_regions (list), uat_flag (bool); outputs — management_vpc_id, account_role_arn.
- module.gpu-pool: inputs — pool_name, instance_family (string), gpu_count, node_taint_map (map-like string JSON), subnet_ids (list), max_spot_percentage; outputs — autoscaling_group_id, node_group_tags.

Naming and tagging conventions

- Resource names: rwd-{env}-{team}-{resource}, e.g., rwd-prod-search-gpu-pool-1.
- Tags: {owner, cost_center, workload, confidentiality, environment, created_by}.
- All tags must be enforced by a terraform pre-commit policy and validated in CI.

Network and egress patterns

1) Egress gateway per account or per-region (depends on scale): NAT gateway + proxy fleet or a managed egress appliance.
2) Default rule: all subnet outbound goes to egress-gateway; Internet access from compute nodes is blocked by default.
3) PrivateLink endpoints are used for critical services (S3, image registry, telemetry) to avoid Internet egress when possible.
4) Egress cost accounting: impose per-tenant egress buckets using flow logs metadata and active tagging on egress gateway.

# pseudo-YAML for egress-gateway-policy
allowed_destinations:
  - name: s3_private_link

CI/CD pipeline template (concise)

1) PR opened -> terraform fmt & validate -> static policy checks (sentinel/opa/policy-as-code) -> unit tests for modules.
2) terraform plan (in a sandbox account) with drift detection checks (compare to state referenced in central registry).
3) Image build stage: build GPU AMI/container image in a restricted build account with SBOM generation.
4) Canary apply: apply changes to a single small canary sandbox with temporary labels and run integration smoke tests (health checks, egress path validation, cost tags).
5) Approval gate: automated checks + human reviewer sign-off for iam/egress/network changes.
6) Promote: apply to target tenant accounts via cross-account CICD runner with least-privilege deploy role.

Example pipeline snippet (GitLab/GitHub Actions style, pseudo-YAML)

- name: terraform-plan-sandbox
  uses: actions/checkout@v3
  steps:
    - run: terraform init -backend-config="bucket=rwd-terraform-state-sandbox"
    - run: terraform plan -out=plan.tfplan
    - run: opa test policies || exit 1

Security and IAM guardrails

- Principle: Terraform modules must not create wildcard principals or grant broad iam:PassRole by default.
- Use a central iam-foundations module that exposes well-scoped roles: rwd-deploy, rwd-readonly, rwd-network-admin.
- All ephemeral CI runners assume a short-lived role via OIDC; long-lived keys are prohibited for deployment.

Cost and quota controls

- Enforce quota guardrails in Terraform module (max_gpus_per_pool, max_ondemand_percentage).
- CI pipeline includes quota-check step that queries a central capacity API and fails plan if requested resources exceed soft quota.
- Billing tags emitted at resource creation, and egress gateway injects tenant_id into flow log records for post-hoc allocation.

Operational runbook (top-level)

When a tenant reports unexpected egress charges:

1) Runbook step 1: Identify source — query egress-gateway flow logs, filter by tenant tags and time.
2) Step 2: Correlate with recent Terraform changes or CI deploys (link to pipeline run ID).
3) Step 3: If traffic originates from new container image, revert to previous image SHA via CI rollback.
4) Step 4: If from policy misconfiguration, apply emergency rollback patch to network ACLs using the pre-approved emergency role.

Terraform testing and validation guidance

- Unit tests: terratest or kitchen-terraform for resource-level checks.
- Policy-as-code: OPA + Conftest for deny-lists (open egress, unfriendly tags).
- Integration: Automated canary apply in a sandbox with synthetic traffic that validates egress path and metrics.

Migration path for existing accounts

- Phase 1: Inventory current GPU resources and egress paths (use the inventory module).
- Phase 2: Pilot by creating a landing-zone overlay in a single target account and migrating one low-risk service.
- Phase 3: Backfill tags and enforce network ACLs; iterate to lock down proxies and PrivateLink.
- Phase 4: Full migration with scheduled maintenance windows and communication plan.

Ownership and SLAs

- Cloud-ops: maintain central modules, egress gateway, and policy-as-code.
- Tenant teams: own gpu-pool module inputs, workload tagging, and canary test suites.
- SLOs: egress-gateway availability 99.95% (regional), terraform-promote lead time 15 minutes (target for small changes).

Acceptance checklist for a landing-zone PR

- [ ] Terraform fmt & validate OK
- [ ] OPA/Conftest pass (no allow-list violations)
- [ ] Quota check against capacity API OK
- [ ] Tagging enforced and present
- [ ] Canary smoke tests pass
- [ ] Reviewer sign-off for iam/network changes

Notes and open decisions

- Decision: per-account vs per-region egress gateways depends on anticipated egress volume (TBD metric: >50TB/month triggers per-region gateway).
- Open: automate automatic downscaling of canary nodes after validation to reduce test cost.
